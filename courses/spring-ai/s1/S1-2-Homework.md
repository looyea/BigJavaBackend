# 作业题 · Tool/Function Calling 与 Agent 编排

## 作业 1：单工具往返观测（必做）

注册 `queryOrder(orderId)` 工具，问一个必须查库才能回答的问题：

- 打开日志，完整记录：带工具清单的请求 → 模型返回 tool call（名称+参数 JSON）→ 服务端执行 → 回喂结果 → 最终答案
- 数一数这个问答一共发生了几次模型调用

**产出**：一次 tool calling 的完整消息序列图（system/user/tool/assistant）。

## 作业 2：写工具 + 幂等 + 人在环（必做，本节核心）

给退款场景做一个 `refund(orderId, amount)` 写工具：

1. 不加防护，构造诱导让模型重复调用，观察可能重复退款风险
2. 加幂等键（同一 orderId+amount 只生效一次）+ 超过阈值金额需人工确认（先返回"待确认"，不直接执行）
3. 服务端对参数二次校验（订单归属、金额上限），拒绝模型给的越权参数

**验收标准**：同一退款请求被模型发起两次只产生一次实际退款；越权参数被拒。

## 作业 3：两步 ReAct 与终止上限（必做）

实现"查未发货订单→逐个催发货"的两步 Agent：

- 设最大步数=4、总超时；构造一个让模型反复兜圈的场景，验证被步数/超时截断并优雅降级回答
- 对可并行的多个催发调用改为并行（`@Async`/虚拟线程），对比耗时

## 作业 4：工具描述 A/B（选做，架构师向）

同一任务下，先给模糊 description 的工具集、再给精修（含前置条件/单位/可空）的版本，各测 20 个问题，统计工具选对率与参数正确率，量化"描述即提示"的收益，形成你团队的工具书写规范。

## 作业 5：多 Agent 编排设计（选做，架构师向）

为"电力故障工单智能处理"设计一套编排：分诊 Agent（判断类型）→ 知识检索 Agent（RAG，见 s2-1）→ 处置建议 Agent → 高危操作人工确认节点。画出状态机，标注每个 Agent 的工具集、最大步数、成本预算、失败与升级路径，说明为什么高危动作必须留在人在环里。
