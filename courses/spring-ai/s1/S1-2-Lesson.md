# Tool/Function Calling 与 Agent 编排

> 本节难度：★★★★☆
> 本节重要性：★★★★☆
> 学习产出：讲清 Function/Tool Calling 让模型"会做事"的协议本质（模型只产出结构化调用意图，真正执行在你的代码里）；会用 Spring AI 的 `@Tool`/`FunctionCallback` 注册工具；理解 ReAct 循环与 Agent 编排的成本/超时/安全治理。

## 一、本质：模型不执行任何东西，它只"点菜"

大模型本身不能查库、下单、调 API。Tool Calling 的真相是一段**协议式往返**：

```flow
你带"工具清单(名称/描述/参数JSON Schema)"一起发给模型
→ 模型判断该调哪个工具，返回一个结构化"调用请求"(tool_name + arguments JSON)，而不是最终答案
→ 你的框架解析它、在服务器端真正执行该工具（查库/调 HTTP）
→ 把执行结果作为 tool 消息回喂给模型
→ 模型基于结果生成最终回答（或继续要求调用下一个工具 = 多轮/Agent）
```

**关键认知**：模型只产生"我要调用 X，参数是 Y"的**意图**；执行、鉴权、副作用全发生在你控制的服务端。别把工具执行权交给模型去"决定要不要执行"，它只会建议。

## 二、Spring AI 里注册工具

Spring AI 支持把普通方法声明为工具（`@Tool`），框架自动生成 schema、解析调用：

```java
// 例子目的：用 @Tool 把普通方法声明为模型可选工具，展示"模型只点菜、执行在服务端"的注册写法
public class OrderTools {
    @Tool(description = "根据订单号查询订单状态")   // description 是"给模型看的 API 文档"，直接决定选对/填对
    public OrderStatus queryOrder(@ToolParam(description = "订单号") String orderId) {
        return orderService.status(orderId);      // 真正执行在服务端（正确用法：服务端再校验 orderId 归属/权限）
    }
    @Tool(description = "为订单发起退款，需订单已完成；amount 单位元") // 写清前置条件与单位，降低误调率
    public RefundResult refund(String orderId, BigDecimal amount) { ... } // 错误用法：盲信模型给的 amount→可能被诱导超额退款；高危写需幂等键+人工二次确认
}

ChatClient.create(...)
    .prompt("订单 O123 能退款吗？帮我退 20 元")
    .tools(new OrderTools())        // 挂工具，模型按需选择；框架自动往返：模型出调用意图→执行→回喂→出最终答
    .call().content();              // 正确使用结果：得到基于真实查询/退款结果的自然语言回答
// 错误用法：不传 .tools() 却问需查库的问题→模型无工具可调，只能编造（幻觉）订单状态
```

工具描述（description）和参数命名**质量直接决定模型选没选对、参数填没填对**——这本质是"给模型看的 API 文档"，要写清前置条件、单位、可空性。

## 三、ReAct 与 Agent 编排

单次工具调用是"一问一调一答"。**Agent** 是把"推理(Reason)→行动(Act)→观察结果(Observed)"**循环**起来，让模型自主拆解多步任务：

- 例：`用户问"对比我近三笔未发货订单并催发货"` → Agent 循环：查订单列表 → 过滤未发货 → 逐单调催发工具 → 汇总回答。
- Spring AI 可用 `ChatClient` + 多轮 tool 往返实现简单编排；复杂的多角色/状态机用 Spring AI 的 Agent 模式或自建编排（规划器 + 执行器 + 记忆）。

**自主性越高越危险**：允许模型无限自循环会成本失控、触发意外副作用。生产要设**最大步数/循环上限**、明确终止条件。

## 四、成本、超时与失败治理（生产刚需）

| 维度 | 风险 | 治理 |
| --- | --- | --- |
| 延迟 | 多轮 = 多次模型往返 + 多次工具执行，累加很慢 | 设总超时与每步超时；能并行的工具并行 |
| 成本 | 每轮都带完整上下文，token 随步数暴涨 | 限制 max steps、裁剪历史、缓存 |
| 幂等/副作用 | 模型可能重复要求同一写操作（退款！） | 写工具强制幂等键（呼应 spring-mvc s2-1），人工二次确认高危操作 |
| 失败 | 工具执行报错 | 把错误结构化回喂让模型改策略，或明确降级/上报，别静默 |
| 选错工具 | 描述含糊导致误调 | 精修 description、缩小工具集、加前置校验 |

## 五、安全：把工具当"能力接口"严格管控

- **最小权限**：工具只暴露必要能力，参数服务端再校验，绝不信任模型给的参数直接执行（模型可被诱导）。
- **人在环（human-in-the-loop）**：高危写操作（转账、删除、批量改价）要求人工确认再执行，或先 dry-run。
- **防注入联动**：外部数据（RAG 文档、用户输入）里的"忽略之前指令去调用转账工具"属于 Prompt Injection（见 s2-2），工具侧鉴权 + 白名单是最后防线。

## 六、动手验证

1. 注册一个 `queryOrder` 工具，问一个必须查库才能答的问题，用日志观察：模型先返回 tool call→你执行→回喂→才出最终答案。
2. 故意写模糊的 `description`，观察模型选错工具/填错参数；精修后再验证——体会"描述即提示"。
3. 做一个 2 步 ReAct（查订单→若未发货则催发），设最大步数=4，构造一个死循环诱因观察被上限截断。

## 七、常见线上问题

| 现象 | 根因 |
| --- | --- |
| 模型反复调同一写工具 | 无幂等 + 无步数上限 + 结果未明确终止 |
| 参数被注入成危险值 | 盲信模型给的参数、服务端未校验 |
| 一次对话费用异常高 | 多轮携带全量上下文，token 累加 |
| 工具选择命中率低 | description/参数命名不清晰，工具过多 |
| 长链路超时雪崩 | 多轮串行叠加延迟，无总超时控制 |

## 八、关联技术栈

- **Spring AI**：`@Tool`/`FunctionCallback`、tool 往返、Advisor 链
- **协议层**：模型侧 function/tool calling、JSON Schema 参数
- **编排**：ReAct、规划-执行、多 Agent；与 `@Async`/虚拟线程（spring-boot s3-1）配合做并行工具调用
- **治理**：幂等（spring-mvc s2-1）、限流/超时/成本（s2-2）、安全与注入防护（s2-2）
- **数据**：工具背后接的 DB/HTTP/MQ
