# 实际面试题 · ChatClient、Prompt 模板与结构化输出

## 题 1：为什么用 Spring AI，而不是直接调 OpenAI 的 SDK？

**考察层次**：初级"方便"；中级能讲可移植与生态整合；高级能讲抽象的代价。

**参考答法**：

1. 可移植：`ChatClient`/`EmbeddingModel`/`VectorStore` 是门面，换厂商主要改依赖+配置，降低锁定。
2. Spring 化体验：自动配置、依赖注入、`Advisor` 链（记忆/RAG/日志横切）、与 Boot 的 Actuator/安全/配置体系天然集成。
3. 统一范式：结构化输出、函数调用、评估等在多模型上一致的 API。
4. 代价：抽象可能滞后于某厂商新特性、排障多一层；对追新单厂商极致能力时需评估是否绕过抽象。

**追问**：抽象会损失厂商独有能力吗？→ 可能，Spring AI 一般通过 options/扩展暴露，新特性有跟进时差，选型要权衡。

## 题 2：怎么让大模型稳定返回你能直接用的 Java 对象？

**答题要点**：用 `BeanOutputConverter`/`.entity()`——它按目标类型生成 JSON Schema 追加进提示，约束模型输出 JSON，再反序列化为 POJO。健壮性关键：① 提示明确"只输出 JSON"；② 用 record/清晰字段；③ schema 尽量扁平简单；④ 必须对非法/缺字段做重试与降级（模型不保证 100% 守约）；⑤ 记录原始返回便于排障。

## 题 3：`call()` 和 `stream()` 分别适合什么场景？流式怎么落地到前端？

**答题要点**：`call()` 适合后端批处理、工具链中间步骤（要完整结果再决策）；`stream()` 适合面向用户的对话式 UI，首字延迟低、体验好，返回 `Flux<String>`。落地：WebFlux/SSE 把 token 增量推给前端（呼应 spring-mvc s2-2），注意超时、断线重连、以及计费按最终 token。CPU/网络要在流式里正确取消（用户关页面要 cancel Flux，避免继续烧 token）。

## 题 4：提示词工程在你的服务里怎么做到可维护、可回滚？

**结构化回答（架构视角）**：

1. 提示词是**资产不是字符串**：外置到模板（`PromptTemplate`）+ 版本化（Git 或配置中心），支持灰度与回滚。
2. 分层：system 定规则/人设、few-shot 示例、user 本轮输入，检索上下文单独注入（RAG）。
3. 约束 token 预算：上下文裁剪、最大输出，避免无界拼接把成本和上下文窗口打爆。
4. A/B 与评估：多版本并行，用评估集（见 s2-2）离线打分 + 线上指标，再放量。

## 高频追问速答

1. System / User / Assistant 消息有什么区别？→ System 定行为最稳、优先级高；User 本轮输入；Assistant 模型历史回复（多轮靠回传历史消息）。
2. 多轮对话记忆怎么实现？→ 把历史 messages 回传，或用 Spring AI 的 `MessageChatMemoryAdvisor` + ChatMemory 存储，避免每轮全量塞。
3. 温度（temperature）设多少？→ 抽取/结构化用低（≈0）求稳定，创意生成用高；结构化输出务必调低。
4. `.entity()` 失败最常见原因？→ 模型输出了 JSON 以外的解释文字或字段类型不符，靠"只要 JSON"+重试+宽松解析缓解。
5. Spring AI 一定联网用云端模型吗？→ 不，可接本地 Ollama/vLLM 等，满足数据不出域（金融/电力合规常见诉求）。
