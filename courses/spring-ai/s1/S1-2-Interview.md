# 实际面试题 · Tool/Function Calling 与 Agent 编排

## 题 1：大模型是怎么"调用函数/工具"的？它自己能执行代码吗？

**考察层次**：初级以为模型会执行；中级能讲协议往返；高级能讲治理与安全边界。

**参考答法**：

1. 模型不能执行任何东西。你把工具清单（名称、描述、参数 JSON Schema）随请求发给它，它若判断需要，就返回一个结构化的"调用意图"（tool_name + arguments），而不是最终答案。
2. 你的框架解析这个意图，在**服务端**真正执行工具（查库、调 API），把结果作为 tool 消息回喂给模型。
3. 模型基于结果生成最终回答，或继续要求调用下一个工具（多轮 = Agent 的基础）。
4. 所以执行权、鉴权、副作用控制全在服务端，模型只是"点菜"。

**追问**：Spring AI 里怎么接？→ `@Tool` 标注方法或注册 `FunctionCallback`，框架自动生成 schema、解析调用、回喂，挂到 `ChatClient.tools(...)`。

## 题 2：Agent 和普通的一次 tool calling 有什么区别？

**答题要点**：一次 tool calling 是"一问一调一答"。Agent 把 ReAct（推理→行动→观察）循环起来，让模型自主把复杂任务拆成多步、连续调用多个工具直到完成。自主性带来能力也带来风险：必须设最大步数、总超时、成本预算、终止条件，否则自循环烧钱且可能触发意外副作用。

## 题 3：让模型自动执行退款/转账这类写操作，你敢吗？怎么设计才安全？

**结构化回答（架构师必答题）**：

1. 绝不无约束自动执行。分层防护：① 服务端对模型给的参数二次校验 + 鉴权（不信任模型输出，可被注入诱导）；② 写操作强制幂等键防重复；③ 高危/超阈值操作走 human-in-the-loop（先 dry-run/待确认，人批准再执行）；④ 工具最小权限、白名单。
2. 审计：每次 tool 调用（意图、参数、结果、发起人）全量留痕。
3. 兜底：限步数/超时/成本，异常结构化回喂或降级到人工。
- 结论：模型负责"决策建议"，能不能落地由你的安全边界说了算。

## 题 4：多 Agent 系统延迟和成本很高，怎么优化？

**答题要点**：

- 结构：能一次工具调用解决的别上 Agent；能并行的小步骤并行化（虚拟线程/`@Async`）；用较小/便宜模型做分诊、规划，只在必要环节用大模型。
- 上下文：每轮带全量历史是成本主因——裁剪/摘要历史、复用缓存、限制最大步数。
- 观测与预算：给每个 Agent/会话设 token 与费用预算、埋点（呼应 s2-2），超阈值熔断。

## 高频追问速答

1. 工具太多模型选不准怎么办？→ 缩小/分组工具集、精修 description、检索式先选子集再给模型、必要时路由 Agent。
2. 模型幻觉出一个不存在的工具/参数怎么办？→ schema 校验严格拒绝、服务端不信任、把校验错误回喂纠偏。
3. function calling 和 JSON 结构化输出区别？→ 前者是"要不要调用外部能力"的协议往返；后者只是把回答约束成 JSON（s1-2），不涉执行。
4. 并行工具调用是什么？→ 模型一次返回多个待执行 tool call，框架并发执行后一起回喂，降低串行延迟。
5. Agent 的记忆从哪来？→ 短期靠会话 messages/ChatMemory，长期靠向量库/RAG（s2-1）持久化与检索。
