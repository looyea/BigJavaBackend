# 实际面试题 · RAG：切分、Embedding 与召回

## 题 1：RAG 的完整流程讲一下，效果不好你会从哪些环节排查？

**考察层次**：初级只会说"检索+生成"；中级能拆离线/在线两线；高级能按环节定位瓶颈并给增强手段。

**参考答法**：

1. 离线：文档 → 解析 → 切分 → 向量化 → 存 VectorStore（含元数据）。
2. 在线：问题向量化 → 相似召回 TopK →（混合检索/重排）→ 拼进 Prompt → LLM 生成带引用答案。
3. 效果差按层排查：① 召回没命中（切分不当/阈值不当/embedding 不合适/缺混合检索）→ ② 命中了但排序不对（缺 rerank）→ ③ 召回对了但答案还差（提示词/上下文组织/模型能力/需要多跳）。
4. 经验：**大多数"RAG 不行"其实是"召回不行"**，先救检索再谈换模型。

**追问**：怎么量化"召回行不行"？→ 构造带标准答案来源的评估集，测召回命中率/TopK 命中、MRR，再评答案忠实度。

## 题 2：文档切分你怎么做？为什么它这么重要？

**答题要点**：切分决定"检索的最小语义单元"。太小缺上下文、太大稀释相似度且费预算。按内容选：结构清晰（规程/手册/合同）用结构感知（标题/段落），叙述杂用语义切分，要精度又要上下文用"小块召回、大块返回"的父子策略。务必保留元数据（来源/章节/日期）做过滤与溯源。这块没有银弹，靠针对问题类型的实验。

## 题 3：纯向量检索有什么坑？怎么增强召回？

**答题要点**：向量擅长语义近似，但对**精确关键词**（型号、错误码、法条/合同编号）、否定、稀有术语容易跑偏。增强：① 混合检索（向量 + BM25/关键词，RRF 融合）——型号/编号场景几乎必上；② rerank（cross-encoder 精排，先广召回再取最相关 TopK）；③ 元数据过滤缩小范围；④ query 改写/多查询扩展。

## 题 4：换了一个更强的 embedding 模型，为什么系统反而乱了？

**答题要点**：不同 embedding 模型的向量空间互不兼容——旧文档向量和新查询向量不在同一空间，相似度失去意义。换模型必须**用新模型重建整个索引**（所有历史文档重新向量化）。这也是为什么选型要一步到位、并把"embedding 版本"记进元数据，迁移时做灰度双索引切换（呼应作业 5）。

## 题 5：企业落地 RAG，安全与权限上要注意什么？

**结构化回答**：

1. **数据隔离**：检索必须按用户/租户权限过滤（元数据 ACL），否则会把越权文档召回进上下文泄露——这是最严重事故。
2. **Prompt 注入**：被检索的文档内容属不可信输入，可能含"忽略指令…"，要做输入/输出防护（见 s2-2）。
3. **可溯源与合规**：金融/电力答案必须可引用来源、可审计；时效性用生效日期过滤。
4. **数据不出域**：敏感知识库常需私有化 embedding/LLM（本地模型）满足合规。

## 高频追问速答

1. TopK 和 similarityThreshold 怎么定？→ 结合答案所需上下文量与 token 预算，用评估集实测召回命中拐点，别拍脑袋。
2. RAG 和微调（fine-tune）怎么选？→ 要"知最新/私有事实且可溯源"用 RAG；要"改变模型风格/领域表达/固定能力"用微调；常互补。
3. 长文档一次塞不下怎么办？→ map-reduce/分块摘要、只塞最相关 TopK、或"检索+多轮"。
4. 多跳问题（需要跨文档推理）怎么办？→ 迭代检索（Agentic RAG）、查询分解、图检索（GraphRAG）。
5. 向量库一定另建吗？→ 不必，pgvector/ES/Redis 已在你栈里就优先复用，降低运维与数据同步成本。
