# 异步模型、指标与容量结论 · 面试题

## 题 1：Gatling 为什么能单机模拟几万虚拟用户？从线程模型讲起。

- JMeter：一用户一平台线程，等待响应时线程 park——栈内存（默认 1MB 级）与调度开销随并发线性涨，万级线程先压垮压力机；
- Gatling：用户=会话数据+状态机，发请求即注册回调并让出线程，响应/超时/pause 到期由事件循环唤醒推进——等待零占用，几千用户只需核数个 IO 线程；
- 天花板仍在：TLS 计算、报文序列化、fd/端口、网卡带宽——所以"能挂用户"≠"能发流量"，重报文场景照样要多机；
- 加分：类比 Netty/虚拟线程思想——"阻塞代码用线程换简洁，压测用状态机换规模"，两种模型分别是各自场景的权衡产物。

## 题 2：mean、标准差、分位数分别在什么问题上使用？

- mean：总吞吐/资源核算（面积类问题，如"平均每秒处理多少"）；单独看 RT mean 是反模式；
- sd：分布形状探针——mean 相近但 sd 巨大提示双峰（缓存命中/未命中、长短尾路由差异），该拆流量再看；
- 分位族（p50/p75/p95/p99/p99.9）：SLA 与用户体验口径，容量评审只认它；
- 加分：点出"分位不可跨窗口合并"——多个时间窗或压力机的 p99 不能取平均，要合并原始样本重算或用直方图近似合并。

## 题 3：报告里 requests/s 上不去，用户注入也没到预期，排查顺序？

- 一查压力机：CPU 饱和（TLS 尤其贵）、GC 日志、fd/临时端口——任何一项超限先扩压力侧；
- 二查连接语义：keep-alive 是否开、每用户连接复用与否、目标 accept 队列/线程池——连接风暴与复用配置能差数倍吞吐；
- 三查目标：伴跑指标里 CPU/队列/DB 等待，判断是真饱和还是排队抖动；
- 四查仿真本身：think time/全局定时器、check 里的正则回溯、feeder 耗尽停摆；
- 加分：强调"到达率未兑现"这一口径——注入是意图、曲线是事实，两者背离的中间地带就是结论作废区。

## 题 4：浸泡测试和负载测试的分工？举一个只有浸泡能抓到的缺陷。

- 负载/压力测试回答"多少量能扛、拐点在哪"；浸泡回答"长时间稳定运行会不会退化"；
- 典型独捕获：连接池泄漏（每请求多借不还，2h 后池空）、本地缓存无界增长触发频繁 Full GC、证书/Token 定时刷新竞态、磁盘日志挤占 page cache 后 IO 变慢；
- 加分：给浸泡配置——膝点 70~80% 负载、2~4h、按分钟采趋势（堆 used、fd、池 active/idle、RT p99 漂移），判"斜率是否显著非零"而非肉眼平不平。

## 题 5：怎么把一次压测写成业务方看得懂又防杠的容量结论？

- 模板五段：流量模型（到达率/混压配比/有无思考）、判据（SLA 阈值与实测）、边界（膝点与退化形态+归因）、稳定性（浸泡结果）、自证（压力机数据）；
- 措辞纪律：不写"支持 X 并发"孤句；每个数字带口径；对超出验证范围的场景（大促 3 倍）明确"未覆盖"并给追加实验建议；
- 加分：主动写风险——如"依赖渠道配额未压到，1.3 倍场景可能先触发对方限流"，把不确定性交回决策者而不是藏起来。

## 题 6：HTTPS 压测有什么特殊注意？压力机侧和目标侧各说。

- 压力机：TLS 握手是 CPU 大户（尤其未复用连接时），万级新建连接先量压力机 CPU，必要时升配/多机或预热会话复用（session resumption）；
- 口径：连接复用与否决定"握手成本是否摊薄"——报告要标注 keep-alive 配置，否则同系统两次压测差倍数都能"合理"；
- 目标侧：证书链验证、SNI、TLS 线程（nginx worker crypto）、握手风暴对 accept 队列的冲击，atOnce 场景专测；
- 加分：提出"两级压测"——纯内网 HTTP 比业务容量，端到端 HTTPS 验 TLS 层叠加成本与握手风暴，分层数字分开给，混在一起就都是糊的。
