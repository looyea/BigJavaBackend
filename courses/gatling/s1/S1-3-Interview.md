# 与 JMeter 选型对比（关联） · 面试题

## 题 1：Gatling 和 JMeter 你推荐哪个？（开放题，考结构化思维）

- 拒答题面先反问四件事：谁维护脚本、压什么协议、目标并发量级、是否要进 CI 门禁——选型是场景分配不是站队；
- 给结论示例：核心链路容量/流水线门禁/万级到达率 → Gatling（代码化+异步模型+断言退出码）；冷协议（JDBC/JMS/Dubbo）、非开发自助、无文档探索 → JMeter（GUI+录制+插件广度）；
- 收口：双轨共存要有口径字典与互拍机制，年度复盘决定是否收敛；
- 加分：点破"工具宗教战"的无意义——结论失真大多来自模型/数据/环境失真，与工具品牌无关。

## 题 2：从压力模型解释 Gatling 的资源优势及其上限。

- 用户=会话+状态机，等待响应/pause 时不占线程，事件循环+全局定时器推进——在途用户数与线程数解耦，数万并发单机可挂；
- 上限不在"用户数"而在吞吐构成：TLS 握手 CPU、大报文序列化内存、fd/端口、网卡——重报文短连接场景 Gatling 一样要多机；
- 加分：对比虚拟线程（Loom）——JMeter 若迁到虚拟线程，阻塞模型的内存税会显著下降，工具差距在缩小，但"脚本形态/生态"差异依旧。

## 题 3："压测脚本即代码"具体好在哪？给出可验证的好处。

- 评审：PR diff 是可读代码而非 XML 噪音，业务同学能看懂断言与注入；
- 复用：登录链/签名链/断言集抽成内部库版本化，接口字段变更编译期报错而不是运行时 400 风暴；
- 演进：参数用 case class/常量收口，环境切换靠配置注入，天然适配多环境矩阵；
- 加分：承认对称成本——DSL 学习期、无录制器、维护者必须会写代码；给出"公共库+模板+梯队"三件套把税降到可承受。

## 题 4：CI 里两个工具的门禁实现有何差异？

- Gatling：assertions 失败→进程非零退出，maven/sbt task 一行接入，HTML 报告目录直接做制品——红绿灯语义内置；
- JMeter：`-n -e -o` 出报告后用后处理脚本解析 JTL/统计判定阈值，或 Taurus 包装——灵活但"判定逻辑在工具外"，容易各工程自写一套口径漂移；
- 加分：门禁分层——PR 跑冒烟档（低到达率+严断言快速失败），主干跑容量档；两边共用阈值配置中心防漂移。

## 题 5：老板说"买了 JMeter 经验，Gatling 从零开始，值吗？"你怎么算这笔账？

- 成本项：学习曲线工时（试点 1 链路 4 周口径）、公共库建设、双轨期维护两套资产的开销；
- 收益项：脚本事故率下降（拿历史 jmx 误改/口径漂移案例量化）、分布式压力机运维工时下降、门禁内置红绿灯省下的后处理脚本维护；
- 决策方式：试点+度量（门禁耗时、误报率、维护人数≥2 才算落地），设退出条件，避免沉没成本绑架；
- 加分：指出隐性收益——压测脚本进代码评审文化后，性能设计左移（开发写接口时自带容量视角），这是 GUI 工具给不了的。

## 题 6：五年后再看，压测工具会被什么替代？

- 大概率方向：流量回放（影子流量+录制回放做全链路压测）、云压测服务（按到达率计费，自建压力机消失）、以及 AI 辅助生成/维护场景脚本；
- 不变内核：模型保真（到达率/数据分布/环境同构）与结论纪律（判据/边界/浸泡）——工具会换，方法论资产直接迁移；
- 加分：由此说明团队该沉淀的是"场景定义 DSL/口径字典/造数服务"这类工具无关层，选型时把"可替换性"本身当评审项。
