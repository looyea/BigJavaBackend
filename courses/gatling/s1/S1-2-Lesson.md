# 异步模型、指标与容量结论

> 本节难度：★★★☆☆
> 本节重要性：★★★★☆
> 学习产出：理解 Gatling"用户=消息驱动状态机 + Netty 非阻塞 IO"为何能单机万级并发，读得懂官方报告全部指标口径（分位数族、标准差、吞吐直方图、活跃用户曲线），并能按"SLA→浸泡→结论"三步产出可辩护的容量陈述。

## 一、异步模型：等待不占资源

```text
图目的：JMeter 与 Gatling 处理"一个用户等响应"的资源形态对比
JMeter：线程发出请求后阻塞 parked —— 1 万在途用户 ≈ 1 万线程（栈内存+调度税）
Gatling：用户是会话数据+一组排期消息
  发出请求 → 注册回调 → 线程立即去推进其他用户   （目的：线程只干"有活"的事）
  响应到达/超时 → 事件唤醒该用户状态机继续走下一节点
  反例心智：把 Gatling 用户当线程——它 1 核可挂数千在途用户，瓶颈转移为目标系统与网络
```

发压端极限经验值：单核数千 RPS 量级（取决于报文大小与 TLS），**超过后先查压力机**：CPU 打满、GC、文件描述符、网卡——与 JMeter 同样的自证纪律。keep-alive 连接池与目标端端口预算仍是硬约束，"能开 10 万用户"不等于"该开"。

## 二、官方报告的指标口径

- 双 Y 轴主图：左轴 requests/s（OK 绿 / KO 红堆叠），右轴 concurrent users 时间线——**到达率是否兑现先看这条**（注入 500/s 而曲线只有 300/s，多半目标已饱和或压力机瓶颈）；
- 响应时间分位：min/mean/max + 标准差（sd1=68%、sd2=95% 区间）+ **percentile3(99.9%) / p75 / p95 / p99**；mean±sd 判断分布是否双峰（缓存命中/未命中两条路混在一起）；
- 请求统计表：按 name（含 group）列 OK/KO 数、占比与分位——评审按业务步骤读它，不是只看 global；
- 异步注意：报告聚合窗口 1s，瞬时脉冲会被抹平，需要秒级峰值细看原始数据（`-Dgatling...` 导出或 gazelle 日志）。

## 三、容量三步：SLA 断言 → 阶梯 → 浸泡

1. **SLA 写成断言**：

```java
// 目的：把 SLA 变成可执行的门禁条件，红灯先于人工读图出现在报告里
scenario("主交易流程")
    .exec(http("创建订单").post("/orders").check(status().isOk()))
    .assertions(
        global().responseTime().percentile3().lt(Duration.ofMillis(800)), // 口径：percentile3 是 p99.9；p99 档用 percentile2()
        global().successRatio().gt(0.995)   // 反例：gt(99.5) ❌ ratio 是 0~1 口径，写成百分数形式判据就全错
    );
// 结果：断言未通过则 Gatling 以非零码退出，流水线容量门禁据此直接停部署
```

2. **阶梯寻顶**：`rampUsersPerSec` 分段升档找"p99 抬头+KO 起量"的膝点（与 JMeter 同一方法论，只是换表达）；
3. **浸泡验证**：膝点 70~80% 负载跑 2~4h，抓慢泄漏（堆、连接、fd）——一次 10 分钟压测永远发现不了的，才是生产半夜挂的主因。

## 四、结论陈述的防杠写法

不写"支撑 X 并发"，写：**"在到达率 Y req/s、混压配比 Z 下，P99<800ms 且成功率 99.95%，浸泡 2h 无泄漏；膝点约 1.6Y，退化形态为 DB 连接池排队（附资源曲线）"**——模型、判据、边界、归因四要素齐了才叫容量结论，数字只是其中一项。
