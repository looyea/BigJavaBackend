# 以太网、交换机与 VLAN

> 后端工程师对这一层最常见的态度是"这不归我管"，于是付出代价：容器 Overlay 网络里 MTU 黑洞查三天、ARP 表溢出导致偶发卡顿、跨交换机通信被 VLAN 未放行拦死、`No route to host` 其实是 MAC 学不到。本节把链路层讲成**能被后端读懂、能被排障用上**的知识（重要度 3/5，标准概览档，但三个"坑"必须掌握）。

## 一、以太网帧：最朴素也最长寿的格式

现代以太网（IEEE 802.3）帧结构：

```
| 前导码 8B | 目的MAC 6B | 源MAC 6B | (VLAN tag 4B) | 类型 2B | 载荷 46~1500B | FCS 4B |
                                            ↑ 0x8100            ↑ 0x0800=IPv4  0x86DD=IPv6  0x0806=ARP
```

关键事实：

1. **MAC 地址 48 位**，前 24 位是厂商 OUI，最高位为**组播位**（1 = 组播/广播，`ff:ff:ff:ff:ff:ff` 是广播）、次高位为**全局/本地管理位**。所以"目标 MAC 首字节是奇数"意味着组播帧。
2. **类型字段**决定上一层是谁，这就是"同一条链路可以并行跑 IP 和 ARP"的原因。
3. **FCS（CRC32）** 在网卡硬件校验，错的帧直接丢，**不会通知上层**——所以"偶发丢包"的第一嫌疑可以是物理链路（光模块/网线/错误计数器，见 `ethtool -S`）。
4. 最小帧 64 字节（含头 18 + 载荷 ≥ 46）是 CSMA/CD 时代的遗产：为了保证发送方能"边发边听"检测到冲突。今天全双工交换网络早已不需要冲突检测，但**最小帧约束仍在**（有些设备会丢弃小于 64 字节的帧）。
5. 载荷 < 46 时由 **padding 补到 46**（IP 层短包实际线上更大），> 1500 就要分片或用巨帧。

## 二、ARP：IP 到 MAC 的翻译，以及它的三个工程后果

同一局域网内通信，必须先知道对方 IP 对应的 MAC：

```
who-has 10.0.1.5 tell 10.0.1.8        ← 广播："谁是 10.0.1.5？"
10.0.1.5 is at 00:11:22:33:44:55      ← 单播回复，同时让对方学到自己的 MAC
```

ARP 的设计是"无状态、无认证、缓存换性能"，因此带来三个必须知道的工程现象：

| 现象 | 原理 | 后端影响 |
|---|---|---|
| **ARP 缓存**（Linux 默认 60~180 s 可达） | 每次问太贵，故缓存 | IP 变更后（弹性扩缩容、漂移 VIP、K8s Pod 重建）通信会**持续打到旧 MAC**，表现为"新节点起来了但连不上"。解法：`arping -U` 发免费 ARP 刷新、`arp_ignore/arp_announce` 调优（LVS-DR 与 keepalived VIP 必配） |
| **免费 ARP（Gratuitous ARP）** | 自己宣布"我是这个 IP" | VRRP/keepalived 主备切换、VIP 漂移靠它秒级刷新交换机 MAC 表与邻居 ARP；也是**ARP 欺骗/风暴**的载体 |
| **ARP 广播域扩散** | 广播帧被交换机泛洪到全 VLAN | 大二层（flatten L2）里成千上万台机器时 ARP 风暴拖垮网络 → 这就是数据中心要用 VXLAN/路由化（L3 to the host）的根本动因 |

Linux 排障命令：`arp -n` / `ip neigh show`（状态 `REACHABLE/STALE/FAILED/INCOMPLETE`，`FAILED` 就是解析不到 MAC —— 对端不在同网段且路由/网关有问题时会看到这个）。

## 三、交换机：自学习 + 转发/泛洪，两个动作建起一张表

交换机是**多端口二层设备**，核心行为只有两条规则：

1. **学习**：收到帧，把 `源 MAC → 入端口` 写进 MAC 地址表（CAM 表，老化时间默认 300 s）。
2. **转发或泛洪**：查 `目的 MAC`，命中则只从对应端口转发；**未命中或是广播/组播 → 泛洪到除入端口的所有端口**。

由此可以推出四个高频线上问题：

- **未知单播泛洪（unknown unicast flooding）**：MAC 表老化了、或两端不对称路由（去程走交换机 A、回程走交换机 B）导致本地学不到目的 MAC，于是持续泛洪 → 端口被打满、CPU 升高、偶发变慢。典型诱因：**负载均衡器与后端之间的非对称路由、STP 拓扑变更、表项溢出**。
- **MAC 表溢出 → 退化为 Hub**：攻击或异常导致表满，交换机只能泛洪，流量被"窃听"，安全风险与性能问题同时发生。
- **环路 + 广播 = 广播风暴**：两个交换机之间插两根线就形成环路，广播帧无限循环放大，秒级瘫痪全网。解法是 **STP/RSTP/MSTP**（生成树协议，逻辑上阻塞冗余端口，保留物理冗余）。今天更多用 **M-LAG / vPC / 堆叠 / 交换机虚拟化**替代 STP，以获得"无环又能全部转发"的效果。
- **抓包抓不到**：正因为交换机不广播单播，所以在别的机器上是抓不到你们之间通信的 —— 要么用端口镜像（SPAN），要么在被测主机上抓。（这解释了"为什么必须在故障机器本机抓包"这条排障纪律，见 s4-2。）

## 四、VLAN：把一台物理交换机切成多个逻辑二层域

**VLAN ID 12 位，可用 1~4094**。原理就是在帧里插 4 字节 tag（`0x8100` + Priority 3bit + CFI 1bit + VLAN ID 12bit），带 tag 的帧只会在同 VLAN 内转发，从而：

- **隔离广播域**：不同 VLAN 之间 ARP/广播互不可见，故障与风暴被限制在小范围。
- **安全与租户隔离**：管理网、业务网、存储网分离；云上的多租户 VPC 底层正是 VLAN/VXLAN。
- **两种端口模式**：
  - **access**：属于单一 VLAN，收发时**剥掉/加上** tag —— 接服务器/PC（它们一般不懂 tag）。
  - **trunk**：允许多个 VLAN 通过，帧**带着 tag** 走 —— 交换机之间、或服务器网卡做"一条线承载多网段"时。

后端会直接接触的两个场景：

```bash
# 例子目的：Linux 网卡做 trunk——一个物理口上划出多个 VLAN 子接口
ip link add link eth0 name eth0.100 type vlan id 100   # 在 eth0 上创建 VLAN 100 子接口
ip addr add 10.0.100.8/24 dev eth0.100                  # 给子接口配管理网地址，此后到 10.0.100.0/24 的流量带 tag 100
# 常用于：机器同时接管理网(100)与业务网(200)，或裸金属交付时的多平面组网
bridge vlan show            # 正确用例：列出端口所属 VLAN，应能看到 eth0.100
# 正确用法结果：ip addr 可见 eth0.100 带 10.0.100.8/24；发往管理网的帧都带上了 VLAN tag 100
# 错误用法：上联交换机端口是 access 模式却发了带 tag 的帧 → 交换机直接丢弃该帧，表现为"同节点通、跨节点不通"
# 错误用法：id 写了 4095（保留值）或 >4094 → ip link 报错 VLAN id out of range，配置不生效
```

> **容器与 K8s 里的真实故障**：CNI 用 Linux bridge / OVS / macvlan 组网时，若宿主侧交换机端口是 access 模式却跑了多 VLAN 的 Pod 流量，包会被打上错误 tag 或直接丢弃，表现为"同节点 Pod 通、跨节点 Pod 不通"或"某些端口通某些不通"。定位手段：在两端同时 `tcpdump -i any -e vlan` 看有没有 tag、VLAN ID 对不对。

## 五、从 VLAN 到 VXLAN：为什么云计算必须"越层"

VLAN 只有 4094 个 ID，且**二层域不能大规模扩展**（广播泛洪 + STP 收敛慢）。云数据中心动辄上万台虚机、多租户隔离需求，于是有了 **VXLAN**：

- 把二层以太网帧**封装进 UDP 包**（目的端口 4789），通过 IP/Underlay 网络传输，用 24 位的 **VNI**（1600 万个隔离域）替代 VLAN ID。
- 效果：跨物理机房的虚机可以"在同一个二层"，虚拟机迁移不断网；同时 Underlay 全用 ECMP 路由，绕开 STP 的限制。
- **对本节的呼应点**：VXLAN 封装 = 外层 UDP(8) + IP(20) + VXLAN(8) = **额外 50 字节**，所以 Overlay 网络的可用 MTU 只有 1450。若 Pod 内按 1500 发包 + DF 位，就会**黑洞丢包**：小请求正常、大响应卡死。标准解法是把 Pod/网卡 MTU 设为 1450（Calico IPIP 是 1480、VXLAN 1450），或开启 `tcp_mtu_probing`，或在 Underlay 直接上巨帧 9000。**这是当代后端最可能撞上的链路层问题。**

## 六、MPLS 与其他技术的定位（了解边界即可）

- **MPLS**：在 L2 与 L3 之间插一层"标签交换"（俗称 2.5 层），用查标签替代查最长前缀路由，实现 **流量工程（TE）与 VPN（L3VPN/L2VPN）**。运营商专线、企业跨域互联常提供"MPLS 专线"，对应用侧表现就像一条低时延稳定链路。云厂商的骨干网内部也大量使用。
- **QoS / 802.1p**：VLAN tag 里有 3 位优先级（PCP），配合 DiffServ（IP 头的 DSCP 6 位）可做分类排队。金融专线、语音/行情链路会申请特定 DSCP 值。
- **RDMA / RoCE**：让网卡直接读写远端内存、绕过内核协议栈和 CPU（配合 GPUDirect、NVMe-oF），是存储与 AI 训练网络的标配。它的存在是"分层设计被性能击穿"的最好例子。

## 七、三大行业场景钩子

- **电商 / 云原生**：K8s 集群跨节点 Pod 通信走 CNI（VXLAN / Calico / Cilium），MTU 一致性与 ARP 表刷新是"偶发 5 秒卡顿""大响应超时"的高频根因；多可用区部署要理解 VPC/子网（L3）与安全组（L3/L4 过滤）的边界。
- **金融**：交易网与办公网、开发测试网严格 VLAN 隔离 + ACL；主备中心切换靠 VIP + 免费 ARP 在秒级把流量牵引到新主；硬件时间戳与交换机透明时钟（PTP/IEEE 1588）用于撮合链路的微秒级时延测量。
- **电力**：变电站内过程层（SV/GOOSE）走二层组播、要求交换机支持 **QoS 优先 + VLAN 划分 + STP 快速收敛（RSTP）**，因为 GOOSE 报文直接以太网帧为目的（类型 0x88B7），根本不经过 IP 层——这是"纯二层协议仍在生产运行"的活教材；配电终端则多走运营商 APN 专网（L3 + NAT），两种范式并存于同一张电网。

## 八、要点回顾

1. 以太网帧：目的/源 MAC + 类型 + 载荷 + FCS；FCS 由网卡硬件校验，错帧静默丢弃（查 `ethtool -S`）。
2. 职责边界：MAC 管**这一跳**、IP 管**端到端**（呼应 s1-1）。
3. ARP 是广播询问 + 单播应答 + 双方缓存；三大后果是 ARP 缓存导致的 IP 变更后打旧 MAC、免费 ARP 用于 VIP 漂移、广播域过大导致 ARP 风暴。
4. 交换机只做两件事：**学源 MAC、按目的 MAC 转发或泛洪**；因此衍生未知单播泛洪、MAC 表溢出、环路广播风暴（STP/RSTP 或 M-LAG 化解）、以及"必须本机抓包"。
5. VLAN 用 4 字节 tag 隔离二层域（12 bit → 4094）；access 剥 tag、trunk 带 tag；Linux 可用 `ip link ... type vlan` 做子接口。
6. VXLAN 用 UDP:4789 把二层帧封进三层，VNI 24 bit 解决数量与扩展性，代价是**吃掉 50 字节 MTU** —— 容器网络 MTU 黑洞的头号原因。
7. MTU 1500 → MSS 1460；Overlay 场景必须同步调小 Pod/网卡 MTU，或启用 PMTUD / `tcp_mtu_probing`。
8. MPLS、DSCP/802.1p、RDMA 分别是"跨层转发加速""优先级分类""绕开协议栈"的代表，理解它们为什么存在比记缩写更重要。
