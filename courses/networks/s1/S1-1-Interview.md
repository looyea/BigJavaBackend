# 面试考点 · 分层模型、封装与分组交换

> 这一层知识在面试里通常不作为独立题目出现，而是**作为其他网络题的评分背景**：能不能准确说出某个字段属于哪一层、能不能算清带宽与时延，决定面试官给你贴"背过题"还是"懂网络"的标签。

## 考点 1：分层与字段的归属（基础必过关）

**起手**：说说 OSI/TCP-IP 分层，各层的关键协议与设备。

**追问链**：
1. 交换机和路由器的区别？→ 二层交换机按 MAC 表转发、广播域内；路由器按 IP 路由表跨网转发、隔离广播域。三层交换机 = 交换 + 路由能力。
2. Hub 和 Switch 的区别？→ Hub 是物理层共享介质（冲突域）、Switch 每端口独立冲突域。
3. `TTL` 是哪一层？`窗口大小` 是哪一层？`MSS` 呢？→ 分别 IP / TCP / TCP 选项（握手协商）。字段归属混乱会直接暴露基础不牢。
4. TLS 属于哪一层？→ 工程上位于应用层之下、被当作独立层实现（Record/Handshake），对 TCP 是载荷。所以说"HTTPS 是 443 端口的 TCP 上的加密流"。

## 考点 2：封装与 MTU/MSS（最容易答错的一组）

**起手**：MTU 1500，MSS 是多少？为什么？

**期望**：1460 = 1500 − 20（IP 头）− 20（TCP 头）；若有 VLAN tag 或 TCP 选项会再小。

**追问链**：
1. IP 分片和 TCP 分段有什么区别？→ TCP 按 MSS 切段（端到端、每段可独立重传）；IP 按 MTU 分片（可能由中间路由器做、**任一分片丢失则整包重传**，效率极差）。所以工程上宁可让 TCP 分段也不要 IP 分片。
2. 怎么避免 IP 分片？→ 置 DF 位 + 路径 MTU 探测（PMTUD），或 clamp MSS（`tcp_mtu_probing`、LB/隧道场景配 `mtu 1400`）。
3. 什么场景会踩 MTU 坑？→ **VXLAN/IPIP/GRE 隧道、IPSec、云容器网络 Overlay**，封装后有效 MTU 变小（VXLAN 减 50 字节 → 1450），跨节点大报文被分片或黑洞丢弃；表现为"小请求正常、大包丢失、SSH 能连但 scp 卡死"。这是高频线上事故，答出来很值钱。
4. Jumbo Frame（9000）要注意什么？→ 全链路所有设备必须同为 9000，否则分片/黑洞；收益是降低每包处理开销与中断数（PPS 受限场景，如万兆存算、DB 备份链路）。

## 考点 3：分组交换的后果（把网络特性接到业务设计）

**起手**：为什么说"网络不可靠"会体现在业务代码里？

**期望**：
- 可能丢包 → 需要超时 + 重试，而重试带来**重复** → 必须幂等（唯一业务号 + 去重表/Redis setnx，对应在 s2-3 与后续分布式章节）。
- 可能乱序 → TCP 内部重排，但**多个连接/多个分区之间不保证顺序**（Kafka 只有分区内有序，MQ 重试可能乱序）。
- 可能长时间不通而无 RST → 需要**应用层心跳**（TCP keepalive 默认 2 小时太慢，呼应 s2-2 与 netty/s3-2）。
- 中间设备会看头 → 端口选择、协议格式受现实约束（不要用 80 跑自定义二进制；LB 可能改写头部）。

## 考点 4：量化能力（区分资深度）

**起手**：一条链路 1 Gbps、RTT 40 ms，最多能同时"在途"多少数据？要跑满需要多大缓冲？

**期望**：BDP = 1e9 bit/s × 0.04 s = 4e7 bit = **5 MB**。因此 socket 缓冲与 TCP 窗口都需 ≥ 5 MB/连接（或按并发分摊），否则吞吐 = 窗口 ÷ RTT，远低于带宽。

**追问链**：
1. 带宽和时延的关系？→ 互相独立；带宽决定传输时间、RTT 决定往返等待。
2. 为什么利用率超 70% 后时延暴涨？→ 缓冲排队（队列时延 ∝ ρ/(1−ρ)），且 tail drop 导致丢包重传。这也是 AQM/CoDel、RED 存在的原因。
3. 跨机房调用怎么优化？→ 减少 RTT 次数（并行、批量、合并）、就近读、缓存、异步化、必要时改协议（HTTP/2 多路复用、gRPC 流式）而不是"换更快的网卡"。
4. 一个 RPC 接口 P99 从 5 ms 涨到 40 ms，但服务端平均处理时间没变，你会怎么查？→ 期望答出"分段计时"：客户端→网关（网络 RTT + 排队）、网关→服务、服务→DB；用 `ss -ti`看重传/RTT、看 TCP 重传率、看连接池等待时间、看 LB 健康检查抖动 —— 这题实际是在考察你会不会把网络当成一个独立的可测环节（s4-2 展开）。

## 考点 5：单位与估算的严谨性（送分/送命题）

**起手**：1 Gbps 等于多少 MB/s？

**期望**：≈ 119 MB/s（10⁹ bit ÷ 8），实际有效约 110–115 MB/s（帧开销 ≈ 5%）。

**红线**：能主动区分 **bit/Byte**、**1000 vs 1024**（网络用 10⁹，存储常混用 2³⁰），并说明**"带宽够不代表延迟低"**。做容量规划时先算 BDP 与并发分摊的缓冲，再算带宽，最后留 30% 余量——把这个顺序讲出来，就是一次高质量的架构回答。

## 考点 6：这道基础题的"架构师视角"落点

- **电商**：静态资源上 CDN 的本质是"用边缘节点换 RTT"；API 合并（BFF/GraphQL）的本质是"用一次 RTT 换多次 RTT"；页面秒开优化要看的是几个 RTT（DNS/TCP/TLS/请求），而不是文件大小。
- **金融**：同城双活要求同步复制，硬门槛是 RTT（一般 < 1~2 ms），这是选址决定的，软件无法突破；行情推送用组播/内核旁路绕开协议栈分层开销。
- **电力**：专网 APN 的 MTU 与丢包率决定采集终端的重试与压缩策略；主站与终端之间是"小报文、高时延容忍、强可靠"的需求组合，因此用 DL/T 645/698 之类的应用层定长/分隔协议而非通用 HTTP（呼应 s2-4 粘包定界）。
