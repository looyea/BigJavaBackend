# 分层模型、封装与分组交换

> 本节是计算机网络的"世界观地基"（重要度 4/5）。后端日常工作似乎只碰第七层，但**每一次"网络慢"的定位、每一个超时参数的设定、每一次跨机房带宽预算**，都要求你脑子里有一套分层 + 量化的模型。学完这节你应该能回答两个问题：一个 HTTP 请求在每一层变成了什么、由谁负责；以及"这条链路理论上限是多少"。

## 一、为什么要分层：把不可解的问题切成可替换的层

网络是一个端到端的巨大系统，涉及介质、编解码、寻址、路由、可靠传输、语义。分层设计的本质是**关注点分离 + 各层可独立演进**：

- 换网卡不需要改应用；把 TCP 换成 QUIC 不需要改业务代码；HTTP/2 换掉报文格式，下面的 IP 完全无感。
- 每一层只对上层提供一个**抽象服务**（"我给你送字节流且保证有序不丢"），不关心下层如何实现。
- 出问题时可按层切分定位——这就是"物理层→链路层→网络层→传输层→应用层"排障顺序的由来（详见 s4-2 抓包排障）。

代价是**封装开销与逐层处理延迟**：每层加自己的头，数据被"包"了一层又一层；每层都要过一次处理逻辑。高性能场景（内核旁路、DPDK、用户态协议栈）就是"牺牲分层通用性换性能"的典型反叛。

## 二、两套模型与它们的对应关系

工程上说的是 **TCP/IP 四层**，教科书用 **OSI 七层**，面试两者都要能对上：

| OSI 七层 | TCP/IP 四层 | 数据单元 | 典型协议/设备 | 这一层回答的问题 |
|---|---|---|---|---|
| 应用 / 表示 / 会话 | 应用层 | Message | HTTP、DNS、TLS(常在应用层实现)、SMTP、Kafka 协议 | 消息的语义是什么 |
| 传输层 | 传输层 | Segment（TCP）/ Datagram（UDP） | TCP、UDP、SCTP；端侧内核 | 该交给哪个进程（端口）？要不要可靠？ |
| 网络层 | 网际层 | Packet | IP、ICMP、IPsec；路由器 | 怎么从源主机到目的主机（跨网路径） |
| 数据链路层 | 网络接口层 | Frame | 以太网、Wi-Fi、ARP、PPP；交换机/网卡 | 相邻两跳之间怎么传，谁在物理上收发（MAC） |
| 物理层 | （同上并入） | Bit | 光纤、双绞线、电平/光脉冲；集线器/中继器 | 0 和 1 怎么变成物理信号 |

**记忆抓手**：MAC 解决"这一跳给谁"，IP 解决"最终到哪台机器"，端口解决"给这台机器的哪个进程"，协议头解决"这段字节是什么意思"。四句话贯穿全课程。

## 三、封装与解封装：一个请求的真实变形记

以 `curl http://10.0.0.2:8080/api/order` 为例，自上而下：

```
应用层   HTTP 报文："GET /api/order HTTP/1.1\r\nHost: ...\r\n\r\n"
            ↓ 加上本层头
传输层   TCP 段：[源端口 51234 | 目的端口 8080 | 序号 | 确认号 | 窗口 | 标志 SYN/ACK/PSH | 校验和]
            ↓
网际层   IP 包：[版本|IHL|总长|标识|TTL=64|协议号 6=TCP|源 IP|目的 IP|头校验和]
            ↓
链路层   以太网帧：[目的 MAC | 源 MAC | 类型 0x0800 | 载荷 | FCS 校验]
            ↓
物理层   比特流：光脉冲 / 电平
```

到对端反向解封装，每层拆掉自己的头。**关键细节，很多"看不见的问题"都出在这里**：

1. **MAC 每一跳都变，IP 端到端不变**。经过一个路由器，源/目的 MAC 换成路由器接口的 MAC，而 IP 头不动（NAT 除外）。所以抓包时看到"目的 IP 是我的服务，但目的 MAC 是网关"完全正常。
2. **分片可以发生在不同层**：IP 层因 MTU 超限而分片（IPv4 可路由器分片，IPv6 只能源端分片 + PMTUD）；TCP 层因 MSS 而切段。两者不是一回事，排障时混淆会导致误判。
3. **TLS 的位置**：它在应用层之下、被当作"一层"实现，加密后的字节对 TCP 来说是载荷。所以抓包看到 `TLS Application Data` 就无法再解语义——排障要看握手与记录层元信息，或走服务端解密（s3-3）。
4. **封装决定有效载荷率**：以太网 MTU 1500，减 IP 头 20 + TCP 头 20 = **MSS 1460**。可以直接算一遍：再算上帧头 14 + FCS 4 + 前导码 8 + 帧间隙 12 = 38 字节开销，每帧线上占 1500 + 38 = 1538 字节，有效载荷率约 `1460 / 1538 ≈ 95%`；若加 VLAN tag（+4）、IP/TCP 选项，还会更低。这就是“千兆网卡（1 Gbit/s ≈ 119 MB/s）实测只能跑到 110–115 MB/s”的完整解释；而百兆网折到 11–12 MB/s、万兆网只能跑到 ≈ 9.4 Gbit/s 也是同一个折扣。

> **单位陷阱**：网络用 **bit**（1 Gbps = 10⁹ bit/s），存储与程序用 **Byte**。1 Gbps 理论 ≈ 119 MB/s。做带宽预算先统一单位，这是容量规划里最常见的低级错误。

## 四、分组交换：为什么不是电路交换

- **电路交换**（传统电话）：通信前建立独占物理通路，带宽被预留，利用率低、建立慢。
- **报文交换**：整条消息逐跳存储转发，需要节点缓存整个大报文，时延不可控。
- **分组交换**（互联网）：把消息切成**大小受限的包**，每包独立选路、存储转发。

分组交换带来三个直接后果，全都是后端工程的现实约束：

1. **包可能乱序**（不同包走了不同路径）→ 所以需要 TCP 用序号重排（s2-3）。
2. **包可能丢**（某跳缓冲溢出）→ 所以需要重传与确认，需要幂等设计。
3. **包可能被中间设备区别对待**（防火墙、LB、conntrack、QoS 只看前 N 字节）→ 所以"自定义协议不要用 80 端口跑非 HTTP 流量"这类经验是硬约束（s2-4、s4-1）。

同时，**共享缓冲**是排队时延与抖动的来源：链路利用率超过 ~70% 后，排队时延非线性飙升（M/M/1 排队模型的结论）。这解释了"带宽还没满但 P99 炸了"的普遍现象，也是容量规划要求留余量的数学依据。

## 五、四个量化口径：带宽、时延、RTT、BDP

只会说"内网很快"是不合格的。四个量必须能算：

| 量 | 含义 | 典型值 | 常见误用 |
|---|---|---|---|
| **带宽** bandwidth | 单位时间能送多少 bit（发送速率） | 机房 10/25 Gbps，跨城专线 1 Gbps | 把带宽当时延："10G 所以肯定低延迟"是错的 |
| **时延** latency | 一个 bit 从 A 到 B 的单程时间 | 同机架 < 0.1 ms，同城 1–5 ms，跨洋 150+ ms | 忽略序列化时延：1 MB 在 1 Gbps 上需 8 ms 才能"推进去" |
| **RTT** | 往返时延，工程真正的对手 | 内网 0.2–1 ms，公网 20–80 ms | 只用平均值：P50 与 P99 差数倍是常态 |
| **BDP** 带宽时延积 | 带宽 × RTT = 在途未确认的字节数 | 1 Gbps × 40 ms = 5 MB | 忽略它 → 窗口/缓冲配小了，链路用不满 |

**BDP 是这一节最有用的工程工具**：它告诉你"要填满这条链路，在途必须有 5 MB 数据"。因此：

- socket 缓冲区（`SO_RCVBUF/SO_SNDBUF`）必须 ≥ BDP，否则吞吐被窗口卡住（详见 s4-1 调优）。
- TCP 初始窗口 10 个段 ≈ 14 KB，在 1 Gbps × 40 ms 的跨城链路上，握手后需要多个 RTT 才能爬到 BDP——这就是"长肥管道（LFN）上小文件请求特别亏、连接复用比新建连接重要得多"的定量原因。
- 反推设计：**跨地域调用一次 = 至少一个 RTT**。一次业务操作若串形调用 5 个远程服务，同城 2 ms RTT 就是 10 ms 起步；把它变成"批量 + 并行 + 就近读"才是解决问题的方向（对应 s1-1 复杂度思维在架构尺度的应用）。

```java
// 例子目的：把"带宽/时延/RTT/BDP"四个量用代码算一遍，同时暴露 bit↔Byte 这个最常踩的单位陷阱
long gbps = 1;                       // 链路标称带宽：1 Gbps（注意网络行业用 bit）
double rttMs = 40;                   // 端到端往返时延 40 ms（跨城）

// 正确用法 1：Gbps → MB/s 必须除 8（1 Byte = 8 bit），再除以 1000 换千
double mbPerSec = gbps * 1_000_000_000 / 8 / 1_000_000;     // 1e9 bit ÷ 8 = 1.25e8 Byte ≈ 119 MiB/s
System.out.println(mbPerSec);                               // 正确使用结果：输出 125.0（MB/s，即 ≈119 MiB/s）

// 正确用法 2：BDP = 带宽 × RTT，得到"在途未确认字节数"，它就是 socket 缓冲的下限
long bdpBytes = (long) (gbps * 1_000_000_000L / 8 * (rttMs / 1000));   // bit/s ÷8 → Byte/s，× 0.04 s
System.out.println(bdpBytes);                             // 正确使用结果：输出 5000000（约 5 MB）
// → 工程结论：SO_SNDBUF/SO_RCVBUF 与 TCP 窗口必须 ≥ 5 MB，否则吞吐被窗口卡死（s4-1）

// 错误用法：把带宽当成字节，写成 gbps * 1_000_000_000L / 1_000_000 当 MB/s → 算出 1000 MB/s，
//            容量规划直接高估 8 倍，不报错但采购与限流阈值全错（这是容量规划最高频事故）
// 错误用法：用 int 算 gbps * 1_000_000_000 → 1e9 尚在 int 范围内，但只要写 10Gbps 就是 1e10 溢出成负数，
//            BDP 变负后缓冲被配成 0，链路吞吐跌到接近 0（现象是"带宽很富余但传得极慢"）
```

### 快速估算练习

问：客户端到新加坡服务器 RTT = 60 ms，下载 5 MB 文件，带宽 100 Mbps，TCP 初始窗口 14 KB，最大窗口 64 KB（未开窗口扩展）。粗估耗时？

- 传输时延（纯打满）= 5 MB ÷ 12.5 MB/s ≈ 0.4 s
- 但窗口限制：64 KB ÷ 60 ms ≈ 1.07 MB/s ≈ 8.6 Mbps（远小于 100 Mbps！）→ 有效速率被窗口卡死
- 于是传输 ≈ 5 MB ÷ 1.07 MB/s ≈ 4.7 s，加上慢启动爬坡（14KB→64KB 需约 2–3 个 RTT ≈ 180 ms）
- **结论：约 5 秒，而不是 0.4 秒。** 优化手段是开窗口扩展与调大 socket 缓冲（s4-1），而不是"升级带宽"。

这类"先看瓶颈在哪一层/哪一个量"的推理，就是分层模型 + 量化口径给后端工程师的真正回报。

## 六、封装带来的"分层可见性"：中间设备只看得到前几层

一个高频工程事实：**你写的每一层头部，都是中间设备可以依据和决策的信息**。

- 路由器只看 L3（IP）；L4 负载均衡（LVS）看 L3+L4（IP+端口）；七层网关（Nginx/Envoy）要解密 TLS 后看 L7（URL/Header）。
- 因此 **把 RPC 协议直接跑在 80 端口上会被七层代理拒掉或改写**；把大文件塞进 HTTP 头会撞上限；用非标准标志位可能被防火墙丢弃。
- 更进一步：**连接的可拆分性/可聚合性由分层决定**。HTTP/2 多路复用把所有请求压进一条 TCP 连接，让"按 URL 分流"的灰度规则失效，只能靠 `:path` 头解析——这是分层演进互相拉扯的现实案例。

## 七、三大行业场景钩子

- **电商**：大促页面一次加载要发 60+ 个请求，HTTP/1.1 下浏览器同源并发只有 6 个 → 域名分片合并发版；上 HTTP/2 后并发限制消失但**证书必须支持 ALPN**（s3-3），静态资源走 CDN 边缘（s3-4）把 RTT 从 40 ms 降到 5 ms。这些决策全部建立在"分层 + RTT 量化"上。
- **金融**：行情/交易撮合对时延极端敏感，链路利用率压低到 30% 以下以避免排队抖动；核心链路用内核旁路（Solarflare OpenOnload / DPDK）牺牲分层通用性换取微秒级；同城双活要求 RTT < 1–2 ms 才能做同步复制，这是选址的硬约束而不是软件问题。
- **电力**：配电自动化三遥（遥信/遥测/遥调）走专线，报文极小（几十字节）但要求秒级到达，因此关心的是"最坏时延"而非带宽；用电信息采集走 230 MHz 无线专网或运营商 APN 通道，MTU 小、丢包高，需要在应用层做批量压缩与断点续传——典型的"链路层特性反向决定应用层协议设计"。

## 八、要点回顾

1. 分层为可替换与可定位；代价是封装开销与逐层时延；高性能场景会以"跨层"换性能。
2. 职责一句话：MAC 管这一跳、IP 管端到端、端口管进程、协议头管语义。
3. 数据单元：Bit → Frame → Packet → Segment → Message；**MAC 逐跳变、IP 端到端不变**（NAT 除外）。
4. MTU 1500 − IP 20 − TCP 20 = MSS 1460；链路带宽要按有效载荷率折算，且 **1 Gbps = 119 MB/s 不是 1000 MB/s**。
5. 分组交换的三个后果：可能乱序、可能丢包、可能被中间设备区别对待——可靠性和幂等性都是它的"账单"。
6. 带宽 ≠ 时延；工程对手是 RTT 及其分布；**BDP = 带宽 × RTT** 决定窗口与缓冲该配多大。
7. 链路利用率超过约 70% 后排队时延非线性飙升，容量规划必须留余量。
8. 每一层头部都是中间设备的决策依据——协议设计与端口选择必须考虑分层可见性。
