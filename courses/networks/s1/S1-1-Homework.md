# 课后作业 · 分层模型、封装与分组交换

> 2 题，一题为动手抓包观察封装层次，一题为容量估算（BDP 与带宽预算），附验收标准与参考答案。

## 作业 1：亲手看见分层——抓一次 HTTP 请求并逐层拆解（50分）

**要求**：在本机对一个明文 HTTP 服务（如 `python -m http.server 8000`）发起一次请求，同时用 `tcpdump` 抓包，输出一份逐层拆解报告：

1. 抓命令：`sudo tcpdump -i lo0 -nn -vv port 8000`（macOS；Linux 用 `-i lo` 或实际网卡）。
2. 从输出中读出并列出：**帧层**（是否有 VLAN tag、帧长）、**IP 层**（`id`、`ttl`、`proto`、`flags` 里的 DF 位、总长）、**TCP 层**（`seq`、`ack`、`win`、`options` 里的 `mss`/`wscale`/`sackOK`）、**HTTP 层**（请求行与响应状态行）。
3. 回答三个观察题：① 握手三个包有没有携带数据、`win` 分别多大？② 服务端发响应时 TCP 段的大小是多少，与 `mss` 选项对得上吗？③ 整个交换一共花了几个 RTT（不含 DNS）？

**验收标准**：
- 报告能明确区分"这是哪一层的字段"，不再把 `ttl` 和窗口混为一谈。
- 能指出本机回环接口的 MTU（通常 65536/16436）与真实网卡的差别，并解释因此 `mss` 选项值不同。
- 能说出 `DF`（Don't Fragment）位的含义，以及它和路径 MTU 探测的关系（s1-3）。
- 若抓的是 HTTPS，能指出"载荷不可解读"，并说明排障时改看哪些元信息（s3-3、s4-2）。

**参考答案要点**：
- 回环抓包会看到 `flags [DF]`、`ttl 64`、`proto TCP (6)`；`options: [mss 65495, sackOK, wscale 7]` —— `mss` 就是 65536 − 20 − 20 − 1（回环上实际值随系统而异），这直接印证 **MSS = MTU − IP头 − TCP头**。
- 握手包：`SYN`（client→server，`win` 为 `tcp_rmem` 中间值经 wscale 放大后的原始 16 位值）、`SYN, ACK`、`ACK`。第三个包可带数据（`PSH, ACK`）——注意 TFO（TCP Fast Open）也在这一步带数据（s4-1）。
- 响应若小于一个 MSS，只有一个段；若大，会被切成多个 MSS 大小的段，抓包能看到 `seq` 递增 1460 —— 这就是"字节流被切段"的直接证据。
- RTT 计数：握手 1 个 RTT（第三个 ACK 到达即完成），HTTP 请求→响应又 1 个 RTT，故明文 HTTP 一次最短请求 = 2 个 RTT；加上 DNS 就是 3~4 个 RTT（这是 s4-3 全链路复盘的基础）。

## 作业 2：为大促做带宽与 RTT 预算（50分）

**要求**：某电商服务峰值 QPS = 20,000，平均响应体 18 KB（gzip 后）、请求体 1.2 KB。请回答：

1. 峰值需要多少网络带宽（Gbps，按线上实际字节含头开销估算）？
2. 若服务部署在异地机房、RTT = 35 ms，一次业务请求需串行调用 4 个下游服务，仅网络往返就吃掉多少毫秒？怎么改？
3. 每条 TCP 连接的 socket 缓冲至少配多大才不吃亏（假设连接要参与大响应传输、并发长连接 8 万条）？这会带来什么内存问题？

**验收标准**：
- 单位换算正确（Byte ↔ bit），并把帧开销按 ≈ 5%~9% 计入。
- 第 2 问要给出"串行 RTT 累加"与"改并行/合并/就近读"的量化收益。
- 第 3 问要能算出总缓冲内存 = 连接数 × 单连接缓冲，并指出这就是"百万连接"必须先算内存的原因（呼应 netty/s3-2）。

**参考答案要点**：
1. 应用层字节：`(18 KB + 1.2 KB) × 20,000 ≈ 384 MB/s` → 换算 `× 8 = 3.07 Gbit/s`；加上各层开销（约 8%）≈ **3.3 Gbps**，再按"利用率不超过 70%"的余量原则规划 → 需要 **≈ 5 Gbps** 以上的出口，即双万兆绑定或至少 10 Gbps 网卡。若没算余量，链路利用率 66% 已是排队时延开始飙升的临界区。
2. 串行 4 次调用 = 4 × 35 ms = **140 ms** 纯网络时间，而业务本身可能只花 20 ms。改造方向：① 能并行的下游并发（140 → 35 ms）；② 合并调用做批量接口（4 个 RTT → 1 个）；③ 数据就近读/本地缓存（RTT → 0）；④ 若下游在同一进程内则消除网络层（合并部署）。核心结论：**跨地域调用次数是延迟预算的一级科目，不能只优化单机 CPU**。
3. 单连接若要跑到满带宽：10 Gbps × 35 ms = 43.75 MB 是理论 BDP，实际按 `min(缓冲上限, 期望速率×RTT)` 配置，例如给每条大流量连接 4 MB 收发缓冲 → 8 万连接 = **640 GB**，机器根本放不下。所以必须：① 只给长肥管道连接配大缓冲（内核 `tcp_rmem` 自动调优正是为此）；② 大文件走独立的少量连接；③ 普通短连接用默认小缓冲 + 连接复用。**这道题的真正答案是"缓冲不能一刀切，按连接类型分级"**，也是 Netty 里 `WriteBufferWaterMark` 与池化内存要考虑内存总量的原因。
