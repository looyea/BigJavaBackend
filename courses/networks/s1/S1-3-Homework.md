# 课后作业 · IP、子网划分与路由

> 2 题，一题为 VPC/子网容量规划（含计算与踩坑），一题为非对称路由与 conntrack 故障诊断，附验收标准与参考答案。

## 作业 1：为三可用区业务做 VPC 地址规划（50分）

**要求**：某电商要新建 VPC，需求如下：3 个可用区（AZ），每 AZ 需要 Pod 网段支撑 4,000 个 Pod、Node 网段 200 台、以及一个共享的"中间件/DB"子网 500 个地址；另外要预留与办公网 `10.100.0.0/16` 打通的 VPN 通道。请给出：

1. VPC 主网段建议（含理由），并说明为什么不能随手选 `172.17.0.0/16`。
2. 每个 AZ 各子网的 CIDR 划分表（Pod / Node / 中间件三类，写出具体前缀与可用地址数）。
3. 若后来发现 Pod 网段不够用，怎么办？
4. 规划中最容易被安全团队追问的两个点是什么？

**验收标准**：
- 主网段选 `10.0.0.0/8` 内的**足够大块**（如 `10.20.0.0/16`）并说明"VPC 主网段一旦确定，扩 subnet 容易、改主网段极难"。
- 每个子网前缀计算正确：4,000 主机 → `2^m − 2 ≥ 4000` → m = 12 → **/20**（4096 地址）；200 → **/24**（254）；500 → **/23**（510）。
- 明确"三类子网 × 3 AZ"要按 AZ 连续切块，便于用一条聚合路由（supernet）表达，例如 AZ-a 用 `10.20.0.0/19`、AZ-b `10.20.32.0/19`、AZ-c `10.20.64.0/19`。
- 说明与办公网 `10.100.0.0/16` **不能重叠**，否则 VPN/专线回程路由冲突。
- 第 3 问要答出"不能原地扩大子网，只能在 VPC 主网段内新增子网并迁移；或预先在 /16 外再挂次网段（secondary CIDR）"。
- 第 4 问答出"是否有意为私网互信、跳板/堡垒可达性、0.0.0.0/0 出方向是否收敛、IPv6 规则是否与 IPv4 等价"。

**参考答案要点（示例划分表）**：

| 用途 | CIDR | 可用地址 | 说明 |
|---|---|---|---|
| VPC 主网段 | `10.20.0.0/16` | 65536 | 保留足够空间，避免与办公/其他 VPC 重叠 |
| AZ-a Pod | `10.20.0.0/20` | 4094 | /20 = 4096 |
| AZ-a Node | `10.20.16.0/24` | 254 | |
| AZ-b Pod | `10.20.32.0/20` | 4094 | 每 AZ 用 /19 连续块聚合 |
| AZ-b Node | `10.20.48.0/24` | 254 | |
| 中间件共享 | `10.20.96.0/23` | 510 | 只在 1 个 AZ 或跨 AZ 各划一份 |
| 预留 | `10.20.128.0/17` | 32768 | 显式留出增长，避免日后无址可分 |

- 关键教训：`172.17.0.0/16` 是 **Docker 默认网桥**，若 VPC 选了它，节点上容器网络会与云内路由重叠，出现"访问云内某个 IP 时被路由到 docker0"的经典故障。
- 路由聚合的价值：防火墙/安全组/路由表用一条 `10.20.0.0/19` 描述整个 AZ，规则数量与匹配开销都更小（也是最长前缀匹配能被合理利用的前提）。

## 作业 2：诊断"连接时通时不通 + 偶发超时"的双网卡机器（50分）

**要求**：一台服务器有 `eth0`（业务网 10.0.1.0/24，网关 10.0.1.254）与 `eth1`（管理网 10.9.0.0/24，网关 10.9.0.254），两条默认路由。现象：外部客户端访问业务端口**成功率约 90%，失败的表现为超时**；服务本身无异常日志；`ping` 业务 IP 一直正常。请：

1. 给出最可能的两个根因假设。
2. 列出你会执行的命令序列（至少 6 条）与各自要确认的点。
3. 给出修复方案（内核参数 + 路由/策略两层）。
4. 说明为什么"改完以后偶发超时消失了，但压测时 conntrack 表仍然涨得很快"，如何继续排查。

**验收标准**：
- 假设 1：**非对称路由**——请求从 eth0 进、响应从 eth1 出（因第二条默认路由 metric 更小或 rp_filter 干预），被路径上的**状态防火墙/conntrack**当作非法包丢弃。
- 假设 2：**conntrack 表接近上限 / 短连接 TIME_WAIT+端口耗尽**（呼应 s2-2），或 `ip_early_demux`/多队列网卡 RSS 哈希在 ECMP 下把同流分到不同链路。
- 命令要能覆盖：`ip route show`、`ip route get <client_ip>`（**回程走哪块网卡**，这是决定性证据）、`sysctl net.ipv4.conf.all.rp_filter`、`ip neigh show`、`ss -s` / `ss -tan state time-of-tcp`、`cat /proc/sys/net/netfilter/nf_conntrack_count` 与 `..._max`、`netstat -s | egrep -i 'drop|overflow|listen'`、`dmesg | grep conntrack`、`tcpdump -i any host <client>`（看在哪个接口看到 SYN/SYN-ACK）。
- 修复：① 删除/提高管理网默认路由的 metric，只保留一条默认路由，管理网用明细路由；② 用策略路由 `ip rule from 10.0.1.0/24 table 100` + `table 100` 内的默认路由走 eth0，实现"哪块网卡进来的从哪块出去"；③ `rp_filter` 从 strict(1) 调整为 loose(2) 或对业务口关闭（并说明安全代价）；④ conntrack 相关：调大 `nf_conntrack_max`、缩短 `nf_conntrack_tcp_timeout_established/time_wait`、对内部高流量网段用 `NOTRACK` 绕过跟踪、增加 `hashsize`。
- 第 4 问要指出：`nf_conntrack_max` 的默认值与内存大小相关（量级为每 GB 内存二三十万条，具体随内核版本而异），高并发短连接每秒新建数万条，即使 `TIME_WAIT` 缩短也仍在表内，所以**要么不跟踪（NOTRACK / 走 hostNetwork 直连）、要么扩容 + 降新建速率（连接复用）**；同时 `nf_conntrack_hashsize` 要跟得上（一般取 `max/4` 量级），否则单桶链表过长导致查表退化。

**参考答案要点（关键判据）**：
- `ip route get <客户端IP>` 若返回 `dev eth1 src 10.9.x.x`，即为回程走错网卡的确凿证据。
- 两端同时抓包：客户端看到 SYN 重传、服务端看到 SYN 但没有 SYN-ACK 出（或被丢弃），且服务端本机 `iptables -L -v` 的 DROP 计数在涨 → 状态防火墙拦截非对称包。
- 通用结论：**"90% 成功 + 超时无 RST"几乎总是"被静默 DROP"**（丢包不报错），而"refused/RST"才是"有人明确拒绝"。这个区分是本题真正要掌握的判断力（与 s1-3 小测第 6 题呼应）。
