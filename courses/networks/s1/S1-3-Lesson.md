# IP、子网划分与路由

> 这一节是"网络能不能通"的最终裁决层（重要度 4/5）。后端日常被问的"`No route to host` 和 `Connection refused` 有什么区别""为什么 Pod 里能 ping 通 IP 但域名不通""为什么加了安全组还是不通"，答案全在 IP 头、路由表和 ICMP 里。同时要掌握子网计算——不是笔试技巧，而是评审网络规划时能否一眼看出"这个 /24 放不下 300 台机器"。

## 一、IPv4 头：只记后端用得到的字段

```
| 版本4 | IHL4 | TOS/DSCP6+ECN2 | 总长度16 | 标识16 | 标志3 | 片偏移13 | TTL8 | 协议8 | 头校验和16 |
| 源 IP 32 | 目的 IP 32 | 选项(可选，长度可变) |
```

| 字段 | 作用 | 与后端的关系 |
|---|---|---|
| **TTL**（64/128 常见） | 每过一跳减 1，为 0 丢弃并回 **ICMP Time Exceeded** | 防环路；`traceroute` 的原理就是故意发小 TTL；容器/云内跳数多时 TTL 太小会莫名丢包 |
| **协议号** | 6=TCP、17=UDP、1=ICMP、41=IPv6-in-IPv4、47=GRE、50/51=ESP/AH | 安全组/IP ACL 按协议号放行；`iptables -p` 用的就是它 |
| **标识 + 标志 + 片偏移** | IP 分片三件套；标志中 **DF**=不许分片、**MF**=后面还有片 | DF + 大包丢失 = PMTUD 黑洞（s1-2 作业）；抓包过滤器 `ip[6] & 0x40` 判 DF |
| **头校验和** | 只校验 IP 头（不含载荷），每跳都要重算 | 与 TCP/UDP 校验和无关；IPv6 干脆取消了头校验和 |
| **DSCP（TOS 高 6 位）** | 差分服务标记，跨设备传递优先级 | 专线/语音/行情链路会要求打标；云上网卡通常重写 |
| **选项** | 时间戳、严格/松散源路由、记录路由 | 一旦有选项，IHL > 5，头 > 20 字节 → MSS 变小；有些实现直接丢弃带选项的包（安全风险） |

> **注意层次**：IP 的"总长度"是 16 位 → **单个 IP 包最大 65535 字节**，与 MTU 无关；超过 MTU 才需要分片。分片后的包**只有第一片带四层头**，所以防火墙/LB 对非首片的过滤能力有限——这是"分片攻击/绕过"与"偶发被拦"的根源。

## 二、CIDR 与子网计算：三个必会公式

一个地址块写作 `10.0.3.128/26`。/n 表示前 n 位是网络位，后 `32-n` 位是主机位。

1. **可用主机数 = 2^(32−n) − 2**（减网络地址与广播地址；云厂商常保留前 4 个 + 最后 1 个，AWS 是 5 个，所以实际更少）。
2. **块大小 = 2^(32−n)**，子网边界一定是块大小的整数倍。
3. **反推掩码**：`/26 → 255.255.255.192`（第 4 段 11000000 = 192），记熟 `/25=128、/26=192、/27=224、/28=240、/29=248、/30=252、/31=252+`（/31 与 /30 的差别是点对点链路特例，只 2 个可用地址）。

**实例**：要给 250 台机器划一个网段 → 需要 `2^m − 2 ≥ 250` → m = 8 → **/24**（256 地址，254 可用）。若误给 /25（126 可用）就不够，VPC 里表现为"扩不出实例"。

**网关**：惯例取子网第一个可用地址（如 `10.0.3.0/24` 的网关 `10.0.3.1`），云厂商各有固定约定（AWS 用 `.2`、GCP 用 `.1`）。**广播地址**是主机位全 1（`10.0.3.255`），网络地址是主机位全 0（`10.0.3.0`），两者都不可分配给主机。

### 特殊地址表（排障必须认得）

| 地址/段 | 含义 | 出现场景 |
|---|---|---|
| `0.0.0.0` | "本机所有接口"/未指定 | `listen 0.0.0.0:8080` 表示接受任意网卡流量；`0.0.0.0/32` 作为源地址仅出现在 DHCP |
| `127.0.0.0/8` | 环回，**整个 /8 都回到本机** | `127.0.0.2` 也可用；容器内 `localhost` 与宿主 `localhost` 不通是正常的 |
| `169.254.0.0/16` | 链路本地（APIPA / mDNS） | DHCP 失败时自动取；K8s 里见到常意味着 Pod 网络没配好 |
| `10/8`、`172.16/12`、`192.168/16` | RFC1918 私网 | 可重复使用，出公网必须 NAT；`172.17.0.0/16` 是 Docker 默认网桥，最常与内网 `172.16/12` **冲突**（典型故障：云上机器用 172.16 网段时 Docker 网段重叠导致访问异常） |
| `224.0.0.0/4` | 组播 | GOOSE、服务发现、集群心跳；交换机需 IGMP snooping 才不乱泛洪 |
| `255.255.255.255` | 受限广播 | DHCP Discover、ARP 类似角色 |

## 三、路由：最长前缀匹配，以及"包怎么走"的完整判定

主机发一个包的决策链（每一步都可能出错）：

```
1) 目的 IP 是否在本机接口/环回？        → 是：直接本地投递
2) 查路由表：匹配"最长前缀"的条目       → ip route get <dst> 可以直接问内核
3) 命中默认路由 (0.0.0.0/0)？          → 交给网关
4) 都没有                              → "No route to host" / "Network is unreachable"
5) 判断目的与本机是否同网段：
     同网段 → ARP 解析目的 IP 的 MAC
     不同网段 → ARP 解析【网关】的 MAC（MAC 是网关，IP 是最终目的！）
6) 查 iptables/nftables OUTPUT/FORWARD、云安全组 → 可能在这一步被静默 DROP
```

**核心规则：最长前缀匹配（LPM）**。内核/路由器从 `/32` 往 `/0` 找最具体的那条；命中即转发，不看后面的条目。所以：

```bash
ip route show
default via 10.0.0.1 dev eth0 proto dhcp metric 100        # 默认路由（最后兜底）
10.0.0.0/24 dev eth0 proto kernel scope link src 10.0.0.8  # 直连路由（接口配 IP 自动生成）
10.0.3.0/24 via 10.0.0.254 dev eth0                        # 静态路由：走下一跳
169.254.169.254/32 dev eth0                                # 云元数据：/32 单 host 精确匹配，优先于默认路由
```

- **`ip route get 10.0.3.5`** 是最快的定位工具：直接告诉你用哪块网卡、哪个源 IP、走不走网关。**排障时永远先跑它**（详见 s4-2）。
- **多条默认路由 / metric**：metric 小的优先（同前缀长度时比优先级）；`policy routing`（`ip rule from <src> table <t>`）实现"按源地址选路"，多网卡机器、K8s 节点双网卡最常见的坑就是**回程走了错误网卡（非对称路由）**，表现为连接时通时不通。
- **ECMP**：同一条前缀多个下一跳、权重相同 → 内核按哈希（源/目的 IP+端口）分流，用于带宽聚合与高可用（也解释了"同一目标 IP 恒定走同一链路"）。
- **`No route to host` vs `Connection refused` vs `timed out`**：这三个报错的区分是网络排障的第一课，见 s4-2 的四段定位法。

## 四、NAT：地址转换的三种形态与它们的代价

**NAT（网络地址转换）**在中间设备上重写 IP/端口，本质是"用一张连接映射表换地址不足"。

| 类型 | 行为 | 典型场景 |
|---|---|---|
| **SNAT / MASQUERADE** | 改**源** IP（+端口），内网共享公网出口 | 服务器出公网、K8s Pod 出网（`iptables -t nat -A POSTROUTING -s 10.244.0.0/16 -j MASQUERADE`） |
| **DNAT / PORT FORWARD** | 改**目的** IP（+端口），外网访问内网服务 | 公网 IP:443 → LB 内网 IP、Docker `-p 8080:80` |
| **双向/静态 NAT** | 固定映射 | 专线对接、需要固定源地址的白名单场景 |

### NAT 的四个代价，每一个都是线上问题

1. **连接数受端口与表项限制**。SNAT 到单个公网 IP，理论可复用 6 万端口 × 目的地址哈希，但实际受 **conntrack 表大小 `net.netfilter.nf_conntrack_max`** 限制。表满时新连接被直接丢弃（日志 `nf_conntrack: table full, dropping packet`），这是高并发出网服务最经典的隐形故障（详见 s4-1）。
2. **端到端原则被破坏**：外部无法主动连入内网服务 → P2P、语音、游戏需要打洞（STUN/TURN/ICE）；服务端看到的源 IP 是 NAT 出口 IP，**"按 IP 限流"会把同一办公楼所有用户一起限掉**，也要靠 `X-Forwarded-For` 还原真实客户端（s3-1）。
3. **超时与保活**：映射表项有老化时间（UDP 常 30~120 s），空闲连接会被静默回收 → 必须做**应用层心跳**（呼应 s2-2 keepalive、netty/s3-2）。
4. **分片/ALG 处理困难**：FTP、SIP 把 IP 写在载荷里，需要 ALG 改写；一旦加密（FTPS/SIPS）就失效。

> **容器与 K8s 里的 NAT 全家桶**：Service 的 ClusterIP 就是 kube-proxy 写入的 **DNAT 规则**（iptables/IPVS），Pod 出网走 **SNAT/MASQUERADE**。"Service 时延高/偶发连接失败"常与 conntrack 满、`random-fully` 缺失、DNAT 规则规模过大有关 —— 这一条在 s3-4 负载均衡处会再次出现：**云上的 Service 就是一个大规模 NAT 设备**。

## 五、ICMP：不承载业务，却是所有诊断的地基

| 类型/代码 | 含义 | 你遇到的现象 |
|---|---|---|
| 3/0 网络不可达、3/1 主机不可达、3/3 端口不可达 | 目的侧无路由 / 无监听端口 | **UDP 发到没监听的端口 → 收 ICMP 3/3 → Java 报 `Port unreachable`**（这是 UDP "Connection refused" 的来源） |
| 3/4 需要分片但 DF 置位 | PMTUD 信号 | 被防火墙吃掉就变成 **MTU 黑洞**（s1-2 作业） |
| 11/0 TTL 超时 | 中途过期 | `traceroute` 的每一行输出；路由环路也报这个 |
| 5 重定向（Redirect） | 路由器告诉你"有更优下一跳" | 同网段配错网关时出现；安全上常被关闭 |
| 8/0 echo、0/0 echo-reply | ping | `ping` 不通可能是 ICMP 被拦而 TCP 正常（**不要用 ping 判断服务可用性**） |

`traceroute`（Linux 默认发 **UDP 高端口**，Windows 用 ICMP）靠递增 TTL 逼出沿途路由器的 ICMP 11，从而列出路径；遇到不返回 ICMP 也不转发探测包的中间设备就显示 `* * *`（多为禁 ICMP 的运营商边界，不是故障）。`mtr` 是"持续 ping + 逐跳统计"，看丢包与抖动分布比 traceroute 有用得多。

## 六、IPv6：现在必须知道的差异点

- 地址 128 位、**没有 NAT**（原则上端到端可达）、**没有广播**（用组播 + **NDP** 替代 ARP）、头部定长 40 字节且**不再由中间设备分片**（源端分片 + `Packet Too Big` ICMPv6 做 PMTUD）。
- 常见地址：`::1` 环回、`fe80::/10` 链路本地（每台必有，抓包里最常见）、`fd00::/8` 私有（ULA）、`2000::/3` 全局单播。
- 写法：前导零可省、连续 0 段可用 `::` 压缩（一个地址只能用一次）；**URL 里必须加方括号** `http://[2001:db8::1]:8080/` —— 忘了方括号会导致解析端口错误，这是 IPv6 上线的经典 bug。
- 双栈排障：`getaddrinfo` 默认返回 A 与 AAAA 并按 RFC 6555 **Happy Eyeballs** 并发/优选；Java 老版本对 IPv6 支持有坑（`java.net.preferIPv4Stack=true` 是常见止血配置）。
- 工程现实：内网双栈逐步铺开，**防火墙/安全组漏配 IPv6 规则 = 事实上的绕过**，是渗透测试的常客。

## 七、三大行业场景钩子

- **电商**：多可用区 VPC 规划要按 `/16 + 每 AZ 若干 /20` 留足扩展位（AWS 的 VPC 子网不可跨 AZ 迁移，划小了要重来）；容器网段必须与办公/内网 `172.16/12` 做冲突检查；出公网走 NAT 网关，要重点监控 **conntrack 使用率与端口分配失败数**。
- **金融**：与外部机构互联常走"专线 + 静态路由 + 双侧白名单"，源地址固定（不做 SNAT 或做静态 NAT），因为对方按 IP 白名单准入；跨网段访问必须逐跳确认路由与 ACL，出现"只通某几个端口"多半是安全组/ACL 而非路由。
- **电力**：配电终端海量私网地址经运营商 APN（天然 NAT）回主站，**主站无法主动连终端** —— 所以协议必须是"终端主动上报 + 长连接 + 应用层心跳"（呼应 s2-2 与 698 协议的"主动请求-应答"设计）；采集系统按区域划分子网、路由聚合，避免主站侧路由表爆炸。

## 八、要点回顾

1. IP 头记住 TTL、协议号、分片三件套（标识/DF+MF/片偏移）、头校验和只覆盖头部。
2. 分片后的非首片不含四层头 → 中间设备过滤能力受限；MSS = MTU − 20 − 20，**有选项则更小**。
3. 子网三公式：可用主机 `2^(32−n) − 2`、块大小 `2^(32−n)`、边界是块大小整数倍；`/26→192、/27→224、/28→240、/29→248、/30→252`。
4. 特殊地址要认得：`0.0.0.0`（所有接口）、`127/8`（全段环回）、`169.254/16`（DHCP 失败）、`172.17/16`（Docker 默认，易与 RFC1918 冲突）。
5. 路由铁律是**最长前缀匹配**；跨网段时"IP 是最终目的、MAC 是网关"；`ip route get <dst>` 是定位第一步；非对称路由与多默认路由是双网卡机器的主要故障源。
6. NAT 三形态（SNAT/DNAT/双向）；四个代价：conntrack 表上限、破坏端到端可达（限流/审计要 `XFF`）、映射老化需要心跳、分片与 ALG 困难。**K8s Service 本质就是一个大 NAT**。
7. ICMP 是诊断地基：`3/3` 端口不可达（UDP 的"拒绝"）、`3/4` 分片需要（被拦则 MTU 黑洞）、`11` TTL 超时（traceroute 原理）；**不要用 ping 判断服务可用性**。
8. IPv6：无 NAT、无广播（NDP 替代 ARP）、源端分片、URL 要加方括号；安全组必须与 IPv4 同时配，否则成为绕过通道。
