# 小测验 · TCP 三次握手 / 四次挥手与状态机

> 本卷共 6 题，混合单选 / 多选 / 判断 / 填空 / 简答，满分 100 分，≥ 60 分过关。

### 1. 服务端全连接队列（accept 队列）满时，Linux 默认行为是？（15分）

- A. 立即回 RST，客户端报 `Connection refused`
- B. 静默丢弃客户端的 SYN（或丢弃第三次 ACK），客户端表现为连接超时重传
- C. 返回 ICMP 主机不可达
- D. 自动把 backlog 扩大一倍

> 答案：B
> 解析：默认 `tcp_abort_on_overflow=0` 时溢出包被静默丢弃，所以现象是 `Connection timed out` 而不是 refused；只有设为 1 才会回 RST。判据命令：`ss -lnt` 看 Recv-Q/Send-Q、`netstat -s | egrep -i 'listen|overflow'` 看 `ListenOverflows`。

### 2. `TIME_WAIT` 存在的两个根本原因是？（15分）

- A. 提高吞吐量 + 减少内存占用
- B. 保证最后一个 ACK 可重传（让对端能正常收尾）+ 让旧连接的报文在网络中消亡，避免污染同四元组的新连接
- C. 防止 SYN 洪泛 + 防止端口被扫描
- D. 加速重连 + 支持半关闭

> 答案：B
> 解析：ACK 丢失时对端会重发 FIN，主动关闭方需在 2MSL 内保留状态才能重答；同时避免迟到报文被同一四元组的新连接接收。它是保护性设计，不是缺陷；缺陷是"高并发短连接下数量堆积"，治理思路是少主动关闭而非删状态。

### 3. 【多选】关于状态机与选项，正确的有哪些？（20分）

- A. 大量 `CLOSE_WAIT` 说明本机应用没有调用 `close()`（漏关连接），长期会耗尽文件描述符
- B. SYN 与 FIN 各消耗一个序号，因此第三次握手的 ACK 号是初始 SYN 号 +1
- C. `wscale`（窗口缩放）在握手时协商，之后不可更改；不开它 16 位窗口字段最大只能表达 65535 字节
- D. 挥手必须是四次，因为 ACK 与自己方向的 FIN 之间可能还有数据要发，两个方向独立关闭

> 答案：ABCD
> 解析：四项均正确。A 的定位命令 `ss -ant state close-wait`（配合 `-p` 找进程）；C 是长肥管道必须协商的原因（与 s1-1 的 BDP 呼应）；B/D 是"为什么是这个次数"的技术答案。

### 4. 判断：为了减少 `TIME_WAIT`，应当开启 `net.ipv4.tcp_tw_recycle`。（10分）

- A. 正确
- B. 错误

> 答案：B
> 解析：`tcp_tw_recycle` 依赖 per-host 时间戳，NAT 后多客户端共享同一源 IP 时时间戳不单调，会导致**新连接被静默丢弃**（表现为部分用户随机连不上），Linux 4.12 已彻底移除。正确手段是长连接复用、`tcp_tw_reuse`（仅出站有效，需时间戳）、扩大 `ip_local_port_range`、或在 LB/网关收敛连接。

### 5. 填空题：半连接队列上限由 `tcp_max_syn_backlog` 控制，全连接队列上限是 ______ 与 ______ 取 min；队列满时可开启 ______ 用 CPU 换内存来抵御 SYN 洪泛；服务端 backlog 在内核中曾长期默认只有 ______ 。（10分）

> 答案：backlog（应用传入） / somaxconn / net.core.somaxconn / syncookies / 128

### 6. 现象：服务每次灰度发布期间，客户端报约 2 分钟的 `Connection reset` 与 `EOF`，之后自愈。请给出完整根因分析，并设计一套"零失败发布"流程（服务端 + LB + 客户端三侧）。（30分）

> 参考答案：
> - 根因：① 进程收到 SIGTERM 后关闭监听 fd，但**已建立的长连接不会因监听关闭而断开**，LB 仍按旧健康状态把新请求送到即将退出的进程；② 进程退出时对未处理完的连接直接 `close()`，缓冲区数据丢弃 → 客户端看到 RST/EOF；③ 客户端没有对"连接失效"与"业务失败"做区分，也没有安全重试（非幂等请求不敢重试）
> - 服务端侧：收到下线信号后 → **停止 accept**（关监听 fd）→ 停止接收新请求（已建立的连接不再接新任务）→ 等待 in-flight 请求完成（设上限如 30 s，超时强制关）→ 关闭业务线程池（`shutdown + awaitTermination`）→ 关闭连接池与监听
> - LB 侧：**先摘流量再关进程**：主动下线接口/置健康检查为 fail → 等 ≥ 2 个健康检查周期 + 连接排空（drain）时间 → 才发 SIGTERM；四层 LB 还要考虑客户端长连接不会重连（需 `max_age`/连接老化强制刷新，HTTP/2 用 GOAWAY）
> - 长连接/网关侧：服务端在下线前发送**应用层下线通知或 GOAWAY**，让客户端优雅切换到其他连接；客户端要能处理"收到 GOAWAY 后在新连接上重发未处理请求"
> - 客户端侧：区分错误类型（EOF/RST = 连接不可信 → 丢弃重建；超时 = 结果未知 → 只对幂等请求重试）；建连超时与读超时分别设置并小于业务超时；配指数退避 + 抖动重连，避免"发布瞬间所有客户端同时重连打爆半连接队列"
> - 可观测：发布期监控 `ListenOverflows/ListenDrops`、`TIME_WAIT/CLOSE_WAIT` 数、连接重建速率、5xx 与 `Connection reset` 计数，用它们验证"零失败"是否真的达成
> - 加分：指出若客户端与服务器之间存在 NAT，静默退出的服务端会让客户端长连接"僵尸化"，必须靠应用层心跳而非 TCP keepalive（默认 7200 s）发现
