# 面试考点 · UDP 与 Socket API 语义

> 这节的面试价值在于：**用接口语义解释线上现象**。能说出"`read()==0` 是 EOF、`write` 成功只代表进内核缓冲"的人，会被认为真写过网络程序。

## 考点 1：UDP vs TCP（必考，考的是取舍而非罗列）

**起手**：UDP 和 TCP 的区别？为什么 UDP 快？

**期望**：先讲结构性差别（无连接 / 无序号确认 / 无窗口与拥塞控制 / 8 字节头 / 保留报文边界），再讲"快"的三个来源（零握手 RTT、无重传等待即无队头阻塞、无速率收敛），最后讲代价（可靠性与顺序全归应用层、无拥塞控制会挤垮同链路 TCP）。

**追问链**：
1. 什么时候必须用 UDP？→ ① 一对多（组播/广播，TCP 做不到）；② 实时（丢帧优于延迟，超播放期限的重传无意义）；③ 极短请求-响应（DNS/NTP，省 1 RTT 与慢启动）；④ **要在用户态自定义传输层**（QUIC/DTLS/RUDP）。
2. QUIC 为什么建在 UDP 上？→ 不是为了"轻量"，而是 **TCP 的队头阻塞在传输层、应用无法绕过**，且内核 TCP 栈无法快速迭代/被中间设备固化。UDP 是"能在用户态写传输层"的唯一现实通道。
3. UDP 能可靠吗？→ 能，但要自己在应用层实现序号/确认/超时重传/去重/流控/拥塞控制——写完基本是慢版 TCP（作业 1 的体感）。所以选 UDP 的理由必须是"需要不同于 TCP 的可靠性策略"。
4. UDP 单包能多大？→ 理论上 65527，但超过 MTU 会 IP 分片，**任一片丢则整包废**且非首片无四层头；因此实践上限是"一个 MTU 内"，DNS 用 512、QUIC 做 PMTU 探测并限制初始包。

## 考点 2：系统调用语义（区分度最高）

**起手**：`read` 返回 0 和返回 -1/EAGAIN 有什么区别？

**期望**：0 = EOF（对端 FIN，连接被正常关闭）；EAGAIN = 非阻塞下当前无数据。混淆者通常没写过非阻塞网络代码。

**追问链**：
1. `write` 返回成功意味着？→ 进入**本体内核发送缓冲区**，不代表对端收到。业务可靠要应用层 ACK（RPC 响应 / MQ ack / 支付回执）。
2. TCP 保证什么、不保证什么？→ 保证"本机内核 → 对端内核"的有序可靠交付；**不保证对端应用读取并处理成功**。这一句是分布式系统所有幂等/对账设计的根基。
3. `connect` 返回成功说明什么？→ 三次握手完成，对端**内核**在；不代表应用可用 → 所以连接池必须有探活/心跳（呼应 s2-2、netty/s3-2）。
4. 想只关一半怎么办？→ `shutdown(SHUT_WR)` 半关闭（发完还能收），`close()` 双向；`SO_LINGER=0` 直接 RST 并丢弃未发数据。
5. `listen(backlog)` 是设什么？→ 全连接队列长度（实际取 `min(backlog, somaxconn)`），半连接队列由 `tcp_max_syn_backlog` 控制；`accept` 从全连接队列取（s2-2 展开）。
6. 一个端口能有多少连接？→ 靠五元组区分，服务端可达数十万；客户端才有本地端口耗尽（`ip_local_port_range` + `TIME_WAIT`，报 `Cannot assign requested address`）。
7. `SO_REUSEPORT` 解决什么？→ 多进程/多队列同端口监听，内核按流哈希分流，消除 accept 惊群与单锁瓶颈（Nginx `reuseport`、Redis 6、Netty 多 group）。

## 考点 3：Java 特有的坑

**起手**：Java 里用 UDP/Socket 遇到过什么奇怪异常？

**期望（任答其二即有实战感）**：
- `PortUnreachableException`：UDP 收到 ICMP 端口不可达（对端未监听/NAT 映射老化），下一次读写才抛出；处理是幂等重试 + 重建 socket（Java 不暴露 `MSG_ERRQUEUE`）。
- `SocketException: Broken pipe` / `Connection reset by peer`：前者对端已关闭（写触发），后者收到 RST（往往因为对端进程崩溃后你继续写，或本机有未读数据时对端已关）。
- `setTcpNoDelay(true)` 忘了开 → 小包延迟 40 ms（Nagle + 延迟 ACK 交互，s2-3）。
- `Socket.setSoTimeout(0)` = 永不超时，最危险的生产默认；DNS/负载均衡场景 `InetAddress.getAllByName` 是**阻塞调用**，会卡住事件循环（Netty 里必须走 resolver 或业务线程池，netty/s2-1）。
- 只监听 `127.0.0.1` 或只监听 IPv6 `::1` → "本地能通、远程不通"（`IPV6_V6ONLY`）。

## 考点 4：设计题（把本节当成决策依据）

**起手**：设计"海量终端上报 + 主站下发指令"，你会用 TCP 还是 UDP？

**期望要点**（评审的是推理链，不是结论）：
- 终端量大且经 NAT → **主站无法主动连终端**（s1-3），所以下发必须由终端保持长连接、主站复用该连接推送 → 需要双向通道，倾向 **TCP/长连接（或 MQTT）** 而不是裸 UDP。
- 若链路质量差且实时性优先（告警、控制命令）→ 可用 UDP/组播 + 应用层序号确认 + 补推通道（金融行情就是"组播主推 + TCP 补包"双通道）。
- 上报侧：小报文高频 → 批量 + 压缩 + 长连接复用；要评估 **PPS 与新建连接速率**（往往比带宽先到瓶颈，因为每包每连接都有固定 CPU/表项成本）。
- 兜底要求：幂等（唯一流水号）、顺序（终端侧带序号）、可靠性判据（应用层 ACK，超时判"未知"而非"失败"）、可观测（重传率、心跳失效数、conntrack 使用率）。

**通用作答模板**：先说清"要解决什么、能容忍什么"（丢包?乱序?延迟?重复?），再选传输层，再补应用层机制。能这样答，就说明你把本节和 s1-1 的复杂度思维连起来了。
