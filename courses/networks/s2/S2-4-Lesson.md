# 拥塞控制、粘包拆包与队头阻塞

> 本节把三件看似不相关、实则同源的"网络麻烦"放在一起：**拥塞控制**（别把网络淹了）、**粘包拆包**（TCP 是字节流，应用要自己定界）、**队头阻塞**（有序 + 可靠带来的结构性代价）。三者共同解释了"为什么 TCP 快不起来""为什么 HTTP/2 有了多路复用还是卡""为什么 QUIC 要换 UDP"。（重要度 5/5，核心精讲；承接 s2-3，铺垫 s3-2）

## 一、拥塞控制 vs 流量控制：两个窗口各管一段

- **流量控制 rwnd**：保护**接收端**（s2-3）。
- **拥塞控制 cwnd**：保护**网络中间链路**（路由器队列、带宽）。发送方无法直接感知网络容量，只能从"丢包 = 拥塞信号""延迟增大 = 即将拥塞"这些间接反馈里推断。
- 二者共同决定：**可发 = min(rwnd, cwnd)**。

拥塞的经典信号是**丢包**（尾丢弃 / RED），新一代（BBR）还引入**RTT 增大 + 投递速率**作为信号。

## 二、Reno 四阶段：慢启动 → 拥塞避免 → 快重传 → 快恢复

```
cwnd
 │                         /\   拥塞避免(线性+)
 │            /\          /  \ /
 │      /\   /  \   _____/    X  ← 丢包:cwnd*=0.5 回到拥塞避免(有SACK/快速恢复)
 │     /  \ /  \ /            \____
 │    / 慢启动(指数×2)             
 │___/  从 10 个 MSS 起                
 └────────────────────────────────────▶ 时间
      ssthresh(慢启动阈值)
```

1. **慢启动（slow start）**：连接刚建、cwnd 未知，从约 **10 个 MSS**（`init_cwnd`）起，**每收到一个 ACK，cwnd += 1 MSS**，效果是**每个 RTT 翻倍（指数增长）**。名字"慢"是相对一上来就填满，其实增长极快。
2. **拥塞避免（congestion avoidance）**：cwnd 达到阈值 `ssthresh` 后改为**每个 RTT 只 +1 MSS（线性）**，谨慎试探容量。
3. **快重传（fast retransmit）**：3 个 dupACK → 立即重传丢失段（s2-3）。
4. **快恢复（fast recovery）**：因 dupACK 说明网络还活着（后续段到达了），不像超时那样绝望 → `ssthresh = cwnd/2`、`cwnd = ssthresh`，**直接进入拥塞避免**，而不是回到慢启动。
   - **超时（RTO）**才是重罚：`ssthresh = cwnd/2`、`cwnd = 1 MSS`、**重回慢启动** —— 这就是"一次超时，吞吐断崖"。

> 关键区分（面试必问）：**丢包走超时 → 回到慢启动（cwnd=1）；只收到 dupACK → 快重传+快恢复（cwnd 减半）。** 二者对吞吐的影响天差地别。

## 三、CUBIC 与 BBR：现代两派

| 维度 | CUBIC（Linux 默认） | BBR（Google） |
|---|---|---|
| 拥塞信号 | **丢包**（包基数 AIMD 变体） | **带宽 + RTT** 建模（不靠丢包） |
| cwnd 增长 | 三次函数逼近最大窗口，高 BDP 下更猛 | 探测 `BDp`（带宽×最小RTT），维持在该点 |
| 浅缓冲友好性 | 需要一定缓冲，否则吞吐抖动 | 不需要大缓冲 |
| 深缓冲（bufferbloat）问题 | 会把队列填满 → 延迟暴涨仍不减速 | 靠 RTT 感知排队，主动降速 |
| 公平性 | 与 CUBIC 流公平 | 与丢包型算法共存时"抢带宽"，有争议 |
| 适用 | 通用、丢包≈拥塞的传统内网 | 高丢包广域网、移动弱网、跨地域 |

**一句话**：CUBIC 假设"丢包=拥塞"，BBR 假设"我能测出管道真实容量并填满它，不该靠制造丢包来试探"。**跨地域/弱网/有 QoS 专线**越来越倾向 BBR（`tcp_congestion_control=bbr` + `fq`）。

## 四、粘包 / 拆包：TCP 是字节流，不是消息流

**根因**：TCP 只保证"字节有序送达"，**不保留应用侧的写边界**。你在代码里 `write(a)`、`write(b)` 两次，对端 `read()` 可能一次读到 `a+b`（粘包），也可能只读到 `a` 的前半（拆包/半包）。发送方向的 Nagle 攒包、接收方向的缓冲、MSS 分片都会加剧。

> 常见误解纠正：**"粘包/拆包是 TCP 的特性，不是 bug"**，UDP 有消息边界不会粘包，但代价是不可靠（s2-1）。凡是自定义 TCP 协议都必须**在应用层自己定界**。

**四种定界方案（背下来 + 会选型）**：

| 方案 | 做法 | 优缺点 | 代表 |
|---|---|---|---|
| **固定长度** | 每包定长，不足补位 | 简单浪费或受限 | 早期二进制协议 |
| **分隔符** | 用特殊字节（`\r\n`）分界 | 直观；正文含分隔符需转义 | HTTP 头部、Redis RESP |
| **消息头带长度（推荐）** | 头部字段声明 body 长度 | 通用高效，工业标准 | LengthFieldBasedFrameDecoder、Dubbo、gRPC(HPACK 帧) |
| **高层协议自带边界** | 依赖协议帧结构 | 复用时透明 | HTTP Content-Length/Chunked |

**Netty 落地**（详见 netty/s2-3）：`LengthFieldBasedFrameDecoder(maxFrameLength, lengthFieldOffset, lengthFieldLength, lengthAdjustment, initialBytesToStrip)` 五参数解决绝大多数"头部含长度"的协议；解码不足一个包就**累积等待**（半包），这就是 `ByteToMessageDecoder` 的机制。

## 五、队头阻塞（Head-of-Line Blocking）：可靠有序的结构性代价

**定义**：一个单元受阻，后面即使就绪也得排队。TCP 世界里有三层：

1. **传输层队头阻塞（TCP 的宿命）**：TCP 保证按序交付，**只要一个段没到，即使后续段都到了也不能向应用交付**（要么缓存等待、要么丢）。丢一个包 → 整条连接的所有后续数据都卡到重传成功。这是**一条 TCP 连接内部**的问题。
2. **HTTP/1.x 应用层队头阻塞**：一个连接同一时刻只处理一个请求-响应（pipelining 也要求按序回，且主流浏览器/服务器基本禁用），前一个慢请求阻塞后一个 → 只能靠**开多条 TCP 连接**（浏览器 6 连接上限）绕过。
3. **HTTP/2 把问题从应用层"下沉"到 TCP**：h2 在**一条 TCP** 上用多路复用交错多个流，消灭了应用层 HOL；**但一旦丢一个 TCP 段，所有复用在这条连接上的流全部被阻塞**（回到第 1 层）。这就是"h2 解决了应用层 HOL，却受制于传输层 HOL"。

**破局 = QUIC/HTTP3**：把可靠性做到**用户态、每条流独立重传**，用 UDP 承载（s3-2）。一个流丢包只阻塞该流，别的流照常交付 —— **这才是 QUIC 消灭传输层队头阻塞的本质**（不是"因为用 UDP"这么简单，而是"每条流有自己的序号与重传"）。

## 六、四者的因果串联（本节灵魂）

```
想可靠有序  ──► TCP 按序交付 + 丢包重传
                      │
              丢一个段就卡住整条连接 ──► 传输层队头阻塞
                      │
        为绕过它 ──► HTTP/1 多连接 / HTTP/2 多路复用(仍一条TCP)
                      │
              h2 仍被 TCP 队头阻塞卡死 ──► 换 QUIC(每流独立,建于 UDP)
```
而**拥塞控制**是"网络尺度"的约束：cwnd 决定同时在途多少字节，丢包既触发重传（队头阻塞）又触发 cwnd 收缩（降速），三者在一根网线上互相拉扯 —— 理解了这条链，才能读懂 s3-2 为什么"HTTP/2 在某些弱网下还不如 HTTP/1.1 多连接"。

## 七、Java / 运维可观测

```bash
# 例子目的：查看当前拥塞算法与逐连接 cwnd/rtt/retrans，并示范切到 BBR
ss -tin                      # cwnd: rto: rtt: retrans: 全在里面
sysctl net.ipv4.tcp_congestion_control   # 当前算法(常为 cubic)
sysctl net.ipv4.tcp_available_congestion_control   # 本内核可用的算法列表
# 切 BBR（需模块已加载）：
#   modprobe tcp_bbr
#   sysctl -w net.core.default_qdisc=fq
#   sysctl -w net.ipv4.tcp_congestion_control=bbr
# 正确用法结果：切换后 sysctl net.ipv4.tcp_congestion_control 回显 bbr，新建连接即用 BBR（存量连接不变）
# 错误用法：只改 tcp_congestion_control=bbr 不配 default_qdisc=fq → BBR 缺 pacing 器，效果大打折扣（不报错但吞吐不达预期）
# 错误用法：modprobe tcp_bbr 失败就强写 bbr → sysctl 报 cannot create /proc... 或值写不进去（内核未编入该算法）
```
- Java 层没有"拥塞算法"开关（内核态），但连接池的**最大在途/并发**、gRPC/Netty 的 **flow control window** 是在应用层复现"别让对端/网络过载"的同类思想（netty/s3-2 背压）。
- 自定义协议**必须**定界：不要假设“一次 read = 一条完整消息”，这是新手写 TCP 协议最常踩的坑。

## 八、三大行业场景钩子

- **电商**：跨地域访问（用户→源站）RTT 高、公网丢包，CUBIC 在丢包链路上 cwnd 反复腰斩 → P99 长尾；源站前置**全站加速/QUIC**，用 BBR 或 h3 抹平长尾。
- **金融**：专线低丢包，CUBIC 足够且公平可控；重点是**应用层协议定界**（FIX/ISO8583 over TCP）——消息边界错乱等于账目错乱，LengthField 定界 + 校验 + 序号缺一不可。
- **电力**：海量终端窄带宽高丢包，TCP 队头阻塞 + 慢启动反复重来让"上报一条数据要好几秒"；因此主站普遍推动 **MQTT over TCP（小报文 + 定界清晰）**，并评估 **QUIC** 终端接入以规避传输层 HOL，弱网下体验提升明显。

## 九、要点回顾

1. **可发 = min(rwnd, cwnd)**：流量控制保护对端、拥塞控制保护网络。
2. Reno 四阶段：**慢启动(指数)→拥塞避免(线性)→（dupACK）快重传+快恢复(cwnd 减半) / （超时）回慢启动(cwnd=1)**。
3. **CUBIC** 以丢包为信号、需缓冲；**BBR** 以带宽+RTT 建模、浅缓冲友好、抗丢包但公平性有争议。
4. TCP 是**字节流不保留写边界** → 粘包/拆包是特性不是 bug → 应用层**定界**（长度字段最通用，Netty `LengthFieldBasedFrameDecoder`）。
5. 队头阻塞三层：**传输层(TCP 按序的宿命) / HTTP1 应用层 / HTTP2 下沉到 TCP**；**QUIC 用"每流独立重传"消灭传输层 HOL**，不是简单"换了 UDP"。
6. 因果链：可靠有序→按序交付→丢包即卡→HOL→多连接/多路复用→QUIC。
