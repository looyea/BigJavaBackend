# TCP 可靠传输与流量控制

> 上一节解决了"连接怎么建、怎么关"，本节解决"连上之后，字节怎么一个不丢、一个不重、还不至于把对端淹死"。这是理解**重传风暴、RTO 抖动、零窗口卡死、GC 停顿引发连接雪崩**的底层模型。（重要度 5/5，核心精讲；承接 s2-2，为 s2-4 拥塞控制铺垫）

## 一、TCP 要对抗的四类故障

网络层（IP）只提供"尽力而为、不保证送达、可能乱序/重复/损坏"的服务。TCP 在其上用四件套保证可靠：

| 故障 | 检测手段 | 恢复手段 |
|---|---|---|
| 损坏 | 校验和 checksum | 丢弃 → 触发重传 |
| 丢失 | 超时 RTO / 重复 ACK / SACK | 重传 |
| 乱序 | 序号排序 + 重组缓冲 | 按序交付应用 |
| 重复 | 序号去重 | 丢弃副本 |

核心机制一句话：**序号 + 确认 + 超时重传 + 滑动窗口**。

## 二、ARQ：从停等到滑动窗口

**停止等待 ARQ**  simplest：发一个段，等 ACK 再发下一个。问题：信道利用率极低。量化 —— 带宽 1 Gbps、RTT 20 ms、MSS 1460 B：停等有效吞吐 = `1460 B / 20 ms ≈ 580 kbps`，只用了 0.06% 的带宽。这就是"带宽时延积 BDP"（s1-1）要解决的场景。

**滑动窗口**：接收方在 ACK 里通告 `win`（我还能收多少字节），发送方维护一个可以**连续发而无需逐个等待**的窗口：

```
        已确认          已发送未确认(在途)         允许发送(窗口内未发)        不允许
  ...────────┼─────────────────┼──────────────────────┼────────────────...
           lastACK          nextSeq(发指针)          窗口右沿=ack+rwnd
```

- 接收窗口 `rwnd`（receive window）：**流量控制**用，防止发送方淹没**接收方**缓冲区。
- 拥塞窗口 `cwnd`：**拥塞控制**用，防止淹没**网络**（下节 s2-4）。
- **实际可发 = min(rwnd, cwnd)** —— 两个窗口共同决定发送速率，是本节与下节的交汇点。

## 三、确认机制：累积确认 + SACK

- **累积确认（cumulative ACK）**：ACK 号 = "我按序收到的下一个期望字节"。收到 1,2,3 就回 ACK(4)，即便 3 后面还收了 5，也只确认到 4。优点：一个 ACK 覆盖多个段、天然抗乱序；缺点：**丢一个包，后面全堵**（队头阻塞的根源之一）。
- **延迟确认（delayed ACK）**：不必每收一个段就回 ACK，最多攒 2 个段或 40 ms（Linux `TCP_DELACK_MIN`）。省带宽，但与 Nagle 交互有坑（见第六节）。
- **SACK（选择性确认）**：握手 `sackOK` 协商后，ACK 选项里可带"我实际收到的不连续块"，如 `SACK=6,9` 表示 6~8 到了。发送方能**只重传真正丢的段**，而非从第一个缺口全重传。没有 SACK，一个段丢失会引发"重传一整窗"的浪费。
- **DSACK**：告知对端"你重传的这个我早收到了"，帮助对端识别"ACK 丢失导致的伪重传"、修正 RTT 估算。

## 四、超时重传 RTO 与 Karn 算法

设窗口只能靠超时兜底时，**RTO 定多少**是关键：太短→没必要的重传（放大拥塞），太长→恢复慢。

- **Jacobson/Karels 算法**（Linux 实现）：对每次 RTT 采样维护 `SRTT`（平滑）与 `RTTVAR`（抖动），
  ```
  err   = r - SRTT
  RTTVAR += (|err| - RTTVAR) / 4      // g=1/4
  SRTT   += (err   - SRTT)   / 8      // h=1/8
  RTO = SRTT + 4 * RTTVAR             // k=4，α=1/2 β=1/4 的经典形式
  ```
  Linux 边界：`RTO_MIN=200ms`、`RTO_MAX=120s`，初值 1 s。
- **超时指数退避**：某段超时后，重传的 RTO 翻倍（`tcp_retries2` 默认 15 次控制总重试时长，约 13~30 分钟才彻底放弃）。
- **Karn 算法**（必考）：**重传的段不用于 RTT 采样**。因为无法区分收到的 ACK 是确认原包还是确认重传包，用它算 RTT 会污染估计。**推论**：拥塞导致 RTT 变大时，Karn 无法从重传采样更新，RTO 会"冻结"恶化 —— 这正是需要**时间戳选项（RTTM）**的原因：带时间戳可以用重传段度量 RTT，突破 Karn 限制（`tcp_timestamps` 默认开）。

## 五、快速重传与恢复：不等到超时

超时太重（至少等一个 RTO）。现代 TCP 主要靠**冗余 ACK** 快速反应：

- **快速重传**：同一 ACK 被重复收到 **3 次**（即 dupthresh=3，说明后面已到 3 个段但中间缺 1 个）→ 立即重传缺失段，不等 RTO。
- **快速恢复**：配合**拥塞避免**把 cwnd 减半而非重置到 1（下节细讲）。
- **RTO 与快速重传的分工**：丢包后若还有后续段到达 → 触发 dupACK → 快速重传；若一整窗都没回来（尾部丢包/严重拥塞）→ 只能靠 RTO 兜底。**"尾部丢失（tail loss）"** 是快速重传的盲区，靠 RTO 或 SACK 补齐。

## 六、流量控制与零窗口：rwnd 的生死线

接收方缓冲区快满时把 ACK 的 `win` 报成很小的值甚至 **0**，发送方必须停止发送，只能维持**至少一个段**的探测：

- **零窗口探测（persist timer / 持续连接计时器）**：发送方窗口为 0 后，定时发 **1 字节探测段**（ZWP, Zero Window Probe），逼接收方回一个带新窗口的 ACK。探测间隔通常指数退避。
- **窗口更新报文丢失死锁**：接收方腾出空间后发的"窗口更新 ACK"若丢失，双方都以为对方在等自己 → **永久死锁**。破解：接收方收到 ZWP 后**必须回带当前窗口的 ACK**；发送方 persist 定时器持续探测。这是"TCP 粘住不动、抓包看到零星 1 字节 probe"的经典成因。
- **窗口缩放 wscale**：16 位 `win` 最大 65535，长肥管道（大 BDP）不够用，握手协商 `wscale`（最大 ×2^14），才能表达 GB 级窗口。没协商 wscale 是高吞吐链路"跑不满"的隐形原因。

> **接收缓冲区与 GC/慢应用的连锁**：Java 应用处理慢（Full GC 1 s）→ 不及时 read → 内核接收缓冲涨满 → 通告 rwnd=0 → 上游发送被卡。上游若也是同步阻塞 + 线程池有限，就逐级反压成雪崩。**所以 `SO_RCVBUF` / `tcp_rmem` 与"消费速度"要一起看**，光调大缓冲区只是把死线往后推。

## 七、Nagle 与延迟 ACK 的恶性交互（200ms 延迟之谜）

- **Nagle 算法**（`TCP_NODELAY` 关闭时默认开）：为了消灭大量"1 字节包"的小包洪水 —— **有未确认的小段时，攒够一个 MSS 或有 ACK 回来才发下一批**。省带宽但增加延迟。
- **延迟 ACK**：收方攒最多 40 ms 再回 ACK。
- **交互死锁**：A 用 Nagle 发小包在等 ACK，B 用 delayed ACK 在攒数据/等第二个包再一起确认 → 两等 → 每次交互被拖到 **40 ms（delayed ACK 超时）**，表现为"小请求成对往返时多出一个 ~40 ms"。
- **对策**：**交互式/请求-响应协议（RPC、数据库、SSH）一律 `setTcpNoDelay(true)` 关 Nagle**；批量传输场景可留 Nagle。这是 s4-1 Socket 选项调优的高频项。

## 八、乱序与重复段处理

- 接收方用序号把乱序段放入重组队列，只有"按序补齐缺口"才向应用交付（**TCP 保证有序字节流**，代价就是缺口引发队头阻塞）。
- 重复段（副本）按序号识别丢弃。
- 乱序常见来源：多路径路由、早先丢包的快速重传超越、网卡多队列 RSS。适度乱序会误伤 RTT 估计，时间戳选项（PAWS）帮助丢弃"迟到太久的旧段"。

## 九、Java / Linux 侧可观测与可调

```java
socket.setTcpNoDelay(true);   // RPC/低延迟必开：关 Nagle（第七节）
socket.setSoTimeout(3000);    // 读超时，防被零窗口/CLOSE_WAIT 卡死
// SO_RCVBUF 不设则内核自动调（tcp_rmem: min default max）
```

```bash

sysctl net.ipv4.tcp_retries2         # RTO 重试上限

netstat -s | grep -i 'retrans'       # 全机重传计数，突增=网络或接收方出问题了
```

## 十、三大行业场景钩子

- **电商**：秒杀链路里 Redis/DB 客户端偶发"稳定 +40 ms"，根因是默认 Nagle 与延迟 ACK 交互；网关侧统一 `TCP_NODELAY` 后 P99 显著收敛。
- **金融**：行情/交易专线要求低抖动，RTO 抖动会放大成"重传风暴→更拥塞→RTO 更长"的正反馈，因此专线普遍开 SACK + 时间戳，并把 `tcp_retries2` 收紧让快速失败走切换而非死等。
- **电力**：主站采集海量终端弱网高丢包，若关 SACK 则一丢包重传整窗、上行本就窄的带宽被打满；终端固件应启用 SACK、合理 rwnd，主站侧零窗口探测参数要与终端 idle timeout 对齐，避免"僵尸连接占坑"。

## 十一、要点回顾

1. 可靠 = **序号 + 累积确认 + 超时/快速重传 + 滑动窗口**，对抗损坏/丢失/乱序/重复四类故障。
2. **实际可发 = min(rwnd 流量控制, cwnd 拥塞控制)**；rwnd 防淹没对端，cwnd 防淹没网络。
3. 累积确认天然抗乱序但造成队头阻塞；**SACK** 让只重传真正丢的段。
4. **RTO** 用 Jacobson/Karels（SRTT+4·RTTVAR）估、超时指数退避；**Karn 算法**规定重传段不采样，靠**时间戳**突破其限制。
5. **快速重传**（3 个 dupACK）先于超时；尾部丢失靠 RTO/SACK 兜底。
6. 流量控制红线：**零窗口** → **persist 探测** → 窗口更新丢失用 ZWP 破解死锁；大 BDP 必须 **wscale**。
7. **Nagle × 延迟 ACK = 40 ms 魔咒**，交互式协议一律 `TCP_NODELAY`。
8. 慢消费（Full GC）→ 接收缓冲涨满 → rwnd=0 → 逐级反压雪崩；调 buffer 只是延后死线。
