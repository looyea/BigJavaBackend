# 小测验 · UDP 与 Socket API 语义

> 本卷共 6 题，混合单选 / 多选 / 判断 / 填空 / 简答，满分 100 分，≥ 60 分过关。

### 1. 非阻塞 socket 上 `read()` 返回 0，含义是？（15分）

- A. 当前没有数据可读，等可读事件再来
- B. 对端已关闭写方向（收到 FIN），本端读到 EOF
- C. 参数 length 传了 0，属于编程错误
- D. 内核缓冲区被重置，需要重连

> 答案：B
> 解析：`read()==0` 表示 EOF（对端 FIN），是"连接被正常关闭"的唯一常规信号；"暂时没数据"在非阻塞下是 `-1 + EAGAIN/EWOULDBLOCK`。把两者混淆会导致连接池里的死连接被发现不了，或者对端已关还在写。

### 2. `write()/send()` 成功返回 100，能确定什么？（15分）

- A. 对端已经收到这 100 字节
- B. 这 100 字节已进入本体内核发送缓冲区（可能被对端收到，也可能丢失）
- C. 对端应用层已处理完这 100 字节
- D. 数据已经离开网卡

> 答案：B
> 解析：`write` 只代表"交给内核"。之后是否发出、是否到达、是否被应用处理，与这个调用无关。因此业务级可靠必须靠**应用层 ACK**（MQ producer ack、RPC 响应、支付回执/对账），这是本节最重要的一条语义。

### 3. 【多选】关于 UDP 与 Socket API，正确的有哪些？（20分）

- A. UDP 保留报文边界：一次 `send` 对应一次 `recv`，不会半包，但接收缓冲区小于包体时会被截断
- B. UDP 上的 `connect()` 不产生任何网络交互，只是设置内核中的默认目的地址，之后可用 `send/recv` 并过滤其他来源
- C. `shutdown(SHUT_WR)` 能实现半关闭（我说完了还能听），而 `close()` 是双向一起关
- D. 一个监听端口只能服务一个连接，所以高并发必须开很多端口

> 答案：ABC
> 解析：D 错。连接由**五元组**唯一确定，服务端靠不同的客户端 IP/端口区分成千上万连接；只有客户端才有本地临时端口耗尽问题。A/B/C 都是常被误用的接口语义。

### 4. 判断：QUIC/HTTP/3 建在 UDP 之上，主要原因是 UDP 实现更简单、CPU 开销更低。（10分）

- A. 正确
- B. 错误

> 答案：B
> 解析：真正原因是 **TCP 的队头阻塞发生在传输层、无法被应用绕过**（一个连接上一个段丢失会阻塞所有流），以及 TCP/IP 逻辑在内核态、协议难以快速迭代。QUIC 在用户态自研可靠传输与拥塞控制，做到**按流独立重传**、0-RTT、连接迁移。UDP 只是"允许我们在用户态自己写传输层"的载体。

### 5. 填空题：UDP 头部长度是 ______ 字节；IPv4 下 UDP 报文超过 ______ 会触发 IP 分片，而分片的致命弱点是 ______ ；`SO_LINGER` 设为 0 时 `close()` 会发送 ______ 而不是 FIN。（10分）

> 答案：8 / MTU / 任一分片丢失则整个数据报作废且不重传 / 非首片无四层头 / RST

### 6. 场景：一个 Java 服务用 UDP 向采集终端发指令，偶发 `PortUnreachableException`；另有 TCP 客户端偶发"发送成功但下游说没收到"。请分别解释两种现象的成因，并给出各自的处理设计。（30分）

> 参考答案：
> - **UDP 的 `PortUnreachableException`**：对端端口无监听时主机会回 ICMP Type3 Code3（端口不可达），内核把它记录在该 UDP 套接字的**错误状态**上（连接过的 UDP 才会收到并上报），下一次 `send/recv` 就以该异常抛出。成因多为：终端下线/NAT 映射老化（呼应 s1-3）、对端进程重启、目标端口配错。处理：① 视为可重试的传输失败，按指令幂等重试；② 用"终端主动注册 + 心跳"维持可达视图，不向不可达地址发指令；③ 需要屏蔽时可用 `connect` 后的错误上报机制做区分（Linux 下靠 `IP_RECVERR` + `recvmsg(MSG_ERRQUEUE)` 主动读走 ICMP 错误，Java 未直接暴露，因此常见做法是**捕获该异常后重建 socket 并重试**），但根本解法仍是**应用层 ACK + 重发队列**
> - **TCP"发送成功但下游没收到"**：`write` 只保证进入内核发送缓冲区（第 2 题），随后可能：连接被 RST 中断、对端 backlog 满、对端进程崩溃导致缓冲数据丢弃、中间设备/NAT 丢弃、对端读了但处理失败。处理：① 业务级**请求-应答/确认**（RPC 响应、MQ ack），必要时带唯一流水号做**幂等 + 对账**；② 打开 `TCP_NODELAY` 避免小包被 Nagle 延迟；③ 写失败/读到 EOF 必须判定连接不可信并丢弃该连接（连接池不能复用可疑连接）；④ 超时不等于失败——只能判"结果未知"，必须靠查询/对账收敛（这是支付场景的铁律）
> - 加分：能指出"TCP 保证的是本机内核到对端内核的可靠交付，不保证对端应用处理成功"——把传输层可靠性和业务可靠性分清，就是本节的核心结论
