# UDP 与 Socket API 语义

> 这一节有两个作用：一是补上 UDP（很多人只会说"UDP 快"，说不清它快在哪、什么时候必须用它）；二是把 **Socket API 这套你要天天调用的接口语义**讲透——`connect` 到底做了什么、`write` 返回 100 是什么意思、`close` 之后数据去哪了。这些是 Netty、RPC 框架、连接池所有行为的解释基础（对应 netty 包全篇）。

## 一、UDP 头：8 字节换来的自由

```
| 源端口 16 | 目的端口 16 | 长度 16 | 校验和 16 |  数据 …
```

- 只有 8 字节头部（TCP 至少 20），**无连接、无序号、无确认、无窗口、无拥塞控制**。
- 长度字段 16 位 → 数据报上限 65535 字节，但实际受 MTU 约束：**超过 MTU 会触发 IP 分片**，而 IP 分片"任一片丢失则整个数据报作废"，且不重传。所以 UDP 应用层的实用上限是"一个包能装多少"（DNS 曾长期以 512 字节为界，后来靠 EDNS0 提高；QUIC 用 PMTU 探测 + 限制初始包大小）。
- 校验和：IPv4 下可选（很多内网环境依赖网卡 offload，实际常开启），IPv6 强制。它只能发现错误、**不能纠错、不会重传**。

## 二、UDP 快在哪、慢在哪（把"快"量化）

**快的三个来源**：

1. **没有握手**：TCP 要 1 个 RTT 才能发数据，UDP 第一个包就带数据。（QUIC 靠 0-RTT/1-RTT 握手 + 与 TLS 融合，把这一优势部分夺回，见 s3-2。）
2. **没有重传与顺序等待**：TCP 丢一个段就要等重传或等快速重传，导致后续数据在应用层**排队等待**（队头阻塞）；UDP 直接跳过。
3. **没有拥塞控制的速率约束**（这既是优势也是危险品，见下文）。

**代价与"慢"的地方**：

- 可靠性、顺序、流控**全部由应用层自己实现**，实现不好的话比 TCP 更慢更差（等于在应用层重写一遍 TCP，还重写不好）。
- 没有拥塞控制 → **自私**：一条 UDP 流会不断吃带宽直到丢包，而 TCP 会退让。历史上 UDP 业务挤垮同链路 TCP 业务是真实事故，这也是 QUIC 必须自己实现拥塞控制的原因。
- 报文边界保留：好处是"一次 `send` 就是一次 `recv`"，坏处是**大报文要么分片要么丢弃**，不像 TCP 可以流式写。

| 维度 | TCP | UDP |
|---|---|---|
| 连接 | 面向连接，五元组状态机 | 无连接，`connect` 只是本地设置默认目的 |
| 交付 | 可靠、有序、去重 | 尽力而为，可能丢/重复/乱序 |
| 边界 | 字节流，**无边界**（需应用层定界，s2-4） | 数据报，**保留边界** |
| 流控/拥塞 | 内置（窗口 + 拥塞控制） | 无，需应用层自己做 |
| 头部开销 | 20~60 B + 选项 | 8 B |
| 建连开销 | 1 RTT（+ TLS 1/2 RTT） | 0 |
| 典型场景 | HTTP/1.1/2、RPC、DB、MQ | DNS、NTP、SNMP、实时音视频、QUIC、游戏 |

## 三、UDP 的四类真实用途（不只是"实时"）

1. **请求-响应且极短**：DNS（s3-4）、NTP、SNMP、Radius。一次一问一答，用 TCP 要付出建连与慢启动的成本，且 DNS 的 512 字节限制本来就是为 UDP 设计的。
2. **实时性优先于完整性**：语音/视频/直播（RTP）、云游戏、投屏。丢一帧不如晚一帧，重传已无意义（播放期限已过）。
3. **一对多**：**组播**（`224/4`，同网内一份流量发给多接收者，金融行情分发、变电站 SV/GOOSE 都用它）与**广播**。TCP 做不到一对多。
4. **承载"自带可靠性的新传输层"**：QUIC/HTTP3、DTLS、UDT、RUDP、各家自研可靠 UDP。**趋势是"把传输层搬到用户态"**——好处是可以自己决定重传粒度（按流而非按连接）、连接迁移、快速迭代（不受内核升级周期约束）。这是理解 QUIC 的关键视角。

### Java 里的 UDP

```java
// 例子目的：用 DatagramSocket 写一个 UDP 回显服务端——收到数据报原路发回（保留报文边界）
try (DatagramSocket sock = new DatagramSocket(9876)) {        // 绑定本地端口 9876（Java 9+ 有 joinGroup 支持组播）
    byte[] buf = new byte[1024];                               // 接收缓冲：必须 ≥ 对端可能发来的最大报文
    DatagramPacket p = new DatagramPacket(buf, buf.length);
    sock.receive(p);                                           // 阻塞直到收到一个数据报（保留边界）
    String msg = new String(p.getData(), 0, p.getLength(), StandardCharsets.UTF_8);   // 只取实际收到的 p.getLength() 字节
    sock.send(new DatagramPacket(msg.getBytes(), msg.length, p.getSocketAddress())); // 回发给数据来源地址
}
// 正确用法结果：客户端 send "hi" 后 receive 到 "hi"；因 UDP 无连接，即使客户端未先连也能直接收发
// 错误用法：new String(p.getData()) 不传 length → 把整个 1024 字节缓冲（含残存旧数据）都转成字符串，回显内容错乱
// 错误用法：buf 太小而对方发了更大的报文 → 数据被静默截断（UDP 不重传也不报错，只能看到变短的内容）
// 错误用法：端口已被占用时 new DatagramSocket(9876) → 抛 BindException: Address already in use
```

要点：`receive` 返回即为完整数据报（不会"半个包"，但**缓冲区小于包体会静默截断**，`setReceiveBufferSize` 与 `truncate` 语义要注意）；对未监听端口发送后，本端可能收到 ICMP 端口不可达，导致下一次 `send/receive` 抛 `PortUnreachableException`——**这是 UDP "偶发异常"的常见根因**。

## 四、Socket API 语义：把每个系统调用讲清楚

后端真正的困惑几乎都来自"我以为 write/close 是某某意思"。逐个说清：

### `socket()` / `bind()` / `listen()` / `accept()`（服务端）

- `socket(AF_INET, SOCK_STREAM, 0)`：创建 fd，此时还没有地址。
- `bind(addr)`：绑定 IP:port。**绑定 `0.0.0.0` = 所有接口**（s1-3），绑定 `127.0.0.1` 只接本机。`port=0` 让内核随机分配临时端口（客户端通常这么干）。
- `listen(backlog)`：**把 fd 变成被动套接字**，并设定**全连接队列**上限（实际长度 = `min(backlog, somaxconn)`）。它不创建线程、不开始接受连接。
- `accept()`：从**已建立连接队列**头部取出一个连接，返回新 fd；队列空时阻塞（或返回 `EAGAIN`）。**新 fd 与监听 fd 不同**——这就是为什么一个端口能服务成千上万连接：五元组不同（s2-2 详解队列）。

### `connect()`（客户端）

- 语义：触发三次握手，**握手完成即返回**（阻塞模式下）。返回成功 ≠ 对端应用活着，只说明对端内核回了 SYN/ACK。这是"连接池里的死连接"的根本原因（要靠心跳/读写错误发现，netty/s3-2）。
- 对 UDP：`connect` **不发生任何网络交互**，只是在内核记录默认目的地址，之后可以 `send/recv`（且会过滤掉别的来源的包，还会把 ICMP 端口不可达上报为异常）。所以"UDP 也 connect"是合法且推荐的。
- 非阻塞 `connect` 立即返回 `EINPROGRESS`，用 `select/writable` 等待可写 + `getsockopt(SO_ERROR)` 取结果——这是所有异步网络库（含 Netty `NioSocketChannel.finishConnect`）的标准写法。

### `read()` / `write()`（以及它们的返回值陷阱）

| 情况 | 语义 |
|---|---|
| `read() > 0` | 读到这么多字节（**可能少于你期望的一条消息**，即“半包”，所以应用层必须自己定界，s2-4） |
| `read() == 0` | **对端正常关闭了写方向（收到 FIN）**，即 EOF。不是"暂时没数据"（那是 `EAGAIN`） |
| `read() < 0, EAGAIN/EWOULDBLOCK` | 非阻塞下当前无数据，等事件再来 |
| `read() < 0, EINTR` | 被信号打断，应重试（JVM 内部已处理，`SocketException: Interrupted system call` 偶尔可见） |
| `write() > 0` | **只表示写进了内核发送缓冲区**，不代表对端收到、不代表发出去了 |
| `write() == 0` | 请求长度为 0；或发送缓冲区满（非阻塞下应为 `EAGAIN`） |
| `write()` 报 `EPIPE` / 收到 RST | 对端已关闭 → Java 侧 `Broken pipe` / `Connection reset by peer` |

> **必须刻在脑子里的一条**：`write` 成功返回意味着"数据交给了内核"，之后能否到达对端**与这个调用无关**。所以任何"发消息给下游"的业务语义，只有靠**应用层 ACK**才能成立——这就是 MQ 的 producer ack、RPC 的响应、支付的对账回执存在的根本理由（呼应 s1-1 分组交换的账单）。

### `close()` / `shutdown()` / `SO_LINGER`

- `close(fd)`：引用计数减一（`dup`/fork 场景），归零则发 FIN。**关闭时发送缓冲区里未发的数据仍会尝试发出**；但若对端已关闭并回 RST，你未读的数据会直接丢弃。
- **半关闭**：`shutdown(SHUT_WR)` 只关写方向、保留读——这是"我说完了但还能听你说"的正确姿势，HTTP 短连接、RPC 双向流常用。`close` 是双向一起关，粗暴且容易丢响应。
- `SO_LINGER`：设 0 → `close` 立即发 **RST** 而非 FIN，丢弃未发送数据（用于"强制断开、不关心数据"，如连接池快速回收）；设非零 → `close` 阻塞等待最多该时长（一般**不建议用**，会阻塞业务线程）。
- Java 的 `try-with-resources` / `Socket.close()` 就是 `close`；Netty 里 `channel.close()` 是异步的，`future.await()` 才等它完成（netty/s3-1）。

### 其他高频选项（详见 s4-1）

`TCP_NODELAY`（关 Nagle，RPC 必开）、`SO_RCVBUF/SO_SNDBUF`（缓冲，影响窗口）、`SO_REUSEADDR`（重启不撞 `TIME_WAIT` 端口）、`SO_REUSEPORT`（多进程/多线程各自 listen 同一端口，内核做哈希分流）、`IPV6_V6ONLY`（双栈监听语义）、`TCP_KEEPIDLE/INTVL/CNT`（内核保活三参数，默认 7200 s 太长）。

## 五、五元组与连接标识：为什么"端口够不够"是个错问题

一条 TCP 连接由 **(源 IP, 源端口, 目的 IP, 目的端口, 协议)** 唯一确定。**监听端口只有一个不代表只能服务一个连接**：服务端连接的区分靠的是源 IP/源端口变化。

- 服务端单机理论上限 = 客户端 IP × 客户端端口 组合数，实际受 **fd 数、内存、conntrack 表**限制（s4-1）。
- 客户端侧才有"本地端口耗尽"问题：临时端口范围 `ip_local_port_range`（默认约 28000~60000 个），高并发短连接 + `TIME_WAIT` 会耗尽（表现为 `Cannot assign requested address`）。这是"连接池/长连接"最硬的技术理由之一（呼应 s2-2 的 TIME_WAIT 治理）。
- `SO_REUSEPORT` 让多个进程/多个 accept 队列共享端口，既解决**惊群**又实现内核层负载均衡，是 Redis 6 多线程 accept、Nginx `reuseport`、Netty 多 EventLoopGroup 绑同端口的底层依据。

## 六、三大行业场景钩子

- **电商**：绝大多数内部调用是 TCP（RPC/HTTP）；但"活动大屏实时推送、行情式批量下发"适合组播/UDP + 应用层补偿；调用第三方（银行、支付）常遇到"对端只支持短连接 + 不给 ACK"，此时必须自建幂等 + 对账（`write` 语义决定的）。
- **金融**：行情广播走组播（一台交易所行情服务器可同时给上千家机构，TCP 做不到），因此机构侧要有"组播丢包 + 补推通道（TCP/文件）"的双通道设计；交易报文体走 TCP 但必须"逐笔序号 + 应用层确认 + 对账"，理由就是第四节那条 `write` 语义。
- **电力**：抄表与配网终端大量使用 UDP/短连接 + 应用层确认（DL/T 698.45 支持多种承载）；因为终端数量极大、上行链路 NAT 普遍存在，**"服务端不能主动连终端"** 决定了所有交互都必须由终端发起并保持心跳（呼应 s1-3 NAT 老化）。

## 七、要点回顾

1. UDP 头仅 8 字节：无连接、无序、无确认、无窗口、无拥塞控制；**保留报文边界**是其与 TCP 最大的语义差别。
2. UDP 的三个"快"：零握手、不等重传（无队头阻塞）、无速率收敛；代价是可靠性/顺序/流控全归应用层，且无拥塞控制会挤垮同链路 TCP。
3. 实用上限是一个 MTU 内的字节数（超 MTU → IP 分片 → 一片丢则整包废）；DNS 512 字节、QUIC 限制初始包都由此起。
4. 四类用途：短问答（DNS/NTP/SNMP）、实时（RTP）、一对多（组播/广播）、承载用户态可靠传输（QUIC/DTLS/RUDP）。
5. `connect` 成功只代表三次握手完成（对端内核活着，不代表应用可用）；UDP 的 `connect` 只是设置默认目的，不发包。
6. **`read()==0` 是 EOF（对端 FIN），`EAGAIN` 才是"暂时没数据"**；`read` 可能返回半包，所以应用层必须定界（s2-4）。
7. **`write` 成功只代表数据进了内核发送缓冲区**；业务级可靠必须靠应用层 ACK——这是 MQ/RPC/支付回执存在的原因。
8. `close` 双向关闭、`shutdown(SHUT_WR)` 可半关闭；`SO_LINGER=0` 直接 RST 且丢弃未发数据。
9. 连接由五元组唯一确定，"一个监听端口只能一个连接"是误解；客户端才有本地端口耗尽问题；`SO_REUSEPORT` 是端口级多队列分流的基础。
