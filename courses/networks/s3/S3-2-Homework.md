# HTTP/2 与 HTTP/3（QUIC） · 课后作业

> 两题各 50 分：一题用 curl/DevTools 观测 h1/h2 差异，一题做一份 h3 落地评估。

## 作业 1：用 curl 观测 HTTP/2 多路复用与头部压缩（50 分）

**要求**：
1. 起一个支持 h2 的本地服务（`caddy`/`nginx http2` 自签证书即可），或直接用公网 h2 站点。
2. `curl -k --http2 -v https://host/` 观察协商结果（`Using HTTP2` / `ALPN: server accepted h2`）与响应是否走 h2。
3. 用浏览器打开一个含 20+ 静态子资源的页面，DevTools Network 面板：
   - 对比 h1 站点（同域多条连接、每连接一请求）与 h2 站点（**同域一条连接、多请求并行**）的连接数与时间线。
   - 记录 h2 下请求的耗时分布，验证"一条连接跑多请求"。
4. 抓包（Wireshark 过滤 `http2`）看一个连接里多个 Stream ID 的帧如何交错，观察 HEADERS 帧是否很小（体现 HPACK）。

**验收标准**：
- 能截图对比 h1 多连接 vs h2 单连接多路复用。
- 能指出 h2 抓包里 HEADERS 帧明显小于 h1 明文头。
- 说明为什么 h2 通常要求 TLS（ALPN 协商 h2）。

**参考答案要点**：
- h1：同域 ~6 条 TCP 连接、每连接串行；h2：同域 1 条连接、请求并行。
- h2 帧交错在同一连接的不同 Stream ID 上，体现多路复用。
- HPACK 让重复头部只发索引，帧很小。

## 作业 2：为"移动电商弱网首屏优化"写一份 h2→h3 评估（50 分）

**背景**：App/H5 首屏依赖大量小请求，用户常在电梯、地铁、4G/5G 切换场景，反馈"首屏转圈久、偶发失败"。

**要求**：
1. 用本节因果链分析：为什么单纯把 h1 升到 h2 不足以解决"弱网 + 切网"痛点？（至少两点：传输层 HOL、切网重连）
2. 给出接入层启用 **HTTP/3/QUIC** 的收益清单（对应每流独立重传 / 0-RTT / 连接迁移）与量化预期（首屏 RTT 数、切网成功率）。
3. 列出上线 QUIC 的**风险与预案**（CPU、UDP 被封、抗 DDoS、0-RTT 重放），并说明**回退机制**（`Alt-Svc` 头 + 保留 h2/h1）。
4. 明确**边界**：内网微服务调用是否也要上 h3？给出结论。

**验收标准**：
- 至少正确写出 h2 在弱网的两点结构性不足。
- 收益与 QUIC 三特性一一对应，不含糊。
- 回退与灰度方案可落地（先 CDN 边缘开 h3、观测后放量）。
- 结论清晰：**边缘/公网接入上 h3、内网 RPC 留 h2/gRPC**。

**参考答案要点**：
- h2 弱网：单 TCP 丢包 → 全流 HOL；切网 → TCP 五元组变 → 断连重握手。
- h3：每流独立（抗丢包）、0-RTT（少 1~2 RTT）、Connection ID（切网不断）。
- 风险：CPU 高、UDP QoS 差、需 Address Validation 抗反射攻击、0-RTT 仅幂等；`Alt-Svc: h3=":443"` 让客户端自动升级并可回退。
- 内网低丢包、可控，h2/gRPC 足够，不必上 h3（徒增 CPU 与运维）。
