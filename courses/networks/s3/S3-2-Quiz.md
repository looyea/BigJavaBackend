# HTTP/2 与 HTTP/3（QUIC） · 小测验

### 1. HTTP/2 实现单连接多路复用的关键机制是（15分）

- A. 开多条 TCP 连接分摊请求
- B. 把报文拆成带 Stream ID 的二进制帧，多流帧交错、按 ID 重组
- C. 用更长的 keep-alive 超时
- D. 强制 gzip 压缩 body

> 答案：B
> 解析：h2 引入二进制分帧层，一个连接上有多条逻辑流（stream），每帧带 Stream ID，接收端按 ID 重组，实现单连接并发多请求，消灭 h1 的应用层队头阻塞。

### 2. HTTP/2 压缩请求/响应头部使用的算法族是（15分）

- A. gzip
- B. brotli
- C. HPACK（静态表 + 动态表 + 哈夫曼）
- D. LZ4

> 答案：C
> 解析：h2 用 HPACK 压缩头部（预置静态表 + 连接级动态表 + 哈夫曼编码），把重复的 Cookie/UA 头压到几字节。gzip/br 压的是 body 不是头。QUIC/H3 改用 QPACK。

### 3.【多选】相比 HTTP/2，QUIC/HTTP3 带来的改进有（20分）

- A. 消灭传输层队头阻塞（每流独立重传）
- B. 支持 0-RTT/1-RTT 建连
- C. 用 Connection ID 实现连接迁移
- D. 完全不需要 CPU，性能零开销

> 答案：ABC
> 解析：D 错，QUIC 在用户态处理每个 UDP 包与加解密，**CPU 开销反而更高**、且失去部分内核硬件卸载红利。A/B/C 是 QUIC 三大招牌改进。

### 4. 说"HTTP/2 仍有队头阻塞"，阻塞发生在哪一层（10分）

- A. 应用层，一个慢请求挡下一个
- B. 传输层，一条 TCP 丢一个段会卡住所有流
- C. 表示层，头部解压失败
- D. 会话层，Cookie 失效

> 答案：B
> 解析：h2 消灭了应用层 HOL，但所有 stream 复用一条 TCP；TCP 要求按序交付，丢一个段则全连接所有流都要等重传（传输层 HOL）。这正是弱网下 h2 可能不如 h1 多连接的原因，也是 QUIC 出现的动机。

### 5. QUIC 的"连接迁移"能力主要得益于（10分）

- A. 使用 UDP 端口更大
- B. 用 Connection ID 而非四元组标识连接
- C. 引入了 Server Push
- D. 拥塞控制放在内核

> 答案：B
> 解析：QUIC 用 Connection ID 标识连接身份，换网络（Wi-Fi→4G）导致 IP/Port 变化时无需重建连接；TCP 用五/四元组，IP 或端口一变连接就断。

### 6. 简答：某移动电商 App 在弱网/频繁切网场景下首屏慢、请求偶发失败。团队纠结上 HTTP/2 还是 HTTP/3。请用本节知识给出建议与理由，并说出上 QUIC 需要额外注意的两三点成本。（30分）

> 参考答案：
> - 要点：诊断——弱网下 h2 因**单条 TCP 的传输层队头阻塞**放大丢包影响，切网下 TCP 连接必须**重建 + 重握手**，故 h2 不足以解决该场景。
> - 要点：建议前端接入层启用 **HTTP/3/QUIC**：每流独立重传（抗丢包）、**0-RTT/1-RTT** 建连（首屏更快）、**Connection ID 连接迁移**（切网不掉线），显著降 LCP 与失败率。
> - 要点：内部微服务调用（内网低丢包、高可靠）仍用 **h2/gRPC** 即可，无需全链路 h3。
> - 成本要点：① **CPU 更高**（用户态处理每个 UDP 包、加解密）；② **UDP 被防火墙/QoS 限速或丢弃**、需保留 h2 over TCP 回退（Alt-Svc）；③ **抗 DDoS**（QUIC 需 Address Validation/Retry，且 UDP 放大攻击面）、可观测工具链较新。
> - 加分：提到 0-RTT 的重放风险需只对幂等请求开放（呼应 s3-3）。
