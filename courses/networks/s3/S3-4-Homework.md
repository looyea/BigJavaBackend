# DNS、CDN 与负载均衡 · 课后作业

> 两题各 50 分：一题用 dig 摸清一条域名解析链，一题设计一套"多机房就近 + 容灾切流"的调度方案。

## 作业 1：用 dig 拆解一次真实域名的解析链（50 分）

**要求**：
1. `dig www.example.com` 看完整返回，记录：`ANSWER`（A/CNAME）、`AUTHORITY`（NS）、`ADDITIONAL`、以及 ANSWER 的 **TTL**。
2. `dig www.example.com +trace` 观察 根 → TLD → 权威 的迭代全过程，指出每一跳返回了什么。
3. 若 ANSWER 是 CNAME 指向 CDN 域名（如 `xxx.cdn.net`），继续 `dig` 那个目标，理解"多级 CNAME 到边缘"。
4. 换不同 DNS 服务器解析同一域名（`dig @223.5.5.5` 与 `dig @8.8.8.8` 与 `dig @<权威>`），对比返回 IP 是否不同，验证 **GSLB 按来源调度**。
5. 记录 `dig` 输出里 `flags: qr rd ra` 的含义，以及是否 `aa`（authoritative answer）。

**验收标准**：
- 能画出该域名"客户端→LD→根→TLD→权威→(CNAME)→CDN边缘"的路径。
- 观察到不同递归 DNS 返回不同 IP，并解释 GSLB/ECS 机制。
- 说明"提前调小 TTL 再切流"的实操步骤。

**参考答案要点**：
- `+trace` 从根开始逐跳；`aa` 标志表示是否权威直答。
- CNAME 链最终落到按线路返回的 A 记录。
- 切流 SOP：T-1 天调小 TTL → 变更解析 → 观测各地生效 → 恢复大 TTL。

## 作业 2：设计"同城双活 + 异地容灾"的流量调度（50 分）

**背景**：交易类系统，要求单机房故障时分钟级恢复、日常两机房分担、发布不停机。

**要求**：
1. 画出从域名到后端的分层调度：GSLB（跨机房）→ 机房内四层 LVS-DR → 七层 Nginx（灰度/路由）→ 后端集群 → 一致性哈希缓存。
2. 说明每层健康检查怎么配（探测协议、阈值、摘除/恢复条件），避免"抖动误摘"和"故障漏摘"。
3. 设计一次"机房 A 整体宕机"的切流：GSLB 如何感知、TTL 如何配合、数据库/会话层要注意什么（会话外置、数据同步延迟）。
4. 设计"后端单机发布"的平滑上下线（先摘流量→等在途→关闭→重启→预热再加权）。

**验收标准**：
- 分层职责清晰，四层抗量 + 七层灵活组合合理。
- 健康检查有主动 + 被动（5xx 熔断）双重、含防抖。
- 切流方案考虑 DNS TTL 生效延迟与会话/数据一致性，不是"改个记录就完事"。
- 明确 DR 模式对后端 ARP 抑制（`arp_ignore=1/arp_announce=2`）与 VIP 配置的要求。

**参考答案要点**：
- GSLB 用健康检查 + 权重把流量从故障机房逐步调到 0；短 TTL + HTTPDNS 加速生效。
- 会话必须外置（Redis/JWT），否则 sticky 用户在切流后掉登录。
- 数据层注意跨机房复制延迟，写主读备要设 lag 阈值。
- 发布：LB 摘节点 → 等 `in-flight` 排空（设上限秒）→ 停 → 启 → 预热（JIT/连接池/本地缓存热了再加满权重）。
