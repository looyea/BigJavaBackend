# HTTP/1.x：报文、持久连接与缓存 · 小测验

### 1. 关于 HTTP 报文头与体的边界，正确的是（15分）

- A. 用 `\r\n\r\n` 空行分隔头部与主体
- B. 头部字段名区分大小写
- C. body 长度只能靠 Content-Length
- D. chunked 与 Content-Length 可以同时出现

> 答案：A
> 解析：头与体之间是空行 `\r\n\r\n`。头部字段名**大小写不敏感**；body 长度可用 Content-Length 或 chunked 两种方式，且二者**互斥**。

### 2. 下列哪个方法"幂等但不安全"？（15分）

- A. GET
- B. POST
- C. DELETE
- D. HEAD

> 答案：C
> 解析：安全=只读不改状态（GET/HEAD 安全），幂等=多次与一次效果相同。DELETE 会改变状态（不安全），但重复删同一资源效果一致（幂等）。POST 既不幂等也不安全。

### 3.【多选】关于 HTTP 缓存，下列说法正确的有（20分）

- A. `Cache-Control: max-age=60` 属于强缓存，新鲜期内不发请求
- B. `no-cache` 的含义是"完全不缓存"
- C. `ETag/If-None-Match` 协商命中返回 304
- D. `Cache-Control` 优先级高于 `Expires`

> 答案：ACD
> 解析：B 错。`no-cache` 是"**可以存但每次都要向服务器协商确认**"，真正"完全不缓存"的是 `no-store`。A/C/D 均正确。

### 4. 网关返回 502 与 504 的区别是（10分）

- A. 502 上游超时，504 上游返回无效响应
- B. 502 上游返回无效响应，504 上游在时限内未响应（超时）
- C. 两者等价，只是版本不同
- D. 502 是客户端错误，504 是服务端错误

> 答案：B
> 解析：502 Bad Gateway = 上游回了个非法/无法解析的响应；504 Gateway Timeout = 上游压根没在超时窗口内回。二者都是 5xx 服务端侧问题，常出现在发布/GC 停顿期间（呼应 s2-2）。

### 5. HTTP/1.1 持久连接带来的主要问题是（10分）

- A. 每次请求都要重新三次握手
- B. 应用层队头阻塞（一条连接同时只处理一个请求-响应）
- C. 无法使用 Content-Length
- D. 不支持 gzip 压缩

> 答案：B
> 解析：持久连接恰恰是为了省握手（A 是短连接的问题）。代价是同一连接上请求串行，慢请求阻塞后续 → 应用层队头阻塞，浏览器靠多开连接硬扛，h2 多路复用才根治（呼应 s2-4）。

### 6. 简答：大促发布后，部分用户打开页面报 JS 报错、白屏，刷新有时又正常。结合 HTTP 缓存与连接语义，给出两条最可能的成因与对应修复。（30分）

> 参考答案：
> - 要点一（缓存版本错配）：HTML 用了强缓存（max-age）没协商，用户拿**旧 HTML** 去引用已被替换/删除的 **hash JS 文件名**（旧文件已不在 CDN）→ 404 报错。修复：HTML 设 `Cache-Control: no-cache`（每次协商），静态资源带 hash 才配 `max-age=1y, immutable`；发布顺序先传新静态资源、再切 HTML。
> - 要点二（复用死连接 502/EOF）：发布时后端滚动重启关闭了 keep-alive 连接，而中间层/客户端仍复用已失效连接 → 偶发 502/EOF，重试即好（"刷新有时正常"）。修复：服务端 keep-alive idle timeout **小于** 上游/网关超时；发布走优雅下线先摘流量；客户端对幂等 GET 开启一次重试。
> - 要点：能指出"刷新有时正常"正是**间歇性连接复用失败/缓存新旧交替**的特征。
