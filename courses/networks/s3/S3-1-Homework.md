# HTTP/1.x：报文、持久连接与缓存 · 课后作业

> 两题各 50 分：一题用 `curl -v` 把缓存决策链跑通，一题为下单接口设计正确的状态码 + 幂等策略。

## 作业 1：用 curl 验证强缓存 → 协商缓存 → 304 全链路（50 分）

**要求**：
1. 起一个能返回静态文件的服务器（Nginx/Python http.server 皆可），对一个 css 文件配置：首次响应带 `ETag` 与 `Cache-Control: max-age=10`。
2. 第一次 `curl -v http://host/a.css`，记录响应头里的 `Cache-Control`、`ETag`、状态码。
3. 10 秒内第二次请求同一 URL，观察是否仍向服务器发请求（强缓存命中在真实浏览器里是 `from disk cache`，curl 不缓存需说明如何用浏览器 DevTools 佐证）。
4. 等超过 10 秒（新鲜期过期），第三次带 `If-None-Match: <上次的 ETag>` 请求，验证服务器返回 **304** 且无 body。
5. 改动文件内容后再发条件请求，验证返回 **200 + 新 ETag + 新 body**。

**验收标准**：
- 能贴出三次请求的头与状态码，并标注各自命中了哪一级缓存。
- 用浏览器 Network 面板区分 `200 (from memory/disk cache)`、`304`、`200` 三种外观。
- 说清"为什么带 ETag 的 304 能省 body 但省不掉一次 RTT"（协商仍需问服务器）。

**参考答案要点**：
- 强缓存（max-age 内）：不发请求，最快。
- 协商缓存（过期后）：发条件请求，命中 304 只回头不回头，省带宽不省 RTT。
- 内容变了 → ETag 变 → 服务器不匹配 304 → 回 200 新内容。

## 作业 2：为"创建订单"接口设计状态码 + 幂等方案（50 分）

**背景**：`POST /api/orders` 创建订单，网络可能超时，客户端会重试。

**要求**：
1. 为下列情形各选一个最贴切的 HTTP 状态码并说明理由：参数校验失败、未登录、登录了但无权限、订单号冲突/重复提交、下游库存服务超时、限流。
2. 设计**幂等键**方案：客户端生成 `requestId`（UUID）随请求带上，服务端如何用 Redis 保证"同一 requestId 重复提交只创建一单"，并处理"第一次请求还在处理中，重试就到了"的并发。
3. 说明为什么这个接口**不能**用 GET、为什么不能靠 HTTP 层自动重试。

**验收标准**：
- 状态码选择正确：400 / 401 / 403 / 409 / 504（或 502）/ 429，且能区分 401vs403、502vs504。
- 幂等方案含：`SETNX requestId`（带 TTL）占位 + 处理中状态 + 完成后存结果；重试命中直接返回已建订单（回 200 + 原结果，不是 409）。
- 能解释 POST 非幂等 → 只能业务层幂等键去重。

**参考答案要点**：
- `SET key value NX PX 30000` 抢占；抢到才真正下单，下单成功写入最终结果；没抢到则查结果/返回"处理中"让客户端稍后再取。
- 幂等键作用域 = 业务动作（同一 requestId 同一语义），过期时间要覆盖最长重试窗口。
- 限流 429 要带 `Retry-After`，客户端据此退避。
