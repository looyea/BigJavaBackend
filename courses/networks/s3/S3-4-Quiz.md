# DNS、CDN 与负载均衡 · 小测验

### 1. 本地域名服务器(LR)向根/TLD/权威服务器发起的查询方式是（15分）

- A. 递归查询
- B. 迭代查询
- C. 广播查询
- D. 组播查询

> 答案：B
> 解析：客户端到 LR 是递归（一次问到底），LR 到根/TLD/权威之间是**迭代**（每级返回"下一级该问谁"，LR 自己去问）。注意区分"谁对谁"。

### 2. LVS-DR 模式吞吐高的关键是（15分）

- A. 请求和响应都经过 LB
- B. LB 只改目标 MAC，后端用 VIP 直接把响应发给客户端（响应不过 LB）
- C. LB 做 TLS 卸载
- D. LB 改写源 IP 为后端地址

> 答案：B
> 解析：DR 模式下 LB 仅做二层转发（改 MAC），响应由后端直回客户端，LB 不承担回程带宽 → 吞吐极高。要求后端与 LB 同二层并抑制 ARP。

### 3.【多选】下面哪些是缓解"CDN 缓存大面积失效打穿源站"的有效手段（20分）

- A. 过期时间打散（避免同批 key 同时过期）
- B. 回源合并（同一 key 只放一个回源请求）
- C. 大促前对热点资源做预热
- D. 把所有资源 max-age 设为 0

> 答案：ABC
> 解析：D 会让每个请求都回源，直接压垮源站，与目标相反。A/B/C 分别是防"雪崩/击穿"与主动预热标准做法。

### 4. 一致性哈希相比 `hash(key)%N` 的价值在于（10分）

- A. 计算更快
- B. 加减节点时只影响环上相邻区段的 key，数据迁移量小
- C. 不需要哈希函数
- D. 能保证绝对均匀无需虚拟节点

> 答案：B
> 解析：普通取模在 N 变化时几乎全部 key 重映射；一致性哈希把节点与 key 映射到环上，增删节点只移动相邻段，配虚拟节点进一步打散倾斜。

### 5. 把域名记录改成新 IP 后立即全网生效（判断题）（10分）

- A. 正确
- B. 错误

> 答案：B
> 解析：各级 DNS 缓存按 TTL 缓存旧值，改记录要等 TTL 过期才逐级生效；精准切流应**提前调小 TTL**，变更、生效后再调回。这也是 HTTPDNS/应用层调度存在的原因之一。

### 6. 简答：一次"某省电信用户突然大面积打不开 App，其他运营商正常"的线上事件，请沿 DNS→GSLB→CDN→LB 链路给出排查思路与两条最可能根因。（30分）

> 参考答案：
> - 要点（定位面）：只有单一运营商异常 → 优先怀疑 **GSLB 分线路解析** 把电信用户调度到了故障/下线节点，或该线路 DNS 被**劫持/污染**（电信 LD 返回假 IP）。
> - 要点（验证）：用不同 DNS（电信 LD vs 223.5.5.5 vs `dig @权威`）解析对比返回 IP；看是否命中了挂掉的 VIP/边缘节点；`curl -v` 测该 IP 连通与 TLS。
> - 要点（根因一：调度/健康检查）：GSLB 健康检查未及时摘除故障机房，仍返回其 IP。修复：修健康检查探测条件、手动改线路权重把电信流量切走（注意 TTL）。
> - 要点（根因二：劫持）：运营侧 LD 劫持/缓存污染。修复：App 走 **HTTPDNS** 直连解析、下发 IP 列表，绕开 LD，并可做域名/证书二次校验防被导向假站。
> - 加分：提到 CDN 边缘某节点故障也可能只影响部分线路，可用多 CDN/回源兜底。
