# 火焰图怎么看与常见瓶颈 · 作业

## 作业 1：亲手制造并识别一个"宽平顶"

- **目标**：把"找宽平顶"从概念变成手感。
- **任务**：本地跑一个反复执行热点计算的程序（候选：病态正则回溯、大对象 JSON 序列化循环、`String.split` 高频调用），用 `./asprof -d 30 -f cpu.html <pid>` 采样：
  1. 在 HTML 中 Ctrl+F 高亮你的热点方法，记录其占比；
  2. 把该计算结果缓存/算法替换后再采一次，对比两张图宽度变化；
  3. 输出两份 collapsed 文件，用 `awk` 聚合顶层方法样本数做定量对比。
- **验收标准**：前后两张火焰图 + 一组"占比数字"证明优化命中；能口述"为什么横向位置变了不代表行为变了"（字母序）。
- **参考解法要点**：采样窗口要覆盖稳定负载；单次几秒的毛刺不算结论，多采几轮看重复性。

## 作业 2：GC 与分配归因链

- **目标**：练"CPU 图发现 GC 粗壮 → alloc 事件找分配者"的两步归因。
- **任务**：写一个高分配小程序（循环里拼接大字符串/新建 ObjectMapper/每请求深拷贝列表），`-t` 采样确认 GC 线程占比后，改用 `./asprof -e alloc -d 30 -f alloc.html <pid>` 找出分配热点栈；按图上指认改造一处（复用对象/换流式处理），再采一次验证分配宽度下降。
- **验收标准**：两张图（cpu -t 与 alloc）都有指认标注；改造后分配热点栈宽度或 GC 线程占比有量化下降。
- **参考解法要点**：alloc 图宽度是"采样折算的分配量"而非耗时，别把它读成 CPU 占比；衔接 Arthas 单点验证见 [热更新、反编译与线上排查](../../arthas/s1/S1-2-Lesson.md)。

## 作业 3：压测归因演练（与 JMeter/Gatling 联动）

- **目标**：把火焰图接进容量测试证据链，产出"结论四要素"完整陈述。
- **任务**：用 JMeter 或 Gatling 对演示服务压至膝点（TPS 持平、p99 抬头），在服务端高 CPU 平台期采 60s 火焰图；判断瓶颈形态（业务宽平顶 / GC / 锁等待——锁用 `-e lock` 补采），写一段容量归因陈述：负载模型 + 指标拐点 + 火焰图证据 + 优化动作预期。
- **验收标准**：压测报告曲线截图与火焰图同时间轴对齐；陈述含"退化形态归因"而非只报数字。
- **参考解法要点**：先自证压力机无恙（[并发模型、思考时间与 TPS/RT 解读](../../jmeter/s1/S1-2-Lesson.md) 的纪律）；机器层对照 [进程/内存/CPU/IO 四件套与 Top/vmstat](../../linux-shell/s1/S1-1-Lesson.md)。
