# 安全点采样偏差与线上低开销实践 · 面试题

## 题 1：什么是安全点（Safepoint）采样偏差？为什么会失真？

- HotSpot 的 cpu 采样若走 safepoint 机制，只在安全点取线程栈，而安全点分布受 JIT 与代码结构影响并不均匀。
- 小循环被编译优化几乎没有安全点（采样不足、看着不热），长循环回边/去优化点安全点密集（过度采样、看着虚热），编译线程也会显现在栈顶。
- 加分：能画出"安全点分布不均→采样扎堆"的示意解释失真来源。

## 题 2：怎么减小采样偏差？

- 用 `--cstack dwarf`（基于帧信息 unwind，不依赖 safepoint）或 `--cstack vm`，比默认 `--safe` 更接近真实执行位置。
- 读图时主动剔除 JIT 编译线程帧、内核态帧、回边"虚热"帧。
- 加分：说明 `--safe` 稳但偏差大、dwarf 准但依赖帧信息，生产建议两者交叉印证。

## 题 3：async-profiler 能常驻生产吗？怎么控制开销？

- 它单次采样开销极低（几十微秒级），可以按需起停或短窗口低频常驻。
- 控制手段：拉大 `-i` 采样间隔、用 `-d` 短窗口或 `--loop` 自动停、限制导出频率。
- 加分：反例——极小间隔+每秒导出+全天常驻会让落盘和采样开销叠加、拖慢线上。

## 题 4：JFR 输出有什么价值？

- `.jfr` 二进制体积小、可被 JDK Mission Control 分析、便于集中存储与长期留存。
- 适合常态化诊断产物的管理与回溯，比一堆大 html 更好收纳。
- 加分：JFR 还能带 GC/线程/分配等多维事件，与火焰图互补。

## 题 5：容器里 cpu 事件采不到怎么办？

- 容器常缺 perf_events 权限，cpu 采样会失败或不准。
- 退化为 `itimer` 时钟模式（精度略降但可用），或放开 `perf_event_paranoid`/加权限运行。
- 加分：延迟型问题在容器里更适合直接用 wall 模式，绕开 perf 依赖。

## 题 6：给你一张火焰图，你怎么保证不把"偏差"当成"热点"？

- 先看宽帧是不是编译线程/内核帧/回边密集帧，是则视为噪声剔除。
- 换 `--cstack dwarf` 或多事件（cpu/wall/alloc/lock）交叉验证，稳定出现且语义合理的才是真热点。
- 加分：强调"宽≠热"，要结合采样机制与业务语义双重判断，避免据此做错误的性能优化。
