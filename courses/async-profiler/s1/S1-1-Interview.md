# 火焰图怎么看与常见瓶颈 · 面试题

## 题 1：为什么异步信号采样比"安全点采样"更可信？

- 依赖 safepoint 的采样器只能在线程到达安全点时取栈，热点会被系统性拉向 safepoint polling、循环边界与阻塞点——慢的地方看不到、看的都是"假热点"；
- async-profiler 用 perf_events 信号在任意指令处打断，经 AsyncGetCallTrace 安全取 Java 栈：采样分布与真实 CPU 消耗对齐；
- 代价与边界：统计近似（短方法可能被摊掉）、依赖 OS 权限（容器要 CAP_PERFMON，否则退 itimer）；
- 加分：能对比 JFR 采样事件的常驻定位——长期趋势用 JFR，专项深挖用 asprof 直采。

## 题 2：给你一张火焰图，说出你的读法。

- 三规则先行：高=调用深度、宽=样本占比、横向字母序与时间无关；
- 找"宽平顶"（帧宽且栈浅）= 自身烧 CPU 的头号对象；再看"整体在哪一层分叉最宽"定位消耗集中的层；
- 区分包含占比与自身占比：框架入口（如 servlet 分发、序列化边界）天然通吃全图，热点判断看它**上面**的栈形态；
- 结论要可复核：报方法名+占比+多轮采样的重复性，配合 Ctrl+F 高亮截图；
- 加分：主动提 GC/native 线程混入问题——先 -t 分流再下结论。

## 题 3：CPU 100% 但火焰图里业务方法都不宽，接下来查什么？

- 大概率"不是业务在忙"：-t 按线程分图，看 GC 线程（分配压力）、C2 编译器（启动期/JIT 风暴）、定时任务/native 线程；
- GC 粗壮 → `-e alloc` 找分配大户（大集合拷贝、每请求新建重对象、String 拼接），治本是减分配而不是扩堆；
- 全是内核态（sy 高）→ 上下文切换/系统调用风暴，回 linux 层 vmstat 看 cs 与 si，对照 Arthas thread --state 找忙线程；
- 加分：说出"火焰图回答 CPU 花在哪，回答不了'时间都等了谁'——等待问题切 wall/lock 事件"。

## 题 4：alloc 模式和"堆里存了什么"（dump）有什么本质区别？

- alloc 火焰图回答"**谁在生产**垃圾"：采样折算的分配调用栈，看的是流量（速率）；
- heap dump 回答"**谁占着不放**"：存活对象引用树，看的是存量；MAT 的 Dominator 干这个；
- 高分配率 ≠ 泄漏（短命对象 GC 能收）；泄漏 = 分配少但晋升存活、老年代持续爬升——两个证据链要分开取；
- 加分：给出组合拳——GC 日志发现老年代锯齿不回落 → alloc 图定位分配者 → 若属存活累积再 dump 查引用根。

## 题 5：怎么向团队证明"这次优化真的有效"？

- 同负载模型复压（脚本与参数固化进仓库，JMeter/Gatling 均可），前后各采 ≥30s 稳定期火焰图；
- 用 collapsed 差分（或 flamegraph 对比模式）给出量化：热点方法占比从 X% → Y%，TPS/p99 同窗口对比曲线；
- 排除混杂变量：同机型、同 JVM 参数、同数据规模、预热一致——容量结论四要素（模型/判据/边界/归因）同样适用于性能优化汇报；
- 加分：主动交代采样误差（统计近似）与多轮重复性，防止"3% 波动被当成功劳"。

## 题 6：Arthas trace 和火焰图都能找慢方法，什么时候用哪个？

- trace 是**单点即时**：对一次慢调用做逐跳分解，回答"这一笔为什么慢"，适合偶发、可按条件过滤的现场手术；
- 火焰图是**全景统计**：一段时间整个进程 CPU 的分布，回答"系统整体把资源烧在哪"，能发现 trace 视野外的线程（GC、native、框架层）；
- 典型联动：压测膝点用火焰图圈定"大队"，再用 Arthas trace/watch 审讯"小兵"（参数与数据形态）；
- 加分：点出开销模型差异——trace 是字节码增强（按方法计酬、要卸载复位），火焰图是采样（1% 量级、采完即走），生产常驻性完全不同。
