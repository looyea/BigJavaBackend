# CPU/alloc/lock 与 Wall 模式采样 · 小测

> 本卷满分 100 分：单选 7×6=42，多选 2×9=18，简答 1×40=40。

### 1. async-profiler 的 cpu 事件采样的是（6分）

- A. 所有线程的墙上时间
- B. 线程"占用 CPU 运行时"的栈，用于找计算热点
- C. 对象分配
- D. 锁等待

> 答案：B
> 解析：cpu 事件只在线程跑在 CPU 上时采，看得见计算密集处，看不见阻塞/IO 等待。

### 2. 接口 P99 很高但 CPU 使用率不高，最该用的采样模式是（6分）

- A. cpu
- B. wall（wall-clock）
- C. alloc
- D. 不采

> 答案：B
> 解析：慢在"等"（IO/锁/排队）而非"算"，cpu 模式几乎采不到，wall 按真实时间采样能暴露等待。

### 3. alloc 事件火焰图的宽帧代表的是（6分）

- A. 占 CPU 最久
- B. 该处对象分配量大，是 GC 压力来源
- C. 锁竞争最激烈
- D. 调用最深

> 答案：B
> 解析：alloc 图看"分配量"不是"耗时"，宽帧=疯狂 new/TLAB 溢出，用来定位 GC 压力，别当 CPU 热点读。

### 4. lock 事件主要用来定位（6分）

- A. 内存泄漏
- B. 锁等待与竞争（synchronized/偏向锁升级等）
- C. 网络延迟
- D. GC 停顿

> 答案：B
> 解析：lock 事件采线程等锁的时间，能找出竞争最激烈的同步点。

### 5. 容器里因权限不足采不到 cpu 事件时，常见的兜底是（6分）

- A. 改用 wall
- B. 退化为 itimer 时钟模式
- C. 放弃采样
- D. 用 alloc 代替 cpu

> 答案：B
> 解析：无 perf_events 权限时 cpu 用 itimer 定时器近似采样，精度略降但仍可用。

### 6. cpu 模式看不见的一种耗时是（6分）

- A. 密集循环计算
- B. 正则回溯等纯 CPU 操作
- C. 线程阻塞在 socketRead 等 IO 上
- D. 大量字符串拼接的 CPU 开销

> 答案：C
> 解析：IO 等待不占 CPU，cpu 模式采不到，要靠 wall 才能看到"在等"的时间。

### 7. 关于"算得多"和"等得久"，正确的图选择是（6分）

- A. 都看 cpu 图
- B. 算得多看 cpu 宽帧，等得久看 wall 宽帧
- C. 都看 alloc 图
- D. 看 lock 图即可

> 答案：B
> 解析：cpu 与 wall 回答两类问题、结论可能完全不同，要按瓶颈性质选图。

### 8.（多选）下列哪些场景应优先考虑 wall 模式？（9分）

- A. CPU 不高但接口延迟高
- B. 怀疑下游 RPC/DB 的 IO 等待占大头
- C. 线程池排队/等锁导致变慢
- D. 定位一个纯计算的数学函数热点

> 答案：A、B、C
> 解析：D 是典型 cpu 场景；A/B/C 都是"在等"的耗时，wall 能覆盖、cpu 看不见。

### 9.（多选）关于采样事件与解读，正确的有（9分）

- A. 一张火焰图只回答一类问题，按事件选图
- B. alloc 宽帧不能等同于 CPU 热点
- C. lock/alloc 小样本噪声大，应拉长窗口或多采
- D. cpu 图能完整反映所有等待耗时

> 答案：A、B、C
> 解析：D 错误，cpu 图不反映等待；A/B/C 是正确解读原则。

### 10. 一个订单查询接口大促时 P99 从 80ms 涨到 900ms，但监控显示机器 CPU 使用率并不高。请用 async-profiler 设计一套定位思路：选哪些事件、怎么解读、最终期望定位到什么。说明为什么不能只采 cpu。（40分）

> 参考答案：
- 要点1：先判性质——CPU 不高却延迟高，瓶颈大概率在"等"而非"算"，主采 wall 模式（-e wall -t）暴露 IO/锁/排队耗时，不能只采 cpu（cpu 看不见等待）（10分）
- 要点2：wall 判读——看 wall 图最宽帧，通常是 socketRead/下游 RPC/DB 获取连接/线程池 take，定位到底是下游慢、连接池不够还是锁排队（10分）
- 要点3：辅证——若怀疑锁竞争补采 lock，若怀疑大量临时对象触发 GC 补采 alloc 并看分配量；三者分事件、别混读（10分）
- 要点4：结论与权限——给出"等在哪一跳"的证据链并指导修复（下游超时/扩容连接池/减锁粒度）；容器无 perf 权限时 cpu 用 itimer 兜底（10分）
