# 安全点采样偏差与线上低开销实践

> 本节难度：★★★★☆
> 重要程度：★★★★☆
> 学习产出：既能读懂火焰图"哪里可能骗了你"（安全点采样偏差），又能把 async-profiler 安全地常驻在生产做低开销诊断。**安全点偏差（Safepoint Bias）**：HotSpot 的 `cpu` 采样若走 safepoint 机制，只在"安全点"取栈，而安全点分布受 JIT 影响——编译/去优化、长方法的回边、以及被编译掉的小循环，都会让采样"扎堆"在某些位置，结果是把 **JIT 编译器自身、或安全点密集的行**当成热点，失真。缓解手段：用 `--cstack dwarf`（基于帧信息的 DWARF/nmethod unwind，不依赖 safepoint）或 `--cstack vm`，比默认 `--safe` 更接近真实执行位置；`--safe` 更稳但偏差更大。低开销实践：async-profiler 本身开销极低（几十微秒级采样），可**短窗口/低占空比常驻**或按需起停；产出用 `-f`（html）或接 **JFR**（`.jfr` 二进制、可被 JDK Mission Control 分析、便于集中存储），控制导出频率与文件体积，避免诊断本身拖慢线上。要点：读图先怀疑"编译帧/内核帧不是业务热点"；容器缺 perf 权限时退 itimer；常驻采样要设窗口与自动停止，别无限跑。识破"把 C2 编译线程当业务瓶颈""`--safe` 下长循环方法看起来超热其实是回边安全点密集""导出太频繁导致落盘开销叠加"等坑。

## 一、安全点偏差：为什么有的帧"看起来"特别热

```bash
# 目的：理解并规避 safepoint 偏差, 让火焰图更接近真实热点
./asprof -e cpu --safe -d 30 -f safe.html $PID          # 说明：--safe 只在安全点取栈, 稳但偏向安全点密集处/编译相关
./asprof -e cpu --cstack dwarf -d 30 -f dwarf.html $PID # 结果：DWARF unwind 不依赖安全点, 采样位置更真实, 偏差更小
# 反例：--safe 图里把 C2 编译线程或长循环回边当成业务热点 ❌ 那是偏差不是真相, 需换 cstack 或剔除 JVM 帧
```

## 二、偏差从哪来：一图看懂

```text
图目的：safepoint 采样为何会"扎堆"造成失真
HotSpot 只在安全点(方法返回/循环回边/异常等)取线程栈
小循环被编译优化 → 几乎没有安全点 → 被"采样不足", 看着不热
长方法回边多/去优化点密集 → 安全点多 → 被"过度采样", 看着偏热
JIT(C1/C2)编译自身占 CPU 时也会出现在栈顶 → 非业务热点却显眼
结论：默认 --safe 有偏, --cstack dwarf/vm 可减小; 读图先剔除编译/内核帧
```

## 三、低开销常驻与输出控制

```bash
# 目的：让采样能安全常驻生产, 开销可控、产物好收纳
./asprof -d 30 -i 1ms -f out.html $PID   # 说明：-i 设采样间隔(如 1ms/10ms), 间隔越大样本越稀、开销越低
./asprof -o jfr -f out.jfr $PID          # 结果：输出 JFR 二进制, 体积小、可被 JMC 分析、便于集中存储
./asprof --loop 10s -f seg.html $PID     # 说明：分段/短窗口自动停, 避免无限常驻; 按需起停优于长期开
# 反例：高频导出 + 极小间隔常驻全天 ❌ 落盘与采样开销叠加、文件爆量, 诊断反拖慢线上, 应控间隔与频率
```

## 四、坑与底线

- **读图先做"帧过滤"**：把 C1/C2 编译线程、内核态帧视为噪声剔除，再谈业务热点；`--safe` 下的"超热长循环"很可能是回边安全点密集造成的假象。
- **偏差与稳定性权衡**：`--safe` 稳但偏差大、`--cstack dwarf` 更准但依赖帧信息；生产排障建议两者都采、交叉印证。
- **常驻要设边界**：用 `-i` 拉大间隔降开销、用短窗口/`--loop` 自动停止、输出优先 JFR 控体积，绝不让采样+导出无限期高频跑。
