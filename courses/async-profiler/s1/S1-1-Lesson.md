# 火焰图怎么看与常见瓶颈

> 本节难度：★★★★☆
> 本节重要性：★★★★★
> 学习产出：理解 async-profiler"信号驱动采样、不依赖安全点"为何能作为生产常备武器；能独立读火焰图（宽=占比、高=深度、横向无序），并识别宽平顶、GC 线程占比、锁热点、native 栈断裂四类典型瓶颈形态。

## 一、为什么是 async-profiler：安全点偏差问题

传统方法级采样器（基于 JVMTI Method Sampling 的 VisualVM sampler、部分 APM agent）取栈要等线程走到**安全点**，结果采样栈被系统性拉向 safepoint polling 与阻塞方法——热点图"看起来很平，全在等"。async-profiler 走另一条路：Linux 上用 `perf_events` 信号在任意时刻打断线程，通过 `AsyncGetCallTrace` 安全地取 Java 栈——**采样落在真正消耗 CPU 的指令上**，对目标进程开销约 1% 量级，这才是"生产可挂"的底气。

```shell
# 目的：对目标进程采 30 秒 CPU 事件，输出交互式 HTML 火焰图
./asprof -d 30 -f cpu.html 12345
# 说明：-e 换事件：alloc（分配热点）/ lock（锁竞争）/ wall（含阻塞的墙钟时间）；-t 按线程分图
# 反例：CPU 问题用默认模式却忘了高 CPU 可能来自 GC/native 线程——先 -t 看清是谁在忙再下结论
# 结果：浏览器打开 cpu.html，点击可缩放，Ctrl+F 按方法名高亮占比
```

## 二、读图三规则与"宽平顶"直觉

```text
图目的：火焰图的几何语义（90% 的误读都违反这三条）
纵向（高）：调用深度，下是调用者、上是 callee——只有栈顶才是"正在执行"
横向（宽）：样本占比——宽度=该帧自身+子孙被采到的次数比例
横向位置：按字母序排列，❌ 不代表时间先后！"左边先执行"是最常见误读
判热点：找"宽平顶"——某帧很宽而其上栈很浅，说明它自身在烧 CPU（自身时间大）
```

细节：父帧宽度 ≥ 子帧之和的视图是"包含占比"，要区分"框架宽"（如 servlet 分发天然通吃）与"业务方法宽"——看**被谁包着**；缩放后对比兄弟帧相对宽度才有意义；默认配色无语义，差分图（两次采样对比）里红/蓝才表示增/减。

## 三、四类常见瓶颈形态

1. **业务宽平顶**：某方法（正则回溯、JSON 序列化、加解密、深拷贝）在栈顶形成宽平台——CPU 就烧在明处，直接优化算法/缓存结果；
2. **GC/JIT 线程占比高**：`-t` 视图里 GC 线程火焰粗壮，说明分配率或晋升压力问题——换 `-e alloc` 重采，找出"谁在分配"，而不是急着调堆参数；启动期 C2 编译线程旺盛属正常暂态；
3. **锁热点**：`-e lock` 图上 `synchronized`/`ReentrantLock` 等待帧宽——竞争点与持锁时间可见，衔接 Arthas `thread -b`/`--state` 的即时点名（快照 vs 全景互补）；
4. **native 栈断裂/[unknown]**：Java 帧之上出现大片碎片或未知帧——多为缺帧指针的 native 库导致回溯失败，可试 `--cstack dwarf`，或对自编译库补 `-fno-omit-frame-pointer`；wall 模式下 IO 阻塞才可见，CPU 模式看不到"等"。

## 四、工程化用法

`-f collapsed.txt` 输出折叠栈便于脚本聚合与跨机对比；`--total` 让宽度表示总耗时而非自身耗时；基准前后各采一段做 diff 图验证优化收益；容器内运行需要 perf 事件访问权限（CAP_PERFMON 或调低 `perf_event_paranoid`），拿不到时退化用 `-e itimer`（用户态定时器，精度略降）。与 JFR 的分工：JFR 的 `jdk.ExecutionSample` 适合长期常驻录制（`jfr` 命令行也能聚合成火焰图），专项深挖时用 asprof 直采更可控——事件切换、采样间隔、按线程分图这些精细旋钮都在 asprof 手里。
