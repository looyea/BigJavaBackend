# CPU/alloc/lock 与 Wall 模式采样 · 面试题

## 题 1：async-profiler 有哪些采样事件？分别回答什么问题？

- cpu（计算热点）、alloc（对象分配量/GC 压力源）、lock（锁等待/竞争）、wall（真实墙上时间，含 IO/阻塞/排队）、itimer（无 perf 权限的兜底）。
- 按"要算得多、分配多、等得久还是锁竞争"选事件，一张图只回答一类问题。
- 加分：强调选错事件等于问错问题，结论会误导。

## 题 2：cpu 模式和 wall 模式有什么本质区别？

- cpu 只在线程占用 CPU 时采样，看得见计算密集处，看不见阻塞/IO/等锁的时间。
- wall 按真实墙上时间周期性采所有线程栈，把"在等"的耗时也算进来。
- 加分：CPU 不高但接口很慢时，cpu 图几乎空白、必须上 wall 才能看到 socketRead/取连接/线程池排队。

## 题 3：接口 P99 很高但 CPU 使用率不高，你会怎么查？

- 判断瓶颈在"等"而非"算"，主采 `-e wall -t` 看最宽帧是 IO、锁还是线程池排队。
- 结合怀疑点辅采 lock（锁竞争）或 alloc（大量临时对象触发 GC）。
- 加分：给出对应修复——下游超时/扩容连接池/减小锁粒度/降分配，形成证据链。

## 题 4：alloc 火焰图的宽帧能当成 CPU 热点吗？

- 不能。alloc 宽帧代表"分配量大"，是 GC 压力来源，不代表占 CPU 时间长。
- 典型如循环里频繁 new/字符串拼接，cpu 图不明显但 Young GC 被推高。
- 加分：提出复用缓冲、预分配容量、避免大对象直接进老年代等优化。

## 题 5：lock 事件怎么帮你找锁竞争？有什么使用注意？

- lock 采线程等锁的时间，宽帧即竞争最激烈的同步点，能定位是哪段 synchronized/锁把线程堵住。
- 注意小样本噪声大，需拉长采样窗口或多采几次，稳定出现的才算瓶颈。
- 加分：可配 wall 的 -t 分线程视角佐证阻塞都卡在同一临界区，并对比 LongAdder/细粒度锁改造效果。

## 题 6：容器环境采 cpu 事件有什么坑？

- 容器常无 perf_events 权限，cpu 事件采不到或不准。
- 兜底：退化为 itimer 时钟模式（精度略降但可用），或以 root/放开 `perf_event_paranoid` 运行。
- 加分：说明延迟型问题在容器里更适合直接走 wall 模式，绕开 perf 权限依赖。
