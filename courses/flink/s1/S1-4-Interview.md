# 与 Kafka Streams 选型（关联） · 面试题

## 题 1：Flink 和 Kafka Streams 最本质的区别是什么？

- Flink 是独立分布式集群引擎，作业提交到集群跑；KS 是嵌入应用的 Java 库，随应用进程运行、普通横向扩容即可。
- 这个"引擎 vs 库"的分野决定了部署、状态规模、容错与生态的所有取舍。
- 加分：能一句话点出"要不要为它单独运维一套集群"是团队最先敏感的现实差异。

## 题 2：状态很大时为什么更倾向 Flink？

- Flink 用 RocksDB 状态后端 + 分布式 Checkpoint，状态可随并行子任务横向扩展到 TB 级。
- KS 状态存本地 RocksDB，受单机磁盘/内存限制，超大状态/大 join 易盘紧、rebalance 风暴、恢复慢。
- 加分：能补充 KS 状态需靠 standby task / 迁移恢复，跨机重平衡代价高，而 Flink 状态与计算可弹性重分布。

## 题 3：两者都宣称 exactly-once，实现路径一样吗？

- 层次不同：Flink 用 Checkpoint（引擎内 once）+ 可重放 Source + 2PC/幂等 Sink（端到端 once）；KS 基于 Kafka 事务实现 EOS。
- 共同前提：端到端 once 都要求输入可重放、输出事务或幂等，不是引擎自带魔法。
- 加分：给反例——KS 里引入外部非事务副作用、Flink Sink 非幂等，都会打破 once，体现理解边界。

## 题 4：什么场景下你会果断选 Kafka Streams？

- 处理逻辑贴合某个微服务、状态小、以 Kafka 为输入输出，且团队不想再养一套流集群。
- 用现有 CI/CD 和部署方式管理流任务、迭代快、运维轻。
- 加分：强调"库把流处理变成应用的一部分"，适合领域内自治的轻量实时，而不是平台级统一计算。

## 题 5：什么信号出现说明该上 Flink 了？

- 需要大状态 join、跨天复杂窗口、CEP、流批一体，或要做跨团队共享的统一实时数仓/多目标 CDC 管道。
- 需要独立扩缩容、精细资源与容错控制，并具备平台化运维能力。
- 加分：能诚实说清代价——引入集群的运维/学习/资源成本，选型是收益与复杂度权衡而非追强。

## 题 6：一家公司能同时用 Flink 和 Kafka Streams 吗？怎么划边界？

- 能，且常是成熟形态：应用内局部轻量实时用 KS，平台级统一管道/数仓用 Flink。
- 边界：就地自治 vs 平台共享；避免为统一而把轻量逻辑强塞集群，也避免重复建设两套 EOS/监控。
- 加分：给出"KS 作业何时升级并入 Flink"的触发条件（状态增大、跨服务复用、运维归一），体现演进式架构观。
