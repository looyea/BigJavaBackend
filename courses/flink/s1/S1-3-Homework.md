# CDC、数据管道与流批一体 · 作业

## 作业 1：把商品表实时同步到 ES

- 目标：搭一条 MySQL→Flink CDC→ES 的最小镜像管道。
- 任务：用 `MySqlSource` 捕获 `shop.product` 变更，反序列化出 `op/before/after`，下游对 ES 按 `_id=主键` 做 upsert，`op=d` 时删除对应文档；先跑全量快照再自动衔接增量。
- 验收标准：源库增/改/删在秒级反映到 ES；删除行能从索引中真正移除；重启作业能从位点续传不重复不遗漏。
- 参考解法要点：把 CDC 的 changelog 映射为 ES 的 index/delete；忽略 delete 是必须避免的错误。

## 作业 2：设计可回放的多目标管道

- 目标：让一份变更同时喂湖仓、ES、缓存且下游可各自重放。
- 任务：Flink CDC 先把变更写入 Kafka（按主键分区保证同键有序），再由独立消费作业分别落 Paimon 湖表（upsert）、ES、Redis；说明新增一个下游时为何无需改动源库与采集作业。
- 验收标准：同主键事件在 Kafka 分区内有序；某下游可重置 offset 重放补数而不影响其它下游；源库只被采集一次。
- 参考解法要点：Kafka 解耦采集与消费；重放能力来自保留历史 + 幂等 sink。

## 作业 3：处理 schema 演进与全量衔接边界

- 目标：让管道在上游改列、以及全量转增量切换时不崩不丢。
- 任务：给下游配置 schema 兼容策略（新增列可容忍、改名/删列有告警与降级），并验证增量快照阶段在 chunk 切换期间发生的 update/delete 被正确回填、最终与源库一致；构造"快照中途该行被改"的用例。
- 验收标准：加一列后管道继续运行、旧记录不报错；快照期变更不丢；给出改名列的运维处置流程。
- 参考解法要点：schema evolution 是 CDC 事故高发区；低/高水位回填保证全量增量无缝且不重。
