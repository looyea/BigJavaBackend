# 与 Kafka Streams 选型（关联） · 作业

## 作业 1：为三个场景做选型并写理由

- 目标：把"引擎 vs 库"的决策轴落到具体场景。
- 任务：分别就"①某订单微服务把自身 topic 做无状态清洗后写回 Kafka""②全公司统一实时数仓，多源 CDC 大表关联落湖仓""③风控需要跨小时大窗口 + TB 级用户画像 join"，给出选 Kafka Streams 还是 Flink，并各写 3 条基于状态规模/运维成本/能力生态的理由。
- 验收标准：①选 KS、②③选 Flink 且理由命中对应维度；明确说明每个选择的"代价"（如 KS 的大状态风险、Flink 的集群运维成本）。
- 参考解法要点：以"状态是否超单机、是否需平台化共享、是否要复杂窗口/CEP/批"为轴，不以"哪个更流行"决策。

## 作业 2：评估迁移成本与共存方案

- 目标：论证一个"已有若干 KS 应用、又新建 Flink 平台"的共存架构。
- 任务：画出一个团队同时使用 KS（应用内局部实时）与 Flink（统一管道）的边界划分，指出重复建设的风险点（如两套 EOS 语义、两套监控），给出"什么情况下把 KS 作业合并进 Flink 平台"的判断标准。
- 验收标准：边界清晰（就地轻量 vs 平台共享）；列出合并触发条件（状态增大、跨服务复用、运维统一诉求）；避免"为统一而统一"把轻量逻辑强塞集群。
- 参考解法要点：选型是可演进的，先用库快速交付、当约束被突破再升级到引擎。

## 作业 3：用一段代码意图说明 EOS 层次差异

- 目标：区分"引擎内 once"与"端到端 once"在两种工具上的实现路径。
- 任务：写伪代码分别表达 Flink（Checkpoint + 可重放 Source + 2PC/幂等 Sink）与 KS（Kafka 事务 `EXACTLY_ONCE_V2`）达成 exactly-once 的关键配置点，并各标注一个"会破坏 once"的反例（Flink：Sink 非幂等；KS：读写非事务/自定义外部副作用）。
- 验收标准：两侧都点明"once 依赖输入可重放与输出事务/幂等"这一共同前提；反例具体可验证。
- 参考解法要点：once 不是引擎自带魔法，端到端成立取决于 Source/Sink 与事务边界。
