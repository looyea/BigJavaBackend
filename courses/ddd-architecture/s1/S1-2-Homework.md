# 战术设计：聚合、实体、值对象与领域事件 · 作业题

> 本节作业 3 题：一版聚合设计、一场贫血手术、一条 outbox 通路。

## 作业 1：设计"电力账户余额与缴费销账"聚合（设计）

业务事实：账户有余额（Money 值对象含币种）；欠费账单逐条存在；缴费先入余额再逐单销账；销账顺序影响违约金（先到期先销）；余额不允许为负（销账只动可动用部分）。

产出模型文档 + 骨架代码：

- 聚合清单与边界：账单要不要独立成聚合？判据写出（它是否有独立生命周期与并发写？"账单已销部分"的不变式由谁守护）；
- 不变式列表，每条标注被哪个聚合的哪个方法在同一事务内保证；
- 命令（祈使）与事件（过去式）双清单，事件载荷逐字段说明"为什么需要/不需要"（避免拖全量快照）；
- 并发场景推演：同账户并发缴费+并发冻结，version 冲突谁重试、会不会死锁。

**验收标准**：每条不变式能指到唯一守卫方法；"账单聚合归属"的论证有正反两面（这是本题真正的分叉点）。

## 作业 2：把一段贫血 CRUD 改造成守门员模型（动手）

选仓库里一个"Service 里塞满校验+set"的场景（状态流转类最佳）：

1. 先跑现状：列出该实体所有字段写入点（grep `setStatus|setAmount` 类），统计有业务校验的写入点占比——这张"裸写率"表是手术前的影像；
2. 引入值对象（金额/状态码至少一个）+ 聚合根业务动词方法，删除对应 setter，编译器会替你找出所有调用点逐个迁移；
3. 每迁一个方法补一个聚合单测（不依赖 Spring 与 DB——聚合测试便宜是战术设计的隐藏福利，记录测试运行耗时对比）；
4. 迁移完成后复跑第 1 步统计：裸写率应趋近 0，所有写路径可枚举。

**验收标准**：before/after 裸写率；聚合单测无需容器且总耗时 <1s；至少一处"迁移中发现了 Service 里漏校验的 bug"的记录。

## 作业 3：实现 outbox + 轮询投递 + 幂等消费的最小闭环（动手）

在 demo 项目实现"扣库存→通知发货"：

1. 库存服务：扣减聚合 + outbox 表同事务写入（列：id/event_type/payload/status/created_at，索引 status+id）；
2. 投递器：`@Scheduled` 200ms 轮询未发记录，按 id 升序批量投 MQ，成功置 SENT；kill -9 投递器再重启，验证不丢不重（不重靠消费端）；
3. 发货消费者：eventId 唯一索引去重表 + 业务处理同事务；人工重放同一条消息两次，断言只发货一次；
4. 混沌一击：在"本地事务提交后、outbox 标记前"注入崩溃（调试器断点 kill），重启后确认消息仍能补发且消费幂等兜住——把这条时间线写成故障报告。

**验收标准**：第 3/4 步的日志与断言证据；一句"为什么 at-least-once + 幂等消费 比 exactly-once 投递现实"的结论。

**提示**：顺手把 outbox 清理策略（SENT 保留 7 天）也做了，不然第三个月它会变成新的熔岩流。
