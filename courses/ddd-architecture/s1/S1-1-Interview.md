# 战略设计：统一语言与限界上下文 · 实际面试题

## 题 1：DDD 落地到底能解决什么问题？你们怎么落地的？

**考察点**：能不能把 DDD 从"一套术语"讲成"一条问题→方法→证据的链"。

**参考答案**：它解决的头号问题是**模型漂移**——业务脑中的规则与代码里的规则渐行渐远，表现为需求做反、改一处坏三处、没人敢碰老代码。落地分两步：战略上先做术语表+多义词挖掘，把限界上下文画出来（我们系统"客户"在销售/计费两个语境属性集重叠不到一半，据此切开）；战术上把规则收回领域对象（状态迁移+不变式），Service 退化为编排。我们的落地证据：切分后计费规则需求的平均改动文件数从 11 降到 4，上下文间只经事件/接口翻译。同时坦白适用边界：纯 CRUD 后台与生命周期短的活动页不值得全套 DDD，战略设计思维便宜、战术建模要看域的核心度。

**追问**：
- 最大的阻力是什么？——开发端的"表驱动思维"（先建表再写 Service）；解法是评审顺序反转：先审术语与模型归属，再看 DDL。

**加分点**：主动区分"核心域/支撑域/通用域"并说明资源投放差异（核心域精雕聚合，通用域直接买 SaaS）。

## 题 2：限界上下文和微服务是什么关系？你们的拆分依据是什么？

**考察点**：最易露馅的一题——答"一个上下文一个服务"基本可判定没真做过。

**参考答案**：上下文是**模型边界**，服务是**部署边界**，两者维度不同。我们的原则：一个服务可以承载多个强一致上下文（比如订单+价格计算初期同库同服务），但一个上下文绝不拆进两个服务（同一状态两处判定必然漂移）。拆分触发用四要素举证：变更频率断层、团队所有权、伸缩/可用性隔离、一致性半径，至少占两项才立项；不满足就停在"模块化单体+接口冻结"阶段——模块边界随时可以升级为服务边界，反向合并却近乎重写。判错的止损信号：联调频率持续高企、两个服务对同一业务概念的状态机不同步——我们据此合并回过一个"活动服务"。

**追问**：
- 怎么防止"模块化单体"永远无法演进成真微服务？——设门禁：模块间只走接口+事件、CI 里 ArchUnit 锁 import 规则；演进成本被纪律压平后，拆与不拆只剩运维账。

**加分点**：引用"分布式单体"作为反例收尾——拆了进程没拆依赖，两头的成本都付了。

## 题 3：多个服务共用一个 common-model 包，你们也这么干过，问题出在哪？

**考察点**：诚实复盘能力 + 契约演进的方案度。

**参考答案**：共享类=共享模型=共享变更半径：一方为自家需求加字段，其他方被迫重新编译发版；更阴险的是语义漂移——注释长出"仅支付使用"，字段成为各消费者的私有领土，公共包从"复用"沦为"耦合登记处"；上游改类型直接 breaking 全链路。替代：每个上下文持有自己的模型副本（哪怕 90% 重合——那 10% 恰是差异化的存在理由），边界处显式转换，跨边界只交换**版本化的领域事件/API 契约**（发布语言）。迁移策略：新代码禁止 import 公共 model（ArchUnit 门禁）；存量逐上下文本地化，公共包最终只留无业务语义的技术工具（Result/Page 这类）。

**追问**：
- 事件契约字段要不要也怕"改字段"？——要管：契约带版本号+兼容性规则（只加可选字段、删字段走双写过渡期），消费者按"未知字段忽略"解析。

**加分点**：给出度量——"改一个字段需要几个服务发版"作为边界健康度指标，这个数字的下降曲线就是治理成果。

## 题 4：业务方自己用的词都不统一（一会儿说"缴费"一会儿"充值"），统一语言怎么做下去？

**考察点**：软技能——UL 不是技术内政，是与人协作。

**参考答案**：这正是 UL 要处理的常态而不是障碍。动作：① 拉一张词频表，把同一事物的所有别名摊到业务方面前问"这两个是同一件事吗？"——多数时候他们自己也愣住，并当场给出裁决（"充值仅指余额入账，缴费指账单销账"）；② 裁决入术语表并标"禁用混写"；③ 代码、事件名、DB 表、产品文档四处的用词由 CI 词表校验/评审检查项对齐——术语表是活文档不是仪式文件；④ 历史包袱分阶段：新增接口强制新词，旧接口加别名映射层并设废弃期。本质是把"隐性歧义"显性化为"一次性讨论"，省下的是未来每次需求都要重新对齐的税。

**追问**：
- 业务方不配合怎么办？——降低参与成本：不搞"DDD 培训"，改为每两周 30 分钟的"读代码命名"会，让业务方从他们看得懂的方法名里挑错；纠错一次，语言统一一寸。

**加分点**：提到"代码里出现业务方没用过的自造缩写（payFlg、transAmt2）是语言断裂的量化信号"，可用 git 历史做统计追踪。

## 题 5：哪些项目不值得上 DDD？你见过把它用坏的案例吗？

**考察点**：反向判断——工具理性 vs 方法论传教。

**参考答案**：不值得的画像：逻辑简单的管理后台（CRUD+审批流）、生命周期以月计的活动系统、规则由外部不可变标准决定（对接银联报文，conformist 即可）、团队只有一人且无长期演进预期。DDD 的成本在"建模讨论与纪律维持"，收益在"复杂域长期演进"——两者不匹配就是浪费。用坏的真实案例两类：① 贫血包装——建了 domain 包放实体，规则仍全在 Service，只是把三层改叫 DDD 层（比没上更糟，因为名实不符挡住了真问题）；② 过度聚合化——每个名词都建聚合根+领域事件，三行能说的逻辑穿越四层调用栈，简单需求交付变慢后团队对整个方法论产生免疫排斥。我的标准姿势：先按"域的核心度"分级，核心域做深、支撑域薄模型、通用域外购，DDD 只用在配得上它的地方。

**追问**：
- 那核心域怎么快速识别？——三问：它错了业务会不会死（资金/计费）？它的规则是否市场差异化的来源（定价策略 vs 工单流转）？它是否占据变更需求流的头部——三项占二即核心域。

**加分点**：点出"微服务时代 DDD 被重新发明成服务拆分方法论（domain-driven design → service boundary design），但战略设计的成本对中小系统远高于收益"——显示方法论史观。
