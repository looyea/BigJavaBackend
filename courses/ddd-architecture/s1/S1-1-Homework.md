# 战略设计：统一语言与限界上下文 · 作业题

> 本节作业 3 题：一次多义词挖掘、一张遗留系统边界考古图、一场拆分论证。

## 作业 1：多义词挖掘与术语表立项（分析+动手）

在你熟悉的系统里做"同词不同义"实验：

1. 选 5 个高频名词（必含"用户/订单"级别的公共词），分别收集它在各模块的字段集合与生命周期状态机，做成对照表——预期至少一个词出现"属性集重叠 <50%"的分叉；
2. 拿分叉最严重的一个词去找业务方（或读需求文档）：验证分叉是"本来就该不同"还是"开发理解漂移"——两种结论的处置完全不同（划边界 vs 修模型）；
3. 产出该域的术语表 v1：词 × 所属上下文 × 定义 × 禁用的同义混写（如"付款/支付/缴费"只许一个），并写进 PR 模板一条检查项；
4. 反例收集：找一处代码里的词业务方绝不会用（如 `process/doHandle/handle2`），用统一语言重写其签名。

**验收标准**：对照表能支撑"这个词属于几个上下文"的结论；术语表经至少一位业务/产品同学过目并纠错一次以上。

## 作业 2：遗留系统的上下文考古（分析）

对一个边界混乱的真实系统（开源/公司项目均可）：

1. 从两条线索反推上下文边界：a) 变更耦合——git 共变文件聚类（接 S2-2 作业 3 的脚本）；b) 数据拥有权——谁能真正决定一张表的状态字段含义；
2. 标出三类违例：双向依赖对、跨上下文直连他人库表、公共 model 包里长注释的共享类；各给一条整改路径（事件化/ACL/本地化拷贝）；
3. 画出"现状上下文地图"与"目标地图"两张图，图下用四要素（频率/所有权/伸缩/一致性）逐条论证两图差异的必要性——不为拆而拆；
4. 排一个迁移序：哪条边先切断收益最大（通常是被改得最勤的那条）。

**交付物**：两张地图 + 违例清单 + 带论证的迁移序。

## 作业 3：一次拆分答辩（设计）

场景：产品要求把"营销活动"从交易主链路拆成独立服务，团队已写好新服务的脚手架。你用本课框架写一页答辩意见：

- 该域与订单/库存/价格各自的上下文关系（谁上游谁下游、集成模式选哪种、事件契约草案）；
- 四要素逐项打分：哪些支持拆、哪些其实不成立；"拆"与"先做模块内隔离+接口冻结、半年后视数据再拆"两方案对比；
- 给出你的立场与止损条件（拆后出现什么信号说明边界画错了，例如两个服务对同一状态各有判定）。

**验收标准**：论证里必须出现至少一条"反对部分拆分"的自我质询（考判断不考顺从）。

**提示**：这题真正的考点是——架构决策文档要让三年后的人看懂"当时为什么这么切"，而不只是"切成了什么样"。
