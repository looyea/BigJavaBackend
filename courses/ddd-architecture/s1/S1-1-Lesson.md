# 战略设计：统一语言与限界上下文

> 本节难度：★★★★☆
> 重要程度：★★★★★
> 学习产出：能用"同词不同义"实验在真实需求里找出限界上下文边界；解释统一语言不是全局词典而是"上下文内一词一义"；画出一张含上下游关系与集成方式（ACL/ conforms / 共享内核 / 发布语言）的上下文地图；说出"微服务边界画错的首要根因是跳过了战略设计直接分库"，并为拆分给出上下文对齐的论证模板。

```flow
例子目的：一次需求会里"客户"一词的三次变形——语义漂移如何把同一张表拖成三套系统的耦合灾难
销售说"客户": 有线索状态、跟进记录(营销语境的 Customer)
财务说"客户": 有开票资质、账期(计费语境的 Customer——根本不是同一批属性与生命周期)
物流说"客户": 只有收件地址与联系人(履约语境里它只是 AddressHolder)
结论: 三个上下文各养一套模型, 用翻译层对接; 硬造一个"大一统 Customer 表"= 三方需求互相踩踏的开始
```

## 一、DDD 解决的是沟通问题，其次才是代码问题

软件失败的头号原因不是技术，是"业务脑子里的模型"与"代码里的模型"不是一回事：需求文档说一套、开发实现猜一套、上线后运营用得别扭一套。战略设计的两件武器都对着这个病灶：

**统一语言（Ubiquitous Language）**：业务专家和开发者共用一套词表，且**词直接落进代码命名**——业务说"核销"，代码里就该有 `redeem()` 而不是 `updateStatusTo3()`。判据：拿一段代码让业务专家读方法名，他能纠正你说"这里应该先判断是否在冻结期"——读不懂或纠正不了，说明语言断了。

```java
// 目的：一次"语言泄漏"检查——业务词汇混进技术词汇, 是边界腐坏的最早信号
class OrderService {
    // 反例: 方法签名与注释里全是技术词——业务规则藏进了 SQL 和 DTO 转换的缝隙
    void process(Map<String,Object> param) {
        orderMapper.updateById(dto);            // "process"什么? dto 是什么的东西? 业务方无法参与任何评审
    }
    // 正例: 同一件事用统一语言重写——方法的业务前置条件让领域规则显形
    void markAsPaid(Order order, PaymentReceipt receipt) {   // 结果: 需求评审时业务方能直接指出"部分支付不允许调用它"
        order.markAsPaid(receipt);               // 行为归位到对象(接战术设计), Service 只做编排
    }
}
// 说明: 词表进 README/术语表 wiki 并挂进 PR 模板——"新词必须先入表再入码"是纪律不是倡议
```

## 二、限界上下文：模型的适用边界

同一个词在不同上下文含义不同，不是缺陷而是现实——限界上下文（Bounded Context）就是**给每个模型声明适用半径**：上下文内一词一义，跨上下文必须翻译。边界识别信号：

- **语义分叉**：上例的"客户"；再如"商品"在编辑上下文（草稿/审核/版本）与搜索上下文（扁平化可检索快照）里根本不是同一生命期；
- **变更频率断层**：定价规则每周变、账户主体十年不变，揉在一起会让稳定模块陪着抖动；
- **一致性需求差异**：库存扣减要强一致、营销展示容忍分钟级旧——不同一致性半径天然该在不同上下文；
- **团队/合规边界**：支付数据受 PCI 审计、行为数据不受——合规要求是硬边界。

切分工具：事件风暴（领域事件+命令+聚合的便利贴会议）里"谁发起命令、谁关心事件"的聚簇，通常就是上下文轮廓。

## 三、上下文集成：映射关系决定架构形态

```java
// 目的：ACL（防腐层）的最小形态——上游模型的"方言"止步于本上下文边界
@Component
class LegacyErpCustomerTranslator {                       // 上游: ERP 的 CUSTOMER_TBL 大宽表(140列, 三态复用字段)
    Customer toDomain(ErpCustomerRecord r) {              // 结果: 下游订单上下文只认识干净的 Customer, ERP 改字段不扩散
        return new Customer(r.getId(), r.getActive().equals("Y1")   // 反例预演: 不加这层, "Y1/N0/2=待定"的魔法值将渗透全模块
                ? Status.ACTIVE : parseAmbiguous(r), r.getTaxNo());
    }
}
// 错误用法: 把 ERP 的实体类直接 import 进订单领域模型——上游每次"顺手加列"都是一次跨团队 breaking change
// 说明: 集成模式四选一——conformist(服从上游标准, 对方是行业事实如银联报文)/ACL(对方烂但必须接)/
// 共享内核(两个上下文共用语义确实一致的一小块, 需联合发版纪律)/发布语言(公开稳定协议如开放平台 API)
```

上下文地图不是一次画完的：第一版标"谁依赖谁、依赖方向、集成方式"三列即可；**方向必须唯一**（上游不感知下游），出现双向依赖说明这里该拆新上下文或该设共享内核。

## 四、战略设计与微服务边界

"先定限界上下文，再决定要不要为它单独建服务"——这是把 DDD 用于架构决策的正确顺序：

- 上下文 ≠ 服务：一个服务可承载多个强一致上下文（单体演进友好），一个上下文也不该被拆进两个服务（同一个"订单状态"两处维护必然漂移）；
- 拆分论证模板：变更频率差异 / 团队所有权 / 伸缩与可用性隔离 / 一致性半径——四者至少占两项，否则拆了只多一套部署；
- 电商典型切法：商品、库存、价格、订单、支付、履约、营销、会员——注意"价格"独立成上下文（计价规则高频变）是多数系统踩坑后才懂的课。

## 五、常见线上问题

- 术语绑架：全局建了"字典服务"，把多义词强行统一成单一定义——所有上下文开始绕开它自建字段，字典沦为摆设；
- 共享 DTO 包：多个服务 import 同一个 `common-model` 的 `Order` 类，字段注释里长满 `// 仅支付使用 // 物流忽略`——这是没有边界的分布式单体；
- 事件即表结构：上下文间用"数据库表变更事件"耦合（字段级 publish），上游改列名下游全炸——发布语言应是稳定领域事件而非表结构投影；
- 边界漂移：需求压力期把新规则写进"最近的那个 Service"，半年后同一个业务概念的判定逻辑散在三处——需要"词-归属"审计例行公事。

## 六、小结与过关要点

战略设计回答的是"**哪里该一致、哪里该不同**"：统一语言保证上下文内不含糊，限界上下文承认不同视角不该含糊，集成模式管理边界上的翻译成本。过关自测：挑你系统里被用得最多的一个名词（十有八九是"用户/订单/商品"），说出它在几个上下文里有几种含义——只有一种含义的系统，通常是谁都没认真想过它的含义。
