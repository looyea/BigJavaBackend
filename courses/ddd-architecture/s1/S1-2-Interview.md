# 战术设计：聚合、实体、值对象与领域事件 · 实际面试题

## 题 1：你们怎么划聚合？划大了划小了分别什么症状？

**考察点**：战术设计第一题，考"不变式思维"还是"表思维"。

**参考答案**：唯一判据是"哪些规则必须在同一事务瞬间同时成立"——这些规则涉及的对象圈成一个聚合，其余跨对象协作全部降级为事件最终一致。症状对照：划大了=热点行锁争用（秒杀把"活动"整体当聚合，所有 SKU 扣减抢同一 version）、一次加载几 MB 对象图、并发冲突重试率高；划小了=不变式没人守（余额与流水分属两聚合，"合计相等"变成异步对账目标而非事务保证）——注意划小的真正风险不是性能而是**一致性承诺降级**，必须先确认业务能接受最终一致再切。我们的实操顺序：先列不变式清单（业务方评审），每条标注"必须瞬时成立吗"，是→同聚合，否→事件链——聚合边界是问答出来的，不是设计出来的。

**追问**：
- 订单明细无限增长会不会撑爆聚合？——会，对策是"列表分页物化"：明细聚合根不变，读路径走只读投影（CQRS 读模型），不把 500 条明细全加载进写模型；这是读写分离在聚合层的形态。

**加分点**：主动引用"一个事务一个聚合"并承认例外（创建聚合时新根+初始子实体同事务是合法的"一聚合"）。

## 题 2：这个字段是实体还是值对象？我怎么三秒钟判断？

**考察点**：小考——判断力是否已内化为口诀。

**参考答案**：三问：① 业务会不会追问"改完后还是原来那个吗"——会（订单号不变改地址）是实体，不会（换一张 50 元券还是那张券吗？没有此问）是值对象；② 它有没有独立生命周期与独立负责人——账单能不能脱离订单被财务单独追讨？能则倾向实体/独立聚合；③ 修改是"变更状态"还是"整体替换"——替换语义即值对象。三秒口诀：**有身份历史的是实体，只有值的是值对象**。顺手给出收益：值对象不可变→并发安全→可以随便共享缓存；"裸 BigDecimal + 裸 String 币种"的组合 bug（跨币种相加）在 `Money.add` 的类型约束下直接编译不过。

**追问**：
- 把 Address 建成值对象后, 客户改了地址、老订单要显示旧地址怎么办？——恰证明它是值对象：每订单持自己的 Address 副本，改的是"客户档案"那个聚合里的值，历史订单里的旧值天然留存——建实体表共享引用反而会做出"改一处全订单变"的事故。

**加分点**：能提"实体太多是模型没想清楚的报警"并给出你们收敛实体的真实案例。

## 题 3：业务要"下单成功后通知积分"，你怎么保证事件一定不丢不重？

**考察点**：可靠性工程的综合题（连回 dist-theory）。

**参考答案**：先破题：exactly-once 投递是神话，工程解=**至少一次投递 + 幂等消费 = 效果一次**。生产侧用 outbox：聚合状态与事件记录同本地事务写库（消灭"回滚了但消息发了/提交了但消息没发"两个窗口），投递器轮询或 CDC 订阅 outbox 发 MQ，失败重试直到 ACK；消费侧按 eventId 唯一索引去重表 + 业务动作同事务（先查后插的竞态靠唯一键兜底，见 dist-theory S1-3）。顺序补充：同账户事件按 key 进同一分区保证可序消费，积分侧还要带 version 做"旧事件不覆盖新状态"守卫。最后必须有对账闭环：outbox 已发总数 vs 消费落库总数按小时 diff——可靠性方案的最后一公里永远是核对。

**追问**：
- RocketMQ 事务消息不是更优雅？——半消息+回查同样解决双写原子性；差别是依赖面：outbox 零新增中间件、CDC 方案近实时，事务消息要 MQ 支持回查接口且业务表与消息状态仍在两个存储里——多数团队选 outbox 是因为"只赌本地事务"。

**加分点**：主动说出清理策略（SENT 记录归档删除）与积压监控（未发条数是告警一级指标）——方案的运维面常被候选人漏掉。

## 题 4：删 setter 这事在你们团队推得动吗？充血模型怎么过 code review 这关？

**考察点**：理想落地成现实的谈判能力——senior 真实痛点。

**参考答案**：推行的关键不是说服而是**换举证方向**：我们发生过一次"外部直接 setStatus 绕过冻结校验"的资损后，规范变成"状态字段写权限默认收进聚合根，新增写路径需在 PR 里说明为什么不能走业务动词"——贫血不再是默认选项而是需要申请的例外。工具护航：ArchUnit 规则禁止 `*.entity` 包外调用 setter、MapStruct 做 DO↔Domain 转换（持久化需要无业务构造时走 Converter/Reconstitution 专用入口，测试锁死它不能被业务调用）。收益侧也让 review 看得见：聚合单测不起 Spring 容器、毫秒级跑完，同一规则校验从"八处 Service 各一份"收敛到一处——改规则时 diff 只有一个文件，这是说服力本身。

**追问**：
- JPA 要求无参构造器和字段访问, 和充血模型怎么共存？——字段级访问+Converter 重建聚合；或干脆让领域模型不挂 JPA 注解（纯 POJO），用 MyBatis/jOOQ 做显式映射——"领域纯净度 vs ORM 便利"的账各自算，我们选后者因为团队 SQL 掌控优先。

**加分点**：坦承边界："不是所有类都要充血——DTO/配置/查询对象保持贫血是美德，这条纪律只划在领域模型圈内"，防止对方脑补成教条主义者。

## 题 5：用 DDD 之后交付速度变慢了，你被质疑过吗？怎么回应？

**考察点**：抗压+度量意识，答"坚持长期主义"是零分辨度。

**参考答案**：被质疑过，我的回应分三步：① 认账——头两个迭代确实慢了，建模会议+术语对齐是前置成本，这在我的预期内；② 换指标——不看"编码快慢"看"变更安全成本"：同类需求（改计费规则）的改动文件数从 11 降到 4、回归范围从全模块缩到单聚合、上线后该类 bug 清零——三个月的复利已经覆盖前置成本；③ 分级——只对核心域付这份建模税，支撑域薄模型、CRUD 直接三层快糙猛，DDD 全套用在刀刃上，把"质疑"转化为"适用范围"的技术讨论而不是信仰之争。我的真实立场：**慢的不是 DDD，是第一次把规则想清楚**——不付这笔钱，它只会以线上故障的形式寄账单回来。

**追问**：
- 怎么向管理层证明因果而不是相关？——对照组：同期未改造的模块做同类需求的 lead time 与缺陷逃逸率曲线；两个口径一起看才排除"需求变简单了"的混淆。

**加分点**：提到自己把建模结论沉淀为聚合清单+不变式文档，新人接手模块的 ramp-up 时间从两周缩到三天——速度叙事最硬的证据是团队维度而非个人手感。
