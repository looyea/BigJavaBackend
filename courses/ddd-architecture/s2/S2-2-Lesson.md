# 单体 / SOA / 微服务 / Serverless 权衡

> 本节难度：★★★★★
> 本节重要性：★★★★★
> 学习产出：能用"组织规模×业务复杂度×流量曲线"三轴给四种架构定位；说清微服务真正的成本清单（分布式事务/运维/网络/一致性）而非只谈收益；解释 SOA 与微服务的分野（企业服务总线 vs 去中心化、共享契约 vs 自治）；给出单体优先论（Monolith First）的落地判据与拆分的四个触发信号；讲清 Serverless 的冷启动/厂商锁定/时长限制三笔暗账，并能在一次架构评审里给出可反悔的过渡方案。

```flow
例子目的：四种架构不是先进程度递进, 而是四种"耦合放在哪里"的取舍
单体:      一个进程装所有模块, 复杂度低时最省 —— 编译/部署/事务都在本地
SOA:       粗粒度服务 + ESB 总线 + 企业级共享契约(ESB 是"电话总机") —— 适合异构系统整合
微服务:    细粒度 + 去中心 + 每个服务自带 DB —— 用分布式代价换团队自治与独立伸缩
Serverless:函数 + 事件驱动 + 按调用计费 —— 流量陡峭时最省, 平坦流量反而最贵
一句话: 架构选型的本质是"你要把复杂度锁在编译期、部署期还是运行期"
```

## 一、四轴定位法

- **组织规模**：微服务的首要驱动力是"康威定律"——服务边界对齐团队边界，两个披萨团队（≤8 人）拆 20 个服务是自找苦吃；
- **业务复杂度**：领域是否复杂到需要独立演进（接 ddd S1-1 的限界上下文），单体能装下的规则就别上网络；
- **流量曲线**：Serverless 的甜蜜区是"陡峭波峰 + 长时间谷底"（定时任务、图片处理、 webhook），平坦高流量用常驻进程更省；
- **演进阶段**：初创验证期 = 单体（改起来快），规模化期 = 模块化单体 → 按需抽服务，一上来就 200 个微服务是"用未来的复杂度买现在的确定性"，多数亏本。

## 二、微服务到底贵在哪（诚实成本清单）

```java
// 例子目的：把"拆一个服务"的真实代价摊开在评审桌上
// 单体里一次下单：
//   orderService.create(dto)  // 一个本地方法调用, 一个本地事务, @Transactional 直接回滚
// 拆成微服务后同一件事变成：
//   1. 网络: HTTP/gRPC 调用 cart/user/inventory/coupon/payment 5 个服务   ← 新增超时/重试/熔断
//   2. 一致性: 5 个服务各有独立 DB, 本地事务失效 → 上 Saga/TCC/本地消息表  ← 接 dist-theory
//   3. 运维: 5 条 CI/CD 流水线、5 套监控告警、服务发现、链路追踪            ← 接可观测性包
//   4. 分布式坑: 时钟漂移/网络分区/重复投递/乱序 —— 都要幂等与顺序治理
// 错误用例：为了"微服务很先进"把 CRUD 三张表拆成三个服务
//   后果：团队 5 人维护 30 个服务, 一次联调改 3 个仓库发 3 次, 交付速度不升反降
```

收益要如实记：独立伸缩（只扩热点服务）、技术异构（Python 算法服务与 Java 交易服务并存）、故障隔离（优惠券挂了不拖垮下单）、团队自治（对齐康威定律）。**判据一句话：微服务是把"代码复杂度"换成"运维与一致性复杂度"——组织撑得起才换。**

## 三、SOA ≠ 微服务（最常被混谈的一对）

- **SOA**：面向"企业级异构整合"，核心是 **ESB（企业服务总线）**——所有交互经总线路由/转换/编排，契约是重量级（WSDL/ESB Schema），总线是中心，也是单点与瓶颈；适合传统企业把 ERP/CRM/OA 缝起来；
- **微服务**：刻意去中心化，用轻量协议（HTTP/REST、gRPC）+ 服务发现替代总线，强调**服务自治 + 各自持久化 + Decentralized governance**；
- 分野口诀：**SOA 把智能放总线、把系统连起来；微服务把智能放端点、把系统切开**。ESB 项目常常"集成着集成着变成了分布式单体（Distributed Monolith）"——比单体还糟：既有单体的耦合又有网络的脆弱。

## 四、Monolith First 与拆分触发信号

Martin Fowler 的"单体优先"不是保守，是承认**没人能在画第一张架构图时就猜对边界**。合理路径：先用模块化单体把领域边界跑出来（内部按限界上下文分包、包间走接口），等真遇到压力再沿已有边界抽服务——拆的是"已经想清楚的缝"，而不是"猜的缝"。

```text
例子目的：四个"该拆了"的客观信号（缺信号就别拆）
① 发布排队：一个团队改一行要等所有团队回归测试, 每周只能发一次车
② 伸缩失衡：搜索模块要 20 台、用户模块 1 台就够, 整包一起扩浪费
③ 故障传染：报表导出 OOM 把下单进程一起带走（同进程无隔离）
④ 团队超载：> 30 人挤一个代码库, 改公共模块天天开会协调（康威已到极限）
反例信号：仅仅是"隔壁组用了 Go 我们想用"——技术时髦不是拆分理由, 是双输起点
```

## 五、Serverless 的三笔暗账

```yaml
# 例子目的：Function-as-a-Service 的账单不只在"按调用付费"那一栏
scenario: 图片缩略图生成（流量: 白天尖峰百万调用, 深夜近乎 0）
good_fit: 陡峭波峰+长谷底 → 不用为闲置付费, 冷启动可被预热/并发摊薄   # 结果: 比常驻省一个数量级
hidden_costs:
  cold_start: 首次/扩容调用要拉起运行时, Java 函数冷启动可达数百 ms~秒   # 错误用例: 对 P99 敏感的在线接口踩这个坑
  vendor_lock: 事件源/触发器/日志全绑云厂商专有 API, 迁移=重写编排层      # 反例: 核心交易链路放上去等于把命脉交给供应商
  duration_limit: 单次执行有时长上限(如 15min), 长任务要自己切分/状态外置   # 后果: 大文件批处理不能裸跑, 得配 Step Functions
when_not: 流量平坦且高 → 按调用计费反而贵过常驻；强状态/低延迟在线服务 → 别上
```

## 六、常见线上问题

- 拆出"分布式单体"：服务间同步链式调用 + 共享数据库 + 必须一起发布——耦合没减，还叠加了网络失败（识别：改一个字段要同时发 4 个服务）；
- 粒度错误：把一个聚合（不变式闭包）拆到两个服务，跨服务加锁/分布式事务常态化（接 ddd S1-2：聚合是拆分的最小原子，不可切）；
- 数据一致性想当然：默认"消息一定会到、不会重、不会乱"——幂等/顺序/去重三件事没做就上线（接 dist-data S2-1）；
- Serverless 当万能胶：把有状态、长时任务、低延迟在线接口都塞进函数，冷启动+时长限制+锁定三杀。

## 七、小结与过关要点

四种架构回答的是同一个问题：**把耦合锁在哪一层**。单体锁在编译期（一个进程），SOA 锁在中心总线（运行期编排），微服务锁在服务边界+网络（运行期协作），Serverless 锁在事件与计费模型（按次拉起）。选型不看先进展望，看三件事——组织撑不撑得起分布式成本、流量曲线配不配得上计费模型、边界是想清楚了还是在猜。过关自测：给你现在的项目，说出"为什么不拆"或"为什么现在该拆"，并给出一个**可反悔的过渡方案**（模块化单体的包边界就是反悔成本最低的保险）。
