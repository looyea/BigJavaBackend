# CQRS、事件溯源与架构决策 ADR · 实际面试题

## 题 1：CQRS 是什么？什么场景该用，什么场景不该用？

**考察点**：会不会把 CQRS 当教条，能不能分档谈成本。

**参考答案**：CQRS 的出发点是"命令（改状态、要校验、要事务）和查询（只读、要快、要多样视图）天然矛盾"，硬塞一个模型会让查询的灵活 JOIN 拖沉写模型、写模型的充血校验污染查询接口。它有三个递增力度：**① 只分离读写模型**——命令走充血领域模型保不变式，查询绕过聚合直接面向视图用轻量 DTO/物化视图自由 JOIN，**同一个库**，成本最低、最常用，90% 场景应该停在这一档；**② 读写链路分离**——命令与查询走不同代码路径甚至不同处理管道；**③ 读写独立伸缩**——用异构存储，各自按需扩容。该用的是读写真的冲突（列表/报表要多样高性能视图、读 QPS 远高于写）；不该用的是把查询也套进聚合（为一个列表页加载 8 个聚合根再 map，这是要治的反模式，不是要供的教条），以及没需求就上第三档异构存储——那是拿最终一致性凭空换伸缩性，白白背双写同步和两份运维。

**追问**：
- CQRS 一定要配事件溯源吗？——不。CQRS 的读投影完全可以只存最新状态快照，不保留事件流。两者常捆绑是因为天然契合，但可独立。
- 上异构存储后写后读不到怎么办？——就是最终一致，要么前端接受投影滞后、要么做"写路径读自己的库"，代价必须先评估。

**加分点**：一句收口"先问读写到底冲不冲突"——架构选型是成本收益题，不是先进与否题，能守住"从最轻档起步、按信号加码"就是成熟的 CQRS 观。

## 题 2：事件溯源相比直接 UPDATE 存最新状态，多付了哪些代价？

**考察点**：是否只看到 ES 的"审计/时间旅行"糖衣，看不见四笔重账。

**参考答案**：ES 的本质是"事件流是唯一真相源、当前状态是 fold 出来的投影"——`余额 = Σ(入账-出账)`，append-only 不可变，天然带来时间旅行、完整审计、领域事件免费得到、bug 可重放定位。但四笔账必须诚实评估：**① 事件 schema 演进**——事件永久保存，字段改名/拆合比改表结构难得多，要写 Upcaster 把旧事件升级到新版本，版本治理是长期负担；**② 快照**——事件流会变长，不定期打快照，加载一个有 3 万事件的聚合就重放 3 万条，P99 直接炸；**③ 最终一致的 UI**——写后读投影可能滞后，前端要处理"提交成功但列表还没刷新"；**④ 存储增长**——只增不改，容量与归档策略要提前设计。最狠的纪律是**事件不可变性**：一旦图省事 UPDATE/DELETE 历史事件，"真相源"契约就破了，审计与重放全部失真。

**追问**：
- 哪些实体不适合 ES？——没有真实状态演进的（字典表、配置项），上 ES 徒增事件表和投影维护、零收益。
- ES 和 CDC/审计表怎么取舍？——只要"改了什么"的留痕，一张 append 审计表或 binlog CDC 往往就够，不必把整个读模型都建立在重放之上。

**加分点**：主动说"能论证不用 ES 往往比硬上更显成熟"——用一个收益/代价体检表给候选场景判死刑或判活用，展示抵抗银弹冲动的定力。

## 题 3：你们团队怎么做架构决策管理？ADR 到底解决什么问题？

**考察点**：是否有工程治理意识，而不只谈技术。

**参考答案**：ADR 解决的是架构最贵的问题——不是选错，而是**没人记得当初为什么这么选**。典型事故：半年后新人把当年精心设的约束当"历史包袱"删掉，或者团队反复重开已经定过的议题吵三轮。ADR 是一页 markdown，进代码仓库、跟着 PR 走，四段缺一不可：**背景**（当时的约束和痛点）、**决策**（做了什么选择）、**后果**（正负影响都写，不能只报喜）、**替代方案**（考虑过什么、为什么否决），再带一个**状态**字段（已采纳/已废弃/被某 ADR 取代）让决策可被后续推翻且留痕。它的纪律是"轻量但强制"——轻量指一页纯文本进仓库、不建新流程新工具；强制指**改架构约束的 PR 必须链接或新增 ADR，评审时即检查**，否则 ADR 目录会退化成没人读的 wiki。

**追问**：
- ADR 和设计文档有什么区别？——设计文档讲"系统是什么样"，ADR 讲"为什么这么定、放弃了什么"；最值钱的恰恰是记录被否决的替代方案和否决理由。
- ADR 会不会变成形式主义？——会，如果不进评审、不强制挂钩 PR。判断标准：新人能否只读 ADR 就回答"当初为什么不选另一条路"。

**加分点**：给出落地打法——把 `docs/adr/` 纳入模板、PR 检查项加一条"是否触及架构约束、是否挂 ADR"，并强调"被取代"关系链让决策演进可追溯，体现真正的工程治理成熟度。
