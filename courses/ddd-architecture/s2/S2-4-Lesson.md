# 从单体到微服务的演进与拆分策略

> 本节难度：★★★★★
> 本节重要性：★★★★★
> 学习产出：能把"要不要拆、何时拆、怎么拆"讲成一套有纪律的工程决策而非潮流站队。核心判断：**微服务不是目的，是权衡**——它用运维复杂度（服务发现、分布式事务、可观测、独立部署链路）换团队解耦与独立伸缩；只有当**组织/交付瓶颈**（发布互相阻塞、代码所有权冲突、伸缩需求差异大）真实出现时才拆。掌握**战略拆分依据**：按**限界上下文**（业务边界）而非技术分层横切，避免"分布式单体"；按**变更频率与伸缩画像**差异决定拆分粒度。掌握**演进手法**：**绞杀者模式（Strangler Fig）**逐步用新服务替换旧单体功能、**扩展柜（Expansion Branch）**在不碰主干下开新能力、**防腐层（ACL）**隔离遗留模型、**发布/下线**双写与流量灰度迁移。数据拆分是最难点：**先拆代码后拆数据**、按上下文做**数据库去共享**（各服务私有库）、跨服务读写用 API/事件而非直连他库、迁移期**双写 + 回填 + 对账**保证不断流。识破"按团队 KPI 硬拆""共享同一 DB 的伪微服务""没有可观测就上分布式""一次性大重构推倒重来"等坑。

## 一、拆分的触发条件与依据

```text
图目的：先问"为什么拆", 触发条件是组织/交付瓶颈, 不是技术时髦
真实信号: 发布互相阻塞、代码所有权冲突、模块伸缩差异大、故障半径不可接受
拆分依据: 限界上下文(业务边界) > 变更频率 > 伸缩画像; 不要按技术分层横切(那会造分布式单体)
粒度: 团队沟通带宽(2-pizza)、独立部署能力为上限, 拆太细=分布式复杂度爆炸
```

## 二、演进手法：不是推倒重来

```text
图目的：安全地"边开飞机边换引擎"
绞杀者(Strangler Fig): 路由层把已迁移功能导向新服务, 逐步掏空旧单体
扩展柜(Expansion Branch): 新能力另起服务不碰主干, 验证后再反哺
防腐层(ACL): 在新旧模型间加转换层, 阻止遗留模型污染新上下文
灰度迁移: 双写→读切换→下线旧路径, 每步可回滚
```

```java
// 目的：绞杀者——门面按开关把某能力流量切到新服务, 旧单体仍可回退
Response handle(Req r) {
    if (flags.isOn("order.newService")) return orderClient.call(r);   // 说明：新功能走独立服务
    return monolith.order(r);                                          // 结果：未切换流量仍走单体, 平滑迁移、随时回滚
}
// 反例：新服务和旧单体长期共享同一张表直接互写 ❌ 耦合没解开, 变成"分布式单体", 一改双崩
```

## 三、数据拆分：最难也最关键

```text
图目的：代码好拆、数据难分——去共享数据库才是真解耦
① 先按上下文拆代码职责, 再拆数据归属(谁拥有哪张表)
② 各服务私有库; 需要他域数据走 API 或订阅事件, 绝不直连他库
③ 迁移期: 双写 + 存量回填 + 数据对账, 校验一致后才切读、下线旧表
```

## 四、坑与底线

- **没有可观测别上分布式**：链路追踪/指标/日志不就绪时，一次跨服务故障根本查不动——先把监控体系建起来再拆。
- **警惕"合规微服务"**：拆了服务却共享 DB、共享发布节奏、强同步调用链，等于把单体的耦合平移到了网络层。
