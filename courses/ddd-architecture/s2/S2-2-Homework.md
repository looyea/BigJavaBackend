# 单体 / SOA / 微服务 / Serverless 权衡 · 作业题

> 本节作业 3 题：一次架构选型评审、一个拆分信号打分表、一笔 Serverless 成本账。

## 作业 1：给一个真实场景做架构选型评审（设计）

场景：一个日均 3 万单的区域电商，团队 18 人，现状单体（Spring Boot 单应用 + 单 MySQL），近期痛点是"大促时搜索拖垮下单""每次发布全员回归要半天"。

请产出一份**评审结论**（不是 PPT 口号，是能被追问的决策）：

1. 用四轴（组织规模/业务复杂度/流量曲线/演进阶段）给现状定位，指出 18 人撑不撑得起全面微服务（提示：≤8 人两个披萨团队的倍数）；
2. 给出**过渡方案**而非一步到位：先做"模块化单体"（按订单/库存/搜索/用户分限界上下文包，包间走接口、CI 用 ArchUnit 锁边界），只把"搜索"这一个伸缩失衡的模块先抽成独立服务；
3. 写清为什么搜索先拆（伸缩失衡 + 故障隔离两个信号同时命中）、为什么其余暂不拆（缺发布/团队超载信号）；
4. 给出一个**可反悔路径**：若抽出的搜索服务证明没必要，怎么低成本并回单体（提示：端口/适配器边界让搜索既能本地调用也能远程调用）。

**验收标准**：四轴定位一段 + 过渡方案图 + "搜索先拆/其余不拆"的信号对照 + 反悔路径说明（必须点名一个具体反例：为什么不能一上来 18 人拆 15 个服务）。

## 作业 2：为项目建一张"该拆了没"信号打分表（动手）

把本课四个拆分信号做成可量化打分表，对当前/最近一个项目逐项打分（0=没有、1=轻微、2=严重）：

```text
例子目的：把"要不要拆微服务"从感觉变成可核对的分值
发布排队   score=?  证据: 本周发布等待时长 / 是否全员回归才敢发车
伸缩失衡   score=?  证据: 各模块资源用量差异(搜索 vs 用户的 CPU/内存曲线)
故障传染   score=?  证据: 一次 OOM/慢查询是否拖垮整个进程(近 3 月事故单)
团队超载   score=?  证据: 代码库提交者人数 / 改公共模块的协调会议频率
判定阈值: 任一=2 或 总分>=4 才启动"抽一个服务", 全 0 却想拆=过度设计
反例记录: 若仅"想换技术栈"驱动拆分 → 在表下单独写一行"技术时髦, 不计入信号"
```

**验收标准**：填好的打分表（每项附真实或合理编造的量化证据）+ 一句基于阈值的结论（拆谁/不拆）+ 对"技术时髦不计入信号"这一行的一句解释。

## 作业 3：算一笔 Serverless vs 常驻的账（动手+计算）

以"图片缩略图生成"为例，对比两种部署在一个月内的成本：

1. 流量模型 A（陡峭）：白天 100 万次调用集中在 4 小时、深夜近 0 → 用 FaaS 按调用计费 + 常驻按小时计费的 24×满载 对比，估算谁便宜（可查任意云厂商公开价格数量级，重在方法）；
2. 流量模型 B（平坦）：全天均匀 2000 万次调用 → 重算，观察结论是否反转（提示：按调用计费在平坦高流量下会贵过常驻）；
3. 给两种模型各标出三笔暗账落点：冷启动是否伤体验（在线敏感 vs 离线可容忍）、厂商锁定迁移成本、单次时长上限对大文件的影响；
4. 结论：写出"FaaS 适合___流量形态 + ___延迟要求"的一句话选型判据。

**交付物**：A/B 两张成本对比（列出假设与计算过程，不要只给结论）+ 三笔暗账落点 + 一句话判据。

**提示**：这题真正的考点是"别被'按量付费=省钱'直觉骗了"——省不省钱完全取决于流量曲线的形状，平坦高流量按量反而更贵。
