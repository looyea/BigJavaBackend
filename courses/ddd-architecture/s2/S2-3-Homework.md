# CQRS、事件溯源与架构决策 ADR · 作业题

> 本节作业 3 题：搭一个最小 CQRS 读投影、写一份真 ADR、给一个 ES 场景做成本体检。

## 作业 1：给现有查询做"读写分道"（设计+动手）

找一个你项目里"为了一个列表/报表页，把聚合根全加载出来再 map"的慢查询（没有就造一个：订单列表页 JOIN 用户/商品/优惠 8 张表）：

```java
// 例子目的：把 CQRS 第一档落到一个真实接口上
// 命令侧保持充血模型: 下单/改状态仍走 Order 聚合校验不变式
// 查询侧改造前(反例): 列表页 new 出 8 个 Order 聚合根, 只为了显示 3 个字段
List<Order> orders = orderRepo.findAll();              // 错误用例: 加载完整聚合 + 各自懒加载 → N+1 且浪费不变式校验
// 查询侧改造后(正解): 独立只读投影, 一条 SQL 拼视图 DTO, 不碰聚合
List<OrderListVO> rows = jdbc.query(
    "select o.id, o.amount, u.name from orders o join users u ...",  // 结果: 读路径自由 JOIN, 与写模型互不污染
    (rs,i)-> new OrderListVO(rs.getLong(1), rs.getBigDecimal(2), rs.getString(3)));
// 约束: 用 lint/评审防止业务写逻辑漏进这个投影(读侧只准查不准改)
```

要求：① 命令侧与查询侧拆成两个入口（`handle(cmd)` vs `query(q)`）；② 对比改造前后列表接口的 SQL 次数与耗时（贴日志）；③ 说明你用的是哪一档 CQRS、为什么不上异构存储。

**验收标准**：读写两个入口代码 + 改造前后查询次数/耗时对比 + 一句"为什么停在同库不同视图这一档"。

## 作业 2：为你的项目补写 3 份 ADR（动手）

在项目根建 `docs/adr/`，用编号 + `ADR-#### 标题` 命名，写 3 份：

1. **一份真实历史决策**：翻出你们已经采用的一个关键选型（为什么用 MySQL 不用 PG、为什么上 Redis、为什么这样分库），补写成 ADR——重点复原"背景"和"当时否决的替代方案"；
2. **一份当下正在纠结的决策**：按"背景/决策/后果(±)/替代方案/状态"五段写全；
3. **一份"故意写废"再被取代**：写一个 ADR 标 `状态: 已废弃, 被 ADR-xxxx 取代`，演示决策可被后续推翻且留痕。

**验收标准**：3 个 markdown 文件（含状态字段与被取代链接）；每份的"替代方案"段必须写清"考虑过什么、为什么否决"，而不只写结论。

**提示**：检验标准是——半年后的新人读你 ADR，能否回答"当初为什么不选另一条路"。答得出才算合格。

## 作业 3：给一个候选 ES 场景做成本体检（设计）

挑一个业务（钱包余额 / 订单状态流转 / 内容审核记录），判断该不该上事件溯源，产出一页体检：

1. 收益核对：是否真的需要"时间旅行查询 / 完整审计留痕 / 事件即业务真相"？逐条打勾或打叉；
2. 四笔账预估：事件 schema 演进（预计会改字段吗）、快照策略（一个聚合预计多少事件、多久打一次）、最终一致 UI（用户写后立刻读能否接受投影滞后）、存储增长（只增不改，一年量级）；
3. 决策：如果收益 < 代价，明确写"用普通 CRUD + 审计表即可，不上 ES"，并给出替代实现；如果值得上，说明是否顺带要 CQRS（用本课"两个理由都要各自成立"判据）；
4. 把结论回填成作业 2 的一份 ADR。

**交付物**：一页 ES 成本体检表 + 明确"上/不上"结论 + 对应的 ADR。

**提示**：这题真正的考点是"抵抗把 ES 当银弹的冲动"——能论证"不用 ES"往往比硬上更能体现架构成熟度。
