# 分层、六边形与整洁架构 · 实际面试题

## 题 1：三层架构、六边形架构、整洁架构有什么区别？你到底该用哪个？

**考察点**：是不是把三种流派当对立宗教，还是能抓到同一根标尺。

**参考答案**：三者不是互斥竞品，而是同一问题的三代补丁——**依赖箭头只能指向内层（业务），不能让易变的 IO 反过来拴住稳定的业务**。经典三层 UI→Service→DAO 的问题不在"层"而在方向：上层 import 下层具体实现，Service 和 MyBatis/Redis 焊死，跑一段业务逻辑得起容器连数据库，测试成本直接扼杀重构勇气。六边形（Ports & Adapters）把核心抽出来，核心声明两类端口：驱动端口（`OrderUseCase`，被输入适配器实现）和被动端口（`OrderRepository`，被输出适配器实现），Web/DB/MQ 全变成可拔插插件，关键点是**接口定义在消费者包里**，这是 DIP 的架构级落地。整洁架构再加一层同心圆判据：企业级规则（不变式/聚合）> 用例规则 > 接口适配器 > 框架驱动，越靠圆心越稳定。选型结论：中小团队三层够用但必须守住"Service 不 import IO 细节"；领域复杂、要长期演进就上六边形；整洁架构更像给六边形补了"内层还能再分圈"的度量衡。真正答好的标志是那句——**选哪种不重要，能回答"你的圆心是什么、箭头靠什么强制、端口里混进对方类型没有"才重要**。

**追问**：
- 怎么三分钟判断一个项目分层是否失效？——打开最核心业务的包，数 import：出现 redis/ibatis/http，框架包出现几个，架构就"悬"了几层。
- 六边形一定要拆模块/独立进程吗？——不用，包级隔离即可；适配器"可远程化"只是能力不是义务，单体里端口本地调用，拆分那天同一接口改 Feign 实现，核心零改动。

**加分点**：主动点出三种流派的共同敌人是"事务脚本挂名分层"——Controller→Service→DAO 各一千行转发，规则还在 Service if/else，识别法是"领域包薄于一页、用例包厚过规则"。

## 题 2：什么是"依赖倒置执行歪了"？你在实际项目里见过哪些形态？

**考察点**：是否只会画箭头，还是能识别"假倒置"。

**参考答案**：倒置的本质是接口归消费者所有、实现细节不渗入抽象。最常见的两种走形：① **端口被实现方污染**——`OrderRepository` 接口写在 domain 包，可签名里却是 `Page<OrderPO>`、`Pageable`、`Example<OrderPO>` 这些 Spring Data/JPA 类型，倒置只倒了一半，IO 概念顺着接口签名漏回核心，将来换游标分页或换 jOOQ 还得先动领域层；正解是端口世界只用领域类型（自定义 `Page<T>`/`OrderQuery`），PO↔Domain 的翻译关进 adapter。② **领域层反向指挥应用层（聚合自救）**——在 `StockItem` 聚合里注入 `OrderRepository` 自己 `save` 自己，看着像充血，实际把领域层焊死在持久化上；保存是用例（application）编排的职责，`repo.save(item)` 该写在 UseCase 而不是聚合里。

**追问**：
- 贫血 DTO 贯穿三层算不算走形？——算另一类病灶：接口收到的 Request 被 `@Transactional` 直接持久化，等于外部契约即内部模型，上游改字段等于改数据库；应在边界处把 Request 翻译成领域对象。
- MapStruct 放哪层？——放 adapter，它是 PO↔Domain 的翻译工，绝不能让映射逻辑出现在领域层。

**加分点**：给出"端口纯洁度测试"——随便挑一个端口接口，问"换掉底层存储，这个接口要不要改一个字"，要改就是污染。

## 题 3：ArchUnit 真能守住分层吗？团队不认怎么办？

**考察点**：架构治理是讲情怀还是能落地成 CI 红线。

**参考答案**：ArchUnit 的价值是把"分层"从文档愿望变成能自动变红的测试。三条常用规则：`noClasses().that().resideInAPackage("..domain..").should().dependOnClassesThat().resideInAnyPackage("..springframework..","..ibatis..","..redis..")` 守领域纯洁；`layeredArchitecture()` 声明 Domain/Application/Adapter/Infra 并规定依赖只能由外向内；`mayOnlyBeAccessedByLayers` 禁止 Controller 越过 Application 直连 Repository。规则一旦进 PR 流水线，反向 import 30 秒内被拦。团队不认的根因往往不是技术，是"没配规则只建包"——三个月后跨层调用靠记忆执法，记忆比注释先失效，于是大家觉得分层是形式主义。落地打法：先加最硬的一条（domain 禁依赖框架）跑红基线、豁免存量给迁移期，增量代码零容忍；豁免必须带"原因+负责人+到期日"，否则门禁会被 `// NOLINT` 式无注释豁免一点点掏空。

**追问**：
- 存量违规太多，一上来全拦会不会引起反弹？——分层推进：新模块强制、老模块挂"到期豁免"，把技术债显式化成可视化数字，比一刀切更能推进。
- ArchUnit 能替代 code review 吗？——不能，它只兜住"包级依赖方向"这类机器可判的约束，语义分层（规则是否真下沉到领域）仍要人审。

**加分点**：抛出"能自动变红的才是架构，写在文档里的只是愿望"，并说明收益要敢量化——测试账（无容器秒级单测、CI 时长）、替换账（真换过一次 ORM 才算数，没换就是保险费要诚实）、部署账（适配器远程化=微服务演进梯子）。
