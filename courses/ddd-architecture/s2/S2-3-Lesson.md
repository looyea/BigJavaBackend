# CQRS、事件溯源与架构决策 ADR

> 本节难度：★★★★★
> 本节重要性：★★★★☆
> 学习产出：能区分 CQRS 的三个力度（读写模型分离 / 读写链路分离 / 独立伸缩）并判断何时值得上；讲清事件溯源（ES）"以事件为真相源、状态是投影"的本质与它的四笔重账（事件 schema 演进/快照/最终一致 UI/存储增长）；说清 CQRS 与 ES 能独立使用、并非绑定；能用 ADR（架构决策记录）写出一份"背景—决策—后果—替代方案"的可追溯决策，并解释 ADR 为何是"轻量但强制"的治理工具。

```flow
例子目的：CQRS 与 ES 是两件事, 别打包上；ADR 是给"为什么这么选"留的案底
CQRS 三力度:  ①只分离读模型(最常用, 一个库两种视图)  ②读写链路分离(命令走领域模型, 查询走投影)  ③读写独立伸缩(异构存储)
Event Sourcing: 真相源不是"当前状态行", 而是"append-only 事件流"; 状态 = fold(所有事件)
关系:          CQRS 可不用 ES(投影也可以是最新状态快照); ES 可不用 CQRS(但天然契合)
ADR:           一页 markdown 记录"当时为什么这么定", 让半年后的人不用考古邮件群聊
```

## 一、CQRS：把"读"和"写"的复杂度分开

命令（Command，改状态、要校验、要事务）和查询（Query，只读、要快、要多样视图）天然是两种需求，硬塞进同一个模型会导致：查询为了灵活 JOIN 一堆表，反而把写模型拖沉；写模型为了校验堆满领域逻辑，查询接口被污染。CQRS 按投入递增分三档：

```java
// 例子目的：最小可用 CQRS —— 只分离读写模型, 同一个库, 成本最低最常用
// 命令侧: 走充血领域模型, 保证不变式
public void handle(SubmitOrder cmd) {
    Order o = orders.find(cmd.id());
    o.submit(cmd.items());          // 领域方法内校验库存/金额不变式; 结果: 写路径规则集中在模型
    orders.save(o);
}
// 查询侧: 绕过领域模型, 直接面向视图的轻量 DTO/物化视图, 怎么快怎么 JOIN
public OrderDetailVO query(OrderId id) {
    return jdbc.query("select ... join ... where o.id=?", ROW_MAPPER, id);  // 读路径不碰聚合, 可为报表任意拼
}
// 错误用法: 把查询也套进聚合, 为了一个列表页加载 8 个聚合根再 map —— 性能灾难, CQRS 的意义就是允许它俩分道
// 反例: 上了"读写独立异构存储"(第三档)却没有对应的读写伸缩需求 —— 白白背最终一致与双份运维
```

**判据**：读和写真的冲突吗？90% 场景第一档（读写模型分离、同库）就够，别一上来就异构存储+事件同步，那是拿最终一致性换伸缩性，需求不到就是自扰。

## 二、事件溯源：状态是投影，事件才是真相

传统 CRUD 存"当前值"（改一次覆盖一次，历史丢了）。ES 存"发生过什么"——事件 append-only 不可变，当前状态靠重放事件 fold 出来：`余额 = Σ(入账事件 - 出账事件)`。

```java
// 例子目的：ES 的核心循环 —— 事件流是唯一真相, 状态是算出来的投影
// 写: 不 update 余额字段, 而是追加事件
eventStore.append(accountId, new Deposited(100), new Withdrawn(30));  // append-only, 不可篡改, 天然审计日志
// 读: 从快照 + 增量事件重放出当前状态
BalanceSnapshot snap = snapshots.latest(accountId);                   // 快照: 防止事件太多每次从头重放(见"重账")
BigDecimal bal = snap.balance();
eventStore.after(snap.version, accountId).forEach(e -> bal = e.apply(bal));  // fold 增量事件; 输出: 与 DB 存值等价但可回溯
// 价值: 时间旅行(查任意历史点)/审计合规/领域事件免费得到(buggy 可重放定位)
// 错误用例: 把 ES 当普通 CRUD 用, 每个聚合几千上万个事件从不快照 → 加载一个账户重放 3 万条, P99 炸裂
// 反例: 对"没有真实状态演进"的简单实体(如字典表)上 ES —— 徒增事件表与投影维护, 零收益
```

**ES 的四笔重账（务必诚实评估）**：
1. **事件 schema 演进**：事件永久保存，字段改名/拆合要写 Upcaster 迁移旧事件，版本管理比表结构难；
2. **快照**：事件流会变长，要定期打快照否则重放成本失控；
3. **最终一致的 UI**：写后读投影可能滞后，前端要处理"提交成功但列表还没更新"；
4. **存储增长**：只增不改，容量与归档策略要提前设计。

**CQRS 与 ES 的关系**：常被捆绑（ES 天然产生事件流、CQRS 的读侧靠投影喂），但**可以只用其一**。简单 CRUD 加审计，可能只要 ES 不要 CQRS；高并发读多样视图，可能只要 CQRS 不要 ES。**两个都是重型武器，同时上要有 BOTH 都成立的理由。**

## 三、ADR：给架构决策留案底

架构最贵的不是选错，是**没人记得当初为什么这么选**——半年后新人把精心设的约束当"历史包袱"删掉，或反复重开已定议题。ADR（Architecture Decision Record）就是治这个的：一页 markdown，进代码仓库、跟着 PR 走。

```markdown
例子目的：一份能被追问的 ADR 骨架（四段缺一不可）
# ADR-0007: 订单读侧采用 CQRS 读写模型分离(同库)
状态: 已采纳(2026-03) | 取代: 无
背景: 订单详情页与运营报表 JOIN 8 张表, 与写模型充血校验互相拖累, 列表页 P99 超 800ms
决策: 命令走 Order 聚合保不变式; 查询走独立轻量 DTO 投影, 同库不同视图(不上异构存储)
后果: (+)读写模型各自演进互不污染, 列表页可任意 JOIN 优化  (-)两套模型有一定重复, 需 lint 防写逻辑漏进读侧
替代方案: A)读写彻底异构+事件同步(最终一致, 需求未到, 否) B)维持单体一套模型(性能已到顶, 否)
```

ADR 的纪律：**轻量**（一页、纯文本、进仓库，不建新流程）但**强制**（改架构约束的 PR 必须链接或新增 ADR，评审即检查）。它记录的不仅是"决定了什么"，更是"放弃了什么、为什么"——这才是半年后最值钱的部分。

## 四、常见线上问题

- 把 CQRS 当教条强上异构存储：没有读写独立伸缩需求却做双写/事件同步，凭空引入最终一致 bug（接 dist-data S2-1 一致性权衡）；
- ES 当万能审计：所有聚合都上事件流，事件表爆炸、无快照、无 upcasting 策略，重放成为性能黑洞；
- 事件不可变性被破坏：图省事 UPDATE/DELETE 历史事件，ES 的"真相源"契约一破，审计与重放全失真；
- ADR 写成"事后说明书"：只记录结论不记背景与替代方案，或建了 ADR 目录却无人遵守"改约束必挂 ADR"，退化成无人读的 wiki。

## 五、小结与过关要点

CQRS 回答"读写复杂度混在一起怎么办"——从最轻的"模型分离同库"起步，按需再加力度；事件溯源回答"要不要以事件为真相"——收益是审计/时间旅行/免费领域事件，代价是 schema 演进/快照/最终一致/存储四笔账，两者可分开用别捆绑硬上。ADR 回答"决策为什么"——一页纸、进仓库、改约束必挂，把"为什么放弃了另一条路"永久留住。过关自测：下次想上 CQRS+ES 全家桶前，先各写一句"我不用它会怎样"和"我用了要多养哪几笔账"，再写一份 ADR 让团队认账。
