# 从单体到微服务的演进与拆分策略 · 作业

### 作业 1：判断"该不该拆、拆到哪"的决策清单

- 目标：把"要不要上微服务"从潮流站队变成可论证的工程决策。
- 任务：选一个你熟悉的单体系统，列出真实存在的瓶颈信号（发布互相阻塞、代码所有权冲突、模块伸缩差异、故障半径）；若无明显瓶颈，就明确写"暂不拆"及理由。对确需拆的部分，按限界上下文给出纵切边界草案，并标注每块的变更频率与伸缩画像，论证拆分粒度。
- 验收标准：决策依据是组织/交付瓶颈而非"技术时髦"；切分沿业务边界纵切而非技术分层横切；给出粒度上限（沟通带宽/独立部署能力）而非"越细越好"。
- 参考解法要点：先问"为什么拆"再问"怎么拆"；识别"分布式单体"陷阱——按 Web/Service/DAO 横切即错。

### 作业 2：绞杀者迁移 + 防腐层落地

- 目标：在不推倒旧单体的前提下，安全地把一个能力迁移到新服务并能随时回退。
- 任务：为一个能力（如下单）实现门面路由：读取开关 `order.newService`，开则调新服务、关则回退旧单体；为新服务与遗留模型之间加防腐层做字段/语义转换；设计"双写→读切换→下线旧路径"三步灰度计划，每步给出回滚动作。
- 验收标准：开关可秒级切换且未迁移流量仍走单体；新上下文模型不被遗留结构污染；迁移每一步都可回滚、不出现停机一夜硬切。
- 参考解法要点：严禁新服务与单体长期共享同一张表互写；用扩展柜思路让新能力先不碰主干。

### 作业 3：数据拆分与一致性迁移方案

- 目标：把"共享大库"拆成各服务私有库，并保证迁移期数据不断流、最终一致。
- 任务：为一张被多模块共享的表设计拆分：明确归属上下文与私有库；他域访问改为 API 或事件订阅；给出迁移期"双写 + 存量回填 + 数据对账"流程，写清对账维度（总量、逐条、金额/状态）与不一致时的修复与告警，定义切读、下线旧表的准入条件。
- 验收标准：迁移期任一步可回滚；对账通过前绝不切读、不下线旧表；杜绝跨服务直连他库。
- 参考解法要点：先拆代码职责再拆数据归属；一致性校验数据可复用数据修复工具链，与 dist-data 的一致性校验思路一致。
