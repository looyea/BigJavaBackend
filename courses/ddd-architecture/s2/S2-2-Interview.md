# 单体 / SOA / 微服务 / Serverless 权衡 · 实际面试题

## 题 1：你们为什么用微服务（或为什么不用）？架构是怎么选型的？

**考察点**：这是架构面试的"元问题"，考的是你有没有真正的取舍思维，而不是站队。

**参考答案**：我不会先说"微服务先进所以用"。选型我用四轴定位——**组织规模、业务复杂度、流量曲线、演进阶段**。微服务的首要驱动力其实是康威定律：服务边界要对齐团队边界，一个 8 人团队拆 20 个服务是自找苦吃；它的本质是把"代码复杂度"换成"运维与一致性复杂度"，组织撑得起才换。所以我会坦白成本：拆一个下单服务，本地方法调用变成 5 个服务的网络调用（新增超时/重试/熔断），本地事务失效要上 Saga/TCC/本地消息表，运维多 5 条流水线加服务发现链路追踪。反过来，独立伸缩（只扩热点）、技术异构（Python 算法 + Java 交易并存）、故障隔离、团队自治是真收益。结论往往是 **Monolith First**：先用模块化单体把限界上下文跑清楚（内部按上下文分包、包间走接口、ArchUnit 锁边界），等命中"发布排队/伸缩失衡/故障传染/团队超载"这四个客观信号再沿已有边界抽服务——拆的是想清楚的缝，不是猜的缝。

**追问**：
- 那你怎么判断一个项目已经"过度微服务化"了？——出现"分布式单体"症状：服务间同步链式调用、共享数据库、改一个字段要同时发 4 个服务、必须一起发布，耦合没减还叠加了网络脆弱，比单体更糟。
- 为什么不一步到位拆干净？——没人能在画第一张图时猜对边界，一步到位是用未来的复杂度买现在的确定性，多数亏本。

**加分点**：主动给"可反悔路径"——模块化单体的包边界就是反悔成本最低的保险，抽出的服务若证明没必要能低成本并回（端口/适配器让同一接口既能本地又能远程调用）。

## 题 2：SOA 和微服务到底是不是一回事？ESB 现在还有价值吗？

**考察点**：会不会把两者混谈，能不能讲出分野的本质。

**参考答案**：不是一回事，最常被混。分野口诀——**SOA 把智能放在中心总线（ESB）、把异构系统"连起来"；微服务把智能放在端点、去中心地把系统"切开"**。SOA 面向企业级异构整合，核心是 ESB：所有交互经总线路由/转换/编排，契约重量级（WSDL/Schema），总线既是中心也是单点和瓶颈，适合把传统 ERP/CRM/OA 缝在一起。微服务刻意去中心化，用 HTTP/REST、gRPC + 服务发现替代总线，强调服务自治、各自持久化、去中心治理。ESB 今天没死，只是退到合适的位：企业系统集成（EAI）、遗留系统包装、协议/数据转换繁重的场景仍好用；但在互联网高并发核心链路里，中心总线会成为吞吐瓶颈和单点故障源。要警惕的是 ESB 项目"集成着集成着变成分布式单体"——这比单体还糟。

**追问**：
- 微服务之间就不能有"总线"类组件吗？——可以，但形态是**轻量、去中心、旁路**的（服务网格 sidecar、消息中间件做事件通道），不是把所有流量串在一个中心进程里的重量级 ESB。
- 服务网格（Istio）算不算新 ESB？——思想不同：网格把通信/治理下沉到边车、控制面不碰数据面，避免中心总线成为单点，是"去中心化的基础设施"而非"中心编排"。

**加分点**：能点出 SOA 也能很轻（早期一些 SOA 用轻量总线），微服务也能被用成 SOA（强行中心编排），关键看"智能放哪、有没有真正的服务自治与独立持久化"，展示不被名词带跑。

## 题 3：Serverless 能不能替代微服务成为主流架构？

**考察点**：对 FaaS 的边界认知，是否只会跟风。

**参考答案**：Serverless 和微服务不是替代关系，是**正交的两个维度**——微服务讲"怎么拆"，Serverless 讲"怎么跑和怎么计费"，一个微服务可以用 FaaS 承载，也可以常驻。FaaS 真正的甜蜜区是**陡峭波峰 + 长时间谷底**：图片缩略图生成、定时任务、webhook、事件驱动的胶水逻辑，不用为闲置买单，能省一个数量级。但它有三笔暗账：① 冷启动——首次/扩容调用要拉起运行时，Java 函数能到数百 ms~秒，伤 P99，所以强状态、低延迟在线交易接口不该上；② 厂商锁定——事件源/触发器/日志全绑云厂商专有 API，迁移等于重写编排层，核心链路放上去等于把命脉交给供应商；③ 时长上限——单次执行常限 15 分钟，大文件批处理不能裸跑要自己切分、状态外置。而且"按量付费=省钱"是直觉陷阱：平坦高流量下按调用计费反而贵过常驻。

**追问**：
- 冷启动在现代运行时缓解了吗？——有改善（预留实例/预热、GraalVM 原生镜像、SnapStart 等把 Java 冷启动大幅压低），但把它当"零成本"仍是错的，扩容突发仍会撞冷启动尾巴。
- BaaS/FaaS 会替代传统后端吗？——不会全面替代，会成为架构里"处理尖峰与事件"的一种算力形态，和常驻服务混用。

**加分点**：给出选型判据一句话——"FaaS 适合陡峭流量 + 可容忍冷启动的（近）离线场景；平坦高流量与低延迟在线核心用常驻"，并说明这本质是"把耦合和成本锁在事件与计费模型"这一层。
