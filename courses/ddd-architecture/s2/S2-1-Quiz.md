# 分层、六边形与整洁架构 · 小测验

> 全卷 100 分：单选 5×10 + 多选 2×10 + 判断 1×5 + 简答 15+10。达到 60 分解锁下一节。

### 1. 六边形架构（Ports & Adapters）里，"接口定义在谁的包里"遵循的原则是（10分）

- A. 谁实现接口，接口就写在谁的包
- B. 接口写在消费者（声明需求的一方）的包里，即 DIP 的架构级执行
- C. 接口统一放在最外层 infra 包
- D. 接口必须放在独立的 api 模块供所有人 import

> 答案：B
> 解析：应用核心声明"我需要什么"（如 OrderRepository），持久化适配器去实现它——接口在消费者包，依赖箭头指向内层，这才是倒置；写在实现方包里等于没倒置。

### 2. 判断"分层是否失效"最省事的审计动作是（10分）

- A. 数一数代码总行数
- B. 打开领域层（domain）的 import 列表，看是否出现 redis/ibatis/http 等框架包
- C. 看 Controller 有多少个
- D. 检查数据库表数量

> 答案：B
> 解析：领域层应零框架依赖；一旦 domain import 了 IO 框架，业务就得起容器连库才能跑，箭头反了整套架构就塌。

### 3. 整洁架构同心圆从圆心到外的正确顺序是（10分）

- A. Frameworks → InterfaceAdapters → UseCases → Entities
- B. Entities（企业规则）→ UseCases（用例规则）→ InterfaceAdapters → Frameworks&Drivers
- C. UseCases → Entities → Frameworks → InterfaceAdapters
- D. InterfaceAdapters → Entities → UseCases → Frameworks

> 答案：B
> 解析：越靠圆心越稳定，企业级不变式在最内，框架驱动在最外，外部变化不该惊动内部。

### 4. "端口被实现方污染"的典型表现是（10分）

- A. 端口接口方法太多
- B. `OrderRepository` 接口签名里出现 `OrderPO`（JPA 实体）或 `Pageable`（Spring 类型）
- C. 端口没有被任何适配器实现
- D. 端口方法名用了动词

> 答案：B
> 解析：倒置只倒了一半——IO 概念顺着接口签名漏回核心；正解是端口世界只用领域类型，PO↔Domain 转换关在适配器内。

### 5. 关于"聚合自救"（领域层反向指挥应用层），正确做法是（10分）

- A. 在 StockItem 聚合里注入 OrderRepository 自己 save 自己
- B. 保存是用例（application）的职责，把 `repo.save(item)` 写进 UseCase 而非聚合
- C. 让 Controller 直接调 Repository
- D. 聚合不返回任何东西

> 答案：B
> 解析：聚合不该知道持久化存在；充血不等于自救，注入仓储自我保存会把领域层焊死在 IO 上。

### 6. 六边形架构中"驱动侧端口"与"被动侧端口"，下列说法正确的有（多选）（10分）

- A. 驱动端口（如 OrderUseCase）由输入适配器（Web/MQ）实现，负责"外部驱动核心"
- B. 被动端口（如 OrderRepository）由输出适配器实现，负责"核心向外索取"
- C. 两侧端口接口都定义在应用核心包里
- D. 驱动端口和被动端口是同一个东西的不同叫法

> 答案：A、B、C
> 解析：D 错——两侧方向相反：左侧驱动（外部→核心），右侧被驱动（核心→外部）；但接口都归核心所有，这正是 DIP。

### 7. 用 ArchUnit 做分层 CI 门禁，下列说法正确的有（多选）（10分）

- A. `noClasses().that().resideInAPackage("..domain..").should().dependOnClassesThat().resideInAnyPackage("..springframework..")` 可禁止领域层依赖框架
- B. `layeredArchitecture()` 可声明层间依赖方向并禁止跨层
- C. 只要建好包结构，不配规则也能自动守住分层
- D. 豁免规则应带注释和到期日，否则门禁会被逐步掏空

> 答案：A、B、D
> 解析：C 错——"只建包不配规则"三个月后跨层调用靠记忆执法，记忆比注释先失效；分层必须被 CI 强制执行才作数。

### 8. 判断："贫血 DTO 贯穿三层——接口收到的 Request 直接被 @Transactional 持久化，是推荐做法。"（5分）

- A. 正确
- B. 错误

> 答案：B
> 解析：外部契约即内部模型，上游改字段等于改数据库；应在边界处把 Request 翻译为领域对象，隔离内外。

### 9. 简答题：说明"依赖箭头方向"为何是评价三层/六边形/整洁三种流派的同一根标尺，并各指出它们的病灶。（15分）

> 参考答案：
> - 统一判据：依赖只能指向内层（业务），箭头反了架构就塌，三种流派都在修上一代的漏
> - 经典三层病灶：上层 import 下层具体实现，Service 与 MyBatis/Redis 焊死，测试得起容器
> - 六边形改进：核心声明端口（驱动/被动），Web/DB/MQ 皆插件，接口在消费者包里（DIP）
> - 整洁架构再加同心圆：企业规则>用例规则>接口适配器>框架驱动，越内越稳定
> - 结论：选哪种不重要，能回答"圆心是什么、箭头靠什么强制、端口有没有混入对方类型"才重要

### 10. 简答题：分层架构落地收益如何量化？给出三本账并各举一个可测量指标。（10分）

> 参考答案：
> - 测试账：领域+用例单测无容器秒级跑完——指标=可测试比例与 CI 时长（改造前后各截覆盖率×耗时图）
> - 替换账：换 ORM/缓存/MQ 只动 adapter 包——真换过一次才算数，没换过就是保险费要诚实说
> - 部署账：适配器可远程化，是微服务演进路径——单体端口本地调用，拆分时改 Feign 核心零改动
> - 加分点：指出收益要"敢量化"，用数据而非 PPT 说服团队
