# 实验设计与 K8s 故障类型 · 面试题

## 题 1：混沌工程和"压测/故障演练"有什么关系与区别？

- 混沌工程是方法论：以科学实验（稳态假设 + 变量 + 对照 + 渐进爆炸半径）主动注入真实故障，提前暴露韧性缺陷；
- 压测（JMeter/Gatling）关注容量与性能拐点，故障演练是混沌的具体执行形式之一；
- 关键区别：混沌要求"先有假设、后有结论"，不是"随便杀个 Pod 看看挂不挂"，产出是可执行的改进项。

## 题 2：一次合格的混沌实验要满足哪些原则？

- 围绕可量化稳态指标建立假设；把现实世界事件（节点宕机/依赖超时/AZ 故障）作为变量；对照组并行；
- 在生产持续运行、爆炸半径从小到大地渐进；每次实验闭环到"暴露缺陷 + 修复"；
- 加分：强调"没稳态假设的实验没有价值"——它无法告诉你系统到底变好还是变差。

## 题 3：Chaos Mesh 里各故障类型分别验证什么？

- PodChaos：无状态副本自愈、重调度、探针是否挡住未就绪实例；
- NetworkChaos：延迟/丢包/分区/DNS——超时、重试、熔断、跨 AZ 容灾；
- IOChaos：磁盘读写延迟/错误——存储依赖健壮性、日志写失败不拖垮主流程；
- StressChaos：CPU/内存压力——limit、HPA、OOM、限流降级；TimeChaos：时钟敏感的定时/过期/对账；HTTPChaos：异常响应码容错。
- 加分：能指出"有状态服务不能照搬 PodChaos 结论"。

## 题 4：为什么"注入网络延迟前必须先有合理超时"？

- 若调用没设超时，注入延迟不会"验证熔断"，只会把线程池/连接耗尽——暴露的是"根本没配容错"这一已知缺陷，且容易演成真实事故；
- 混沌的前提是系统已有一条"韧性基线"，实验是去检验基线是否真的生效（如超时是否触发、半开是否恢复）；
- 加分：可对比"200ms 超时"与"5s 超时"同样 300ms 延迟注入下的 RT/错误率差异说明。

## 题 5：生产做混沌，你怎么保证不真出事？

- 渐进爆炸半径：staging 预演 → prod 单副本（mode: one / fixed-percent）→ 逐步扩大；
- 量化 abort 条件先行：注入前写好"成功率跌破 X 立即停"，靠 duration 到期自愈 + dashboard 一键 pause 兜底，不靠人肉反应；
- 避开大促封网/结算窗口、限定命名空间与 ServiceAccount、走变更审批；数据类故障先验证备份可恢复；
- 加分：把"完善的可观测"列为前置——没有指标看板就无法判断稳态被破坏，等于蒙眼实验。

## 题 6：演练做完系统没挂，是不是就没价值？

- "没挂"只是证明当前这条故障假设下韧性好，但前提是真有稳态度量证明"扛住了"；
- 更大价值往往在暴露的边界：半开恢复慢、某降级未生效、副本同 AZ 反亲和缺失——这些才是产出；
- 若确实什么都没暴露，应扩大爆炸半径/换更狠的故障类型继续，或复盘"稳态假设是否定得太松"，而不是宣布"我们很稳"就收工。
