# 实验设计与 K8s 故障类型 · 作业

## 作业 1：Chaos Mesh 环境 + 第一个 PodChaos（动手题）

**目标**：跑通"声明故障 → 注入 → 观测自愈 → 撤销"最小闭环。

**任务**：
1. Kind/k3s 集群装 Chaos Mesh（helm），起一个 `nginx` 多副本（3 副本）部署 + Dashboard；
2. 写一个 `PodChaos action: pod-kill mode: one` 打到一个 `app=nginx` 的 Deployment，`duration: 30s`；
3. 注入期间用 `kubectl get pods -w` 与一个持续打流量的 `wrk`/`hey` 观察：是否出现 5xx、就绪探针如何挡住未 ready 副本；
4. 把 `mode: one` 改 `all` 再跑一次，对比现象，说明"为什么生产从 one 起步"。

**验收标准**：`one` 模式下用户请求无 5xx（证明多副本+探针生效）；`all` 模式出现短暂不可用；能复述"无状态才可随便杀，有状态服务不适用此结论"。

**参考解法要点**：`all` 会同时杀全部副本——这正说明反亲和/多副本不足以救"全量注入"，爆炸半径必须渐进。

## 作业 2：网络延迟验证熔断（工程题）

**目标**：用 NetworkChaos 检验你对下游的超时/熔断是否真的生效。

**任务**：
1. 部署一对服务：`caller` 调用 `downstream`，`downstream` 正常 50ms 返回；caller 侧配 200ms 超时 + 熔断（Resilience4j/Sentinel）；
2. 用 NetworkChaos 给 downstream 注入 `latency 300ms`，验证：caller 是否按超时快速失败、熔断是否在半开后恢复；
3. **反例复现**：临时把 caller 超时改成 5s（远大于延迟+超时链），重跑注入，观察线程池被拖垮（RT 飙升、错误雪崩）——体会"没配好容错时混沌只会制造事故";
4. 记录两组实验的稳态指标对比。

**验收标准**：能画出"合理超时"与"无限超时"两种配置下，同样 300ms 延迟注入的 RT/错误率差异；给出结论"混沌前必须先有韧性基线"。

## 作业 3：Game Day 演练计划（文档题）

为你负责的一条链路写一份可提交审批的混沌演练方案。**验收标准**：必须含——稳态 SLI 定义、注入前置检查清单（超时/副本/备份就绪）、所选故障类型与验证假设、爆炸半径分阶段计划、量化 abort 中止阈值与回滚手段、演练时间窗（避开业务敏感期）、以及"预期暴露的缺陷 + 复盘 action 模板"；缺"中止条件"直接判不通过。
