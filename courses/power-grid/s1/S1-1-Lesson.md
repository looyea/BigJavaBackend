# 用电采集与时序数据处理

> 本节难度：★★★★☆
> 重要程度：★★★☆☆
> 学习产出：能设计电力行业的**海量采集与时序数据处理**系统：理解智能电表/采集终端**高频定时上报**的海量写入特征(点位多、周期短、只增不改、按时间范围查)，用**接入层 + 消息队列缓冲削峰**(Kafka 按表箱/区域分区)扛住上报洪峰与网络抖动；掌握**时序数据模型**(以" measurement + 时间戳 + 标签 + 值"组织，天然适合**降采样**与**补采/乱序/去重**处理)；做**存储选型**——专用时序库(高压缩、按时间分区、TTL 自动过期、写多读少)与传统关系库按时间分区表的取舍；落地**批量入库**(攒批写、避免逐条 insert)、**冷热分离**(近期热存在线、历史归档)与**多级降采样**(原始秒/分钟 → 小时 → 日聚合)的降本增效链路。识破"逐条 insert 打爆 DB""乱序补采直接覆盖新值""时序表无限增长不清理""用错分区键导致范围扫描全表"等坑。

## 一、海量上报：接入削峰再落库

```text
图目的：先扛住"几十万表同一分钟齐上报"的尖峰
电表/终端 → 采集网关(汇聚/边缘缓存/断点续传) → Kafka(按区域/表箱分区) → 消费批量入库
关键：削峰填谷，网络抖动时边缘暂存补传；下游按分区并行消费，避免直连 DB 被瞬时写垮
```

```java
// 目的：把逐条高频写改造成攒批写，保护数据库
void onBatch(List<MeterReading> msgs) {           // 说明：一个消费批次(如 500 条或 2s 窗口)
    Map<String,MeterReading> dedup = new LinkedHashMap<>();
    for (MeterReading r : msgs)                    // 结果：同点位同一时间戳只保留最新到达的有效值
        dedup.merge(r.pointId()+"#"+r.ts(), r, (a,b) -> a.arriveTs() >= b.arriveTs() ? a : b); // 乱序/补采去重键=点位+时间戳
    timeSeriesDao.batchUpsert(new ArrayList<>(dedup.values())); // 反例：循环单条 insert ❌ 每条一次往返，尖峰直接打爆 DB
}
// 反例：补采(迟到旧数据)直接覆盖已入库的新值 ❌ 时序错乱、聚合失真
// 异常：批量写失败要整批重试且幂等，否则半批落库造成重复点位 ❌
```

## 二、时序数据模型与乱序/补采

```text
图目的：电力采集是"时间"为主轴的数据，处理要点与普通业务表不同
组织：measurement(如正向有功总) + tags(区域/表号/相别) + time + value，天然按时间分区
乱序：补采/断点续传使数据晚到 → 按(点位,时间戳)幂等 upsert，迟到不覆盖更晚到达的有效值
去重：同一采集时刻重复上报，以时间戳为幂等键，只留一份
```

## 三、存储选型与冷热、降采样

```text
图目的：写多读少、量级巨大，存储必须为时间轴优化
专用时序库：高压缩、按时间分区、TTL 自动过期、天然支持降采样连续查询
关系库分区表：按时间 RANGE 分区 + (点位,时间) 联合索引，复用事务生态但压缩/过期要自建
冷热分离：近 N 天热存在线可查，历史降采样后归档到便宜存储
降采样：原始秒/分 → 分钟 → 小时 → 日聚合(求和/均值/峰谷)，越老粒度越粗、成本越低
```

## 四、坑与底线

- **分区键选时间**：范围查询(查某区域某天曲线)才能命中分区裁剪，选错键会全表扫。
- **写入攒批 + 幂等**：逐条 insert 与"补采覆盖新值"是两大吞吐/正确性杀手。
