# 服务治理：负载均衡、集群容错与流量管控

> 本节难度：★★★★☆
> 重要程度：★★★★☆
> 学习产出：能从"一次远程调用会落到哪台机器、失败了怎么办、流量怎么切"三个问题出发，搭出一套可治理的 RPC 消费链路。核心是三层能力：**负载均衡**（random/roundrobin/leastactive/一致性哈希，决定同批提供者里选谁）、**集群容错**（failover 重试其他节点、failfast 只调一次、failsafe/fallback/forbidden，决定失败后是否放大压力）、**流量管控**（version/group/标签路由做灰度、机房就近做单元化、优雅停机摘流、超时预算与重试次数的乘积控制）。要点：负载策略要看"权重 + 活跃数"而非纯随机；写接口默认关重试防重复；超时是"链路总预算"而非单点设置，`retries × timeout` 会成倍放大下游 QPS。识破"非幂等写配了 failover 导致重复下单""灰度不打标签放全量波及稳定用户""优雅停机没先摘注册就下线导致瞬时 5xx""上游设 3s 超时下游链一叠加雪崩"等坑。

## 一、负载均衡：选谁比怎么选更重要

```java
// 目的：给关键写接口配"最小活跃 + 不重试"的消费端, 防止超时重试放大下游压力
ReferenceConfig<OrderService> ref = new ReferenceConfig<>();
ref.setInterface(OrderService.class);
ref.setCluster("failfast");          // 结果：非幂等写只调一次, 失败即抛, 避免重试造成重复下单
ref.setLoadbalance("leastactive");   // 说明：活跃数少的节点优先, 天然把慢机器流量降下来, 比 random 抗不均
ref.setTimeout(3000);                // 说明：单次调用超时预算, 需给整条链路总预算留出余量
ref.setRetries(0);                   // 结果：显式关重试; 反例：默认 retries=2 叠加 failover 把 1 请求变 3 ❌
```

## 二、集群容错：失败后的行为决定会不会雪崩

```text
图目的：常见 cluster 策略在"失败时做什么"上的分野
failover   失败自动重试其他节点(可设 retries) —— 读接口/幂等写适用, 但会放大下游压力
failfast   只调一次失败立即抛错 —— 非幂等写(下单/扣款)首选, 杜绝重试重复
failsafe   失败吞掉不抛 —— 记录型弱依赖, 不能影响主流程
forking    并行调多个取最快 —— 低延迟敏感且下游扛得住副本流量
forbidden  超过并发上限直接拒 —— 自我保护, 防止把下游压垮
```

## 三、流量管控：路由、灰度与优雅停机

```yaml
# 目的：用 version/group/标签把流量按用途切分, 支撑灰度发布与单元就近
dubbo:
  provider:
    version: "2.0.0"     # 说明：新链路打标 2.0.0, 消费端按 version 精确路由到灰度实例
    group: "gray"        # 结果：灰度实例只接 gray 组流量, 与稳定组物理隔离, 出问题秒级回切
  # 反例：不打标签直接把新版本放进全量 ❌ 一旦有缺陷波及所有用户且无法快速回切
```

## 四、坑与底线

- **写接口默认关重试**：非幂等的下单/扣款必须 `failfast` 或 `retries=0`；要重试就走幂等设计，别指望 RPC 层重试兜底。
- **超时是链路总预算**：从入口往下逐层递减（网关 5s→服务 3s→下游 1.5s），并注意 `timeout × (retries+1)` 才是真实占用，防止重试叠加放大 QPS 造成雪崩。
- **优雅停机先摘流再下线**：先从注册中心反注册并等待客户端刷新，再关进程，否则正在路由的调用会打到已停实例出现瞬时 5xx。
