# 行为型模式 · 实际面试题

## 题 1：订单状态控制不好就资损，你们怎么管状态迁移？

**考察点**：有没有把"状态"当一等公民建模；高频电商/金融题。

**参考答案**：三层收敛：① 唯一入口——全系统只有 `transition(from,to)` 能改 status，迁移表（Map<状态,Set<目标>>）声明合法边，非法即异常+告警；② 并发正确性——落库必带 `WHERE status=from` 的 CAS，影响行数≠1 判并发失败走查询返回既有结果，杜绝双退款；③ 外显幂等——客户端重试带退款单号，返回首次结果。形态上不必每状态一个类，迁移表+守卫就是状态模式的工程甜点；状态爆炸（几十态多事件）再考虑 Spring Statemachine 并警惕它的持久化成本。

**追问**：
- 运营要"紧急加一条迁移边"怎么办？——迁移表进配置需评审：边的增删本质是业务规则变更，热更要配回归用例；至少做到"改表不改代码但改表走发布"。
- 跨服务状态（订单 vs 支付单）不一致怎么管？——各自状态机 + 对账/补偿事件，别幻想全局单状态机。

**加分点**：主动讲一次"散点 update 导致的双写覆盖"真实故障与收敛后的告警数据。

## 题 2：用 Spring 事件做"下单后发券"，事务回滚了券发出去了怎么办？

**考察点**：观察者在事务语境下的时机认知——答错即事故制造者。

**参考答案**：裸 `@EventListener` 同步同线程、发生在事务提交前，监听器看到的"订单存在"是未提交的未来——主流程回滚、券已发出。正解 `@TransactionalEventListener(phase=AFTER_COMMIT)` 把触发时机钉在提交后；耗时或不可靠的消费再加 `@Async`（独立线程池+失败重试落表）。同时保持清醒：这是进程内广播，重启丢事件、跨服务不可达——发券若属跨服务契约，升级为事务消息（outbox），事件只做进程内解耦。

**追问**：
- `@Async` 没生效通常为什么？——缺 `@EnableAsync`、监听方法是 private/自调用、或异常被异步吞掉要配 `AsyncUncaughtExceptionHandler`；
- AFTER_COMMIT 里监听器抛异常会影响已提交事务吗？——不会回滚（已提交），但异常默认被吞——要有失败补偿路径。

**加分点**：说出"事件发布点最好放在 Service 方法末尾且紧邻提交，中间不要再夹可能失败的写"这种时序纪律。

## 题 3：Filter 和 Interceptor 有什么区别？责任链的"链"到底价值在哪？

**考察点**：八股之上加结构理解。

**参考答案**：层次与能力不同：Filter 归 Servlet 容器，拿到的是原始 Request/Response，做认证、编码、压缩这类"业务无感知"的横切；Interceptor 归 SpringMVC，在 HandlerMapping 之后，能拿到处理器方法与模型，做鉴权细粒度、日志埋点、接口幂等 token 校验。链的价值在三点：节点可插拔（配置顺序即策略）、每节点自主决定"后续是否执行"（递归结构使截断是局部决定）、洋葱时序（前置正序后置逆序让外层能观测内层全部耗时）。顺序即语义：鉴权必须在限流前还是后，取决于你想不想给未授权请求消耗配额——这问题本身就该在评审清单里。

**追问**：
- 拦截器 preHandle 返回 false，之前节点的 afterCompletion 会执行吗？——会，Spring 记录了"已完成节点栈"逆序补偿——自己写链要复刻这语义，否则资源清理不对称。

**加分点**：能对比 Netty pipeline 的双向链表职责链（出站事件逆序），说明同一模式在不同方向的变体。

## 题 4：`for (String s : list) { if (...) list.remove(s); }` 为什么抛异常？生产上你怎么规范？

**考察点**：小考——fail-fast 的理解与团队规范输出能力。

**参考答案**：增强 for 展开为迭代器，`list.remove` 使 modCount++ 而迭代器预期不变，下次 `next()` 校验抛 CME——单线程也抛，它防的是"迭代期间结构修改导致游标语义崩坏"（跳元素/漏元素）。规范：删元素用 `removeIf`（首选）或 `Iterator.remove`；并发读多写少用 CopyOnWriteArrayList，别 catch CME 重试——CME 是尽力检测，没抛不代表安全。补充一个更隐蔽的近亲：`Arrays.asList` 视图上的 `add` 抛 UnsupportedOperationException，和"不可变"是两个问题。

**追问**：
- 为什么设计成抛异常而不是静默容忍？——静默的跳过/重复比快速失败更难查；fail-fast 把"并发/结构修改 bug"在开发期炸出来。

**加分点**：能说出 ConcurrentHashMap 的迭代器是 fail-safe（弱一致性，不抛 CME 但可能读到旧结构），对比两种设计取舍。

## 题 5：行为型模式里你觉得哪个最被高估、哪个最被低估？

**考察点**：开放观点题，考的是有没有独立判断与论据。

**参考答案**（示范，立场自洽即可）：最被高估——解释器与访问者的"模式照抄"：业务里 DSL 极少该自研，而访问者在 Java 里对抗开闭（加元素改所有访问者），sealed+模式匹配已是更优解，面试背双分派的人八成没写过 AST。最被低估——命令模式的"请求日志化"视角：把用户操作对象化成可回放、可审计、可撤销的日志记录（后台审批流、工单系统、编辑器历史都靠它），很多人天天用 Runnable/队列却从没意识到自己站在命令模式上。中间地带：状态模式被当作"纸上 OO"忽略，而它对应的恰是资损重灾区——status 字段裸奔。

**追问**：怎么证明不是背概念？——要求现场给一个"自己项目里该模式缺席导致的问题"（如本题的状态散写或事件时机事故）。

**加分点**：补一句"模式名不重要，重要的是认出'变化压力长什么样'并选择对应的收敛手段"，呼应 S2-2 反模式篇。
