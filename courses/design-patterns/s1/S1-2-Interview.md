# 创建型与结构型模式 · 实际面试题

## 题 1：Java 里实现单例有几种写法？Spring 的 singleton 和 JVM 单例是一回事吗？

**考察点**：Basics 之外的深度——线程安全原理与作用域辨析。

**参考答案**：写法四层递进：饿汉（类加载即建，简单但无懒加载）、DCL+volatile（volatile 挡初始化重排，缺了会读到半成品）、持有者类（静态内部类，懒加载+JVM 保证安全，无枚举的序列化顾虑）、枚举（防反射防反序列化，Effective Java 推荐）。Spring 的 singleton 是**容器作用域单例**：一个容器内一个实例，不是 JVM 级——多容器/多 ClassLoader 各有其一；而且 Spring bean 默认不开 final 构造防多实例。所以"手写 getInstance + @Component"双轨是大忌，会出现两份实例各写各的状态。

**追问**：
- 枚举单例为什么防反射？——`Constructor.newInstance` 对枚举类显式抛 `IllegalArgumentException`（JDK 源码里有这道防线）；
- 什么时候根本不该用单例？——对象无全局唯一性需求（连接池每库一个即可分片）、或它的"唯一"只是懒得当断线重连逻辑的窝。

**加分点**：能说出"单例可测试性差"的解法——依赖它的类通过接口注入，测试给假实现；直接 `Xxx.getInstance()` 硬-call 才是问题。

## 题 2：一分钟内讲清适配器、装饰器、代理、享元的区别。

**考察点**：概念压缩能力+能否落到真实出处。

**参考答案**：都持有"别的对象"，区别在意图——适配器**变接口**：目标接口客户端用不了，翻译一层（`InputStreamReader` 把字节流译成字符流）；装饰器**加行为**：接口不变、调用方主动叠（`BufferedInputStream` 加缓冲，可多层）；代理**管访问**：接口不变、调用方通常不知情，为懒加载/远程/事务而拦（`@Transactional` 的 CGLIB 子类、Feign）；享元**省对象**：细粒度大量相似实例共享化（`Integer.valueOf` 缓存）。判据口诀：接口变没变、调用方知不知情、为能力还是为管控。

**追问**：
- 装饰器和代理结构几乎一样，怎么区分代码意图？——看谁构造它：显式 `new XxxDecorator(target)` 是装饰；容器/框架塞给你一个 `$$Proxy` 是代理；命名与文档兜底。

**加分点**：能举一个"自己写错意图"的案例（如给装饰器加了缓存逻辑变成代理，导致测试无法绕开缓存）。

## 题 3：都 2026 年了还学 GoF 吗？lambda 和 record 是不是消灭了一批模式？

**考察点**：技术判断力——背模式列表的人会防御，有思考的人会认同并划线。

**参考答案**：被吸收的是"载体"不是"问题"：策略/命令模式作为类族基本被 `Function/Runnable` + 方法引用替代（注册表 value 从策略类变 lambda），Builder 被 record + of/with 削掉大半，抽象工厂在 DI 容器下退化为配置声明。但模式描述的张力还在：OCP 要挂点（注册表本身没消失，只是更薄）、资源管控要代理（AOP 就是模式工业化）、跨系统兼容要适配器（防腐层是架构级适配器）。所以我的学法是：**学每个模式解决的变化压力，别背 UML**——GoF 23 个在 Java 8+ 语境下值得直接写出来的不到 8 个，但它们的"坏味道对照表"价值反而更大：看到 200 行构造器知道它在喊 Builder，看到 if 分发知道它在喊策略。

**追问**：哪些模式 lambda 替代不了？——需要状态与身份的多层结构（装饰器链、组合模式的树、迭代器的游标状态）；单函数接口表达不了"对象有自己的生命周期与内部结构"。

**加分点**：提到 Kotlin DSL/Sealed 接口对"解释器/访问者"的替代（visitor 在代数数据类型+模式匹配下近乎自动）。

## 题 4：一个对象有 20 个配置项，你用什么方式构建？

**考察点**：从"背 Builder"到"按约束选型"。

**参考答案**：先分类 20 项：必填有几项（通常 ≤3）→ 全部进 `of(...)` 构造器；默认值安全的（超时、池大小）→ 可选 with 链式定制，record 化保不可变；互斥/联合校验项（如 key 与 cert 必须同现）→ 用类型系统前置消灭（嵌套 record 成 `TlsConfig`，非法组合编译不过）；运行时按配置文本装配 → 干脆交给 Spring `@ConfigurationProperties`，别手搓 Builder。经典手写 Builder 只在两个信号出现时才值：参数跨方法逐步累积、或构建前要一次性做昂贵校验/规范化。反例也要能讲：用链式 setter 的"半成品对象"漂过三层方法，中间任何一层读它都是不合法状态。

**追问**：
- 为什么 `setXxx` 链式（返回 this 的可变 Fluent）常被认为不如不可变 with？——builder 实例可被共享/中途读，并发下互踩；with 每步新对象，"漂在半路"的永远合法。

**加分点**：给出"配置对象字段 >10 个时先问该类是否该拆"的 SRP 反思（接 S1-1）。

## 题 5：`Integer a=127, b=127; a==b` 和 `128` 的结果分别是什么？这算不算一个坑？

**考察点**：享元的边界意识；也是包装类比较的综合题。

**参考答案**：127 两边都命中 `Integer.valueOf` 的 -128~127 缓存，`==` 为 true；128 各 new 一个对象，`==` 为 false（编译期常量折叠在 final 局部变量场景可能让直觉再翻车，运行时装箱才是本题语义）。这是真坑但坑的不是性能而是**语义**：`==` 对包装类比的是引用，行为却随值域漂移——今天的"测试通过"只是踩在缓存里。规范：包装类型一律 `equals`/`Objects.equals`，金额等比较场景从根上用 `long`/`BigDecimal`；`Integer` 缓存的实现细节绝不可依赖（JDK 允许调上界，`-XX:AutoBoxCacheMax`）。

**追问**：
- 享元模式在这件事上的教训？——共享让"身份"与"值"分离：享元适用条件是对象不可变且客户端不做身份判断，Integer 缓存违背了后半个使用约定（用户拿它当普通对象用）。

**加分点**：顺带说出 `String.intern` 在 JDK7 后从永久代挪堆、以及用 `==` 比较 intern 串做去重的历史玩法为何被淘汰。
