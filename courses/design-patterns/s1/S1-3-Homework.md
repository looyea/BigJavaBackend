# 行为型模式 · 作业题

> 本节作业 3 题：一台状态机手术、一次事件时机对照实验、一条迷你责任链。

## 作业 1：把真实订单状态迁移收敛为迁移表（动手）

在仓库（或自造 demo）里找一段"多处 `update status`"的订单/工单代码：

1. 统计全部写入 status 的位置与各自的前置 if 条件，列成矩阵，找出**互相矛盾**的判定（A 处允许 PAID→CLOSED、B 处不允许）；
2. 实现迁移表+守卫+CAS 的唯一入口（参照本课 `transition`），把散点写入全部改为调用它；
3. 写并发测试：同一订单两个退款请求同时进，断言恰好一个成功、另一个得到"已在处理"语义（不是 500）；
4. 回归：故意在测试里发起一条非法迁移（REFUNDED→PAID），断言异常+告警埋点被触发。

**验收标准**：改造前后 status 写入点数量对比（应归一为 1）；并发测试通过截图；矛盾判定矩阵作为"考古证据"保留在 commit message 里。

## 作业 2：Spring 事件三种监听时机的行为对照（动手）

同一个 `OrderCreatedEvent`，注册三个监听器：裸 `@EventListener`、`@TransactionalEventListener(AFTER_COMMIT)`、`AFTER_COMMIT + @Async`。主流程发布事件后手动 `setRollbackOnly()` 制造回滚。

1. 分别记录三种监听器在"回滚事务"场景下是否执行、执行线程名、与主流程的时序（日志时间戳对齐）；
2. 再测"监听器抛异常"对主流程的影响差异；
3. 输出一张 时机×线程×异常传导 对照表，并为"发券"与"写审计日志"两个真实需求各选出正确组合并说明理由。

**验收标准**：对照表与预测不一致处需用调试栈解释原因（尤其 @Async 失效的常见配置坑——缺 `@EnableAsync` 或自调用）。

## 作业 3：手写一条带异常语义的迷你责任链（动手）

实现 `Handler` 接口（`handle(Context, Chain)`）与三个节点：Trace（写入 traceId）、Auth（无 token 截断 401）、RateLimit（超阈值截断 429）。

1. 验证洋葱顺序：三节点的前后日志交错打印符合"正序进逆序出"；
2. 制造两种死法并修复：Auth 放行分支漏 `chain.handle`（现象：请求静默无响应）；RateLimit catch 异常后既不抛也不置状态码（现象：半处理响应）；
3. 复刻 Spring 拦截器语义：某节点抛异常时，已完成节点的 `finally` 补偿仍按逆序执行——用日志证明；
4. 反思题（写在 README）：这条链与"用 List<Filter> 顺序 for 循环"的实现差异在哪，`Chain` 对象存在的意义是什么。

**验收标准**：两种死法的复现日志 + 修复 diff；反思题答案能点出"递归结构让每个节点决定'后续是否执行'"这一核心。
