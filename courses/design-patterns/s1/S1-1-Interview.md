# 设计原则 SOLID 与组合优于继承 · 实际面试题

## 题 1：说说 SOLID，别只给定义。

**考察点**：能否每条落到一个工程动作上；背定义者在第二条追问即现形。

**参考答案**：串成一条线讲——五原则共同目标是"让变更便宜"。S：按变更原因拆类，判据是"哪几种角色提需求会动它"；O：给持续新增的维度建抽象挂点（策略+注册表），新增不改存量；L：子类型必须满足父类行为契约，否则多态调用方随机炸；I：接口按调用方最小面设计，别让实现者背无关方法；D：接口所有权归消费者，JDBC/SPI 是范本，Spring 只是把装配工程化。收尾表明立场：原则是权衡工具不是教条，变更频率决定投入。

**追问**：
- 五条里实战中最常破的是哪条？——诚答 SRP/O 之间摇摆：拆太碎损可读性，最好的切入点是"从变更历史里找热区"。

**加分点**：主动提 DIP 口诀"接口在谁的包里"；引用自己重构过的真实案例。

## 题 2：你们代码里的 if-else 很多，你会全改成策略模式吗？

**考察点**：是否把模式当银弹——考工程判断力。

**参考答案**：不会，先做两个统计：该分支维度一年新增几次、每次新增改动要不要回归全部分支。低频且分支短（≤3、逻辑一行）的 if 比"接口+实现+注册表+找不到类的调试"更便宜；高频新增（支付渠道、计费规则、消息类型分发）才值得注册表化，并且要补三件套防护：重复注册启动失败、未知 key 报错带已注册清单、每策略独立单测。重构时机选在"下一次新增需求进来时顺手做"，专项大重构风险高。

**追问**：
- 策略类多了导致类爆炸怎么控？——按域收纳包、简单策略用枚举/函数式字段表达（`Map<Type, Function>`）而不必每支一个类。

**加分点**：引用"Rule of Three"（同一变化第三次出现才抽象）并承认自己抽象过早翻过车。

## 题 3：为什么"组合优于继承"？Java 只允许单继承是不是唯一原因？

**考察点**：是否理解耦合本质而非语法限制。

**参考答案**：单继承只是表象，三个更深的坑：① 脆弱基类——子类隐式依赖父类未承诺的实现细节，父类升级（含 JDK 升级）行为静默改变，如重写 `add()` 统计但 `addAll()` 内部路径变了；② this 逃逸——父类方法内部调用被重写方法，重写方无法审计触发源；③ 继承是白盒复用，组合是黑盒复用——后者可用装饰器/策略表达"多能力叠加"，继承表达不了（这正是"mix-in 靠接口堆"痛苦的根源）。何时该继承：真正的子类型多态且契约完全一致（List 的实现们），或模板方法明确文档化了钩子语义。

**追问**：
- Lombok/IDE 自动生成委托与手写装饰器哪个用？——生成器解决样板，不解决"委托关系显式化"的价值；接口演进时生成方案要重新生成防漏委托。

**加分点**：提到记录类型 record + 组合在 Java 17+ 进一步降低了复用型继承的存在感。

## 题 4：什么样的接口设计算违反 ISP？你拆接口的时机怎么把握？

**考察点**：对"接口是契约不是能力清单"的理解。

**参考答案**：信号有三个：实现类里出现 `throw new UnsupportedOperationException()`；mock 测试要 stub 八个方法但用例只用两个；给接口加方法时半数实现者被迫发版。时机把握：接口初建按"当前调用方实际用到的方法"设计（YAGNI），第二个调用方出现且需求面不同时才拆——拆是组合式拆分（`ReadRepo`/`WriteRepo`，大接口 extends 小接口保兼容），并先用 default 方法止血再排期重构。公共 API（对外发布的 SDK）拆早比拆晚好，因为发布后加方法容易删方法难。

**追问**：
- Spring 的 `Repository` 标记接口什么都没有，算不算反例？——恰好正例：消费者只需要"这是个仓储"的类型标记，零方法契约正是 ISP 的极致。

**加分点**：说出接口与实现分离部署时的"方法增加二进制兼容、删除不兼容"约束对拆分的反向影响。

## 题 5：原则之间打架时你怎么裁决？举个例子。

**考察点**：开放题，考的是有没有真实权衡过程。

**参考答案**（示范案例，须换成自己的）：SRP 与可读性/性能打架：电力采集链路把"校验→换算→落库"拆成三个类后，热点路径上对象分配与调用链变长，压测 TPS 降 8%。裁决依据是"变化频率×出错代价"：校验规则每季度变、换算表每年变、落库几乎不变——于是只把校验拆出独立类，换算与落库留在一处用清晰分段+行内说明代偿，接受该类的"两因"状态并在 README 标注触发重构的条件（换算表需要热更新时）。原则服务演进成本，不服务仪式感；违背原则要留下"债条"而不是假装没看见。

**追问**：怎么防止这种"权衡"变成摆烂借口？——把裁决写进 ADR/代码注释，review 时按"变化频率"举证，而不是"我觉得没事"。

**加分点**：能自然引用"最小知识原则、组合优于继承、先测量再抽象"互相咬合的实例。
