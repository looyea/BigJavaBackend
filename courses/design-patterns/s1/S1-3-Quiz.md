# 行为型模式 · 小测验

> 全卷 100 分：单选 5×10 + 多选 2×10 + 判断 1×5 + 简答 15+10。达到 60 分解锁下一节。

### 1. 状态模式工程版（迁移表+守卫）最核心的价值是（10分）

- A. 让每个状态成为一个类，看起来更 OO
- B. 把"合法迁移+并发 CAS"收敛到唯一入口，非法迁移集中拒绝
- C. 减少数据库表字段
- D. 让状态可以用 int 存储

> 答案：B
> 解析：形态不重要，收敛才重要——散落八处的 `if(status==X) update` 必有一处漏 CAS；迁移表顺带成为可评审的活文档。

### 2. `@EventListener`（不加任何额外注解）监听下单事务内发布的事件，默认行为是（10分）

- A. 事务提交后异步执行
- B. 同步同线程立即执行, 仍处于事务内——监听器抛异常会回滚主流程, 主流程回滚它却可能已产生副作用
- C. 自动在新线程执行
- D. 不会被调用

> 答案：B
> 解析：默认就是普通方法调用；"提交后才触发"要 `@TransactionalEventListener(AFTER_COMMIT)`，副作用型监听器几乎都应加。

### 3. Servlet 过滤器链的洋葱模型执行顺序是（10分）

- A. 前置与后置都按注册正序
- B. 前置正序进入、后置逆序出栈
- C. 随机顺序, 由容器决定
- D. 全部前置执行完才全部后置

> 答案：B
> 解析：`chain.doFilter` 调用点把方法劈成前后两半, 内层先完成——所以外层 filter 的 finally 能看到内层写入的上下文。

### 4. 命令模式的本质价值是（10分）

- A. 让方法调用变快
- B. 把"请求"对象化, 从而可排队、可回放、可撤销、可与执行者解耦
- C. 替代 if-else
- D. 强制所有 Service 实现同一接口

> 答案：B
> 解析：Runnable/JobMessage 都是它；单纯"包一层 Command 类再转发"没有兑现任何一个"可"字, 属仪式代码。

### 5. 增强 for 中调用 `list.remove(e)` 抛 ConcurrentModificationException 的原因是（10分）

- A. 列表容量不足
- B. 迭代器校验 modCount 与预期不符——集合发生迭代外的结构性修改
- C. remove 方法线程不安全被锁拒绝
- D. JVM 内存溢出前兆

> 答案：B
> 解析：fail-fast 是尽力检测的契约不是并发控制；单线程也会抛。改 removeIf/Iterator.remove 即可。

### 6. 关于 Spring 事件机制的适用边界，正确的有（多选）（10分）

- A. 它是进程内广播, 订阅者与发布者同生共死, 不能替代 MQ 做跨服务投递
- B. 监听器默认同步执行, 耗时监听器会直接拉长主流程 RT
- C. `@Async` + `@TransactionalEventListener(AFTER_COMMIT)` 组合可同时解决时机与耗时问题
- D. 事件发布后即使事务回滚, 监听器也保证已完成所有副作用

> 答案：A、B、C
> 解析：D 恰是需要 AFTER_COMMIT 的原因——裸事件监听器看到副作用时事务"还可能回滚"；这正是"回滚后券已发"事故的根因。

### 7. 以下关于各行为型模式在 Java 现代语境下的替代, 正确的有（多选）（10分）

- A. 策略模式的"每策略一类"常被 lambda + 注册表取代
- B. 访问者模式在 sealed interface + 模式匹配下大多可省
- C. 模板方法的"钩子"在函数式参数化下（传入 Function）常更轻
- D. 观察者模式已被彻底淘汰, 任何场景都不应再用

> 答案：A、B、C
> 解析：D 过头——进程内解耦仍大量用事件（模块内审计、指标上报）, 被淘汰的是"跨服务用它"这一误用。

### 8. 判断："责任链中某个节点抛异常后, 后续节点一定不再执行, 这与拦截器语义完全一致。"（5分）

- A. 正确
- B. 错误

> 答案：B
> 解析：异常是否截断链取决于 catch 位置——外层 try-finally 结构下后续节点的 finally 仍可能执行; Spring 拦截器还有"已执行者的 afterCompletion 逆序补偿"语义, 两者不能划等号。

### 9. 简答题：为退款流程设计一个"迁移表+守卫"状态机, 列出关键表项, 并说明并发双请求打进来时它如何保证只成功一次。（15分）

> 参考答案：
> - 状态集: PAID/REFUNDING/REFUNDED/CLOSED, 表项 PAID→{REFUNDING}, REFUNDING→{REFUNDED, PAID}(驳回回滚)
> - 唯一入口 transition(from,to): 查表非法即抛异常+告警
> - 落库用 CAS: UPDATE ... SET status=to WHERE id=? AND status=from, 影响行数≠1 判定并发失败
> - 双请求: 都查到 PAID, 都试 CAS, 只有一个 rows=1, 另一个抛 ConcurrentTransition 走查询返回"已在处理"
> - 幂等外显: 客户端重试同一退款号返回首次结果而非再次执行

### 10. 简答题：模板方法与"函数参数化"都能做骨架复用，各给一个场景说明该选谁。（10分）

> 参考答案：
> - 骨架多钩子少、且子类要共享钩子间状态(缓存的连接/事务上下文) → 模板方法(JdbcTemplate 的 StatementCallback 内部仍靠类层次持资源)
> - 钩子即全部输入、无跨钩子状态 → 函数参数化: 排序传 Comparator, 别为"一个比较逻辑"建抽象类
> - 判据: 数一数"钩子要读写骨架的私有字段吗", 是→继承, 否→组合传参
> - 补充: 模板方法父类演进风险(脆弱基类)在钩子≤2 时通常可接受
