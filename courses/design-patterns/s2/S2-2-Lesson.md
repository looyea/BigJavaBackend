# 过度设计与反模式、重构手法

> 本节难度：★★★★☆
> 本节重要性：★★★☆☆
> 学习产出：能用"删除测试/Rule of Three/变化已发生三次"三个判据识别仪式代码与推测式泛化；背出七个高频反模式并各配一个"我见过"的案例；按风险分层组织重构手法并说出重构三纪律（测试先行、小步可编译、重构与功能变更分 commit）；面对"这里要不要抽一层"的评审争论，给出可执行的决策程序而不是站队。

```flow
例子目的：过度设计的真实账单——一个只有短信实现的"通知框架", 与晚一步再抽象的对照轨迹
过度设计: NotifyFactory -> AbstractNotifier -> SmsNotifier (三层间接) 每加一个真需求要改3文件, 调试栈穿越3层, 单测×3
顺势演化: sendSms() 直写 -> 第二个渠道来了抽接口(一次改动) -> 选择逻辑变了再抽注册表(又一次改动)
账单: 抽象的收益=未来变更成本↓, 成本=今天的间接层+理解负担; 变化从未发生的维度上, 收益恒为0
```

## 一、过度设计的五个信号（评审时直接对照）

1. **单实现接口**且该实现从未按接口注入替换过——抽象没挡住任何变化，只挡住了阅读视线；
2. **推测式泛化**（speculative generality）：参数/配置/钩子服务于"以后可能有"的需求，YAGNI 的正主；
3. **间接深度 ≥3 才见到业务**：Controller→Facade→Manager→Service→Handler，每层都是薄转发（电话交换机式转发）；
4. **模式命名先行**：类名叫 XxxCommandExecutorHandler，行为却兑现不了模式承诺的任何"可"（可回放/可撤销/可插拔）；
5. **框架化业务**：给一个模块的 CRUD 配插件机制、规则引擎、元数据中心——平台化的冲动第一次出现时，先问第二个消费者是谁。

```java
// 目的：三个可执行的"删除测试", 终结评审里"万一以后要扩展呢"的抬杠
// 测试1 删除测试: 删掉这层抽象, 复杂度消失还是转移? 消失=它本就制造复杂度, 该删
// 测试2 第三实现测试: 该接口是否存在≥2个真实实现且第3个在路上? 只有1个=留, 连0个都嫌多
// 测试3 时机测试: 变化已经发生几次? 0次不抽, 1次重写不改设计, 第2次出现再抽象(Rule of Three)
// 反例: 评审里用"支持未来扩展"说服自己加的空钩子类, 两年后随宿主一起删除, 从未被第二个实现使用
```

## 二、高频反模式图鉴（识别 → 对应手法）

| 反模式 | 症状 | 重构方向 |
|---|---|---|
| 上帝类 | 千行 Service，谁都不敢碰 | Extract Class 按变更原因拆（接 S1-1） |
| 霰弹式修改 | 加一个字段改 11 个文件 | Move Method / 收敛数据归属 |
| 羡慕特性 | 方法 A 疯狂访问 B 的 getter | Move Method 把行为搬到数据家（Tell Dont Ask） |
| 基本类型偏执 | `String status, double price, String addr` 裸奔 40 处 | Replace Type Code / Introduction Value Object |
| 数据泥团 | 七八个参数永远成串出现 | Introduce Parameter Object（record） |
| 希腊花瓶死分支 | 注释掉的代码 + 永不进入的开关 | 删；git 记得一切 |
| 熔岩流 | 没人懂没人删的祖传层 | strangler 圈地，新代码绕开旧核心 |
| 贫血域模型 | Entity 只有 getter，逻辑全在 Service 里 | 把不变式与行为搬回领域对象（接 ddd 包） |

**黄金锤**是反模式之母：刚学会 Kafka 就用 Kafka 解决一切——"手里有锤子看什么都是钉子"的工程版。解药是选型必列两个被排除的候选及排除理由，写进 ADR。

## 三、重构手法：按风险分层使用

重构的定义必须刻在骨子里：**不改变外部行为的结构变换**——"顺手修个 bug"混进重构 commit，评审者就再也分不清"这是行为变化还是结构变化"，review 质量断崖。

```java
// 目的：一组小手法的"前后对照", 感受"小步"的尺度——每步都能编译、测试全绿
// 手法1 Extract Method: 60 行方法里"校验段"剪成 validateForm() —— 最常用, 风险≈0
// 手法2 Replace Conditional with Polymorphism: 稳定新增的 if 链 → 策略注册表(接 S1-1, 注意时机测试)
// 手法3 Replace Inheritance with Delegation: 爬继承树找行为 → 组合字段直读(接 S1-2)
// 手法4 Introduce Null Object: 散落各处的 if (x == null) → NullXxx 实例, 调用方零判断
// 反例: 一次 commit 改 40 个文件"大重构", 测试红了两处理解着改绿——没人能评审, 出事无法 bisect 定位
// 说明: IDEA 的 Refactor 菜单不是"便利贴"是"语义保证"——手动剪切粘贴重命名漏改一处引用, 编译器不会替你找
```

**重构三纪律**：① 无测试先补测试——characterization test（特征测试：锁定现状行为，不管现状多荒谬）是老代码的入场券；② 步长以"秒级编译+分钟级测试绿"为单位，绿了就 commit；③ 纯重构 commit 不加行为，message 前缀 `refactor:` 让 `git log --grep` 能剥离噪声。

**何时不重构**（与何时重构同等重要）：将要废弃的模块（strangler 已圈地）、没有测试也没有时间补测试且不在变更热区的角落（标记债条而不是硬闯）、业务即将大改的同一区域（等需求把刀递过来再动）。

## 四、常见线上问题

- "重构周"产出的新 bug 集中在两个混合 commit 里：重构+功能混提交，bisect 失效；
- 抽象层数与 NPE 定位：链式转发 6 层后异常栈里全是 `lambda$xxx$0`，堆栈噪音是过度间接的复利利息；
- 死配置开关：灰度结束后开关代码不删，半年后没人知道哪个分支还活着——开关是有到期日的债务；
- "顺手优化"引入的静默行为变化：把 `equals` 从常量侧移到变量侧修了 NPE，却改了 null 语义——重构的定义已经违背。

## 五、小结与过关要点

S1-1 教你把变化装进结构，本节教你**别为没发生的变化预付结构成本**——两者是同一枚硬币。设计能力的最高证明不是画得出框架，而是敢在评审会上说"这里先写死，第二个用例出现时我来抽"。过关自测：找出你仓库里抽象层级最深的一个包，对它跑一遍三个删除测试；再翻 git log，数有几个 commit 同时包含 refactor 和 feat。
