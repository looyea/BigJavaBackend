# 过度设计与反模式、重构手法 · 小测验

> 全卷 100 分：单选 5×10 + 多选 2×10 + 判断 1×5 + 简答 15+10。达到 60 分解锁下一节。

### 1. Rule of Three 主张的抽象时机是（10分）

- A. 第一次出现该变化时就抽象，一步到位
- B. 同一变化第三次出现（或第二次确凿在路上）时才泛化
- C. 只要方法超过 20 行就抽
- D. 每个接口都应预留默认实现

> 答案：B
> 解析：第一次写死、第二次小幅重写、第三次才泛化——让"变化样本"告诉你抽象的正确边界，提前抽象八成抽错维度。

### 2. "删除测试"的判定方法是（10分）

- A. 删掉抽象层看编译是否报错
- B. 假想删除该层：复杂度消失则是过度设计, 复杂度转移扩散到多处才是必要抽象
- C. 删掉后跑一遍性能测试
- D. 看该层有没有单元测试

> 答案：B
> 解析：好抽象是"复杂度吸尘器"，坏抽象是"复杂度转发器"——判据是删掉后系统总复杂度升降，不是能否编译。

### 3. 遗留代码里没有测试又不能大改时, 进入的第一步是（10分）

- A. 直接边读边改, 靠 code review 兜底
- B. 先写 characterization test 锁定现状行为（哪怕现状是 bug）, 再在绿伞下重构
- C. 把整模块推倒重写
- D. 加满日志观察一周

> 答案：B
> 解析：特征测试记录"现在实际做什么"而非"应该做什么"；没有这张安全网，任何重构都是在拆盲雷。

### 4. 重构的严格定义包含的关键约束是（10分）

- A. 必须用 IDE 的自动化工具
- B. 不改变外部行为的结构变换, 且每一步代码都可编译、测试保持绿
- C. 只能由原作者执行
- D. 必须在专门的"重构周"完成

> 答案：B
> 解析：A/C/D 是工程习惯不是定义；"行为不变 + 小步可验证"是重构区别于重写的生命线。

### 5. 一次 commit 里混入重构与功能变更的最实际危害是（10分）

- A. commit 行数太好看
- B. git bisect 定位回归时无法区分"结构挪动"与"行为改变", 且评审者看不清改了什么
- C. 违反了分支命名规范
- D. 会导致 CI 无法构建

> 答案：B
> 解析：混合 commit 让二分定位失效（每个中间点都同时含两类变化）、评审注意力被噪声淹没——"revert 这个 commit 会连带回滚无关重构"也是它。

### 6. 以下哪些是过度设计的可靠信号？（多选）（10分）

- A. 接口只有一个实现, 且从未在测试/运行时被替换
- B. 为"未来可能多租户"给每张表加 tenantId 却没有任何调用方使用
- C. Controller→Facade→Manager→Service 层层薄转发
- D. 一个策略接口有三个实现且每季度新增一个

> 答案：A、B、C
> 解析：D 是被真实变化持续验证的抽象, 恰是"该设计"；前三个共同点是"为没发生/不存在的需求预付结构成本"。

### 7. 坏味道与重构手法的对应, 正确的有（多选）（10分）

- A. 数据泥团（参数总是成串）——Introduce Parameter Object
- B. 羡慕特性（A 疯狂调 B 的 getter）——Move Method 把行为搬到数据侧
- C. 永远为真的开关分支——保留并加注释说明
- D. 千行上帝类——Extract Class 按变更原因拆

> 答案：A、B、D
> 解析：C 错——死分支应删除（git 记得一切）, 注释不复活僵尸代码。

### 8. 判断："贫血模型是反模式，所以 Entity 里应该写满业务逻辑包括调用远程服务。"（5分）

- A. 正确
- B. 错误

> 答案：B
> 解析：贫血的解药是把"不变式与领域行为"搬回对象，不是把基础设施塞进去——领域对象该依赖注入的是端口抽象（仓储/发布器），远程细节留在适配器层（接 ddd 包）。

### 9. 简答题：评审会上有人提议"给通知模块加插件机制以支持未来扩展"，用本课判据给出一套完整的质询与决策程序。（15分）

> 参考答案：
> - 时机测试: 第二/第三个真实消费者是谁? 拿不出名字=第0次变化, 不抽
> - 删除测试: 不建机制直接 if 分发, 未来加渠道时复杂度转移还是消失? 消失则现在就是过度设计
> - 成本提问: 插件机制的接口冻结/文档/测试维护成本 vs 直写方案未来改动成本, 让数字说话
> - 决策: 需求排进 Roadmap(≥2 渠道且时间明确)→现在抽接口; 否则记录债条, 第二渠道到来时由实现者顺手抽
> - 制度化: 把"抽象必须举出已发生的变化样本"写进 checklist, 避免每次靠嗓门

### 10. 简答题：给出"何时不该重构"的三条判据，并说明不重构时如何管理这笔债。（10分）

> 参考答案：
> - 判据: ① 模块进入 strangler 圈地/废弃倒计时, 翻新投入随迁葬清零
> - ② 无测试且补测试成本>重构收益, 又不在变更热区(改它频率极低)——风险收益倒挂
> - ③ 同一区域业务即将大改, 现在重构的形状大概率被新需求推翻
> - 管理: 记债条(位置+触发条件+预估成本)进 backlog 而非脑内; 设触发器(如"下个需求碰它则先补测试再动")
> - 纪律: 债要可视化统计, 否则"暂不重构"会退化成"永不重构"
