# 过度设计与反模式、重构手法 · 作业题

> 本节作业 3 题：一次抽象审计、一场小步重构直播、一份热区考古报告。

## 作业 1：用三个删除测试审计仓库抽象（分析+动手）

在仓库里找出**间接层级最深**的一条调用链（从入口到第一行业务逻辑经过的类/接口数最多者）：

1. 画出链路图，对每一层跑三个测试（删除测试/第三实现测试/时机测试），标注"必要/存疑/冗余"；
2. 对判为"冗余"的层执行真实删除（合并转发逻辑），全量测试必须保持绿——绿不了说明它其实不冗余，记录差异；
3. 统计删除前后：到达业务代码需打开的文件数、异常栈平均深度、新人定位一个 bug 的耗时（可用自己闭卷模拟）；
4. 产出一页"抽象审计报告"：哪些抽象被变化验证、哪些在裸奔。

**验收标准**：至少一个真实的"删除后全绿"案例 + diff 行数；被反驳的存疑层要有"它挡住的真实变化样本"。

## 作业 2：把一个 150 行方法小步重构到可评审（动手）

选一个无测试的长方法（或自造等价难度的）：

1. 第一步不许动结构：给它补 characterization test——把当前所有分支的输出固化成断言（含你认为的 bug，注释标记"现状锁定"）；
2. 连续小步重构：Extract Method → 参数对象化 → 死分支删除 → 守卫子句替换嵌套 if，**每步编译+测试绿才 commit**，message 前缀 `refactor:`；
3. 最后单独一个 `feat:` commit 修掉第 1 步标记的那个"现状 bug"，展示测试网如何让它现形；
4. 导出 `git log --oneline --stat`：数 commit 数与平均改动行数，回答"为什么不能一个 commit 做完"。

**验收标准**：commit 序列符合"每步可编译可测试"；第 3 步的 feat commit 改行 ≤5（前面重构铺垫到位的证据）。

## 作业 3：git 热区考古——霰弹式修改取证（分析）

用 git 历史给仓库做一次"变更耦合"分析：

1. `git log --format= --name-only` 统计近一年同时出现在同一 commit 的文件对，排出 Top10 共变对（可写 20 行脚本）；
2. 挑共变最狠的一组（典型如"加字段要改 Entity+DTO+VO+Mapper+Converter+ES索引"六连）：判定坏味道（霰弹/数据泥团/贫血），画出期望的收敛目标（哪个模块该拥有这个变化）；
3. 估算：这类"一次需求 N 个文件"的累计改动行数 × 历史次数 ≈ 这笔债的年化利息；
4. 给出三行还债计划：第一步动哪个手法、需要哪些测试护航、什么信号出现时必须停手（接"何时不该重构"）。

**交付物**：共变 Top10 表 + 一组深度取证 + 年化利息估算 + 还债计划。

**提示**：这份报告直接可以当技术评审素材——用变更历史代替审美争论。
