# 探针与优雅停机 · 作业

## 作业 1：三探针行为区分

**目标**：用实验坐实"重启 vs 摘流"。

1. 配一个 liveness 恒定失败（探一个 500 路径）的 Pod，观察它反复 RESTARTS 增长（输出：restart 计数）；再换成 readiness 失败，观察它是 Ready=False 但不重启、且从 Service 端点消失（验收：两种失败现象对比清晰）。
2. 慢启动应用（sleep 60 才 listen）只配严格 liveness → 复现启动期被反复杀；加 startupProbe 修复（错误用例→修复：理解 startup 的豁免作用）。

## 作业 2：复现发布 502 再消除

**目标**：亲手踩中摘流并发窗口并修好。

1. 起一个持续被打压测的服务，滚动发布，`hey`/压测脚本统计 5xx——裸配（无 preStop、宽限 30）复现零星 502（输出：错误率）。
2. 加 preStop `sleep 8` + `server.shutdown=graceful` + 宽限期调 45，重跑压测看 5xx 归零（验收：发布全程无失败请求）。
3. 把 ENTRYPOINT 从 exec 改回 shell 形式重测，观察优雅关闭失效（`Shutdown` 日志不出现）——证明信号可达是前提（异常：配了 graceful 也白搭）。

## 作业 3：生产级探针评审清单

**目标**：形成可复用的评审条目。

1. 检查一个真实服务：liveness 是否探测了外部依赖（若是，标记为雪崩风险）、readiness 是否用了依赖就绪组、startup 预算是否覆盖冷启动（每项给结论与改法）。
2. 输出一页"探针+停机"配置模板（含 preStop/宽限期/graceful 三处联动数值），写清各数值间的算术约束（说明：宽限期>preStop+排空 这类不等式要显式写死）。
3. 反例：贴一份"三探针全打到同一个聚合健康端点"的配置，指出为什么这是最差实践。
