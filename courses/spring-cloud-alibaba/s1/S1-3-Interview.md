# SCA 落地与自建/开源选型边界（关联） · 面试题

## 题 1：Spring Cloud Netflix 现在还能作为新项目首选吗？

- 不建议。Hystrix 停维护、Eureka/Ribbon/Zuul 1.x 进维护模式，官方栈已转向 Gateway/LoadBalancer/CircuitBreaker+Resilience4j。
- 留旧栈=背不再演进的技术债。
- 加分：能说出每个停滞件对应的替代件。

## 题 2：SCA 相比 Netflix 栈的优势和代价？

- 优势：Nacos/Sentinel/Seata/Dubbo 一体化、与阿里生态与国产云亲和、信创合规友好、中文社区易招聘。
- 代价：要吃透各组件运维（鉴权、HA、规则持久化、版本兼容）。
- 加分：强调"用 SCA BOM 锁版本"是把一体化优势落地的前提。

## 题 3：版本对齐为什么重要？怎么管？

- Boot/Cloud/Alibaba 三套必须落在官方兼容矩阵，否则混合栈运行期类冲突、自动配置打架。
- 用 `dependencyManagement` 引入三个 BOM、子模块不各写版本。
- 加分：讲一个"混搭版本导致启动 NoSuchMethod/Bean 冲突"的排障经历。

## 题 4：公司要不要自研注册中心/配置中心？

- 多数为负 ROI：要养团队、造监控告警、扛稳定性事故，收益仅在强定制/极致规模/合规物理隔离时才可能为正。
- 一般选成熟开源、把自研精力留给业务护城河。
- 加分：把"稳定性事故半径 + 持续维护成本"计入自建的隐性成本。

## 题 5：已有 Netflix 老栈要不要迁到 SCA？怎么迁稳妥？

- 先评估改动量与双栈过渡风险，别为换而换；分阶段：先替换低风险的 LB/CircuitBreaker，网关与注册中心最后动。
- 过渡期可 Eureka/Nacos 双注册等兼容手段，保留回滚点。
- 加分：给出"迁/留/分阶段"的判定依据（团队熟悉度、合规、生态）。

## 题 6：做技术选型时你怎么避免"技术信仰"陷阱？

- 用可权衡维度打分：团队熟悉度、招聘、监控运维成本、合规（信创/自主可控）、生态适配、迁移成本。
- 结论对场景负责：政务信创、金融自主可控、电商快速交付的最优解不同。
- 加分：强调把决策写成成本/风险文档而非"哪个更牛"，允许被数据推翻。
