# 核心角色与四种授权模式 · 面试题

## 题 1：OAuth2 和 OIDC 有什么区别？

- OAuth2 是**授权**框架——解决"第三方能否访问用户的某些资源"，发的是 Access Token，关心 scope。
- OIDC 建在 OAuth2 之上做**认证**——多发一个 id_token（JWT），告诉 Client"这个用户是谁"，引入 `scope=openid` 与 userinfo 端点。
- 一句话：OAuth2 回答"能干什么"，OIDC 回答"你是谁"；用 OAuth2 单独做登录是常见误用。
- 加分：能讲"微信登录本质是 OAuth2 但被拿来做认证是历史包袱"，展开见 [OIDC、SSO 与令牌关系（关联 JWT）](S1-3-Lesson.md)。

## 题 2：为什么授权码模式要先给 code 再换 token，而不直接返回 token？

- 前端通道（浏览器重定向）是不可信通道，易被历史记录/Referer/恶意扩展截获；code 走这条道，token 走后端 TLS 直连通道换取。
- code 一次性、极短命、绑定 redirect_uri 与 PKCE 挑战，即使被截也换不出 token（缺 client_secret / code_verifier）。
- 这个"两段式"正是隐式模式被废弃的根本原因——隐式让 token 直接暴露在不可信前端通道。
- 加分：点出后端通道还可做客户端认证（secret/私钥），把"持码者"和"合法客户端"两件事分开验证。

## 题 3：Access Token 该设多长？为什么不能用超长有效期？

- 无状态令牌一旦签发无法收回，TTL 就是"吊销延迟"的上限——设 30 天等于留 30 天越权窗口。
- 折中：access 分钟级（5~15 分钟）压低暴露面，配 refresh token 续期，用户不必频繁登录。
- 反例：为了"少跳登录页"把 access 设成一年，等于放弃撤销能力，令牌进日志/被抓包即长期失守。
- 加分：真要即时吊销就上 token 黑名单 / introspection（见 [无状态登出、吊销与与 OAuth2 协同（关联）](../../jwt/s1/S1-3-Lesson.md)），用可用性换撤销性。

## 题 4：客户端凭证模式和授权码模式的本质区别？

- 有没有"第三方用户"这个主角：客户端凭证里 token 代表**应用自身**，只能访问应用自有资源；授权码里 token 代表**某个用户授权的范围**。
- 客户端凭证无 code、无用户跳转、通常无 refresh，直接 client_id+secret 换 token。
- 典型误用：用客户端凭证 token 去访问"用户 A 的订单"——越权，因为它根本不携带用户身份。
- 加分：M2M 场景（对账、抓取、后台任务）是客户端凭证主场，claims 里看有没有 `sub`/用户标识即可判定。

## 题 5：Refresh Token 安全上要注意什么？

- 它比 access 权限更大（能不断续命），必须只在 AS 的 token 端点使用、绝不发给 RS、必须走 TLS。
- 绑定 client + 轮换（rotation）：每次刷新签发新 refresh 并作废旧的，检测到旧值复用即判重放、吊销整条链。
- 反例：refresh 不设过期、不轮换、可跨设备复用——一旦泄露等于永久后门。
- 加分：盗用检测思路——旧 refresh 被再次使用时触发告警并撤销全家族令牌（OAuth 安全 BCP 建议）。

## 题 6：设计一个开放平台，第三方接入要守住哪些安全底线？

- 模式：机密客户端授权码、公共客户端授权码 + PKCE，禁隐式禁密码。
- 端点：redirect_uri 精确白名单（防子域/前缀绕过）、state 防 CSRF、token 端点做客户端认证。
- 授权：scope 最小化 + 用户同意页明示权限；限流与配额按 client 维度。
- 生命周期：client_secret 可轮转、token 可吊销、接入方有审计日志。
- 加分：把"要账号密码=红线、藏按钮≠鉴权、数据权限下推 SQL"三条常识写进接入规范，与 [认证授权模型与权限设计](../../spring-security/s1/S1-2-Lesson.md) 呼应。
