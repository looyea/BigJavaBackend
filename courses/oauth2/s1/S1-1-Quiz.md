# 核心角色与四种授权模式 · 小测

## 一、单项选择题（每题 6 分，共 42 分）

### 1. OAuth2 解决的核心问题是？（6分）

- A. 让用户把账号密码分享给第三方以简化登录
- B. 让用户在不交出密码的前提下，把部分资源访问权委托给第三方
- C. 给 API 做签名防篡改
- D. 替代 HTTPS 做传输加密

> 答案：B
> 解析：委托授权是 OAuth2 的立身之本，"拿密码"恰恰是它要避免的（密码模式因此被废弃）。

### 2. 签发令牌的组件是？（6分）

- A. Resource Server
- B. Client
- C. Authorization Server
- D. Resource Owner

> 答案：C
> 解析：AS 负责认证用户并签发令牌；RS 只验牌取货，不发牌。

### 3. 关于 Access Token 与 Refresh Token，正确的说法是？（6分）

- A. 二者可互换使用，都是拿去过资源的
- B. Refresh Token 应随每次请求发给 Resource Server
- C. Access Token 短命随请求携带，Refresh Token 只在 AS 的 token 端点换新、绝不发给 RS
- D. 客户端凭证模式必须下发 Refresh Token

> 答案：C
> 解析：两种令牌作用域不同，把 refresh 当 access 用是常见集成错误，RS 应拒绝；机器可自行重取，客户端凭证通常无 refresh。

### 4. 一个纯后端定时任务要拉取开放平台数据，无用户参与，应选？（6分）

- A. 授权码模式
- B. 客户端凭证模式
- C. 隐式模式
- D. 密码模式

> 答案：B
> 解析：Machine-to-Machine、无"用户"主角时用客户端凭证，签发的是应用身份令牌。

### 5. OAuth 2.1 明确废弃隐式（implicit）与密码（password）两种模式，共同原因是？（6分）

- A. 性能太差
- B. 都无法与 JWT 兼容
- C. 令牌/凭证暴露面过大、违背最小权限与可撤销原则
- D. AS 端实现太复杂

> 答案：C
> 解析：隐式把 token 暴露在 URL 片段，密码模式让第三方直接收集口令，都破坏了委托授权的安全前提。

### 6. 第三方接入时开口要"给我你们的账号密码我来帮你登录"，架构师应？（6分）

- A. 评估其 token 有效期后决定
- B. 判定为安全红线，改走授权码跳转，Client 全程不接触口令
- C. 允许，但要求加密传输
- D. 让它用客户端凭证模式替代

> 答案：B
> 解析：这是红线而非选型问题；正确路径是跳转 AS 登录，回调只拿一次性 code。

### 7. Resource Server 校验一个 Bearer 令牌时，本质上关心的是？（6分）

- A. 用户是谁、密码对不对
- B. 令牌由可信 AS 签发、未过期未吊销、且 scope 覆盖本次操作
- C. Client 的 secret 是否正确
- D. 令牌的 Base64 能否解码

> 答案：B
> 解析：验牌方不关心口令，只验签名字有效性 + 有效期 + 授权范围是否足够。

## 二、多项选择题（每题 9 分，共 18 分）

### 8. 关于四种 grant 的适用，正确的有？（多选）（9分）

- A. Web 机密客户端标准答案是授权码模式
- B. SPA/移动端这类公共客户端用授权码 + PKCE
- C. 服务端对服务端无用户场景用客户端凭证
- D. 遗留 App 想直接吃用户口令，在新规范下仍被推荐

> 答案：A、B、C
> 解析：D 错——密码模式在 OAuth 2.1 被禁止，仅第一方高信任遗留系统可能临时存在，新接入一律打回。

### 9. 关于令牌设计，正确的有？（多选）（9分）

- A. Access Token 短 TTL 可降低被窃后的可用窗口
- B. Refresh Token 泄露危害更大，应绑定 client、可轮换、能吊销
- C. 为省事把 access token 有效期设成 30 天是安全最佳实践
- D. RS 应拒绝把 refresh token 当 access token 携带访问资源

> 答案：A、B、D
> 解析：C 是反例——长命 access 使吊销形同虚设、一旦被窃即长期越权，正是"无状态便利"与"可撤销"的取舍点。

## 三、简答题（40 分）

### 10. 某电商要开放平台给第三方 ISV 拉取"用户订单"，请给出 OAuth2 接入方案要点。（40分）

> 参考答案：
- 角色：用户=RO，ISV=Client，开放平台=AS，订单 API=RS。
- 模式：机密客户端走授权码；纯前端 ISV 走授权码 + PKCE。
- scope：用 orders.read 精确限权，遵循最小权限，别给全站 scope。
- 令牌：短命 access + 可轮换 refresh，refresh 绑 client 且可吊销。
- RS 侧：校验签名/过期/scope，越权返回 403，不验证用户口令。
- 治理：redirect_uri 精确白名单、client_secret 轮转、审计与限流按 client 维度。

> 解析：能覆盖"角色—模式—scope—令牌—校验—治理"六层即达生产水准。
