# 实际面试题 · 复杂度分析与大 O 思维

> 复杂度是架构师面试的"隐形必考项"：它藏在每一道系统设计、每一次性能优化、每一个"为什么慢"的追问里。答好的标志不是背大 O，而是**能把复杂度和线上资源预算挂钩**。

## 题 1：你们线上遇到过因复杂度导致的性能问题吗？怎么发现和解决的？

**期望时长**：2 分钟

**答题要点**：

- 给真实案例：接口慢 → 火焰图/慢 SQL/`trace` 定位到热点方法。
- 根因往往是"循环里做集合查找 / 循环里查库做 RPC / 全表扫无索引"。
- 解法：把 O(m) 查找降 O(1)（哈希/索引）、N+1 查询合批、加缓存。

**追问链**：

1. 你是怎么判断"这段代码是 O(n²)"的？→ 看嵌套循环依赖关系 + 循环内的操作本身复杂度。
2. 数据量小的时候为什么不慢？→ 常数与低阶项在 n 小时不显现，大 O 只在规模上来后暴露。

## 题 2：大 O 里的"忽略常数"在工程上会不会误导你？

**答题要点**：

- 会。同为 O(n)，一条 HashMap 链路和一条 TreeMap 链路常数差好几倍。
- 小规模数据（n < 几十）时，常数、缓存友好性、内存布局往往比量级更影响真实耗时。
- 正确姿势：先用大 O 排除会随规模爆炸的方案，再在同量级内用压测/火焰图比常数。

**追问链**：那什么时候该关心常数？→ 热点循环、向量化/基本类型拆箱、分支预测、内存局部性（数组 vs 链表）。

## 题 3：ArrayList 和 LinkedList，取第 i 个元素、中间插入，分别什么复杂度？

**答题要点**：

- `get(i)`：ArrayList O(1)，LinkedList O(n)（要遍历定位）。
- 已知节点引用时中间插入：LinkedList O(1)（改指针），ArrayList O(n)（后移）。
- 但插入前"找位置"LinkedList 仍 O(n)，所以 LinkedList 的插入优势只在已持有迭代器/节点时才成立。

**追问链**：那为什么实际开发几乎总用 ArrayList？→ 缓存友好 + 无指针开销，绝大多数场景遍历/随机访问为主，LinkedList 的 O(1) 插入难以兑现（详见下一节）。

## 题 4：为什么"在 for 循环里查数据库/RPC"是架构级大忌？复杂度视角怎么说？

**答题要点**：

- 单次网络往返有微秒~毫秒级固定成本，循环把它放大成 O(n) 次 RTT，且串/并行都吃连接池。
- 属于"隐藏的高常数 O(n)"，比纯计算的 O(n²) 更早成为瓶颈（IO-bound）。
- 解法：批量接口（`IN`/batch）、预取、管道化；把 n 次压成 1 次。

**追问链**：批量 `IN` 5000 个 ID 有没有问题？→ 有，SQL 过长/索引扫描退化/内存膨胀，需分片批量（如每 500~1000 一批）。

## 题 5：时间换空间、空间换时间，你怎么决策？

**答题要点**：

- 看瓶颈：CPU-bound 就考虑用内存/缓存换时间；内存-bound 就考虑排序/分批把空间换出来。
- 给组合方案：哈希加速、前缀和空间换 O(1) 区间查询、布隆过滤器以极小空间换大量回源削减。
- 强调"没有银弹"，最终由容量预算和 SLA 决定。

**追问链**：举一个你用空间换时间把系统救活的例子？→ 结合本地缓存(Caffeine)、预计算物化视图、索引等真实场景作答。
