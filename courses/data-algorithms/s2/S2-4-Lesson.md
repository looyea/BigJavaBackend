# B/B+ 树、Trie、跳表、并查集、布隆过滤器

> 前几节的结构都活在内存里。这一节把视野拉到**磁盘、Redis、网络、大规模去重**——五种"工程现场长出来的结构"。
> 每种抓住三问：**它解决什么、为什么是这样、代价是什么**。它们是数据库索引、缓存、前缀检索、依赖聚并、海量判存的底层答案。

## 一、B 树 / B+ 树：为磁盘而生的多叉矮胖树

**动机**：内存树（红黑）太高，而数据库索引存在磁盘上，**每次 IO 以页（16KB）为单位**。树太高 = 一次查询几十次磁盘读 = 灾难。

**B+ 树设计**：
- **多叉**：一个节点存几百个 key（一页装满），扇出极大 → 千万行只有 **3~4 层** → 一次范围查 3~4 次 IO。
- **非叶只存 key 和指针，数据全在叶子**：非叶更"矮胖"，扇出更大。
- **叶子用双向链表串联**：范围扫描（`between`、`order by`）顺序走链表，不必回到上层。

| 对比 | 红黑/AVL | B+ 树 |
|---|---|---|
| 分支 | 二叉，高 | 多叉，矮（IO 少） |
| 数据位置 | 每节点 | 只在叶子 |
| 范围查询 | 需中序回溯 | 叶子链表顺序扫 |
| 场景 | 内存 | 磁盘（MySQL InnoDB 索引） |

**代价**：插入/分裂维护复杂、写放大（页分裂）。**这是 MySQL 索引用 B+ 树而非哈希/红黑的根本原因**（详见 mysql 分区）。

## 二、Trie 前缀树：按"字符"分叉的检索结构

**动机**：哈希只能整串精确匹配；当你要**前缀检索、自动补全、最长前缀匹配**，需要把 key 拆成字符逐层下探。

```
"cat","car","do","dog" →
      root
     /    \
    c      d
   / \      \
  a   ...    o
 / \          \
t   r          g✓
```

- 查找一个词 O(词长)，与库里多少词无关；天然支持"以某前缀开头的所有词"。
- 典型应用：搜索框联想、敏感词过滤、IP 路由最长前缀匹配、字典树去重。
- 优化：**压缩 Trie（Radix）** 合并单链省空间；每个节点可挂 count 做词频。
- 代价：字符集大时节点多、指针开销大 → 用哈希表存孩子或压缩。

## 三、跳表 SkipList：用"多层索引链表"换 O(log n)

**动机**：链表查找 O(n)。跳表给链表加**多级稀疏索引**（像地铁图的快慢线），查找时从高层往下跳，期望 O(log n)。

```
L2:  1 ─────────────→ 9
L1:  1 ──────→ 5 ───→ 9 ──→ 12
L0:  1 → 3 → 5 → 7 → 9 → 11 → 12
```

- 每个节点插入时**随机决定升几层**（概率提级），无需旋转，实现远比红黑简单。
- **Redis ZSet 为什么用跳表不用红黑树**：① 范围查询（`ZRANGEBYSCORE`）顺着底层链表走，天然高效；② 实现简单、易调试；③ 插入删除只改指针不旋转，并发/局部性好；④ 按名次/分数定位都方便。
- 代价：多层指针占额外内存、性能依赖随机化质量。

## 四、并查集 Union-Find：只关心"属不属于同一组"

**动机**：动态维护**不相交集合的归属关系**——高频做两件操作：`union(a,b)` 合并两类、`find(x)` 查 x 的代表元（判断两点是否连通）。

- 用"森林 + 每棵树的根代表一个集合"实现，`find` 沿父指针爬到根。
- 两大优化：**路径压缩**（find 时把节点直接挂到根）+ **按秩/大小合并** → 均摊近似 O(α(n))，几乎常数。
- 应用：无向图连通分量、Kruskal 最小生成树、账号合并/好友推荐、商品聚类、判断依赖是否成环。

```java
int[] parent;
int find(int x){ return parent[x]==x ? x : (parent[x]=find(parent[x])); } // 路径压缩
void union(int a,int b){ parent[find(a)] = find(b); }
```

- 代价：只支持合并与查询，**不支持拆分**（撤销 union 很难）。图的遍历类问题它管不了，得回 BFS/DFS（s3-1）。

## 五、布隆过滤器 Bloom Filter：用极小内存换"可能有、定无"

**动机**：10 亿 URL 判"是否见过"，HashSet 存不下。布隆用**一个位数组 + k 个哈希函数**，只花几十字节/亿元素。

- 插入：k 个哈希把 k 个位置置 1；查询：k 个位置**全 1 → 可能存在**，**有一个 0 → 一定不存在**。
- **核心特性**：**说"没有"绝对可信，说"有"可能误判**（假阳性），且**不支持删除**（位被共享，标准版）。误判率随装载率上升而升高，可调位数与哈希个数控制。
- 应用（都是"用一次判存挡掉大量无效穿透"）：**缓存穿透防护**（先问布隆，说没有直接返回，不打 DB）、URL/爬虫去重、风控黑名单粗筛、推荐已读过滤。
- 变体：**Counting Bloom**（用计数器代替位，支持删除）、**Cuckoo Filter**（更省、可删）。

> 工程红线：布隆**只能当"前置粗筛"**——它说"有"时仍需回源精确确认；用于缓存穿透时，热 key 删除要重建布隆，否则新 key 被误判为"不存在"而进不去。

## 六、五结构选型速查

| 需求 | 结构 | 关键理由 |
|---|---|---|
| 磁盘索引、范围查询 | B+ 树 | 矮胖少 IO、叶子链表有序 |
| 前缀检索、自动补全 | Trie | 按字符下探、O(词长) |
| 有序 + 范围 + 简单实现(Redis ZSet) | 跳表 | 多层索引、范围友好、无需旋转 |
| 动态连通性、分组、判环 | 并查集 | α(n) 近常数，只合并不拆分 |
| 海量判存、可容忍假阳性 | 布隆过滤器 | 极省内存，"无"绝对可信 |

## 七、本节要点回顾

1. B+ 树为磁盘 IO 而生：多叉矮胖 + 叶子链表，是数据库索引的标准答案。
2. Trie 按字符分叉，独门前缀/补全/最长前缀匹配。
3. 跳表用随机多级索引换 O(log n)，Redis ZSet 选它因范围友好 + 实现简单。
4. 并查集近 O(1) 维护"同组归属"，擅长判连通/聚并，但不能拆分。
5. 布隆以极小内存做"判存粗筛"，"说无必真、说有存疑"，防缓存穿透利器。
