# 小测验 · B/B+树、Trie、跳表、并查集、布隆过滤器

> 本卷共 6 题，混合单选 / 多选 / 判断 / 填空 / 简答，满分 100 分，≥ 60 分过关。

### 1. 数据库（InnoDB）索引用 B+ 树而非红黑树，最核心的原因是？（15分）

- A. B+ 树实现更简单
- B. 磁盘按页读，B+ 树多叉矮胖使 IO 次数少，且叶子链表利于范围扫描
- C. 红黑树不能存 key
- D. B+ 树查找一定是 O(1)

> 答案：B
> 解析：磁盘 IO 是瓶颈，红黑太高每层一次 IO；B+ 一个节点装满一页、千万行仅 3~4 层，叶子双向链让 `between/order by` 顺序扫。

### 2. 布隆过滤器的判定特性是？（15分）

- A. 说"存在"一定存在，说"不存在"可能不存在
- B. 说"不存在"一定不存在，说"存在"可能是假阳性
- C. 完全准确，只是更省内存
- D. 支持高效的删除任意元素

> 答案：B
> 解析：布隆靠 k 个哈希位判存——有位为 0 则必不存在（可信）；全 1 可能因哈希冲突误判为存在（假阳性）。标准版不支持删除。

### 3. 【多选】关于这几种工程结构，正确的有哪些？（20分）

- A. 跳表用随机化的多级稀疏索引换 O(log n)，无需旋转、实现比红黑简单
- B. Redis ZSet 选跳表之一原因是范围查询顺底层链表走很高效
- C. 并查集支持 union/find，同时也能方便地 undo 一次合并（拆分集合）
- D. Trie 擅长前缀匹配与自动补全，查询复杂度是 O(词长)

> 答案：ABD
> 解析：C 错——并查集只合并与查询，**拆分极难**（路径压缩后结构已扁平）。A/B/D 均正确。

### 4. 判断：要做"10 亿 URL 去重、可容忍极小误判、内存有限"，最适合用 HashSet 全量存。（10分）

- A. 正确
- B. 错误

> 答案：B
> 解析：10 亿字符串 HashSet 内存爆炸；正解是布隆过滤器，几十字节/亿元素，接受假阳性做粗筛。

### 5. 填空题：并查集用 ______ 和按秩合并两个优化后均摊复杂度近似 ______；B+ 树的数据只存放在 ______ 节点，非叶节点只存 key 与指针。（10分）

> 答案：路径压缩 / O(α(n)) 近常数 / 叶子

### 6. 电商详情页缓存每天被海量"不存在的商品 ID"打穿直达数据库（缓存穿透）。请用本节结构给出防护方案，说明它挡在哪一层、误判会带来什么后果、如何缓解。（30分）

> 参考答案：
> - 在缓存前加一层布隆过滤器，装载全部有效商品 ID；请求先问布隆
> - 布隆说"不存在"→ 直接返回空，不打 DB（"无"绝对可信，挡掉绝大部分穿透）
> - 布隆说"存在"→ 再走缓存/DB 精确确认；假阳性只是极少数穿透没被挡住，不影响正确性
> - 缓解误判与"新品/删除"问题：新品要同步 add 进布隆；删除商品标准布隆不能删 → 用 Counting Bloom/定期重建，或"DB 查无也缓存空值 + 短 TTL"兜底
> - 关键：布隆是前置粗筛，用它换"用一次内存判存挡掉无效穿透"，绝不拿它的"存在"结论当最终真相
