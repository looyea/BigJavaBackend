# HTTPS/TLS、脱敏与合规落地（关联）

> 本节难度：★★★★☆
> 本节重要性：★★★★☆
> 学习产出：能把"数据安全"从口号落成三层可控工程——**传输层**用 HTTPS/TLS 保证链路不被窃听/篡改（强制 TLS 1.2/1.3、禁用弱协议与弱密码套件、证书链完整可验证、HSTS、内部服务间也 mTLS），**存储层**对敏感字段做落盘加密（AES-GCM 对称加密数据、密钥由 KMS 托管与轮换，绝不明文入库、绝不硬编码密钥），**使用层**按场景脱敏（展示掩码、分析用哈希/去标识、导出与日志二次管控）。三层职责不同、不可互相替代：TLS 只保护"在传"，管不了"在库"；展示掩码只护"给人看"，管不了"拖库"。**合规落地**是把 等保 2.0、GDPR、PCI-DSS 的条款映射成具体技术控制：PCI 要求卡号 PAN 存储加密 + 展示截断 + 传输 TLS；GDPR 要求个人数据最小化、可删除（被遗忘权）、去标识化与跨境传输合规；等保要求分等级保护、加密与审计留痕。要点：密码（口令）用不可逆强哈希（bcrypt/scrypt/Argon2）不是"加密"，别和字段加密混；密钥与数据分离存放、可轮换、可审计访问；被遗忘权要能真正物理删或不可逆匿名化，光软删不够。识破"只上了 HTTPS 就以为合规、库里卡号仍明文""把口令用 AES 可逆加密存起来""脱敏只挡页面、导出/日志又漏原文""证书过期/链条不全导致握手失败或降级""密钥和数据同库同备份，一处泄露全崩"等坑。

## 一、传输层：强制强协议、可验证证书

```yaml
# 目的：链路加密防窃听篡改, 只留强协议, 证书链可验证
server:
  ssl:
    enabled: true                        # 说明：对外只走 HTTPS, 明文 HTTP 301 跳转
    enabled-protocols: TLSv1.2,TLSv1.3   # 结果：剔除 SSLv3/TLS1.0/1.1 弱版本, 满足 PCI/等保对传输的要求
    # 反例：仍开放 TLS1.0 且用弱密码套件 ❌ 握手可被降级破解 ❌ 内部服务间也应上 mTLS 别只保护边界
```

## 二、存储层 vs 使用层：加密和脱敏各司其职

```java
// 目的：区分"落盘加密"和"展示脱敏"两层, 敏感字段即使脱库也是密文、给人看时再掩码
@Convert(converter = EncryptedStringConverter.class) // 说明：入库前 AES-GCM 加密, 数据密钥由 KMS 托管、可轮换
private String cardNo;   // 结果：库里是密文; 查询展示时按合规掩码成 6222****1234, 两层职责不重叠
// 反例①：只做页面 mask、库里存明文 ❌ 拖库即全裸奔 ❌ 展示脱敏≠存储加密, 必须叠加落盘加密
// 反例②：把登录口令用 AES 可逆加密存 ❌ 密钥泄露即可还原明文 ❌ 口令应用不可逆强哈希 bcrypt/Argon2
```

## 三、把合规条款翻译成技术控制

```text
图目的：常见合规要求各自约束的是哪一层, 避免"上一个 HTTPS 就宣称合规"
PCI-DSS ──▶ 卡号 PAN 存储加密 + 展示截断(前6后4) + 传输走 TLS + 访问审计
GDPR    ──▶ 个人数据最小化、可删除(被遗忘权须真删/不可逆匿名)、去标识化、跨境合规
等保2.0 ──▶ 分等级保护、传输与存储加密、日志与操作留痕可审计、密钥集中管控(KMS)
共性底线: 密钥与数据分离存放、可轮换、访问可审计; 脱敏要覆盖所有出口(查询/导出/日志)
```

## 四、坑与底线

- **三层缺一不算合规**：TLS 护传输、加密护落盘、脱敏护使用，任何"只做了其中一层就宣布安全"都挡不住对应的攻击面与审计问题。
- **口令≠字段加密**：登录口令用不可逆强哈希（bcrypt/scrypt/Argon2，带盐、可调工作因子），可逆加密只用于"以后要还原"的业务敏感字段，两者混用会埋大雷。
- **密钥治理是命门**：密钥进 KMS、与数据分离、定期轮换、访问留痕；被遗忘权要求数据能真正物理删除或不可逆匿名化，软删除/仅脱敏不满足 GDPR。
