# 接口签名、防重放与 KMS · 面试题

## 题 1：接口签名能防篡改，是不是就自动防重放了？

- 不是。签名只证明报文合法且未被改动，不证明它是"新鲜"的，原样截获重发永远合法。
- 防重放必须叠加时效（时间戳窗口）+ 唯一性（nonce 去重），二者与签名是正交的三层。
- 加分：能讲清时间戳挡"过期重放"、nonce 挡"窗口内重放"，缺一不可，且 nonce 过期要 ≥ 窗口。

## 题 2：签名串为什么要严格按 key 字典序排序、还要统一编码？

- 验签方要字节级复现同一段明文串再算哈希，任何顺序/编码差异都会导致签名对不上。
- HashMap 遍历顺序不定会造成偶发验签失败；中文/空格/null/嵌套 JSON 编码不约定同样翻车。
- 加分：提到把签名规范固化为公共 SDK/文档，禁止多端各自实现，是治理这类"偶发不一致"的关键。

## 题 3：内部服务和开放平台，签名算法选型有什么不同？

- 内部服务双方可共享密钥，用 HMAC-SHA256 又快又简单。
- 开放平台要给大量第三方验签但不暴露签名权，用 RSA/ECDSA 非对称——平台持私钥签、第三方拿公钥验。
- 加分：点明"验证方数量与是否可信"是选择轴，并能对应国密 SM3-HMAC/SM2。

## 题 4：nonce 去重为什么必须用 SETNX 而不是先 GET 再 SET？

- GET+SET 非原子，高并发下两个相同 nonce 请求可能同时读到"不存在"从而双双放行，留下重放窗口。
- SETNX（SET ... NX PX）原子占位，只有一个成功，天然抗竞态并自带过期回收。
- 加分：能扩展到幂等 token 也依赖同样的原子语义，并谈 Redis 集群下 key 前缀与过期治理。

## 题 5：为什么密钥不能写在配置文件里？KMS 到底解决了什么？

- 明文密钥进配置/代码/日志等于锁和钥匙一起挂门口，一旦泄露全线失守且难审计、难轮转。
- KMS 托管密钥全生命周期，明文密钥永不出信任边界，应用只做"请求用密钥"而非"持有密钥"。
- 加分：讲出信封加密（KEK 保护 DEK）、最小权限到具体 CMK、密钥使用可追溯审计三点工程价值。

## 题 6：主密钥轮转时，如何做到不重新加密海量历史数据？

- 用信封加密分层：数据由 DEK 加密、DEK 由 KEK 保护；轮转 KEK 只需用新 KEK 重包 DEK 密文。
- 业务密文不动，成本从"重算全量数据"降到"重算少量 DEK"，可平滑灰度。
- 加分：能对比 KMS 自动轮转 vs 手动重包，说明密钥版本(kid/KeyId)与新旧并存期如何兼容解密。
