# 网络模型与容器互联 · 小测

### 1. Docker 默认网络模式是？（6分）

- A. host
- B. bridge
- C. overlay
- D. none

> 答案：B
> 解析：默认挂 docker0 网桥、独立 IP、NAT 出网；`--network=host` 等需显式指定。

### 2. host 网络模式的特点是？（6分）

- A. 完全隔离网络
- B. 容器共用宿主网络栈，无独立 NET Namespace，省 NAT 但端口冲突
- C. 用于跨主机通信
- D. 不能访问外网

> 答案：B
> 解析：host 直用宿主网络，性能高、少一层 NAT，代价是失去端口/网络隔离（结果：多个容器撞同端口）。

### 3. 让两个容器能用"容器名"互相访问，前提是？（6分）

- A. 都用 --link
- B. 加入同一自定义 bridge 网络
- C. 都开 host 网络
- D. 分配固定 IP 并写进配置

> 答案：B
> 解析：自定义网络自带 DNS，按容器名/别名解析成容器 IP；默认 docker0 无按名 DNS，--link 已废弃。

### 4. `-p 8080:8080` 的实现机制是？（6分）

- A. 容器直接监听宿主 8080
- B. iptables DNAT 把宿主:8080 流量转发到容器IP:8080
- C. 修改容器端口为宿主端口
- D. 起一个用户态代理进程

> 答案：B
> 解析：端口映射靠 NAT 规则，`iptables -t nat -L DOCKER` 可见 DNAT（说明：容器间互访不走这个映射）。

### 5. 同一自定义网络内 order 连 mysql，应用的地址是？（6分）

- A. localhost:3306
- B. 宿主IP:映射端口
- C. mysql:3306（容器名+容器真实端口）
- D. docker0:3306

> 答案：C
> 解析：容器有独立 NET Namespace，localhost 指自己；同网走内部 DNS 用服务名直连容器端口，不经过 -p 映射（错误预期常见）。

### 6. 不同自定义网络之间的容器，默认可达性？（6分）

- A. 总是互通
- B. 默认不通，需 network connect 双挂或经宿主
- C. 自动路由
- D. 通过 DNS 互通

> 答案：B
> 解析：网络即隔离边界，这是"前端网/数据网分离"的基础；打通要显式挂到同一网络。

### 7. Linux 容器要访问宿主机上已运行的服务，稳妥方式是？（6分）

- A. localhost
- B. 宿主在网络上的可达 IP 或 host.docker.internal/--add-host
- C. 127.0.0.1
- D. 广播地址

> 答案：B
> 解析：容器里的 localhost 是它自己 NET Namespace；要到宿主需用宿主真实 IP 或特殊域名（Desktop 提供 host.docker.internal）。

### 8. 关于网络隔离与安全，正确的有（多选）（9分）

- A. 把 DB 只放后端网络、不 -p 公网，是纵深防御
- B. 所有服务塞一个 bridge 且都暴露端口，内网横移成本为零
- C. overlay 用于跨主机容器组成同一逻辑网络
- D. none 模式隔离性最强，适合纯计算批处理

> 答案：ABCD
> 解析：四项均正确——A/B 讲隔离价值与反例，C 是 overlay 定位，D 是 none 用途（结果：网络模式选择本身即安全设计）。

### 9. 排查"容器 A 连不上容器 B"，合理的检查项有（多选）（9分）

- A. 两者是否在同一自定义网络
- B. 用的地址是服务名还是误用了 localhost
- C. B 是否真的在监听、监听地址是否为 0.0.0.0 而非 127.0.0.1
- D. 防火墙/security group 是否放行

> 答案：ABCD
> 解析：网络归属、寻址方式、服务监听地址、外部防火墙是四条主要怀疑线（错误用例：B 里应用 bind 127.0.0.1 → 容器内也只有自己能连）。

### 10. 简答题：设计一个电商"网关 + 订单服务 + MySQL + Redis"的单机 Docker 网络拓扑，要求公网只暴露网关。给出方案与理由。（40分）

- 要点1：建两张自定义网络：frontend-net（网关+订单）、backend-net（订单+MySQL+Redis）；目的：DB/缓存不进任何公网可达网段。
- 要点2：只有网关 `-p 80:8000`（或 443）映射宿主端口对外，其余服务一律不 -p（验收：宿主防火墙扫描仅网关端口开放；异常消除：DB 直接暴露的经典事故）。
- 要点3：订单服务双挂 frontend-net 与 backend-net，作为唯一能在两网间转发的节点（说明：跨网默认不通，双挂点即受控边界）。
- 要点4：服务发现用容器名：网关→order:8080、order→mysql:3306/redis:6379，全部走内置 DNS，不写 IP（结果：容器重建 IP 变化不影响连接串）。
- 要点5：MySQL/Redis 数据持久化用卷、且限制监听 0.0.0.0 但仅在 backend-net 内可达（结合 s2-2 卷）；加健康检查确保依赖就绪再放量。
- 要点6：可迁移性说明：该拓扑升级到 K8s 时，自定义网络→Namespace/NetworkPolicy、容器名 DNS→CoreDNS Service、双挂点→Ingress/Service（关联 kubernetes s2-1），设计思想一脉相承。

> 答案：见要点
