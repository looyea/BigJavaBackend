# 容器 vs 虚拟机与底层隔离 · 面试题

## 题 1：容器是不是"轻量级虚拟机"？

- 不是，这个说法本身是错的：VM 带自己的内核走硬件模拟，容器共享宿主内核、只是被 Namespace/CGroup 约束的普通进程（结果：启动、密度、开销数量级差异的根源）。
- 一句话定位："容器是隔离且受限的进程，虚拟机是隔离且完整的操作系统"。
- 加分：说出代价——共享内核意味着内核漏洞的爆炸半径覆盖所有容器，强隔离要多一层（gVisor/Kata）。

## 题 2：Namespace、CGroup、UnionFS 各管什么？举例说明缺一个会怎样。

| 机制 | 职责 | 缺失后果 |
|------|------|----------|
| Namespace | 可见性隔离（PID/NET/MNT/UTS/IPC/USER） | 容器能看见/动宿主全部进程与文件 |
| CGroup | 资源用量上限与权重 | 一个失控容器吃光宿主 CPU/内存（异常：雪崩） |
| UnionFS | 镜像分层与写时复制 | 无共享层、每次全量复制、镜像巨大且慢 |
- 追问：容器内 `ps` 只有一个进程靠哪个？答：PID Namespace。

## 题 3：容器 CPU 打满和内存打满，表现和排查有何不同？

```bash
# 目的：两类资源的语义差异决定现象
CPU 超额 -> 调度 throttle：容器不死，但 P99 飙升、GC 停顿变长（易被误判成"代码/数据库变慢"）
   证据：cat /sys/fs/cgroup/cpu.stat 看 nr_throttled/throttled_time 是否增长
内存超额 -> cgroup OOM Kill：进程直接死，退出码 137、OOMKilled=true（现象果断，反而好认）
# 错误做法：只盯着重启次数查 CPU 问题 —— 应先看 throttle，限流才是真凶
```

## 题 4：镜像分层给部署带来什么红利？有什么反直觉的坑？

- 红利：相同基础层跨镜像/主机复用，push/pull 只传差量，CI 缓存层命中即秒构建。
- 坑：CoW 下"后置 RUN rm"不能真正瘦身（下层数据仍在），要把生成和清理写在同一层（结果：Dockerfile 优化第一章）。
- 加分：层顺序影响缓存失效——把最不常变的（依赖）放上层，常变的（业务代码）放下层。

## 题 5：什么时候不该用普通 runc 容器？

- 多租户执行不可信代码（在线判题、Serverless 函数）：逃逸风险 → gVisor/Firecracker/Kata。
- 需要特定内核版本/内核模块/异构 OS：共享内核满足不了 → VM 或专用运行时。
- 金融强合规物理隔离要求：审计可能直接要求"每租户独立内核"，容器不达标（说明：合规也是技术选型输入）。

## 题 6：容器里跑 `top` 看到宿主机全部内存/核数，为什么？怎么修？

- 因为 cgroup 之前的老工具读 `/proc/meminfo`、`nproc`，看到的是宿主视图（Namespace 没隔离这些数值文件）。
- 修法：新版 cgroup-aware 工具（如 `ctop`/`systemd-cgtop`）、或 `lxcfs` 重写这些文件；JVM 侧的等价问题见 s1-3 容器感知（错误预期：容器 limit 512m，JVM 按宿主 64G 算堆 → 秒 OOM）。
