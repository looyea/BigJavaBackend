# 服务拓扑、指标与分析、告警 · 面试题

## 题 1：SkyWalking 的指标和 Prometheus 的指标，本质区别是什么？

```text
Prom：应用暴露当前值，Prom 拉取存储 —— "谁埋谁负责"，类型语义在应用侧。
SW ：应用只上报 Trace/Metric 原始流，OAP 流式聚合出指标 —— 应用零指标代码。
结果差异：SW 指标口径全司统一（内置模型）不可任意定制；Prom 灵活但易口径漂移。
选型追问：重度定制业务指标仍应 micrometer+Prom；APM 标准指标交给 SW，两边以 Event/Adapter 互通。
```

## 题 2：拓扑上某条边延迟高但目标服务自身 resp_time 正常，怎么解释？

- 边延迟 = 发起方视角（含序列化、网络、对端线程排队）；目标 resp_time = 服务端 Entry Span 计时。
- 差值大 → 网络 RTT/带宽、连接池等待、DNS、TLS 握手或序列化开销（说明定位方向）。
- 实例拓扑 + Profiling 佐证：发起方 Exit Span 前是否卡在线程池（对被调是排队，对主调是耗时）。
- 反例：直接结论"数据库慢"——DB 节点指标未动就归因，复盘被打脸（错误示范）。

## 题 3：SLA 指标在 SW 里怎么定义？为什么阈值写 9800 表示 98%？

- service_sla = 成功请求数 / 总请求数 × 10000（‱ 万分比定点存储，避免浮点）。
- 判定"成功"= Span error=false；HTTP 5xx 是否算失败取决于插件的 status 判定规则（可配）。
- 追问：能自定义"业务失败码"进 SLA 吗？答：原生 SLA 不看业务码 —— 需要 LAL 合成指标或 MQE 二次计算（目的：错误定义对齐业务语义）。

## 题 4：告警为什么要有 silence-period？和"恢复通知"矛盾吗？

- 高频评估（每分钟）下同一故障会连续 firing → silence 窗口内压制重复通知（结果：一条故障一条消息）。
- 不矛盾：恢复仍会发 resolved（webhook 消息含当前状态字段），运维靠状态翻转闭环。
- 治理经验：silence 太短 = 轰炸，太长 = 严重故障升级不及时 —— critical 类应缩短并配升级策略（escalation 需自建或用 AM 侧做）。

## 题 5：不重启应用如何对某个热点接口做线程级性能剖析？

1. UI Profiling 页对目标端点创建 Task（采样时长/阈值可配）→ OAP 下发指令到对应 Agent。
2. Agent 对命中 Trace 的目标线程做方法级采样，结果回传火焰图（说明：按需触发、到量自动停）。
3. 注意点：采样有开销，只对疑病端点开；实例数多时任务按实例粒度下发。
4. 与 async-profiler 对比：SW Profiling 胜在"生产常备、无侵入、按请求触发"，async-profiler 胜在全局低开销与 Wall/Alloc 多事件（两者互补）。

## 题 6：Event 机制解决什么问题？没有它会出现什么排障错觉？

- 解决："曲线突变"与"发布/配置变更/扩缩容"的时间对齐——把变更事件推到 SW，指标曲线自动标注。
- 无它错觉：把 10:00 的发版劣化读成"自然流量增长导致"，走错处置方向（真实误判案例）。
- 落地：CI/CD 流水线收尾步骤调 SW Event HTTP API（携带 service + 时间窗），零人工成本。
