# 与 OpenTelemetry 集成及选型（关联） · 面试题

## 题 1：老板问"OTel 和 SkyWalking 选一个"，你怎么纠正这个问题？

```text
纠正：两者不同层 —— OTel 是采集/传播标准与工具链，SW 是分析产品。
真问题：采集层用谁（SW Agent vs OTel Agent）、分析存储层用谁（SW OAP vs Tempo+Prom+Loki）。
组合合法：OTel 采集 + SW 分析（OTLP 直入），或 SW 采集 + SW 分析（一体化）。
高分答法：把选择变量摆出（语言分布/团队/时间/合规），给出条件化结论而非站队。
```

## 题 2：为什么大厂终态常见"OTel 采、后端可换"？

- 埋点是最大沉没成本：一次全量改造（几千服务），后端 UI/存储换代不应再动业务应用。
- Collector 层做协议转换/采样/纠偏，把"脏活"从 5000 个应用收敛到 10 个 Collector。
- 结果：商业 APM（Datadog）与开源（SW/Tempo）之间迁移成本趋近 exporter 改一行配置。
- 反方观点也要能答：标准收敛慢、语义约定版本漂移、深度产品功能（如 SW 拓扑）OTel 生态要靠拼件。

## 题 3：SW Agent 与 OTel Java Agent 能同时挂在一个 JVM 上吗？

```text
技术上可启动（都是 javaagent），但强烈不建议：
1. 双 transformer 增强同一框架类 → 顺序互踩，Span 重复/上下文错乱（结果不可预期）；
2. 双份上报 = 开销与存储双罚；
3. 排障时"哪个探针的数据"本身成为悬案。
共存正确姿势：进程级二选一，链路级靠边界转换（双 Header 注入）。
```

## 题 4：迁移后如何量化"监控没有退化"？

- 覆盖指标：Trace 完整率（无断链比例）、端点覆盖率、告警规则等价通过率（回放历史故障）。
- 效率指标：模拟故障工单的 MTTR 对比（新旧栈各演练 10 单，结果数据进汇报）。
- 成本指标：每百万 Span 存储成本、值班人均告警量（防止"升级=更贵更吵"）。
- 反例：只看"功能都有"就下线旧系统 —— 一周后某类断链只有旧栈能发现（真实回滚事故）。

## 题 5：SkyWalking 需要被"供起来"吗？谈维护健康度。

- 关注社区信号：发布节奏、OTLP/语义约定跟进速度、存储适配（BanyanDB 成熟度）。
- 团队自身：探针升级是否纳入中间件治理（版本超两年 = 兼容性风险累积）。
- 退出策略：正因为 SW 支持 OTLP 双向，"先用 SW、将来可撤"是低成本路径——选型汇报要讲清退出成本（目的：不是宗教选择是工程决策）。

## 题 6：一句话对比 sw8、traceparent、B3 三种传播格式。

| 格式 | 出身 | Header 形态 | 采样位 | 互操作 |
|------|------|-------------|--------|--------|
| sw8 | SkyWalking | 单 Header 多字段 | 有 | SW 生态原生 |
| traceparent | W3C 标准 | 版本- tid-sid-flags | flags | OTel 默认，全行业收敛方向 |
| B3 | Zipkin | 多 Header（X-B3-*） | X-B3-Sampled | 老牌，可被 Composite 兼容 |

结论：新建跨组织链路优先 W3C；生态内用各自原生无妨，边界转换兜底。
