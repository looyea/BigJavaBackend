# 并发模型、思考时间与 TPS/RT 解读

> 本节难度：★★★☆☆
> 重要程度：★★★★☆
> 学习产出：会用 Open Thread Group 与吞吐量整形器按"目标到达率"建模压力，理解思考时间与集合点的用途和副作用，能用 Little 定律换算线程数，并按"吞吐上升→膝点→平台→衰退"曲线形态给出瓶颈结论。

## 一、两种并发模型：线程驱动 vs 到达率驱动

经典线程组是"线程数+循环"驱动，RT 一变 TPS 就漂；JMeter 3.3+ 的 **Open Thread Group** 按到达率建模：`Target Rate`（每分钟新 arrivals）+ `Ramp Up`（线性升压）+ `Hold/Time`，压测目标从"我开了多少线程"变成"系统以 3000 req/min 的流量长什么样"——更接近生产真实（流量由用户到达决定，不由你线程数决定）。

```text
图目的：负载-响应三区形态（横轴并发/到达率，纵轴指标）
吞吐区：TPS 随压力近线性升，RT 几乎不动 —— 资源未饱和，此区测不出瓶颈
膝  点：TPS 增速放缓、P99 开始抬头 —— 目标容量常在膝点前 10~20%
平台/衰退区：TPS 走平或下跌、RT 陡升、错误率飙升 —— 队列溢出/超时雪崩
（反例：只在吞吐区压 5 分钟就宣布"能扛 5000 TPS"——没碰到膝点的结论都是外推）
```

## 二、思考时间与到达率的换算

真实用户点完一单会看 3 秒页面：`TPS = 并发用户 / (RT + ThinkTime)`。2000 用户、RT 200ms、思考 1.8s → 1000 TPS。两种实现：Uniform Random Timer 模拟思考；或直接 Open Thread Group 定到达率让系统自己排队算有效并发。**无思考时间的"火力全开"压出的是系统极限而非日常水位**——两种都要，但报告里必须写清是哪种。

## 三、吞吐量整形与集合点

- Constant Throughput Timer：按"目标每分钟样本数"节流每线程，粒度粗；**Precise Throughput Timer** 用随机泊松过程逼近真实到达分布，容量测试首选；Throughput Shaping Timer 插件可画阶梯/浪涌曲线（大促秒杀的"3 秒内从 0 到峰值"）；
- 集合点 = Synchronizing Timer：攒 N 线程同时释放，制造瞬时并发（秒杀开抢一刻）。副作用必须量化：等待期这些线程不产生吞吐，且 `timeout` 不设时若释放数凑不齐会永久挂住——设定超时或用分组集合点，别拿"总时长平均 TPS"解读集合点场景。

## 四、RT 的口径与分位数

聚合报告的 Average 会骗人：P50=80ms 而 P99=2.4s 的系统，均值可能"好看"但每 125 个用户就有 1 个 2 秒+。看 RT 至少 P90/P99 + Max；JMeter 5 报告里区分 **Latency**（首字节）与 **Connect**（建连）与总 Elapsed——总时长高、Latency 低=响应体大/带宽问题；Connect 高=网络或后端 accept 队列饱和（对照 [Linux 网络排查](../../linux-shell/s1/S1-2-Lesson.md)）。子请求（页面带 10 个静态资源）默认并入父样本，口径要先定：主 API 测试建议关掉嵌入式资源采样。

## 五、加压策略与结论产出

```shell
# 目的：按到达率档位阶梯执行，每档独立结果文件便于对齐膝点
jmeter -n -t flashsale.jmx -Jrate=3000 -l res_r3000.jtl -e -o rpt_r3000
# 说明：-Jrate 是传给 Open Thread Group Target Rate（每分钟到达数）的 J-property，脚本内用 ${__P(rate)} 引用
# 反例：GUI 模式挂着 View Results Tree 跑长压 ❌ ——压力机先 OOM，制造假瓶颈（上一节自证清单）
# 结果：该档 TPS 走平且 P99 陡升，则记 3000/min 为膝点候选，降档复测三次取中值
```

阶梯压测（每档持续 ≥5 分钟且丢弃 ramp 数据）定位膝点；同档位做 3 次取稳定；结论四件套：**目标 TPS 下的 P99、错误率、资源水位（CPU/连接池/GC）、拐点并发数**，并注明压力机自证清白（见上一节清单）。SLA 写"成功率 99.95% 前提下 P99<500ms 的最大 TPS"，而不是单点"支撑 X 并发"。
