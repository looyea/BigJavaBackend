# 组件模型与非 GUI 执行

> 本节难度：★★☆☆☆
> 重要程度：★★★☆☆
> 学习产出：能按"线程组→取样器→配置/定时器→断言→监听器"组装 JMeter 测试计划，掌握 CSV 参数化与提取器关联，并坚持"GUI 只用于调试、压测必须非 GUI 出报告"的执行纪律。

## 一、组件模型：一棵测试计划树

JMeter 执行模型 = 线程组模拟并发用户，每个"用户"循环跑一遍元件树：

| 元件 | 角色 | 备注 |
|------|------|------|
| 线程组 Thread Group | 并发模型：线程数/ramp-up/循环次数 | 线程≠真实浏览器，一个线程串行发请求 |
| HTTP 请求取样器 | 发一次请求并记录结果 | 名字里的"Sampler"即发起并采样耗时 |
| HTTP 请求默认值/头部管理器 | 配置：协议主机端口、Content-Type | 别在每个请求里重复写 |
| CSV 数据文件设置 Data Set Config | 参数化数据源 | 共享模式决定线程间怎么分数据 |
| 定时器（固定/高斯） | 请求间隔 | 作用域是"每线程每循环"，不是全局 QPS 控制 |
| 断言（响应/JSON） | 判对错 | 没有断言=只看 HTTP 200，业务错误全绿，是最大反例 |
| 监听器（聚合报告等） | 看结果 | 压测运行时必须全部禁用 |

## 二、非 GUI 执行与报告

```bash
# 目的：压测与看结果分离，GUI 渲染树和结果树极耗内存，正式压测必须 -n
jmeter -n -t order_load.jmx -l results.jtl \
       -e -o ./report                      # 结果：跑完自动产出 HTML 报告（含 TPS/RT 分位曲线）
# 反例：jmeter order_load.jmx 双击进 GUI 压 500 线程 → JMeter 自己先成瓶颈，测出的是"笔记本性能"
```

调优三件套：`heap=-Xms4g -Xmx4g`（改 `JVM_ARGS`）、禁用所有监听器、`jmeter.save.saveservice` 里关掉响应体保存。单机压不动就分布式（`-R host1,host2`），但要注意时序与数据文件要在各 slave 上同步。

## 三、参数化与关联

- CSV Data Set Config：`订单号.csv` 按列注入变量，共享模式选 "All threads"（即 shareAll）时所有线程共读一个游标（数据消费型），而 "Current thread" 模式每线程独立切片——"同一订单会不会被并发抢"正是由它决定：测幂等/锁冲突偏要用 shareAll 让线程抢同一批 key；
- 关联（拿响应再传下游）：JSON 提取器 `$.data.orderNo` → 下游请求用 `${orderNo}`；忘记关联是新手第一坑——下游永远 400；
- 函数助手：`${__UUID}`、`${__time(yyyyMMdd)}`、`${__P(threads,100)}`（-Jthreads 外部可调，计划零改动）。

## 四、断言与"绿"的定义

HTTP 状态码 200 不等于成功：业务约定 `{"code": 0}` 才算。响应断言匹配 `"code":0` 或 JSON 断言 `$.code == 0`；再加一条"响应时间断言"抓长尾。没有断言的报告，错误率恒为 0%，这种"全绿"比红灯更危险。
