# 与 Gatling 选型对比（关联） · 面试题

## 题 1：JMeter 和 Gatling 怎么选？给一个架构师级的答法。

- 先声明没有全赢答案，摆四问：谁维护（技能面）、压什么协议（生态面）、要多大并发（压力模型）、资产怎么养（版本化/CI）；
- 压力模型定量：JMeter 一用户一线程，数千并发舒适、数万要分布式；Gatling 异步模型单机万级——但团队没人写 Scala/Java 时该优势为零；
- 结论示例：非开发自助+冷协议 → JMeter；核心链路常态化门禁 → Gatling；大厂常见双轨共存，统一报告口径防结论打架；
- 加分：补一句"工具选错代价可控，模型/数据失真代价才致命"，把话题引向压测方法论成熟度。

## 题 2：为什么"5 万虚拟用户"对 JMeter 是难题、对 Gatling 相对轻松？

- 阻塞模型下每个"在途用户"要占一个平台线程（栈约 1MB 起）+ 连接，5 万线程的内存、调度与 GC 先把压力机压垮，测出的 RT 含工具噪音；
- Gatling 把"用户"降为状态机对象挂在全局定时器上，请求完成回调驱动推进——等待期不占线程，少量 I/O 线程撑数万连接；
- 加分：指出等价替代——JMeter 用 Open Thread Group 按到达率压 + 多机分布式，或用 wrk/k6 这类工具；"万级并发"本质是异步 I/O 问题不是品牌问题。

## 题 3：.jmx 文件被吐槽"不可维护"，具体差在哪？有什么缓解手段？

- XML 巨型树：一次元件拖动 diff 数百行；无类型检查，接口字段变更靠全局肉眼替换；复用只有 Include Module 与属性拼接，无法函数化；
- 缓解：计划拆分+参数化（-J 属性）、JSR223 脚本集中管理逻辑、jmx 版本化前用 JMeter 的"清理测试片段"瘦身、关键链路逐步 DSL 化迁移；
- 加分：对比 Gatling 的"压测即代码"享受 IDE 重构/单测/包管理——并承认代码脚本也有腐化，纪律（评审+公共库）比工具更决定资产寿命。

## 题 4：两边报告口径不一致时信谁？

- 都不直接信：导出原始样本（.jtl / Gatling request execution 数据或 batch 输出）按同一定义重算——成功定义（断言口径）、时间窗（剔除爬坡）、分位数算法必须一致；
- 常见差异源：Gatling 默认把 timeout 计为失败且分位算法/聚合窗口与 JMeter HTML 报告不同；连接复用（keep-alive）配置不一致导致 RT 差一截；
- 加分：给出流程——先压力机自证，再同环境同数据重跑对拍，最后把"口径字典"沉淀进压测平台；对不上就查口径而非先怀疑系统玄学。

## 题 5：团队只有 QA 会用 JMeter，老板问"要不要上 Gatling"，你怎么决策？

- 先量化痛点：当前是否有"单机并发不够、脚本腐化致维护事故、CI 门禁缺位"三类硬需求——没有就是伪需求；
- 试点路径：挑一条核心链路做一次 Gatling PoC（种子工程师 1 名），对照工时与产出质量，评估真实技能税；
- 组织视角：工具跟着人走——若招聘市场与团队栈以 Java 为主，Gatling Java DSL 或 k6/Java 客户端可能比 Scala 更现实；JMeter 规范化使用也可能是最优解；
- 加分：明确"双轨的长期成本"（两套造数、两套口径），给出回收条件，避免选型变成永久负债。

## 题 6：从压测平台化视角看，两者各自缺什么？

- JMeter 缺：版本化的元件抽象、原生按到达率的资源效率（高并发成本）、与代码流水线的一等公民集成（靠 Jenkins 插件凑合）；
- Gatling 开源缺：图形化面向非开发的面、协议广度、官方分布式编排（企业版收费能力）；
- 平台化实践：把"场景描述（SLA/模型/数据）"从工具中抽出成元数据，工具只是执行器，结果统一入仓做跨版本容量趋势——这才是大促平台的护城河；
- 加分：顺带提流量回放/全链路压测（影子库表）与工具选型正交，量大之后瓶颈在造数与环境同构而非发压引擎。
