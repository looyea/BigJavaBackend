# 并发模型、思考时间与 TPS/RT 解读 · 面试题

## 题 1：并发用户数、TPS、RT 三者什么关系？压测时怎么选自变量？

- Little 定律口径：TPS = 并发用户 / (RT + 思考时间)；三者知二求一，报告里必须写口径；
- 容量/SLA 验证：以到达率（TPS）为自变量——Open Thread Group/Precise Throughput 定流量，观察 RT 与错误率；摸极限：以并发为自变量火力全开，找吞吐拐点；
- 加分：指出"固定线程数模型"在 RT 恶化时 TPS 自己会掉，容易把"系统变慢"误读成"压力不够"——这是很多 JMeter 报告结论失真的源头。

## 题 2：为什么平均响应时间不可靠？你汇报时用哪些数？

- 均值对长尾不敏感：GC 停顿、锁等待、慢查询都藏在尾部，P50 80ms/P99 2.4s 的系统均值可以很"漂亮"；
- 汇报分位族 P50/P90/P99 + Max + 错误率（断言口径），并给时间窗（稳态段）；SLA 表述成"99.95% 成功率下 P99<X ms 的最大 TPS"；
- 加分：进一步谈"分位数可加性问题"——多台压力机/多接口合并不能平均 P99，要么合并原始样本重算，要么用聚合近似的工具口径说明局限。

## 题 3：思考时间该不该加？加了测不出极限怎么办？

- 面向用户体验/容量规划：必须按真实停留分布加（Uniform Random），否则高估瞬时承载、限流阈值配错；
- 摸系统极限：另开一组无思考时间的"火力全开"场景，用途是找拐点与退化形态；
- 两不混淆：报告分开命名（"日常水位验证" vs "极限容量探测"），同一组数字里混口径是最常见的解读事故；
- 加分：提到思考时间与到达率的等价性——Open Thread Group 下到达率已含"用户节奏"，无需再逐请求堆定时器。

## 题 4：集合点在什么场景用？有什么坑？

- 场景：秒杀开抢、整点批量（电费代扣/工资日）这类"同步脉冲"，验证瞬时并发下的锁、队列与限流；
- 坑：等待期无吞吐使总平均 TPS 失真；释放数凑不齐会挂线程（必须设超时）；分布式下各 slave 独立计时，"同步"只在本机内成立；
- 加分：给出分析替代法——按 1 秒粒度重算 .jtl 的瞬时 QPS 曲线，证明脉冲被集合点真实制造出来。

## 题 5：压测中错误率突增但 CPU 不高，可能的瓶颈形态列举三个？

- 等待型：线程池/连接池排队超时、DB 锁等待——RT 飙升而 CPU 空闲，用 [Arthas](../../arthas/s1/S1-1-Lesson.md) thread/trace 看 BLOCKED/WAITING 栈；
- 限流/熔断触发：网关或 Sentinel 按阈值拒绝，错误码集中且规整——查拒绝策略与阈值配置；
- 资源耗尽非 CPU 类：fd/线程数上限、临时端口耗尽、GC 停顿、磁盘 IO 饱和（iostat %util/await）；
- 加分：强调"错误样本聚类"——按错误码/消息分组再定位，比笼统错误率有效十倍。

## 题 6：怎么向业务方解释"压测说能扛 5000，线上 3000 就崩"？

- 常见根因清单：压测模型失真（无思考时间的匀速流量 vs 突发脉冲）、数据规模失真（测试库小、索引路径不同）、依赖未同构（影子下游/缓存未预热）、环境差异（实例规格/网络拓扑/版本漂移）；
- 复盘动作：把线上故障时刻的瞬时到达率、慢查询、GC 与压测数据重放对照，找出未被压测覆盖的变量；
- 机制改进：容量结论标注适用条件与置信边界，大促前做"全链路+真实流量回放"级压测（联动 [混沌演练](../../chaos/s1/S1-1-Lesson.md)）；
- 加分：主动谈"压测通过≠容量承诺"——容量是带概率与条件的陈述，把安全系数与降级预案一起交付才是完整结论。
