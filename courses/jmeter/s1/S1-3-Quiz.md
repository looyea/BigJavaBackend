# 与 Gatling 选型对比（关联） · 小测

## 一、单项选择题（每题 6 分，共 42 分）

### 1. JMeter 与 Gatling 压力模型的本质差异是？（6分）

- A. 前者支持 HTTP 后者不支持
- B. 前者一虚拟用户一平台线程阻塞式，后者少量线程+异步状态机承载海量虚拟用户
- C. 前者不能加断言
- D. 后者只能压静态页面
> 答案：B
> 解析：线程阻塞模型的并发上限受平台线程内存/切换约束；异步模型是 Gatling 单机万级并发的根源。

### 2. 需要压测 JDBC、JMS、LDAP 等协议，通常倾向选？（6分）

- A. Gatling 开源版
- B. JMeter
- C. wrk
- D. ab
> 答案：B
> 解析：JMeter 协议面广（含插件生态）是"一票通过"级优势；Gatling 开源版深但窄，非 HTTP 多要自研。

### 3. 团队把压测脚本当产品代码长期维护（PR 评审、复用抽象），哪边摩擦更小？（6分）

- A. JMeter，因为 XML 好 diff
- B. Gatling，代码 DSL 天然融入 code review 与重构工具体系
- C. 两者一样
- D. 都不可以
> 答案：B
> 解析：.jmx 的 XML diff 噪音大、无类型检查、重构靠肉眼；代码化脚本可函数化、版本化、进 CI 门禁。

### 4. "录制浏览器操作生成脚本、交给非开发测试人员维护"是谁的典型优势？（6分）

- A. Gatling
- B. JMeter
- C. k6
- D. wrk2
> 答案：B
> 解析：GUI+Recorder 让不会写代码的角色能自助维护压测资产；Gatling 需要读代码写 Scala/Java。

### 5. 要单机模拟 5 万虚拟用户匀速到达，现实的选择是？（6分）

- A. JMeter 单机开 5 万线程
- B. JMeter 多机分布式拼到达率，或换 Gatling/k6 类异步工具
- C. 放弃压测
- D. 用 GUI 长时间跑
> 答案：B
> 解析：5 万平台线程会先把压力机拖垮（内存/切换）；分布式拼压力或异步模型才是解。

### 6. 选择 JMeter 时应主动认下的"税"不包括？（6分）

- A. jmx 资产腐化需要规范约束
- B. 分布式 RMI/时钟/文件分发的运维成本
- C. 监听器误用造成的假瓶颈文化
- D. 必须付费才能出 HTML 报告
> 答案：D
> 解析：HTML 报告（-e -o）是内置能力，无需付费；其余三项是使用 JMeter 的真实治理成本。

### 7. 关于两者报告能力，正确说法是？（6分）

- A. JMeter 原生只有表格没有任何分位数
- B. Gatling 官方 HTML 报告的分位曲线与时间序列开箱质量高，JMeter 的 -e -o 报告可用但细粒度分析常靠插件/自算
- C. Gatling 无报告
- D. JMeter 报告无法在 CI 生成
> 答案：B
> 解析：两边都能在 CI 出报告；差异在默认观感与二次分析生态，重大结论两边都建议保留原始样本自行重算。

## 二、多项选择题（每题 9 分，共 18 分）

### 8. （多选）选型四问包括？（9分）

- A. 谁来写和维护脚本（技能面）
- B. 压什么协议（生态面）
- C. 要多大并发（压力模型上限）
- D. 脚本资产怎么进版本库与 CI（资产形态）
> 答案：ABCD
> 解析：四问对应课程主线：技能/协议/并发/资产，逐项打分即得结论，没有全赢工具。

### 9. （多选）哪些情形下 Gatling 的优势会"归零甚至转负"？（9分）

- A. 团队完全没有人能写/愿意写 Scala 或 Java 代码
- B. 只需要一次性手工压一个 JDBC 查询接口
- C. 需要把压测长期嵌入微服务每迭代 CI
- D. 压测使用者是只会 Postman 的运营同学
> 答案：ABD
> 解析：C 恰是 Gatling 的主场；A/D 是技能税压过工具收益，B 是协议面+一次性场景两边都不划算但要 JMeter 更快。

## 三、简答题（40 分）（每题 40 分，共 40 分）

### 10. 你负责一个 Java 电商团队的大促压测平台选型：给出 JMeter vs Gatling 的评估框架、推荐结论与迁移/共存策略。（40分）

> 参考答案：
- 要点1：四问框架打分——维护者画像（测试+开发混合）、协议清单（HTTP+Dubbo/MQ）、并发量级（峰值 3 万到达率）、资产去向（进 CI 常态化）；
- 要点2：压力模型核算：3 万虚拟用户线程模型≈数台压力机分布式，异步模型单机可承载——运维成本对比；
- 要点3：推荐常见落地：双轨——非开发维护的日常回归/接口级场景用 JMeter（GUI+录制+规范约束监听器使用），核心链路容量与 CI 门禁用 Gatling 代码化脚本；
- 要点4：统一口径：两边断言=业务码+P99 分位报告、容量结论模板一致，样本原始文件留存可重算；
- 要点5：迁移路径：把最痛的 jmx（超长 XML、复制粘贴腐化）逐个用 DSL 重写，配套公共 feeder/断言库降低门槛，招/培 1~2 名种子；
- 要点6：风险提示：工具论易被带偏成宗教战——定期回顾"结论失真事故"归因是模型/数据/环境哪头，多数与工具无关。
