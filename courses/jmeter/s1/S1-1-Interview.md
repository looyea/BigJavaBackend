# 组件模型与非 GUI 执行 · 面试题

## 题 1：JMeter 的线程模型和真实用户行为有什么差距？怎么弥补？

- 线程=串行发请求的虚拟用户：循环内"发一个、等一个"，没有浏览器的并发资源加载、JS 执行与渲染；
- 差距：真实用户点击有思考时间、浏览器会并发拉静态资源；弥补： Constant Timer/Uniform Random 模拟思考时间，Gauge/吞吐量整形控制到达率，静态资源要么不计入要么单独场景；
- 加分：由此引出"并发用户数 ≠ QPS"——QPS = 并发 / (RT + 思考时间)，Little 定律口径要说得清。

## 题 2：为什么 GUI 不能用来压测？给个机理层面的解释。

- GUI 进程同时承担：样本结果渲染（结果树在内存攒全量响应）、Swing 事件循环、统计面板刷新，这些与发压抢同一堆内存和 CPU，还会因 GC 停顿造成人为超时；
- 结果：压力机先到瓶颈，报告里的 RT 尾部与错误率混入工具自身噪音——测的是笔记本不是系统；
- 加分：给出标准姿势——`-n` + `-l jtl` + `-e -o` 事后出报告；监听器在运行版计划里全部禁用；堆配 4G 并开 GC 日志自证。

## 题 3：聚合报告里的"错误率 0%"为什么可能比红灯更危险？

- JMeter 默认按 HTTP 层判成功：网关返回 200 + 业务错误码（code=50001）在它眼里全是"对"；
- 必须显式挂断言（响应/JSON/SHA256 等）把业务语义纳入成功定义，再加超时断言防"慢成功"；
- 加分：讲一次真实教训——压测全绿上线后才发现降级开关一直在返回 200 空数据；提出"断言即需求"的评审纪律：报告错误率必须与业务码口径一致。

## 题 4：CSV Data Set Config 的共享模式怎么选？

- "All threads"（shareAll）：全线程共享一个游标，配合 recycle 可让数据被反复争抢——幂等、锁冲突、热点 key 场景；
- "Current thread group/thread"：线程各自切片或独立游标，互不重叠——常规链路压测避免数据互踩；
- 文件读完的行为（recycle/stop/thread 结束）要与循环次数一起算，否则出现"后段线程拿不到参数"的隐性降速；
- 加分：数据准备工程化——造数脚本+幂等消费标记，大文件用内存映射前先估算行吞吐是否撑得住目标 TPS。

## 题 5：TPS 加压后进入平台期，你怎么排查"瓶颈到底在谁"？

- 第一问永远是压力机自证：JMeter 主机 CPU>85%、GC 长停顿、fd/临时端口耗尽、TIME_WAIT 堆积——任一命中则先扩压力机或分布式；
- 再看被测侧分层定位：入口 nginx 连接数 → 应用线程池/队列 → DB 慢查询与锁 → 下游依赖 RT；对照 [Arthas 方法级观测](../../arthas/s1/S1-1-Lesson.md) 找代码级热点；
- 判据形态：服务端 CPU 空闲但 RT 高=等待型瓶颈（锁/IO/线程池排队）；服务端 CPU 打满+RT 稳=算力瓶颈，平台期是真实容量上限；
- 加分：给出"TPS=并发/(RT+思考时间)"的核算——平台期也可能是并发给不够而非系统饱和。

## 题 6：JMeter 分布式压测的原理与坑？

- RMI 控制模型：master 调度，slave 各自发压并把样本回传 master 汇总（也可各 slave 独立 -l 再合并 jtl，更稳）；
- 坑：slave 间时钟不同步使 TPS 曲线毛刺、csv/插件/jar 必须逐机分发、rmi 端口被防火墙挡、master 汇总成为新瓶颈；
- 实践：更推荐"多机各跑一份计划、结果事后合并"（jtl 合并再出报告），或直接上云压测平台编排；
- 加分：能对比 Gatling 集群方案与云端施压（按量计费的到达率控制），说明为什么"单机 2000 线程"通常不如"4 机各 500"。
