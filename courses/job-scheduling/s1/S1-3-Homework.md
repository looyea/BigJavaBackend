# 调度高可用、可视化与生态对比（关联） · 作业

### 作业 1：搭一个高可用调度并验证不重复触发

- 目标：验证调度器多节点不会把同一触发跑两次。
- 任务：部署 XXL-Job 调度中心两个实例（共用同一 DB），注册两个执行器，跑一个会打印"执行次数"的任务； kill 其中一个调度节点，观察任务仍被触发且不多跑。或用 Quartz clustered（JDBC JobStore）复现。
- 验收标准：调度节点有宕机时任务照常触发、不重复执行；能说清 DB 抢锁/集群模式的防重原理。
- 参考解法要点：调度中心靠 DB 行锁抢占；对比单点调度宕机=任务全停的风险。

### 作业 2：misfire 补偿策略对照实验

- 目标：直观感受"错过触发"不同策略的行为差异。
- 任务：用 Quartz 建一个每 10 秒触发的 CronTrigger，人为阻塞调度线程使其错过若干触发点；分别配 `FireAndProceed` 与 `DoNothing`，记录恢复后是"立即补跑一次"还是"直接等下一次"。
- 验收标准：能展示两种策略在错过后的不同表现，并给出"日切选补跑、清理选跳过"的结论依据。
- 参考解法要点：misfire 判定依赖 `misfireThreshold`；策略选错会漏跑关键批处理。

### 作业 3：分片广播下的任务幂等

- 目标：验证失效转移/重跑同一分片不产生重复副作用。
- 任务：写一个分片广播任务，按 `shardIndex` 处理对应数据分片；在其中一片里用"业务键去重 + upsert"保证幂等；手动重跑或模拟执行器宕机触发重分配，验证同一分片重复执行不重复处理。
- 验收标准：同一分片被重复触发时，最终结果与只跑一次一致；能说明为何分片/HA 场景必须幂等。
- 参考解法要点：幂等键=业务唯一标识（如订单号分片）；配合失败重试与报警形成不漏不重闭环。
