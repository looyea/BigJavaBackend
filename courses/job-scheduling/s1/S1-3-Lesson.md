# 调度高可用、可视化与生态对比（关联）

> 本节难度：★★★☆☆
> 本节重要性：★★★★☆
> 学习产出：能把分布式定时任务平台的关键工程问题——**调度高可用、错过触发补偿、任务依赖与可视化运维、框架选型**——串成一张决策图。首要原则是把**调度器（决定"何时触发"）与执行器（真正干活）解耦、各自做 HA**：调度器若是单点，一旦宕机全站任务停摆，所以 XXL-Job 的调度中心要多节点集群（靠 DB 行锁抢占避免重复调度），ElasticJob 靠注册中心（ZooKeeper）协调、无中心调度单点，Quartz 用 JDBC 存储 + clustered 模式让多实例抢同一触发锁。第二是 **misfire（错过触发）处理**：当该触发时调度线程被长任务占满、或调度器停机错过时间点，恢复后要"立即补跑"还是"跳过等下次"——Quartz 用 `withMisfireHandlingInstructionFireAndProceed`/`DoNothing`/`IgnoreMisfires` 显式声明，日切/对账这类"必须执行"的选补跑，纯清理类可跳过。第三是**任务依赖 DAG 与可视化运维**：复杂批处理常有先后依赖（A 完成才跑 B），要靠子任务/工作流表达；企业更需要控制台看执行历史、失败重试、报警、动态改 Cron、GLUE 在线改脚本、按**分片广播**把大任务拆到多执行器并行。选型：**Quartz** 嵌入式、轻量、无强可视化、集群靠 DB；**XXL-Job** 中心化控制台 + 路由策略（第一个/轮询/随机/一致性哈希/故障转移/忙碌转移）+ 报警 + 生态成熟，适合统一运维；**ElasticJob** 强分片弹性、失效转移、去中心靠 ZK。识破"调度中心没集群成单点""misfire 策略缺省导致大促错过补偿""所有执行器下线仍触发报无可用执行器""分片广播没幂等重复跑"等坑——电力巡检工单生成、电商定时结算、金融日切批处理都吃这套。

## 一、调度器与执行器分别做 HA

```java
// 目的：用 Quartz CronTrigger 显式声明"错过触发点"后的补偿策略, 别用默认含糊行为
CronTrigger trigger = newTrigger()
    .withSchedule(cronScheduleBuilder()
        .withMisfireHandlingInstructionFireAndProceed()) // 结果：错过则立即补跑一次再继续(适合必须执行的日切/对账)
    .build();                                            // 说明：另有 DoNothing(跳过等下次)/Ignore 策略, 语义按业务选
// 反例：调度线程池太小 + 长任务占满 → 后续触发点全部 misfire ❌ 未配策略时按默认可能整批错过 ❌
```

## 二、错过触发、失败与重复的治理

```text
图目的：分布式调度三大"异常时刻"的处理抓手
misfire(错过触发点): 显式声明补偿——必须跑的(FireAndProceed 补一次) vs 可跳过的(DoNothing 等下次)
failover(执行失败): 路由策略"故障转移/忙碌转移"把任务改派到其它执行器; 配失败重试与报警
重复触发(多调度节点抢锁失败/网络分区): 靠 DB 抢占锁或注册中心协调保证同一触发只跑一次
分片广播: 大任务按 shardIndex 拆到多实例并行 → 每片必须幂等, 否则重分配就重复处理
```

## 三、可视化运维与依赖

```text
图目的：企业选调度平台, 一半是在选"运维面板"
控制台看: 执行历史/耗时/成败、失败自动重试与人工重试、报警(邮件/钉钉/企微)

```

## 四、选型与底线

- **调度器不留单点**：XXL-Job 调度中心至少 2 节点、Quartz 开 clustered、ElasticJob 保证 ZK 可用。
- **misfire 策略显式化**：按"必须补跑还是可跳过"选，绝不依赖含糊默认值，大促/日切尤其重要。
- **执行层幂等兜底**：分片/失效转移/重跑都可能造成重复，任务本身要幂等（承接分片幂等设计）。
