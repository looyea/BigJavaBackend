# 跨技术联动：秒杀全链路 · 小测

## 一、单项选择题（每题 6 分，共 42 分）

### 1. 秒杀分层链路的首要目的是？（6分）

- A. 代码解耦好看
- B. 逐层削峰，把打到 DB 的量压到库存可控量级
- C. 增加延迟
- D. 提高一致性协议复杂度
> 答案：B
> 解析：接入限流→Redis 预扣→MQ 排队→DB 兜底，是一层比一层窄的流量漏斗，保护最脆弱的 DB。

### 2. Redis 预扣库存为什么必须用 Lua/原子命令而非"先读再扣"？（6分）

- A. Lua 更快
- B. check-then-set 两步有竞态，并发下都读到>0 各扣导致超卖
- C. 省内存
- D. Redis 不支持 get
> 答案：B
> 解析：把"判断+扣减"合成一个原子操作（Lua/单命令），消除读后写之间的窗口，杜绝超卖。

### 3. DB 兜底扣减防超卖的关键写法是？（6分）

- A. 先 SELECT 判断再 UPDATE
- B. `UPDATE stock SET qty=qty-1 WHERE item_id=? AND qty>0`
- C. 应用层加锁
- D. 删行重插
> 答案：B
> 解析：把边界判断交给数据库的原子 UPDATE，影响行数为 0 即售罄，天然防负库存；A 仍是有锁前的竞态。

### 4. 防止"重复下单/重复扣款"最贴合 DB 层的手段是？（6分）

- A. 前端按钮置灰
- B. (user_id,item_id,activity_id) 唯一索引 + 幂等消费
- C. 加缓存
- D. 提高 QPS
> 答案：B
> 解析：唯一约束让重复提交/重复消费在 DB 层被拒；配合消费幂等（去重表/状态机）形成双保险。

### 5. 库存单 key 成为热点，最有效的分散手段是？（6分）

- A. 加大 Redis 内存
- B. 库存分桶，把总量拆到多个子 key/行分散争抢
- C. 单实例串行处理
- D. 关闭预扣
> 答案：B
> 解析：分桶把一个热 key 拆成 N 个，请求打散到不同分片/行，降低单点排队与争抢。

### 6. MQ 在秒杀链路中的角色是？（6分）

- A. 存储库存
- B. 把"抢资格"与"创建订单"解耦，削峰填谷
- C. 做限流
- D. 做鉴权
> 答案：B
> 解析：预扣即快速判定资格，真实下单经 MQ 缓冲成平稳流，避免创建订单的重操作冲击 DB。

### 7. 活动结束或下单超时未支付，必须做什么以免"少卖"？（6分）

- A. 什么都不做
- B. 回补 Redis 桶库存并释放占用
- C. 直接删订单
- D. 冻结用户
> 答案：B
> 解析：预扣了却没最终成交的库存要回补，否则可售量被虚假占用导致少卖。

## 二、多项选择题（每题 9 分，共 18 分）

### 8. 秒杀接入/网关层通常承担哪些削峰防护？（多选）（9分）

- A. 按用户/设备维度限流
- B. 请求签名 + 时间戳防重放刷单
- C. 黑名单/风控拦截
- D. 直接扣减并落订单
> 答案：A、B、C
> 解析：接入层只做拦截与削量；扣减落单是下游 DB/服务职责（D 错），否则等于没分层保护。

### 9. 关于秒杀链路的故障降级，正确的有？（多选）（9分）

- A. Redis 挂可降级为 DB 小流量限流扣减，绝不放量直打
- B. MQ 挂时预扣要么可回滚要么落本地待重投，不丢资格
- C. 任一异常都遵循"宁可拒绝不可超卖"的安全失败
- D. DB 抖动时应加大并发冲过去
> 答案：A、B、C
> 解析：D 反了，DB 抖动要熔断/排队/拒绝来保护它，加大并发只会压垮，引发雪崩。

## 三、简答题（共 40 分）

### 10. 简答题：设计一条秒杀全链路，说明网关、Redis、MQ、DB 各自职责，并解释如何同时防"超卖"和"重复下单"，以及某一层故障时怎么降级。（40分）

> 参考答案：
- 要点1：漏斗分层——网关限流/签名/黑名单削无效流量；Redis 原子预扣判资格；MQ 削峰异步下单；DB 最终强一致扣减落单。（12分）
- 要点2：防超卖——Redis 用 Lua 原子"读-判-扣"，DB 用 `WHERE qty>0` 原子 UPDATE，影响行数 0 即售罄。（12分）
- 要点3：防重复——订单唯一索引 + 消费幂等（去重表/状态机），重复提交/重投被拦下。（8分）
- 要点4：降级——Redis/MQ/DB 任一失效都有安全落点，统一遵循"宁可拒绝不可超卖"，异常安全失败并回补库存。（8分）
