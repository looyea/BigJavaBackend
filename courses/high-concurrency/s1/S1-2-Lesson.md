# 跨技术联动：秒杀全链路

> 本节难度：★★★★★
> 本节重要性：★★★★★
> 学习产出：能把上一节的三大原则组合成一条可落地的秒杀全链路——**网关限流 → 库存 Redis 预扣 → MQ 异步下单 → DB 兜底扣减**，讲清每一层拦截什么、为什么这样分层；掌握"超卖/少卖"的成因与用原子操作 + 唯一约束 + 幂等消费防治；理解热点库存分桶、前端/接入层削峰、请求签名防刷在秒杀里的配合作用；能对整个链路做容量与故障推演（某层挂了会怎样、如何优雅降级），识破"直接打到 DB 扣库存""check-then-set 扣减导致超卖"等致命错误。

## 一、为什么必须分层：一条流量漏斗

```text
图目的：把百万请求逐层削到 DB 只承接可售库存量级
接入/网关：挡掉超量与恶意——限流、签名校验、黑名单，先削掉 80%+ 无效流量
应用/缓存：Redis 原子预扣库存，瞬间判定"有没有"，售罄即快速失败不再下探
MQ：抢到资格的真实请求排队成平稳下单流，削峰填谷
DB：只做最终、强一致的扣减与订单落库，量级已被压到可控
```

## 二、库存扣减：超卖是红线

```java
// 目的：Redis 预扣必须是原子的"判断+扣减"，杜绝 check-then-set 竞态
Long left = redis.eval(DECR_IF_POSITIVE_LUA, keys("stock:item:1001"), args(1)); // 结果：Lua 内"读-判-扣"单命令原子
if (left != null && left >= 0) { mq.send(new OrderMsg(userId, itemId)); }        // 说明：抢到资格才投递下单
// 反例：if(get(stock)>0){ decr(stock) } 两步 ❌ 高并发下两个线程都读到>0 各自扣，超卖
// 反例：预扣成功但下单消息重复投递、消费不幂等 ❌ 同一人重复扣款/重复生成订单
```

```java
// 目的：DB 兜底扣减用带条件的原子 UPDATE + 唯一约束，双保险防超卖防重复
// SQL: UPDATE stock SET qty = qty - 1 WHERE item_id=? AND qty > 0;  （结果：影响行数=0 即已售罄，无超卖）
// 订单表 (user_id, item_id, activity_id) 唯一索引 → 重复消费/重复提交被约束拦下
int rows = mapper.deduct(itemId);                        // 说明：靠 WHERE qty>0 让数据库自己判边界
if (rows == 0) { /* 售罄或重复，安全返回，不产生负库存 */ }
```

## 三、热点治理：把一把锁拆成多把

```text
图目的：单 key 库存是热点，所有请求争抢同一分片/行
库存分桶：把 1000 件拆成 N 个子桶(各 100)，请求分散到不同桶键/行，降单点争抢
某桶售罄只做本桶失败或跨桶再分配，别让用户都撞在同一 key 上排队
配套：本地缓存活动配置、限流按用户/设备维度、请求带签名与时间戳防重放刷单
```

## 四、异步下单与幂等消费

```text
图目的：MQ 把"抢资格"和"慢慢创建订单"解耦
预扣成功→发消息→消费者创建订单并 DB 扣减；消费必须幂等（唯一约束/去重表/状态机）
活动结束或超时未支付→回补 Redis 桶库存与释放，避免"少卖"与占坑
最终一致：允许短暂"已扣未成单"，用补偿/对账收敛，不用分布式强事务拖垮吞吐
```

## 五、全链路故障与降级推演

```text
图目的：每层失效都要有安全落点，宁可拒绝不可超卖
Redis 挂：快速失败或降级到 DB 限流小流量扣减，绝不放量直打 DB
MQ 挂：预扣但暂时无法下单→要么回滚预扣、要么落本地待恢复重投，不可丢资格
DB 抖动：扣减 RT 飙升→上游熔断、排队、拒绝，保护 DB 不被压垮
兜底原则：售罄/异常一律"安全失败"，用唯一约束与原子 UPDATE 兜住正确性
```
