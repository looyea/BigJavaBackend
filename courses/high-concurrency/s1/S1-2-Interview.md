# 跨技术联动：秒杀全链路 · 面试题

## 题 1：秒杀为什么要分层？请求进来后各层分别拦什么？

- 分层是流量漏斗：越往下越贵，逐层把百万请求削到 DB 可承受量级。
- 接入/网关限流+签名+黑名单削无效与恶意；Redis 原子预扣判资格、售罄即快速失败；MQ 把抢中者缓冲成平稳下单流；DB 做最终强一致扣减落单。
- 加分：能画出"每层拦掉多少"的量级递减，说明设计的核心是保护最脆弱的 DB。

## 题 2：超卖是怎么发生的？Redis 和 DB 分别怎么防？

- 根因是"读判断+扣减"两步之间存在并发窗口（check-then-set），两个线程都读到有货各扣一次。
- Redis 用 Lua/原子命令把"读-判-扣"合成一步；DB 用 `UPDATE ... SET qty=qty-1 WHERE qty>0` 让数据库原子判边界，影响行数 0 即售罄。
- 加分：强调"宁可拒绝不可超卖"，两层都原子形成双保险，任一层单独都不够稳。

## 题 3：如何防止同一用户重复下单/重复扣款？

- 给订单表建 `(user_id,item_id,activity_id)` 唯一索引，重复提交被 DB 约束拒绝。
- MQ 消费做幂等：唯一约束/去重表/状态机，重复投递只生效一次；捕获唯一冲突按"已成功"处理。
- 加分：区分"防超卖（库存边界）"与"防重复（幂等键）"是两件事，秒杀要同时做对。

## 题 4：库存只有一个 Redis key 会成为什么问题？怎么解？

- 单 key 是热点，所有请求争抢同一分片，形成排队与 CPU 瓶颈，压不上去。
- 库存分桶：把总量拆成 N 个子 key/子行，请求打散到不同分片降低争抢；某桶售罄做本桶失败或跨桶再分配。
- 加分：能提"分桶后回补/对账要跨桶汇总"，说明分桶带来的新一致性维护点。

## 题 5：MQ 挂了，预扣了库存但下不了单，怎么办？

- 不能让资格凭空消失：要么设计成可回滚（超时未成单则 INCR 回补桶库存），要么把消息落本地/备用缓冲待恢复重投。
- 关键是预扣只是"占资格"，最终以 DB 扣减为准，用超时回补+对账收敛"已扣未成单"。
- 加分：点出"少卖"同样是事故，回补机制保证可售量不被虚假占用，兼顾最终一致。

## 题 6：整条链路你如何做容量与降级预案？

- 按峰值 QPS 用 Little 定律估各层并发/实例/池；每层设限流阈值与降级开关。
- 故障落点：Redis 挂→小流量放 DB 或拒绝；DB 抖→上游熔断/排队；全程安全失败并可回补，绝不放量直打脆弱层。
- 加分：强调降级是事前演练的预案（开关平台一键切换）而非临场发挥，并解释为什么秒杀常牺牲强一致换吞吐。
