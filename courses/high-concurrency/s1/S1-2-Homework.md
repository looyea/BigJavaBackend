# 跨技术联动：秒杀全链路 · 作业

## 作业 1：搭一条"预扣→异步下单→DB 兜底"最小链路

- 目标：把分层漏斗实现出来。
- 任务：网关用限流放行；Redis 用 Lua 脚本原子预扣库存（读到>0 才扣，返回剩余）；预扣成功投递 MQ；消费者创建订单并执行 `UPDATE stock SET qty=qty-1 WHERE item_id=? AND qty>0`，影响行数 0 时判定售罄/重复并不产生负库存。
- 验收标准：并发压测下不超卖（总扣减=初始库存）、DB 无负库存；预扣与最终扣减一致；售罄后快速失败不再下探 DB。
- 参考解法要点：Redis 与 DB 各自原子，别用两步 check-then-set；分层把量削到 DB 可承受。

## 作业 2：验证防重复下单的幂等

- 目标：同一用户重复提交/消息重复消费只成交一次。
- 任务：给订单表加 `(user_id, item_id, activity_id)` 唯一索引；消费者用幂等（唯一约束捕获冲突 / 去重表 / 状态机）；构造"前端重复点击 + MQ 重复投递"用例，断言只生成一笔有效订单、库存只扣一次。
- 验收标准：重复请求被约束或幂等逻辑拦下、不产生重复订单/重复扣款；能区分"防超卖"（库存边界）与"防重复"（幂等键）两件事。
- 参考解法要点：幂等要有唯一业务键；捕获唯一冲突按"成功（已存在）"处理而非报错回滚。

## 作业 3：做一次链路故障演练与降级设计

- 目标：给每层失效准备安全落点。
- 任务：分别模拟 Redis 不可用、MQ 堆积/宕、DB 扣减 RT 飙升三种故障，设计并验证降级：Redis 挂→小流量限流放 DB 或直接拒绝；MQ 挂→预扣可回滚或落本地待重投、不丢资格；DB 抖→上游熔断/排队/拒绝；全程坚守"宁可拒绝不可超卖"，并对未成交预扣做超时回补。
- 验收标准：三种故障下都不出现超卖与丢资格；有明确的回补/对账路径收敛"少卖"；给出降级开关与恢复步骤。
- 参考解法要点：降级是预案不是临场发挥；用开关平台一键切换，事后对账兜最终一致。
