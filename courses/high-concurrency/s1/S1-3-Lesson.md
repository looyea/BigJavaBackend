# 接入层限流、削峰与流量整形

> 本节难度：★★★★☆
> 本节重要性：★★★★★
> 学习产出：能把"高并发第一道闸门"建在**接入层**——在流量进入业务之前就完成**限流、削峰、整形**，保护后端。掌握四大限流算法的取舍：**固定窗口**（实现简单但有临界突刺）、**滑动窗口**（平滑但仍计数量）、**漏桶**（恒定速率流出、强行整形、不容突发）、**令牌桶**（允许一定突发、最贴合真实流量）；理解**分层限流**（LB/网关/应用/接口/用户多维，全局 vs 单机、集群限流用 Redis/Token Server 协调配额）与**削峰**（MQ 异步缓冲 + 请求排队/快速失败）如何配合；用**流量整形**（预热 warm-up、排队等待）平滑冷启动与抖动。关键取舍：限流阈值来自容量压测（承接下一节），宁可**快速失败 + 友好降级**也别把后端拖垮；防**热 Key/单用户刷爆**用参数级/用户级细粒度限流。识破"固定窗口临界翻倍""只限总量不限单用户""限流阈值拍脑袋""削峰队列无上限反而 OOM"等坑。

## 一、四大限流算法的取舍

```text
图目的：选算法=选"如何对待突发", 各有适用面
固定窗口: 计数超阈即拒; 实现最简, 但窗口交界处可达 2× 阈值(临界突刺)
滑动窗口: 细分小格滚动统计, 平滑临界; 仍是"计数量"思路
漏桶:     请求进桶恒定速率流出, 强行整形、绝不容突发, 适合保护极脆弱下游
令牌桶:   按速率放令牌、桶容量允许有限突发, 最贴合真实互联网流量, 最常用
```

```java
// 目的：令牌桶允许突发又控平均速率, 是网关/应用入口默认选择
boolean allow = rateLimiter.tryAcquire(1, waitMs);   // 说明：拿不到令牌则等待 waitMs 或直接拒绝(快速失败)
if (!allow) return degraded(req);                     // 结果：超配额请求走降级/友好提示, 绝不放穿后端
// 反例：用固定窗口且窗口=1 分钟 ❌ 交界两个窗口各放满, 实际瞬时可达 2 倍阈值
// 反例：漏桶放在面向用户主链路 ❌ 恒定速率无法吸收正常突发, 高并发点直接大面积超时
```

## 二、分层与集群限流

```text
图目的：不同层限不同维度, 单机配额扛不住整体, 需全局协调
维度：全局 QPS / 单接口 / 单用户 / 单参数(热点) / 单 IP
单机限流: 每个实例各限一份, 简单但整体=实例数×单机, 扩缩容即漂移
集群限流: 用 Redis 计数或 Sentinel Token Server 统一发配额, 全局精确但依赖中心
```

- **热点与单用户**：只限"总量"会被单个用户/单个热点商品刷光全部配额；对秒杀要叠加**参数级限流**（同一 sku）与**用户级限流**（同一 uid 频次），配合黑名单。

## 三、削峰与快速失败

```text
图目的：入口挡不住的用队列缓冲, 但队列要有界且能丢弃
同步链路扛不住: 把写请求投 MQ, 下游按消费能力匀速处理(削峰填谷)
前端/接口层: 排队令牌、验证码、答题、错峰, 把瞬时洪峰摊平到时间轴
底线: 超过阈值的请求要么排队要么快速失败, 绝不能无限堆积拖垮接入层
```

- **有界队列**：削峰用 MQ/内存队列必须设容量与丢弃/降级策略，否则"削峰"变成"积压到 OOM"。

## 四、坑与底线

- **阈值来自压测不来自直觉**：限流值应由单机与集群容量压测得出（见容量规划一节），拍脑袋定要么误杀要么形同虚设。
- **限流要与熔断/降级成套**：被限/被熔断的请求要有兜底响应（缓存快照、友好提示、排队页），用户体验与系统保护并举。
