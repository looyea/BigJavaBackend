# 高并发三大原则与容量模型

> 本节难度：★★★★☆
> 重要程度：★★★★★
> 学习产出：能背出并落地高并发三大原则——**无状态化、缓存、异步化**，说明每一条分别在扩展性、延迟、吞吐上解决什么瓶颈；用 **Little 定律**（L = λ × W）从到达率与耗时推导所需并发/连接/容量，建立"以 TPS 和 RT 为轴"的容量模型；理解从接入到存储的**分层削峰与水平扩展**总纲，并能对一个接口做量级测算（要多少实例、多少连接、扛多少 QPS），识破"有状态导致无法水平扩""同步串行链路拖垮 RT""无预算拍脑袋扩容"三类问题。

## 一、三大原则各解决什么

```text
图目的：三条原则对应三个不同瓶颈，不是同义反复
无状态化：任何实例都能处理任何请求 → 可水平扩展、无需会话粘滞、扩容即加机器
缓存：把读从昂贵后端前移到内存/近端 → 降 RT、降后端压力（读多写少的命脉）
异步化：把非关键路径移出请求主链路 → 提升吞吐、削峰、解耦（写/通知/风控后置）
一句话：无状态决定"能不能扩"，缓存决定"读扛不扛得住"，异步决定"峰值会不会把自己打垮"
```

## 二、Little 定律：容量推导的底层公式

```text
图目的：系统稳态下"在架数量 = 到达率 × 停留时间"
L = λ × W   L=系统内平均并发/在架请求数，λ=到达率(QPS)，W=平均处理时间(RT)
推论：要支撑 λ=1000 QPS、RT=200ms，则稳态并发 L=1000×0.2=200 个同时在处理
→ 每个实例若只能并行 50（线程数/连接数），就至少需 200/50=4 实例（再留冗余）
同一公式可用于线程池大小、连接池上限、队列容量、库存周转的测算
```

```java
// 目的：用 Little 定律反推线程池/连接池规模（估算非精确，需压测校准）
int qps = 1000; double rtSeconds = 0.2;
int concurrent = (int) Math.ceil(qps * rtSeconds);   // 结果：≈200 并发同时在处理
int pool = concurrent;                               // 说明：工作线程数≈并发需求，再叠加 IO 等待修正
// 反例：线程池开 10000"越大越能扛" ❌ 上下文切换与 DB 连接被打爆，RT 反升、雪崩更早来
// 反例：不看 RT 只按 QPS 拍容量 ❌ RT 一抖，L 暴涨，连接/线程瞬间耗尽
```

## 三、以 TPS × RT 为轴的容量模型

```text
图目的：容量规划的两个观测量，缺一即失真
TPS/QPS：单位能处理多少请求（吞吐）
RT（响应时间）：每请求多慢，且看 P99 而非均值（尾延迟才是杀手）
容量 = 单机有效吞吐 × 实例数；健康线要同时看 TPS 达标下 RT 是否劣化（拐点即容量上限）
冗余预算：按峰值 ×(1+安全水位) 定容，并预留故障时其余实例的接管余量
```

## 四、分层削峰与水平扩展总纲

```text
图目的：从接入到存储逐层消化流量，越往下越贵越要保护
接入层：DNS/CDN 分流、静态资源卸载、网关限流熔断
应用层：无状态 + 水平扩容，线程池/连接池隔离，本地+分布式缓存
中间层：MQ 异步削峰填谷，把突发写缓冲成平稳消费
存储层：读写分离、分库分表、缓存兜底、DB 只承接必要的强一致读写
```
