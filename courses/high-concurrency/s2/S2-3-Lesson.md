# 容量规划、压测与线性扩展验证

> 本节难度：★★★★☆
> 本节重要性：★★★★★
> 学习产出：能把"扛不扛得住"从玄学变成**可计算、可验证、可回归**的工程——先由业务指标（日活/峰值 QPS、读写比、单请求资源消耗）**反推容量**（用 Little 定律 `并发数 = QPS × 平均 RT` 估线程/连接，按 CPU、内存、IO、下游 DB 连接数逐项折算并预留安全水位）；再用**压测**验证：区分基准/负载/压力/稳定性/容量测试，关注 **TPS、RT 分位（P50/P99/P999）、错误率、资源饱和点**，找"吞吐拐点"和第一个瓶颈；大促场景做**全链路压测**（影子库/影子表 + 流量染色 + Mock 第三方）在不污染真实数据下演练真实链路；最后做**线性扩展验证**——加实例后吞吐是否近似线性、拐点是否随瓶颈层（往往是 DB / 锁 / 单点）迁移，识别"加机器也不涨"的假扩展。识破"只测平均不测 P99""压测环境和生产差异大导致结论失真""影子流量写进真实表造成资损""把连接池上限当容量却忽略 DB 侧上限"等坑。

## 一、从目标反推容量

```text
图目的：容量是算出来的, 不是玄学
业务量 → 峰值 QPS(平时×大促倍数) → 单请求资源(CPU ms / DB 连接 / 带宽)
Little 定律: 所需并发/线程 ≈ 目标 QPS × 平均 RT(秒)
逐层折算 + 预留 30%~50% 水位; 短板决定整体(木桶): CPU/内存/IO/连接/下游
```

```java
// 目的：用 Little 定律粗估线程池/连接规模, 再让压测去证伪
int qps = 8000; double rtSec = 0.05;                       // 说明：目标 8000 QPS、平均 RT 50ms
int needConcurrency = (int) Math.ceil(qps * rtSec);        // 结果：稳态约需 400 并发, 据此配 Tomcat/连接池下限
// 反例：把应用线程池开到 400 却没核对 DB 连接上限 ❌ 请求全卡在获取连接, 应用能收却打不穿 DB
// 反例：按 CPU 核数线性推算 TPS 却不做压测 ❌ 真实拐点常在锁/IO/下游, 推算严重偏乐观
```

## 二、压测：测什么、怎么看

```text
图目的：看分布与拐点, 不看平均值
测试类型: 基准(单接口) / 负载(递增找容量) / 压力(推到崩) / 稳定性(长时间) / 容量(最大承载)
核心指标: TPS + RT 分位(P50/P99/P999) + 错误率 + CPU/内存/GC/IO/连接水位
判读: 随并发上升 TPS 先增后平再降的"拐点"即容量; P99 骤升说明排队/锁竞争
```

- **只看平均 RT 会骗人**：大促体验由长尾决定，必须盯 P99/P999；平均没变而 P99 飙升往往是 GC、锁或线程池排队。

## 三、全链路压测（影子机制）

```text
图目的：在生产演练真实洪峰, 但绝不污染真实数据
流量染色: 压测请求打标记(tag), 全链路透传
影子存储: 命中 tag 写影子库/影子表; 缓存走影子 key; 第三方用 Mock/挡板
闭环: 影子数据可整体清理, 压测结束后不留真实账
```

- **资损红线**：金融/库存链路若染色遗漏，压测流量写进真实表就是事故；上线前必须验证"影子隔离全链路无死角"。

## 四、线性扩展验证与瓶颈回收

```text
图目的：验证"加机器是否真的加吞吐", 定位假扩展
1 实例→N 实例 TPS 应近似线性; 增幅递减处 = 共享瓶颈(DB 写/全局锁/单点/带宽)
瓶颈常在数据层: 分库分表/读写分离/热点分桶后, 再看应用与下游是否解封
```
