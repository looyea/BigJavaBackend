# 热点治理与读写分离 · 面试题

## 题 1：什么是热点？它和"整体高并发"有什么本质区别？

- 热点是海量请求集中在单 Key/单行/单账户这类无法再分的点上，而非系统总量超限。
- 后果是单 Redis 分片网卡饱和、单行锁串行导致 TPS 被锁死，而其余节点/资源却很空闲。
- 加分：能区分读热点（热 Key）、写热点（热行/热账户），并指出"加机器扩副本对单点热点无效"。

## 题 2：一个爆款商品详情把单个 Redis 分片打满了，你怎么治理？

- 先探测确认是热 Key，再上本地缓存(Caffeine)作 L1 承接最热访问，减 Redis 网络往返。
- 动静分离：可静态化的部分推 CDN，把读从服务端彻底剥走。
- 终极手段：把热 Key 打散成多个子 Key 分布到不同分片，读时聚合。
- 加分：提到热 Key 探测方案（客户端统计 / Redis 4.0+ hotkey / 抓包分析）与打散带来的一致性代价。

## 题 3：缓存击穿、雪崩、穿透分别是什么，怎么防？

- 穿透：查根本不存在的 Key，每次都打 DB → 空值缓存 + 布隆过滤器。
- 击穿：单个热 Key 过期瞬间被并发打到 DB → 互斥重建 或 逻辑过期/永不过期+后台刷新。
- 雪崩：大批 Key 同刻过期或 Redis 整体宕机 → 过期时间加随机抖动打散 + 多级缓存 + 限流降级。
- 加分：点明三者本质都是"请求绕过缓存落到 DB"，只是触发条件不同。

## 题 4：秒杀单 SKU 库存行被高频 update，TPS 上不去，怎么办？

- 这是写热点（热行），加从库无用，因为写只发生在主库单行。
- 拆分：把一个库存行拆成 N 个子桶，请求按规则路由到不同桶分摊行锁争抢，Redis Lua 原子预扣。
- 合并：对热点账户类场景，本地累加后按阈值合并成一笔批量更新，把单行 update 降频。
- 加分：说明分桶后"跨桶不足"的回捞/汇总逻辑，以及宁可拒绝不可超卖的兜底。

## 题 5：读写分离会带来什么问题？"下单成功却查不到订单"怎么解？

- 根因是主从异步复制延迟，写主后立读从读到旧值（读不到自己的写）。
- 对策：写后一段时间强制读主（会话一致性）、关键读走主、或写后回填最新值到缓存遮蔽延迟。
- 也可基于 GTID 等待从库追平指定位置再读。
- 加分：区分"会话一致性/单调读"与全局强一致的成本，说明哪些路径值得走主、哪些可容忍从库延迟。

## 题 6：缓存和数据库怎么保证一致？直接双写行不行？

- 基础范式是 Cache-Aside：读时未命中回源并回填，写时更新 DB 后删除缓存（而非直接写缓存）。
- 直接双写、先更 DB 再删缓存之间存在并发读回填旧值窗口 → 延迟双删 或 订阅 binlog(CDC) 异步失效收敛。
- 强一致代价高，多数高并发场景只追求最终一致 + 短 TTL 兜底。
- 加分：能分析"删缓存失败""binlog 乱序"等边角，并给出重试/版本号/时间戳比较的应对。
