# 热点治理与读写分离

> 本节难度：★★★★★
> 重要程度：★★★★★
> 学习产出：能识别高并发系统的"热点"（热 Key/热行/热账户）从何而来及其危害（单分片/单行锁争抢、连接打满），给出治理组合拳——**本地+多级缓存、动静分离、热 Key 探测与打散、库存分桶、热点账户合并/异步汇总**；讲清读写分离的原理（主写从读 + 复制）、主从延迟带来的"读不到刚写"问题及其对策（强制走主/缓存回填/会话一致性）；能为具体热点选择正确手段，并识破"读写分离后所有读都打从库导致延迟读到旧值""缓存与 DB 双写不一致"等坑。

## 一、热点是什么：从"整体高并发"到"单点过载"

```text
图目的：负载不均才是真正的杀手
热 Key：一个商品/话题被海量读，请求全打到它所在的单个 Redis 分片 → 单网卡/CPU 饱和
热 行：秒杀同一库存行、爆款单 SKU 更新 → 行锁串行，TPS 被锁死
热账户：平台商户/备付金账户被高频记账 → 单行 update 排队，账务吞吐瓶颈
共性：不是总量扛不住，是总量压在了一个无法再分的点上
```

## 二、读热点：本地+多级缓存与动静分离

```text
图目的：把读尽量拦在离用户近、代价低的层
本地缓存(Caffeine)：进程内，纳秒级，扛住最热 Key 的第一层，但每台各存一份需注意容量
分布式缓存(Redis)：跨实例共享，热 Key 打散前先靠它承接绝大读量
多级：L1 本地 → L2 Redis → 回源 DB，逐层过滤，DB 只接长尾冷数据
动静分离：静态化页面/CDN 卸载不变内容，动态内容才走渲染，把"读"从服务端剥走
```

```java
// 目的：给热 Key 兜一层本地缓存并防击穿
Object v = localCache.get(key, k -> {                    // 说明：L1 未命中再回源
    return redis.get(key, () -> db.load(k));             // 结果：L2 未命中才打 DB，且用互斥/逻辑过期防击穿
});
// 反例：热 Key 过期瞬间海量请求同时穿透到 DB ❌ 缓存击穿/雪崩，需互斥重建或永不过期+后台刷新
// 反例：不设本地缓存，最热 Key 每次走一次 Redis 网络往返 ❌ 单分片被热 Key 打满
```

## 三、写热点：打散与合并

```text
图目的：读靠缓存挡，写要么拆、要么并
库存/热 Key 打散：一个热 key/行拆成 N 个子桶/子行分摊争抢（秒杀预扣即此法）
热点账户合并：对同一账户的高频记账，先在本地/内存累加，定时或按阈值合并成一笔批量更新主账
异步汇总：明细流水异步落库，余额用"增量合并+定期快照"，把单行 update 频次降下来
```

## 四、读写分离与主从延迟

```text
图目的：一写多读扩吞吐，但要直面复制延迟
原理：写走主库，读分散到多个从库；提升读扩展与可用性
风险：异步复制有延迟 → 刚写完立刻读从库可能读到旧值（"读不到自己的写"）
对策：写后强制读主（会话一致性）、关键读走主、或写后短暂把该 key 结果回填缓存遮蔽延迟
```

```java
// 目的：对"写后立读"场景保证读到最新（三类常见手段）
txTemplate.execute(...);                       // 主库写入
cache.put(orderKey, freshOrder);               // 结果：写完立即把最新值回填缓存，后续读命中新值遮蔽延迟
// 反例：下单后立刻查"我的订单"走从库 ❌ 复制延迟导致列表缺刚下的单，用户以为没成功
// 反例：缓存与 DB 双写、先更 DB 再删缓存之间并发读回填旧值 ❌ 需延迟双删/订阅 binlog 保证最终一致
```

- 缓存一致性常用 **Cache-Aside + 更新后删除**（而非直接写缓存），配合 binlog(CDC) 异步失效，收敛双写不一致。
