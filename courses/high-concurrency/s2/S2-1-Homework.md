# 热点治理与读写分离 · 作业

### 作业 1：定位并治理一个读热点（热 Key）

- 目标：体会"总量压在一个不可再分的点"是什么感受，并落地本地+多级缓存。
- 任务：选一个会被海量读的 Key（如爆款商品详情），先用压测复现单 Redis 分片被打满；再引入 Caffeine 作 L1、Redis 作 L2 构成多级缓存，并给热 Key 加互斥重建或逻辑过期防击穿。
- 验收标准：改造后 DB QPS 显著下降、单分片网卡/CPU 不再饱和；热 Key 过期瞬间不出现穿透到 DB 的请求尖峰。
- 参考解法要点：L1 未命中回源 L2、L2 未命中才打 DB；击穿用互斥锁或"逻辑过期+后台刷新"，雪崩用过期时间加随机抖动打散；超热 Key 探测后打散到多分片。

### 作业 2：拆解一个写热点（热行 / 热点账户）

- 目标：理解行锁串行如何锁死 TPS，掌握"打散"与"合并"两种写治理范式。
- 任务：对秒杀单 SKU 库存，把一个库存行拆成 N 个子桶做分摊预扣；对高频记账的热点账户，实现"本地累加 + 按阈值合并成一笔批量更新主账"。
- 验收标准：子桶方案下并发扣减不再因单行锁排队而吞吐骤降，且不超卖；账户合并方案把单行 update 频次降低一个数量级。
- 参考解法要点：分桶后用 Redis Lua 原子扣减、跨桶不足时的回捞/汇总；合并写要保证明细流水不丢、余额用增量+定期快照收敛一致。

### 作业 3：处理读写分离下的"读不到刚写"

- 目标：把主从延迟的工程对策落到一条真实链路（下单 → 查我的订单）。
- 任务：复现"下单成功但订单列表缺单"的从库延迟问题，然后分别用①写后强制读主的会话一致性、②写后回填缓存遮蔽延迟两种方案修复，并说明各自适用场景。
- 验收标准：修复后"写后立读"稳定读到最新数据；普通列表读仍能享受从库扩展；给出两种方案的取舍说明。
- 参考解法要点：会话一致性可用"写后 N 秒内该用户读走主"或基于 GTID 等待同步；回填缓存用最新值 short-TTL 遮蔽延迟；双写场景统一走 Cache-Aside 更新后删除 + binlog 异步失效。
