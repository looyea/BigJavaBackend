# 与 GitLab CI 的取舍（关联） · 作业

## 作业 1：双向翻译训练

**目标**：把同一条 Java 流水线在两个平台各实现一遍。

1. 把前面两节学到的 Actions 流水线（build→test→deploy + matrix JDK17/21）改写为等价 .gitlab-ci.yml：stages+needs、parallel:matrix、artifacts 自动传递（验收：两平台各跑绿，输出对照表标注每处语法映射）。
2. 故意保留一处"直译"错误（如 cache paths 照搬 ~/.m2 到 GitLab），观察缓存全空现象并修复（错误用例：目录必须在项目内）。
3. 写 10 行总结：哪一侧写法更简洁、分歧最大的三个机制点。

## 作业 2：双跑与门禁一致性实验

**目标**：验证两平台门禁语义差异。

1. Actions 侧：不加 needs 让 deploy 与 test 并行跑通一次，记录"测试未过 deploy 照样跑"的危险现象，再用 needs+if 修复（异常场景体验）。
2. GitLab 侧：同样需求下只用 stages 是否天然安全，再加 needs 提速对比。
3. 结论段：写出你对"质量门语义显式化"的理解（两边各自的最佳实践一条）。

## 作业 3：平台决策沙盘

**目标**：为虚拟公司做一份两平台演进提案（一页）。

1. 背景：金融公司，监管要求代码不出境；60 个 Java 服务；已用 GitHub Enterprise Server。评估"CI 留 Actions(self-hosted) / 迁自建 GitLab / 混合"三方案，给出安全、成本、工程量三维评分表（说明：评分依据写明假设）。
2. 选一个方案写 90 天路线：先统一脚本层→模板仓试点→批量迁移→旧侧下线（结果：每阶段验收指标与回退条件）。
3. 列出三条最容易翻车的迁移风险及预案（如缓存策略全空期、secrets 断层、门禁旁路）。
