# 倒排索引与分词器链路 · 面试题

## 题 1：倒排索引和关系数据库的 B+ 树索引有什么本质不同？

- B+ 树索引仍按"字段值→行"正排组织，擅长等值/范围；对 `LIKE '%词%'` 中缀匹配无能为力，只能全表扫描。
- 倒排索引按"词→文档列表"组织，天生为"由词反查文档"的全检索场景服务，代价与命中数相关而非全库。
- 加分：能提到倒排 dictionary 用 FST 前缀压缩、posting list 用 delta+位图编码，解释它为何省空间又快。

## 题 2：一段文本进入 ES 到能被检索，经历了什么？

- 走 analysis 链路：character filter 清洗字符 → tokenizer 切成 token → token filter 加工（小写/停用词/同义词）。
- 加工后的 term 写入倒排索引 dictionary 与 posting list，检索词经同一链路才能对上。
- 加分：区分 tokenizer（切词）与 token filter（切完再改），并说明中文必须换 ik 而非默认 standard。

## 题 3：text 和 keyword 什么时候用哪个？为什么很多人踩坑？

- 需要全文分词检索用 text；需要精确匹配、排序、聚合用 keyword。
- 高频坑：把 title 建成 keyword 导致 match 搜不到；对 text 用 term 查整串也查不到；拿 text 做聚合报 fielddata 错。
- 加分：给出 multi-field（text + .raw keyword）一字段两用的标准解法，并强调类型定错只能 reindex。

## 题 4：索引期和搜索期的分词器可以不一样吗？

- 可以，但必须是显式设计而非误配。经典例子：索引 `ik_max_word` 细切提召回，搜索 `ik_smart` 粗切提精度。
- 如果是无意配成两套毫不相关的 analyzer，切出的 term 对不上，会直接导致"有数据搜不到"。
- 加分：用 `_analyze` API 对比两端 token 来定位这类故障，说明"非对称设计"与"非对称事故"的边界。

## 题 5：为什么同样的关键词，不同文档的相关度分数不同？

- ES 默认 BM25 打分：词频 TF（有饱和）、逆文档频率 IDF（稀有词更值钱）、字段长度归一（短文档更相关）三者共同决定。
- 所以"命中"不等于"同分"，排序反映的是相关性梯度而非布尔结果。
- 加分：能讲如何用 function_score/boost 叠加业务权重（时间、销量），并提醒别让权重淹没相关性。

## 题 6：mapping 定错了能改吗？生产上怎么安全改？

- 字段类型等核心定义不可原地改，因为倒排结构已按旧类型生成，改类型等于换数据结构。
- 生产做法：新建正确 mapping 的索引 → reindex 迁移数据 → 别名切换读写，实现近乎无缝的重建。
- 加分：能补充"新增字段可以直接 PUT mapping"这类可增量演进的例外，体现对 mapping 可变边界的把握。
