# 写入流程与近实时可见 · 作业

## 作业 1：复现并解释"NRT 可见性"

- 目标：亲手验证"写入成功 ≠ 立即可搜"。
- 任务：向一个 `refresh_interval=1s` 的索引写入一条文档，立刻发起 search 断言查不到；再带 `refresh=wait_for` 写入并立即查询断言查到；分别记录耗时。
- 验收标准：能展示两次查询结果差异，并用 buffer→refresh→segment 的路径解释原因；说明为什么不能靠全局调小 refresh_interval 解决。
- 参考解法要点：用 RefreshPolicy.WAIT_UNTIL / WAIT_FOR；测试里禁止假设写入即时可见。

## 作业 2：安全地做一批百万级导入

- 目标：以吞吐优先、可恢复的方式批量灌数据。
- 任务：设计导入流程——临时将副本数设为 0、`refresh_interval=-1`、用 bulk API 分批写入并控制并发；导完后恢复副本与 refresh、触发一次 forcemerge 收敛段；给出导入期间的 translog 与监控观测点。
- 验收标准：导入期间无 reject、吞吐显著高于默认配置；收尾后副本与 refresh 恢复到位、段数量回落；文档说明为何导入完再建副本更省。
- 参考解法要点：bulk 尺寸与并发需压测确定；先关 refresh/副本再恢复是官方提速套路，不是把 interval 调到毫秒。

## 作业 3：给账户余额类写入加乐观并发

- 目标：防"读-改-写"丢更新。
- 任务：实现一个更新流程：先 GET 取 `_seq_no`/`_primary_term`，再带 If-Seq-No/If-Primary-Term 写回；捕获 409 version_conflict 后重新读取并重试（有上限）；对比不启用并发控制时两个线程互相覆盖的丢更新现象。
- 验收标准：并发下不出现丢失更新；冲突能被检测并有限重试；能解释为何应用层"读时判断版本"不可靠。
- 参考解法要点：CAS 语义交给主分片判定；重试要有退避与上限，避免活锁；关键账务亦可回归数据库事务，ES 只做检索视图。
