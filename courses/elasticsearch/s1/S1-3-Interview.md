# 聚合、深分页与集群容量规划 · 面试题

## 题 1：为什么 ES 的 terms 聚合结果有时不准确？怎么改善？

- 聚合是各分片本地先算 TopN 再协调合并的近似过程，某桶在单分片排名靠后就可能进不了全局候选，被大桶挤出。
- 改善靠调大 shard_size 让每分片上送更多候选，并用 doc_count_error_upper_bound、sum_other_doc_count 判断可信度。
- 加分：能说明需要绝对精确时改用 composite 聚合分页遍历所有桶，用吞吐换准确。

## 题 2：from+size 深分页为什么会拖垮集群？max_result_window 是什么？

- from=9000,size=100 要求每个分片都返回 9100 条，协调节点再对 N×9100 条合并排序，内存与 CPU 随页码线性放大。
- max_result_window 默认 10000 是防止单请求打爆内存的护栏，不是"允许你翻到一万"的许可。
- 加分：把它和 MySQL 大 offset 深分页类比，指出两者本质相同——扫描并丢弃前缀。

## 题 3：search_after 和 scroll 该怎么选？

- search_after 基于上一页末条排序值做游标顺序翻页，实时、资源可控、无 10000 墙，适合无限下拉/深翻。
- scroll 固定一个数据快照批量遍历全量，适合导出/重建索引，但快照非实时、上下文开销大，不适合在线分页。
- 加分：点出 search_after 只能顺翻不能跳页，且排序必须含唯一 tiebreaker（_id/_shard_doc）保证稳定不重不漏。

## 题 4：主分片数为什么不能随便改？规划时怎么定？

- 路由 `hash(routing)%主分片数` 依赖分片数，改了会打散已有文档归属，所以不可原地改，只能 reindex 或 split。
- 规划看总量与单分片目标大小（数十 GB 量级）、并发查询需求：过大难扩展、过多则小分片与集群状态开销高。
- 加分：能提"用 rollover/按天索引避免单索引无限增长"，把分片数决策从一次性变滚动式。

## 题 5：什么是冷热架构，解决什么问题？

- 按数据生命周期把高频写入/查询的热索引放 SSD 热节点，历史只读索引迁到大容量盘的温/冷节点，甚至冻结。
- 解决"用昂贵资源养着几乎不查的老数据"的成本问题，同时保住热数据性能。
- 加分：结合 ILM 的 hot→warm→cold→delete 自动迁移与到期删除，说明容量随保留期封顶、成本可预测。

## 题 6：海量日志平台做检索，如何同时满足实时看板、全量导出和翻页？

- 实时看板 TopN 用 terms+合理 shardSize（走 keyword 子字段）；全量导出用 scroll/sliced scroll；在线翻页用 search_after。
- 底层靠按天滚动索引 + 别名统一读写 + ILM 冷热分层，兼得性能、成本与可运维性。
- 加分：能强调"三类诉求对应三种 API，硬用 from+size 一把梭是事故源"，并提到聚合与深翻都要盯内存/段数量。
