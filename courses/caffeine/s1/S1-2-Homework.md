# 作业题 · 多级缓存与一致性广播

> 作业不判分，做完对照参考答案自查。需要 Caffeine + Redis，多节点验证起两个进程。

## 作业 1：脏读复现 + 失效广播修复（必做）

```java
// 例子目的：两进程 A/B 各有 L1、共享 L2(Redis)
// 阶段A（脏读）：B 已把 product:1 载入 L1；A 改价 → 只"更新 DB + 删 L2"，未清 L1；B 再读 → 命中自己 L1 旧价（错误用法：漏清 L1）
// 阶段B（修复）：A 删 L2 后 PUBLISH cache:evict "1"；B 订阅到 → l1.invalidate(1)；B 再读 → L1 空 → 落 L2/DB → 新价
cache.get(1L);   // 正确使用结果：广播后 B 读到新价，脏读消失
```

注释贴阶段 A/B 两次 B 读到的价格，证明"只删 L2 不清 L1 = 脏读"。

## 作业 2：漏广播 + TTL 自愈（必做）

在作业1基础上，让 B 进程 `kill` 掉、A 改价并广播（B 漏收）、再重启 B（L1 冷启动本就没数据，改用"暂停订阅"模拟更真实）——验证：漏广播后 B 的 L1 旧值最多存活到 `expireAfterWrite(30s)` 到期即自愈。

**参考答案要点**：最坏脏读窗口 = L1 TTL；这正是"Pub/Sub 至多一次会漏、必须用短 TTL 兜底必达"的量化证据。

## 作业 3：L1 给 Redis 挡热点（必做）

对一个热 key 打 50k QPS：① 只用 Redis；② L1+Redis+广播。用 `redis-cli INFO stats`（instantaneous_ops_per_sec）与客户端 P99 对比。

**参考答案要点**：加 L1 后 Redis ops 从 ≈50k 骤降到仅广播/回填量级，P99 从亚毫秒网络级降到微秒级——L1 是热 key（redis s2-3）最有效的分摊手段之一。

## 作业 4：广播失效 vs 广播新值（选做）

把订阅端从"收到 key 清 L1"改成"收到 {key,newValue} 直接写 L1"，制造两次快速连续改价（v1→v2）与网络乱序，观察 L1 可能被旧值 v1 覆盖成新值丢失。

**参考答案要点**：广播新值有序/覆盖难题（乱序会把 v1 盖到 v2 上），广播失效让下次读各自回源则天然取到最新——这就是课文"广播失效优于广播新值"（同 Cache Aside 删不改）的实测。

## 作业 5：分层缓存设计题（选做）

给"商品详情页"设计三级：本地 Caffeine、Redis、DB。写清：各层 TTL、哪些字段进 L1、失效链路（改价/改库存分别怎么处理）、漏广播兜底、穿透/击穿叠加方案。

**参考答案要点**：体现"极热可容忍秒级不一致的进 L1 + 广播 + 短 TTL；库存终值等强一致不进 L1；读链路逐层回填、失效链路逐层作废"的完整多级心智，并与 redis s2 的穿透/击穿/一致性拼成一套。
