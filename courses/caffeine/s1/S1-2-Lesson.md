# 多级缓存与一致性广播

> 本节难度：★★★★☆
> 本节重要性：★★★★☆
> 学习产出：把 Caffeine（本地、L1）与 Redis（分布式、L2）拼成**多级缓存**——理解为什么要多级（把最热读拦在进程内，省一次网络 RTT、给 Redis 减压、抗热点），标准读写链路（L1→L2→DB 逐层回填、逐层失效），以及**多级缓存最难的一致性问题**：本地缓存是"每个 JVM 各一份"，数据变更时如何让所有节点的 L1 同时失效 → **失效广播**（Redis Pub/Sub 或 MQ 通知）。给出"哪些数据适合多级、失效丢失怎么兜底（短 TTL）、与 Cache Aside 如何协同"的工程判断。

## 一、为什么要多级：L1 到底赚在哪（★★★★★）

| 层 | 介质 | 延迟 | 容量 | 一致性 |
| --- | --- | --- | --- | --- |
| L1 Caffeine | 进程内堆 | **纳秒~微秒**（无网络） | 受单 JVM 堆限 | 各节点独立、最难一致 |
| L2 Redis | 进程外内存 | 亚毫秒（一次 RTT） | 大、共享 | 全局单份、较好一致 |
| DB | 磁盘 | 毫秒~ | 无限 | 强 |

- **L1 的核心价值 = 省掉到 Redis 的那次网络往返 + 给 Redis 挡热点**（呼应 redis s2-3 热 key：热到爆的 key 用本地缓存分摊，Redis 单分片也扛不住百万 QPS，但每节点本地扛几千就很轻松）；
- 代价：L1 是**每个进程一份副本**，天然难一致——这就引出本节主角"失效广播"。

```java
// 例子目的：标准多级读链路 L1(Caffeine) → L2(Redis) → DB，逐层回填
public Product get(Long id) {
    return l1.get(id, k -> {                       // L1 miss 时 loader 触发（同 key 并发合并，防击穿）
        Product p = l2Get(k);                      // 查 Redis
        if (p == null) {                           // L2 也 miss
            p = db.load(k);                        // 回源 DB
            if (p != null) l2Put(k, p);            // 回填 L2（带 TTL）（正确：逐层回填，下次命中 L2 不再打 DB）
        }
        return p;                                  // 返回同时回填 L1；p==null 时 Caffeine 不缓存（防穿透需另配哨兵，见 s1-1）
    });
}
// 正确使用结果：绝大多数读命中 L1（纳秒级），少量落 L2，DB 只接冷数据
// 错误用法：L1 不设容量/TTL 直接缓存所有 → 堆 OOM + 各节点数据长期漂移
```

## 二、失效广播：让所有节点的 L1 一起失效（★★★★★，最难也最爱考）

数据变更时，只更新 DB + 删 L2（Cache Aside，redis s2-2）还不够——**别的 JVM 的 L1 仍持有旧值**。解法：变更节点发一条"key X 失效"广播，所有订阅节点清掉自己的 L1。

```flow
例子目的：一次商品改价的多级缓存失效广播时序
写节点 --> 1.更新DB
写节点 --> 2.删 L2(Redis) 的 key
写节点 --> 3.PUBLISH cache:evict {key}     (Redis Pub/Sub 或 MQ)
其它所有节点 --> 订阅到消息 --> 清除各自 L1(Caffeine) 中该 key
下次读 --> L1 已空 → 落 L2/DB → 回填新值
```

```java
// 例子目的：Redis Pub/Sub 做 L1 失效广播（订阅端）
redis.subscribe("cache:evict", (chan, key) -> {
    l1.invalidate((Long) key);         // 收到失效通知 → 只清本地 L1，下次读自然回源新值（正确：广播"失效"而非广播"新值"，避免各节点写入顺序问题，且消息极小）
});
// 变更端：更新 DB + 删 L2 后
redis.publish("cache:evict", String.valueOf(id));   // 通知全集群清该 key 的 L1
// 致命边界：Pub/Sub 是"至多一次"——某节点当时宕机/网络抖动会漏收这条失效 → 它的 L1 旧值残留到过期
//   兜底：L1 必须设较短 expireAfterWrite（如 30s~2min），把"漏广播的最坏脏读窗口"钉死在 TTL 内（宁可短 TTL，不追求 L1 强一致）
```

## 三、一致性与选型的工程判断（★★★★☆）

- **广播"失效"优于广播"新值"**：广播新值要求各节点按序写、还可能有并发旧值覆盖；只广播"作废"让下次读各自回源，更简单正确（与 Cache Aside"删不改"同理，redis s2-2）。
- **L1 TTL 是安全阀**：失效广播只负责"尽快一致"，TTL 负责"兜底一定一致"——两者叠加，漏广播最多脏读到 TTL 结束。
- **哪些数据适合多级 L1**：读极热、能容忍**秒级**不一致的（商品详情、配置、类目）；**不适合**：强一致要求（余额、库存扣减终值）→ 别放 L1，或只放极短 TTL。

| 方案 | 一致性 | 复杂度 | 适用 |
| --- | --- | --- | --- |
| 只用 Redis(L2) | 较好（单份） | 低 | 通用、一致性敏感 |
| L1+L2 + Pub/Sub 失效广播 | 秒级最终一致 | 中 | 读极热、热点分散 |
| L1+L2 + MQ 广播（持久） | 秒级、丢消息概率更低 | 中高 | 节点多、跨服务 |

## 四、动手题

1. 搭 L1(Caffeine)+L2(Redis)，改价后仅"更新 DB+删 L2"不清 L1，观察另一节点读到旧值（脏读复现）；加上 Pub/Sub 失效广播后复测一致。
2. 让某订阅节点在处理广播前 `kill` 掉再重启，验证它漏收失效 → L1 旧值残留，直到 `expireAfterWrite` 到期自愈，量化这个脏读窗口。
3. 压测对比"只用 Redis" vs "L1+Redis"：热 key 场景下 Redis 的 QPS 与连接压力下降幅度。

## 五、常见线上问题

| 现象 | 根因 |
| --- | --- |
| 改了价部分用户仍看旧价（分钟级） | 只删 L2 未清 L1，或失效广播漏收且 L1 TTL 过长 |
| 广播风暴打满 CPU | 高频变更 key 每条都广播；应合并/限流，或该类数据不放 L1 |
| 各节点 L1 数据长期不一致 | 没有失效广播机制，纯靠超长 TTL 各自为政 |
| L1 命中率极低反而多一层开销 | 缓存了访问稀疏的冷 key；L1 只放"小而热"集 |
| 用 Pub/Sub 广播但要求不丢 | Pub/Sub 至多一次，需换 MQ 持久广播或缩 L1 TTL 兜底 |

## 六、关联技术栈

- **向前**：W-TinyLFU/TTL/哨兵 ↔ s1-1；Cache Aside 删不改、Canal ↔ redis s2-2；热 key 打散 ↔ redis s2-3
- **向后**：包内收官，转 minio/memcached 等历史与对象存储
- **横向**：MQ 广播 ↔ rocketmq；Redisson near-cache 即本模式的封装 ↔ redisson s1-3

## 七、本节小结

多级缓存的本质是**用 L1(Caffeine) 把最热读拦在进程内、省一次网络 RTT 并给 Redis 挡热点**，代价是 L1 每 JVM 一份、天然难一致。补上这块短板的机制是**失效广播**：数据变更时"更新 DB → 删 L2 → PUBLISH 失效 → 各节点清 L1"，且要**广播失效而非广播新值**（更简单正确）。工程铁律：**L1 必须配一个可容忍脏读窗口内的短 TTL 作安全阀**——Pub/Sub 至多一次会漏，TTL 保证"迟早一致"；强一致数据（余额/库存终值）不进 L1。选型看"读是否极热 + 能否容忍秒级不一致"，能则 L1+L2+广播（Redisson near-cache 即其成品封装），不能则退回只用 Redis。至此 Caffeine 本地缓存与多级体系收官。
