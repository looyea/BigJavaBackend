# 实际面试题 · 多级缓存与一致性广播

> 收录 2024—2026 国内中大厂 Java 后端真实面试，含追问链。考"多级缓存架构、本地缓存一致性、失效广播"。

## 题 1：你们的多级缓存怎么分层？各自解决什么？

**期望时长**：90 秒

**答题要点**：

- L1 本地（Caffeine）：进程内、纳秒级，拦最热读、给 Redis 挡热点、抗单机超高频；
- L2 分布式（Redis）：跨节点共享、容量大、一致性较好，兜住 L1 未命中的次热；
- DB：最终数据源。
- 读链路 L1→L2→DB 逐层回填，写/失效逐层作废。

**追问链**：既然有 Redis 为什么还要 L1？→ 省一次网络 RTT + 热 key 打到 Redis 单分片会成瓶颈，L1 把百万级热点摊成"每节点几千"，Redis 压力与延迟都降一个量级。

## 题 2：加了本地缓存，一致性问题出在哪？怎么解？

**答题要点**：

- 出问题在"L1 每个 JVM 一份"，改数据时只删 L2，别的节点 L1 仍旧值 → 脏读；
- 解法：**失效广播**——变更节点更新 DB + 删 L2 + PUBLISH(key)，各订阅节点收到清自己 L1；
- 广播"失效"而非"新值"（避免乱序覆盖，简单正确）。

**追问链**：广播用什么？→ Redis Pub/Sub（轻量但至多一次会漏）或 MQ（持久、丢概率低）；也可 Canal 订阅 binlog 统一发失效事件，解耦业务代码。

## 题 3：Pub/Sub 广播会丢，L1 不就永久脏读了吗？

**答题要点**：

- 不会永久——L1 一定配较短 `expireAfterWrite`，漏广播的旧值最多活到 TTL 到期回源自愈；
- 分工：**广播保"尽快一致"，TTL 保"迟早一致"**，双保险；
- 最坏脏读窗口 = L1 TTL，按业务容忍度设（详情页 30s~2min）。

**追问链**：能容忍脏读的数据才放 L1？→ 对。强一致数据（余额、库存终值）不进 L1 或只给极短 TTL；"读极热 + 容忍秒级不一致"是进 L1 的准入条件。

## 题 4：为什么不广播"新值"直接让各节点更新 L1？

**答题要点**：

- 广播新值要处理**乱序**（v1、v2 消息颠倒 → 旧值覆盖新值）和版本号对齐，复杂；
- 广播失效 = 让各节点下次读各自回源，天然拿到当前最新，无覆盖问题；
- 与 Cache Aside "删缓存而非更新缓存" 同一哲学（redis s2-2）。

**追问链**：广播失效会不会导致某 key 瞬间所有节点同时回源打爆 DB？→ 可能，配 L2 兜底（只有 L2 也 miss 才到 DB）+ L1 加载合并 + refresh；再担心就叠加互斥重建/逻辑过期（redis s2-1）。

## 题 5：什么数据不该上多级缓存，只放 Redis 甚至不放缓存？

**答题要点**：

- 不该放 L1：强一致（钱/库存终值）、写多读少、访问稀疏无热点、数据量巨大装不进堆；
- 不该放任何缓存：一次性读、实时性要求毫秒级、缓存收益 < 一致性成本；
- 判断轴：**读热度 × 一致性容忍度 × 数据体量**。

**追问链**：给电商商品详情做缓存你的分层？→ 详情/类目/评价等极热可秒级延迟的进 L1+L2+广播（短 TTL）；价格中的"活动价"若强敏感只放 L2 或带版本号；库存终值不放缓存，走 Redis 原子扣减 + DB 约束（redis s2、redisson s1-4）。
