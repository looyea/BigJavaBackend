# PromQL 与直方图分位计算 · 面试题

## 题 1：sum(rate(x[m])) 和 rate(sum(x)[m]) 结果一样吗？

```text
通常一样（rate 与线性算子可交换），但有两个例外场景：
1. 序列在窗口中途新增/消失（Pod 重建）：rate(sum) 对"总和"检测 reset，可能把消失误判为归零 → 偏差。
2. 需要 by 维度时写法不同。
生产惯例：先 rate 再 sum —— 每条序列独立处理 reset，语义更稳（结果可复现）。
```

## 题 2：为什么 histogram_quantile 要求保留 le 标签？

- 函数内部按 le 排序构造累计分布曲线，再在曲线上找分位点插值。
- 经典错误：`histogram_quantile(0.99, sum(rate(b[5m])))` —— le 被 sum 吞掉 → 每个输入原样返回，曲线"看起来有值"但完全是错的。
- 说明：这是 Prom 新手造成 P99 面板失真第一大原因，review 看板时先查这条。

## 题 3：P99 告警阈值 500ms，但业务方说"从没这么慢过"，可能的原因？

```text
1. 桶太粗：真值 120ms 落在 (0.1,0.5] 桶 → 插值可能报 400+ms（桶边界假象）。
2. 窗口效应：[5m] rate 把 4 分钟前的慢流量也算进来，与"刚才那一单"体感错位。
3. 聚合掩盖：某单机劣化被 by(service) 平均——改 by (service,instance) 定位。
4. 超上界桶：慢请求全进 +Inf → 输出≈最大有限桶值，恰好"贴着"阈值。
解决：SLO 附近密桶 + 告警附 exemplar 跳 Trace 看真实样本。
```

## 题 4：什么是 staleness（样本过期）？对 rate 有什么影响？

- Prom 规则：某序列最后一次采样后 5 分钟无新点 → 查询视为"不存在"（不是 0）。
- 影响：Pod 销毁后 topk 列表自动消失；但 `sum` 的窗口跨过死亡点时，rate 按 reset 处理最后一跳。
- 错误用法：拿"序列消失"当"值为 0"写告警 → 应使用 `absent()` 或 `unless` 显式判缺。

## 题 5：看板一打开 Prom CPU 飙满，如何治理？

1. 定位重查询：`promql_engine_active` 与慢日志，找出 `=~".+"` 全匹配、大窗口、嵌套聚合。
2. Recording rules 预计算公共子表达式（rate 结果复用），查询侧只读预算序列（结果：QPS 成本降一个量级）。
3. 面板默认时间窗从 7d 缩到 6h + Grafana 结果缓存；数据源侧配 `query_log_file` 持续审计。
4. 长期方案：高频看板下沉 Mimir/Thanos 的 downsample 数据。

## 题 6：irate 为什么"只用于调试"？

- 只用最后两个样本点，任何一次抓取延迟/重启 reset 都会把瞬时值推到极端 → 告警必然误报。
- 排障价值：5m 的 rate 抹平的秒级突刺，irate 能暴露（适合"刚才到底发生了什么"）。
- 结论一句话：容量与告警看 rate，突刺取证看 irate。
