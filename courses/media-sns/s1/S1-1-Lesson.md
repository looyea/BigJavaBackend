# Feed 流推拉结合与热 Key

> 本节难度：★★★★★
> 重要程度：★★★★☆
> 学习产出：能设计社交/自媒体的**信息流(Feed)系统**：讲透三种分发模型的取舍——**推(写扩散)**：发布时把内容写进每个粉丝的收件箱，读极快、写重，适合**普通小 V**；**拉(读扩散)**：读时按关注列表实时聚合，写轻、读重，适合**大 V/海量粉丝**；**推拉结合**：普通号推、大 V 拉、混合时间线归并，兼顾读写成本。掌握**收件箱模型**(Redis ZSet 以时间戳为 score 存近期 Feed + 分页游标 + 多源归并排序)、内容**删除/撤回的同步**、时间戳乱序处理。深入**热 Key** 难题——大 V 的 Feed key 或某爆款内容被海量读打到**单分片 Redis** 造成热点甚至雪崩，用**多级缓存 + 本地缓存 + key 打散(分片复制 N 份随机读) + 热点探测降级**治理。识破"给百万粉大 V 也全量写扩散拖垮发布""热 key 单分片被读爆""收件箱无限增长不裁剪""分页游标遇数据增删出现重复/漏项"等坑。

## 一、推 vs 拉 vs 推拉结合

```text
图目的：写扩散与读扩散是镜像取舍，按"粉丝量级"选策略
推(写扩散)：发布 → 异步写进每个粉丝收件箱；读=直接读自己收件箱(O(1)快)，写=N 份扩散(重)
拉(读扩散)：发布只存自己；读时按关注列表拉各作者最新归并；写轻、读重
推拉结合：普通号推、大V(粉丝超阈值)拉、混合时间线归并——既不让大V发布拖垮、又保小V读快
```

```java
// 目的：按作者粉丝量级决定推还是拉，避免给百万粉大V做全量写扩散
void publish(Post p) {
    fanstore.save(p);                                    // 说明：内容本体都落"作者时间线"，供拉模式读
    if (p.authorFollowers() < PULL_THRESHOLD) {          // 结果：小 V 才写扩散；大 V 走读时拉，省 N 倍写
        fanoutQueue.async(p.id());                       // 反例：百万粉也同步写扩散 ❌ 发布卡死、收件箱写爆
    }                                                    // 扩散走 MQ 异步削峰 + 分批，失败可重投(幂等)
}
Timeline read(Long uid, Cursor c) {                      // 收件箱(推来的) + 关注大V时间线(拉的) 多路归并
    return merge(inboxOf(uid, c), pullRecentFollowedBigV(uid, c)); // 按时间戳倒序归并、去重，分页游标下推
}
// 反例：收件箱 ZSet 不裁剪、无限增长 ❌ 内存膨胀、读取变慢——只保留近期 N 条 + 冷数据回源
// 异常：内容删除/撤回要同步清各收件箱引用，否则读到"已删除"死链 ❌
```

## 二、收件箱模型与分页

```text
图目的：Feed 读路径的性能来自"预聚合 + 游标"
存储：Redis ZSet，member=postId，score=时间戳，取一页=按 score 区间倒序分页
归并：推来的收件箱 + 拉来的若干大 V 时间线，多路按时间戳归并去重后截一页
分页：用"最后一条时间戳 + postId"做游标；应对翻页期间增删，用稳定游标防重复/漏项
```

## 三、热 Key：爆款把单分片打爆

```text
图目的：某大 V 的 Feed / 某爆款被海量并发读，压垮它所在的那个 Redis 分片
症状：单分片 CPU/带宽打满，同分片其它 key 被拖累 → 局部雪崩
治理：① 本地缓存(热点内容在应用进程缓存极短 TTL) ② key 打散(热 key 复制 N 份后缀随机读)
     ③ 多级缓存 + 热点探测自动降级 ④ 推拉结合本身就降低"单收件箱被反复重建"的热度
```

## 四、坑与底线

- **扩散走异步**：写扩散/重建必经 MQ 异步 + 幂等 + 分批，绝不同步 fanout 阻塞发布。
- **热 key 早打散**：识别到热点就复制到多分片 + 本地缓存兜底，别等单分片读爆引发雪崩。
