# Feed 流推拉结合与热 Key · 面试题

## 题 1：推和拉(写扩散 vs 读扩散)怎么选？

- 推：发布即写进粉丝收件箱，读快写重，适合小 V；拉：读时按关注列表聚合，写轻读重，适合大 V。
- 主流是推拉结合——按粉丝量级分档，大 V 拉、小 V 推，再混合归并。
- 加分：一句话点透"把成本放在读前还是读后"，并说明为什么百万粉不能写扩散。

## 题 2：百万粉大 V 发一条动态，你会怎么设计？

- 绝不同步全量写扩散——只落作者时间线，粉丝读时拉；或异步分批渐进扩散。
- 扩散走 MQ 异步 + 幂等 + 削峰，发布本身低延迟。
- 加分：提"读多写少的大 V 走拉、活跃小 V 走推"，并处理撤回时的引用清理。

## 题 3：收件箱怎么存、怎么分页？

- Redis ZSet，member=postId、score=时间戳，按 score 区间倒序取一页。
- 用"时间戳+postId"稳定游标，避免 offset 在数据增删时重复/漏项；收件箱只留近期 N 条、冷数据回源。
- 加分：多路(推+拉)归并去重后再截页；处理时间戳乱序。

## 题 4：什么是热 Key，为什么会致命？

- 某大 V/爆款 Feed 被海量并发读，因 Redis 按 key 分片，全压到一个分片 → 单分片打满、拖累同分片其它 key → 局部雪崩。
- 加分：区分热 key(单分片扛不住)与热数据被反复重建(CPU/带宽)，治理手段不同。

## 题 5：热 Key 怎么治理？

- 本地缓存挡重复读、热 key 复制 N 份加后缀随机读打散摊薄、热点探测自动降级；推拉结合本身降低单收件箱热度。
- 加分：注意打散带来的一致性权衡与本地缓存极短 TTL + 主动失效。

## 题 6：内容被删/撤回了，Feed 侧要注意什么？

- 写扩散下同一内容散在多个收件箱，必须同步 ZREM 清引用，否则用户点开是死链。
- 拉模式相对简单(源没了自然拉不到)，但缓存要失效。
- 加分：提"删除消息广播 + 收件箱清理 + 缓存失效"三者协同，兼顾即时性与成本。
