# 关系链、计数器与内容审核 · 小测

> 本卷满分 100 分：单选 7×6=42，多选 2×9=18，简答 1×40=40。

### 1. 求两个用户的"共同好友"，最直接的 Redis 做法是（6分）

- A. 遍历数据库全表
- B. 把两人关注集存 Set，用 SINTER 求交集
- C. 用一个 String 拼起来
- D. 无法实现

> 答案：B
> 解析：关注/粉丝天然是集合，Set 的 SINTER 能高效求共同好友，这也是好友推荐(共同好友数)的基础。

### 2. 存"按时间排序的最近关注列表"应选（6分）

- A. Set
- B. ZSet，score=关注时间戳
- C. String
- D. Hash

> 答案：B
> 解析：ZSet 以时间戳为 score 可按时间范围取"最近 N 个关注"，Set 无序不适合时间排序。

### 3. 海量点赞计数写在 Redis 的主要目的是（6分）

- A. 省内存
- B. 用原子 INCR 挡在 DB 前扛高并发累加，写不直压数据库
- C. 不需要持久化
- D. 让计数永远精确即时

> 答案：B
> 解析：Redis 原子自增吸收写洪峰，定期回写 DB 持久化；代价是最终一致，需配合防丢与对账。

### 4. 计数"只在 Redis、宕机后回源 DB"的风险是（6分）

- A. 变慢
- B. 未回写的增量丢失，重启后计数比真实值偏小
- C. 变精确
- D. 无风险

> 答案：B
> 解析：Redis 非持久真值，须用增量流水/AOF 保证可重建，宕机回源才能补齐未落盘增量、不丢计数。

### 5. 定时把 Redis 计数回写 DB 时，必须防止（6分）

- A. 读缓存
- B. 盲目覆盖导致并发期间的新增量被冲掉，应带乐观条件/增量对账
- C. 记日志
- D. 加索引

> 答案：B
> 解析：直接 SET 会覆盖回写窗口内的新累加；用"上次写入值"做乐观条件或增量对账，落后超阈值触发修正。

### 6. 爆款内容点赞把单 key 打爆，正确治理是（6分）

- A. 全压一个 like:{postId} key
- B. 按 N 个子 key 分片累加、读时求和，摊薄单分片
- C. 关闭点赞
- D. 每次点赞都同步写 DB

> 答案：B
> 解析：热点计数分片累加再汇总，避免单分片被读爆/写爆，与热 key 打散同构。

### 7. "先发后审"适合的场景与代价是（6分）

- A. 追求即时曝光，代价是违规内容有短暂曝光窗口，需下架联动清理
- B. 完全零风险
- C. 只能用于付费内容
- D. 不需要机审

> 答案：A
> 解析：先发后审体验快但有误放风险，靠机审秒级初筛 + 违规下架同步清 Feed/计数来兜底。

### 8.（多选）内容审核体系的合理构成包括（9分）

- A. 机审初筛：敏感词(Trie/AC)、图像模型、风控规则
- B. 分层决策：违规拦/下架、疑似进人审、正常放行
- C. 送审走 Kafka 消费组异步削峰，可水平扩容
- D. 只靠人工逐条看即可

> 答案：A、B、C
> 解析：海量 UGC 必须机审 + 异步队列，纯人审(D)扛不住量也做不到实时。

### 9.（多选）关于关系/计数一致性，正确的有（9分）

- A. 关注/粉丝关系增删要与缓存同步，避免脏集合
- B. 计数用 Redis 累加 + DB 持久 + 增量流水对账
- C. 违规下架要同步清 Feed 引用与计数失效
- D. 关系变更后 Feed 和计数永远不用管一致性

> 答案：A、B、C
> 解析：D 错——关系变更会影响 Feed 拉取与粉丝计数，不做同步会出现"取关仍收到、计数对不上"。

### 10. 为一个日活巨大的社交平台设计"关系链 + 计数 + 审核"底座，要求：共同好友快查、计数高并发不丢、违规内容不再曝光。请给出方案。（40分）

> 参考答案：
- 要点1：关系链建模——following/followers 用 Redis Set 存、按时间关注用 ZSet(score=时间戳)，共同好友走 SINTER、好友推荐基于共同好友数/图召回；关系增删与缓存同步（10分）
- 要点2：计数高并发不丢——Redis INCR 原子累加挡写洪峰，定期回写 DB 持久化；增量流水/AOF 保证宕机可重建；回写用乐观条件/增量对账防覆盖；爆款计数分片累加再汇总摊薄热点（10分）
- 要点3：审核分层 + 异步——机审(敏感词/图像/风控)秒级初筛、疑似进人审、按业务选先审/先发后审；送审进 Kafka 消费组异步削峰、可水平扩容（10分）
- 要点4：违规闭环——判违规即下架并同步清各收件箱 Feed 引用、失效计数，杜绝"库删了仍在流里曝光"；下架与 Feed/缓存联动一致（10分）
