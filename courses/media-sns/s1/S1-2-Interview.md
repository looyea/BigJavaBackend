# 关系链、计数器与内容审核 · 面试题

## 题 1：共同好友怎么高效求？

- 关注/粉丝存 Redis Set，`SINTER` 直接求两人交集即共同好友。
- 好友推荐基于共同好友数量或更大规模的图召回。
- 加分：按时间排序的"最近关注"用 ZSet(score=时间戳)，Set 无序不适合。

## 题 2：海量点赞计数怎么设计才既快又不丢？

- Redis INCR 原子累加挡写洪峰，定期回写 DB 持久化。
- 不丢靠增量流水/AOF 重建；回写用乐观条件/增量对账，防止覆盖窗口内新增量。
- 加分：讲清"Redis 是高速累加、DB 是持久真值"，二者靠对账收敛为最终一致。

## 题 3：计数回写 DB 为什么不能直接 SET 覆盖？

- 回写窗口内还在持续累加，盲目 SET 会冲掉这些新增量、计数偏小。
- 用"上次写入值"做乐观条件，或按增量对账，落后超阈值触发修正。
- 加分：宕机回源要能把未回写增量补上(靠流水)，保证回写幂等。

## 题 4：爆款把计数单 key 打爆怎么办？

- 把 like:{postId} 拆成 N 个子 key 分片累加、读时求和，摊薄单分片压力。
- 这与热 key 打散/写热点治理同构。
- 加分：区分"读热点"与"写热点"，读可加本地缓存、写靠分片累加。

## 题 5：先审后发和先发后审怎么选？

- 先审后发合规风险低但影响发布时效；先发后审体验快但有误放曝光窗口。
- 靠机审(敏感词 Trie/AC、图像模型、风控)秒级初筛、疑似进人审分层降风险。
- 加分：强调违规下架必须联动清 Feed 引用 + 失效计数，否则"库删了还在流里曝光"。

## 题 6：审核系统怎么扛海量 UGC？

- 送审进 Kafka 按内容分区，审核服务作为消费组消费，可加实例水平扩容提升吞吐。
- 机审先行拦截绝大多数、人审只处理疑似，成本分层。
- 加分：结合幂等(同内容不重复审)与优先级(热点内容优先审)，削峰与实时兼顾。
