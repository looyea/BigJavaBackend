# 关系链、计数器与内容审核 · 作业

### 作业 1：关系链集合运算与共同好友

- 目标：用 Redis 高效支撑关注/粉丝与共同好友查询。
- 任务：用 Set 存 following/followers、ZSet(score=关注时间戳)存最近关注；实现 `SINTER` 求两人共同好友、按共同好友数给"可能认识的人"排序；关注/取关时同步维护两个集合并保证与缓存一致。构造关注/取关并发验证。
- 验收标准：共同好友结果正确、集合不出现脏数据；取关后不再出现在对方粉丝集合；最近关注按时间正确返回。
- 参考解法要点：关系增删成对更新(following↔followers)；大集合分页/裁剪；关系变更事件驱动 Feed/计数联动。

### 作业 2：高并发计数不丢 + 热点分片

- 目标：既扛海量累加、又不丢、还打散热点。
- 任务：点赞用 Redis INCR 累加 + 增量流水(append)；定时回写 DB 用"上次写入值"乐观条件防覆盖、落后超阈值触发对账；对爆款 like:{postId} 按 N 个子 key 分片 INCR、读时求和。模拟"Redis 宕机重启"与"回写窗口内继续点赞"。
- 验收标准：宕机回源后计数不丢(用流水重建)；回写不冲掉新增量；热点分片使单 key 压力下降。
- 参考解法要点：Redis 高速累加、DB 持久真值、流水兜底；分片数与一致性权衡。

### 作业 3：机审 + 人审异步审核与下架联动

- 目标：违规内容秒级初筛、疑似进人审、下架后不再曝光。
- 任务：实现敏感词 Trie/AC 初筛 + 规则分级(违规拦/疑似转人审/正常放行)；送审投 Kafka 按内容分区、审核服务多实例消费组水平扩容；判违规触发下架事件，同步 `ZREM` 清各收件箱 Feed 引用并失效计数。构造一条"先发后审"的违规内容验证下架后流里不可见。
- 验收标准：违规被初筛拦截或送人审；消费组扩容能加快处理；下架后信息流不再返回该内容、计数失效。
- 参考解法要点：先审后发 vs 先发后审按业务选；下架联动 Feed 清理 + 缓存失效，闭环到底。
