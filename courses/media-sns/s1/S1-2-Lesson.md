# 关系链、计数器与内容审核

> 本节难度：★★★★★
> 重要程度：★★★☆☆
> 学习产出：能搭建 SNS 的三大基础服务：**关系链**——用 Redis Set 存关注/粉丝集合、ZSet 存按时间排序的关注列表，`SINTER` 求**共同好友**、以"可能认识的人/好友推荐"做图式召回，并保证关系变更与 Feed 一致性；**计数器**——点赞/播放/粉丝数等海量计数用 Redis `INCR/HINCRBY` 高并发累加、**定期回写 DB** 落盘，用**增量流水/AOF 防丢**，读多写多的**热点计数**(爆款点赞)靠**分片累加再汇总**摊薄单 key(承热点治理)；**内容审核**——机审(敏感词 Trie/图像模型/风控) + 人审分层，按业务选**先审后发**或**先发后审**，审核走 **Kafka 消费组异步削峰**、可水平扩容，违规**下架要同步清 Feed 引用与计数**。识破"计数只在 Redis、宕机回源丢数""回写 DB 覆盖并发增量致计数错乱""大 V 计数单 key 被打爆""审核队列不同步、违规内容仍在 Feed 曝光""好友关系增删与缓存不一致"等坑。

## 一、关系链：Set / ZSet 与共同好友

```text
图目的：关系是"集合运算"，用对结构天然高效
关注集：following:{uid} = Set(关注的人)；followers:{uid} = Set(粉丝)
按时间关注：用 ZSet，score=关注时间戳，可取"最近关注的 N 个"
共同好友：SINTER following:A、following:B 或 取两人关注集交集；好友推荐基于共同好友数/图召回
```

```java
// 目的：计数高并发累加 + 定期落盘，且宕机不丢、并发覆盖不打乱增量
void like(long postId) {
    redis.incr("like:" + postId);                        // 说明：Redis 原子累加挡在 DB 前，扛海量点赞
    likeLog.append(postId, +1, ts);                      // 反例：只改 Redis 不落增量流水 ❌ 宕机后回源 DB 值偏小、丢计数
}
void flushToDb() {                                       // 定时把 Redis 计数回写 DB
    long cur = redis.get("like:"+postId);
    db.update("SET like=? WHERE post=? AND like=?", cur, postId, lastWritten) // 结果：带乐观条件/增量对账，防并发覆盖
        || reconcile(postId, cur, db.getLike());         // 异常：发现 DB 落后>阈值触发对账修正，绝不盲目覆盖
}
// 反例：爆款点赞全压 like:{postId} 单 key 热点 ❌ 单分片打爆——按 sub 分片 INCR 再汇总
// 反例：违规下架只删库不清 Feed/计数 ❌ 内容仍在信息流曝光
```

## 二、计数器：高并发累加、落盘与热点

```text
图目的：读多 + 写多的计数，既要快又要不丢
累加：Redis INCR/HINCRBY 原子自增，写不直压 DB；定期(或阈值触发)回写 DB 持久化
防丢：Redis 非持久真值——增量流水/操作日志 + AOF 保证宕机能重建；回写用"增量对账"而非盲目覆盖
热点：爆款计数按 N 个子 key 分片累加、读时求和，摊薄单分片(承写热点治理/热 key 打散)
```

## 三、内容审核：机审 + 人审 + 异步队列

```text
图目的：海量 UGC 必须在"曝光速度"与"合规风险"间取平衡
机审先行：敏感词(Trie/AC 自动机)、图像/视频模型、风控规则秒级初筛
分层决策：机审"违规直接拦/下架"、"疑似进人审"、"正常放行"；按业务选先审后发 或 先发后审
异步削峰：送审进 Kafka(按内容分区)，审核服务作为消费组消费，可水平扩容加并发
下架联动：判违规 → 内容下架 + 同步清各收件箱 Feed 引用 + 计数失效，防继续曝光
```

## 四、坑与底线

- **计数不丢**：Redis 作高速累加、DB 作持久真值，靠增量流水对账收敛，回写防并发覆盖。
- **审核闭环**：下架必须联动 Feed 清理与缓存失效，否则"库删了还在流里曝光"。
