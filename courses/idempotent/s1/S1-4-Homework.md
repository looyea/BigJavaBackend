# 乐观锁、CAS 与状态机幂等 · 作业

### 作业 1：用 version CAS 实现防重复扣款

- 目标：让同一扣款请求重复提交只生效一次，用条件更新而非外部锁。
- 任务：给账户表加 `version`，实现 `UPDATE ... SET balance=balance-?, version=version+1 WHERE id=? AND version=?`。并发提交两次相同扣款，验证只有一次 affected=1、另一次 0 行。构造 ABA 场景（扣 100 又加 100，余额回到原值）说明"只比 value"会误判、"比 version"能识别。
- 验收标准：重复扣款第二次不生效；0 行能区分幂等重放与并发冲突；version 单调、能防 ABA。
- 参考解法要点：0 行若是重复提交应返回成功/原结果，不能盲目 while 重试。

### 作业 2：给订单建状态机防乱序与倒流

- 目标：用单向流转 + 前置状态条件，让重复/乱序消息无法损坏状态。
- 任务：定义 `UNPAID→PAID→SHIPPED→DONE` 状态机，所有跃迁用 `UPDATE ... WHERE order_id=? AND status=<前置>`。投递"重复支付成功""先发货后迟到的支付"消息，验证不生效（0 行）、状态不倒流。故意去掉 WHERE 前置条件复现"已发货被改回待支付"。
- 验收标准：终态不可被覆盖；非法/重复跃迁被拒；能演示加/不加前置条件的差异。
- 参考解法要点：终态要设计成能容纳合法幂等重放（返回成功而非报错丢弃）。

### 作业 3：库存防超卖的条件更新 + 0 行语义辨析

- 目标：用一条原子条件更新既防超卖又幂等，并正确解释"没更新到"。
- 任务：实现 `UPDATE stock SET qty=qty-? WHERE id=? AND qty>=?` 扣减，压测并发不超卖。对"更新 0 行"结合幂等键判定：是重复提交（返回首次结果）还是库存不足（真失败）。与悲观锁 `SELECT FOR UPDATE` 做吞吐对比，说明各自适用场景。
- 验收标准：不出现负库存/超卖；重复扣减请求不重复扣；0 行按语义分流处理；能讲乐观 vs 悲观的取舍。
- 参考解法要点：冲突极激烈时乐观重试成本高，需权衡；与幂等键方案组合更稳。
