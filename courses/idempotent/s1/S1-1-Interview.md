# 重复请求的四类解法 · 面试题

## 题 1：什么是接口幂等？重复请求应该怎么被对待？

- 幂等 = 同一请求执行一次和执行多次，对系统状态与返回结果的影响相同。
- 正确处理是"检测重复 + 返回首次结果"，而不是抛"重复请求"错误。
- 加分：点出只判重报错会让调用方拿不到已成事实、进而反复重试或重复下单。

## 题 2：重复请求都从哪里来？能根除吗？

- 三类源：用户双击/刷新、RPC/HTTP 超时重试（请求可能已成功）、MQ 至少一次投递。
- 无法根除——重试是提高可用性的必要手段，只能在被操作一侧做幂等承受它。
- 加分：说明"超时"最危险：客户端以为失败发起重试，其实服务端已执行成功。

## 题 3：讲讲 Token、DB 唯一约束、状态机、去重表四类解法及选型。

- Token：预发令牌，提交原子消费(删)，删成功才放行——表单防重。
- DB 唯一约束：业务唯一键建唯一索引，冲突即重复——最可靠兜底。
- 状态机：只允许合法跃迁，重复回调因状态不符丢弃——支付/履约。
- 去重/幂等表：记录已处理 key，先查后写并返回上次结果——通用。
- 加分：强调生产常"应用层判重 + DB 唯一约束兜底"组合，而非单用一种。

## 题 4：幂等键（Idempotency-Key）怎么选？为什么不能用时间戳？

- 键要唯一标识"一次业务意图"且在重试间保持不变：客户端 UUID、业务单号、(操作+用户+对象) 组合。
- 时间戳每次不同、报文 hash 会随微调变化，都无法判定"是同一次"。
- 加分：提到作用域隔离——下单的键和退款的键不能复用同值，且需按操作划分命名空间。

## 题 5：check-then-set 为什么在并发下会双写？怎么关闭这个窗口？

- 两条请求可能都先"查到不存在"再各自写，读判重与写不是原子操作。
- 关闭手段：DB 唯一索引让第二条冲突失败；或用原子操作（Redis SETNX、去重表主键、`INSERT ... ON DUPLICATE`）。
- 加分：把幂等记录写入与业务写入放同一事务，避免"业务成功、幂等漏记"导致的二次执行。

## 题 6：支付回调被重复推送，你怎么设计？

- 幂等键 = 渠道流水号（稳定唯一）；状态机只放行"待支付→已支付"，其余态判重返回成功。
- 入账明细对流水号建唯一索引兜并发；返回体保持与首次一致。
- 加分：区分"渠道重复推送"与"不同订单碰巧同金额"，前者用全局唯一流水号天然幂等。
