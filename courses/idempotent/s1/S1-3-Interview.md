# 幂等键设计与分布式去重 · 面试题

## 题 1：幂等键一般怎么选？

- 优先业务唯一键（订单号/流水号/商户号+商户订单号）——天然唯一稳定、可跨系统对账。
- 无天然键时用技术幂等键：客户端为每次业务意图生成 UUID（HTTP `Idempotency-Key`），重试带同一 key。
- 加分：强调键要"唯一/稳定/可覆盖窗口"，绝不能用时间戳/随机数。

## 题 2：为什么用时间戳或随机数当幂等键是错的？

- 它们每次请求都不同，无法把"同一次操作"的多次重试聚到一起。
- 幂等键的意义正是"代表同一次业务意图"。
- 加分：区分"请求级唯一"与"操作级唯一"——幂等要后者。

## 题 3：去重怎么保证并发下不重复执行？

- 把"检查是否已处理 + 占位"压成一步原子：Redis `SETNX` 或 DB 唯一索引 insert 捕获冲突。
- get 再 set 两步非原子，并发会双双放行。
- 加分：去重存储必须共享，进程内存去重多实例失效。

## 题 4：幂等记录要不要设 TTL？设多久？

- 要。永久留存会让表无限膨胀。
- 按"业务最大重试时长 + 安全余量"设窗口，需覆盖消息重投、用户手抖、网络重传跨度。
- 加分：太短则迟到的重复被判新，要在"防膨胀"与"覆盖迟到"间权衡。

## 题 5：处理失败时幂等记录怎么处理？

- 区分"已受理"与"已完成"：失败要清占位/标未终态，让同键能重试。
- 若失败仍留"已受理"，重试被判重复、永远修不了，卡死业务。
- 加分：成功才回放缓存结果，未完成允许重来。

## 题 6：同一操作既走接口又走 MQ，怎么去重才一致？

- 两条物理路径都携带同一稳定业务键，落到同一张去重表/同一 Redis key。
- 归一到同一键才能穿透"用户重复点 + 网关重试 + MQ at-least-once 重投"识别为同一次。
- 加分：键粒度对齐业务意图（订单 vs 订单行），与状态机/乐观锁组合成端到端幂等。
