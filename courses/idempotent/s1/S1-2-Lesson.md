# 消息消费幂等与事务消息

> 本节难度：★★★★★
> 重要程度：★★★★★
> 学习产出：能解决 MQ 里"消息重复投递 + 本地事务与发消息不原子"两大一致性问题。**消费幂等**：理解"至少一次(at-least-once)"投递 + 再平衡/重试必然产生重复，靠**去重缓存(Redis SETNX by msgId/业务键) + DB 唯一约束 + 状态机 + 处理位点**做到"重复消息只生效一次"，并辨明用 msgId 去重与用业务键去重的差异（重发换 msgId 时只有业务键能兜住）。**事务消息 / 本地消息表(Outbox)**：解决"扣了库存但消息没发出 / 发了消息但事务回滚"的半状态——用 RocketMQ 半消息+回查、或本地消息表与业务同事务落库再异步投递，保证"本地写与发消息最终都成功"；识破"先发消息再提交事务(事务回滚了消息已飞)""消费失败无限重试不打死信""仅用 msgId 去重漏掉生产端重发"等坑。

## 一、为什么消费必然重复：at-least-once 的代价

```text
图目的：MQ 的可靠性语义决定了重复不可避免
at-most-once：可能丢、不重复——不适合资金/订单
at-least-once：不丢、但会重复——主流选择，重复由消费端幂等消化
重复源：消费处理成功但 ack 前崩溃 → 重投；再平衡后从旧位点重放；生产端重试重发
结论：既然选了至少一次，就必须把消费者写成幂等的
```

## 二、消费幂等的四把锁

```java
// 目的：重复投递的消息只产生一次业务副作用（去重 + 唯一约束双保险）
public boolean onMessage(Msg m) {
    if (!redis.setNx("consumed:" + m.bizKey(), "1", TTL)) // 说明：先按业务键原子占位，占不到=已处理过
        return true;                                       // 结果：判为重复，直接 ack 丢弃（返回 true=消费成功）
    try {
        ledger.insertUnique(m.bizKey(), effect);           // 说明：DB 唯一约束兜底——Redis 失效/过期也拦得住
        return true;
    } catch (DupKeyException e) {                          // 异常：并发下两条都过了 Redis，唯一键最终挡住
        return true;
    }
}
// 反例：用 msgId 去重但生产端重发换了新 msgId ❌ 同一条业务被处理两次，必须用业务键
// 反例：消费抛异常 → 无限重试刷同一失败消息，堆积打爆队列 ❌ 需重试上限 + 进死信队列
```

- 四把锁：**去重缓存**(Redis SETNX，快) / **DB 唯一约束**(可靠兜底) / **状态机**(只放行合法跃迁) / **位点管理**(处理完再提交 offset)。
- 键选择：**业务键**(订单号+事件) > msgId——msgId 在生产端重试时可能变，业务键才锁得住"同一业务意图"。

## 三、事务消息 / 本地消息表：发与写的原子

```text
图目的：解决"改库"和"发消息"不能同生同死的半状态
错误顺序：先发消息→再提交事务 → 事务回滚但消息已飞出 → 下游做了未发生的业务
RocketMQ 事务消息：发"半消息"(对消费者不可见)→ 执行本地事务 → commit/rollback → 超时则 Broker 回查
本地消息表(Outbox)：业务与"待发消息"同一本地事务落库 → 后台轮询/CDC 投递 → 投递成功再标记，至少一次+幂等消费
```

- 取舍：事务消息依赖 MQ 支持(回查逻辑)；Outbox 更通用、易审计，但需轮询器且要保证投递不丢；两者都靠"下游消费幂等"闭合最终一致。

## 四、坑与边界

- 消费成功再提交 offset：处理前就提交，崩溃则消息丢失；处理后提交才是 at-least-once。
- 重试要有上限并转**死信队列(DLQ)**：否则毒消息(poison)反复重试堵塞分区，需人工/告警介入。
- 幂等表/去重键要有 TTL 与业务生命周期匹配，既防无限膨胀又要覆盖最大重投时间窗。
