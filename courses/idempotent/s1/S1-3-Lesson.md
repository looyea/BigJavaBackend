# 幂等键设计与分布式去重

> 本节难度：★★★★☆
> 重要程度：★★★★★
> 学习产出：能为一个接口/消费链路设计"对重复执行天然免疫"的幂等键，并在分布式多实例下一致去重。幂等的本质是**同一操作重复执行 N 次，效果与执行 1 次相同**，其技术支点是"**用什么唯一标识来判定'这是同一次操作'**"——这就是**幂等键（Idempotency Key）**。键的选取有两类：**业务唯一键**（如订单号、流水号、`商户号+商户订单号`——业务天然唯一、最可靠，能跨系统对账）与**技术幂等键**（客户端为每次"业务意图"生成的 UUID/请求指纹，重试时携带同一个 key，适合无天然业务键的接口，HTTP `Idempotency-Key` 头即此模式）。去重存储要保证**原子"检查-占位"**：用 `SET key NX`/唯一索引插入把"是否已处理"变成一次原子操作，命中重复即拒绝或返回首次结果（缓存结果回放，让重试拿到一致的响应）。**TTL 与窗口**是难点：幂等记录不能永久留存，要按"业务最大重试时长 + 安全余量"设窗口（太短→迟到的重复被判新、太长→存储膨胀），且 TTL 要覆盖"消息重投 + 用户手抖 + 网络重传"的时间跨度。**跨请求/跨消息的一致去重**：同一逻辑操作可能经由不同物理请求（用户重复点、网关重试、MQ at-least-once 重投）到达，必须用**同一幂等键**（优先稳定业务键）归一，才能穿透这些路径识别为"同一次"。要区分**去重（防并发重复）**与**串行化（并发同键怎么排队）**、以及"处理失败时幂等记录要不要回滚以便重试"（成功才标记完成，失败要能重来）。识破"用时间戳/随机数当键（每次不同、失去幂等）""键不稳定（同一操作两次算出不同键）""去重表无 TTL 无限膨胀""只在本机内存去重多实例失效""把'已受理'当'已完成'导致失败也不可重试""业务键选错粒度（订单号 vs 订单行）"等坑。

## 一、幂等键的选取：稳定唯一是命门

```text
图目的：先问"用什么判定同一次操作"——键不稳, 幂等全废
业务唯一键: 订单号/流水号/商户号+商户订单号 —— 天然唯一、可跨系统对账, 首选
技术幂等键: 客户端为每次"业务意图"生成 UUID(HTTP Idempotency-Key), 重试带同一 key
键的三性: 唯一(一次操作一key)、稳定(同操作多次算出同key)、可覆盖(重试/重投都在窗口内)
反例: 用请求时间戳/服务器随机数当键 ❌ 每次重试都不同 → 根本聚不成"同一次" ❌
```

## 二、原子去重 + 结果回放

```java
// 目的：用 Redis 原子 SETNX "检查-占位"防并发重复, 首次结果缓存供重试回放
String key = "idem:" + bizKey;                        // 说明：bizKey=稳定业务唯一键(或客户端幂等键), 不是时间戳
Boolean first = redis.setIfAbsent(key, "PROCESSING", TTL); // 结果：原子占位; false=已存在=重复请求
if (!first) {                                          // 反例：先 get 再 set 两步 ❌ 并发下两请求都判"没有" → 双执行 ❌
    return readResultOrThrow(key);                     // 命中重复: 回放首次结果(已完成)或提示处理中
}
try {
    Result r = doBusiness(req);                        // 说明：真正执行一次业务
    redis.set(key, serialize(r));                      // 成功后写结果, 后续同键重试拿到一致响应
    return r;
} catch (Exception e) {
    redis.delete(key);                                 // 反例：失败也留着"已受理"标记 ❌ 再重试被判重复、永远修不了 ❌
    throw e;                                           // 结果：失败清键 → 允许重来(区分"完成"与"仅受理")
}
// 反例：去重记录永不过期、无 TTL ❌ 表无限膨胀 ❌ TTL 须覆盖"重投+手抖+重传"最大窗口
```

## 三、跨请求 / 跨消息的一致去重

```text
图目的：同一逻辑操作会从多条物理路径到达, 必须归一到同一键才能穿透识别
路径: 用户重复点、网关超时重试、MQ at-least-once 重投、上下游各重试
归一: 各路径都携带同一稳定业务键 → 落到同一张去重表/同一 Redis key
多实例: 去重存储须共享(Redis/DB 唯一约束), 进程内存去重在集群下形同虚设
粒度: 键的粒度对齐"一次业务意图"(订单 vs 订单行), 选错会漏防或误拦
```

## 四、坑与底线

- **去重要"原子检查-占位"**：`get`+`set` 两步非原子，并发会双双放行；要么 `SETNX`、要么数据库唯一索引 insert 靠约束判冲突。
- **区分"已受理"与"已完成"**：处理失败必须能重试（清掉占位或标记未终态），否则一次抖动就永久卡死，幂等变成"幂等地拒绝修复"。
