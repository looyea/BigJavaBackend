# 幂等键设计与分布式去重 · 小测

> 本卷满分 100 分：单选 7×6=42，多选 2×9=18，简答 1×40=40。

### 1. 幂等的本质定义是（6分）

- A. 请求一定成功
- B. 同一操作重复执行 N 次的效果与执行 1 次相同
- C. 响应很快
- D. 加锁串行

> 答案：B
> 解析：幂等关心"重复执行是否产生额外副作用"，其技术支点是用唯一键判定"这是同一次操作"。

### 2. 最可靠、能跨系统对账的幂等键通常是（6分）

- A. 服务器当前时间戳
- B. 业务唯一键（订单号/流水号/商户号+商户订单号）
- C. 每次生成的随机数
- D. 客户端 IP

> 答案：B
> 解析：业务键天然唯一且稳定、可跨系统追溯；时间戳/随机数每次不同，聚不成"同一次"。

### 3. HTTP 接口没有天然业务键时，常用做法是（6分）

- A. 不做幂等
- B. 客户端为每次业务意图生成 UUID 放 `Idempotency-Key` 头，重试带同一 key
- C. 用 POST 无限重试
- D. 靠 IP 去重

> 答案：B
> 解析：技术幂等键由客户端生成并保持稳定，服务端按该 key 去重，重试命中同一条记录。

### 4. 去重存储防并发重复的关键是（6分）

- A. 先 get 判断再 set
- B. 用 SETNX / 数据库唯一索引做"检查-占位"的一步原子操作
- C. 加读写锁各判一次
- D. 靠应用层 if 判断

> 答案：B
> 解析：get+set 两步非原子，并发会双双放行；必须把"是否已处理"压成一次原子操作。

### 5. 幂等记录 TTL 设置的正确原则是（6分）

- A. 永不过期最安全
- B. 按"业务最大重试时长 + 安全余量"设窗口，覆盖消息重投/手抖/网络重传跨度
- C. 越短越省空间
- D. 固定 1 秒

> 答案：B
> 解析：太短则迟到的重复被判新、太长则存储膨胀，要匹配业务重试的最大时间窗。

### 6. 处理失败时对幂等占位记录的正确处理是（6分）

- A. 保留"已受理"标记不再动
- B. 清掉占位/标记未终态，让后续同键能重试
- C. 永久拒绝该键
- D. 换一个新键

> 答案：B
> 解析：要区分"已完成"与"仅受理"；失败留标记会让重试被判重复、永远修不了，卡死业务。

### 7. 分布式多实例下"进程内存去重"的问题是（6分）

- A. 太慢
- B. 各实例各判各的，同键请求打到不同实例仍会重复执行
- C. 占内存
- D. 无法缓存结果

> 答案：B
> 解析：去重存储必须共享（Redis/DB 唯一约束），本地内存去重在集群下形同虚设。

### 8.（多选）一个合格幂等键应具备（9分）

- A. 唯一（一次操作一 key）
- B. 稳定（同操作多次算出同 key）
- C. 可覆盖重试/重投窗口
- D. 每次请求都用新随机数

> 答案：A、B、C
> 解析：D 直接破坏幂等——键必须能代表"同一次业务意图"。

### 9.（多选）同一逻辑操作可能经由哪些物理路径重复到达（需归一到同一键去重）？（9分）

- A. 用户重复点击
- B. 网关超时重试
- C. MQ at-least-once 重投
- D. 上下游各自重试

> 答案：A、B、C、D
> 解析：这些路径都携带同一稳定业务键才能穿透识别为"同一次"，一致去重。

### 10. 为一个支付网关接口设计幂等键与分布式去重方案，要求覆盖重试/重投、多实例一致、失败可重来、存储不膨胀。请给出方案。（40分）

> 参考答案：
- 要点1：键选取——优先业务唯一键（商户号+商户订单号），无则客户端 `Idempotency-Key` UUID；保证唯一/稳定/可覆盖，绝不用时间戳随机数（10分）
- 要点2：原子去重 + 回放——Redis SETNX 或 DB 唯一索引做检查-占位一步原子；首次成功缓存结果，重复请求回放同一响应（10分）
- 要点3：多实例一致 + 粒度——去重存储共享、键粒度对齐"一次业务意图"（订单 vs 订单行），覆盖用户重复点/网关重试/MQ 重投各路径归一（10分）
- 要点4：TTL 与失败可重试——按业务最大重试窗口设 TTL 防膨胀又覆盖迟到；区分"已受理/已完成"，失败清占位允许重来（10分）
