# 乐观锁、CAS 与状态机幂等

> 本节难度：★★★★☆
> 本节重要性：★★★★☆
> 学习产出：能用"数据版本 + 状态单向流转"这两条内在机制实现幂等，而不只依赖外部去重表。**乐观锁/CAS（Compare-And-Swap）**：给记录一个 `version`（或状态字段），更新时带上"我读到的旧值"作为条件——`UPDATE ... SET x=?, version=version+1 WHERE id=? AND version=?`，只有版本匹配才更新成功（影响行数 1），并发/重复提交中"后到的相同更新"因版本已变而条件不成立、影响行数 0，于是**天然拒绝重复写**；这就是用数据库原子 update 实现 CAS，无需显式锁。CAS 的幂等价值在于：**同一更新重复执行，第二次起就不再改变数据**（因为版本/前置状态已不满足），效果等价执行一次。**状态机幂等**：把业务建模为有限状态机（如订单 `待支付→已支付→已发货→完成`，或 `INIT→SUCCESS`），状态**只允许沿合法方向的单向流转**，更新写 `WHERE status = 前置状态`；重复请求或乱序消息到达时，"已支付"再收到"支付成功"会因 `status 已不是待支付` 而更新不生效——**终态不可被覆盖**，非法跃迁被拒。两者都靠"更新条件不满足 → 影响 0 行 → 幂等/拒绝"的机制，把去重内聚到数据本身，比外部记录更强一致（不存在去重表与业务数据不一致的窗口）。要注意 **ABA 问题**（值绕回原样但中间变过，纯 version 能防、纯值比较不能防，故用单调 version 而非 value）、以及"更新 0 行时要区分'重复提交'还是'并发冲突需重试/报错'"、终态设计要吸收所有合法重复。识破"用悲观锁 `SELECT FOR UPDATE` 抗高并发吞吐差""CAS 只比 value 不比 version 中 ABA""状态可回跳导致旧消息把'已发货'改回'待支付'""更新 0 行一律当成功吞掉错误""终态没设计好、迟到合法消息被丢"等坑。

## 一、乐观锁 CAS：用条件更新拒绝重复写

```java
// 目的：更新带"我读到的 version"作条件, 原子 update 实现 CAS, 重复/并发写自动失效
int affected = dao.update("UPDATE account SET balance=bal-?, version=version+1 "
        + "WHERE id=? AND version=?", amt, id, readVersion);   // 说明：版本匹配才更新成功
if (affected == 0) {                       // 结果：0 行=版本已变=别人(或重复请求)已改 → 本次写不生效
    // 反例：一律重试到成功 ❌ 若这是"重复提交", 重试反而制造第二次扣款 ❌ 须先判是否幂等重放
    throw new ConflictOrDuplicate();       // 区分"并发冲突(可重读重试)" vs "重复提交(幂等拒绝)"
}
// 反例：CAS 只比较 balance 值不比较 version ❌ ABA: 扣了又加回原值被误判"没变" ❌ 用单调 version 防
```

## 二、状态机幂等：单向流转 + 终态不可覆盖

```sql
-- 目的：状态只允许沿合法方向单向流转, 重复/乱序消息因前置状态不符而更新 0 行
UPDATE orders SET status='PAID', pay_time=NOW()
 WHERE order_id=? AND status='UNPAID';    -- 说明：只有"未支付"才能被置为"已支付"
-- 结果：重复的"支付成功"到达时 status 已=PAID → WHERE 不成立 → 影响 0 行 → 天然幂等
-- 反例：不加 status 前置条件直接 set ❌ 迟到的旧消息能把"已发货"改回"待支付" ❌ 状态倒流=数据损坏
-- 反例：终态设计漏了合法迟到路径 ❌ 本该吸收的重复回调被当非法丢弃 ❌ 终态要能容纳幂等重放
```

## 三、两种"更新 0 行"的语义辨析

```text
图目的：0 行不等于失败, 要分清是哪种情形
① 幂等重放: 同一操作重复到达, 前置条件已不满足 → 0 行 = 正确(已生效过), 返回成功/首次结果
② 并发冲突: 别人并发改了 version → 0 行 = 需重读最新再按业务决定重试或报错
关键: 结合"是否同一幂等键/是否已达目标终态"判定, 别一律吞掉也别一律重试
```

## 四、坑与底线

- **单向流转 + 终态不可逆**：状态机一旦进入终态不能被后续(重复/乱序)消息改写，这是防"状态倒流损坏数据"的底线；跃迁合法性由 `WHERE status=前置` 兜住。
- **0 行语义要辨析**：幂等重放应返回成功/原结果，并发冲突才需重试；一刀切处理要么掩盖错误要么制造重复。
