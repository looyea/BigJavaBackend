# 消息消费幂等与事务消息 · 面试题

## 题 1：MQ 为什么会产生重复消息？at-least-once 下你怎么保证不重复处理？

- 重复源：消费处理成功但 ack 前崩溃 → 重投；再平衡从旧位点重放；生产端超时重发。
- 保证：把消费者写成幂等——去重缓存 + DB 唯一约束 + 状态机 + "处理完再提交位点"。
- 加分：点明"既然要不丢就只能至少一次，重复是必须承受的代价，只能靠幂等消化"。

## 题 2：消费幂等用 msgId 去重还是业务键去重？为什么？

- 优先业务键（订单号 + 事件类型）：它在重试/重发间稳定，代表同一次业务意图。
- msgId/offset 在生产端重发时会变，用它去重会漏判，导致同一业务处理两次。
- 加分：给出"SETNX 业务键快判 + DB 唯一约束兜底"的双层设计。

## 题 3：本地消息表(Outbox) 怎么解决"改库和发消息不原子"？

- 业务数据与"待发消息"在同一本地事务里落库，二者同生同死；再由投递器异步轮询/CDC 发 MQ，成功标记。
- 投递保证至少一次，配合下游消费幂等实现最终一致。
- 加分：对比 RocketMQ 事务消息（半消息 + 本地事务 + Broker 回查）——Outbox 更通用易审计、事务消息更省轮询。

## 题 4：先发消息再提交事务，和先提交事务再发消息，各有什么问题？

- 先发消息：事务回滚但消息已飞出，下游执行了未发生的业务（脏消息）。
- 先提交事务：事务成功但发消息前崩溃，下游永远收不到（丢消息）。
- 加分：指出两者都做不到原子，正解是"业务与发消息解耦为同事务落库(Outbox)或事务消息回查"。

## 题 5：消费一直失败（毒消息）怎么办？

- 设重试上限，超过转死信队列(DLQ)并告警，保留原消息与失败原因供排查。
- 主队列继续消费，不被毒消息堵塞；修复后可从 DLQ 重放。
- 加分：强调"处理前提交位点"会导致崩溃丢消息，正确是处理成功再提交；重试要退避避免打爆下游。

## 题 6：端到端"扣库存→发消息→加积分"，你怎么设计不丢不重不半状态？

- 发与写原子：扣库存与消息同事务落库(Outbox)或走事务消息，杜绝"扣了没发/发了却回滚"。
- 不丢：至少一次 + 处理成功后提交位点 + 投递器重试。
- 不重：积分服务按 orderId 幂等（SETNX + 唯一约束）。
- 加分：补充去重记录 TTL 要覆盖最大重投窗口、DLQ 兜底毒消息，形成完整闭环。
