# 重复请求的四类解法

> 本节难度：★★★★☆
> 重要程度：★★★★★
> 学习产出：能针对"同一请求被重复提交/重复投递"给出四类**幂等**解法并选对场景——**Token 机制**（先取令牌、提交即消费、一次即废）、**DB 唯一约束**（业务唯一键/幂等键建唯一索引，靠冲突兜底）、**状态机**（只允许合法的状态跃迁，重复流转被判定丢弃）、**去重表/幂等表**（记录已处理的 requestId，处理前先查后写）；讲清幂等键（Idempotency-Key）如何选取与三要素"唯一、可判、可返回上次结果"，并在**网络重试、用户双击、MQ 至少一次投递**三大真实重复源下设计"检测重复 + 返回首次结果"的完整闭环；识破"只判重不返回上次结果导致重复下单""把幂等键放进不可控的客户端时间戳""check-then-set 竞态仍会双写""去重表无过期无限膨胀"等坑。

## 一、重复从哪来：幂等要解决的三类源头

```text
图目的：先认清重复的产生路径，才知道在哪一层判重
用户/前端：双击提交、页面刷新重放、超时后手动重试
网络/客户端：RPC/HTTP 超时重试（请求可能已到达并执行成功）
消息中间件：MQ "至少一次" 语义 → 消费者重启/再平衡导致重复投递
本质：这些重复无法根除，只能在被操作的一侧做幂等
```

## 二、四类解法与适用场景

```java
// 目的：用幂等键做"检测重复 + 返回首次结果"的完整闭环（去重表/幂等表）
public Order submit(String idemKey, OrderReq req) {
    if (idempotentTable.exists(idemKey))                 // 说明：先查——已处理过，直接返回上次结果（不是报错）
        return idempotentTable.resultOf(idemKey);        // 结果：幂等 = 重复请求得到与首次一致的响应
    Order o = doCreate(req);                             // 说明：真正业务执行
    idempotentTable.save(idemKey, o);                   // 结果：与业务同事务落幂等记录，防"执行成功但没记"
    return o;
}
// 反例：只 if(exists) throw "重复请求" ❌ 用户重试拿不到已成订单，误以为失败又下一单
// 反例：查与写不在同一事务、且无唯一约束 ❌ check-then-set 并发窗口仍双写，需唯一索引兜底
```

- **Token 机制**：服务端预发令牌（存 Redis），提交时 `DEL key` 原子消费，删成功者才放行——适合表单防重复提交。
- **DB 唯一约束**：业务天然唯一键（订单号、`(user_id,activity_id)` 领取记录）建唯一索引，冲突即重复——最可靠的最后兜底。
- **状态机**：只允许 `待支付→已支付→已发货` 的合法跃迁，重复回调因状态不匹配被丢弃——适合支付/履约。

## 三、幂等键怎么选

```text
图目的：键选错，幂等要么失效要么误伤
要求：唯一标识"同一次业务意图"，且重试时保持不变
好 的选择：客户端生成的 UUID 放 Idempotency-Key 头、业务单号、(操作+用户+业务对象) 组合
坏 的选择：请求时间戳（每次不同→判不出重复）、可变的报文内容 hash
作用域：按业务操作划分（下单的键和退款的键不能同值复用）
```

## 四、工程细节与坑

- 幂等要**返回首次结果**而非仅"识别重复"：重复请求应拿到与首次一致的响应，否则调用方无法收敛。
- 幂等记录要有**唯一约束 + 与业务同生命周期（同事务）**，避免"业务成功、幂等表漏写"导致下次判为重试而二次执行。
- 去重/Token 表要有**过期/归档**（如按业务窗口设 TTL），否则无限膨胀；但过期时间要 > 最大重试周期，防"刚过期又来一条"。
