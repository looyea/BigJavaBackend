# 重复请求的四类解法 · 作业

### 作业 1：实现 Token 机制防表单重复提交

- 目标：掌握"预发令牌 + 原子消费"的一次性防重。
- 任务：为下单表单实现：进入页面时服务端发 token 存 Redis；提交时用 Lua/`DEL` 原子消费，删除成功才放行；模拟用户快速双击两次提交。
- 验收标准：两次提交只有第一次成功，第二次因 token 已废被拒；并发双击不出现两单。
- 参考解法要点：token 与业务/用户绑定并设合理 TTL；消费必须原子（`GET+DEL` 用 Lua 或 `DEL` 返回值判断）；前端置灰只是体验、不能替代服务端幂等。

### 作业 2：用幂等表实现"检测重复 + 返回首次结果"

- 目标：把幂等从"报错"升级为"可返回上次结果"。
- 任务：建 `idempotent(key PK, result, created_at)` 表，接口接收 `Idempotency-Key`；处理前查、命中则返回存好的 result，未命中则执行业务并与幂等记录同事务写入 result。
- 验收标准：同一 key 重复调用得到字节一致的响应；并发同 key 提交不产生重复业务行（key 主键/唯一约束兜底）。
- 参考解法要点：查-改-写放同一事务或加唯一约束；result 要能序列化存回；对执行失败要区分"可重试的失败"与"已幂等完成"。

### 作业 3：为支付回调设计"状态机 + 唯一索引"双重幂等

- 目标：在真实重复源（渠道重推 + 人工重试并发）下保证不重复入账。
- 任务：回调以渠道流水号为幂等键；仅允许"待支付→已支付"跃迁，非该态判重返回成功；入账明细对流水号建唯一索引；写幂等记录设 TTL。
- 验收标准：重复/乱序/并发回调都只入账一次且每次返回一致；唯一索引能兜住并发穿透，状态机能在应用层早退。
- 参考解法要点：应用层状态机做快速判重、DB 唯一约束做最终兜底，二者互补；明确"返回成功"指幂等成功而非重复执行成功。
