# 乐观锁、CAS 与状态机幂等 · 面试题

## 题 1：乐观锁怎么实现幂等？

- 更新带"读到的 version"作条件：`WHERE id=? AND version=?`，命中才更新成功、version+1。
- 并发/重复提交中后到的相同更新因版本已变而 0 行，天然拒绝重复写。
- 加分：点出这是用 DB 原子 update 实现 CAS，判定与写入合一、无外部不一致窗口。

## 题 2：状态机为什么"天然幂等"？

- 状态只沿合法方向单向流转，更新写 `WHERE status=前置状态`。
- 重复/乱序消息到达时前置状态已不满足 → 0 行 → 不生效；终态不可被覆盖。
- 加分：能画出订单状态跃迁图并指出非法跃迁如何被拒。

## 题 3：CAS 为什么要用 version 而不是直接比 value？

- 只比 value 会中 ABA：值被改过又绕回原样会被误判"没变"。
- 单调递增 version 能可靠识别"确实变过"。
- 加分：讲 ABA 实际例子（扣 100 又加 100 余额相同但语义不同）。

## 题 4：更新影响 0 行该怎么处理？

- 不能一概而论：可能是幂等重放（已生效过，返回成功/原结果），也可能是并发冲突（重读再决定重试/报错）。
- 一律吞掉会掩盖错误，一律重试会制造重复。
- 加分：结合是否同一幂等键、是否已达终态来判定语义。

## 题 5：乐观锁 vs 悲观锁怎么选？

- 冲突少、读多写少 → 乐观（避免长期持锁、吞吐好）；冲突极激烈 → 乐观会频繁重试，悲观/单点排队可能更稳。
- `SELECT FOR UPDATE` 持锁串行、热点行易瓶颈。
- 加分：结合具体 QPS 与冲突概率权衡，别教条。

## 题 6：如何防"状态倒流"损坏数据？

- 严禁无前置条件的裸 set；所有跃迁带 `WHERE status=前置`，终态不可逆。
- 迟到的旧/重复消息因条件不满足而不生效。
- 加分：终态要能容纳合法幂等重放（返回成功而非当非法丢弃）。
