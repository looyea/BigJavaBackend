# 消息消费幂等与事务消息 · 作业

### 作业 1：把一个消费者改成 at-least-once 下的幂等消费者

- 目标：用业务键 + SETNX + DB 唯一约束做到"重复只生效一次"。
- 任务：写一个"加积分"消费者，收到 `OrderCreated(orderId)`；用 `SETNX consumed:orderId` 占位、命中即判重复返回成功；再加一层"积分流水对 orderId 建唯一索引"兜底。人为制造重复投递（重启消费者从旧位点重放）验证。
- 验收标准：同一 orderId 的消息投递多次，账户只加一次分；Redis 去重记录过期后仍被唯一索引挡住；日志区分"首次处理"与"判重丢弃"。
- 参考解法要点：优先业务键而非 msgId；去重占位与业务写最终要能被唯一约束收敛；TTL > 最大重投窗口。

### 作业 2：用本地消息表实现"扣库存 + 发消息"的原子

- 目标：消除"库扣了、消息没发"或"消息发了、事务回滚"的半状态。
- 任务：下单扣库存时，同事务向 `outbox_msg` 表插一条待发消息；写独立投递器轮询未发记录→发 MQ→成功标记已发；消费者按作业 1 幂等。断言：崩溃在任意一步都不丢不重。
- 验收标准：kill 投递器/消费者后重启，消息最终被投递且只生效一次；DB 与消息不出现"改库成功却无消息"。
- 参考解法要点：业务与消息同事务落库是原子关键；投递"至少一次"，靠下游消费幂等闭合；投递器需防重复投递标记的并发。

### 作业 3：处理毒消息与位点提交

- 目标：验证"处理成功才提交 offset"和"重试上限 + 死信"。
- 任务：构造一条必然失败的消息，配置最多重试 3 次、超限转 DLQ；分别实现"处理前提交"与"处理后提交"两版，观察崩溃时是否丢消息。
- 验收标准：处理后提交版在消费者崩溃重启后能重放该消息不丢失；毒消息 3 次后进 DLQ 且触发告警、不堵塞其余消息。
- 参考解法要点：手动 ack / 显式提交位点；DLQ 保留原消息与失败原因；主队列继续消费不受毒消息阻塞。
