# 支付、库存与消息重试的幂等实战 · 作业

### 作业 1：支付回调去重 + 只翻一次状态

- 目标：第三方反复回调只记账/发货一次。
- 任务：以商户订单号为业务键，实现 `UPDATE pay_order SET status='PAID' WHERE out_trade_no=? AND status='UNPAID'`；affected=0 时直接返回 SUCCESS 不再触发发货。模拟"同一订单回调三次 + 乱序先到'退款'再到'支付'"，验证只发货一次、状态不倒流。
- 验收标准：重复回调不重复记账/发货；终态不被覆盖；对账脚本能查出本地与渠道账单差异。
- 参考解法要点：先判状态再动作；验签之外必须有状态幂等。

### 作业 2：库存扣减防超卖且防重复扣

- 目标：既不打负库存，也不因同单重试重复扣。
- 任务：用 `UPDATE stock SET qty=qty-? WHERE sku=? AND qty>=?` 防超卖压测（并发不出现负库存）；再为扣减流水加业务唯一键(orderNo+sku)去重，让同一订单重试只扣一次。构造"同一 orderNo 提交两次"复现"只有条件更新会重复扣"的坑，加幂等键后修复。
- 验收标准：并发不超卖；同单重试不重复扣；能说清"防超卖 ≠ 防重复扣"。
- 参考解法要点：扣减动作与去重记录同事务或最终一致；释放/回补也走幂等键。

### 作业 3：MQ 重投幂等 + 对账兜底

- 目标：消费端在重投下只处理一次，且用对账发现幂等漏/重。
- 任务：消费入口按消息业务键 SETNX/去重表幂等，处理成功才手动 ACK；模拟"处理失败重投""重复投递""迟到消息"验证不重复处理。再写一个对账任务：库存 vs 出库流水、订单 vs 渠道账单，输出差异清单并告警。
- 验收标准：重投/迟到都被业务键拦住；成功才 ACK、失败会重投不丢；对账能捕获人为注入的"漏记/重记"。
- 参考解法要点：去重 TTL 覆盖重投+补单+回调最大窗口；幂等防事故、对账查事故缺一不可。
