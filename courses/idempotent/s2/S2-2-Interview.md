# 支付、库存与消息重试的幂等实战 · 面试题

## 题 1：支付回调为什么要做幂等？怎么做？

- 第三方因网络/超时会对同笔订单反复回调，不幂等就重复记账/发货。
- 以商户订单号为业务键，用状态机条件更新 `WHERE status=UNPAID`，只有翻 PAID 那次算数，重复回调 0 行直接回 SUCCESS。
- 加分：验签之外必须有状态幂等 + 对账兜底。

## 题 2：库存扣减怎么防超卖？条件更新够吗？

- `UPDATE stock SET qty=qty-? WHERE sku=? AND qty>=?` 原子条件更新保证不为负。
- 但它只防超卖，不防"同一订单重试重复扣"——扣减流水还要带业务唯一键(orderNo+sku)去重。
- 加分：讲清"防超卖 ≠ 防重复扣"，这是高发资损坑。

## 题 3：MQ 重投下怎么做消费幂等？

- 消费入口以消息业务键(订单号/流水号)去重：SETNX/去重表/状态机，已处理过直接跳过。
- 识别"同一条逻辑消息"而非"同一次投递"。
- 加分：处理成功才手动 ACK，失败不 ACK 让其重投，避免丢消息。

## 题 4：先 ACK 还是先处理？

- 先处理成功再 ACK。处理前就 ACK，一旦失败消息不再重投 = 丢消息。
- 配合业务键幂等，重投也不会重复处理。
- 加分：区分 at-least-once（配幂等）与"精确一次"的宣传。

## 题 5：为什么有了幂等还要对账？

- 幂等逻辑本身可能有 bug 或有兜不到的路径，会造成"静默资损/差异"。
- 对账（库存 vs 出库流水、订单 vs 渠道账单）是发现漏/重的最后防线。
- 加分："幂等防事故、对账查事故"，二者缺一不可。

## 题 6：这三条链路的幂等键/TTL 有什么共性要注意？

- 都用稳定业务唯一键归一重复（回调重发、同单重试、MQ 重投）。
- 去重记录 TTL 要覆盖"回调重发 + 重投 + 人工补单"的最大时间跨度，太短会放过迟到重复。
- 加分：状态机终态不可覆盖 + 条件更新，把幂等内聚到数据本身、少留不一致窗口。
