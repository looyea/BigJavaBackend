# 接口幂等网关与 Token 分发 · 小测

> 本卷满分 100 分：单选 7×6=42，多选 2×9=18，简答 1×40=40。

### 1. 把幂等做成"网关/拦截器统一基础设施"的最大好处是（6分）

- A. 减少接口数量
- B. 业务对幂等无感知、各接口复用同一套，不必每个接口各写一遍
- C. 一定更快
- D. 不用测了

> 答案：B
> 解析：集中式颁发与校验让上游只需先领 token 再携带，幂等逻辑从业务代码里剥离、统一治理。

### 2. Token 分发模型的标准流程是（6分）

- A. 直接调用、失败重试
- B. 先向网关申领幂等 Token → 携 token 调接口 → 网关原子校验并一次性消费 token
- C. 每次换新 token 无限用
- D. token 只用于登录

> 答案：B
> 解析：一次领对应一次业务意图，调用时原子消费，重复携带同一 token 命中"已消费"被拒。

### 3. 校验 token 为何必须用 Redis 原子操作(Lua/删除判定)？（6分）

- A. 更省内存
- B. "GET 判存在 + DEL"两步非原子，并发会都看到存在再各放行，幂等被打穿
- C. 为了加密
- D. 避免过期

> 答案：B
> 解析：把"检查+消费"合成一步原子（GET==token 才 DEL），才能可靠保证同一 token 只用一次。

### 4. token 被消费但业务处理失败了，正确做法是（6分）

- A. 就此作废、让用户换新订单
- B. 归还/重建可重试凭据（重新可用或允许换新 token），保证合法重试不被误拦
- C. 忽略不管
- D. 永久拉黑该用户

> 答案：B
> 解析：否则"已消费未成功"会堵死用户重试，体验与资金都出问题；生命周期要与业务成败联动。

### 5. Token 分发方案更适合的场景是（6分）

- A. 有稳定业务号、需跨系统对账
- B. 前端可先申领、接口无天然业务唯一键的场景
- C. 只读查询
- D. 内部批处理

> 答案：B
> 解析：有天然业务号且要对账更适合业务键方案；Token 适合先申领、集中挡重复提交的场景。

### 6. token 的 TTL 应如何设置？（6分）

- A. 越短越好
- B. 覆盖"申领→调用→可能重试"的最大窗口，过短会误拦正常重试
- C. 永久
- D. 固定 1 秒

> 答案：B
> 解析：TTL 要大于等于合法重试跨度，否则用户在窗口内合理重试会因 token 过期被拒。

### 7. "对上游透明"在幂等网关里指（6分）

- A. 上游看不到代码
- B. 业务代码不写幂等逻辑，由网关/拦截器统一处理，上游只需先领 token 再携带
- C. 不需要 token
- D. 免鉴权

> 答案：B
> 解析：集中式设计的价值就是把幂等从散落业务代码上移为平台能力，业务无感。

### 8.（多选）Token 分发幂等需要配套处理的有（9分）

- A. 原子消费（防并发穿透）
- B. 失败回收/归还 token（保可重试）
- C. 合理 TTL 覆盖重试窗口
- D. 让后端可被直连绕过网关

> 答案：A、B、C
> 解析：D 是隐患——若后端可被直连绕过，幂等只挡一层会失守，应纵深兜底。

### 9.（多选）Token 方案与业务键方案的关系，正确的有（9分）

- A. 二者可组合：网关挡重复提交、后端以业务键/状态机兜跨路径重复
- B. 业务键更适合有稳定唯一号、需对账的场景
- C. Token 适合前端可先申领、无天然键的场景
- D. 只能二选一、绝不能同用

> 答案：A、B、C
> 解析：D 错；纵深防御常常两者叠加。

### 10. 为一个多写接口的电商后台设计"网关统一幂等 Token"能力，要求业务无感、并发不被穿透、失败可重试、后端不可绕过。请给出方案。（40分）

> 参考答案：
- 要点1：申领-校验链路——网关提供领 token 接口(Redis 存 + TTL)，写接口经拦截器校验；业务代码不写幂等，对上游透明（10分）
- 要点2：原子消费——用 Lua "GET==token 才 DEL"一步完成检查+消费，杜绝 GET+DEL 两步被并发穿透；命中已消费即拒或回放首次结果（10分）
- 要点3：生命周期——失败时归还/允许换新 token 保证合法重试不被误拦，TTL 覆盖申领→调用→重试最大窗口（10分）
- 要点4：纵深——防止后端被直连绕过网关（内网鉴权/服务间也校），关键接口再叠加业务键/状态机兜跨路径重复（10分）
