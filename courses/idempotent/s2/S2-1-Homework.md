# 接口幂等网关与 Token 分发 · 作业

### 作业 1：实现"申领 + 原子消费"的幂等 Token

- 目标：让同一 token 只能被成功使用一次，并发不被穿透。
- 任务：写一个领取 token 的接口（Redis `SET token NX TTL`）与一个拦截器（Lua `GET==token 才 DEL` 原子消费），返回 1 放行、0 判重复。并发发起两次相同 token 调用，验证只有一次放行。对比"GET 判存在 + DEL"两步写法的穿透 bug。
- 验收标准：重复携带同一 token 被拒；并发下不放行两次；业务代码中无幂等逻辑（透明）。
- 参考解法要点：token 与 bizKey 关联，一次领对应一次业务意图。

### 作业 2：失败回收与重试窗口

- 目标：解决"消费了 token 却执行失败"导致用户无法重试的问题。
- 任务：在拦截器/服务里实现：业务成功→token 已消费不再可用；业务失败→归还 token（重新置为可用）或允许换新 token。模拟"执行到一半异常"，验证用户随后能合法重试成功。给 token 设覆盖"申领→调用→重试"窗口的 TTL。
- 验收标准：失败后合法重试不被误拦；TTL 不会在正常重试前把 token 过期；成功后重复请求仍被拒。
- 参考解法要点：区分"已受理"与"已完成"；TTL 与业务最大重试时长对齐。

### 作业 3：防止绕过 + 纵深设计

- 目标：让"网关挡重复提交"不会被后端直连绕过，并与后端幂等叠加。
- 任务：设计服务间调用也校验幂等（内网鉴权 / 二跳仍校 token 或业务键），并在关键写接口用业务唯一键/状态机再兜一层。构造"绕过网关直连后端重复调用"场景，验证后端层仍能防重。
- 验收标准：仅靠网关一层不再是唯一防线；后端对跨路径重复也能幂等；说明 Token 与业务键如何组合成纵深。
- 参考解法要点：与"支付、库存与消息重试的幂等实战"联动，端到端一致。
