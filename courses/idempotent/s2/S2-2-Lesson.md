# 支付、库存与消息重试的幂等实战

> 本节难度：★★★★★
> 重要程度：★★★★★
> 学习产出：能把前面所有幂等机制在**最容易出资金事故的三条链路**上落地成端到端一致——支付回调、库存扣减、消息重投。这三处的共同特征是"**至少一次(at-least-once)**"语义叠加"**外部世界不可控的重复**"，稍不慎就是重复扣款、超卖、重复发货。**支付回调幂等**：第三方支付网关因网络/超时会对同笔订单**反复回调**，必须以**商户订单号（业务唯一键）**做去重——回调进来先"查状态：若已是 SUCCESS 直接返回、不再记账"，更新用 `WHERE status=待支付` 的条件更新（状态机幂等），**只有把状态从"待支付"翻到"已支付"那一次才算数**；对账兜底防漏/防重。**库存扣减防超卖**：扣减用**原子条件更新** `UPDATE stock SET qty=qty-? WHERE sku=? AND qty>=?`（qty>=? 保证不扣成负、影响 0 行=库存不足），这是"扣减天然幂等/防超卖"的 DB 侧支点；但要注意**同一请求重试的重复扣减**仍需**幂等键/去重**（扣了多少、为哪笔单）配合，条件更新只防超卖不防"合法地重复扣两次"，所以扣减流水要带业务唯一键。**消息重试幂等**：MQ 是 at-least-once（消费失败/超时/重平衡会**重投**），消费端必须**以消息里的业务键去重**（去重表/Redis SETNX/状态机），处理成功才 ACK；关键是识别"**同一条逻辑消息**"而非"同一次投递"。三条链路都要**端到端一致 + 对账兜底**：幂等挡住重复，但对账（业务系统 vs 支付渠道、库存 vs 出库流水）是发现"幂等也没兜住的漏/重"的最终防线——幂等防事故、对账查事故。**去重窗口/TTL**要覆盖"回调重发 + MQ 重投 + 人工补单"的最大时间跨度。识破"只靠回调签名不判状态→重复记账""库存条件更新当万能却漏了防重复扣同一单""MQ 用投递次数而非业务键去重""处理成功前就 ACK→丢了不重投""没有对账兜底、幂等 bug 长期静默造成资损"等坑。

## 一、支付回调：状态机 + 业务键，只认一次翻状态

```java
// 目的：第三方对同笔订单反复回调, 用状态机条件更新保证"只记账一次"
// 商户订单号 outTradeNo 作业务唯一键; 只有把 待支付→已支付 的那次更新算数
int n = dao.update("UPDATE pay_order SET status='PAID', channel_no=?, pay_time=NOW() "
        + "WHERE out_trade_no=? AND status='UNPAID'", channelNo, outTradeNo, /*前置状态*/);
if (n == 0) return "SUCCESS";               // 结果：0 行=status 已 PAID=重复回调, 直接回 SUCCESS 不再记账
notifyDelivery(outTradeNo);                  // 说明：仅在真正翻成功这一次触发后续发货
// 反例：只验签名不判状态、每次回调都记账/发货 ❌ 三次回调=三次发货三次记账 ❌
```

## 二、库存扣减：条件更新防超卖 ≠ 防重复扣

```java
// 目的：原子条件更新挡住"扣成负数"(防超卖), 但同单重试的重复扣要另配幂等键
int n = dao.update("UPDATE stock SET qty=qty-? WHERE sku=? AND qty>=?", cnt, sku, cnt);
if (n == 0) throw new SoldOut();              // 结果：库存不足 或 已被本次业务扣过 —— 条件更新保证不为负
// 说明：防"同一订单重复扣两次"要靠扣减流水带业务唯一键(orderNo+sku)去重, 条件更新只防超卖不防合法重扣
// 反例：以为 qty>=? 就万事大吉 ❌ 同一 orderNo 重试两次会各扣一次 → 重复扣减 ❌ 必须幂等键去重
```

## 三、消息重投：按业务键去重 + 成功才 ACK

```text
图目的：MQ at-least-once 会重投, 幂等要识别"同一条逻辑消息"
去重: 消费入口用消息业务键(订单号/流水号) SETNX/去重表; 已处理过直接 ACK 跳过
ACK 时机: 业务真正处理成功才手动 ACK; 处理前就 ACK → 失败不再重投 → 丢消息
窗口: 去重记录 TTL 覆盖"重投+人工补单+回调重发"最大跨度, 太短会放过迟到重复
兜底: 幂等防事故 + 对账查事故 —— 库存 vs 出库流水、订单 vs 渠道账单, 发现漏/重
```

## 四、坑与底线

- **防超卖 ≠ 防重复扣**：`qty>=?` 条件更新只保证不为负，同单重试仍会重复扣；必须叠加业务唯一键幂等。
- **幂等之外要有对账**：幂等逻辑本身可能有 bug 或有兜不到的路径，对账是发现"静默资损"的最后防线——幂等防、对账查，缺一不可。
