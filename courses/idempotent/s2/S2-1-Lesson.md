# 接口幂等网关与 Token 分发

> 本节难度：★★★★☆
> 本节重要性：★★★★★
> 学习产出：能把幂等能力从"每个业务接口各写一套"上移为**平台化的统一基础设施**——在网关/拦截器层集中颁发与校验幂等 Token，让业务对幂等**无感知（对上游透明）**。典型流程（Token 申领-校验模型）：① 客户端在真正调用写接口前，先向网关**申请一个幂等 Token**（网关生成随机 token 存 Redis 并设 TTL，一次领取对应一次业务意图）；② 客户端携 token 调用目标接口；③ 网关/拦截器用 **Redis 原子操作（如 Lua：`GET` 判存在 + `DEL`）** 校验并**一次性消费**该 token——存在且删除成功才放行，不存在/已消费则判为重复直接拒绝或返回首次结果，从而把"同一 token 只能被用一次"变成原子保证；④ 请求**处理失败要能回收/归还 token**（删除占位或延长有效期），否则用户重试会因 token 已耗尽而被误拦。这种集中式方案优点是所有接口复用同一套、前端只需先取 token；代价与难点：需要**申领接口 + 校验拦截**两条链路、token 与"业务键"的关系要说清（token 代表一次意图、而非请求本身）、**失败/超时的 token 生命周期**要处理好（防止"消费了 token 却没执行成功"导致无法重试）。要与"业务键方案"（客户端直接带稳定幂等键，见幂等键设计小节）对比选型：Token 分发适合**前端可先申领、无天然业务键**的场景；业务键适合**有稳定唯一业务号、跨系统对账**的场景。识破"校验用 GET+DEL 两步非原子被并发穿透""token 消费后业务失败却不归还 → 用户无法重试""token TTL 短于业务重试窗口""把 token 当认证凭证混用""网关只挡一层、后端直连调用绕过幂等"等坑。

## 一、Token 申领与一次性原子消费

```java
// 目的：网关集中颁发、拦截器原子消费幂等 Token, 让"同一 token 只用一次"成为原子保证
String lua = "if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end";
// 说明：ARGV[1]=本次携带 token; GET 判存在 + DEL 删除合成一步, 防并发两请求都"看到存在"再各删
Long ok = redis.eval(lua, 1, "idem:token:" + bizKey, token);   // 结果：1=首次放行, 0=不存在/已被消费=重复 → 拒
// 反例：先 GET 判存在再 DEL 两步 ❌ 并发下两请求都 GET 到"存在" → 都放行 → 幂等被打穿 ❌
```

## 二、失败回收与生命周期

```text
图目的：Token 不能"消费即永久作废", 要与业务成败联动
成功: token 已原子删除, 重复请求命中"不存在"被拒或回放首次结果
失败: 必须归还/重建可重试凭据(重新可用或允许换新 token), 否则用户永远重试不了 ❌
TTL: token 有效期须覆盖"申领→调用→可能重试"的最大窗口, 过短会误拦正常重试
透明性: 业务代码不写幂等逻辑, 由网关/拦截器统一挡, 上游只需先申领再带 token
```

## 三、Token 方案 vs 业务键方案 选型

```text
图目的：两种集中/分散幂等的取舍
Token 分发: 前端先申领、无天然业务键场景; 集中复用、业务无感; 需申领+校验两条链路 + 失败回收
业务唯一键: 有稳定业务号(订单号/流水号)、需跨系统对账; 直接以键去重(SETNX/唯一索引)
组合: 网关 Token 挡"重复提交", 后端仍可用业务键/状态机兜"跨路径重复", 纵深防御
```

## 四、坑与底线

- **校验必须原子消费 token**：GET+DEL 两步非原子会被并发穿透，用 Lua 或删除返回值判定，把"用一次"压成原子。
- **别让"已消费未成功"堵死重试**：token 被消费但业务失败时必须能归还或允许换新，否则用户合法重试被判重复、体验与资金都出问题。
