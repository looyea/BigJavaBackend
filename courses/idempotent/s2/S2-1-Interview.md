# 接口幂等网关与 Token 分发 · 面试题

## 题 1：为什么要做"网关统一幂等"而不是每个接口各写？

- 集中颁发/校验、业务对幂等无感、各接口复用同一套，避免重复实现与口径不一。
- 上游只需先领 token 再携带。
- 加分：也点出代价——需要申领+校验两条链路、失败回收逻辑。

## 题 2：幂等 Token 的标准流程讲讲？

- 先向网关申领 token（Redis 存 + TTL）→ 携 token 调写接口 → 拦截器原子校验并一次性消费 token。
- 重复携带同一 token 命中"已消费"被拒或回放首次结果。
- 加分：token 代表"一次业务意图"而非"一次请求"。

## 题 3：为什么校验 token 必须原子？

- "GET 判存在 + DEL"两步非原子，并发会都看到存在、各放行一次，幂等被打穿。
- 用 Lua `if GET==token then DEL` 把检查+消费合成一步。
- 加分：或用删除返回值判定，保证"同一 token 只用一次"。

## 题 4：token 消费了但业务失败怎么办？

- 必须归还/允许换新，保证用户合法重试不被"已消费"误拦。
- 区分"已受理"与"已完成"。
- 加分：TTL 要覆盖申领→调用→重试的最大窗口。

## 题 5：Token 方案和业务唯一键方案怎么选？

- Token：前端可先申领、接口无天然业务键。
- 业务键：有稳定唯一号（订单号/流水号）、需跨系统对账。
- 加分：两者可组合成纵深——网关挡重复提交、后端以业务键/状态机兜跨路径重复。

## 题 6：统一幂等网关有什么被绕过的风险？

- 若后端可被直连绕过网关，只挡一层就失守。
- 应服务间调用也校验（内网鉴权/二跳仍校），关键接口叠加业务键/状态机。
- 加分：强调"网关是第一道但不是唯一道"，幂等要端到端设计。
