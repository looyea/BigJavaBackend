# 促销价格计算与优惠券引擎

> 本节难度：★★★★☆
> 重要程度：★★★★☆
> 学习产出：能设计一个**可组合、可解释、可防刷**的促销与优惠券引擎：把优惠抽象成**规则链/计算管线**（单品价 → 活动价/满减 → 平台券 → 店铺券 → 积分抵现，按**优先级与叠加/互斥矩阵**顺序计算），产出**可追溯的优惠明细与分摊**（每个 SKU 承担了多少优惠，供售后按比例退）；落地**优惠券三要素**——领取（限领 N 张、防脚本批量薅，靠唯一约束/令牌桶）、核销（下单锁定→支付成功消耗→取消回退，状态机 + 幂等）、**预算控制**（券的资金池/发放总量扣减，原子防超发，发放与核销分别限流）；识破"优惠叠加顺序不固定导致同一购物车两次算出不同价""券无预算池被超发资损""核销不幂等重复扣券""退款按原价而非优惠分摊比例退导致多退"等坑。

## 一、优惠计算管线与叠加矩阵

```text
图目的：优惠不是拍脑袋相加，而是有顺序、可解释的规则链
顺序：商品原价 → 单品直降/活动价 → 店铺满减/满折 → 平台券 → 支付优惠 → 积分抵现
叠加/互斥矩阵：哪些券能同时用、哪些二选一，用配置而非硬编码；顺序变化会影响最终价
产出：不仅算"到手价"，还要算"每项优惠额 + 按 SKU 分摊"，落库供售后/对账复算
确定性：同一购物车在相同规则版本下必须算出同一个价（可重放、可审计）
```

```java
// 目的：券的领取与核销都要防超发/防重复，且可回退
// 领取：原子扣券池预算，扣不到=已发完，杜绝超发资损
boolean got = redis.eval(LUA_GRAB, couponBudgetKey, 1);   // 结果：预算池 Lua 原子减，返回不足则拒绝
if (!got) throw new SoldOut("券已抢完");
// 反例：先查 if(remain>0) 再 DECR，并发下大量超发 ❌ 资金池被薅穿，须原子扣减
// 反例：核销不判状态，重复请求扣同一张券两次 ❌ 需状态机(已领→已用→已回退)+幂等
```

## 二、优惠券的预算、领取与核销

```text
图目的：券=钱，必须像资金一样做总量控制与状态流转
预算池：每张券预设发放总量/资金上限，领取即原子扣减，扣不动即"已抢完"（同秒杀库存）
限领防刷：每人限领 N 张 → (user_id, coupon_id) 唯一约束；领取接口按用户维度令牌桶限流
核销：下单锁券 → 支付成功置"已用" → 取消/超时回退"可用"；用状态机 + 幂等键防重复扣/重复退
```

## 三、优惠分摊与退款

- 售后按比例退：一单享了满减/券，退其中一件时**按该 SKU 分摊到的优惠**计算应退金额，而非按原价退，否则被"凑单享满减再退主件"薅羊毛。
- 分摊口径落进订单明细快照（承下单链路），退款引擎据此复算，保证"退得准、不超退"。

## 四、坑与取舍

- **计算确定性**：规则要有版本号，购物车试算与下单结算必须用同一版本，避免"两次价格不一致"。
- **发放与核销分别限流**：大促开始瞬时抢券是写热点，预算扣减/领取要原子 + 限流，别把 DB 打崩。
- 优惠种类多时警惕**组合爆炸**：用矩阵声明叠加/互斥并做冲突校验，而非在代码里 if-else 硬凑。
