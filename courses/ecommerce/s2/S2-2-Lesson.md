# 购物车、搜索推荐与售后逆向履约

> 本节难度：★★★★☆
> 重要程度：★★★★☆
> 学习产出：能串起交易"前（购物车/搜索推荐）—后（售后逆向履约）"两端。**购物车**：多端合并（未登录临时车与登录永久车按 SKU 数量合并、取最大值或累加的口径要定）、加购/结算前的**实时校验**（库存、价格、上下架、促销变更，防止"加购时有效、结算时已变"）、以 Redis Hash 承载热点购物车并处理容量与失效。**搜索与推荐**：搜索走倒排召回（相关度、过滤、分页深翻成本），推荐走召回+排序，二者与交易解耦、异步更新。**售后逆向履约**：退款/退换货是一台**状态机**（申请→审核→退货物流→收货质检→退款），退款金额按**优惠分摊**计算、库存按规则回补、支付退款异步回执幂等入账。识破"购物车合并直接覆盖导致少算""结算不复核价格库存导致下单即失败/被薅""逆向状态机缺环导致钱货两空""退款不幂等重复退"等坑。

## 一、购物车：合并、校验与热点存储

```text
图目的：购物车是交易入口，既要体验又要防"状态过期"
合并口径：未登录临时车 + 登录永久车按 SKU 合并，同 SKU 数量取 max 还是累加须定死，避免覆盖少算
实时校验：加购/进入结算都要复核 库存/价格/上下架/促销——加购时有效 ≠ 结算时有效
存储：Redis Hash(field=sku, value=数量/选中) 扛高频读写；登录态迁移、容量上限、失效清理
```

## 二、搜索与推荐：与交易解耦的召回层

```text
图目的：找得到 + 推得准，但别把交易链路拖慢
搜索：倒排召回 + 过滤(价格/库存/状态) + 排序，深分页成本高 → 用 search_after/限制翻页
推荐：召回(候选) + 排序(打分) 两段，结果异步更新、可降级(挂了返回默认榜单不阻断下单)
共同：都是"读多写多但允许最终一致"，索引/模型离线或准实时构建，不与下单强耦合
```

## 三、售后逆向履约：一台必须闭环的状态机

```java
// 目的：退换货是逆向状态机，任一环节缺失都可能"钱货两空"或重复退款
enum ReverseState { APPLIED, APPROVED, RETURNED, INSPECTED, REFUNDED, REJECTED, CLOSED }
// 合法跃迁：申请→审核通过→用户寄回→收货质检→退款；不通过→拒绝→关闭
// 退款金额 = 该 SKU 分摊优惠后的实付（承促销引擎），不是原价
if (refundedAlready(orderLine)) return OK;              // 结果：退款幂等——异步回执/重试不重复退
// 反例：先退款再等质检 ❌ 用户不退货也拿到钱，钱货两空；顺序须"质检通过后才退"
// 反例：退款回执重复推送无幂等 ❌ 重复退造成资损
```

- 库存回补：拒收/退货按"是否可二次销售"决定回补可售库存还是转不良品，回补同样要幂等（防同一退货补两次）。

## 四、坑与底线

- 购物车合并是**语义问题**不是技术问题：合并规则(取大/累加/去重)要与产品对齐，直接覆盖会少算、直接累加会重复。
- 结算页必须**再次复核**价格与库存，前端携带的一切金额/促销都不可信（与下单链路一致）。
- 搜索推荐**可降级**：它们挂了就返回兜底结果，绝不能成为下单链路的强依赖拖垮主流程（与高可用降级一脉）。
