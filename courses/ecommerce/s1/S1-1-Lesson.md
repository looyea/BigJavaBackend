# 下单链路与库存扣减

> 本节难度：★★★★☆
> 本节重要性：★★★★★
> 学习产出：能设计一条**从购物车到订单落库、库存扣减、超时释放**的交易主链路，讲清关键工程决策：**订单快照**（下单瞬间把商品标题/价格/优惠/规格定格进订单，防后续改价改文案污染历史订单与售后）、**库存扣减时机**（拍下减 vs 付款减，各自适用与防超卖）、**预扣—确认—回补三段式**（下单预扣占用、支付成功实扣、超时/取消回补，用 Redis 原子操作扛高并发再以 DB 兜底）、**超时未支付自动关单释放库存**（延迟消息/时间轮，避免库存被"占着不用"锁死）；并串起**防重复下单(幂等)、价格校验(防薅)、库存最终一致**。识破"用商品当前价而非快照价结算导致改价纠纷""预扣后无释放机制导致超卖假象/库存长年被占""先扣 DB 库存再建单，建单失败库存不回滚""Redis 预扣与 DB 最终扣减不对账"等坑。

## 一、下单链路全景与订单快照

```text
图目的：一条主链路上每个环节都有必须定格的"事实"
购物车 → 结算页(试算价格/优惠) → 提交订单 → 库存预扣 → 生成订单+明细 → 待支付
订单快照：下单瞬间写死 商品名/规格/成交价/优惠分摊/店铺，之后商品如何变都不影响该单
为什么快照：售后/对账/纠纷要以"用户当时看到的价"为准，实时读商品表必然随改价漂移
```

## 二、库存扣减的时机与三段式

```java
// 目的：高并发下用 Redis 原子预扣抗峰值，DB 做最终一致兜底，且必带释放
Long left = redis.eval(LUA_DEDUCT, skuKey, qty);  // 结果：Lua 判断 left>=qty 才扣，原子防超卖（对应秒杀预扣）
if (left == null || left < 0) throw new SoldOutException();   // 异常：库存不足，快速拒绝，绝不继续建单
// 预扣只是"占用"：支付成功走"实扣"落 DB，超时/取消必须回补，否则库存被死占
```

- **拍下减库存**（下单即扣）：防超卖强，但恶意/未付订单占库存 → 必须配**超时释放**。
- **付款减库存**（支付才扣）：不怕占库存，但并发下易超卖 → 高并发场景普遍选"预扣 + 释放"折中。
- **三段式**：预扣(Redis 占用) → 确认(支付后 DB 实扣) → 回补(取消/超时把占用归还)，扣与补都要幂等。

## 三、超时未支付自动关单

```text
图目的：让"占着库存不付款"的订单到期自动了结并回补
实现选型：延迟消息(RocketMQ 延时/时间轮) > 定时扫表(量大时扫库压力大) > Redis过期回调(不可靠,仅提醒)
流程：下单投递"30分钟后关单"延迟消息 → 到期检查订单仍未支付 → 置为已取消 + 回补库存(幂等)
并发坑：用户恰在关单瞬间支付成功 → 关单与支付用状态机互斥(CAS: 待支付→已取消 / 待支付→已支付)，谁先成功谁生效
```

## 四、坑与兜底

- 结算必须用**快照价/试算价**并二次校验，不信任前端传来的金额；优惠分摊明细落库以便售后按比例退。
- 预扣与 DB 实扣要有**对账**：Redis 扣了但最终没成单/没回补，会造成"可售库存"与实物长期偏差。
- 建单与预扣的原子性：Redis 预扣成功但建单失败，要能补偿回滚（捕获异常即时归还），别把库存"扣丢"。
