# 支付与对账体系

> 本节难度：★★★★☆
> 重要程度：★★★★★
> 学习产出：能设计"下单→发起支付→渠道回调→更新订单→对账"的资金链路：**支付流水**（每笔支付/退款都留独立流水单，与业务订单解耦，一次订单可能多次支付尝试）、**异步通知(回调)**的处理范式——验签、幂等（渠道会重推）、金额与状态核对后再更新订单、并**返回明确 ACK**；理解回调可能**丢失/延迟**，必须配**主动查单兜底**（定时向渠道查单，防止"用户已付、我方未收到通知"的掉单）；建立**对账**体系（与渠道 T+1 账单逐笔核对，发现**掉单/长款/短款**三类差错并挂账处理）。识破"收到回调不改状态只 print / 不幂等导致重复入账""只依赖回调不查单导致掉单资损""退款无原路返回校验""对账只看总额不逐笔、差错无法定位"等坑。

## 一、支付流水与订单解耦

```text
图目的：一次订单可能对应多次支付尝试，资金事实要单独留痕
订单(order) 1 ── N 支付流水(pay_trade)：用户换卡/失败重试会产生多条流水
每条流水：渠道、渠道单号、金额、状态(处理中/成功/失败)、原始报文快照
好处：回调按"渠道单号"定位流水再回写订单，避免一订单多流水时状态错乱
```

## 二、异步回调：验签 + 幂等 + 查单兜底

```java
// 目的：安全处理渠道重复回调，且不怕通知丢失
public String onNotify(NotifyReq n) {
    if (!channel.verify(n.sign())) return "fail";              // 说明：先验签，拒绝伪造回调（防越权改单）
    PayTrade t = repo.byChannelNo(n.channelNo());               // 结果：按渠道单号定位支付流水
    if (t.isPaid()) return "SUCCESS";                          // 幂等：渠道会重推，已支付直接 ACK，绝不重复入账
    if (t.amount().compareTo(n.amount()) != 0) { markDiff(t,n); return "SUCCESS"; } // 异常：金额不符挂差错
    t.markPaid(n); order.markPaid();                            // 核对通过才更新，落库幂等(唯一约束)
    return "SUCCESS";                                           // 明确 ACK，停止渠道继续重推
}
// 反例：不验签直接改订单状态 ❌ 他人伪造"已支付"回调白拿货
// 反例：只等回调不主动查单 ❌ 回调丢失→用户已付却掉单，形成资损
```

- **主动查单兜底**：定时任务对"处理中"流水向渠道查单，补偿回调丢失；关单/超时用状态机与支付互斥（承上节）。

## 三、对账：三类差错

```text
图目的：每天与渠道账单逐笔核对，账实相符才可结账
我方有、渠道无(掉单/短款方向)：我方记已付渠道没有 → 多为伪造/未到账，需追回
渠道有、我方无(长款)：渠道扣款成功我方没记 → 回调丢了，补单或退款
金额不一致：费率/优惠口径差异 → 逐笔挂账人工核
做法：拉渠道 T+1 账单 → 与本地流水按渠道单号 diff → 差错进差错池 → 自动补单/退款或人工
```

- 退款要**原路返回**并校验"退款额 ≤ 已支付额 − 已退额"，退款也走独立流水与幂等，防重复退款资损。

## 四、坑与底线

- 回调必须**幂等 + 返回明确成功标志**：处理失败要返回非 ACK 让渠道重试，处理成功返回 ACK 停止重推。
- 金额一律用**整数分/Decimal**，禁浮点，避免精度差错（与金融账务同源原则）。
- 对账要**逐笔**而非只看总额——总额相等掩盖不了"A 多 B 少"的对冲差错。
