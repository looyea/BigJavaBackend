# 与 ELK 选型对比（关联）

> 本节难度：★★★☆☆
> 重要程度：★★★☆☆
> 学习产出：能从 Loki 视角系统对比两套栈的运维心智、查询范式与成本模型，判断一类日志该进哪条管道，并给出"从 ELK 迁移到 Loki（或双栈并存）"的落地方法。

## 一、同一枚硬币的两面

ELK 那节从 Elasticsearch 视角讲了分野，本节站在 Loki 一侧补上运维视角的差异——**选型差异本质是"把复杂度放哪一层"**：

| 维度 | ELK | Loki |
|------|-----|------|
| 复杂度落在 | 写入与存储（分词/分片/ILM/mapping 治理） | 查询与标签设计（先选流、控扫描、防基数爆炸） |
| 团队日常 | 调 ILM、盯 shard/merge、治 mapping | 定标签白名单、审查询形状、配 Grafana |
| 查询范式 | "给任意关键词，秒级返回" | "先定位到少数流，再翻上下文" |
| 失败模式 | mapping 爆炸、red、查询 OOM | 流基数爆炸、扫描超时、被限额拒绝 |
| 谁为体验付费 | 每次写入预付索引成本 | 每次查询按需扫描成本 |

一句话：**ELK 让"想查什么查什么"变便宜（对使用者），Loki 让"存得起海量日志"变便宜（对建设者）。**

## 二、Loki 赢在哪：三个真实收益

- **存得起**：正文不进索引、chunk 落对象存储，同量日志存储成本通常是 ES 的 1/5~1/10；保留期一拉长，差距是数量级——对 debug 洪流、K8s 全组件事件尤其关键。
- **栈统一**：与 Prometheus/Tempo/Grafana 同源（标签模型一致、Alerting 一个入口、指标↔日志↔trace 天然联动），值班心智负担小。
- **运维面小**：无分片再平衡、无冷热 ILM 状态机、扩容主要是加 ingester/query 副本 + 一个对象存储桶；对比 ES 的 master 选举/shard 迁移/段合并，事故面窄。

## 三、Loki 输在哪：别自欺

- **任意词检索是硬伤**：`|~ "regex"` 是逐行扫描不是索引，宽窗口 + 高扇出必超时。审计"按商户号 + 错误码组合全文查 180 天"这类需求，Loki 模型撑不住——这就是 ELK 存在的理由。
- **标签纪律是持续成本**：ES 的 mapping 爆炸换成了 Loki 的流爆炸，治理强度不降反升，且更隐蔽（一个采集配置改动就可能悄悄开爆流）。
- **推模型无队列兜底**：采集器挂了日志就断，可靠性敏感处要补本地缓冲或前置 Kafka。
- **聚合看板弱**：unwrap 派生指标精度/性能都逊于 ES doc_values，别把 Loki 当 BI。

## 四、按"日志类别"分流，而不是整体二选一

```text
图目的：决策树——一条日志该进 Loki 还是 ELK，判据是查询范式与合规而非个人偏好
这条日志会被"任意关键词全文检索"吗？
  ├─ 是（审计/风控/工单排障带错误码） ─────→ 进 ELK/ClickHouse（需全文索引）
  └─ 否 → 排障方式是"选服务+时间窗翻上下文"吗？
        ├─ 是（K8s 组件/应用运行日志/debug） ─→ 进 Loki（便宜、够用）
        └─ 既要留存合规又要海量省存 ─────────→ 双写：全量进 Loki + 关键类别进 ELK
```

关键判据是**合规红线**：监管"任意要素可检索留存 N 天"直接决定关键流必须有全文能力，这条常盖过成本考量。双写是"贵的那一小部分单独存"，不是无差别两份（无差别双写=成本失控）。

## 五、从 ELK 迁 Loki 的方法（Loki 建设者视角）

```yaml
# 迁移期的双写路由（Logstash 侧示意）：结果——只把该进 ELK 的留全文索引，其余转 Loki
# 错误做法：一刀切下线 ES，历史合规查询当场失效，审计抽查失败
output:
  - elasticsearch:                 # 目的：审计/错误类保留全文能力
      hosts: ["http://es:9200"]    # 说明：ES 侧只接高价值类别
      index: "audit-%{+yyyy.MM.dd}"
      # 反例：把海量 debug 也塞进索引，等于白付全文索引成本
  - http:                          # 目的：全量日志推 Loki 打底（推模型）
      url: "http://loki:3100/loki/api/v1/push"   # 结果：便宜存储兑现成本优势
```

步骤：① 查询盘点（把 Kibana 高频查询导成清单，逐条判 LogQL 可行性）→ ② 影子双写跑一个发布周期 → ③ 按类别切读到 Loki → ④ 用"排障 MTTR、Loki 查询超时率、月账单"三指标验收，设回退条件（超时率>5% 或审计抽查失败即回切 ES）。别用"省钱"单因驱动迁移——能力退化是隐性成本。
