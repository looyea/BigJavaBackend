# 与 ELK 选型对比（关联） · 面试题

## 题 1：Loki 和 ELK 最本质的取舍，用一句话讲清。

- 写时全文索引 vs 读时暴力扫描的成本转移：ELK 每次写入预付索引成本换"任意词秒查"，Loki 省掉索引换"存得起海量"，代价是查询必须先被标签圈定。
- 更抽象一层：**选型是"把复杂度放哪一层"**——ELK 复杂度在写/存（分片/ILM/mapping），Loki 在查与标签设计（控扫描/防基数爆炸）。
- 加分：能推导出两边失败模式同构（mapping 爆炸 ↔ 流爆炸，都是高基数进索引结构）。

## 题 2：什么样的日志你坚持放 ELK 不放 Loki？

- 合规红线：监管要求"任意要素可检索留存 N 天"（审计、支付流水），Loki 的标签模型撑不住组合全文查询——这条常是终局判据；
- 值班文化：带任意错误码/单号全局搜上下文的团队，Loki 的 `|~` 扫描会频繁超时；
- 强聚合：要在日志上做多维数值看板（doc_values 才有优势）；
- 反例自嘲：把无界 K8s debug 洪流也塞 ELK 是浪费——那正是 Loki 的地盘。

## 题 3：Loki 省的钱会不会以"运维更累"还回去？

- 部分会：标签纪律要长期守（采集配置评审、流上限告警），查询超时治理、Grafana 动线搭建都是人力；
- 但事故面比 ES 窄：没有 master 选举/shard 迁移/段合并/ILM 卡步这一类重运维；
- 结论：省的是"存储与写放大"，换来的是"查询规范与标签治理"——团队若不守标签纪律，Loki 也能把自己玩挂（流爆炸）。

## 题 4：给老板汇报"要不要上 Loki"，你怎么算账？

- 别报绝对数，报结构：把日志按"需不需要全文"拆开，量化"贵的那部分其实是无价值 debug"；
- 三条线一起看：存储账单（对象存储 vs SSD）、查询体验（排障 MTTR 会不会退化）、合规（能不能过审计抽查）；
- 给盈亏平衡：高价值日志占比低于约 15% 时，"全量 Loki + 关键进 ELK"双写总成本仍低于全量 ELK；
- 强调可回退：影子双写一个发布周期，超时率>5% 或审计失败即回切——把决策风险降到可撤销。

## 题 5：双栈并存会不会长期维护两套成本？

- 会，所以要让两套各司其职而非重复：Loki 是全量热存 + 排障检索，ELK 只承接合规全文子集——重叠面刻意做小；
- 口径治理：明确"审计正式记录 = ELK、日常排障 = Loki"写进 runbook，避免同一需求两边各查一半；
- 演进方向：日志类别与路由规则版本化进 Git，季度复审比例，随合规/成本变化再平衡；不是"永远两份"而是"每个类别恰好一份权威 + 可选一份廉价副本"。

## 题 6：面试官追问"ClickHouse/其他方案呢"，怎么扩展？

- 第三条路：列式 + 轻量倒排（ClickHouse、以及 ES logsdb 模板降本、Grafana 新栈的列式实验），介于"全索引"与"无索引"之间，适合既要全文又要海量；
- 判断维度不变：还是"查询范式 + 合规 + 成本"三角，只是把"必须二选一"松绑成"按类别多路复用"；
- 加分：坦诚"选型没有银弹，原则（GitOps 之于部署、索引取舍之于日志）比具体工具更持久"，展示架构观而非工具站队。
