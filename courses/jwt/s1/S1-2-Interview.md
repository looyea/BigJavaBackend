# Claims、刷新与算法攻击防护 · 面试题

## 题 1：讲一下 JWT 里有哪些标准 claim，各自作用？

- `iss` 签发者、`sub` 主体（用户标识）、`aud` 受众（发给哪个服务）、`exp` 过期、`nbf` 生效时间、`iat` 签发时间、`jti` 唯一 ID。
- exp/iat/nbf 管时间窗，iss/aud 管信任边界，jti 管唯一性（配黑名单/防重放）。
- 私有 claim 放业务字段（role、tenant_id），别撞注册名。
- 加分：`aud` 常被忽略——不校验会导致 A 服务的令牌被拿去访问 B 服务（受众混淆）。

## 题 2：`alg=none` 攻击原理与防御？

- 攻击：改 header 为 `{"alg":"none"}`、篡改 payload、清空签名，赌服务端"信任 header 算法且 none 就跳过验签"。
- 防御：验签入口锁算法白名单（只 RS256/ES256），none 永远不在候选；升级有 CVE 的老 JWT 库。
- 根因还是"信任 token 自报字段"——和服务端配置冲突时以配置为准。
- 加分：能提"某些库历史上默认允许 none"，说明防御要覆盖依赖版本治理。

## 题 3：RS256 → HS256 算法混淆是怎么骗过验签的？

- 背景：RS256 下公钥公开可得（JWKS）。
- 攻击：把 `alg` 改成 HS256，用**公钥当 HMAC secret** 对篡改后的 payload 签名。
- 得手条件：服务端"按 header.alg 选验证方式"，于是走 HMAC 分支、拿公钥字符串当密钥验，恰好通过。
- 根治：验证算法与密钥由服务端固定，token 声称 HS256 但配置是 RS256 → 直接拒。
- 加分：还有反向 RS 公钥被当 HMAC key 的变体、以及 `kid` 被诱导指向攻击者可控密钥——都归到"不信任自报字段"。

## 题 4：refresh token 为什么要轮换？固定不动有什么风险？

- 固定 refresh 一旦泄露，攻击者可在有效期内无限续命，且无法察觉被复用。
- 轮换（rotation）：每次刷新发新 refresh、作废旧的，把 refresh 也变成"一次性"。
- 复用检测：旧 refresh 再次出现 = 大概率被窃，立即吊销整族令牌并强制重登。
- 加分：能说"轮换 + 复用检测 = 把泄露窗口从 refresh 全生命周期压缩到一次使用之间"。

## 题 5：`kid` 用得好好的，怎么会成为攻击面？

- 场景：服务端按 `kid` 去文件系统/数据库/远程 JWKS 找密钥。
- 风险：`kid` 未校验直接拼路径 → 路径穿越读任意文件；拼 SQL → 注入；当作 URL → 让服务端去攻击者服务器拉"合法"公钥。
- 防御：`kid` 仅作受信映射表的键，不解释成路径/SQL；JWKS 来源固定白名单地址。
- 加分：把 `kid`、`alg`、`iss` 归成一类——"token 里任何驱动服务端行为的字段都要当不可信输入"。

## 题 6：为什么权限/角色塞进 JWT 是双刃剑？

- 好处：无状态，RS 不用回源即可判权，扩展性好。
- 代价：签发即冻结，撤权在令牌到期前无效——撤销只能等过期或全量拉黑，实时性差。
- 体积：大权限列表撑爆 header，每请求背着走；明文可读还暴露权限拓扑。
- 平衡：只放粗粒度 scope/角色 + `sub`，细粒度/敏感权限按 `sub` 服务端实时查；配合短 TTL 收敛撤销窗口，详见 [无状态登出、吊销与与 OAuth2 协同（关联）](S1-3-Lesson.md)。
