# JWT 结构与签名验证 · 面试题

## 题 1：JWT 由哪几部分组成？为什么说它"透明"？

- 三段：`Header.Payload.Signature`，各自 Base64URL 编码后以 `.` 连接。
- Header 声明 `alg`/`typ`/（可选 `kid`），Payload 放 claims，Signature 是对前两段的签名。
- "透明"指前两段仅编码不加密，任何人可解码查看——所以不能放敏感数据。
- 加分：能现场拆一段 JWT 并指出签名只保证不可篡改、不保证不可见。

## 题 2：HS256 和 RS256 分别在什么场景用？

- HS256 对称：签发与验证同一把 secret，简单快速，适合自签自验的单体。
- 多方验签的隐患：每个验签方都得持 secret，等于人人可伪造——不适合开放/微服务多方。
- RS256 非对称：私钥只在 AS 签发，公钥经 JWKS 分发给任意 RS，验签方无法伪造。
- 加分：OAuth2/OIDC 标准几乎都走 RS256/ES256；判定轴是"有多少互不信任的验签方"。

## 题 3：拿到一个 JWT，验证它需要哪几步？漏掉哪步最危险？

- 选密钥：按 header `kid` + 服务端锁定的 `alg` 取可信密钥，绝不信任 token 自报 alg。
- 验签：用可信密钥重算签名比对，不过直接拒。
- 校验时间：`exp`/`nbf`（默认开启，容差别放太宽）。
- 校验业务 claims：`iss`/`aud`/自定义 `sub` 等。
- 加分：最危险是"信任 header.alg"和"只解码不验签"，分别打开算法混淆与伪造大门（下节展开）。

## 题 4：JWT 和传统 Session + Cookie 鉴权怎么选？

- Session：状态在服务端，天然可即时撤销（删 session 即失效），但每请求查会话、集群要共享会话存储。
- JWT：无状态自证，RS 不用回源、天然横向扩展，但签发后到期前难撤销、体积更大。
- 混合：短命 JWT + refresh，或 JWT + 黑名单/introspection 兼顾扩展与可撤销。
- 加分：能点出"高敏金融宁可回源验（introspection）换即时撤销"，撤销难题见 [无状态登出、吊销与与 OAuth2 协同（关联）](S1-3-Lesson.md)。

## 题 5：为什么不该把用户权限列表塞进 JWT？

- 一旦签发，权限被"冻结"到令牌过期前——改了权限用户仍带旧授权，撤销只能等过期或全量黑名单。
- 权限列表可能很大，撑爆 header，且每次请求都背着走。
- JWT 明文可读，权限拓扑暴露给持 token 者。
- 加分：折中放粗粒度 scope/角色 + 敏感/细粒度权限落服务端按 `sub` 实时查，兼顾无状态与可变性。

## 题 6：Signature 到底保护了什么？改 Payload 会怎样？

- 保护 `base64url(header) + "." + base64url(payload)` 的完整性：任何改动使重算签名与令牌尾部不符。
- 改 Payload 而不改签名 → 验签失败被拒；攻击者无法用公开密钥重算出合法签名。
- 若同时改 `alg` 为 none 且服务端盲信 → 绕过签名（alg=none 攻击），所以必须服务端锁算法。
- 加分：能说明"密钥泄露 = 全部 JWT 可伪造"，密钥轮转与 KMS 托管见 [接口签名、防重放与 KMS](../../data-security/s1/S1-2-Lesson.md)。
