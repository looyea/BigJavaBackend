# 实际面试题 · 依赖注入与循环依赖

## 题 1：Spring 是怎么解决循环依赖的？

**考察层次**：初级答"三级缓存"三个字；中级能讲每层存什么、流程怎么走；高级能讲清"为什么是三级不是两级"和"哪些循环解决不了"。

**参考答法**：

1. 前提：只解决**单例 + setter/字段注入**的循环。
2. 核心是把"实例化"和"属性填充"拆开：A 实例化后（还没填属性），就把一个能产出 A 早期引用的 `ObjectFactory` 放进三级缓存。
3. 填 A 需要 B → 去造 B；填 B 需要 A → 从缓存拿到 A 的早期引用（此时按需提前生成 A 的 AOP 代理），B 先完成，A 再完成。
4. 三级缓存：一级成品、二级提前暴露的早期（可能已代理）对象、三级产出早期引用的工厂。

**追问**：为什么要有第三级？→ 为了 AOP 代理时机：无环时代理在初始化后正常生成，只有真发生循环被别人引用时才提前生成，第三级的工厂延迟了这个决定，保证身份一致。

## 题 2：构造器注入的循环依赖为什么解决不了？

**答题要点**：三级缓存能救场的前提是"先实例化、再暴露、后填属性"。构造器注入要求**实例化时就得有依赖**——A 的构造函数需要 B 已存在，B 的构造函数又需要 A 已存在，两对象都还没造出来，没有任何"半成品"能提前暴露，直接死锁 → `BeanCurrentlyInCreationException`。解法只能改设计或把一条边换成 setter/`@Lazy`。

## 题 3：字段注入、setter 注入、构造器注入怎么选？

**答题要点**：

- 必需依赖用构造器（final、创建即完整、易测、暴露环）；可选/可重配置用 setter；字段注入虽省事但不推荐（不可 final、难测、掩盖依赖膨胀）。
- 架构视角：构造器让"依赖过多"和"循环依赖"在启动期就暴露，是一种设计约束的正反馈。

**加分**：Boot 官方、@ConfigurationProperties 构造绑定、record 化配置，都倾向构造器注入。

## 题 4：Boot 2.6 把循环依赖默认关了，你怎么看？老项目怎么办？

**参考答法**：

- 认同：三级缓存只是"能让应用启动"，不代表设计正确；循环依赖往往意味着职责纠缠，默认关是逼你治理。
- 老项目应对顺序：① 优先真消环（抽公共 Bean、事件解耦、依赖倒置）；② 来不及就用 `@Lazy` 精准破一条边作过渡；③ 最后手段才 `allow-circular-references=true` 全局放开，且必须挂治理工单、设截止。
- 千万别一上来就全局 reopen——那是把架构债重新藏起来。

## 题 5：出现"事务/缓存注解不生效"，和循环依赖有关吗？

**答题要点**：可能相关但不该靠调缓存解决。循环依赖 + AOP 代理时机叠加时，某些边角（如自调用、被提前暴露的对象与最终代理不一致的历史 bug、`@Async` 与循环）会表现为增强丢失。正确方向是消环、避免自调用（拆到另一个 Bean 或用 `AopContext`/注入自身代理）、把增强方法放到被代理的公共入口。

## 高频追问速答

1. 一级缓存能拿到未完成属性填充的对象吗？→ 通过 `allowRawInjectionDespiteWrapping` 等可拿到"原始对象"，但 Boot 默认不允许，因为会导致注入的是原始、成品是代理。
2. 二级缓存能省吗？→ 不能，它缓存"已生成早期引用"的结果，防止同一个半成品在一次创建中被重复从工厂取用产生多个不同对象。
3. 单例池叫什么？→ `singletonObjects`（一级），`getBean` 最终从这里返回成品。
4. `@Lazy` 破环的原理？→ 注入的是一个代理占位，首次真正调用方法时才去解析目标 Bean，从而跳过实例化期的相互需求。
5. prototype 为什么没这机制？→ 原型不入单例池、每次新建，没有"提前暴露同一实例"的落脚点，无法共享半成品。
