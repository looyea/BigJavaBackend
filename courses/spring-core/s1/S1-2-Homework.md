# 作业题 · 依赖注入与循环依赖

## 作业 1：复现三类循环依赖的边界（必做）

分别构造并记录启动结果：

1. 单例 A、B **字段注入**互引 → 启动成功
2. 把其中一条改成**构造器注入** → 启动抛 `BeanCurrentlyInCreationException`
3. 两个 **prototype** Bean 互引 → 启动/获取即失败

**产出**：一张"哪种循环能解、报什么异常"的对照表，并解释构造器循环为什么死锁在实例化之前。

## 作业 2：三级缓存断点走查（必做，本节核心）

在 A↔B 字段注入循环、且 A 被 `@Aspect` 代理的前提下：

- 在 `DefaultSingletonBeanRegistry.getSingleton(...)` 的三级命中处与 `getEarlyBeanReference` 打断点
- 逐步记录：A 的 factory 何时进三级、二级何时出现 A 的早期引用、B 拿到的是不是代理、A 最终成品与早期引用是否同一对象

**验收标准**：画出 A、B 从创建到进一级缓存的时序，标注每一次缓存读写。

## 作业 3：用设计消除循环（必做）

拿一个真实存在的 A↔B 双向依赖（如 OrderService↔InventoryService）：

1. 先复现循环
2. 分别用三种手段各解一次：① 抽出第三个 Bean 下沉公共逻辑；② 用 `ApplicationEventPublisher` 事件解耦；③ 依赖倒置（各自实现接口互相只依赖抽象）
3. 对比三种方案对可测试性、职责清晰度的影响，给出你团队的默认选择

## 作业 4：@Lazy 打破一条边（选做，架构师向）

在必须临时保留循环的遗留模块里，用 `@Lazy` 只打破一条依赖边使 Boot 2.6+ 默认配置下能启动，并写清：这是过渡方案，配套的治理工单应包含哪些验收项（消环后删除 `@Lazy` 的 TODO 与自动化检查）。

## 作业 5：注入方式规范落地（选做，架构师向）

为一个中型服务制定注入规范并给出静态检查思路：必需依赖必须构造器注入、禁止字段注入（ArchUnit 规则示例）、依赖个数超过阈值视为设计异味告警。评估"全量改造 + 禁止 lombok `@RequiredArgsConstructor` 滥用"的成本与收益。
