# 实际面试题 · 事务传播与失效场景

## 题 1：说说七种事务传播行为，重点讲三个常用的

**考察层次**：初级只会 REQUIRED；中级能区分 REQUIRES_NEW/NESTED；高级能讲清嵌套失败时的回滚语义并给场景。

**参考答法**：

1. REQUIRED（默认）：有则加入、无则新建，和调用方同一事务，整体提交/回滚。
2. REQUIRES_NEW：无论如何开新事务，挂起外层；内外层提交回滚互不影响——用于审计、流水这类"不受主业务成败影响"的记录。
3. NESTED：外层有事务时在其内设保存点，内层失败回滚到保存点，外层可选择继续；外层回滚则内层一起没。
4. 其余：SUPPORTS/NOT_SUPPORTED（有无皆可/挂起转非事务）、MANDATORY（必须在外层事务内否则报错）、NEVER（必须非事务否则报错）。

**追问**：REQUIRES_NEW 和 NESTED 都能"内层出错不影响外层继续"，区别？→ REQUIRES_NEW 是完全独立事务，内层可独立提交，外层回滚也拉不回已提交的内层；NESTED 属外层事务的一部分，靠 savepoint，外层一旦回滚内层未提交的也一起回滚。

## 题 2：`@Transactional` 什么时候会失效？

**答题要点**：非 public、自调用绕过代理、异常被吞、checked 异常未配 rollbackFor、对象不是 Spring Bean、事务管理器/数据源配错、存储引擎不支持事务、传播用错（NOT_SUPPORTED/NEVER 以非事务跑）。核心归因：**要么代理增强没触发，要么回滚规则没命中，要么根本不在事务里**。

## 题 3：一个方法里先更新库存再调远程风控，风控超时把事务拖很长，怎么办？

**结构化回答**：

1. 问题本质：事务内做 RPC = 长事务，长时间占用数据库连接，连接池易被打满、死锁概率上升。
2. 优化：把 RPC 移出事务边界——事务内只做必须原子化的 DB 操作；远程调用改为提交后异步（`afterCommit` 事件 / MQ / 编排）。
3. 若风控必须先于落库：拆成"预占（短事务）→ 调风控 → 确认/补偿（短事务）"，用状态机 + 补偿保证最终一致。
4. 兜底：给事务设 `timeout`，连接池监控活跃/等待时间。

**加分**：金融场景强调"绝不用长事务换强一致，宁可短事务 + 补偿/对账"。

## 题 4：下单成功要发优惠券，怎么保证"事务回滚了券没发、事务提交了券一定发"？

**答题要点**：这是本地事务与外部副作用的一致性问题。单靠 `afterCommit` 能做到"回滚不发"，但做不到"提交后一定发"（提交后进程崩溃就漏发）。完整方案：**本地消息表/事务消息**——在同一个 DB 事务里写业务数据 + 一条待发送消息（原子），提交后由投递任务/监听发 MQ，消费端幂等；或用 RocketMQ 事务消息的半消息 + 回查。引出分布式事务（见分布式分区）。

## 高频追问速答

1. `@Transactional` 加在类上和方法上区别？→ 加类上对所有 public 方法生效；方法上更精准；同时存在时方法级配置覆盖类级。
2. 事务隔离级别在哪配？默认是什么？→ `@Transactional(isolation=...)`，默认 `DEFAULT` 跟随数据库（MySQL 默认 REPEATABLE_READ）。
3. 只读事务有什么用？→ `readOnly=true` 提示优化、禁写、某些驱动/代理可用于读写分离路由到从库。
4. 同类里 public A 调 public B（都 @Transactional）会怎样？→ 自调用不走代理，B 的独立事务语义失效，实际只在 A 进入代理时开的那个事务里。
5. rollback 和 commit 由谁决定？→ `TransactionInterceptor`（around 通知）根据方法是否正常返回/抛出匹配回滚规则的异常来 commit 或 rollback。
