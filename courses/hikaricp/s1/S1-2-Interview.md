# 连接池参数调优与容量测算 · 面试题

## 题 1：HikariCP 的池大小怎么定？越大越好吗？

- 不是。吞吐受数据库 CPU/锁/IO 上限约束，超过承受力后更多连接加剧排队与锁竞争，吞吐下降、延迟上升。
- 起点用经验公式 `核数×2 + 有效磁盘数`，再用压测找"吞吐-延迟拐点"，池定在拐点左侧。
- 加分：给出典型 OLTP 服务 10~20 就够、开几百反而更差的实测直觉。

## 题 2：`minimumIdle` 和 `maximumPoolSize` 怎么配合？什么是固定池？

- `min=max` 即固定池：连接数恒定，突发不必临时建连（TCP+认证+SSL 代价高），官方推荐。
- 动态池压低 `minimumIdle` 省空闲资源，但突发首批有建连延迟，且 `idleTimeout` 才有意义。
- 加分：说明固定池下 `idleTimeout` 不起作用、抖动更小更可预测。

## 题 3：`maxLifetime` 为什么必须小于数据库的 `wait_timeout`？

- 若服务端按 `wait_timeout` 空闲断开连接、而池仍持有并借出它，应用拿到的就是死连接 → `Communications link failure`。
- 让 `maxLifetime` 显著小于 DB 侧空闲断开时间并留 30~60s 余量，池会在被服务端踢掉前主动换连接。
- 加分：提到 `maxLifetime` 加随机抖动防同时到期、云库/代理/防火墙更隐蔽的空闲断开需实测。

## 题 4：`connectionTimeout`、`idleTimeout`、`keepaliveTime` 各管什么？

- `connectionTimeout`：从池借连接的最长等待，超时抛异常（快速失败，别设太长拖死线程）。
- `idleTimeout`：非固定池下回收超出 `minimumIdle` 的空闲连接。
- `keepaliveTime`：定期探测空闲连接，提前剔除被中间层静默断开的死连接。
- 加分：强调它救不了"连接被借走没归还"的泄漏——那是 `leakDetectionThreshold` 的活。

## 题 5：压测时数据库端出现大量锁等待，怀疑池配置问题，你从哪查？

- 先看池大小是否远超 DB 承受力（大池把并发全压到 DB 引发行锁竞争），必要时收敛 `maximumPoolSize`。
- 再看是否存在慢事务长时间持有连接/锁，把池占满引发连锁等待。
- 加分：区分"池太小借不到"（`connectionTimeout` 超时报错）与"池太大压垮 DB"（DB 侧锁等待/连接数告警）两类相反症状。

## 题 6：如何向团队解释"我们不该把连接池开到 500"？

- 数据库能高效承载的并发连接有限，500 连接里大量在 DB 端排队争锁、做无用上下文切换。
- 吞吐由"最短木板"（DB）决定，池只需喂饱 DB 即可，超出部分是负担；用拐点曲线说话。
- 加分：结合 HikariCP 官方"小池更快"的理念与"池大小 = 数据库承受力"的一句话总结。
