# 秒杀 / 短链 / Feed 流 · 作业题

> 本节作业 3 题：写一段真会超卖的秒杀扣减并修好、实现 base62 短码发号、用推拉结合重算一个 Feed 场景的写放大。

## 作业 1：复现超卖并用 Lua 修好（动手）

用 Redis 模拟库存=10，起 100 个线程并发"抢"：

```java
// 例子目的：先用错误写法复现超卖, 再用 Lua 原子扣减修复, 对比输出
// 错误写法(反例): 先 get 判断 >0 再 decr —— 两步之间有并发窗口
Long stock = redis.get("stock");                 // 100 个线程几乎同时读到 stock=1
if (stock > 0) redis.decr("stock");              // 结果: 都判断通过一起 decr, 库存被扣成负数 = 超卖!
// 正确写法: 判断+扣减合成一个 Lua, Redis 单线程执行不可分割
String lua = "local s = tonumber(redis.call('get',KEYS[1])) " +
             "if s > 0 then return redis.call('decr',KEYS[1]) else return -1 end";   // 输出: 恰好 10 人成功, 其余 -1
redis.eval(lua, 1, "stock");
```

要求：① 跑错误写法，贴出"成功数 > 10"的超卖现场；② 换 Lua 后成功数恰好=库存数；③ 再加 reqId 幂等（同一用户重复提交只生效一次），构造重复请求验证去重。

**验收标准**：超卖前后两次成功计数对比 + Lua 版本代码 + 幂等键去重测试。

## 作业 2：实现 base62 短码发号器（动手）

1. 写 `toBase62(long)`：把自增 ID 映射到 `[0-9a-zA-Z]` 62 进制字符串，验证 id=0、id=61、id=62、id=62^6-1 的输出（末项应为 6 位全满），确认 6 位容量 ≈ 56.8 亿；
2. 讨论发号：单库 `AUTO_INCREMENT` 作为 ID 源在高并发下的瓶颈，改用号段/Leaf 思路（一次取一段号在内存分发），说清为什么中心发号能同时避免"冲突重试"和"暴露业务量"；
3. 存与跳：设计 `code → longUrl` 的 KV 表 + Redis 热点缓存 + 跳转接口，给 301 与 302 两种实现，并各写一句"适合什么业务"。

**交付物**：toBase62 代码 + 4 个边界值输出 + 号段发号一句话原理 + 301/302 两个接口与适用场景。

**提示**：这题考点是把"短、唯一、不冲突、不暴露业务量"四个约束同时满足的思路讲圆。

## 作业 3：给 Feed 场景算一笔推拉账（设计+计算）

场景：某平台有 1000 万普通用户（平均关注 50 人）和 1 万个大 V（平均粉丝 100 万）。请估算：

```text
例子目的：用数字证明"纯写扩散会被大 V 写崩", 从而得出推拉结合
纯写扩散: 大 V 发 1 条 → 要写 100 万条收件箱; 若 1 万大 V 每人每天发 3 条 → 写 = 1e4×3×1e6 = 3e10 扇出/天  ← 爆
纯读扩散: 普通用户读 1 次 → 归并 50 路时间线; 峰值读 QPS 高时归并成本 ×50  ← 慢
推拉结合: 普通用户(粉丝少)走推 → 扇出 50 可忽略; 大 V 走拉 → 发时只写自己 1 条, 读时把收件箱 + 关注的大 V 时间线归并
结论: 用"粉丝数阈值"决定推还是拉, 把写洪峰从 3e10 砍到大 V 完全不扇出
```

**交付物**：三种模型各自的"写扇出/读归并"量级估算 + 一个"粉丝数超过 X 走拉"的阈值设定理由 + 一句话总结推拉结合为何两头都省。

**提示**：这题真正的考点是用数量级论证设计选择——不是背"推拉结合"四个字，是能算出为什么必须这么选。
