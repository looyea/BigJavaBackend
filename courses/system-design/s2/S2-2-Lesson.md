## 一、限流器：四算法与两种落地

限流是系统入口的保命阀。四个经典算法各有性格：

```text
例子目的：四种限流算法的差异不在"能不能限", 在"对突发流量友好度"与实现成本
计数窗口: 每固定窗口计数, 超阈值拒绝  → 简单, 但窗口边界可 2 倍突发(17:00:59 和 17:01:00 各放满)
滑动日志: 记录每次请求时间戳, 统计最近 N 秒内条数  → 精确, 但内存随请求量涨, 高 QPS 存不下
漏桶:     请求进水桶, 恒定速率流出(削峰整形)  → 输出极平滑, 但不允许任何突发, 后端利用率低
令牌桶 ★: 恒速往桶里放令牌, 请求取令牌才放行, 桶有容量 → 允许有限突发(桶内存着的令牌), 最常用
```

```java
// 例子目的：令牌桶骨架 —— 关键在"惰性计算"而非真起线程放令牌
double rate = 100; long capacity = 200;           // 每秒 100 个令牌, 桶容量 200(允许短暂突发攒到 200)
tokens = Math.min(capacity, tokens + elapsed*rate);  // 惰性补算: 距上次请求过了 elapsed 秒, 补 elapsed*rate 个
if (tokens >= 1) { tokens--; allow(); } else { reject(429); }  // 结果: 无后台线程、无定时器、请求驱动计算
// 错误用法: 起一个 1ms 定时器往 Redis 塞令牌 —— 高并发下定时器精度+Redis 写压力双杀
```

**单机 vs 分布式**：单机用 Guava `RateLimiter`（令牌桶）足够；分布式限流要**全局计数**——典型方案 Redis + Lua（原子令牌桶或滑动窗口），代价是每次判定一个 Redis 调用（热点可加本地令牌桶预分片）；另一派集群整体令牌桶（每实例分得 rate/N，本地扣减 + 异步向中心申请，即"预分片令牌桶"）。

## 二、排行榜：ZSet 的三种典型用法与三个坑

实时排行榜（游戏积分榜/热搜/直播间礼物榜）标准选型是 Redis ZSet（跳表，O(logN) 有序维护 + 范围查询）：

```java
// 例子目的：ZSet 做排行榜的三个动作与一个核心坑
redis.zadd("rank:2026-09", 150, "player:42");            // 更新分数(同 key 覆盖旧分, 原子)
List<ScoredEntry> top = redis.zrevrange("rank:2026-09", 0, 99, WITH_SCORES);  // 取前 100, 有序
long rank = redis.zrevrank("rank:2026-09", "player:42");  // 查某人排名(0-based)
// 坑一 同分排序: ZSet 按 score+lex 排序, score 相同按 member 字典序 → "同时到 100 分谁前?" 业务要先到先排
//   解法: 把分数编码成"score + (1e12 - 首次到达时间戳)"使先到者分更高, 或用双排序字段
// 坑二 时间维度: "日榜/周榜/总榜" → 拆 key(rank:daily:20260927), 过期清理; 总榜实时聚合 or 定时合并
// 坑三 大排名分页: zrevrange 前 N 万可走, 查"某人在第 80 万位"可以 zrevrank 但展示前后十名需要二次查询
// 错误用例: 用 MySQL ORDER BY score DESC LIMIT 1000000,10 做深分页 → 越翻越慢, 百万级必死
```

**加分设计**：排行榜的"写入洪峰"（百万人同时得分变化）用 **ZSet 天然覆盖同 key 旧分** 解，不需要先删后加；但如果是"增量得分"要 `zincrby` 保原子；数据持久化（ZSet 是内存）用 RDB/AOF 或异步落 DB 快照。

## 三、附近的人：GeoHash 降维与多桶合并

"附近的人/骑手/车辆"本质是**空间索引 + 半径查询**——暴力算距离 O(N) 不可能，核心思路是把 2D 经纬度降到 1D 可排序编码：

```text
例子目的：GeoHash 原理、Redis GEO 实现、边界问题与正解
原理: 把经纬度做区间二分编码成字符串(如"wx4g0e1k"), 前缀相同=地理相近, 字符串排序=空间聚集
实现: Redis GEO (底层 ZSet, score=GeoHash 值), GEOADD + GEORADIUS 一条命令查半径内成员
精度: GeoHash 每多 1 字符精度提升约 2.5 倍; "wx4g0"≈±2.4km, "wx4g0e"≈±0.6km, "wx4g0e1"≈±0.07km
边界问题: 查"以 A 为圆心 R 为半径"时, GeoHash 分桶是矩形, A 在桶边缘 → 真实圆跨相邻桶, 只查当前桶会漏
正解: 取中心点 GeoHash 前缀 + 相邻 8 个桶前缀, 多桶候选集 → 精算 Haversine 距离过滤; Redis GEORADIUS 帮你封装了这步
规模分治: 若需自己分桶(不用 Redis GEO), 取 GeoHash 前 N 位作分桶键, 同桶存一起, 跨桶查询取 9 宫格
```

**工程取舍**：Redis GEO 适合活跃点 < 几千万规模（全内存 ZSet）；更大/冷数据用 **PostGIS / Elasticsearch Geo 查询 / H3**（Uber 六边形分桶解决边界问题更优雅）。附近的人还要处理"实时性 vs 写成本"：用户移动频繁 GEOADD 更新，加节流（如位移>50m 或 >30s 才更新），否则百万人在线 ZSet 写爆。

## 四、常见线上问题

- 分布式限流 Redis 挂了等于没限：要么快速失败（宁可限死不可放穿），要么退化为本地限流（阈值缩到 1/N）；
- ZSet 当无界用：百万 member 常驻 + 不清理 → Redis 内存膨胀、热 key 单分片打满；要分日 key + 过期 + 按维度拆；
- 附近的人返回一堆"500m 外的人"（桶边界精度不够）：检查 GEORADIUS 的 count 预过滤与精算距离是否二次筛了；GeoHash 前缀太短精度不够；
- 限流 + 排队混淆：限流是"超过就拒"，排队是"超过就等"——秒杀用排队页、API 保护用快速 429，场景不同算法不同。

## 五、小结与过关要点

三道题的共同骨架：**高并发写入 → 选对数据结构 → 解决分布/一致性/边界三类工程细节**。限流选令牌桶（允许突发、惰性计算）+ 分布式用 Redis Lua 或预分片；排行榜选 ZSet（同分坑用时间戳编码、日榜按 key 过期、大排名二次查询）；附近的人用 GeoHash/ZSet（边界用九宫格合并/Redis 封装、写入加节流）。过关自测：每道题你能否说清"哪个数据结构决定了这个系统的天花板"以及"边界/深分页/同分这三类坑怎么填"。
