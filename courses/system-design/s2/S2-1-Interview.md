# 秒杀 / 短链 / Feed 流 · 实际面试题

## 题 1：设计一个秒杀系统，100 万人抢 100 件货，怎么不超卖也不崩？

**考察点**：高频压轴题，考漏斗式削峰 + 原子扣减 + 异步落库的完整链路。

**参考答案**：核心是把 100 万请求做成一个**漏斗**，逐层过滤，只有真·可买请求才走到扣减。① **入口限流**：网关按 IP/用户维度令牌桶，超阈值直接 429 或排队页，先拦掉超额并发；② **削无效流量**：页面静态化 + 答题/验证码挡掉脚本与乱点；③ **售罄本地拦**：活动前把库存预热到 Redis，前端有"售罄"标记，库存=0 直接在就近层返回，不再打下游；④ **原子扣减**：用 Redis Lua 把"判断库存>0 + decr"合成一个不可分割操作（绝不能 get 判断再 decr，两步之间有并发窗口会超卖），抢到的极少数请求才继续；⑤ **异步落库**：扣减成功发 MQ，订单/DB 按平稳速率消费落库，把瞬时写洪峰摊平——用户看到"抢购成功"不依赖落库完成，最终一致即可。再叠加**幂等（reqId 去重）+ 一人一单 + 热点 sku 本地缓存挡读**。100 件货，最终只有 100 个请求通过 Lua，DB 只会面对这 100 条写。

**追问**：
- 扣了库存但没付款怎么办？——"预扣→支付超时/取消→回补"状态机，超时未支付把 Redis 库存与 DB 一起回补；
- Redis 扣减和 DB 怎么对齐、会不会 Redis 说成功 DB 落不下？——MQ 落库要幂等 + 对账兜底；Redis 是"资格判定"，DB 是"事实记录"，两者用最终一致 + 定期对账收敛，落不下的进补偿队列。
- MySQL 的 `update ... where n>0` 为什么不行？——它能防负库存但扛不住 100 万并发同时打这行：行锁排队、连接池耗尽、雪崩，问题在吞吐不在正确性。

**加分点**：主动点出"秒杀不需要强一致，是用可用性/吞吐换一点一致性延迟"，并说出降级预案（活动开关、限流阈值动态调、Redis 挂了直接快速失败不穿到 DB）。

## 题 2：设计一个短链系统，短码怎么保证又短又唯一还不冲突？

**考察点**：发号方案取舍 + 读密集存储 + 重定向语义。

**参考答案**：短码生成有三条路，我都比过：**A) 哈希取前 6 位**——无状态简单，但 MD5/Murmur 截断必然有碰撞，量越大撞得越频繁，要冲突重试，不可控；**B) 随机生成 + 查重**——每次 insert 前先查有没有，冲突就重来，高并发时重试风暴、写放大；**C) 中心发号器自增 ID + base62 编码**——把全局唯一自增 ID 转成 62 进制（0-9a-zA-Z），天然唯一无冲突、长度可预估，6 位 base62 就有 62^6≈56.8 亿容量，够用很久。工业界选 C。发号器本身不能用单库 `AUTO_INCREMENT` 顶高并发（写瓶颈 + 暴露业务量），改成**号段/Leaf**：一次取一段号在内存分发。存储用 KV/HBase 按短码哈希分片（读极多），热点链上 Redis。跳转接口 `GET /{code}` 先查缓存未命中回源，返回 301 还是 302 看需求。

**追问**：
- 301 和 302 到底怎么选？——301 永久重定向被浏览器/CDN 缓存，省带宽省回源，但之后点击不再回源，**统计不到访问次数也无法改向**；302 每次回源便于埋点统计和动态改向。要数据分析就 302（可配异步点击日志）。
- 会不会有人拿 base62 递增规律猜到别人的链接？——把发号 ID 做映射混淆（如异或/乘逆元）或双射打散，避免顺序暴露；这也是"不暴露业务量"的一部分。
- 想支持自定义短别名怎么办？——别名走人工注册 + 唯一约束，和发号短码放同一张 KV、冲突检测，属功能增强不改主链路。

**加分点**：主动说清"读写比极端偏读决定这个系统的成败在缓存与分片，不在生成算法"，展示估算驱动设计的意识。

## 题 3：微信朋友圈/微博首页这类时间线，推还是拉？大 V 怎么办？

**考察点**：推拉模型取舍与混合方案，能否用数量级论证。

**参考答案**：两种根本模型各有致命代价。**读扩散（pull）**：发帖不分发，看的时候实时把"我关注的 N 个人的时间线"归并——省写、发得爽，但读要归并 N 路，关注的人一多就慢、大 V 的时间线还热。**写扩散（push）**：发帖时把动态写进每个粉丝的收件箱——读极快（只读自己一路），但大 V 发一条要写百万粉丝收件箱，是写放大 + 写洪峰。工业界答案是**推拉结合**：按**粉丝数量级分治**——普通人（粉丝少）发帖走推，扇出可忽略；大 V 发帖不扇出、只存自己的时间线，用户刷新时把"自己的推送收件箱"和"所关注大 V 的时间线"做归并（拉）。这样把纯 push 的写洪峰（我算过：1 万大 V 每人日发 3 条 × 百万粉丝 = 3e10 扇出/天）和纯 pull 的读爆炸两头都砍掉。翻页用 (maxId 或 时间戳+id) 游标做增量拉，避免 offset 深分页。

**追问**：
- 推拉结合下新动态的一致性怎么保证？——推送收件箱天然是最终一致的异步写，用户下拉刷新可接受秒级延迟；首页缓存要能感知"有新内容"（增量游标 + 未读计数）。
- 怎么定大 V 阈值？——按写扇出成本和读归并成本平衡点定，例如粉丝 > 10 万走拉；本质是"单条扇出上限"控制。
- 已读/未读、删帖怎么在推模式收件箱里处理？——删/改走反向消息（timeline 打删除标记 + 收件箱增量修正），这也是为什么收件箱常存 ID 引用而非内容副本。

**加分点**：现场给一个"粉丝数阈值"的数量级论证（像我上面算的 3e10），说明推拉结合不是背来的名词而是算出来的选择——这最能拉开候选人差距。
