# 限流器 / 排行榜 / 附近的人 · 实际面试题

## 题 1：设计一个分布式限流器，要求允许合理突发但保护后端不被打穿。

**考察点**：算法选择（令牌桶 vs 漏桶）+ 分布式落地（Redis Lua vs 预分片）+ 降级方案。

**参考答案**：算法选**令牌桶**——恒速放令牌、请求取令牌才放行、桶容量允许有限突发，兼顾保护和吞吐（漏桶不允许任何突发，后端利用率低；计数窗口有边界 2 倍突发）。单机用 Guava RateLimiter 够；分布式要全局计数，两种落地：① **Redis + Lua**：把令牌桶逻辑（惰性计算 elapsed×rate、取令牌）写在一个 Lua 里保原子，每次判定一个 Redis 调用（延迟可控在 1ms 内），好处是精确、可动态调 rate，代价是多一跳网络；② **预分片令牌桶**：中心维护总桶，每实例异步申请配额（一次拿一批 rate/N），本地扣减不每请求打 Redis，适合超低延迟场景，代价是突发精度略差。**降级**：Redis 挂了必须快速失败或退化为本地限流（阈值缩到约 1/N），宁可限死不可放穿。

**追问**：
- 为什么令牌桶不真起线程放令牌？——惰性计算：每次请求按 elapsed×rate 补算即可，省线程/定时器精度/空跑开销。
- 如何动态调整 rate？——Redis Lua 把 rate/capacity 读自 KEYS 对应 Hash 配置，运维改一个字段所有实例下次请求就生效，无需重启。
- 限流粒度怎么做"用户维度"？——在 key 里编入 userId/tenantId（`rate:{userId}:api`），ZSet 或 Hash 计数，每用户独立桶；热点用户走单独阈值。

**加分点**：主动给出"限流 + 排队"的场景对比（秒杀用排队不丢用户 vs API 网关用快速 429 保后端），以及熔断联动（连续被限触发 circuit-breaker 自动降级），展示限流只是流控体系的一层。

## 题 2：直播间要实时礼物榜，每秒几万条送礼消息更新排名，你怎么设计？

**考察点**：高写入吞吐 + 实时排序 + 分页展示的工程细节。

**参考答案**：核心选型 **Redis ZSet**——member=userId、score=累计礼物金额，`ZINCRBY` 原子加分（O(logN)），天然支持覆盖同 key 旧分。每秒几万写入没问题（Redis 单实例 ~10 万 ops/s），写入洪峰正是 ZSet 甜区。三个高频追问的坑我直接讲方案：**同分排序**——ZSet score 相同按 member 字典序，直播业务要"先到先排"，解法把 score 编码为 `金额×1e10 + (1e10 - 首次到达时间戳后10位)`，先到者 score 更大；**时间维度**——场次 key `rank:live:{roomId}:session`，结束设 TTL 或异步归档 DB；**分页/大排名**——`ZREVRANGE 0 99` 取 top100 展示，"我在第几位 + 前后 5 名"用 `ZREVRANK` + `ZREVRANGE (rank-5) (rank+5)` 二次查。写入侧如果"送礼记录"也要查（不只是分数），另走 MQ → DB 异步落流水，榜单 ZSet 只管排名。

**追问**：
- 如果礼物榜要"小时榜"和"总榜"并存？——分 key（rank:live:{id}:hourly 按小时过期 + 总榜不自动过期）；小时切定时把当小时数据合并到总榜（ZUNIONSTORE），避免实时归并成本。
- 几十万在线观众同时刷新 top100，读压大？——ZREVRANGE 走只读从节点/本地缓存（几百毫秒 TTL）；top100 数据量极小，天然适合本地缓存挡读。

**加分点**：主动提"写入洪峰如果单机 Redis 扛不住怎么办"——按 roomId 分 key（不同直播间天然分片），或者用 Redis Cluster；并说"榜单持久化用 AOF everysec + 开播从 DB 恢复 score"保证 Redis 挂后重启不丢排名。

## 题 3：附近的人怎么查？如果用户上亿怎么不退化成 O(N) 遍历？

**考察点**：GeoHash 降维 + 边界处理 + 规模选型。

**参考答案**：暴力算距离 O(N) 不可行，核心思路是**降维分桶**：把经纬度编码成 GeoHash 字符串（区间二分 → 前缀相同=地理相近），按前缀分桶，查询只扫目标桶候选集而非全部用户。活跃点上千万级用 **Redis GEO**（底层就是 ZSet，score=GeoHash 的 52bit 截断编码，天然支持范围查询），`GEOADD` 更新位置 + `GEORADIUS` 一条命令查半径内——它帮你封装了九宫格多桶查询。但要知道底层坑：GeoHash 分桶是**矩形**，查圆如果只查中心桶会**漏边界点**（正解=取中心 + 8 相邻桶候选再精算 Haversine 过滤）。工程注意：写更新加**节流**（位移>50m 或 >30s 才 GEOADD，否则百万人在线 ZSet 写爆）；查询结果要加 **COUNT 预过滤**（先按 GeoHash 精度粗筛、再按距离精算）。规模更大或需要持久化：用 **PostGIS**（GiST 空间索引）、**Elasticsearch Geo**（BKD-Tree）、**H3**（Uber 六边形分桶，天然消除矩形边界问题）。

**追问**：
- GeoHash 的精度怎么选？——位数越多桶越小精度越高；5km 搜索取 ~4 位（±39km）做粗筛再精算即可，6~7 位给 1km 内；不是越精确越好——太细要更多桶合并。
- 为什么 Redis GEO 用 ZSet 不用 KV 前缀匹配？——ZSet 的 score 是数值型 GeoHash 编码，天然支持范围查询（ZRANGEBYSCORE），不需要 KEYS 前缀扫描那种 O(N) 操作。
- 上亿用户全内存放得下？——活跃用户（在线且最近上报位置）可能才几百万到千万级，只放活跃集；冷用户落 DB/ES，查"附近"只查活跃，合理裁剪规模。

**加分点**：主动说出 H3（六边形分桶）相比 GeoHash（矩形）在邻居查询与边界对称性上的优势，以及为什么 Uber 外卖选 H3 而非 GeoHash——展示知识面不止 Redis。
