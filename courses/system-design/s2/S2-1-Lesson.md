# 秒杀 / 短链 / Feed 流

> 本节难度：★★★★★
> 重要程度：★★★★★
> 学习产出：能完整设计三大高频经典题——秒杀（读多写少瞬时洪峰：限流→库存预热到 Redis→Lua 原子扣减→MQ 异步落库→防超卖防刷）、短链（发号器 base62 + KV 存储 + 301/302 取舍 + 热点缓存 + 分片）、Feed 流（读扩散 pull vs 写扩散 push 的取舍、推拉结合、时间线游标）；并能说清每道体的"瓶颈本质"和最容易被面试官追问的点。

```flow
例子目的：三道题各有一个"矛盾内核", 抓住内核就抓住设计主线
秒杀   内核: 极少库存 × 瞬时超大并发 → 矛盾=不能超卖又要扛洪峰 → 主线=层层漏斗削峰 + 原子扣减
短链   内核: 读极多写少 + 短码唯一且要短 → 矛盾=唯一性 vs 长度 vs 无冲突 → 主线=中心发号 + KV + 缓存
Feed   内核: 大 V 发一条万人要看到 → 矛盾=实时(push贵) vs 省(push少) → 主线=推拉结合按粉丝数分治
```

## 一、秒杀：把洪峰挡在数据库之前

秒杀本质是"漏斗"——请求从入口到扣库存逐层过滤，绝大多数在到达 DB 前就被挡掉或快速失败。链路顺序即得分顺序：

```java
// 例子目的：秒杀五层漏斗, 每层拦掉大部分流量, 只有真·可买请求才走到扣减
// ① 入口限流: 网关/IP/用户维度令牌桶, 超阈值直接 429 或排队页(接 sentinel 限流)
// ② 静态化+答题/验证码: 削掉机器脚本与无效请求
// ③ 库存预热到 Redis + 前端"售罄"标记: 库存=0 直接本地拦, 不再打下游
boolean ok = redis.eval(        // ④ 原子扣减: Lua 保证"判断+扣减"不被并发撕裂(反例: get 再 decr 会超卖)
    "if redis.call('get',KEYS[1])>0 then return redis.call('decr',KEYS[1]) else return -1 end",
    1, "seckill:stock:1001");
if (ok) mq.send(new SeckillOrder(userId, skuId, reqId));  // ⑤ 异步落库: MQ 把瞬时写摊平成 DB 平稳消费
// 结果: 100 万请求经①②③拦掉大半, 真正打到 Redis 扣减的已是可承接量, DB 只面对 MQ 匀速消费
// 错误用例: 用 MySQL `update stock set n=n-1 where id=? and n>0` 直接顶洪峰 → 行锁排队、连接池耗尽、雪崩
// 防重/防刷: reqId 幂等键(同用户重复请求只生效一次)、一人一单(用户维度已购标记)、热点 sku 加本地缓存挡读
```

**最常被追问的两点**：① **为什么 Redis 扣了还要 MQ 落库**——Redis 抗读抗扣减、MQ 削写峰，落库慢不影响用户"抢购成功"感知，最终一致即可；② **超卖怎么根治**——扣减必须原子（Lua/单线程），且扣减与订单落库用"预扣→支付确认→回补"状态机对齐，失败/超时回补库存。

## 二、短链：中心发号换"短且唯一"

短链读写比极端（读极多），核心矛盾是**短码要短、要全局唯一、要不冲突**。三种生成法对比后选发号器：

```java
// 例子目的：短码生成三选一, 讲清为何"自增 ID + base62"最平衡
// A) 哈希(MD5/Murmur 取前 6 位): 无状态但有碰撞, 要冲突重试 —— 不可控
// B) 随机+查重: 每次 insert 前查是否存在, 高冲突时重试风暴 —— 写放大
// C) 中心发号(自增 ID) → base62 编码: 天然唯一无冲突、码短且可预估长度 ★推荐
long id = leaf.nextId();                       // 全局自增/号段发号器(接 S3-1), 避免单库自增瓶颈与暴露业务量
String code = toBase62(id);                    // 6 位 base62 ≈ 56.8 亿容量(62^6), 够用到天荒地老
kv.put(code, longUrl, TTL_or_permanent);       // 存 KV/HBase: 读多 → 按 code 哈希分片; 永久链接另设冷热
// 跳转: GET /{code} → 查缓存(Redis 热点) → 未命中回源 KV → 302(要统计点击) 或 301(要省一跳/可缓存)
// 错误用例: 把短码做 md5 直接返回 → 碰撞率随量级上升, 上线半年某天 insert 主键冲突开始丢链接
```

**301 vs 302 是高频考点**：301 永久重定向被浏览器/CDN 缓存、之后点击不再回源（省带宽）但你**统计不到访问次数、也无法改向**；302 每次回源，便于埋点统计与动态改向。要统计就用 302，或"302 + 异步写点击日志"。

## 三、Feed 流：推还是拉，按大 V 分治

时间线（我关注的人的动态聚合）有两种根本模型，各有致命代价：

```text
例子目的：读扩散 vs 写扩散的取舍, 以及工业界的"推拉结合"答案
读扩散(pull/拉): 发时不分发, 看时实时把"我关注的 N 人的时间线"归并  → 省写、发得爽; 但读时归并 N 路, 大 V 多则读爆炸、慢
写扩散(push/推): 发时把动态写进"所有粉丝的收件箱(推模式)"  → 读极快(读自己收件箱一路即可); 但大 V 发一条要写百万粉丝收件箱 = 写放大、洪峰
推拉结合(工业主流): 普通人发→推(粉丝少, 写得起); 大 V 发→只存自己时间线, 用户读时把自己的收件箱 + 所关注大 V 的时间线做归并(拉)  → 写放大与读放大两头都砍
时间线游标: 用 (maxId 或 时间戳+id) 做增量拉取游标, 避免 offset 深分页(接 mybatis 深分页坑)
```

**瓶颈本质**：Feed 是**读密集 + 写也要分发**，难点在"如何不为大 V 写崩"。推拉结合的核心是**用"账号粉丝数量级"决定推还是拉**——这正是分层分治思想（接 ddd 限界、高并发包）。首页缓存要处理"新动态到达"的一致性（推模式收件箱天然是最终一致的写，用户下拉刷新可接受秒级延迟）。

## 四、三题共同心法

- 都先问**读写比**：秒杀/短链读重（靠缓存挡）、Feed 读写都重（靠分发模型）；
- 都靠**逐层卸载**：秒杀用漏斗、短链用缓存+CDN、Feed 用推拉分治；
- 都讲**一致性让步**：三者都不需要强一致，用"最终一致 + 幂等 + 状态机"换吞吐（接 dist-theory、dist-data）。

## 五、小结与过关要点

秒杀考"洪峰下不超卖"——五层漏斗 + Lua 原子扣减 + MQ 削峰 + 幂等防重；短链考"短码唯一且短"——中心发号 + base62 + KV 分片 + 301/302 取舍；Feed 考"大 V 不写崩"——推拉结合按粉丝数量级分治 + 时间线游标。过关自测：每道题你能否一句话点出它的"矛盾内核"，再顺着内核推出三层以上的设计与对应取舍。
