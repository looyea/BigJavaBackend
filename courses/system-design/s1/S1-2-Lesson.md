# 容量估算与瓶颈识别

> 本节难度：★★★★☆
> 重要程度：★★★★★
> 学习产出：掌握系统设计里 8 个必背数字（人均日活时长、读写比、单机 QPS/存储、内存/磁盘/网络量级换算、2 的幂、几个 9 的停机时间）；能用"日活→峰值 QPS→存储/带宽/内存"三步把模糊规模变成可决策的数量级；会用"木桶最短板的三板斧"（先测后猜、按请求链路逐跳定位、区分 CPU/IO/内存/网络瓶颈类型）识别系统瓶颈；能估算缓存命中率、分片数、副本容量。

```flow
例子目的：估算的目的不是精确, 是"数量级对了它就有解、错得离谱架构就崩"
输入三要素:  DAU(日活) | 人均操作数 | 读写比
主链路换算:  DAU × 人均请求 / 86400  = 平均 QPS;  平均 QPS × (5~10 峰值系数) = 峰值 QPS
派生:       峰值 QPS ÷ 单机安全 QPS = 需要多少实例;  记录数 × 单条大小 × 保留期 = 存储;  QPS × 单响应大小 = 带宽
```

## 一、八个必背数字（把心算时间压到最低）

面试里估算要脱口而出，靠的是把常用锚点数背下来，现场只做乘除：

```text
例子目的：这组数背熟, 估算从"卡壳计算"变成"套公式", 且给出常见取值理由
1) 时间: 1 天 ≈ 8.64 万秒(取 10 万好算); 1 年 ≈ 3.15e7 秒 ≈ π×10^7
2) 2 的幂: 2^10=1KB, 2^20=1MB, 2^30=1GB, 2^40=1TB —— 每级 1024, 10 亿=2^30
3) 人均: 一个重度 App 用户日均使用 ~1 小时, 刷 ~100 次; 一般 10~50 次操作
4) 单机锚点: 一个普通 Web 服务单机安全 QPS ~1000(保守); 缓存 Redis 单实例 ~10 万 ops/s
5) 存储锚点: 一条结构化记录 ~0.5~1 KB; 一张图片 ~100 KB~1 MB; 一条短视频 ~10 MB
6) 网络: 内存访问 ~100ns, SSD 读 ~100μs, 同机房 RTT ~0.5ms, 跨城 RTT ~50ms, 跨国 ~200ms
7) 读写比: 社交/内容类常 读:写 = 100:1;  IM 接近 1:1; 先问清再取
8) 可用性换算: 99.9%→年停 8.76h, 99.99%→年停 52.6min, 99.999%→年停 5.26min(见 dist-theory)
错误用法: 把峰值系数乱取 100 倍吓唬人 —— 取整要能被追问住, 一般 5~10 倍足够
```

## 二、三步估算法：从 DAU 到该买几台机器

以最经典的"日活 → 峰值 QPS → 实例数/存储/带宽"为主线：

```java
// 例子目的：一个能直接口算的模板(数字取整, 展示推理链而非精确值)
// 场景: 设计信息流 Feed, 假设 DAU=1 亿, 人均刷新 20 次/天, 每次拉 20 条, 读写比 100:1
long avgReadQps  = 1e8 * 20 / 86400;         // ≈ 2.3 万 平均读/秒;  结果: 取整约 2~3 万
long peakReadQps = avgReadQps * 10;           // 峰值系数取 10 → ≈ 23 万 读/秒   ← 决定要不要缓存/分片
int  webCount    = (int)(peakReadQps / 1000); // 单机安全 1000 → 约 230 台无状态 Web 实例(可水平扩)
// 写 QPS: 发布 100 条内容/人? 不, 写少 → 1e8 人若 1% 每天发 1 条 = 1e6 写/天, 平均<12 写/秒, 写不是瓶颈
// 存储: 每天新增 1e6 条 × (内容 1KB + 索引) × 3 年 ≈ 1e6×365×3×1KB ≈ 1 TB 级 → 单机可扛但要备份/分片
// 带宽: 峰值 23 万 QPS × 每条响应 ~20KB(20 条 Feed) ≈ 4.6 GB/s ≈ 37 Gbps → 需 CDN 卸载静态/热点
// 反例: 不做这步就喊"上 10 个 MySQL 分片" —— 分片数应来自存储与 QPS 估算, 不是拍脑袋
```

## 三、瓶颈识别三板斧

系统慢/扛不住时，先用结构化方法定位短板，别凭直觉乱优化：

1. **先测后猜**：没有监控数据的优化都是占卜。先看指标（QPS、P99 延迟、错误率、饱和度 CPU/内存/IO/连接数）定位是**哪一层**先饱和——USE 法（Utilization/Saturation/Errors）逐资源看；
2. **按请求链路逐跳定位**：客户端→CDN→LB→网关→服务→缓存→DB→磁盘/网络，用**分布式追踪**测每一跳耗时，找最慢的一跳（往往是 DB 或外部调用）；
3. **区分瓶颈类型对症**：

```text
例子目的：四种瓶颈的指纹与处置, 认错类型会南辕北辙
CPU 型:  指纹=用户态 CPU 打满, 火焰图热点集中计算/序列化/正则  → 处置: 算法优化/缓存计算结果/加机器(计算密集可水平扩)
IO 型:   指纹=CPU 不高但 iowait 高, DB/磁盘慢                  → 处置: 加缓存/读写分离/索引/换 SSD(接 dist-data 读写分离)
内存型:  指纹=GC 频繁/OOM, 堆占用锯齿                          → 处置: 对象复用/换缓存策略/限流防打爆(接 jvm)
网络型:  指纹=带宽跑满或 RTT 高, 连接池耗尽                     → 处置: 合并请求/长连接/就近部署/CDN
错误做法: CPU 打满却去加索引(IO 优化) —— 瓶颈类型判断错, 越优化越偏
```

## 四、几个高频估算小场景

- **缓存容量**：热数据遵循 20/80（20% 数据扛 80% 访问）→ 缓存只需存 ~20% 热点；要 90% 命中率，估算"热点集大小"÷"单机内存"= 几个缓存节点，还要乘副本数与冗余系数（接 redis）；
- **分片数**：`分片数 = max(总存储 ÷ 单分片安全容量, 峰值写QPS ÷ 单分片写能力)`——存储和写入两个维度取大的那个；
- **副本与容灾**：几个 9 反推需要几副本几机房（接 S2-2 异地多活、dist-theory）。

## 五、常见线上问题

- **只看平均不看峰值**：平均 QPS 能扛，晚高峰直接雪崩——估算必须带峰值系数与突发（微博之夜型）；
- **忽略数据增长斜率**：只算今天不算三年后，上线一年存储/连接数爆表；
- **单位换算翻车**：把 1 MB=10^6 还是 2^20 混用，容量估算差出 5%~几十% 累计成大坑；
- **优化错瓶颈**：没测就上，CPU 型去加缓存、IO 型去堆计算实例，钱花了 P99 不动。

## 六、小结与过关要点

估算的肌肉是"三个输入（DAU/人均/读写比）→ 一条换算链（平均QPS→峰值QPS→实例/存储/带宽）→ 一组锚点数支撑心算"。瓶颈识别的肌肉是"先测后猜、逐跳定位、按指纹分类型"。两者合起来让架构组件**由数据说话而非由时髦说话**。过关自测：给你任意一道题（消息系统/网盘/排行榜），你能否 5 分钟内口算出峰值 QPS、需要几台机器、瓶颈最可能压在哪一层，并说出判断依据。
