# 系统设计答题框架

> 本节难度：★★★★☆
> 本节重要性：★★★★★
> 学习产出：能背出一套可复用的系统设计答题骨架（澄清需求→估算→API→数据模型→高层架构→深挖→权衡收尾）；能在开场 3 分钟内用结构化提问把模糊题面收敛成明确约束；会用"先广度后深度、先骨架后细节、边画边讲权衡"的节奏主导一场 40 分钟面试；识别面试官信号并动态调整；避开"上来就画框""只给方案不给取舍""忽视需求澄清"三大挂科点。

```flow
例子目的：把 40 分钟系统设计面试切成 7 段, 每段有明确产出与时间盒
① 澄清需求(3-5min)   → 功能范围 + 非功能约束(QPS/延迟/一致性/读写比) + 规模量级
② 顶层估算(3-5min)   → QPS/存储/带宽/内存, 得出"要不要分片/要不要缓存"的数量级判断
③ API 设计(2-3min)   → 核心读写接口与数据契约(REST/RPC), 暴露系统边界
④ 数据模型(3-5min)   → 关键实体与存储选型(SQL/NoSQL/KV/对象), 索引与分片键雏形
⑤ 高层架构(5-8min)   → 客户端→LB→服务→缓存→DB→MQ→存储 的数据流, 画成一张图
⑥ 深挖组件(8-10min)  → 挑 1-2 个最有区分度的点深入(热点/一致性/扩展), 展示纵深
⑦ 权衡收尾(3-5min)   → 瓶颈/单点/演进路径 + "如果量翻 10 倍我会怎么改"
```

## 一、开场：用结构化提问把模糊题收敛（最被低估的得分项）

题目如"设计一个短链服务"几乎是不可答的——范围太宽。高手第一步不是画框，而是**把开放题变成有约束的题**。提问要有结构，别散问：

```text
例子目的：一套可直接背的澄清问题清单(功能/非功能/规模三组)
功能: 核心用例是什么? 只缩短+跳转, 还是要后台统计/自定义别名/批量?  读多写少还是写多?
非功能: 一致性要求? 可用性目标几个9? 延迟预算(P99 多少 ms)? 链接可否永久?
规模:  月活多少? 每天新链多少条? 读写比? → 让面试官给量级, 或"我假设 DAU 1 亿、读写 100:1, 可以吗"
错误做法: 一声不吭直接开画 —— 面试官无法判断你到底懂不懂需求, 大概率被打断
反例话术: "用什么数据库?" 问太早, 数据选型应在估算和模型之后自然得出, 不该一上来问
```

**关键心法**：主动给出假设再请面试官确认（"我按 XX 量级做，对吗？"），比被动挤牙膏显得更有主导力，也能防止做到一半被推翻重来。

## 二、估算驱动设计：让每个组件都"有理由存在"

框架的价值在于**用数量级倒推架构**，而不是堆砌时髦组件。估算不是精确算术，是把"要不要上缓存/分库/CDN"变成可论证的判断：

```java
// 例子目的：用三段估算决定架构强度(数字取整, 重方法)
// 1) 写 QPS:  每天新链 1 亿条 → 1e8 / 86400 ≈ 1157 写/秒; 峰值取 5 倍 ≈ 6000 写/秒
// 2) 读 QPS:  读写比 100:1 → 约 11.6 万 读/秒, 峰值约 58 万 读/秒   → 结论: 读是绝对瓶颈, 必须重缓存
// 3) 存储:    每条记录(短码+长链+元数据)约 500B × 3年 × 1e8/天
//             ≈ 500B × 365×3×1e8 ≈ 5.5e13 B ≈ 55 TB   → 结论: 单表必炸, 要按短码哈希分片
// 由估算自然推出: 高读 → 热点缓存 + CDN; 海量存储 → 分片 + 冷热分离; 无强事务 → 最终一致够用
// 错误用法: 不做估算就喊"上 Kafka/Redis 集群" —— 组件成了装饰, 面试官一问"为什么"就露底
```

## 三、四层递进：广度→深度→权衡→演进

答题节奏是**先铺全链路骨架（广度），再挑重点下钻（深度），全程显式讲取舍（权衡），结尾给成长路径（演进）**：

- **广度**：高层架构图要让数据流从客户端一路走到持久化，每跳说清"这层解决什么"；宁可组件糙也要链路通；
- **深度**：主动请命"我想展开讲讲热点 key 的处理，可以吗？"——挑一两个最有区分度的点（缓存、一致性、分片、削峰）钻到底，这是拉开差距的地方；
- **权衡**：任何选择都配一句"放弃了什么、代价是什么"（CP vs AP、缓存 vs 直查、SQL vs NoSQL）；
- **演进**：结尾给"量级翻 10 倍/需求变复杂"时系统怎么长——体现你不是设计一张静态图，而是设计一个会演化的系统。

## 四、识别面试官信号并动态调整

系统设计面试是**对话不是报告**。要读信号：

```text
例子目的：把面试官的反馈实时翻译成"该加速/该展开/该收"
"这个先放放/我们时间不够"      → 你在过度纠结细节, 立刻收到骨架、往下一个组件推进
"这里能多说点吗?"              → 命中区分度考点, 这是你深挖加分的黄金机会, 展开讲
沉默+皱眉                       → 可能链路有断点或跳步, 主动回捞:"我这步假设 XX, 您看合理吗"
面试官给新约束("现在要支持国际站") → 增量需求测试演进能力, 回到数据/部署层面响应, 别推倒重来
错误做法: 无视打断一头扎进实现细节 —— 失去主导权, 40 分钟困在一个子问题里
```

## 五、三大挂科点

- **上来就画**：不澄清不估算直接摆组件——暴露"背题"痕迹，面试官无法评估你的工程判断；
- **只给方案不给取舍**：列一堆"用 Redis、用 Kafka、用分库分表"却从不说代价与替代——系统设计本质是 trade-off，没有取舍等于没答；
- **一张图定终身**：给完静态架构就结束，不谈单点、瓶颈、失败恢复、演进——显得只见过 happy path，缺乏生产判断力。

## 六、小结与过关要点

框架不是套路，是**把"面对开放性大问题的失控感"变成"可管理的推进节奏"**：澄清让题目有边界，估算让组件有理由，四层递进让回答有纵深，权衡与演进让回答有工程师的分寸感。过关自测：随便抽一道题（秒杀、Feed、排行榜），你能否在开口前先问出 5 个改变设计走向的关键问题，并在白板上留出"①需求②估算③API④数据⑤架构⑥深挖⑦权衡"七块空白逐块填满。
