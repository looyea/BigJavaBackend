# 容量估算与瓶颈识别 · 作业题

> 本节作业 3 题：手算一道完整估算、给一个慢接口做瓶颈定位、把锚点数做成速查卡。

## 作业 1：给"设计一个微博类 Feed 系统"做完整估算（动手计算）

假设 DAU=2 亿、人均刷新 30 次/天、每次拉 20 条、读写比 100:1、关注关系平均每人关注 100 人。请逐步算并写出推理链：

```text
例子目的：把估算落成有因有果的可核对计算过程(取整, 重方法)
1) 平均读 QPS = 2e8 × 30 / 86400 ≈ ?         // 结果: 约 7 万/秒
2) 峰值读 QPS = 平均 × 10 ≈ ?                 // 约 70 万/秒 → 决定缓存与分片强度
3) 写(发微博)QPS: 若 2% 用户日发 1 条 = 4e6 写/天 ≈ ? 平均/秒   // 很小, 写非瓶颈
4) 单条微博存储(正文+索引) ~1KB × 4e6/天 × 3年 ≈ ?              // 判断要不要分片
5) 读带宽 = 峰值QPS × 每次响应 ~20KB ≈ ? GB/s                    // 是否需要 CDN
6) 由 2) 推出: 无状态 Web 实例数 = 峰值/单机1000 ≈ ?
反例: 只给最终数字不给"由此推出哪个组件" —— 估算没服务架构就白算
```

**验收标准**：六个问号全部填出数量级 + 每一步后写一句"所以架构上要怎么做" + 明确指出这个系统的第一瓶颈是什么。

## 作业 2：给一个真实慢接口做瓶颈定位（动手+复盘）

找一个你项目里慢的接口（或造一个：某列表接口 P99=2s）：

1. 列出你会先看哪些监控指标来定位是哪一层饱和（QPS、P99、错误率、CPU/内存/IO/连接池饱和度）；
2. 用"逐跳定位"思路画出这个接口的调用链（Controller→Service→缓存→DB→外部），假设你给每跳埋了耗时，判断最慢一跳是哪里；
3. 判瓶颈类型并给处置：例如发现是"DB 慢查询 + iowait 高"→ IO 型 → 加索引/读写分离/缓存；例如"GC 频繁 + 堆锯齿"→ 内存型 → 对象复用/限流；
4. 写一句反例警示：如果误判成 CPU 型去堆计算实例，会发生什么。

**交付物**：监控指标清单 + 调用链逐跳耗时表(可合理编造数字) + 瓶颈类型判定与处置 + 一句误判代价说明。

**提示**：这题真正的考点是"先测后猜"——你的每一步结论都必须挂着某个监控数字作证据，不许凭直觉。

## 作业 3：做一张"估算锚点数"速查卡（设计）

把本课八个必背数字 + 你自己项目常用量级整理成一张可贴在工位/写进笔记的速查卡：

```text
例子目的：一张让口算提速的卡, 考前 30 秒扫一遍
时间: 1天≈86400s(取1e5) | 1年≈3.15e7s
2幂: 2^10=1K 2^20=1M 2^30=1G 2^40=1T | 1e9≈2^30
锚点: Web单机安全QPS~1e3 | Redis单实例~1e5 ops/s | 记录~0.5-1KB | 图~100KB-1MB
时延: 内存100ns SSD100μs 同机房RTT0.5ms 跨城50ms 跨国200ms
可用: 99.9%停8.76h 99.99%停52.6min 99.999%停5.26min
换算链: 平均QPS=DAU×人均/86400 | 峰值=平均×5~10 | 实例=峰值÷单机安全QPS
```

**交付物**：一张速查卡（含时间/2幂/单机锚点/时延/可用性换算/换算链六类），并用自己的话在卡末补一条"最常算错的一步"。

**提示**：估算是系统设计面试的"体力活基本功"——锚点数不背熟，现场就会卡在乘除上，把主导权丢给紧张情绪。
