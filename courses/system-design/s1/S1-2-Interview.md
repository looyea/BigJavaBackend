# 容量估算与瓶颈识别 · 实际面试题

## 题 1：面试里让你估算，你怕算错怎么办？怎么估才显得专业？

**考察点**：是否理解估算的目的是"数量级 + 推理链"而非精确值。

**参考答案**：估算的目标从来不是算准，是**用数量级把架构决策锚定**——判断"要不要缓存/分片/CDN/几个实例"。专业做法有三支：① **背锚点数**，现场只做乘除不做记忆检索（1 天≈86400 秒取 1e5、2^30=1GB、Web 单机安全 QPS≈1000、Redis 单实例≈10万 ops/s、记录≈1KB、几个 9 的年停机）；② **走固定换算链**：平均 QPS = DAU×人均操作/86400，峰值 = 平均×5~10，实例数 = 峰值÷单机安全 QPS，存储 = 记录数×单条大小×保留期，带宽 = QPS×响应大小；③ **每算一步就落到一个设计结论**（"峰值 70 万读/秒 → 必须重缓存 + 分片"）。数字一律取整、透明说出假设，并主动补"我按 10 倍峰值，若你的业务突发更强这个系数要调"。算错数量级不丢人，**给不出推理链、组件靠拍脑袋才丢人**。

**追问**：
- 峰值系数怎么定？——内容/社交类 5~10 倍足够；有明显定时突发（秒杀、晚高峰、整点播报）要单列突发流量另算。
- 面试官嫌你数字不对怎么办？——数字是可替换的输入，当场接住："那我把 DAU 换成 X 重推一遍链路"——展示的是方法可迁移，不是背了一个答案。

**加分点**：强调"估算服务架构"——只给数字不给"由此推出哪个组件"就白算，专业感来自数据到决策的因果链。

## 题 2：线上系统变慢了，你怎么定位瓶颈？别只说"加机器"。

**考察点**：有没有结构化的性能诊断方法论，而不是碰运气优化。

**参考答案**：我遵循三板斧。**一、先测后猜**——没有监控数据的优化都是占卜，先看核心指标（QPS、P99 延迟、错误率、四类饱和度 CPU/内存/IO/连接数），用 USE 法（利用率/饱和度/错误）逐资源看哪层先满。**二、按请求链路逐跳定位**——客户端→CDN→LB→网关→服务→缓存→DB→磁盘/网络，靠分布式追踪测每跳耗时，揪出最慢的一跳（实践中八成是 DB 慢查询或某个外部调用）。**三、按瓶颈类型对症**——四类指纹各有药方：CPU 型（用户态 CPU 满、火焰图热点在计算/序列化）走算法优化/缓存结果/水平扩；IO 型（CPU 不高但 iowait 高、DB 慢）走加缓存/读写分离/加索引/换 SSD；内存型（GC 频繁、堆锯齿）走对象复用/换缓存策略/限流防打爆；网络型（带宽满、RTT 高、连接池耗尽）走合并请求/长连接/就近部署/CDN。**"加机器"只对 CPU 型这类可水平扩的瓶颈有效**，对单点 DB、对锁竞争、对慢 SQL 加机器没用甚至更糟。

**追问**：
- 为什么"优化错瓶颈类型"比不优化更危险？——花了钱加了与瓶颈无关的资源（CPU 型去堆 IO 实例、或反过来），P99 纹丝不动，还掩盖了真问题、误导后续决策。
- 找到是 DB 慢之后呢？——先看是单查询慢（索引/SQL 改写）还是并发压垮（连接池、读写分离、分片、缓存挡在前面），继续分层。

**加分点**：主动提"先测后猜"的纪律 + 举一个"误判类型浪费资源"的真实感案例，展示你是拿数据说话而不是拿直觉说话的工程师。

## 题 3：给你一个"设计微信/IM 消息系统"的题，你怎么边估边推架构？

**考察点**：估算与架构能否咬合，读写比这类输入如何改变设计。

**参考答案**：IM 与内容类系统的关键差异是**读写比接近 1:1**（发消息和收消息一样多），不能照搬"读 100:1 靠缓存"的套路。假设 DAU 10 亿、人均发 40 条/天：写 QPS 平均 = 1e9×40/86400 ≈ 46 万/秒、峰值取 5 倍 ≈ 230 万/秒，这是**写密集**系统，瓶颈在写扩散与消息持久化吞吐。据此倒推：① 消息 ID 用雪花/Long 型（时间可排序 + 分布式无冲突，接 S3-1 ID 生成器）；② 写路径先落 Kafka/存储再异步分发，扛写峰；③ 会话与消息分片按 uid 哈希，写吞吐与存储双约束定分片数；④ 未读计数这类高频读写放 Redis 且做本地缓存合并；⑤ 在线推走长连接、离线补拉用"信箱 + 拉取"混合。整个过程就是"输入(1:1 读写比) → 估算(写密集) → 架构(削峰+分片+混合推拉)"。

**追问**：
- 10 亿 DAU 这个数字靠谱吗？——微信量级确实在十亿，取整即可；重点是方法，面试官换个数我当场重推。
- 为什么消息 ID 用 Long 时间有序？——客户端拉增量只需带"最后一条 ID"比较大小，天然游标分页；无序 ID 就得另建时间索引。

**加分点**：点出"读写比这一个输入就把系统从读密集型(内容)推成写密集型(IM)，架构重心随之从缓存/CDN 转向削峰/分片/持久化"——展示你真正理解估算如何驱动设计，而不是背了一张 IM 架构图。
