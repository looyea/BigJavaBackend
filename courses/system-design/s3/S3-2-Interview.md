# 面试题：API 网关 / Web 爬虫 / 支付对账系统

## 高频面试题

### Q1：API 网关如何做服务发现与动态路由？

**答题要点**：
- 注册中心（Nacos/Consul/Eureka）→ 网关定时拉取实例列表 → 本地维护路由表
- 动态路由：配置中心推送路由规则变更，网关热更新无需重启
- 负载均衡：网关内置 Round-Robin / 一致性哈希 / 最少连接
- 健康检查：主动探测 + 被动剔除（连续 N 次 5xx 摘除实例）

**追问方向**：网关节点本身挂了怎么办？（答：前置 L4 LB 多活部署，DNS 切流兜底）

### Q2：设计爬虫时如何处理 JS 动态渲染的页面？

**答题要点**：
- Headless Chrome / Playwright：无头浏览器执行 JS，等待网络空闲后取 DOM
- 逆向 API：分析 XHR 请求直接调后端接口，效率更高
- 混合策略：静态页用 HttpClient；检测到动态标记再交给浏览器引擎
- 性能权衡：浏览器渲染开销 10x+，需单独 Worker 池避免拖慢整体

**追问方向**：如何检测到页面是动态渲染的？（答：初始 HTML 内容极少 + JS 加载大量资源）

### Q3：支付对账中如何防止资损？

**答题要点**：
- 实时核对：支付回调时即查渠道订单状态，秒级发现差异
- 自动化补单：掉单自动重发；漏单自动入账；避免人工延迟
- 大额拦截：超阈值差错冻结资金，人工复核后才放行
- 熔断机制：当日差错率 > 0.1% 暂停该渠道自动结算，触发告警
- 日终总账：三方（我方、渠道、清算）总额轧平

**追问方向**：如果微信回调延迟 2 小时到达，你的对账系统怎么处理？（答：T+1 对账留容差窗口；回调到达后先走实时核对补单，次日对账不再判为掉单）

### Q4：网关限流的令牌桶算法具体怎么实现？

**答题要点**：
- 核心公式：`tokens = min(capacity, tokens + elapsed × rate)`
- Redis + Lua：KEY 存 tokens + lastRefillTimestamp；原子执行补充 & 扣减
- 突发：capacity 允许短时超出 rate；平滑：令牌匀速生成
- 与漏桶对比：漏桶严格匀速（不允许突发），令牌桶弹性更好

**追问方向**：网关集群 10 个节点共享同一个 Redis 限流器，有什么性能瓶颈？（答：Redis 单线程瓶颈 ~10 万 ops/s，高并发场景用本地限流 + 异步同步 Redis 的混合模式）

### Q5：爬虫如何避免被封 IP？

**答题要点**：
- 代理 IP 池：每次请求随机选 IP，住宅代理 > 机房代理
- 请求频率控制：按域名级 Crawl-delay + 随机抖动
- 请求指纹伪装：UA 池轮换 + Accept-Language 随机 + TLS 指纹（curl-impersonate）
- Cookie 管理：模拟登录态，Session 池复用
- 验证码识别/打码平台兜底

**追问方向**：如果对方用 Cloudflare WAF 怎么办？（答：用真实浏览器环境绕过 JS Challenge；或找 API 接口绕过前端防护）

### Q6：微服务网关选型——Kong vs Spring Cloud Gateway vs Envoy？

**答题要点**：
- Kong：基于 OpenResty(Nginx+Lua)，插件生态丰富（认证/限流/日志），性能好
- Spring Cloud Gateway：Java 生态无缝集成，适合 Spring Cloud 全家桶
- Envoy：Service Mesh sidecar 模式，L7 路由精细；本身不直接对外
- 选型依据：语言栈、性能需求、插件定制能力、运维团队熟悉度

**追问方向**：Gateway 的 Filter 链和 AOP 有什么异同？（答：都是责任链；Gateway Filter 作用于请求/响应，支持全局和路由级；AOP 作用于方法调用）

### Q7：对账系统如何处理"跨日交易"问题？

**答题要点**：
- 统一时区：所有时间戳转为 UTC 存储，对账时按 UTC 日期切割
- 容差窗口：T 日对账包含 T-1 23:50~T+1 00:10 的交易（防止渠道日切时间不一致）
- 双日期字段：业务日期（用户下单时间）vs 结算日期（渠道入账时间）分别记录
- 二次对账：首次未匹配的记录进入 T+2/T+3 再试队列

**追问方向**：跨境支付 T+2 才能拿到银行对账单怎么办？（答：设计异步对账模式，收到账单后立即触发增量对账；未收到前挂"待对账"状态）

### Q8：如何设计爬虫系统的断点续爬？

**答题要点**：
- 任务状态持久化：每个 URL 记录 {status: pending/fetching/done/failed, retryCount}
- 进度 Checkpoint：定期把当前队列状态快照到 Redis/DB
- 重启恢复：从 status=pending 和 status=fetching（可能是中断的）继续
- 幂等保证：下载用 ETag 条件请求；解析入库用 (url, content_hash) 去重

**追问方向**：大规模爬虫如何做到增量抓取而不重复下载？（答：Sitemap lastmod + 页面 content_hash 比对 + ETag 条件请求 304 Not Modified）
