# 热点参数限流、集群限流与规则持久化（关联） · 面试题

## 题 1：什么是热点参数限流？解决什么问题？

- 按某个"参数值"单独统计限流（`ParamFlowRule`），如按 `itemId`、`userId`、渠道码。
- 解决"单个热值打爆接口"：秒杀爆款只压垮一个 SKU，不该连累正常商品；接口级总限流做不到这种粒度隔离。
- 加分：用 `paramFlowItemList` 给特定值设例外项，爆款单独放宽/收紧。

## 题 2：多实例部署为什么单机限流会失真？怎么解？

- 每台各自计数，N 台配 100 全局就放到约 N×100，起不到总量控制。
- 用集群限流：Token Server 统一发令牌、各实例申请，得到全局阈值；或按实例数折算单机阈值。
- 加分：指出折算法脆弱（扩缩容就要改），集群模式更可靠。

## 题 3：Sentinel 集群限流的 Token Server 怎么部署？挂了怎么办？

- 嵌入模式（某业务节点兼任 TC）或独立模式（专门 TC 进程）。
- 必须配退化（degrade）：TC 不可用/通信失败时自动回落本地限流，避免"全不限流"或"全被限死"。
- 加分：强调 TC 是限流的潜在单点，退化是保可用的关键。

## 题 4：Sentinel 规则默认怎么存？生产为什么要外置？

- 默认存内存，控制台改完一重启就丢，也没法程序化批量下发。
- 生产接 `NacosDataSource`/Zookeeper/Apollo 做动态规则源：监听变更→热更新→重启不丢→可批量下发。
- 加分：还要配本地快照兜底，数据源拉取失败时不至于"无规则裸奔"。

## 题 5：热点参数限流的例外项是干什么的？

- 对某个具体参数值单独设定阈值，覆盖大盘默认值。
- 典型：大盘每个 itemId 限 100，爆款 8888 单独限 500（或收紧到 50 保护）。
- 加分：能说明没有例外项时爆款只能吃大盘阈值，要么误伤正常、要么挡不住爆款。

## 题 6：被限流的请求怎么处理才对？

- 通过 `@SentinelResource(blockHandler=...)` 走兜底：返回缓存、排队页、降级默认值，而不是把 `BlockException` 直接抛给前端。
- 加分：结合熔断降级（S1-2）说明"限流兜底"和"熔断 fallback"的协同，形成不阻断的用户体验。
