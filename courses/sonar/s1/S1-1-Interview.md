# 规则集与门禁策略 · 面试题

## 题 1：SonarQube 的 Profile、Gate、Clean as You Code 分别是什么？

- Quality Profile：某语言启用哪些规则（规则集），团队统一、改规则走评审；
- Quality Gate：pass/fail 的指标条件（覆盖率、新增违规、热点复核等）；
- Clean as You Code：Gate 只作用在**新增/变更代码**，存量债单独治理——避免老项目首扫即红、门禁被弃用。
- 加分：能讲扫描流程（跑规则→算指标→对照 Gate），并强调扫描只读 jacoco 报告不自己跑测试。

## 题 2：怎么让 Sonar 真正成为合并门禁而不是事后看板？

- CI 里 MR 触发 `mvn verify sonar:sonar -Dsonar.qualitygate.wait=true`——`wait` 让流水线阻塞等 Gate 结果，不过就 fail，进而 block 合并；
- 前置必须先跑测试产出覆盖率，否则 new_coverage=0 必红；
- token 走 CI 变量/密钥管理，绝不写进仓库；
- 加分：设置例外审批（谁可标记 False Positive/Won't Fix、留什么记录），否则大家会绕过而非遵守。

## 题 3：Security Hotspot 和 Vulnerability 有什么区别？

- Vulnerability：规则能确定判定为安全缺陷，计入失败；
- Hotspot：安全敏感但需人工判断上下文（如 `Math.random()` 生成 token——是漏洞还是可接受取决于场景），不自动判违规；
- 门禁常见做法：要求"新增 Hotspot 100% 复核"，即每处都被人标记 Safe/Fix，而不是机器放过。
- 加分：Hotspot 复核率作为指标能推动安全评审文化。

## 题 4：覆盖率指标怎么才不被"玩坏"？

- Sonar 覆盖率来自 jacoco 行覆盖，容易被"无断言地跑过代码"刷高——真质量靠有意义的断言（见 [JUnit](../../junit/s1/S1-1-Lesson.md)）；
- 用 `new_coverage` 只卡增量；别追求 100% 全量覆盖（成本畸高、逼出垃圾测试）；
- 结合变异测试思路（如 PIT）看断言强度，覆盖率只是必要条件不是充分条件。

## 题 5：复杂度和重复率这类指标怎么设才不会反噬？

- 别把圈复杂度/认知复杂度设成 Blocking 一刀切，否则催生"为过线把大函数拆成一堆无意义小函数"的应试代码；
- 重复率适度（如新代码 <3%），容忍必要的配置式重复；
- 原则：指标是"引路的灯"不是"考核的鞭"，用来自我改进而非惩罚，否则团队会优化指标本身而非代码质量。

## 题 6：老项目一堆历史问题，领导要"本月清零"，你怎么应对？

- 先解释为什么这是反模式：全量红线限期清零 = 乱标记 False Positive + 拆函数应试 + 团队抵触，质量没真提升；
- 给替代方案：Clean as You Code（先止血，新代码 0 新增问题）+ 存量按模块风险/热度加权、分冲刺清理、用技术债雷达设 baseline；
- 可量化收敛指标：新增问题数保持 0 + 存量下降曲线，让"变好"可见，用趋势而非一次性大爆炸；
- 加分：静态"可能慢/可能有坑"要配合运行时证据（[Arthas/火焰图](../../arthas/s1/S1-1-Lesson.md)）验证，别被误报牵着走。
