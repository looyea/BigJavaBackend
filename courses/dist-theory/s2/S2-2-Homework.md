# 分布式锁的工程与坑 · 作业题

> 本节作业 3 题：三连坑实验、一次选型答辩、一份锁审计。

## 作业 1：复现分布式锁三大经典坑（动手）

用单实例 Redis（主从两节点更好）依次复现并记录现象：

1. **误删他人锁**：A 加锁 TTL=2s，业务睡 3s；B 在 A 过期后加锁成功；A 醒来直接 DEL——B 的锁消失。再改 Lua 校验释放，确认误删消失；
2. **双持有（过期赛跑）**：TTL=3s、业务耗时正态分布(均值4s)，20 并发统计"同一资源两个线程同时在临界区"的次数；接入 Redisson 看门狗复测确认归零；
3. **主从丢锁**：kill -9 掉 Redis 主，哨兵切主后立即验证锁 key 是否存在、第二客户端是否可重复加锁。

**验收标准**：每个坑给出复现脚本、现象计数、修复后对照数据。

## 作业 2：Fencing token 端到端实现（动手）

1. 用 Redis `INCR lockseq:{key}` 在加锁时取号，把号写进锁 value 一并返回；
2. 改造一个假存储（Map 即可）：只接受 `token >= 已见最大` 的写；
3. 用 `Thread.sleep(超长)` 或 `kill -STOP` 模拟持有者停顿跨过 TTL，验证其苏醒后的写被拒；
4. 讨论：INCR 与 SETNX 两步非原子，如何改进（Lua 合并/红锁不适用结论）。

**交付物**：≤120 行的可运行 Demo + 一句"为什么大多数 Redis 锁教程缺这一环"。

## 作业 3：本包锁选型答辩（设计）

场景：订单超时取消任务，32 实例部署，要求同一订单只被取消一次；订单表已有状态机（PAID→CANCELLABLE→CANCELLED）。

写一份 ≤1 页答辩：

- 方案 A Redis 锁 / 方案 B ZK 锁 / 方案 C 无锁（状态机 CAS + 分片领取）；
- 指出该场景属于效率锁还是正确性锁，据此给出选择与理由；
- 给出你选定方案的失败矩阵（锁服务挂/网络抖动/实例全重启）。

**验收标准**：若最终选了 C，必须解释"为什么互斥下沉到 `UPDATE ... WHERE status='CANCELLABLE'` 就够了"。
