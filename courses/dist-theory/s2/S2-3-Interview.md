# 分布式 ID 方案与取舍 · 实际面试题

## 题 1：分库分表后主键怎么生成？为什么不用各库自增？

**考察点**：唯一性来源的基本判断。

**参考答案**：各库自增会在分片间撞号（两个库都从 1 加），步长错开法改拓扑即崩、多活不可用。正解把唯一性来源换成"全局规则"：雪花（时间+机器+序列，本地生成无运行时中心）或号段服务（中心只管发段）。再配分片键设计：主键本身建议取哈希友好的尾部位段（雪花低位的 seq 分布均匀），避免"按 ID 范围查"热点集中最新分片。

**追问**：
- 雪花做主键，查询按用户维度路由还是按 ID？——业务查询走 user_id 分片，主键只保证唯一；按 ID 反查需广播或基因法（把用户分片位嵌进 ID 低位，ShardingSphere 的"基因片段"）。
- 基因法的坑？——ID 结构即契约，改分片数=基因失效，容量规划要一步到位。

**加分点**：主动区分"发号性能"与"落库性能"两个瓶颈。

## 题 2：雪花 ID 的时钟回拨，你们的真实处理是什么？

**考察点**：是否背过方案又动过真格。

**参考答案**：分层答：检测（now<lastTs）→ 小幅（≤5ms）自旋等待；中幅（<1s）借用未来时间戳（lastTs+1）保单调并告警；大幅拒绝发号快速失败，等 NTP 追平或运维介入。更可靠的仲裁：与 zk/etcd 的系统时间比对——本机说回拨可能是本机错，多数节点说了算（Leaf 做法）。虚拟机快照恢复是大幅回拨最高频诱因，容器场景加 `chrony` 步进限制并监控 `offset`。

**追问**：为什么不干脆重启进程？——重启不能改系统时钟；且重启期间 workerId 若被回收复用，反而引入双重风险。

## 题 3：号段模式的"双 Buffer"到底解决什么？step 设大设小怎么权衡？

**考察点**：预取设计与故障容忍的量化感。

**参考答案**：单 Buffer 换段时发号线程直接等 DB（DB 抖=P99 抖）；双 Buffer 在当前段用到阈值（如 10%）异步取下一段，发号路径与 DB 解耦，DB 故障时已领段照常发。step 大：DB 访问频率低、故障容忍久，但重启浪费多、号前进跳变大；step 小反之。典型千级；有"号连续"洁癖的业务要把浪费段也对外解释（ID 只承诺趋势递增，不承诺无洞）。

**追问**：号段表本身怎么高可用？——MySQL 主从+双写保护不必要（CAS version 串行化天然防双领）；Leaf 用多 DB 分组（biz 分桶到不同 DB）避免单点。

## 题 4：订单号要不要对外暴露自增？怎么防遍历和竞品推算？

**考察点**：安全与工程的结合。

**参考答案**：不能纯自增（一天一单暴露规模）。常见配方：日期前缀+号段但**随机起点**+非线性步进；或干脆对外用雪花（时间段可粗估总量但难精确）、或独立资源标识（UUIDv7/短码）而把内部主键 BIGINT 藏起来——对外单号与内部主键解耦是最干净的方案。防遍历评估口径：枚举成本=键空间/请求配额，短号加校验位（Luhn 类）让乱猜先过格式闸。

**追问**：对外单号加密（如 Hashids）行不行？——可行但要管密钥轮换与"解密回内部 ID"的性能；强调它属于混淆不是授权，越权仍须鉴权层。

## 题 5：设计题：给多活架构（三地域均可写）设计全链路 ID。

**考察点**：地理多活下唯一性方案综合（高频压轴）。

**参考答案**：要点四条：① 避免任何单点发号中心（跨域取号 RTT 灾难）→ 选本地生成：雪花，机器段切分为"地域位+实例位"（如 3bit 地域+7bit 实例），地域内 workerId 由本地 etcd 租约；② 各域时钟独立，回拨防护按域部署；③ 冲突检测兜底：主键唯一索引让最坏情况可见可告警，绝不静默覆盖；④ 对外 ID 带地域标识段便于路由回源（就近读写+数据归并时按域分桶）。若业务要求"号像流水"（对监管报数），退一步：全局日期+域内号段，接受跨域不连续。

**追问**：数据最终归并到一处时两个域的 ID 段会重吗？——机器/地域位保证不重；归并只是空间合并，唯一性由位段结构担保——这正体现"结构担保优于中心担保"。
