# 分布式锁的工程与坑 · 小测验

> 全卷 100 分：单选 5×10 + 多选 2×10 + 判断 1×5 + 简答 15+10。达到 60 分解锁下一节。

### 1. Redis 分布式锁释放时用 Lua 脚本的原因是（10分）

- A. Lua 执行更快
- B. "比对持有者身份 + 删除"必须原子完成，防止判完后锁恰好过期又被他人获取
- C. 避免 keys 命令
- D. Redis 不支持 DEL

> 答案：B
> 解析：GET 判断与 DEL 之间有时间窗：锁恰好过期并被 B 获取后 A 再 DEL 就误删——两步合进一个 Lua 即原子。

### 2. 主从架构 Redis 锁的丢锁场景是（10分）

- A. 从库读延迟
- B. 主节点加锁成功但未同步到从即宕机，新主无锁记录，第二个客户端加锁成功形成双持有
- C. 过期键未及时清理
- D. 内存淘汰把锁键驱逐前会通知客户端

> 答案：B
> 解析：Redis 复制异步，锁状态不在持久化保证内——RedLock 的动机正在于此，但 Kleppmann 论证其仍不解决停顿问题。

### 3. 看门狗（watchdog）续期机制生效的前提是（10分）

- A. 显式指定 30 秒 leaseTime
- B. 加锁时不传 leaseTime，由框架后台线程周期性检查持有线程存活并续期
- C. 业务必须小于 TTL
- D. Redis 开启 AOF

> 答案：B
> 解析：Redisson 语义：传了 leaseTime 即关闭看门狗——"配了自动续期参数实际没续期"是高频线上事故。

### 4. Fencing token 防御的场景是（10分）

- A. 锁服务宕机
- B. 旧持有者因 GC 停顿错过续期，苏醒后带着过期锁继续写存储——存储层比较单调序号拒绝旧令牌
- C. 客户端忘解锁
- D. 锁粒度太粗

> 答案：B
> 解析：token 把"互斥正确性"从客户端自律转为存储层仲裁：写请求携带加锁时获得的单调递增序号，存储只接受不小于已见最大值的写。

### 5. ZooKeeper 锁用"临时顺序节点 + watch 前驱"而不是直接创建普通节点，主要收益是（10分）

- A. 减少网络包
- B. 会话断开自动释放（临时节点）+ 公平排队且避免羊群效应（顺序节点 watch 前驱）
- C. 支持可重入
- D. 不需要序列化

> 答案：B
> 解析：ephemeral 绑定 session 解决死锁；sequential+只watch前一个，等锁链唤醒而非全员争抢通知。

### 6. 下列哪些属于"效率锁可以、正确性锁不可以"直接依赖 Redis 单实例锁的理由？（多选）（10分）

- A. 主从切换可能丢锁导致双持有
- B. 客户端长停顿后不自知锁已过期
- C. Redis 的 SETNX 不返回单调序号，存储层无法拒绝旧持有者
- D. Redis 内存成本太高

> 答案：ABC
> 解析：A/B/C 分别对应复制窗口、停顿假设、缺 fencing 三个结构性缺陷；D 不成立——Redis 锁成本恰恰低。

### 7. 关于 RedLock 的争议，以下说法正确的有（多选）（10分）

- A. Kleppmann 质疑其依赖时钟近似单调与"持有者不会长时间停顿"两个弱假设
- B. Antirez 的回应否认了时钟漂移风险但补充了 token 机制
- C. 对"错了会出资损事故"的场景，主流建议是改用带会话/序号语义的共识存储或下沉到数据层 CAS
- D. RedLock 需要 N 个独立 Redis master，运维面显著大于单主从

> 答案：ACD
> 解析：B 错——Antirez 并未提供 fencing token；这也是学界认为 RedLock 不适合正确性锁的核心原因。

### 8. 判断题：把库存扣减写成 `UPDATE stock SET n=n-1 WHERE id=? AND n>0` 后，就秒杀主流程而言可以不再依赖通用分布式锁保证不超卖。（5分）

- A. 正确
- B. 错误

> 答案：A
> 解析：条件更新把互斥下沉到数据库行（单点定序+原子判断），正确性不依赖外部锁；锁只用于减少无效竞争的"效率"层。

### 9. 简答题：列出 Redis 分布式锁从"加锁→业务→释放"完整使用中至少五个工程要点（含参数与代码结构）。（15分）

> 参考答案：
> - SET key uuid NX PX 毫秒 TTL：value 必须请求唯一（uuid），NX+PX 一条命令原子完成
> - 释放用 Lua：GET 比对 uuid 后 DEL，两步原子
> - 业务时长不确定→看门狗续期（不传 leaseTime 才生效）或租约保守覆盖 P99
> - tryLock 设置等待上限并走降级路径，禁止无限阻塞
> - 锁 key 落到最小冲突粒度（sku 而非全表），前缀统一便于运维清理
> - 关键资金操作叠加数据层 CAS/唯一键，不把 Redis 锁当正确性终点

> 解析：五要点覆盖互斥、防误删、防过期、防堆积、防粒度失当——与四条底线一一对应。

### 10. 简答题：为什么说"锁服务本身高可用"不等于"锁语义正确"？用主从 Redis 与 ZK 各说明一句。（10分）

> 参考答案：
> - 主从 Redis 部署 6 节点仍异步复制：切换窗口丢锁，可用性高但互斥语义有洞
> - ZK 多数派写使"锁节点存在与否"本身被共识定序：语义随仲裁者成立，不是靠节点数量堆可用性
> - 正确性取决于"锁状态由谁权威决定、失效判定是否单调"，而非部署了几个进程
> - 结论：选型看协议（共识/会话/序号），不是看副本数

> 解析：把"高可用"与"正确性"分开是理解分布式锁争议的关键一步。
