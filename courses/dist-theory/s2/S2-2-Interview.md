# 分布式锁的工程与坑 · 实际面试题

## 题 1：手写一个 Redis 分布式锁，说说每一行的必要性。

**考察点**：加锁/解锁的最小正确结构。

**参考答案**：加锁 `SET key uuid NX PX 30000`——NX 互斥、PX 防死锁、uuid 标识持有者，一条命令原子（分开 SETNX+EXPIRE 会有崩溃夹缝）。解锁 Lua：`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end`——比对+删除原子，防误删。再往上就是续期（看门狗）与等待策略（tryLock 有界+降级）。

**追问**：
- 为什么不用 `GET` 再 `DEL`？——两命令间锁可能过期易主，删了别人的锁。
- uuid 用什么生成？——线程级唯一（如 Redisson 的 uuid:threadId），要支持同线程可重入计数。

**加分点**：主动提"这把锁防不住 GC 停顿超 TTL 的旧持有者，引出 fencing token"。

## 题 2：RedLock 能不能用于金融扣费互斥？

**考察点**：对 2016 大论战的立场与论据。

**参考答案**：不能。Kleppmann 的三个攻击点都成立在实践层：时钟快跳使锁提前过期（Redis 过期靠本机 monotonic clock 但系统休眠/NTP step 场景仍出问题）、进程停顿使"自认为持有"失效且 RedLock 无 token 防御、多数派达成后旧主网络迟到包仍可能干扰。金融互斥的正解：把互斥下沉到账务存储（行级 CAS/唯一流水键），或用带会话语义的 ZK/etcd——锁错了有仲裁者能否决旧持有者。

**追问**：Antirez 怎么回应的？——主张时钟漂移可控、程序停顿可用 minor GC 实践规避；但双方都没有给 RedLock 加序号防御，所以"安全性弱于宣传"仍是主流结论。

## 题 3：ZooKeeper 锁和 Redis 锁的性能差多少？为什么？什么时候仍该选 ZK？

**考察点**：机制决定性能的推理。

**参考答案**：量级差约 1~2 个数量级：ZK 每次写要走 ZAB 多数派 fsync+广播，Redis 单线程内存操作微秒级。ZK 赢在语义：临时节点绑定 session（断线即释放且可被 watch 通知）、zxid 提供单调仲裁、等待队列公平且防羊群。选择标准：**锁错误不可接受或需要"持有者失联立刻知道"**（选主、单写者分片）用 ZK/etcd；防重复计算的效率锁用 Redis。

**追问**：ZK session 超时设多少？——权衡抖动误杀与死锁时长，典型 15~30s，且要看 GC 日志保证停顿远小于 session——否则"僵尸持有者"照样出现。

## 题 4：秒杀要不要分布式锁？给出你的完整答案。

**考察点**：高频陷阱题——考"锁不是来防超卖的"认知。

**参考答案**：不靠锁防超卖。正确性用 `UPDATE ... WHERE remain>0`（或 Redis Lua 原子扣减预扣库存）——单点定序天然互斥；分布式锁在这只当**效率**部件：把并发请求收敛成少股进入，减少无谓竞争与回滚。完整答案分层：令牌/库存预热到 Redis 原子扣 → 扣成功者发消息异步落单 → DB 终态 CAS 兜底 → 锁（若有）只在防重复提交层。若回答"上 Redisson 锁排队扣库存"直接暴露单机思维。

**追问**：Redis 扣减与 DB 落单不一致怎么办？——扣减即预占，落单失败由超时回补（延迟队列归还库存），对账兜底。

## 题 5：线上发现锁等待堆积最终雪崩，排查与治理路线？

**考察点**：锁引发故障的处置经验。

**参考答案**：排查：① 看锁 key 分布——是否粗粒度大锁（品类级/全局配置锁）；② 持有者是谁——慢 SQL/GC 导致持锁时长飙升；③ 续期是否正常——看门狗线程池饥饿也会导致锁提前释放后双持竞争加剧。治理：拆粒度（全局锁→分片锁→行级 CAS）、tryLock 必须有界+快速失败降级、持锁段内禁 RPC 长调用、锁服务故障预案（Redis 挂→放行还是拒绝按业务定：防重复类宁放行配下游幂等）。

**追问**：为什么说"锁内不做远程调用"？——远程调用 P99 不可控直接放大持锁时长，锁排队深度=持锁时长×QPS。

## 题 6：开放题：如果只能选一个方案做"跨三个云的互斥"，你选什么？

**考察点**：共识在地理约束下的应用（结合上两节）。

**参考答案**：示范立场：不跨云做通用锁——把互斥域单元化（每云独立锁域+资源按归属分域，跨域走异步调拨），这与"共识跨城写 P99 不可行"同构；若业务必须全局单锁（全局唯一调度器），选每云各部署 ZK/etcd 集群 + 域名路由到主集群，接受主集群故障时全局互斥暂停（fail-closed），因为正确性锁宁可拒绝服务也不允许双持有——用 PACELC 语言：P 时选 C。

**追问**：fail-closed 的代价怎么评估？——锁不可用的分钟数×业务错一单的损失 vs 放行错一次的期望损失，让数字替你答辩。
