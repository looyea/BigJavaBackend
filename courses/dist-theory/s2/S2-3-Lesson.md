# 分布式 ID 方案与取舍

> 本节难度：★★★★☆
> 重要程度：★★★★★
> 学习产出：能推导雪花 64 位的每一段为什么是这个宽度，处理时钟回拨的三种工程策略；讲清号段模式（Leaf-segment）双 Buffer 如何把"取号"与"发号"解耦；对比 UUID/号段/雪花/Redis INCR/数据库自增在有序性、吞吐、信息泄露、依赖面四个维度的取舍，为订单号与分库分表分片键选出可辩护的方案。

```flow
例子目的：雪花 ID 一条号的生成路径与位布局——时间段保证大体有序，机器段隔离实例冲突，序列段吃掉同毫秒并发
取当前毫秒(41bit, 自定义纪元起算) -> 左移22位
拼接 数据中心5bit+机器5bit(共10bit, 最多1024台) -> 左移12位
同毫秒内 seq 0~4095 自增 -> 溢出则自旋等到下一毫秒
输出 64bit 长整型 ID: 单调近似时间序 + 无中心协调
```

## 一、为什么"自增"在分布式下失效

单库 `AUTO_INCREMENT` 的三根支柱全部依赖单点：全局唯一（一个引擎计数）、单调（一个时间轴）、无冲突（一个写者）。分库分表后每个库各自加会撞号；多活写同一表更不可能。合格分布式 ID 的需求清单：

- **全局唯一**（底线）；
- **趋势递增**（InnoDB 主键随机写=页分裂+缓存命中率崩，业务排序友好）；
- **高吞吐低延迟**（每次发号 P99 < 1ms，不能有中心强依赖瓶颈）；
- **不泄露业务量**（连续自增=竞品可推算单量，电商大忌——所以订单号常用雪花+扰动或加密序号）；
- **短且可索引**（BIGINT 优于 36 字符 UUID 字符串）。

## 二、UUID：唯一但几乎不适合做主键

UUID v4 随机 122 位：无中心、无顺序、16 字节（字符串 36 字符）。做 InnoDB 主键的问题：插入位置随机 → 页分裂常态化、二级索引全带 36 字节主键膨胀、B+ 树缓存局部性差。补救路线是 **UUIDv7**（前 48bit 毫秒时间戳+随机尾）：恢复时间有序但仍是 16 字节。**工程结论**：UUID 适合做对外防遍历的资源标识（如文件 key），不适合做主键与排序键。

## 三、数据库号段模式：Leaf-segment 的精髓

```sql
-- 例子目的：号段表结构与"取一段、发一批"的核心 SQL（MySQL）
CREATE TABLE leaf_alloc (                       -- 说明：Leaf 号段表，业务名隔离多个发号域
  biz_tag VARCHAR(64) PRIMARY KEY,              -- 例子：'order' / 'pay_flow' 各自独立号段
  max_id    BIGINT NOT NULL DEFAULT 1,          -- 说明：已发放到的水位
  step      INT    NOT NULL DEFAULT 1000,       -- 目的：一次取 1000 个号——DB 访问频率降为 1/1000
  version   INT    NOT NULL DEFAULT 0           -- 说明：乐观锁列，并发更新号段靠它串行化
);
UPDATE leaf_alloc SET max_id = max_id + step, version = version + 1   -- 目的：CAS 领取号段（WHERE version 旧值由应用带上）
WHERE biz_tag = 'order' AND version = 17;                              -- 输出：影响 1 行=领取成功 [17001,18000]；0 行=被并发抢走，重试
```

**双 Buffer**（Leaf 的核心改进）：内存里持两段号——当前段用到 **10%**（阈值可配）就异步预取下一段；取号线程永不等 DB。对比单段：DB 抖动/主从切换时已发段继续可用，**把"发号"从 DB 强依赖降级为"取段"弱依赖**——号段模式的可用性本质是 step 的函数（step 越大，DB 故障容忍越久，但重启丢段越多，浪费换可用）。

其他细节：机器列表分段（Leaf-snowflake 路线用 zk 管 workerId）、`step=1000` 时实例重启最多浪费 1000 个号（趋势递增不破坏连续性假设的业务要评估此点）。

## 四、Snowflake：时间+机器+序列的三段式

位布局（Twitter 原版）：`1 符号 + 41 时间(ms, 自定义纪元可用69年) + 10 机器(1024 实例) + 12 序列(每毫秒4096个)` → 单机每毫秒 4096、理论 409.6 万/秒。

三个工程问题与解法：

1. **时钟回拨**：`now < lastTimestamp` 时——回拨 <5ms 自旋等待追平；<1s 用"借用上一毫秒序列号扩位"或直接抛错；>1s 快速失败+告警（美团 Leaf 借 ZooKeeper 判断是否真的回拨：与 zk 时间比对，只信多数）；
2. **workerId 分配**：写死配置文件=扩容忘改撞号；正解=启动时向 zk/etcd/DB 租约注册拿号，下线自动回收；
3. **单毫秒序列溢出**：自旋到下一毫秒（等待天然限流），不能回绕。

```java
// 例子目的：时钟回拨防护的最小实现——生产可用的三分支策略
class SnowflakeGuard {
    long lastTs = -1;                                // 说明：上次发号用的毫秒
    synchronized long nextId() {
        long now = currentTimeMillis();
        if (now < lastTs) {                          // 目的：检测回拨（NTP step / 虚机快照恢复）
            long offset = lastTs - now;
            if (offset <= 5) {                       // 例子：小回拨→等待追平，代价 5ms 内可忽略
                try { Thread.sleep(offset + 1); } catch (InterruptedException ignored) { }
                now = currentTimeMillis();           // 输出：追平后继续发号
            } else if (offset < 1000) {              // 例子：中回拨→用未来时间戳继续但打点告警（seq 与机器位保证不撞）
                now = lastTs + 1;                    // 结果：ID 仍单调，代价是"时间段"暂时超前真实时间
            } else {
                throw new IllegalStateException("clock rolled back " + offset + "ms");   // 错误用法兜底：大回拨宁停不发——防止长时间段撞号，交给运维介入
            }
        }
        if (now == lastTs) { /* 同毫秒 seq++ 溢出则自旋等下一毫秒，说明：略——见正文第3点 */ }
        lastTs = now;
        return (now - EPOCH) << 22 | workerId << 12 | seq;   // 目的：位拼装——时间 41bit + 机器 10bit + 序列 12bit
    }
}
```

**变体认知**：百度 UnifiedID（ZK 管时钟+秒段）、美团 Leaf-snowflake（ZK 分配 workerId+回拨仲裁）、Sonyflake（DB 记时钟）——全部围绕"机器位从哪来、回拨信谁"两问展开。

## 五、其他路线与全景对比

- **Redis INCR**：`INCR` 单线程原子、性能高、号连续；风险=持久化边界（AOF everysec 崩溃可能丢计数器最后一段→重号），需 `CONFIG SET`+号段化包装（步长预取）；适合中等严肃场景；
- **Mongo ObjectId**：4字节秒+5字节随机+3字节自增，趋势有序、12字节，天然适配无中心；
- **数据库自增+步长错开**：两库 step=2 各走奇偶——扩容改步长、多活拓扑变化即崩，只算过渡方案。

| 方案 | 有序性 | 吞吐 | 依赖 | 泄露业务量 | 典型场景 |
| --- | --- | --- | --- | --- | --- |
| UUID v4/v7 | 无/时间序 | 极高（本地） | 无 | 不泄露 | 对外资源 key、幂等 token |
| 号段（Leaf） | 趋势递增连续 | 高（缓存段） | DB 弱依赖 | 连续会泄露（可加随机起点） | 订单/账单这类要"号像流水"的 |
| 雪花 | 趋势有序不连续 | 极高（本地） | workerId 分配组件 | 可推算时间但难推总量 | 分库分表主键、消息 key |
| Redis INCR | 严格连续 | 高 | Redis（持久化边界） | 泄露 | 计数型短号（优惠券批次） |

**选型一句话**：主键要"短+趋势递增+高并发"→雪花（配 Leaf 式 workerId 管理）；对外要"像流水号的业务单号"→号段+随机起点+日期前缀（`yyyyMMdd + 号段`顺带分表路由）；防遍历的资源标识→UUIDv7。

## 六、常见线上问题

- **容器漂移动态 workerId**：Pod 重建拿到重复 workerId（配置写死）→ 同毫秒撞号；租约未释放也撞——workerId 生命周期必须与实例会话绑定。
- **NTP 步进回拨**：虚机恢复快照后回拨数分钟，未防护的发号器静默重号数月后主键冲突才暴露。
- **号段服务全实例同时重启**：各自丢掉半段号，短期大量空洞——业务把"ID 连续"当"流水连续"时投诉；号只保证唯一与趋势递增，别赋予业务语义。
- **雪花当排序键跨毫秒乱序**：时钟漂移下两实例的"时间段"不同步，ID 大小≠真实发生序；严格定序仍需逻辑时钟/Leader 序号。

## 九、本节小结

分布式 ID 的四维约束是"唯一、趋势有序、吞吐、防泄露"，没有任何方案四项全优：UUID 放弃有序、自增放弃去中心、号段放弃连续不浪费、雪花放弃严格连续。工程上按用途分刀：主键雪花（管好 workerId 与回拨）、业务单号号段（双 Buffer+日期前缀顺手做路由）、对外标识 UUIDv7——发号器的可靠性最终落在两件事上：机器身份如何租约化、时钟回拨如何仲裁。
