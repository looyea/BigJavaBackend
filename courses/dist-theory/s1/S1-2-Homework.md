# 分布式共识：Paxos / Raft / ZAB · 作业题

> 本节作业 3 题：一次故障演练 + 一次源码/论文精读 + 一道设计题。

## 作业 1：etcd 多数派塌方演练（动手）

1. 用 docker-compose 起 3 节点 etcd（固定 IP，peer 端口互通）；
2. 基线：`etcdctl put foo bar` 记录时延，`etcdctl member list` 确认 leader；
3. kill leader，观察日志中的选举过程：term 如何递增、旧 leader 复活后是否自动降级为 follower（记录时间线）；
4. 再停一个节点，使剩余 1 个，尝试读写：预期写失败报多数派不足、某些版本线性读也失败——把报错原文抄下来；
5. 恢复两节点，验证自动重新加入与日志追平。

**验收标准**：给出"term 变化表 + 每步现象与 Raft 规则的对应解释"，解释为什么剩 1 节点时连读都危险。

## 作业 2：Raft 论文三安全性定理精读（分析）

精读 Raft Extended Paper 的 §5.2（Election Restriction）、§5.3（Leader Completeness）、§5.4（State Machine Safety）：

- 用自己的话复述三个定理的证明思路（各不超过 150 字）；
- 构造一个反例：如果去掉"只投票给日志不低于自己的候选者"这条限制，画出时间线展示已提交条目如何被新主覆盖、状态机如何分叉；
- 对照 etcd/TiKV 任选其一的源码或文档，指出该限制在实现中的落点（函数/日志名）。

**验收标准**：反例时间线里必须同时出现"多数派落盘已提交"与"新主不含该条目"两个条件，并说明哪个环节被限制卡住。

## 作业 3：为电商设计元数据共识层（设计）

背景：自研配置/注册中心，需要选主与全局定序。要求：

- 比较"嵌入 JRaft/LogCabin 库自研"与"直接依赖 etcd/ZooKeeper"两条路线：运维成本、故障半径、读性能（大量客户端轮询 watch）、升级耦合；
- 给出你的选择与三条理由，并明确：如果 etcd 整体不可用，你的业务降级路径是什么（缓存旧配置 + 只读模式？拒绝发布？）；
- 画出 3 机房部署图：leader 分布、跨机房 RTT 对写入 P99 的影响估算（同城 2ms / 异地 30ms 两档）。

**验收标准**：方案里必须出现"共识集群数据量上限与快照策略"的考虑——共识日志不是业务数据库。
