# CAP / BASE 与一致性谱系 · 作业题

> 本节作业 4 题：两篇分析 + 两个动手实验。完成并在自测环境验证后，回到小节页点"手动过关"或靠小测 ≥60 分过关。

## 作业 1：给现有系统做一次"数据一致性分级"（分析）

挑选你熟悉（或仓库里任意一个）业务系统的 8~12 张核心表/缓存对象，为每个对象标注：

- 一致性等级（线性一致 / 顺序 / 因果 / 读己之写 / 最终一致）；
- 当前读写路由（主/从/缓存/Leader）是否兑现了该等级；
- 若降级了，写出触发场景（复制延迟、分区、切主）与业务损失。

**交付物**：一张分级表 + 至少两处"声明等级与实现不符"的结论。

**提示**：判断口诀——"读错会不会赔钱"决定是否上强一致端；"多读几毫秒旧数据是否有人投诉"决定能否留在最终一致端。

## 作业 2：PACELC 四象限归位（分析）

把下列系统放入 PACELC 四象限（分区时选 P-A 或 P-C；常态选 E-L 或 E-C），并用一节文字解释每个放置理由：

MySQL 组复制（leader 模式）、Cassandra（默认 quorum R=W=N/2+1）、Apollo/Nacos 配置中心、Redis Cluster 异步复制、etcd、DNS。

**提示**：Cassandra 调高 R、W 到 N 时行为向 PACELC 的 E-C 端移动——注意同一系统可通过参数在象限间移动，这正是"参数即立场"。

## 作业 3：制造一次"读不到自己写"并修复（动手）

1. 搭一主一从 MySQL（异步复制），用 `sysbench` 或脚本在主库写、从库读；
2. 用 `tc netem delay 800ms` 给复制链路加延迟；
3. 循环执行"主库更新 → 立即从库读"1000 次，统计读到旧值的比例；
4. 分别用三种方案修复并对比：会话粘滞读主、携带 GTID/版本号等待回放、写后短 TTL 内双读比对取新值；
5. 记录三种方案的 P99 延迟代价。

**交付物**：旧值命中率数据 + 三种修复方案的延迟对比表。

## 作业 4：分区演练（动手，选做加分）

三节点 etcd 集群中用 iptables 隔离 leader，观察：

- 被隔离侧客户端 `put` 的报错与时间；
- 剩余两节点选出新 leader 的耗时；
- 旧 leader 恢复网络后是否自动退位（对比 term 号）。

**交付物**：时间线记录 + 用"多数派"解释每一步现象的 200 字总结。
