```flow
例子目的：展示一次"分区期"里 CAP 的真实发生过程——网络分区把集群劈成两半，此时任何系统只能在放弃一致性或放弃可用性之间二选一
ClientA -> 分区左侧(旧Leader): 写 x=1 被接受(A侧继续服务)
分区左侧(旧Leader) -> ClientB: 读到旧值 x=0(C被牺牲, 这是AP系统的选择)
ClientC -> 分区右侧(多数派): 写请求被拒绝(右侧无法凑齐多数派, 这是CP系统的选择)
分区右侧(多数派) -> 恢复后: 左侧未同步的写被仲裁丢弃(分区愈合后对账)
```

## 一、CAP 定理到底说了什么（以及它没说什么）

CAP 的形式化陈述：一个分布式读写系统，只要满足

- **分区容忍（P）**：消息可以在网络上任意丢失/延迟（分布式系统的前提，不是选项）；

那么在**分区正在发生的那一刻**，每个操作要么保证**一致性（C，这里特指线性一致）**，要么保证**可用性（A，每个请求都得到非错误响应）**，不能兼得。

"三选二"为什么是误导：

1. **P 不是可选的**。选择了分布式，就选择了"分区可能发生"。你在 Cassandra 标注"AP"、在 ZooKeeper 标注"CP"，但两者平时都不在分区状态，这时 C 和 A 同时都有——CAP 只在分区窗口内成立。
2. **C 只指线性一致**。CAP 语境下的 C 不是日常说的"数据别错"，读己之写、单调读这些不在定义里。很多"CP"系统（如 ZooKeeper）其实只保证顺序一致，并不满足 CAP 严格定义的 C——所以论文作者 Gilbert 与 Lynch 本人后来都承认：**拿 CAP 给系统贴 CP/AP 标签基本没有信息量**。
3. **粒度错了**。真实系统里不同操作、不同数据的一致性等级不同：订单余额要强一致，商品浏览量最终一致即可。CAP 是系统级一刀切，工程上要落到**数据级**。

**例子目的：用一段可运行的单机模拟，直观看到"分区时保 A 就丢 C"的机制**

```java
// 例子目的：模拟两副本网络分区，对比 AP 策略（各写各的）与 CP 策略（凑不齐多数派就拒绝）
class PartitionDemo {
    static class ApNode {                       // AP 节点：分区期照常接受写，结果=牺牲一致性
        volatile long value;                    // 本副本的本地值，说明：两个副本各自独立，无仲裁
        void write(long v) { value = v; }       // 输出：永远接受，不检查对端是否可达——这就是"保 A"
    }
    static class CpNode {                       // CP 节点：必须多数派确认才提交，结果=分区期拒绝服务
        long value;                             // 本地值，说明：只有收到多数派 ack 才更新
        boolean quorumOk(int alive) {           // 目的：模拟 Raft/Paxos 的多数派检查
            return alive * 2 > 3;               // 输出：分区劈成 2+1 时，被隔离侧 alive=1，1*2>3 为 false → 拒绝写
        }
    }
    public static void main(String[] args) {
        ApNode a1 = new ApNode(), a2 = new ApNode();   // 例子：分区中的两个副本
        a1.write(1);                                     // 结果：a1=1，a2 仍是 0——两副本同时接收不同写，分叉
        a2.write(2);                                     // 错误用法：以为 AP 只是"稍后同步一下"，冲突值必须靠版本向量/LWW 裁决，可能丢写
        System.out.println(a1.value + " vs " + a2.value);// 输出：1 vs 2，这就是分区期 AP 付出的 C 代价
        CpNode c = new CpNode();
        System.out.println(c.quorumOk(1));               // 输出：false——CP 系统在分区另一侧直接拒写，牺牲 A 保 C
    }
}
```

## 二、一致性谱系：从线性一致到最终一致

一致性是一个**谱系**而不是开关，按强度降序：

| 等级 | 保证 | 一句话识别 | 中间件实例 |
| --- | --- | --- | --- |
| 线性一致（强一致） | 所有读看到"最近一次成功写"，且全体客户端看到的顺序与真实时间一致 | 读完立刻别人也能读到 | etcd/ZooKeeper 写路径（Quorum 读写）、Spanner |
| 顺序一致 | 全体客户端看到**同一个**操作顺序，但不必贴合真实时间 | 大家账本相同、翻页可能滞后一拍 | ZooKeeper 的 zxid 全局单调序号（实际是顺序一致） |
| 因果一致 | 有因果关系的操作保序，并发无因果的操作可乱序 | 评论一定在发帖之后出现 | Cassandra 的 LW-Counter、Riak 版本向量 |
| 读己之写/单调读 | 至少自己能看到自己的写；读到的不回退 | 发完帖刷新不能是旧列表 | Redis 主从 + 会话粘滞读主 |
| 最终一致 | 停止写入后**无时限**收敛到相同值；期间允许读到旧值 | "过会儿就对了" | MySQL 主从异步复制、DNS |

关键辨析：**线性一致 ≠ 分布式事务**。线性一致只是单个对象读写的"像是原子地发生在某一刻"；跨对象原子性（转账）要靠事务/共识叠加。

```java
// 例子目的：识别"违反读己之写"这个最常见的最终一致踩坑代码，并给出修正
class StaleReadBug {
    // 错误用法：写走主库、读走从库且无任何防护 → 提交成功后立刻刷新，从库还没回放 binlog，用户看到旧数据
    void badWithdraw(Repo master, Repo replica, long uid) {
        master.updateBalance(uid, -100);            // 写主库，结果：主库余额已减
        double shown = replica.getBalance(uid);     // 读从库——说明：复制延迟窗口内返回旧值，用户以为没扣成功又点一次
    }
    // 正确用例之一：写后的短窗口内强制读主（或带上版本号/会话标记），牺牲一点主库压力换 read-your-writes
    void goodWithdraw(Repo master, ReplicaRouter router, long uid, Session s) {
        long ver = master.updateBalance(uid, -100); // 输出：返回主库 binlog 位点/版本号 128
        s.pinMasterUntil = System.currentTimeMillis() + 2000;   // 目的：写后 2s 会话粘滞读主，覆盖典型复制延迟
        double shown = router.read(uid, ver, s);    // 结果：版本 >= 128 才返回，保证读到自己的写
    }
}
```

## 三、BASE：对"不可能三角"的工程妥协

BASE = **B**asically **A**vailable（基本可用）+ **S**oft state（软状态，允许中间态存在）+ **E**ventually consistent（最终一致）。它不是理论，是 eBay 提出的一种**运营哲学**：把"必须全局强一致"的数据缩到最小集合，其余用最终一致换取可用与吞吐。

落地三板斧：

1. **状态机收敛**：允许中间态（订单"处理中"），靠对账/补偿把状态推向终态；
2. **异步消息削竞态**：更新以事件流重放，而非多点并发写同一行；
3. **对账兜底**：最终一致必须有"最终"的度量——定时对账任务发现偏差并修复，否则"最终一致"退化成"永远不一致"。

**PACELC** 补上 CAP 的另一半：**P**artition 时选 **A** 或 **C**；**E**lse（无分区常态）在**L**atency 与 **C**onsistency 间再选一次。Quorum 参数 `W+R>N` 就是在 E 阶段买强一致（写要等 W 副本 ack，延迟上升）。

## 四、选型对比：给数据分级，而不是给系统贴标签

| 数据类别 | 一致性要求 | 典型方案 | 代价 |
| --- | --- | --- | --- |
| 余额/库存扣减 | 线性一致 | 单行事务、etcd/ZK 协调、数据库 CAS | 吞吐低、跨机房延迟高 |
| 抢锁/选主 | 线性一致（单对象） | Redlock 慎用、首选 ZK/etcd 会话 | 依赖共识集群健康 |
| 订单状态流转 | 因果一致 | 事件溯源 + 版本号 + 状态机 | 需处理乱序与重复事件 |
| 商品详情/浏览量 | 最终一致 | 主从复制 + 缓存 TTL | 短暂脏读可容忍 |
| 配置下发 | 最终一致 + 收敛检测 | 推送 + 拉取对账 | 灰度期新旧并存 |

## 六、常见线上问题

- **把"CP"当保险箱**：ZooKeeper 分区期拒写，但客户端旧会话超时前的缓存读仍是历史值——应用层拿缓存当强一致读。
- **异步复制切主丢数据**：MySQL 半同步退化普通异步时强切，最后事务未回放即丢失——一致性目标被运维流程静默降级。
- **最终一致没有对账**：消息丢了没人发现，两侧数据"最终"分叉数年。
- **读扩散写扩散混用**：同一路数据两种模型并跑，出现顺序违反因果的展示。

## 七、关联技术栈

Raft/Paxos（达成线性一致的执行机制，见下一节共识）、Canal/binlog 订阅（最终一致的收敛通道）、Redis 主从与 Lettuce 读策略、Seata（把跨服务一致性收敛到事务语义）、Caffeine/本地缓存（谱系最弱一档：单机视图）。

## 八、本节小结

CAP 不是选型口号而是"分区窗口的两难"，P 不可选、C 仅指线性一致、标签粒度错配是三大误读；真实工程做法是**按数据分级**落在一致性谱系上：钱放强一致端，展示放最终一致端，中间用因果与会话保证撑住用户体验；BASE 是配套哲学，且必须用对账证明"最终"可达；别忘了 PACELC 的下半场——平时你每次 Quorum 写都在用延迟买一致。
