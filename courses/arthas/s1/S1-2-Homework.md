# 热更新、反编译与线上排查 · 作业

## 作业 1：CPU 飙高定位全流程

- **目标**：走通"top 确认进程 → Arthas 定位热点线程 → 归因到代码行"的完整链条。
- **任务**：写一个死循环或病态正则（如 `(.*)*` 匹配长串）的测试接口并触发；然后：
  1. linux 层 `top`/`top -H` 找到高 CPU 线程并换算 16 进制 nid（老手艺，练一遍）；
  2. 用 `thread -n 3` 直接拿到同样结论，对比两种路径的耗时；
  3. `trace` 该热点方法确认耗时分布，贴出栈顶代码行。
- **验收标准**：两种定位方式输出齐全，并总结"为什么 Arthas 时代仍要会 top -H 换算"（答案指向：无 Arthas 授权的机器、容器内、面试基本功）。
- **参考解法要点**：可对照 [进程/内存/CPU/IO 四件套与 Top/vmstat](../../linux-shell/s1/S1-1-Lesson.md) 的分流表；确认热点后可用 profiler 采一段火焰图留证据。

## 作业 2：jad + mc + retransform 热止血演练（仅限本地/测试环境）

- **目标**：在安全环境完整体验热修复生命周期与它的红线。
- **任务**：对一个演示应用：
  1. `jad --source-only` 导出某服务类，把方法体内一个常量判断改错方向（如 `>` 改 `>=`）；
  2. `mc` 编译、`retransform --classLoaderHash` 注入，调用接口验证行为已变；
  3. 再尝试给该类**新增一个字段**后重复流程，记录失败报错信息；
  4. `stop` 退出后再次调用接口，观察热修是否被还原并解释原因。
- **验收标准**：三、四两步的报错/现象截图齐全；用一段话复述"retransform 只能改方法体"与"stop 会复位包括热修在内的全部增强"两条纪律。
- 注意：本作业严禁在生产或共享测试环境执行第 2、4 步。

## 作业 3：死锁与池耗尽的判定文档（文档题）

- **目标**：把 thread 命令族输出读成结论。
- **任务**：构造一个双锁交叉死锁 demo（线程 1 拿 A 等 B，线程 2 拿 B 等 A），用 `thread -b` 取证；再构造"连接池 2 个连接、4 个并发查询"的池堵场景，用 `thread --state WAITING` 观察栈聚集点。写半页判定说明：死锁与池耗尽在线程状态、栈形态、止血手段上有何区别。
- **验收标准**：两份命令输出 + 对比表（状态分布/栈顶形态/第一止血动作三列）。
- **参考解法要点**：死锁是"互等且都不释放"，池耗尽是"都在等同一个资源池"——前者解法是修加锁顺序，后者先看下游为什么慢（衔接上一节 trace）。
