# 方法级观测与调用链耗时 · 小测

## 一、单项选择题（每题 6 分，共 42 分）

### 1. Arthas 能不停机观测 Java 方法的根本机制是？（6分）

- A. 修改 JVM 启动参数开启探针
- B. 基于 java.lang.instrument 对目标类 retransform，织入观测逻辑
- C. 读取 GC 日志推断方法耗时
- D. 附带 agent 需要重启应用
> 答案：B
> 解析：attach 后动态字节码增强是 Arthas 立身之本；A/D 与"不停机"矛盾，C 与观测无关。

### 2. trace 命令中 `'params[0] != null && #cost > 100'` 的作用是？（6分）

- A. 只观测前 100 次调用
- B. 条件表达式：满足入参非空且耗时超 100ms 的调用才被记录输出
- C. 把耗时截断为 100ms
- D. 关闭 JDK 方法统计
> 答案：B
> 解析：`#cost` 是返回后才有值的内置耗时变量，条件表达式用于过滤噪声调用。

### 3. 想知道"哪个入口在调用这个方法"，应使用？（6分）

- A. stack
- B. monitor
- C. dashboard
- D. sc
> 答案：A
> 解析：stack 输出反向调用树，专治"谁调用了我"；monitor 是聚合统计，dashboard 是总览。

### 4. watch 观察大对象时控制输出体积的关键参数是？（6分）

- A. -n
- B. -x（对象展开深度）
- C. -b
- D. --skipJDKMethod
> 答案：B
> 解析：-x 限制递归展开层数；不设深度又无限定条件，toString 拷贝会刷爆堆内存。

### 5. 对 tt 记录的时间片段执行回放（`tt -i N -p`）最大的风险是？（6分）

- A. 消耗太多 CPU
- B. 非幂等方法（如下单）回放会产生真实副作用
- C. 回放后无法再观测
- D. 回放会导致 JVM 重启
> 答案：B
> 解析：回放就是重新执行那次调用，写操作可能真实落库/扣款/发短信，生产严禁对非幂等方法回放。

### 6. 出现 NoSuchMethodError，用 `sc -d 类名` 主要排查什么？（6分）

- A. 方法是否被 synchronized 修饰
- B. 同一个类被多个 ClassLoader 加载了不同版本
- C. 类是否实现了接口
- D. 类的继承层级太深
> 答案：B
> 解析："类 = 全限定名 + 加载器"，多个 classLoaderHash/code-source 即双份加载命中旧版的嫌疑。

### 7. 关于 Arthas 的使用纪律，下列哪条正确？（6分）

- A. 增强命令可以长期挂着便于随时查看
- B. 排查结束应 stop 复位全部字节码增强，而非只退出会话
- C. 同一方法可以同时叠加 trace+watch+tt 越多信息越好
- D. dashboard 会修改运行中程序的行为，生产禁用
> 答案：B
> 解析：quit 只退会话、stop 才彻底关停并还原字节码；A/C 是观测工具反噬生产的典型路径，D 错——dashboard 是只读总览。

## 二、多项选择题（每题 9 分，共 18 分）

### 8. （多选）关于 trace 与 watch 的分工，说法正确的有？（9分）

- A. trace 回答"调用链哪一跳慢"，watch 回答"这个方法的数据长什么样"
- B. trace 能看到每跳耗时，但看不到入参和返回值内容
- C. watch 的条件表达式可以只在异常时观测（如 `throwExp != null`）
- D. trace 能看到 synchronized 锁内部的等待耗时明细
> 答案：ABC
> 解析：D 超出能力边界——Arthas 粒度在 Java 方法边界，锁内部/native 等待不可见，这类问题该上 thread/火焰图。

### 9. （多选）下列哪些是"观测工具把自己变成生产风险"的反模式？（9分）

- A. 大促高峰对交易核心方法 trace 不加条件表达式与 -n 限制
- B. watch 一个包含整页订单列表的大对象且不限 -x 深度
- C. 排查完成后让 watch/tt 增强常驻过夜
- D. 用 sc -d 查看类加载器信息
> 答案：ABC
> 解析：三者分别是全量织入计时、toString 拷贝刷堆、增强残留；D 是只读查询，安全且必要。

## 三、简答题（40 分）（每题 40 分，共 40 分）

### 10. 线上某下单接口 P99 从 200ms 突升到 2s，只有单机现象（其余副本正常），请用 Arthas 设计一条从总览到根因的观测路径。（40分）

> 参考答案：
- 要点1：先分流层——dashboard/thread -n 3 判断该机是 CPU 高还是线程堆积，排除机器层问题（对照 top/vmstat）；
- 要点2：trace OrderService createOrder '#cost>500' -n 5，把慢调用逐跳分解，锁定慢在内部计算还是某个下游子调用；
- 要点3：对锁定的慢跳类再下一层 trace 二分下钻，直至定位到具体方法；
- 要点4：watch 该慢跳 '{params, returnObj, throwExp}' -x 2 带条件观测，看是数据异常（如缓存未命中回源）还是依赖超时；
- 要点5：若是"类版本不对/方法找不到"方向，sc -d 检查是否该机灰度遗留导致同类双加载，classloader -t 佐证；
- 要点6：得出结论后 monitor 回读验证修复效果，最后 stop 复位全部增强，输出观测记录进事故报告。
