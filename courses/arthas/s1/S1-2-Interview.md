# 热更新、反编译与线上排查 · 面试题

## 题 1：线上怀疑"部署的版本不对"，你怎么取证？

- 不要争论打包流程，直接看运行时：`sc -d 类名` 拿到 code-source 与 classLoaderHash，确认这个类究竟从哪个 jar、被哪个加载器加载；
- `jad --source-only` 反编译内存中生效的字节码，和 Git 目标版本 diff——运行时字节码是唯一可信证据；
- 常见实锤：灰度批次残留、fat-jar 与共享目录双份、启动脚本 classpath 指向旧包；
- 加分：指出多 ClassLoader 并存时必须按 hash 指定，否则反编译/操作到"另一份"产生误判。

## 题 2：retransform 热修复的能力边界？为什么不能当发布手段？

- 基于 JVM Redefinition：只能改方法体；增删字段/方法、改继承、改签名都会被拒绝，静态初始化改动也不保证按预期重跑；
- stop 退出会复位包括 retransform 在内的全部增强——热修天然易失，机器重启/Arthas 退出就没了；
- 定位是"发布通道阻塞时的止血钳"：止血后必须合入代码仓、走补发、验证一致，否则线上运行着无主代码，配置一漂移谁都不认账；
- 加分：对比商业热修框架（基座补丁+分发）与合规审计要求，说明金融/电力场景热修必须走应急变更流程。

## 题 3：生产一台机器 CPU 100%，从登机器到给出嫌疑人线程，说你的完整步骤。

- top 确认是 us 高还是 sy 高（用户态算子/正则 vs GC/系统调用），找到 java 进程 pid；
- `top -H -p pid` 找最忙线程 tid，`printf "%x\n" tid` 换算 16 进制 nid；
- Arthas 在场就一步 `thread -n 3` 直接给出最忙线程与完整栈；不在场 jstack 连抓 3 份对比 nid；
- 栈顶归因：业务方法→trace/watch 看数据形态；GC 线程忙→转向堆与 GC 日志；JIT 编译线程短期高属正常；
- 加分：主动区分"CPU 高是症状不是病"，并说出用火焰图验证热点分布的后续动作。

## 题 4：thread -b 找到死锁后，怎么给出治本方案？

- 读输出：两个线程各持有哪把锁、在等对方的哪把锁，落到代码就是加锁顺序不一致；
- 治本三选一：统一加锁顺序（最常用）、缩小同步范围改用tryLock带超时、用并发容器/单线程写消除交叉；
- 止血：重启受害实例（死锁线程不可自愈），并确认死锁是偶发数据形态触发还是必现逻辑；
- 加分：指出 `thread -b` 只报 JVM 显式死锁，"逻辑死锁"（都在等永远不来的条件/池耗尽互等）要靠 thread --state 分布 + trace 归因。

## 题 5：Arthas 的 profiler 命令和 Async-Profiler 是什么关系？什么时候用哪个？

- Arthas `profiler start/stop` 就是对 Async-Profiler 的封装，事件（cpu/alloc/lock）与火焰图输出同源；
- 差别在入口与权限：已有 Arthas 会话、临时抓一段，profiler 命令最顺手；要长期采样、sidecar/CI 集成、精细参数（--total、cstack 模式），直接跑 asprof；
- 与 thread -n 的分工：thread -n 是"瞬时快照点名"，火焰图是"一段时间的全景统计"——先点名救火，后采图定根因；
- 加分：能说出采样不依赖安全点、对生产开销低（1% 量级）这一选型理由，细节留给火焰图课程。

## 题 6：把"线上止血"讲成一个流程题：凌晨 3 点交易成功率跌 10%，你有 Arthas 权限。

- 第 0 步并行止血与取证：先摘除/重启一台受害实例验证是否环境性全局故障，避免全集群陪葬；
- 分流：dashboard + thread -n 3 + trace 条件过滤，10 分钟内给出"哪类方法/哪类数据"假设；watch 抓异常现场坐实；
- 若定位为代码级缺陷且可方法体修改：低峰实例先行 retransform 止血（留痕、可回滚），同时拉起正式修复；
- 若为容量/依赖问题：止血靠限流降级开关而不是热修，热修解决不了下游变慢；
- 加分：强调每一步的"输出留档进事故单"与事后复盘改进（补告警、补测试），把工具链讲成工程纪律而不是炫技。
