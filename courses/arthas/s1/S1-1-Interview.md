# 方法级观测与调用链耗时 · 面试题

## 题 1：线上不能重启、不能改代码，如何定位一个接口偶发变慢的原因？

- 分层分流：先机器层（top/vmstat 判 CPU、IO、内存），再进程层（Arthas dashboard + thread -n 3 看热点线程），最后方法层；
- 方法层用 `trace 类 方法 '#cost > N' -n 5` 做调用链逐跳分解，锁定慢跳后再对该类下钻一层 trace，二分逼近；
- 锁定嫌疑方法后用 `watch '{params, returnObj, throwExp}' -x 2 条件` 看数据形态（缓存未命中回源、超大入参、慢 SQL 拼装）；
- 加分：强调条件表达式与 -n 是生产纪律——无过滤全量增强等于给自己加了一次故障注入。

## 题 2：trace 和 watch 分别回答什么问题？为什么不能互相替代？

- trace 回答"哪一跳慢"：给出方法内子调用树的耗时分解，但不展示任何数据内容；
- watch 回答"为什么"：在方法进/出/异常边界抓入参、返回值、异常对象，但不给你调用链结构；
- 组合拳是标准姿势：trace 定位慢跳 → watch 验证该跳的数据假设；stack 再补"谁调用我"的反向问题；
- 加分：指出两者粒度都在 Java 方法边界——锁等待、native 耗时、GC 停顿都不是它们的菜，要转 thread/火焰图/GC 日志。

## 题 3：tt 时间隧道的"回放"功能什么时候不能用？

- 回放等于以当时的入参真实重新执行方法：下单、扣款、发短信这类**非幂等写操作**会产生真实副作用，绝对禁止；
- 只读查询接口理论上可回放，但生产回放仍会打依赖（DB/下游），要评估流量与限流；
- 更稳的用法是"只索引、只查看"：`tt -i N` 展开现场快照排查数据，不动执行；
- 加分：能提出"要复现问题不如把 tt 现场参数抄下来在预发环境重放"的隔离思路。

## 题 4：NoSuchMethodError / 类冲突类事故，Arthas 怎么查？根因通常出在哪？

- `sc -d 类名` 看同名类出现几次、各自的 classLoaderHash 与 code-source——多加载器多副本即"双份加载"实锤；
- `classloader -t` 看加载器父子树，判断哪个版本按委托模型该被命中；`jad` 反编译运行时真正生效的那份字节码做终审；
- 根因常在依赖打包：fat-jar 与容器共享目录各带一份不同版本的工具类、shade 未 relocate、灰度残留旧包；
- 加分：强调治本是统一版本/排除依赖，retransform 热补丁只是止血，且下个类冲突还会再来。

## 题 5：Arthas 观测会不会影响生产？边界与纪律是什么？

- 会：每条增强命令都是字节码替换 + 方法边界织入逻辑，高频方法上无条件观测的开销可观；watch 大对象不设 -x 会拷贝刷堆，tt 存储索引吃内存；
- 纪律：一切增强命令带条件表达式与 `-n`；避开每秒数千调用的公共方法全量观测；同方法不叠加多种增强；排查完 `stop` 复位（quit 只是退会话）；
- 观测窗口选择：能用预发复现的不上生产；必须上生产的放在低峰并留好回滚；
- 加分：对比"Arthas 单点即时观测 vs Async-Profiler 全局持续采样"的适用面差异，说明二者是互补不是二选一。

## 题 6：只有单机异常（其余副本正常）时，你的排查路径和常见结论是什么？

- 先坐实"单机"：对照正常副本的 dashboard/GC 数据，确认是环境差异不是全局缺陷；
- 常见结论分层：机器层（同宿主机邻居抢资源、NUMA/swap）、JVM 层（该机 Full GC 频繁、JIT 未预热、连接池打满）、部署层（灰度残留导致类双加载或配置漂移）、数据层（路由到该机分片的热点数据）；
- Arthas 路径：thread -n 3 + trace 条件过滤对比"该机慢跳分布"与正常机差异，sc -d 排除版本漂移；
- 加分：提出"观测取证后优先摘流量再慢慢查"——止血与根因分析是两条并行线，别让全集群等一台机器的诊断。
