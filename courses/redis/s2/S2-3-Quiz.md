# 小测验 · 大 Key、热 Key 与内存治理

> 本卷共 6 题，混合单选 / 多选 / 判断 / 填空 / 简答，满分 100 分折算百分制，≥ 60 分过关。

### 1. 直接 `DEL` 一个 100 万元素的 Hash 会发生什么？（15分）

- A. 后台线程慢慢回收，无感知
- B. 单线程同步释放 100 万个元素，主线程阻塞数百 ms 到秒级，期间所有请求排队
- C. 只删索引不删数据
- D. 自动转为 UNLINK

> 答案：B
> 解析：DEL 的时间复杂度与元素数成正比且在主线程执行——"清理动作本身引发事故"的经典案例；大 key 删除一律用 UNLINK（分离线程异步回收）或惰性分批 HSCAN+HDEL。

### 2. Redis 的 LRU 淘汰是"近似"的，原因是？（15分）

- A. 全量 LRU 链表维护成本太高，Redis 改为每个 key 记最后访问时间、淘汰时随机采样 `maxmemory-samples` 个 key 取其中最旧者
- B. LRU 算法已被证明无效
- C. Redis 无法感知访问时间
- D. 只有企业版才有真 LRU

> 答案：A
> 解析：给全库维护有序 LRU 链是 O(1) 空间换时间的做法但写放大巨大；采样近似以极小代价逼近真 LRU，samples 越大越准越耗 CPU。C 错——lru 位正是记录在 obj 上的。

### 3. 【多选】关于热 Key 治理，正确的措施有哪些？（20分）

- A. 应用层本地缓存（短 TTL + 失效广播）把热点消化在 Redis 之外
- B. `key#1…key#N` 多副本写、读随机打散，把单分片压力除以 N
- C. 热 Key 配很长的 TTL 且过期用互斥重建/永不过期后台刷，避免"热+过期=击穿风暴"
- D. 给热 Key 所在节点加更多从库即可线性提升该 key 的读 QPS 上限

> 答案：ABC
> 解析：D 错——Cluster 下写与"该 key 的读"都路由到同一槽的主节点，加从库不解决单 key 集中（读写分离还引入延迟问题）；热 key 必须"散"（本地/副本）而不是"堆"。

### 4. 判断：`mem_fragmentation_ratio` 大于 1.5 说明内存用得太省，无需处理。（10分）

- A. 正确
- B. 错误

> 答案：B
> 解析：>1.5 表示 RSS 远大于数据实际占用——分配器碎片严重（或含换页），浪费内存；应开 activedefrag 或计划内重启压实。而 **<1 更危险**：说明部分内存被 swap 出去，延迟即将爆炸。

### 5. 填空题：发现大 Key 用 `redis-cli --bigkeys`（基于 ______ 游标扫描不阻塞）与 `______ USAGE` 精量字节；发现热 Key 在 LFU 策略下用 `redis-cli ______`；缓存库淘汰策略应选 allkeys-lru/lfu，绝不能配成 ______（写全报错）。（20分）

> 答案：SCAN / MEMORY / --hotkeys / noeviction

### 6. 线上巡检发现：某 Cluster 节点 CPU 与带宽独高，其它节点正常。给出排查路径与两类根因的对应治理。（20分）

> 参考答案：
> - 排查：INFO commandstats/latency 确认该节点命令特征 → --hotkeys(LFU)/代理统计查单 key QPS 集中度 → --bigkeys/MEMORY USAGE 查该节点是否有超大 key 或 hash tag 聚集
> - 根因一 热 Key：治理=本地缓存+多副本打散+防击穿配套
> - 根因二 大 Key（或 hash tag 滥用致槽不均）：治理=拆桶分页+UNLINK 清理+纠正 tag 设计，必要时 reshard 迁移槽
> - 收口：两类都要写入巡检例行（事故前发现），并配 CPU/带宽/命中率告警阈值
