# 实际面试题 · 大 Key、热 Key 与内存治理

> 收录 2024—2026 国内中大厂 Java 后端真实面试，含追问链。考"大 key 出过事故吗、淘汰策略怎么选、内存告警怎么处理"。

## 题 1：什么叫大 Key？它到底伤在哪？

**期望时长**：60 秒

**答题要点**：

- 经验线：String >10KB、集合元素 >5000 / 整体 >10MB（各厂阈值不同，思想一致）。
- 伤害四层：① 单线程执行 O(n) 命令（HGETALL/DEL/大 value 序列化）期间**全库排队**；② 网络传输挤占带宽、慢客户端 output buffer 堆积；③ fork/持久化与复制被大 value 放大（COW、全量同步风暴，s1-2）；④ Cluster 下槽不均，单节点独高。

**追问链**：怎么发现？→ 离线：`--bigkeys`（SCAN 不阻塞）+ `MEMORY USAGE` 精量 + 云厂商 RDB 全量分析；在线线索：SLOWLOG 里的大 O 命令、带宽/延迟毛刺。

## 题 2：线上要清理一个亿级元素的大 Key，怎么做才安全？

**答题要点**：

- 绝不同步 DEL：O(n) 阻塞秒级；用 **UNLINK** 交给后台线程回收。
- 更温和：SCAN/HSCAN **分批游标删除**（每批几百 field + sleep），配合低峰执行——和 mysql 大事务分批删除（s3-3）同一思想。
- 事前：确认没有依赖方在读（业务下线后再删），删除动作本身要能中断续跑。

**追问链**：UNLINK 的代价是什么？→ 内存释放滞后（后台慢慢还），极端写入下 RSS 峰值更高；空间本来就紧张时要评估。

## 题 3：热 Key 怎么发现、怎么治理？

**答题要点**：

- 发现：`--hotkeys`（需 LFU 策略）、OBJECT FREQ、代理/客户端 QPS 统计、大促前按榜单预估名单。
- 治理三件套：**本地缓存**（短 TTL+失效广播，终极解）；**多副本打散**（key#1..N 随机读）；**热点保护**（永不过期+后台刷或互斥重建，防"热+过期=击穿"，s2-1）。
- 架构层：独立热点池（把爆款 key 路由到专属实例，伤不到普通业务）。

**追问链**：为什么加从库救不了热 Key？→ Cluster 同 key 同槽，读仍集中主节点；哨兵模式下所有读打同一实例也要靠"散"而非"堆副本"（副本还引入延迟）。

## 题 4：maxmemory-policy 八种策略，你们怎么配？

**答题要点**：

- 记法：noeviction（默认，写报错）+ allkeys-{lru,lfu,random} + volatile-{lru,lfu,random,ttl}。
- 纯缓存库：**allkeys-lru**（或 lfu，抗一次刷屏更稳）；带 TTL 语义的库才可用 volatile-*；**混放锁/计数器的库绝不能让 allkeys 淘汰到它们**——分区隔离（不同实例/不同 db+noeviction）优于赌策略。
- 近似 LRU：随机采样 samples 个取最旧，越大越准越耗 CPU。

**追问链**：缓存库配了 noeviction 会怎样？→ 满了之后所有 SET (error) OOM command not allowed，写全挂——比淘汰更糟；反之锁库配 allkeys-lru 会锁被驱逐导致互斥失效（redisson 章节细谈）。

## 题 5：`mem_fragmentation_ratio` 是什么？高低分别说明什么、怎么处理？

**答题要点**：

- 定义：RSS（OS 视角占用）/ used_memory（Redis 数据视角）。
- **>1.5**：分配器碎片多（jemalloc）或含缓冲区开销 → 开 `activedefrag yes` 在线整理，或低峰重启靠 RDB 加载自然压实。
- **<1**：部分内存被 swap → 延迟灾难前夜；处理：加物理内存/降 maxmemory/关 swap，而不是"庆祝省内存"。
- 配套巡检三指标：水位（used/maxmemory）、evicted_keys 增速、碎片率——**内存治理靠日常巡检不靠事故复盘**。

**追问链**：为什么 Redis 6/7 后碎片问题少了些？→ 多线程 IO 只并行网络读写，键操作仍单线程，分配行为变化不大；改善主要来自 jemalloc 调优与 activedefrag 普及——诚实回答比编造加分。
