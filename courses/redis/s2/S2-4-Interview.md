# Redis 作为协调服务：锁、限流与计数器 · 面试题

## 题 1：用 Redis 怎么做分布式锁？

- `SET key token NX PX ttl`：NX 原子抢占、PX 定 TTL 防死锁。
- 解锁必须"比对 token 再删"且用 Lua 原子执行，避免误删他人锁；持锁期间看门狗续期防提前过期。
- 加分：点出先 GET 再 SET、裸 DEL 不校验、无 TTL 三大经典坑。

## 题 2：Redis 锁可靠吗？会出什么问题？

- 主从异步复制：主确认锁后崩溃、新主无此锁 → 可能双持有。
- RedLock 依赖多节点与时钟一致，怕 GC/网络暂停，学界有争议。
- 加分：强正确性临界区应退让给 ZK/etcd(CP) 或数据库唯一约束/CAS。

## 题 3：多实例部署下如何全局限流？

- 把计数收敛到 Redis 单一真值源，用原子命令：INCR+EXPIRE 固定窗口、ZSET 滑动窗口、Lua 令牌桶。
- 本地计数器在多实例下形同虚设。
- 加分：说明固定窗口边界突刺、令牌桶允许可控突发的取舍。

## 题 4：为什么解锁不能直接 DEL？

- 自己锁过期后他人已抢占，裸 DEL 会删掉新持有者的锁，导致并发进入临界区。
- 必须 `GET==token 才 DEL` 且原子完成（Lua）。
- 加分：token 要每次唯一（线程+随机），这是持有者识别的基础。

## 题 5：加了锁是不是业务就绝对正确了？

- 不是。锁可能因过期、failover 丢锁而失效。
- 被保护操作还应有幂等键/唯一约束/CAS 兜底，锁只是护城河之一。
- 加分：把"锁 + 幂等"组合防线讲清楚，体现对失效场景的工程清醒。

## 题 6：Redis 协调 vs ZooKeeper/etcd 怎么选型？

- Redis(AP 取向)：高并发、允许极小概率失效的锁/限流/防重，性能优先。
- ZK/etcd(CP)：强一致临界区、服务发现/选主等对正确性零容忍场景。
- 加分：结合 CAP 讲清"协调"也要按一致性要求分档，不是一刀切。
