# Redis 作为协调服务：锁、限流与计数器 · 作业

### 作业 1：一把"能放心用"的 Redis 分布式锁

- 目标：实现抢占、续期、原子释放三要素齐备的锁，杜绝误删他人锁与死锁。
- 任务：用 `SET key token NX PX 30000` 加锁，生成唯一持有者 token；解锁用 Lua "GET==token 才 DEL"；启动看门狗在持锁期间周期续期。构造并发场景：A 持锁业务超时、B 抢到锁后，A 释放不能删掉 B 的锁。
- 验收标准：先 GET 再 SET 的竞态写法不出现；裸 DEL 被 Lua 比较删除替代；业务超过初始 TTL 时锁仍被续期不误放；并发验证只有持有者能解锁。
- 参考解法要点：token=线程+随机；续期间隔取 TTL 的 1/3；明确这把锁在异步复制下仍可能失效，不作唯一正确性保证。

### 作业 2：全局限流器（固定窗口 → 令牌桶）

- 目标：让限流在多实例部署下对全局生效，而非每实例各限各的。
- 任务：先用 `INCR + 首次 EXPIRE` 实现固定窗口限流，指出其边界突刺；再用 ZSET 实现滑动窗口、用 Lua 实现令牌桶（按时间补币+取币），对比三者对"突发容忍"与平滑度的差异。压测多实例并发请求验证阈值全局一致。
- 验收标准：计数落在 Redis 单一真值源、多实例结果一致；能复现固定窗口在窗口交界的突刺；令牌桶允许可控突发。
- 参考解法要点：Lua 保证"补币+取币"原子；Cluster 下所有 key 需同槽或用 hash tag。

### 作业 3：协调边界的选型论证

- 目标：能讲清"什么时候 Redis 协调够用、什么时候必须换 CP 方案"。
- 任务：给出三类场景（秒杀防超卖、接口防重、资金双扣防护），为每类判定用 Redis 锁/限流是否足够、失效后果多严重、是否需要幂等键或数据库唯一约束/CAS 兜底，并说明若换 ZK/etcd 的代价。
- 验收标准：对"零容忍丢锁"的场景明确倾向 CP 或数据库约束；对"允许极小概率失效"的高并发场景合理留在 Redis；每类都给出兜底手段。
- 参考解法要点：把锁当护城河之一而非唯一保证；与幂等、乐观锁/CAS 形成组合防线。
