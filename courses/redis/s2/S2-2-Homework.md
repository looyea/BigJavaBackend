## 作业 1：复现"先删后更"的无限残留（必做）

```java
// 例子目的：用人为 sleep 放大并发交错，亲眼看到旧值被回填后永不自愈
// 线程 R（读）：redis.get 得 null → db.select 得旧价 99 → 【sleep 3s】→ redis.set(key, 99)     // 模拟慢回填
// 线程 W（写）：sleep 1s 后执行"先 del 缓存，再 update DB=88"                                    // 错误用法：先删后更
// 预期观察：3s 后缓存被回填 99，而 DB 已是 88；不再有任何写发生的话，99 将存到 TTL 到期（正确对比实验：改成"先更后删"重跑，缓存只剩毫秒级窗口）
```

注释写下你观察到的最终缓存值、DB 值，以及"为什么这次没有自愈机制"。

## 作业 2：Cache Aside 工程化（必做）

把课文的 afterCommit + 重试队列写成可复用切面（注解 `@CacheEvictAfterCommit(key="prod:#id")`），删除失败投递到本地队列并每秒重试 3 次。

**参考答案要点**：事务同步回调 `afterCommit` 保证"提交成功才删"；重试 3 次仍失败落库告警——剩下的不一致交给 TTL，心里要有"最坏窗口=TTL"的数。

## 作业 3：延迟双删参数实测（必做）

在作业 1 场景上启用"先更后删 + sleep 后二删"，测出你环境的读回填 P99 耗时，把 sleep 设为 P99×2；复跑交错脚本确认二删能扫掉回填残留；再把 sleep 故意设成 P99 的一半，观察仍残留的概率。

注释结论：sleep 定多长算"对"？为什么这是概率补丁而非保证。

## 作业 4：Canal 旁路写失效（选做）

docker 起 canal-server 连 MySQL（ROW binlog），消费端脚本打印变更并 `DEL prod:1001`。用客户端**直连 DB** 执行 `UPDATE product SET price=77 WHERE id=1001`（完全绕过应用），验证缓存被失效。

**参考答案要点**：Canal 需要 `server-id`、`binlog_format=ROW`、复制权限账号（呼应 mysql s3-1/s3-2 主从原理——它就是一个"从库"）。

## 作业 5：一致性分级设计文档（选做）

为你熟悉的一个业务（电商商品/电力抄表/金融账户）写一页缓存一致性设计：列出 3 类读场景、各自允许的旧值窗口、采用的方案（Cache Aside/双删/binlog/直读 DB）与监控指标。

**参考答案要点**：能写出"错了谁负责、窗口多大可接受"并与业务确认记录，比堆方案更加分。
