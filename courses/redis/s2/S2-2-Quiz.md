# 小测验 · 缓存与数据库一致性

> 本卷共 6 题，混合单选 / 多选 / 判断 / 填空 / 简答，满分 100 分折算百分制，≥ 60 分过关。

### 1. 写路径采用 Cache Aside 时，正确的操作顺序是？（15分）

- A. 先删缓存，再更新 DB
- B. 更新 DB → 事务提交后再删除缓存（删除失败入重试）
- C. 更新 DB → 更新缓存
- D. 先更新缓存，再更新 DB

> 答案：B
> 解析：先删后更留给并发读"回填旧值且无人再删"的无限窗口；提交前删遇到回滚会留下"缓存空+DB 旧+被回填旧值"的问题；更新缓存则有并发写乱序钉旧值风险。B 把窗口压到毫秒级并用 TTL 兜底。

### 2. "删除缓存"而不是"更新缓存"的核心理由不包括？（15分）

- A. 并发两个写对缓存的更新可能乱序，把旧值长期钉在缓存
- B. 缓存常是多表聚合视图，单行变更无法独立重算
- C. 删除是 O(1) 而更新是 O(n)
- D. 懒加载哲学：写了没人读的缓存更新纯属浪费

> 答案：C
> 解析：C 是凑数的——SET 和 DEL 复杂度同级。A/B/D 才是"删不改"的三大真实理由（乱序钉旧值、聚合视图难重算、无效更新浪费）。

### 3. 【多选】关于延迟双删，说法正确的有哪些？（20分）

- A. 做法是"更新 DB 删缓存后，sleep 一段时间再删一次"，第二删用来清掉慢读回填的旧值
- B. sleep 时长要覆盖"一次读回源的最大耗时"，本质是对并发交错窗口的概率性补丁
- C. 用了延迟双删就可以去掉缓存 TTL
- D. 它的局限在于 sleep 只能估、估短了仍可能残留，所以 TTL 兜底不可省

> 答案：ABD
> 解析：C 错得典型——延迟双删压缩窗口但非零，TTL 是所有一致性事故的自愈终点，任何方案都不该拿掉它。

### 4. 判断：订阅 binlog（如 Canal）做缓存失效的最大优势是能兜住"绕过应用的旁路写"（直连 DB 改数、跑批、其它系统写入）。（10分）

- A. 正确
- B. 错误

> 答案：A
> 解析：人肉埋点只覆盖本应用的写路径，旁路写必漏；binlog 是 DB 的唯一出口事实，任何来源的变更都会产生事件，且业务代码零侵入。

### 5. 填空题：双写系统不存在强一致的根源是两个存储的写没有 ______ 性（无共同事务）；Cache Aside 的残留漏洞出现在"读请求查完 DB、______ 之前"恰好跨过整个写路径的慢交错；收敛兜底靠缓存 ______。（20分）

> 答案：原子 / 回填缓存（写回缓存）/ TTL（过期兜底）

### 6. 面试官问"你们商品改价后缓存怎么保证一致"，给出分级方案（详情页 / 库存页 / 资金关联页）并各说一句理由。（20分）

> 参考答案：
> - 详情页：Cache Aside（提交后删 + 重试）+ 分钟级 TTL——旧价几十秒可容忍，TTL 自愈
> - 库存/秒杀页：Cache Aside + 延迟双删或直接读写 DB/Redis 原子扣减（s2-1 逻辑过期禁用），不允许旧值参与成交判断
> - 资金/余额页：不依赖缓存做决策，直读 DB 或以 binlog 管道秒级收敛 + 对账兜底——一致性要求高于性能，为正确性付代价
> - 收口：先与业务确认真实的一致性需求（窗口多大、错了谁负责），再选方案，不为"看起来先进"上组件
