# 实际面试题 · 缓存与数据库一致性

> 收录 2024—2026 国内中大厂 Java 后端真实面试，含追问链。考"先更新缓存还是先删缓存、延迟双删多久、binlog 订阅链路"。

## 题 1：更新数据时，缓存和 DB 怎么保持同步？

**期望时长**：90 秒

**答题要点**：

- 开门见山：两个存储双写**没有原子性**，强一致做不到，谈的是"窗口多小 + 怎么收敛"。
- 标准 **Cache Aside**：更新 DB → **事务提交后**删除缓存；删除失败进重试；缓存必须有 TTL 兜底。
- 读路径：miss 回源 DB 并回填（加互斥防击穿，呼应 s2-1）。

**追问链**：为什么是"删"不是"更新"缓存？→ ① 并发写对缓存的 SET 可能乱序，把旧值钉住；DEL 无此问题（后删总是安全，回源见真相）；② 缓存常是多表聚合视图，单行变更算不出完整新值；③ 写了没人读纯浪费（懒加载）。

## 题 2：先更新 DB 再删缓存，就没有一致性问题了吗？

**答题要点**：

- 有一个极端窗口：**慢读交错**——R 查 DB 得旧值后被挂起，W 完成"更新+删除"，R 醒来把旧值回填 → 残留到 TTL。
- 压缩手段：**延迟双删**（sleep 覆盖回填最大耗时再删一次），但 sleep 只能估算，是概率补丁。
- 底线设计：TTL 让任何残留有自愈终点；核心数据走 binlog 订阅收敛。

**追问链**：那"先删缓存再更新 DB"呢？→ 更糟：删与更之间任何读都会回填旧值，且**没有下一次删除**来纠正——窗口无限长，这是两种顺序的本质差别。

## 题 3：延迟双删的"延迟"到底设多少？

**答题要点**：

- 依据 = 一次"读回源+回填"的最大耗时（用压测 P99×2，不是拍脑袋 1 秒）。
- 实现别用同步 sleep 堵业务线程：异步二删（线程池/MQ 延迟消息）。
- 诚实收口：它只压缩概率不保证归零，必须与 TTL 共存。

**追问链**：为什么二删走异步消息更稳？→ 延迟消息精度可控、可重试，且应用扩容/重启不丢二删任务。

## 题 4：说说 Canal 订阅 binlog 刷缓存的完整链路和坑。

**答题要点**：

- 链路：Canal server 伪装从库（dump 协议，需 ROW binlog+复制权限）→ 解析行变更 → 投 MQ → 失效消费者按 `表+主键` 映射 key 执行 DEL。
- 优点：业务零侵入、**旁路写全覆盖**（直连 DB/跑批/异构系统）。
- 坑：① at-least-once 要幂等（重复 DEL 无害，天然满足）；② 位点卡住/MQ 堆积=收敛延迟拉长，**监控 lag**；③ key 映射规则变更要和缓存写入方同步；④ 不能因此去掉 TTL。

**追问链**：为什么必须 ROW 格式？→ STATEMENT 下同一 SQL 在不同节点可能产生不同结果，下游无法可靠还原行级变更（呼应 mysql s3-1）。

## 题 5：余额/库存这类绝不允许旧值的数据，你怎么设计？

**答题要点**：

- 第一反应：**别让缓存参与成交决策**——扣减用 DB 原子 SQL（`WHERE stock>=n`，mysql s2-1）或 Redis 单线程 Lua 原子扣（数据以 Redis 为主存储、异步落 DB），不是"缓存一致性"问题而是"单一真相源"问题。
- 展示类读可缓存，但要参与决策的值直读真相源。
- 金融级：binlog 级收敛 + 定时对账（缓存/DB 差异告警修复）。

**追问链**：Redis 扣减+异步落 DB，Redis 挂了怎么办？→ AOF everysec + 主从（s1-2），最坏 1s 窗口靠对账回补——把"缓存"升格为"存储"时，持久化与对账体系必须配套到位。
