# 缓存穿透/击穿/雪崩

> 本节难度：★★★★☆
> 本节重要性：★★★★★
> 学习产出：把三个名字相近、机理完全不同的事故掰开——**穿透**（查**根本不存在**的数据，缓存永远空，每次都打 DB）、**击穿**（**单个热点 key** 过期瞬间被并发打爆）、**雪崩**（**大批 key 同时过期**或 Redis 整体不可用）；对每一种给出可落地的组合拳：空值缓存与布隆过滤器、互斥重建与逻辑过期（singleflight 思想）、过期打散与多级缓存兜底，并讲清各方案的**副作用**（空值占内存、布隆不支持删除、逻辑过期读到旧值）。这是大促/秒杀系统的保命题，也是面试"缓存三大问题"的标准答案。

## 一、三问三判，一图分清（★★★★☆）

```flow
区分三者（目的：先确诊再开药——问"DB 收到的是哪种请求"）
穿透：请求的 key 在 DB 里也不存在（如 id=-1、乱造的 sku）→ 缓存查不到→DB 查不到→永远不回填 → DB 每次都挨打
击穿：key 存在但刚过期/正好最热（爆款商品）→ 过期瞬间 1 万并发同时 miss → 全涌向同一行 SQL
雪崩：一大片 key 同一时刻过期（昨晚批量导入 TTL 一样）/ Redis 宕机 → 全量流量回源，DB 被打挂 → 更雪崩
```

- 口诀：**穿透查"无"、击穿打"一"、雪崩打"片"**。
- 监控信号：DB 慢 SQL 里出现大量不存在的 id（穿透）；单条 SQL 并发尖刺（击穿）；命中率断崖 + 全表都慢（雪崩）。

## 二、穿透：空值缓存与布隆过滤器（★★★★★）

```java
// 例子目的：商品详情缓存的穿透双保险——短 TTL 空值 + 布隆前置拦截
public Product getDetail(long skuId) {
    String key = "prod:" + skuId;
    String json = redis.get(key);
    if ("NULL".equals(json)) return null;          // 命中空值标记：直接返回，不再打 DB（正确：挡住已知的穿透流量）
    if (json == null) {
        if (!bloom.mightContain(skuId)) {          // 布隆说"一定不存在"→ 可信；写一个短 TTL 空值防同 id 反复来问
            redis.set(key, "NULL", 60, SECONDS);   // 60s 短过期（正确：空值也占内存，TTL 必须短；新品上架靠布隆重建放行）
            return null;
        }
        json = singleflightLoad(key, skuId);       // 可能存在：走下一节的互斥重建（防与击穿叠加）
    }
    return parse(json);
}
// 正确使用结果：乱造 skuId 的爬虫流量在布隆/空值两层被吃掉，DB QPS 平稳
// 错误用法：空值缓存不设 TTL（或 TTL=正常缓存的 24h）→ 商品真的上架后最长一天查不到（数据"凭空缺失"事故）；
//           布隆误判率配成 10% 还不建空值兜底 → 每 10 个假阳性仍有 1 个打到 DB，量大照样击穿
```

> 布隆的删除难题：不支持删 → 用**周期重建**（每天按 DB 全量新建一个过滤器原子切换）或 counting bloom / Cuckoo filter；新品要**先落库再重建**，重建窗口内靠短 TTL 空值缓存兜底放行（宁可漏几条到 DB，也别把新品挡一天）。

## 三、击穿：互斥重建 vs 逻辑过期（★★★★★）

```java
// 例子目的：热点 key 过期瞬间只放一个请求去重建（互斥式 singleflight）
String v = redis.get(key);
if (v == null) {
    if (redis.set("重建锁:" + key, uuid, nx(), px(3000))) {   // SET key uuid NX PX 3000：抢到锁者一人回源（正确：锁必须带 TTL 防持有者宕机死锁）
        try { Product p = db.load(id); redis.set(key, json(p), ttlWithJitter()); }
        finally { eval(LUA_DEL_IF_VALUE, "重建锁:"+key, uuid); } // 按值释放（错误用法：直接 DEL → 重建慢时锁已过期、删掉的是别人刚抢的锁 → 并发重建失控）
    } else {
        sleep(50); return getDetail(id);                         // 没抢到的自旋等重建者写回（正确：等待有上限，超限降级读旧值/兜底页）
    }
}
```

- **互斥**：强一致取向——其余请求等待或返回旧值，吞吐略降，DB 只挨一次。
- **逻辑过期**：value 里存 `expireAt` 字段、Redis 层不设 TTL；发现"逻辑过期"就**异步**交给后台线程重建，当前请求**直接返回旧值**。可用性最高（永不阻塞），代价是读到过期数据——**秒杀价格/库存绝不能用**。

## 四、雪崩：打散、限流、架构兜底（★★★★★）

- **TTL 打散**：`ttl = base + random(0, base*0.2)`——禁止批量任务用同一个 `EXPIRE`（昨晚导入的 500 万 key 全在凌晨 3 点整过期=定时炸弹）。
- **回源限流**：DB 前挂令牌桶（Sentinel/Resilience4j），超过容量的请求直接返回兜底数据——雪崩时"牺牲新鲜度保 DB"。
- **多级缓存**：本地 Caffeine（1s~30s 短 TTL）→ Redis → DB；Redis 集群挂掉时本地还能扛住读尖峰。
- **架构侧**：Redis 高可用（哨兵/Cluster，s1-2）+ 缓存预热（大促前脚本灌热 key）+ 熔断降级预案演练。

## 五、动手题

1. 用 JMeter 以 1000 QPS 查 `sku=-1`，观察未加防护/空值缓存/布隆三档下 DB QPS 变化。
2. 给爆款 key 设 10s TTL，重启压测对比"直冲 DB""互斥重建""逻辑过期"三版的 DB 尖刺与请求延迟分布。
3. 批量 SET 10 万 key 统一 60s 过期，60s 时观察回源风暴；改 TTL 加随机抖动复测。

## 六、常见线上问题

| 现象 | 根因 |
| --- | --- |
| DB 大量 `id=?` 查不存在记录、QPS 与攻击同步 | 穿透：无空值/布隆，爬虫乱造 id |
| 新品上架一小时"查无商品" | 布隆没重建 + 空值 TTL 过长，双层误挡 |
| 缓存过期瞬间 DB 单行 1 万并发 | 击穿：热点 key 无互斥重建 |
| 每天凌晨 3 点 DB CPU 100% | 雪崩：批量导入用了同一 TTL |
| Redis 主从切换后全线超时 | 切换期间 miss 全部回源且无回源限流/本地缓存兜底 |

## 七、关联技术栈

- **向前**：Cluster/Sentinel 决定"整体不可用"的概率 ↔ s1-2
- **向后**：一致性方案（Cache Aside）与重建锁配合 ↔ s2-2；热点 key 的本地代理缓存 ↔ s2-3
- **横向**：singleflight ↔ juc 锁与 CompletableFuture（java 进程内版）；限流降级 ↔ Sentinel/Gateway 课程

## 八、本节小结

三问机理不同药方不同：**穿透**（查不存在的）用短 TTL 空值 + 布隆前置，警惕"布隆不能删→周期重建"与误杀新品；**击穿**（一点过期）用互斥重建（SET NX PX + 按值释放）保一致性，或逻辑过期换可用性（永远返回旧值，库存价格禁用）；**雪崩**（片过期/集群挂）靠 TTL 打散 + 回源限流 + 多级缓存 + 预热与高可用架构兜底。监控上以"命中率、DB 回源 QPS、单 SQL 并发尖刺"三指标确诊。所有方案都写不进"银弹"两个字——每个补丁都有自己的副作用，选型就是权衡。
