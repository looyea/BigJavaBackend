# 缓存与数据库一致性

> 本节难度：★★★★★
> 重要程度：★★★★★
> 学习产出：先立总纲——**双写系统做不到强一致，只能选"不一致窗口多小、靠什么收敛"**。掌握 **Cache Aside**（读时回填、写时"先更 DB 再删缓存"）及其两个为什么（为什么删不是改、为什么先库后删）；看懂**读-写并发交错**产生的旧值窗口与**延迟双删**的适用边界；理解终极收敛手段**订阅 binlog 失效**（Canal，异步解耦、兜住所有写路径）；建立"删除失败怎么办"（重试队列/本地事务表/TTL 最终一致）的工程闭环。呼应 mysql s3-1/s3-2：binlog 既是复制载体又是一致性信号源。

## 一、总纲：为什么是"删除"而不是"更新"（★★★★★）

```java
// 例子目的：写路径标准姿势 Cache Aside——更新 DB 后删除缓存
@Transactional
public void updateStock(long skuId, int delta) {
    productMapper.decrement(skuId, delta);      // ① 同事务内更新数据库（正确：DB 是唯一真相源，先落库）
    TransactionSynchronizationManager.registerSynchronization(new Synchronization() {
        public void afterCommit() {             // ② 事务提交"之后"再删（正确：提交前删=事务回滚了缓存却被别人回填旧值）
            try { redis.del("prod:" + skuId); }
            catch (Exception e) { retryQueue.add("prod:" + skuId); }  // ③ 删除失败入重试队列（正确：网络抖动不能让缓存永远留旧值）
        }
    });
}
// 正确使用结果：下一次读 miss → 回源 DB 拿到已提交新值回填，不一致窗口≈一次删缓存的毫秒级
// 错误用法（对比"更新缓存"）：两个并发写 A、B 都改库存，DB 按行锁顺序落 A→B，但缓存写可能乱序成 B→A → 缓存长期是 A 的旧值（删除法则天然免疫乱序：谁后删都留 miss，回源见真相）
```

三个"为什么"一次说清：

- **为什么删不改**：① 并发写乱序会把旧值钉在缓存（如上）；② 懒加载——多数 key 写了也没人读，删比算便宜；③ 缓存里往往是**聚合多表**的视图，单表单值更新无从算起。
- **为什么先 DB 后删**：反过来"先删后更"在删与更之间，一个读请求会把**旧值**回填，直到下次写前不再有人删——窗口是**无限长**的。
- **为什么提交后删**：事务未提交就删，回滚后缓存没了、DB 是旧的，且并发读会回填**旧值**——同样长窗口。

## 二、先 DB 后删，就绝对一致了吗（★★★★★，高频追问）

极小概率仍有窗口：**读路径慢速交错**——

```flow
时序（目的：看懂 Cache Aside 唯一的漏洞长什么样）
读请求 R：查缓存 miss ────────────────────→ 查 DB 得到旧值 v1（慢） ──→ 把 v1 回填缓存
写请求 W：        更新 DB=v2 → 删缓存（此刻缓存本来就没有，删除空跑）
结果：回填发生在删除"之后" → 缓存里留下 v1，直到 TTL 到期 ← 这就是要 TTL 兜底的原因
```

- 概率极低（要求 R 的"读 DB"恰好横跨 W 的"整个写+删"），但**不是零**。
- **延迟双删**：写完后 sleep 一个"读回填最大耗时"再删一次，专治上面这个回填残留——sleep 时长是工程玄学点，**别把它当强一致方案**，它只是把窗口从"到 TTL 为止"压到"第二次删除为止"。
- 终极兜底：**缓存必须有 TTL**——任何一致性事故都有自愈终点。

## 三、订阅 binlog：把一致性从"人肉埋点"变成"管道"（★★★★☆）

```java
// 例子目的：Canal 伪装 MySQL 从库拉 binlog，任何来源的写都触发缓存失效（呼应 mysql s3-1/s3-2）
// 架构：业务只写 DB（不再散落 del 缓存的代码）→ Canal 解析 ROW binlog → MQ → 失效服务按表/主键拼 key 删除
@RocketMQMessageListener(topic = "binlog-product")
public void onRow(RowEvent e) {                 // e = {table:"product", pk:1001, type:"UPDATE"}
    redis.del("prod:" + e.pk());                // 正确：兜住直改 DB、跑批、其他系统写等所有旁路（人肉埋点必漏）
    // 失败进重试 + 指标告警；binlog 位点保证 Canal 重启续传不丢事件（at-least-once：重复删无害，天然幂等）
}
// 正确使用结果：写路径与缓存彻底解耦，业务代码零侵入；一致性收敛延迟 = binlog→MQ→删除的毫秒~秒级
// 错误用法：把"订阅 binlog"当成可以删掉 TTL 的理由 → 链路任一环节积压（MQ 堆积/Canal 卡位点）时旧值无限期存活
```

## 四、方案谱系与选型（★★★★☆）

| 方案 | 窗口 | 侵入性 | 适用 |
| --- | --- | --- | --- |
| Cache Aside + TTL | 常规毫秒；交错时到 TTL | 写路径埋删 | 99% 的业务缓存 |
| + 延迟双删 | 压到第二次删 | 略增延迟 | 回填慢的核心读 |
| 订阅 binlog | 收敛=管道延迟 | 零侵入但加组件 | 写路径多、跨系统、金融对账类 |
| 读写都加锁（强一致） | 0 | 性能坍塌 | 几乎不用；宁可用 DB 行锁读 |

> 面试收口：先说"CAP 式取舍——缓存和 DB 是两个存储，双写无原子性，只能谈收敛"；再给 Cache Aside 三问三答；最后按业务分级（详情页 TTL 兜底就够，余额页上 binlog/直读 DB）。**别背"延迟双删保证一致"**，说得出它的边界反而是加分项。

## 五、动手题

1. 复现"先删后更"的回填残留：写脚本让读请求 sleep 在"查 DB 后、回填前"，并发执行删+更，观察缓存最终留下旧值且不再自愈。
2. 同一场景分别用"先更后删 + 延迟双删"复测，记录缓存回到新值的时刻。
3. docker 起 Canal 监听 product 表变更，直连 DB `UPDATE`（绕过应用），验证缓存被自动失效。

## 六、常见线上问题

| 现象 | 根因 |
| --- | --- |
| 改了价前台还是旧价且一直不恢复 | 先删后更 + 并发读回填旧值；或删缓存失败没重试 |
| 偶发旧价几十秒后自愈 | 慢交错回填残留，TTL 到期自愈——正常，评估 TTL 是否过长 |
| 缓存删除代码散落、总有旁路写忘了删 | 没有统一收口：上 binlog 订阅 |
| 事务回滚了缓存却空了/被回填 | 提交前删缓存——挪到 afterCommit |
| Canal 切换后一段时间不一致飙升 | 位点积压/重放风暴，消费端幂等删除+监控 lag |

## 七、关联技术栈

- **向前**：ROW 格式 binlog、双一是 Canal 数据不丢的前提 ↔ mysql s3-1；主从延迟"读旧"是同一类问题 ↔ mysql s3-2
- **向后**：热 key 被反复失效会放大击穿 ↔ s2-1；失效风暴与大 key 删除阻塞 ↔ s2-3
- **横向**：MQ 最终一致（本地事务表+重试）↔ 消息队列课程；Redisson 分布式锁读写串行化（不推荐当常规方案）↔ redisson 包

## 八、本节小结

一致性总纲：**两个存储的双写没有原子性，一切方案都是在压缩并收敛"不一致窗口"**。标准答案 **Cache Aside**：更新 DB、**提交后删除**缓存、删除进重试、**TTL 兜底**——"删不改"防并发乱序钉旧值，"后删"防回填无限残留；唯一的慢读交错窗口用**延迟双删**压缩（认清它是概率补丁而非保证）、用 TTL 终结。规模化后上**订阅 binlog（Canal）**：零侵入、兜住所有旁路写、at-least-once 幂等删除，管道延迟即收敛上限。按业务分级：详情页 Cache Aside+TTL，资金页直读 DB 或 binlog 级收敛——**一致性和新鲜度都是买出来的，先问业务肯付什么价**。
