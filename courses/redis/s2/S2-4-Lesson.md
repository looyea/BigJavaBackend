# Redis 作为协调服务：锁、限流与计数器

> 本节难度：★★★★☆
> 重要程度：★★★★☆
> 学习产出：能用 Redis 的单线程命令原子性搭出三类常见协调原语——分布式锁、限流器、计数器，并清醒划出它作为"协调组件"的能力边界。核心机制：**SET key val NX PX ttl** 抢占式加锁（NX 保证只在不存在时写、PX 定 TTL 防死锁），解锁必须**按持有者 token 用 Lua 原子"比较再删"**，否则误删他人锁；续期靠**看门狗**在持锁期间周期延长 TTL，避免业务未完成锁先过期。限流用 **INCR + EXPIRE**（固定窗口）或**滑动窗口 ZSET**、**令牌桶 Lua**，靠 Redis 原子递增把多实例计数收敛到一个真值源。计数器/信号量同理用 INCR/DECR 做全局配额。要认清边界：Redis 主从**异步复制**会导致已确认的锁在 failover 后丢失，RedLock 争议在于其时钟假设与 GC 暂停；对**强正确性临界区**应倾向 ZK/etcd 之类 CP 协调服务或数据库唯一约束，Redis 更适合**高并发、允许极小概率失效**的锁与限流场景。识破"解锁不校验持有者""SETNX 无 TTL 死锁""限流只在一台实例生效""拿锁当唯一业务正确性保证"等坑。

## 一、分布式锁：抢占 + 原子释放 + 续期

```text
图目的：一把能用的分布式锁三要素缺一不可
加锁: SET lock <token> NX PX 30000 —— NX 原子抢占, PX 兜底 TTL 防持锁进程崩溃后死锁
解锁: Lua 原子 "if GET==token then DEL" —— 只删自己那把, 防止删掉别人的锁
续期: 看门狗周期性把 TTL 拉长, 业务未跑完锁不会先过期
token: 每次加锁唯一(线程+随机), 用于持有者识别
```

```java
// 目的：解锁必须"比对持有者再删"且原子完成, 否则会误删他人锁
String lua = "if redis.call('get',KEYS[1])==ARGV[1] "
           + "then return redis.call('del',KEYS[1]) else return 0 end";
// 说明：GET 与 DEL 之间若有并发, 别人锁刚好过期又被新线程抢占, 普通 DEL 会删掉新持有者的锁
Long r = redis.eval(lua, 1, "lock:order:1001", myToken);   // 结果：原子比较删除, 只有本人能解锁, 返回 1 成功 0 非本人
// 反例：直接 del("lock:order:1001") 不校验 token ❌ 持锁超时后误删他人锁, 两个线程同时进临界区
```

## 二、限流与计数器：把多实例收敛到一个真值源

```text
图目的：Redis 原子递增天然适合全局限流/配额
固定窗口: INCR key; 首次 EXPIRE 设窗口; 值超阈值即限流 —— 简单但有边界突刺
滑动窗口: ZSET 存每次请求时间戳, 裁剪窗口外成员再 ZCARD 计数 —— 更平滑
令牌桶:   Lua 原子"按时间补币 + 取币", 允许一定突发 —— 接近生产限流语义
计数器/信号量: INCR/DECR 做全局配额、并发数控制
```

## 三、能力边界：RedLock 争议与该退让的场景

```text
图目的：什么时候 Redis 不该当"权威协调器"
异步复制: 主确认锁后崩溃, 从升主无该锁 → 双持有; 这是 AP 架构的固有代价
RedLock: 多节点独立加锁过半成功, 但依赖时钟一致 + 怕 GC/网络暂停, 学界有争议
强正确性临界区: 宁可 ZK/etcd(CP) 或数据库唯一约束/乐观锁, 不把业务正确性压在 Redis 锁上
适配场景: 高并发、允许极小概率失效的锁/限流/防重, 才是 Redis 协调的主场
```

## 四、坑与底线

- **锁只是护城河之一，不是业务正确性的唯一保证**：即便锁失效，被保护的操作也应能用幂等/唯一约束兜底（与幂等专题呼应）。
- **别让限流只在一台生效**：本地计数器限流在多实例下形同虚设，必须走 Redis 全局原子计数。
