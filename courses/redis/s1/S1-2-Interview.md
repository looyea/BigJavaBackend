# 实际面试题 · 持久化与高可用架构

> 收录 2024—2026 国内中大厂 Java 后端真实面试，含追问链。考"RDB/AOF 怎么选、主从哨兵 Cluster 什么关系、线上你们用的哪种"。

## 题 1：RDB 和 AOF 各自优缺点？生产怎么配？

**期望时长**：90 秒

**答题要点**：

- **RDB**：二进制快照，fork+COW 不阻塞主流程（fork 瞬间有耗时）；恢复最快；两次快照之间的写会丢；大实例 fork 有内存风险。
- **AOF**：追加写命令，everysec 最多丢 1s；体积大、恢复要重放（慢）；rewrite 控制体积。
- 生产主流：**混合持久化**（AOF everysec + rdb-preamble）——重写出的 AOF 头是 RDB 体，加载快且丢数据窗口小。

**追问链**：为什么 everysec 宕机只丢 1 秒而进程崩溃不丢？→ 命令先进内核页缓存，进程死了页缓存仍会被 OS 刷盘；整机断电才丢未刷部分。

## 题 2：主从复制断了怎么恢复？为什么会频繁全量？

**答题要点**：

- **psync2**：从带 replid+offset 请求续传；主查 **backlog 环形缓冲**——缺口还在就部分重同步（只发缺失增量），否则全量（BGSAVE+缓冲期间写）。
- 频繁全量根因：backlog 太小、网络长期抖动、主从 failover 后 replid 变化。
- 危害：全量期间主库多扛 BGSAVE+快照传输，从库可能服务能力下降。

**追问链**：backlog 多大？→ 复制带宽 × 可容忍断线时长（如 10MB/s × 10min ≈ 6G 太贵，实际按经验 100~500MB 并监控 `master_repl_offset` 落差）。

## 题 3：Sentinel 和 Cluster 的区别与联系？

**答题要点**：

- **Sentinel**：不分片，数据全量副本；解决**自动故障转移**（监控、quorum 判客观下线、选主、改指向）。
- **Cluster**：16384 slot 分片，解决**容量与写扩展**；内置故障转移（槽所在主的新从升主）。
- 联系：两者都用"多数派"防误判；Cluster 每个分片本身仍是一主 N 从。

**追问链**：你们线上用哪种？→ 数据量 <10G 且要求高可用选 Sentinel；超单机容量或写 QPS 顶到单线程上限才 Cluster（并评估跨槽操作受限的改造成本）。

## 题 4：Cluster 的 MOVED 和 ASK 重定向有什么区别？

**答题要点**：

- **MOVED slot ip:port**：该槽的**归属已变更**，客户端应刷新槽缓存并重发——持久性重定向。
- **ASK ip:port**：槽**迁移进行中**，本次请求去目标节点试（可能还在源节点没搬完）——一次性重定向，不更新缓存。
- 迁移协议：源 SETSLOT MIGRATING + 目标 IMPORTING，按 key `MIGRATE` 原子搬运，找不到就整体转发到目标。

**追问链**：为什么客户端要缓存槽表而不是每次都问？→ 每次问多一跳 RTT；表版本由 `clusterNode` 的 configEpoch 维护，MOVED 触发局部刷新。

## 题 5：缓存集群"重启后数据要不要紧"，从持久化角度说说你们的设计。

**答题要点**：

- 纯缓存定位：可靠前提 = 数据可重建 + 重建有**限速/预热**（启动前脚本灌热 key、回源加互斥与熔断，呼应 s2-1/s2-2）。
- 但 Redis 上往往混放**非常缓存**的东西：分布式锁、限流计数、幂等标记——这些丢了是正确性问题，必须 AOF everysec 起步。
- 落地口径：全节点开混合持久化（成本极低）；主从 + 哨兵；大实例把 BGSAVE 调度到从库做，主库 `save ""` 只负责服务。

**追问链**：主库 save "" 那主挂了最后几秒写谁兜底？→ AOF everysec + 从库持有近似数据；新主升上后数据在其 AOF/RDB 里，恢复窗口 ≤1s。
