# 实际面试题 · 五大类型与底层编码

> 收录 2024—2026 国内中大厂 Java 后端真实面试，含追问链。考"五种类型背后的编码你清楚吗、为什么单线程还这么快"。

## 题 1：Redis 为什么每种类型要有多种底层编码？

**期望时长**：60 秒

**答题要点**：

- 缓存绝大多数是**小规模数据**：连续内存布局（listpack/intset）省内存、CPU 缓存友好；但插入扩容代价 O(n)。
- 大规模数据需要 hashtable/skiplist 的 O(1)/O(log n) 通用性能，代价是指针与内存开销。
- 所以按阈值**自动升级**（只升不降）：小用紧凑、大用通用——空间时间双重折中。

**追问链**：为什么取消降级？→ 降级判断本身要扫描、行为不可预期；且"升了又降再升"会造成抖动，宁可只升不降。

## 题 2：讲一下 ziplist 的连锁更新，listpack 怎么解决的？

**答题要点**：

- ziplist 每个 entry 记录**前一 entry 的长度**（prevlen），前一项长度跨过 254 边界时，后一项的 prevlen 从 1 字节变 5 字节 → 后一项空间不足要 realloc → 又级联触发下一项，最坏 O(n²)。
- listpack 每项只存**自身长度**（且 header 最多 1 字节 backlen 记录自己起始位置），任何一项增删只影响自己，连锁更新从结构上消失。

**追问链**：为什么还要限制单值 64B 以下才用 listpack？→ listpack 内定位仍是线性扫描，元素又大又多时 O(n) 遍历+整块内存拷贝成本失控，不如 hashtable。

## 题 3：Redis 的 rehash 和 JDK HashMap 的 resize 有什么区别？

**答题要点**：

- JDK：单表 Node[]，扩容在**put 时一次性**把全部桶迁移完——单次 O(n) 停顿。
- Redis dict：**双表 ht[0]/ht[1]** + `rehashidx`，每次访问 dict 顺手搬一个桶，渐进完成；期间查询找两表、写入只写新表。
- 动机差异：Redis 主线程单线程，一次 O(n) 停顿=全站卡住，必须切碎。

**追问链**：CHM 呢？→ 容量由 CAS size 控制、**永不缩容不 rehash**（树化/合并代替迁移），协助式迁移只发生在扩容初始化桶数组时。

## 题 4：线上一个问题：Hash 存对象突然内存翻倍，可能原因？

**答题要点**：

- 大概率触发 **listpack→hashtable 升级**：域数超 512 或某次写入的 value 超 64B（哪怕就一个大字段）。
- 升级后每个 value 独立 SDS+dictEntry（每个域多约 20+B 开销），且不可逆。
- 治理：大字段拆出去单独 key；或调 `hash-max-listpack-value`；容量评估用 `MEMORY USAGE` 而非 elements 数。

**追问链**：怎么在线确认某 key 编码？→ `OBJECT ENCODING key`；批量扫用 `--bigkeys`/`MEMORY USAGE` 抽样（SCAN 游标防阻塞，呼应 s2-3）。

## 题 5：为什么 Redis 用跳表实现 zset，不用红黑树/B+ 树？

**答题要点**：

- 排行榜核心操作是**范围查询**：跳表找到起点后顺底层链表走，红黑树要中序回溯、实现繁琐。
- 平均 O(log n) 与红黑树同级；实现简单、易调试、易做持久化遍历。
- zset 还并置一个 dict：成员→分数 O(1)（ZSCORE），跳表专管排序范围——两结构互补。

**追问链**：跳表复杂度怎么来的？→ 多层稀疏索引类似二分，期望比较次数 O(log n)，空间多 O(n) 个指针；与 data-algorithms 的跳表实现题联动。
