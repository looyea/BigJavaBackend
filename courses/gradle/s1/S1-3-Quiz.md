# 增量构建、构建缓存与 Daemon 提速 · 小测

### 1. up-to-date 判定的依据是？（6分）

- A. 文件修改时间对比源码目录
- B. 任务声明的输入/输出指纹与上次执行记录比对
- C. git diff 是否为空
- D. 每次都全量执行，只是显示跳过

> 答案：B
> 解析：Gradle 为每个任务记录输入快照与输出哈希，两者一致才跳过——所以"隐形输入"必须显式声明进指纹。

### 2. 构建缓存（build cache）与 up-to-date 的关系是？（6分）

- A. 二者是一回事
- B. 先判 up-to-date（本机输出在），未命中再查缓存拉历史/远程产物
- C. 先查缓存再看 up-to-date
- D. 开启缓存后 up-to-date 失效

> 答案：B
> 解析：up-to-date 是"本机没 clean 的跳过"；缓存让 clean 后、换机器后也能搬回产物（结果：clean build 不再等于全量重算）。

### 3. 远程缓存的推荐推送策略是？（6分）

- A. 本地和 CI 都 push
- B. 只有 CI push，本地只拉
- C. 只有本地 push
- D. 都只拉，人工导入

> 答案：B
> 解析：个人机器 JDK/环境不一，push 会污染缓存导致命中率抖动与产物错乱（错误用例：本机 ARM 编译产物推给 x86 集群拉取）。

### 4. 配置缓存解决的是哪段开销？（6分）

- A. 依赖下载
- B. 任务执行
- C. 每次构建重复评估所有脚本生成任务图
- D. JVM 进程启动

> 答案：C
> 解析：配置缓存把任务图快照化，二次构建跳过脚本评估；A 由依赖缓存管，D 由 Daemon 管。

### 5. Daemon 复用的条件是？（6分）

- A. 任意 gradle 命令都复用同一进程
- B. 同 Gradle 版本 + 兼容的 JVM 参数/JAVA_HOME 才复用
- C. 每次 new 进程但共享磁盘缓存
- D. 只在 Windows 生效

> 答案：B
> 解析：JVM 参数或 Gradle wrapper 版本变化都会新起 Daemon（异常现象：CI 脚本频繁改 org.gradle.jvmargs → 反复冷启动反而更慢）。

### 6. 任务读了系统属性但没声明为 inputs，后果是？（6分）

- A. 构建直接报错
- B. 属性变化后仍显示 UP-TO-DATE，使用过期产物
- C. 自动重新执行
- D. 仅警告无实际影响

> 答案：B
> 解析：指纹缺该项 → 判定输入未变 → 静默跳过（结果：产出与输入不一致，是增量体系最危险的错误用法）。

### 7. `gradle build --info` 在提速排查中的用途是？（6分）

- A. 提高构建速度
- B. 查看每个任务未跳过/未命中的具体原因
- C. 生成 HTML 报告
- D. 清理缓存

> 答案：B
> 解析："Task is not up-to-date because ..." 是定位增量失效的第一手输出；更直观可用 --scan 的 Build Operations 页。

### 8. 哪些做法有利于配置缓存兼容？（多选）（9分）

- A. 任务动作里通过 providers 延迟读取属性，不直接引用 Project
- B. 用 tasks.register 惰性注册代替 create
- C. 在配置期读取 System.getenv 决定任务结构
- D. 把构建逻辑封装为使用类型化 Property 的约定插件

> 答案：ABD
> 解析：A/D 避免执行期持有 Project 引用；B 是惰性模型基础；C 让配置结果依赖外部状态，正是配置缓存明确反对的模式（错误用例）。

### 9. 关于并行与 JVM 参数，正确的有（多选）（9分）

- A. org.gradle.parallel=true 是工程级并行，多模块收益明显
- B. 构建 JVM 默认堆过小会导致频繁 GC，反而拖慢编译
- C. 并行度越高一定越快，无内存代价
- D. 容器内 CI 跑 Daemon 常驻进程收益有限甚至为负

> 答案：ABD
> 解析：A/B 是常见调优两板斧；并行受内存与任务图宽度制约，过高会 OOM 或颠簸（C 错误）；一次性容器里 Daemon 生命周期与容器同始同终，预热收益拿不满（D）。

### 10. 简答题：组里抱怨"Gradle 明明开了缓存还是慢"，请给出系统性诊断路径。（40分）

- 要点1：先分段计时——用 --profile 拆出配置期/执行期/依赖解析三段占比，目的：确认慢在哪一层再开药。
- 要点2：配置期慢 → 检查配置缓存是否真正开启且无 problems 回退（输出：构建日志尾部 "configuration cache problems" 或 state is not stored 字样）；脚本里急切 fileTree 求值、重型 buildSrc 也是嫌疑。
- 要点3：执行期慢 → 看任务为何不 UP-TO-DATE/缓存不命中：隐形输入未声明、输出路径含时间戳/绝对路径导致哈希永远变（错误用例：把 build time 写进产物）。
- 要点4：缓存层 → 远程缓存是否配置、CI 是否 push、本地与 CI 的 JDK/插件版本是否一致（结果：版本漂移使键对不上，命中率个位数）。
- 要点5：依赖解析慢 → 动态版本 + changing modules 缓存时长过短，用 --write-locks 或延长 cacheChangingModulesFor（示例：每次构建多花 40s 查 SNAPSHOT）。
- 要点6：治理动作：把"配置缓存开启、远程缓存 push=CI、关键任务输入声明 review"写进工程模板，验收标准是 clean 后二次构建缓存命中率 ≥80% 且 CI 时长有基线曲线。

> 答案：见要点
