# 增量构建、构建缓存与 Daemon 提速 · 面试题

## 题 1：Gradle 到底为什么比 Maven 快？（不许只答"增量"两个字）

- 分层答：Daemon 省 JVM/类加载预热；配置缓存省重复脚本评估；up-to-date 省重复任务执行；构建缓存让 clean/换机器也省——四层各治构建时序的一段（示例数据：40 模块仓配置期 25s、clean 构建 3min，开满四层后二次 20s）。
- 收尾金句：快的不是编译器，是"指纹判定 + 产物复用"引擎；Java 编译本身两边都是 javac/ecj。
- 加分：说出代价——指纹声明不全时会静默复用过期产物，正确性责任从"每次全算"转移到"输入声明完整"。

## 题 2：一个任务为什么不 UP-TO-DATE？给出完整原因清单与排查命令。

1. 输出被外部改动（有人手删 build 目录）；2. 输入指纹变化（含隐形输入：环境变量、系统属性没声明但实际影响产物时反过来不变化）；3. 插件/Gradle 版本升级使实现哈希变；4. 声明本身有问题——outputs.dir 覆盖了整个 build/、输入用了绝对路径（异常表现：换机器永远不命中）。
- 排查：`--info`/`--scan` 直接读 "not up-to-date because ..."，不要靠猜（结果：官方原因字符串是唯一可信证据）。

## 题 3：本地缓存和远程缓存分别存什么？key 怎么算的？

```text
图目的：一条缓存记录 = 任务输入指纹 -> 输出产物快照。
key：任务实现的类与配置指纹 + 各 @Input/@InputFile 排序哈希（目的：同类任务在任意机器 key 一致才能共享）；
value：输出文件 tar + 相关元数据；远程节点（HTTP/云存储）与本机目录结构不同但条目同构。
错误预期：以为远程缓存缓存的是"依赖 jar" —— 依赖下载缓存在 ~/.gradle/caches/modules，两码事。
```

## 题 4：CI 上用不用 Daemon？

- 一次性容器：Daemon 收益只剩同容器内多命令复用；`./gradlew` 每条 step 起新容器时无意义还占内存（结果：GitLab 单脚本多命令场景可留，多 step 短命令场景 `--no-daemon` 或 `--daemon` 配容器复用卷再权衡）。
- 常驻自托管 Runner/开发机：Daemon 必开，配合 `org.gradle.jvmargs` 固定避免反复新起（说明：JVM 参数漂移是"Daemon 越开越多"的常见根因，`gradle --status` 查看）。

## 题 5：配置缓存的原理与兼容性问题如何产生？

- 原理：配置期结束时把任务图（含任务字段值）序列化快照；下次输入未变直接反序列化执行，跳过全部脚本评估。
- 兼容性根因：快照要求所有状态可序列化且不含活对象——任务字段引用 Project、配置期读 getenv/文件时间等外部状态，都无法安全固化（错误用例输出："Configuration cache problems found in this build" 报告页逐条列调用栈）。
- 落地路径：先本地开、按报告修脚本、升级不兼容插件，CI 最后开——顺序反了会把 CI 变成排障现场（验收：problems=0 且 BUILD 结果与关闭时一致）。

## 题 6：怎么向老板证明"值得花时间治理构建缓存"？

- 指标三件套：CI p50/p95 构建时长曲线、缓存命中率（HTTP 节点 access log 或推送/拉取计数）、开发者日均构建次数 × 节省秒数。
- 换算口径：等待成本=人力单价×日均浪费分钟×人数×工作日（示例：30 人×4min×250 天≈500 人时/年）。
- 风险条款也要写：治理期一次性成本（修任务声明、插件升级），给区间不给承诺——这是资深答法。
