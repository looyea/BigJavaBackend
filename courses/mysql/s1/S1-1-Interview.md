# 实际面试题 · MySQL 体系结构与 SQL 旅程

## 题 1：一条 update 语句在 MySQL 里做了什么？

**标准答法（架构师版本，先讲链路再讲保障）**：

连接器收请求 → 分析器 → 优化器 → 执行器 → InnoDB 读页到缓冲池 → 改内存页 → 写 redo（prepare）→ 写 binlog → redo commit → 后台择机刷脏页。

**追问链**：

1. 为什么不直接刷盘？→ WAL：把随机写变成顺序写，且页是 16KB 而修改可能只有几十字节。
2. 那查询为什么需要 buffer pool？→ 引出命中率、`innodb_buffer_pool_size` 配置（物理内存 50%~70%）。
3. 一条 SQL 从客户端到 MySQL，JDBC 侧还有哪一层？→ 连接池 + 驱动协议（准备语句、批量重写 `rewriteBatchedStatements`）。

## 题 2：redo log 和 binlog 为什么要两套？只用一套不行吗？

**答题要点**：用途与写入方式不同（物理/循环写 vs 逻辑/追加写），历史原因（InnoDB 是插件引擎，binlog 属 Server 层）。只用 redo：无法做长期归档与异构订阅；只用 binlog：崩溃恢复需重放语句，无法保证已分配行号等内部状态一致，且恢复慢。

**追问**：Canal 订阅 binlog 依赖什么参数？→ `binlog_format=ROW`、`server-id`、`binlog_row_image`，以及从库 `log_slave_updates` 的链式订阅问题。

## 题 3：主库挂了切从库，发现少了几条数据，可能原因有哪些？

**考察系统性排查思维**，期望按层展开：

1. 参数层：未开双一，崩溃时 redo 已提交而 binlog 未落盘。
2. 复制层：异步复制默认不保证从库收到；半同步 `rpl_semi_sync_master_wait_point` 的 AFTER_SYNC 与 AFTER_COMMIT 差异。
3. 切换层：切换工具在 master crash 时无法取到 binlog 位点尾部（GTID 可缓解）。
4. 应用层：写走主、读走从的窗口期，业务把"读不到"误判为"丢数据"（本质是延迟）。
5. 归档层：从库开了 `read_only` 但被 DBA 临时关闭写入过。

**加分**：给出金融场景的完整方案——半同步 + GTID + 双一 + 机房级异步 + 对账兜底。

## 题 4：为什么用自增主键而不是 UUID？分库分表后怎么办？

**答题要点**：B+ 树单调追加避免页分裂与碎片，二级索引体积小；UUID 随机导致频繁插入中间位置。分库分表后用分布式 ID（雪花 / 号段 / Leaf），并要求 ID 趋势递增以兼容 MySQL 写入特性 → 自然衔接到"分布式 ID"专题。

**追问**：雪花时钟回拨怎么处理？→ 等待、备用位、WorkerId 注册中心约束机器时钟（NTP + 监控）。

## 题 5：`select *` 为什么被禁止？

**答题要点（别只说"浪费"）**：

1. 破坏覆盖索引（本来 index only scan，现在必须回表）。
2. 网络与序列化放大，应用侧内存压力。
3. ORM 映射成本与字段变更时的隐性耦合。
4. 无法利用索引顺序提前终止（`LIMIT` 场景仍需读全列）。

## 场景题：某接口偶发 2 秒，DB 慢日志里有对应 SQL（考察定位思路）

**期望路径**：

1. 确认是 SQL 本身慢还是排队/连接慢（连接池等待、`Threads_running` 飙升）。
2. `EXPLAIN ANALYZE` 看实际行数与预估是否偏离（统计信息过期会让优化器选错索引）。
3. 检查是否有锁等待（`data_locks` / `innodb_status`）、是否有大事务、是否有隐式转换或函数导致索引失效。
4. 检查是否偶发于刷脏页/DDL/备份窗口，与 IO 抢占相关。
5. 结论要落到"证据 + 可验证的假设 + 灰度验证"，而不是"加索引试试"。
