# 小测验 · 锁机制与死锁排查

> 本卷共 6 题，混合单选 / 多选 / 判断 / 填空 / 简答，满分 100 分折算百分制，≥ 60 分过关。

### 1. InnoDB 行锁本质加在什么上，导致"WHERE 不走索引会锁全表"？（15分）

- A. 加在数据页上
- B. 加在索引记录上；无索引可用时只能沿聚簇索引给所有记录加锁
- C. 加在表头上
- D. 加在事务 ID 上

> 答案：B
> 解析：行锁锁的是索引记录。WHERE 用不到索引，引擎无法定位要锁哪几条记录，只能对所有记录加 Next-Key 锁，效果近似锁全表，并发写被串行化。

### 2. 间隙锁（Gap Lock）的作用是？（15分）

- A. 锁住单条记录防止被 UPDATE
- B. 锁住索引记录之间的间隙，只阻止他人 INSERT，用于防幻读
- C. 锁住整张表
- D. 加速插入

> 答案：B
> 解析：Gap Lock 锁的是两个记录间的开区间，本身不锁记录、只拦向该间隙的 INSERT，是 RR 当前读防幻读的关键；Next-Key = 间隙 + 端点记录。

### 3. 【多选】关于 MDL 元数据锁与在线 DDL，正确的有哪些？（20分）

- A. 事务访问表时加 MDL 读锁，DDL 需 MDL 写锁，二者互斥
- B. 一个未提交的长事务持 MDL 读锁，会让后续 ALTER 排队，并连锁阻塞排在 ALTER 之后的所有新查询
- C. 业务高峰期可直接对大表执行 ALTER，不会影响线上
- D. 大表结构变更宜用 Online DDL 或 gh-ost / pt-osc 影子表方式降低阻塞

> 答案：ABD
> 解析：C 错——高峰期直接 ALTER 大表会因 MDL 写锁请求引发后续读写全线排队，典型整库卡死雪崩。A/B 描述 MDL 机制与事故链，D 是正确规避手段。

### 4. 判断：发生死锁被 InnoDB 回滚后，应用只需重跑失败的那条 UPDATE 语句即可。（10分）

- A. 正确
- B. 错误

> 答案：B
> 解析：死锁会让**整个事务**回滚，只重跑最后一条 SQL 会因前面改动已丢失而状态错乱。正确做法是捕获 `ERROR 1213` 后**从头重试整个事务**（幂等前提下）。

### 5. 填空题：行锁三种算法是 Record Lock、______ Lock、______ Lock；排查死锁看 `SHOW ENGINE INNODB STATUS` 的 ______ 段。（20分）

> 答案：Gap / Next-Key / LATEST DETECTED DEADLOCK

### 6. 列举死锁预防三板斧，并解释"唯一索引等值命中"与"非唯一索引等值命中"加锁范围的区别。（20分）

> 参考答案：
> - 三板斧：① 固定加锁顺序（按主键升序等统一规则访问多行/多表，破坏循环等待）② 缩短事务、把 RPC/发消息移出事务减少持锁时间 ③ 让 WHERE 走索引、合理索引缩小锁范围
> - 死锁被回滚后应用要整事务重试（而非只重跑最后一条 SQL）
> - 唯一索引等值命中：Next-Key 优化为仅 Record Lock（锁一行）
> - 非唯一索引等值命中：锁命中记录的 Next-Key + 右边 Gap（因相同索引值可能多行），故会阻塞相邻间隙插入
