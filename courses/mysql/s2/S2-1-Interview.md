# 实际面试题 · 事务隔离与 MVCC

> 收录 2024—2026 国内中大厂 Java 后端真实面试，含追问链。MVCC 是数据库面试深水区，答要能画出版本链 + ReadView 判断规则。

## 题 1：讲讲 InnoDB 的 MVCC 是怎么工作的？

**期望时长**：2 分钟

**答题要点**：

- 每行隐藏列 `DB_TRX_ID`（最近修改的事务版本）+ `DB_ROLL_PTR`（指向 undo 里的上一版本），多次改串成**版本链**。
- 快照读时生成 **ReadView**（m_ids、min_trx_id、max_trx_id、create_trx_id），沿版本链从新到旧找**第一个可见版本**。
- 于是普通 SELECT **不加锁**也能读到一致性快照。

**追问链**：undo log 的两个作用？→ 回滚 + MVCC 多版本；对比 redo log 只管崩溃恢复（持久性）。

## 题 2：ReadView 怎么判断一个版本可见？

**答题要点**：对版本的 `trx_id`：

1. 等于 `create_trx_id`（自己改的）→ 可见。
2. `< min_trx_id`（建快照前已提交）→ 可见。
3. `>= max_trx_id`（建快照后才开的事务）→ 不可见。
4. 介于中间：在 `m_ids`（当时未提交）→ 不可见；不在 → 已提交 → 可见。

**追问链**：都不可见怎么办？→ 沿链继续往旧找；找不到就当该行不存在。

## 题 3：RC 和 RR 在 MVCC 上的区别？

**答题要点**：

- 快照读机制一样，差别只在 **ReadView 生成时机**。
- RC：**每条 SELECT 重建** ReadView → 看得到别事务新提交 → 不可重复读。
- RR：**仅事务首次快照读生成一次**、之后复用 → 整个事务看到同一时刻世界 → 可重复读。

**追问链**：为什么很多互联网公司把 MySQL 改成 RC？→ RC 锁冲突更少、并发更高（无间隙锁），配合 binlog ROW 格式可接受；但要说清 RR→RC 会放开可重复读与幻读。

## 题 4：MySQL 的 RR 真的解决了幻读吗？

**答题要点**：

- **快照读**靠 MVCC 防幻读；**当前读**（`FOR UPDATE`/`UPDATE`/`DELETE`）靠 **next-key lock（记录锁+间隙锁）** 锁范围防 INSERT。
- 但**快照读与当前读混用**会破功（A 快照读→B 插入提交→A 当前读命中→A 再快照读就见到幻影）。所以是"很大程度上"而非 100%。

**追问链**：要绝对防幻读怎么办？→ 全程当前读 `SELECT ... FOR UPDATE`，或升到串行化（并发差）。

## 题 5：并发扣库存超卖，跟隔离级别有关吗？怎么解？

**答题要点**：

- 超卖的根是 **"先查后改"更新丢失**，RR/MVCC 也救不了——两个事务各自快照读旧值、算完写回。
- 解法：① 单条原子 `UPDATE ... SET stock=stock-1 WHERE id=? AND stock>=1`（判断下推 + 行锁）；② `SELECT ... FOR UPDATE` 当前读加锁串行；③ 乐观锁 version 字段 CAS 重试；④ 高并发下前置 Redis 预扣（呼应 redis 包）。

**追问链**：`WHERE stock>=1` 为什么能防负库存？→ 该 UPDATE 是当前读、对命中行加行锁，条件在锁内原子判断，返回受影响行数 0 即表示扣减失败。
