# 实际面试题 · 锁机制与死锁排查

> 收录 2024—2026 国内中大厂 Java 后端真实面试，含追问链。锁与死锁是"有没有真排过线上故障"的照妖镜，要能画锁范围、读死锁日志。

## 题 1：InnoDB 的行锁是怎么加的？

**期望时长**：90 秒

**答题要点**：

- 行锁**加在索引记录上**，不是加在数据行上。
- 三种算法：**Record（锁单条记录）、Gap（锁间隙，只拦 INSERT）、Next-Key（间隙+端点，左开右闭，RR 当前读默认）**。
- 快照读不加锁（靠 MVCC），当前读（UPDATE/DELETE/FOR UPDATE/FOR SHARE）才加锁。

**追问链**：为什么 WHERE 不走索引会锁全表？→ 定位不到该锁哪几条索引记录，只能沿聚簇索引给所有记录加 Next-Key 锁，近似锁全表。

## 题 2：间隙锁和 Next-Key 锁的区别？

**答题要点**：

- Gap：开区间、**不锁端点记录**，只阻止向间隙 INSERT，不阻止别人按间隙读。
- Next-Key = Gap + 端点记录锁（左开右闭），既防插入幻影行、又锁住已有记录。

**追问链**：唯一索引等值命中加什么锁？→ Next-Key 优化为 **仅 Record Lock**；非唯一索引等值命中则加该记录 Next-Key + 右边 Gap。

## 题 3：线上偶发 `Deadlock found`，怎么处理？

**答题要点**：

- `SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK`，读两个事务的"持锁 / 等锁 / SQL"定位交叉加锁路径。
- **捕获 1213 后整事务重试**（死锁回滚的是整个事务，不能只重跑最后一条 SQL）。
- 预防三板斧：**固定加锁顺序、缩短事务、走索引缩小锁范围**。

**追问链**：热点行更新死锁检测开销大怎么办？→ 评估 `innodb_deadlock_detect`、改用锁等待超时，或从架构上减少争抢（Redis 预扣、MQ 串行化、拆分行热点）。

## 题 4：一条 `ALTER` 把整库卡住了，为什么？

**答题要点**：

- **MDL 元数据锁**：访问表加读锁、DDL 加写锁，互斥。
- 长事务持读锁 → ALTER 写锁排队 → 排在 ALTER 之后的**所有新查询（要读锁）**也被这个未完成 DDL 挡住 → 连接池打满、整库雪崩。

**追问链**：怎么安全变更大表？→ DDL 前查 `innodb_trx` 杀长事务；用 8.0 Online DDL（INSTANT/INPLACE）或 **gh-ost / pt-osc** 影子表 + 灰度切流，避开长期持写锁。

## 题 5：什么是意向锁？

**答题要点**：

- 事务给某行加 S/X 行锁前，先在**表级**加对应的意向锁 IS/IX。
- 作用：当有人要加**表锁**时，只需看表上有无 IX/IS 就能 O(1) 判断"表里有没有行锁"，不必逐行扫描。

**追问链**：意向锁之间互斥吗？→ 意向锁之间基本都兼容（IS/IX 相容），它们只与"真正的表级 S/X 锁"冲突。
