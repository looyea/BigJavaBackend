# 实际面试题 · 慢查询治理与 SQL 优化实战

> 收录 2024—2026 国内中大厂 Java 后端真实面试，含追问链。考"线上慢 SQL 你怎么体系化处理、深分页怎么优化、大批量写怎么不停机"。

## 题 1：线上突然报慢 SQL 告警，你的处理流程？

**期望时长**：90 秒

**答题要点**：

- 取证：慢日志 / performance_schema 拿到 SQL 原文与耗时、扫描行数；看是否伴随流量高峰或发布。
- 归因：`EXPLAIN` 看 type/key/rows/filtered/Extra——是全表扫、失效写法、计划突变还是量级自然增长；统计失真先 `ANALYZE TABLE`。
- 处置：能改写先改写（区间、类型对齐、UNION），该加索引评估后在线加（gh-ost/pt-osc，呼应 s2-2）；短期兜底限流/降级入口。
- 收尾：回归验证 + 复盘入库，同类 SQL 纳入上线前 explain 审核。

**追问链**：为什么按"总耗时"而不是"单次最慢"排 TOP？→ 一条 200ms、每秒千次的 SQL 比一天一次的 10s SQL 对系统伤害更大。

## 题 2：`LIMIT 1000000, 10` 为什么慢？怎么优化？

**答题要点**：

- 慢因：引擎必须真正取到第 1000010 行再丢掉前一百万行，二级索引还要逐行回表，代价随 offset 线性涨。
- **延迟关联**：子查询在覆盖索引里 `LIMIT 1000000,10` 只出主键（Using index 不回表），外层 join 只回表 10 行。
- **书签续页**：`WHERE id > 上页末id ORDER BY id LIMIT 10`，每页恒定成本；配合产品"上一页/下一页"或无限下拉。
- 入口约束：限制最大可跳页数（搜索引擎只给前 100 页的同款思路）。

**追问链**：分库分表后深分页怎么办？→ 跨片 offset 更致命，典型做法是广播改写 + 全局归并只取 needed 行，或迁移 ES/搜索引擎承担翻页。

## 题 3：哪些写法会导致索引失效？给出治理手段。

**答题要点**：

- 列上运算/函数包裹（`DATE(create_time)=…`）→ 改区间比较。
- 隐式类型转换（VARCHAR 列传数字）→ 参数类型对齐（MyBatis 里 String 勿传 Long）。
- 联合索引缺最左列、中间列用范围断了后续列 → 调整条件或索引列序（等值在前范围在后）。
- 前导 `%` LIKE → 全文索引 / ES。
- `OR` 两侧不同索引退化全表 → 拆 UNION。
- 低区分度列单独建索引 → 优化器不走，别白建。

**追问链**：怎么证明失效了？→ EXPLAIN `type=ALL`、key=NULL，改后对比 rows 量级。

## 题 4：一条 SQL 要删 5000 万行，怎么不停机不拖垮从库？

**答题要点**：

- 禁止一把梭：巨事务 → undo 膨胀、锁持有过久、binlog 巨型事件、从库延迟暴涨、回滚比执行还久。
- **分批删**：`DELETE ... WHERE ... ORDER BY id LIMIT 1000` 循环 + 批间 sleep，按条件幂等可断点续跑；低峰执行，盯 `Seconds_Behind_Source`。
- 另一种形态：**反向保留**——建新表把要留的 <10% 数据灌进去，`RENAME TABLE` 原子互换，秒级完成。

**追问链**：为什么 LIMIT 删除要带 ORDER BY id？→ 保证删除顺序确定、进度可观测（按 id 记录断点），也避免无序扫描。

## 题 5：`Using filesort` 和 `Using temporary` 分别意味着什么？怎么消掉？

**答题要点**：

- filesort：结果集需要额外排序（索引没提供所需顺序），先在 sort_buffer 内存排、超限落盘；消法是让联合索引顺序匹配"等值 WHERE + ORDER BY"，混合方向用 8.0 降序索引。
- Using temporary：GROUP BY/ORDER BY 组合无法同走一个索引，需建临时表（可能在内存也可能落盘）；大结果集消不掉就**预聚合**成汇总表。
- 二者同时出现 + rows 巨大 = 慢 SQL 重灾区，优先考虑"索引给序 + 减少参与排序的行数（先过滤再排）"。

**追问链**：调大 `sort_buffer_size` 行不行？→ 治标且按连接分配、过大伤内存；先改 SQL 与索引，最后才调参数（呼应"单变量迭代"调优纪律）。
