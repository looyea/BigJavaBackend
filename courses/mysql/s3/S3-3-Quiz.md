# 小测验 · 慢查询治理与 SQL 优化实战

> 本卷共 6 题，混合单选 / 多选 / 判断 / 填空 / 简答，满分 100 分折算百分制，≥ 60 分过关。

### 1. `LIMIT 500000, 20` 慢的根本原因是？（15分）

- A. LIMIT 语法本身开销大
- B. InnoDB 必须扫描并取出前 500020 行（常含回表）后丢弃前 50 万行，代价随 offset 线性增长
- C. 优化器不支持大 offset
- D. 网络传输数据量大

> 答案：B
> 解析：深分页的代价在"扫描后丢弃"——offset 行被白白读出（二级索引还要回表）。延迟关联让子查询在覆盖索引里翻 offset、只回表最终 20 行；书签续页用 `id > last` 把每页成本恒定。

### 2. 昨天还走索引的 SQL 今天突然全表扫，首选处理是？（15分）

- A. 立刻重建整张表
- B. `ANALYZE TABLE` 刷新统计信息，确认优化器是否因统计失真选错索引，必要时 `FORCE INDEX`
- C. 给所有列加索引
- D. 调大 `sort_buffer_size`

> 答案：B
> 解析：执行计划依赖统计信息估算行数，数据大量变更后统计失真会导致"计划突变"。先 `ANALYZE TABLE` 重采样验证，再决定是否改写或提示索引；重建表与全列加索引都是过度动作。

### 3. 【多选】下列 SQL 写法与治理的对应关系，正确的有哪些？（20分）

- A. `WHERE DATE(create_time)='2026-09-27'` → 改写成 `>= 当天 AND < 次日` 的区间，恢复 range 扫描
- B. VARCHAR 列 `order_no = 1234567890`（传数字）→ 隐式转换使索引失效，应对齐类型为字符串
- C. `user_id=… OR channel_id=…` 退化全表 → 拆成 UNION 让两侧各走索引
- D. `status` 只有 3 个取值，单独给它建索引就能解决慢查询

> 答案：ABC
> 解析：A/B/C 是三类高频失效与标准改写。D 错——低区分度列单独建索引，优化器宁可全表扫，还可能拖累写入；应放进联合索引或改用其他过滤列。

### 4. 判断：`Extra: Using filesort` 表示排序一定发生在磁盘临时文件上。（10分）

- A. 正确
- B. 错误

> 答案：B
> 解析：filesort 先在 `sort_buffer_size` 内存中排序，只有超限时才借助临时文件。消除它的正解是让联合索引顺序与"等值 WHERE + ORDER BY"对齐（天然有序），或 8.0 降序索引解决混合方向。

### 5. 填空题：删除 5000 万行历史数据的正确姿势是加 `ORDER BY id LIMIT 1000` ______ 提交（防巨事务锁表与从库延迟）；批量导入要求 ______（重跑不报 1062 不翻倍，如 `ON DUPLICATE KEY UPDATE`）；超大批量可用建空表灌数后 `RENAME TABLE` 的 ______ 套路秒级切换。（20分）

> 答案：分批 / 幂等 / 影子表（互换）

### 6. 给出慢查询治理的完整闭环流程，并说明为什么"看到 rows 大就加索引"是错误动作。（20分）

> 参考答案：
> - 闭环：开启慢日志（long_query_time 0.5~1s）→ pt-query-digest 按总耗时聚类排 TOP → 逐条 EXPLAIN 归因（type/key/rows/filtered/Extra）→ 改写 SQL 或调整索引 → 回归验证；并把"新 SQL 上线前 explain 审核 + 慢日志周报巡检"固化为机制
> - 错误原因：rows 大可能是失效写法（函数包裹、隐式转换）或低区分度列——前者应改写而非加索引；低区分度列加了优化器也不走，白白拖累写入
> - 正确次序：先归因（统计失真先 ANALYZE），再治理写法，最后才评估索引结构
