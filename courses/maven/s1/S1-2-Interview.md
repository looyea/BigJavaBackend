# 继承、聚合与多模块、BOM · 面试题

## 题 1：parent 继承和 BOM import 都能管版本，什么时候用哪个？

parent 还承担工程结构（modules、属性、插件配置）且 Java/Maven 只允许一个 parent；BOM 只带版本表但可以多份并存。团队实践：**仓内**用 parent（顺带统一插件与属性），**跨仓**用公司 BOM import；两者并按时公司 BOM 放 import 列表第一位（先 import 者优先），关键组件再显式覆盖。

## 题 2：多模块工程怎么避免"公共库改了，服务构建用的还是仓库旧版"？

同一 reactor 内 Maven 优先解析模块间依赖（源码构建产物），前提是**版本书写一致**——用 `${revision}`/`${project.version}` 保证 reactor 内匹配。跨仓消费才走仓库版本。反例：服务硬编码 common:1.0.0 而 reactor 里 common 是 1.1.0 → reactor 匹配失败 → 拉了仓库旧 jar，"改了没生效"的经典成因。

## 题 3：CI 上如何缩短 20 模块的构建时间？

三板斧：① `-T 1C` 并行（反应堆按拓扑分层，同层并行安全）；② 变更检测 + `-pl 变更模块列表 -am -amd` 只跑受影响链（说明：-amd 连下游消费者一起测）；③ 依赖缓存（~/.m2 持久卷或 -Dmaven.repo.local 固定）+ 构建平台缓存。进阶：拆分流水线（公共库 SNAPSHOT 快发、服务并行构建），注意并行 deploy 同版本会互踩（结果：发布串行化）。

## 题 4：dependencyManagement 会被子模块"再传递"吗？

不会。版本表沿 parent 链**向下继承**，但不随依赖**向外传递**——A 依赖 B，B 的 dependencyManagement 对 A 无效（区别于直接依赖的版本约束由调解规则处理）。这是"为什么库作者要发布 BOM 给消费者 import"的根因：管理范围不能搭传递的便车。

## 题 5：什么信号说明你的多模块结构坏了？

① 出现循环依赖（Maven 报错逼你看见，但有人用"合并模块"逃避——错，该重划边界）；② common 里开始有业务代码（下层依赖上层诉求的伪装）；③ 改一行要全仓 20 个模块重发（版本没有真正分层）；④ web 直接 import infra 的类（跨层依赖，模块存在但约束形同虚设）。结论：模块边界就是架构边界，构建报错常常是设计反馈。
