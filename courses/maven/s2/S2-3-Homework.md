# Maven vs Gradle 选型与迁移（关联） · 作业

## 作业 1：同项目双构建对照

**目标**：在一个 Maven 项目旁挂出等价的 Gradle 构建，体验模型差异。

1. 选一个两模块 Maven 项目（父 POM + 一库一服务），用 `gradle init` 生成骨架，把依赖与模块关系翻译为 settings.gradle + build.gradle（输出：两份依赖清单逐条对照表）。
2. 分别记录 `mvn -T 1C package` 与 `gradle build --parallel` 冷构建耗时三次取中位数（结果：不许口径只看一次）。
3. 改一个工具类方法体，二次构建：观察 Maven 全量重编译 vs Gradle 的 UP-TO-DATE 任务列表（说明：增量收益只出现在"改得少、构建多"的场景）。

## 作业 2：迁移决策备忘录

**目标**：产出一份能上技术委员会的一页决策文档。

1. 按构建模型/性能/生态/团队成本四维给本团队现状打分（每维 1-5，附证据：CI 平均构建时长、新人上手周期、私服兼容性事故记录）。
2. 写出"不迁移先优化"清单：Maven `-T`、CI 缓存目录、surefire forkCount、依赖 BOM 收敛，估算各自收益（单位：分钟/构建）。
3. 错误用例自检：检查文档是否犯过"隔壁组快了所以我们也迁"的同款归因错误——性能数字必须能拆到具体机制。

## 作业 3：互操作通路验证

**目标**：验证"仓库格式与构建工具解耦"这一论断。

1. 用 Gradle `maven-publish` 插件把作业 1 的库发布到私服，POM 里 scope/依赖关系是否符合预期（验收：换一个纯 Maven 项目消费该 GAV 并编译通过）。
2. 反例体验：发布时故意漏写 `licenses`/`scm` 字段，观察 Nexus 侧元数据缺失但消费不受影响（说明：元数据完整度影响的是治理扫描，不是可用性）。
