# Maven vs Gradle 选型与迁移（关联） · 小测

### 1. 两者构建模型的根本差异是？（6分）

- A. XML vs YAML
- B. 固定生命周期阶段链 vs 可编程任务依赖图
- C. Java vs Kotlin
- D. 本地 vs 远程

> 答案：B
> 解析：Maven 只能往 phase 上挂插件，Gradle 可以改图的边与节点——其余差异多由此派生。

### 2. Gradle 相对 Maven 独一档的能力是？（6分）

- A. 依赖调解
- B. 基于输入/输出指纹的 up-to-date 与构建缓存
- C. 多模块构建
- D. 私服集成

> 答案：B
> 解析：依赖调解/多模块/私服两边都有；增量与缓存是任务图模型的原生红利。

### 3. Maven 的"配置期性能"优势体现在？（6分）

- A. 编译更快
- B. POM 是纯数据，IDE/扫描器/CI 解析免执行代码
- C. 下载更快
- D. 没有该优势

> 答案：B
> 解析：声明式元数据工具链友好；Gradle 要评估脚本才能拿到模型（配置缓存正为此补课）。

### 4. "换 Gradle 一定大幅提速"错在哪？（6分）

- A. Gradle 单线程
- B. 收益主要在高重复增量场景，冷构建+配置期开销可能反超，且缓存未配好时无增益
- C. Maven 本来就有 build cache
- D. JVM 版本决定一切

> 答案：B
> 解析：先给 Maven 上并行与 CI 缓存做便宜优化，再看增量场景占比决定是否迁移。

### 5. Gradle 项目发布到公司 Nexus 后，Maven 项目消费它，需要哪方改动？（6分）

- A. 两边都要改协议
- B. 都不改——GAV/仓库布局是共同的事实标准
- C. 只有 Maven 端改
- D. 需要转换工具

> 答案：B
> 解析：构建工具与制品仓库协议是两层；Gradle 的 publication 本质生成 POM+artifact。

### 6. 迁移路线中"最易漏的一步"通常是？（6分）

- A. 改 IDE
- B. 治理规则平移（enforcer/覆盖率/依赖白名单在新构建侧重建）
- C. 换语言
- D. 升级 JDK

> 答案：B
> 解析：构建能跑≠治理还在；规则缺位期=合规裸奔期，是迁移事故的隐蔽来源。

### 7. 哪种需求明确倾向 Gradle？（6分）

- A. 传统 WAR 部署银行内系统
- B. Android 应用或复杂代码生成/多语言混合构建
- C. 只需要打一个 jar
- D. 团队全是 Maven 十年老手且无增量痛点

> 答案：B
> 解析：Android 工具链只认 Gradle；可编程任务图擅长生成类场景——其余选项是维持现状的理由。

### 8. 关于两者依赖声明的对应关系，正确的有（多选）？（9分）

- A. Gradle 的 implementation ≈ Maven 的 compile（但 Gradle 不传递编译可见性）
- B. Gradle 没有 scope 概念而是 configuration 体系
- C. 两边解析的是同一套 Maven 仓库 GAV 坐标
- D. exclusion 在 Gradle 里写作 exclude

> 答案：A、B、C、D
> 解析：语义映射基本一一对应，但 implementation/api 的编译期可见性切分是 Gradle 独有的改进。

### 9. 支撑"不迁移 Maven"的合理论据包括（多选）？（9分）

- A. 团队认知成本与教学期产能损失
- B. Maven 的 CI 并行+缓存优化尚未做透
- C. Gradle 配置期开销在超大仓冷构建时可能更慢
- D. Maven 已停止维护

> 答案：A、B、C
> 解析：D 是谣言——Maven 持续演进（Maven 4 引入构建缓存等）；选型论证要基于事实。

### 10. 简答题：CTO 问"要不要全公司从 Maven 迁 Gradle"，给出结构化的决策分析。（40分）

- 要点1：先量化现状收益空间：统计 CI 构建时长分布、增量构建占比、本地构建等待成本（说明：没有数据都是玄学）
- 要点2：低成本优化先行：Maven -T 并行+CI 依赖缓存+模块化 -pl 增量，通常能拿走大半"换工具预期收益"
- 要点3：需求侧盘点：有无 Android/混合语言/代码生成/超大规模 monorepo 等 Gradle 原生场景——没有则迁移动力不足
- 要点4：成本侧盘点：全员再学习、治理插件重建（enforcer/覆盖率/供应链白名单）、双工具过渡期的维护费（结果：迁移是全司税不是项目组私事）
- 要点5：风险与回退：渐进影子期试点一个非关键仓，CI 对拍产物与测试，保留 Maven 回退路径半年（错误用例：一步到位大爆炸式切换）
- 要点6：给出可辩护结论：多数传统后端组织"治理 Maven+局部 Gradle（有原生需求处）"双轨共存是更优解；统一切换只在平台团队充足且增量痛点实证后启动

> 答案：见要点
> 解析：考的是"数据→低成本优化→需求/成本双侧盘点→灰度与回退→结论可辩护"的决策链完整度。
