# 分库分表与分布式主键 · 实际面试题

## 题 1：你们为什么分库分表？按什么分？

**考察点**：动机是否量化、分片键是否有 SQL 依据。

**参考答案**：先给数字：单表 X 亿行、DDL/备份超窗口、写 QPS 峰值 Y——三天花板哪个先碰顶。分片键拿查询画像说话：70% 订单查询带 user_id → 按 user_id 哈希分片，同买家事务收敛单片；商家维度走 Canal 同步的异构索引（merchant_id→order_id 映射或宽表）；运营/客服多维查询走 ES，不碰交易库。若答"因为数据量大"却没有画像与替代方案排除过程，会被持续追问。

**追问**：
- 为什么不迁 TiDB？——可以答成本/团队 MySQL 熟度/跨库 join 性能预期差异；但必须承认"能不拆最好"的立场。
- 分片数怎么定？——容量预算：热行数上限×行均大小×增长 3 年，除以单片舒适容量；常配"逻辑分片多、物理节点少"留迁移退路。

**加分点**：说出先归档/读写分离/升配都被评估过且不够，才拆片。

## 题 2：分片后 join、分页、聚合三个问题分别怎么处理？

**考察点**：跨片代价的认知是否具体。

**参考答案**：join——绑定表（同键同规则对齐）解决主子表同片 join；大表×大表非绑定维度 join 改业务层两步查或异构冗余。分页——offset 深翻在每片放大，游标续读（上一页末行复合锚点）+产品限页；真随机跳页需求交给 ES 聚合层。聚合——可下推类（SUM/COUNT/MAX）中间件改写；精确去重/中位数走预计算或近似（HyperLogLog）；报表全部离线化，不在交易分片上跑分析。

**追问**：为什么 LIMIT 10 每片各取也慢？——若排序列无片内索引或过滤后行数仍巨大，片内 top-K 本身就贵；分片不改变单片 SQL 优化要求。

## 题 3：全局唯一 ID 和分片键是什么关系？基因法讲清楚。

**考察点**：主键设计与路由的耦合理解。

**参考答案**：唯一（主键）与分布（分片键）是两个正交问题，但"按主键查不广播"需要桥——基因法：发号时把分片键（user_id）的低 k 位嵌进订单主键低位，路由时从主键抠出基因直接定位分片。代价三条：ID 结构=永久契约；分片数变更基因失效（预留位或映射表兼容）；序列位被挤占（容量预算重算）。不用基因法的替代：主键查走 ES/映射表二次路由。

**追问**：基因位放高 16 位行不行？——数学上等价可算，但高位基因会破坏 ID 趋势递增（主键顺序写收益丢失），所以惯例嵌低位。

## 题 4：双写扩容时，新老拓扑的写入冲突与数据不一致怎么处理？

**考察点**：迁移工程细节（做过的人答得细）。

**参考答案**：四类问题四套处理：① 写入原子性——双写非同事务，以老为准+新库写失败进补偿队列（按主键幂等重放）；② 存量与增量交叠——先记 binlog 位点再开刷，追平按位点回放，天然去重（UPSERT 按 updated_time 裁决）；③ 校验——分片级 checksum 抽样+行级比对连续多窗口，差异走"老覆盖新"单向修复；④ ID 跨拓扑——号段/workerId 在新旧规则各预留段，或双写期统一走与拓扑无关的发号（雪花），避免迁移自身撞号。

**追问**：什么时候才能停老写？——读全量切新且错误率观察期通过、反向对账（新→老）也跑通后，保留老库只读一个版本周期作审计源。

## 题 5：哪些"分片反模式"你见过或能预判？

**考察点**：批判性认知，区分"会用中间件"与"懂数据架构"。

**参考答案**：高频反模式：① 分片键迁就唯一约束（按手机号分片，业务按 user 全广播）；② 无分片键 SQL 不拦截（客服系统一条全表查打挂全片）；③ 在分片库跑分析报表；④ 分片+跨片外键/事务幻想（分布式事务兜住一切的性能故事）；⑤ 分片数一步拍死且无逻辑映射（扩容=全量迁移事故）；⑥ DDL/权限手工逐片执行（配置漂移）。每条给一个治理钩子（路由检查/资源组隔离/逻辑分片表/Schema 中心化管理）。

**追问**：选一个你踩过的深挖？——按 STAR 讲：现象、定位（执行计划/中间件日志）、止血、结构修复。

## 题 6：设计题：多租户 SaaS，租户规模长尾（最大租户占 40% 数据），怎么分片？

**考察点**：倾斜数据的真实处理经验。

**参考答案**：纯 tenant_id 哈希会被大租户击穿单片。分层方案：小租户共享分片（tenant→片 映射表管理，支持在线搬迁）；Top N 大租户独享分片/独享库（热点隔离）；路由不靠取模而靠映射表（搬迁=改一行映射+双写追平，这正是"逻辑分片多物理少"的兑现）。次级维度（用户查自己数据）走异构索引或片内二级分区。监控项：片容量方差、大租户 QPS 占比——触发"独享化"阈值。

**追问**：映射表本身成了单点怎么办？——映射表放 Redis+本地 Caffeine 双缓存，变更走版本号广播；它的 QPS 是路由级常数，可分域复制。
