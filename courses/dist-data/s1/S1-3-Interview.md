# 分布式事务在数据层的落地选型 · 面试题

## 题 1：分库分表后怎么保证跨库事务一致性？

- 先降维：用合适拆分键让多数写落同库，退化成本地事务。
- 残留跨库写再选方案：强一致用 Seata AT/TCC，最终一致用本地消息表/事务消息/Saga。
- 加分：给出"一致性×性能×侵入度×可回滚性"的选型框架，而不是一刀切上框架。

## 题 2：Seata AT 的原理和代价？

- 一阶段业务直接提交并记录前后镜像 undo_log、抢全局锁；二阶段成功删镜像、失败用镜像反向回滚。
- 代价：全局锁在热点行会串行化，undo_log 带来写放大与膨胀。
- 加分：热点账户应改 TCC 预留或余额分桶摊锁，而非硬扛 AT。

## 题 3：TCC 的空回滚、悬挂、幂等分别是什么、怎么处理？

- 空回滚：Cancel 先到而 Try 未发生，回滚要能识别"没 Try 过"。
- 悬挂：Try 到达时事务已回滚，这个 Try 应成为空操作、不能再预留。
- 幂等：Confirm/Cancel 可能被重复调用，需业务幂等。
- 加分：用统一事务状态表 + 业务号判定，三坑一次兜住。

## 题 4：本地消息表和事务消息怎么选？

- 都是"本地写 + 可靠投递 + 消费幂等"的最终一致，区别在投递机制。
- 本地消息表：自己写表 + 轮询发送，通用但依赖自建可靠性与清理。
- 事务消息（RocketMQ 半消息 + 回查）：中间件保证本地事务与消息投递原子。
- 加分：无论哪种，消费端幂等是底线，且要防消息表膨胀与死信堆积。

## 题 5：能容忍不一致的场景为什么不干脆全上强一致？

- 强一致以吞吐、延迟、可用性为代价（全局锁、资源阻塞、协调者单点风险）。
- 加积分、发通知这类旁路，短暂不一致可接受，最终一致 + 对账兜底性价比更高。
- 加分：CAP/BASE 视角——按业务对一致性的真实需求分层，而非一律强一致。

## 题 6：一次"扣款 + 扣库存 + 加积分"你怎么整体设计？

- 扣款资金强一致 → AT/TCC；扣库存热点 → TCC 预留或预扣+异步实扣；加积分 → 事务消息 + 幂等消费。
- 整体靠业务号串联防重复、防悬挂，并保留对账修复通道。
- 加分：指出先通过路由把可共置的写合并、把强一致范围压到最小，是成本最低的一步。
