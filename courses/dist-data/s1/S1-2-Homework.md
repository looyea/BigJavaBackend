# 读写分离与复制延迟治理 · 作业题

> 本节作业 3 题：延迟解剖实验、GTID 守卫实现、一份路由策略评审。

## 作业 1：复现并解剖 `Seconds_Behind_Master` 的三个骗人时刻（动手）

1. 场景 A：从库空闲 30s 后主库写入，秒查 `SHOW SLAVE STATUS` 观察延迟从 0 跳到真实值的过程；
2. 场景 B：主库执行 50 万行单事务 UPDATE，回放前 SBM 读数与回放中读数记录曲线；
3. 场景 C：开启 WRITESET 并行回放重复 B，观察 SBM 与 GTID 追平时长差异；
4. 结论表：SBM 显示值 vs `gtid_executed` 实际落差的对照。

**验收标准**：至少一个场景证明"SBM=0 但从库确实旧"。

## 作业 2：实现一个 GTID 会话守卫（动手）

基于 JDBC 拦截器或 ShardingSphere 自定义读写权重：

1. 写请求执行后从主库会话查 `@@gtid_executed` 存入用户会话（Redis，TTL 30s）；
2. 后续读路由前查目标从库 `gtid_executed`，包含判定不过则换下一从库，全不过回退主库并打点；
3. 用 200 并发"写后立即读"压测，统计读己之写违背率（对照：关闭守卫时的违背率）；
4. 进阶（选做）：改用 `WAIT_FOR_EXECUTED_GTID_SET(gtid, 1)` 等待方案，对比延迟代价与回退率。

**交付物**：违背率对照数据 + 一句"守卫的误伤场景"（何时过度回退主库）。

## 作业 3：读写分离路由方案评审（分析）

评审以下虚构方案，指出至少 4 个问题并给修订：

> 方案：所有 SELECT 轮询三台从库；事务内 SELECT 也轮询以均衡压力；延迟告警阈值 10s（DBA 人工看）；报表和在线共用以节省成本；主库故障由 keepalived VIP 漂移，应用连接池配置不变。

**提示检查点**：事务内读、告警自动化、分池、VIP 漂移后的连接池/DNS 缓存、读旧的业务分级缺失。
