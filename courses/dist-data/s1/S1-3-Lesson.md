# 分布式事务在数据层的落地选型

> 本节难度：★★★★★
> 本节重要性：★★★★★
> 学习产出：能在**分库分表 / 多数据源**的真实约束下为一次跨库写选择事务方案，并讲清代价阶梯——从**强一致**（单机 XA/2PC、Seata AT 无侵入但全局锁与 undo_log 有吞吐代价）到**最终一致**（TCC 业务侵入换可控、Saga 长事务补偿、本地消息表 / 事务消息用"可靠投递 + 消费幂等"兜底）。核心判断：**能不外抛的事务别外抛**（先靠拆分键让一次交易落在同库）、必须跨库时按"一致性要求 × 性能 × 侵入度 × 可回滚性"选型；跨服务、跨中间件（DB + MQ + 缓存）用事务消息/本地消息表把"多写"转成"一写 + 异步收敛"。识破"分库后仍想用本地 @Transactional 管住多源""Seata AT 高并发下全局锁热点""TCC 漏写 cancel 导致空回滚/悬挂""本地消息表不清理、不幂等"等坑。

## 一、先降维：让事务尽量不出库

```text
图目的：最好的分布式事务是"根本没有分布式事务"
选拆分键让一次交易的多数写落同一分片(如按 user_id/订单主键路由)
跨片写无法避免时才上分布式事务; 能异步的最终一致优先于同步强一致
代价阶梯: 本地事务 < AT(无侵入但有全局锁) < TCC(侵入但可控) < 2PC/XA(阻塞资源)
```

## 二、强一致：Seata AT / XA 的边界

```java
// 目的：一次跨库转账用 Seata AT, 业务只加 @GlobalTransactional, 由框架生成 undo_log 反向补偿
@GlobalTransactional
void transfer(long from, long to, BigDecimal amt) {
    debit(from, amt);   // 说明：一阶段本地直接提交并记录前后镜像(undo_log)
    credit(to, amt);    // 结果：二阶段成功即删 undo_log; 失败用镜像回滚
}
// 反例：跨库仍指望本地 @Transactional 管住两个 DataSource ❌ 单连接事务无法覆盖多库, 出现半提交资损
// 反例：AT 热点账户高频扣款 ❌ 全局锁串行化, TPS 断崖, 应改 TCC 或余额分桶
```

## 三、最终一致：TCC / Saga / 事务消息

```text
图目的：用"业务补偿 + 可靠投递"换吞吐与解耦
TCC: Try(预留)/Confirm(提交)/Cancel(释放) —— 必须处理空回滚、悬挂、幂等
Saga: 正向序列 + 逆向补偿, 无预留、隔离性弱, 适合长流程
本地消息表/事务消息: 把"跨系统写"变成"本地写 + 消息 + 消费幂等", 最终一致
```

- **TCC 三大坑**：Cancel 先于 Try 到达（空回滚）、Try 到达时已被回滚（悬挂）、重复 Confirm/Cancel（幂等）——都要靠事务状态表 + 业务号判定兜住。
- **事务消息**：RocketMQ 半消息 + 回查，把"扣款成功但发货没发"从双写不一致，转为"提交保证消息必达 + 消费端幂等"。

## 四、选型决策与底线

```text
图目的：按四个维度打分选方案, 而不是一刀切上 Seata
一致性要求(能否容忍短暂不一致?) × 性能(热点/TPS) × 侵入度(能否改业务?) × 可回滚性(补偿动作是否可逆?)
资金强一致 → AT/TCC; 长流程/跨企业 → Saga; 通知/积分/库存最终一致 → 事务消息 + 幂等消费
```
