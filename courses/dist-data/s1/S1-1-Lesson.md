# 分库分表与分布式主键

> 本节难度：★★★★★
> 本节重要性：★★★★★
> 学习产出：能用"单表行数/容量/QPS"三个天花板论证何时该拆，垂直拆与水平拆各自解决什么；写对 ShardingSphere 的分片算法配置（哈希取模 vs 范围 vs 基因法）并解释跨片查询的两种代价；给出扩容迁移的三条路线（停机双写/在线双写追平/DistSQL 类自动再平衡）及回滚预案；说清分片键选择为什么是"查询模式决定"的一次性不可逆决策。

```flow
例子目的：一条查询经过分片中间件的全流程——先看路由要什么、广播的代价在哪、结果又是怎么合并的
SQL(带user_id=8) -> 分片算法: user_id%16=8 -> 库db_2: 表t_order_8
db_2.t_order_8 -> 执行单片SQL
单片结果 -> 归并: 排序/聚合/分页改写 -> 返回客户端
对照: 不带user_id的SQL -> 广播16片各查再归并(代价×16, 这就是"分页深翻慢"的结构原因)
```

## 一、什么时候必须拆，拆什么

三个天花板先到哪个拆哪个：

- **行数/容量**：单表 2000 万级后 B+ 树高度与 DDL 时长恶化（加一列锁表小时级）；单库磁盘/连接数封顶；
- **QPS**：单实例写 TPS 千级见顶（行锁热点+binlog fsync）；
- **可用性半径**：一库承载全部订单=全业务单点。

**垂直拆**（按业务分库、按列分表）解决"可用性半径+宽表"，不解决单行太多；**水平拆**（按行分片）才是容量方案。决策顺序：先归档冷热（最便宜）→ 再读写分离 → 最后水平拆——**能不分片就不分片**，分片是查询模式的"婚前协议"，改起来最贵。

## 二、分片算法与分片键：一次性决策

| 算法 | 形态 | 适用 | 致命伤 |
| --- | --- | --- | --- |
| 哈希取模 `key % N` | 均匀 | 点查/写分散 | 扩容需全量迁移（N 变即重算） |
| 一致性哈希/槽位（16384 槽映射） | 虚拟槽迁移友好 | 需扩缩容 | 实现复杂 |
| 范围分片（按时间/ID 段） | 冷热天然分层 | 归档、按日查 | 写热点集中最新片 |
| 列表分片（按枚举：地区/租户） | 隔离性可控 | 多租户、就近 | 数据倾斜随业务 |
| 基因法 | 分片位嵌入主键低位 | 按主键反查不广播 | ID 结构即契约不可变 |

**分片键选择铁律**：拿访问频次 Top10 的 SQL 来投票——90% 查询都带 `user_id` 就按 user_id 分；"商家维度查订单"是第二条路由线，解法不是换分片键而是**异构索引**（按 merchant_id 再存一份轻量映射表/binlog 订阅构建，牺牲存储换路由）。

```yaml
# 例子目的：ShardingSphere-JDBC 5.x 订单表分片配置——每个参数对应正文的一个决策
rules:
  - !SHARDING
    tables:
      t_order:
        actualDataNodes: ds_${0..3}.t_order_${0..3}     # 例子：4 库×4 表=16 分片，先算清楚容量预算再定数
        databaseStrategy:
          standard:
            shardingColumn: user_id                      # 目的：分片键=最高频查询条件（买家维度）
            shardingAlgorithmName: mod-db                # 说明：库级哈希
        tableStrategy:
          standard:
            shardingColumn: user_id                      # 结果：同买家数据收敛单库，买家事务不跨库
            shardingAlgorithmName: mod-table
    shardingAlgorithms:
      mod-db:    { type: MOD, props: { sharding-count: 4 } }     # 错误用法：MOD 扩容需全量重分布——预算内长期方案或换 CONSISTENT_HASH
      mod-table: { type: MOD, props: { sharding-count: 4 } }
    keyGenerateStrategy:
      column: id                                          # 例子：主键由中间件生成
      keyGeneratorName: snowflake                         # 目的：分布式主键（上一节方案），绝不用各片各自自增
```

## 三、跨片查询的两种代价与改写

中间件把广播查询拆成"逐片执行+归并"，代价结构：

- **排序归并**：`ORDER BY create_time LIMIT 10` 每片各取 10 条归并——可接受；
- **深分页**：`LIMIT 100000,10` 每片都要取前 100010 条再归并，放大 N 倍——正解：**游标续读**（`WHERE (create_time,id) < 上次游标 LIMIT 10`）或业务改"仅可翻 N 页"（ES 同款限制）；
- **跨片聚合**：`COUNT/SUM` 可下推改写，`AVG/中位数` 要两段聚合或近似；
- **跨片 JOIN**：广播小表（放在每个库的绑定表/复制表）或分片键对齐的**绑定表**（t_order 与 t_order_item 都按 order 的 user_id 分片——同库同规则，join 不跨库）。

```sql
-- 例子目的：分片表深分页的错误写法与游标改写对照（16 分片场景）
-- 错误用法：LIMIT 偏移在中间件层放大——结果：每片取 100010 行归并 10 行，16 倍 IO 与内存
-- SELECT * FROM t_order ORDER BY create_time DESC LIMIT 100000, 10;

SELECT * FROM t_order                                   -- 目的：游标续读：以上一页末行做锚点
WHERE (create_time, id) < ('2026-09-20 10:30:00', 8837)  -- 例子：复合游标（时间+主键保平局确定性），每片只取 10 行
ORDER BY create_time DESC, id DESC LIMIT 10;            -- 输出：总代价恒定为 片数×10 行，翻页深度不再影响性能
```

## 四、扩容迁移：三条路线

1. **停机窗口迁移**：业务暂停→全量导→校验→切流量。最简单，仅可接受小时停的后台系统适用；
2. **在线双写（主流）**：新库上线先"双写老库+新库（以老为准读）"→ 存量追平（binlog 订阅/批量刷+增量补偿）→ 数据一致性校验（全量 checksum 抽样+实时比对）→ 读切新→停老写。每一步可回滚（读切回、写切回），**回滚靠"老库始终可作真相源"撑住**；
3. **中间件自动再平衡**：DistSQL/Vitess 类按槽迁移，工具化处理双写与校验，但引入更重运维体系。

扩容比率的工程常识：MOD 16→32 每行都要挪（重算哈希）；范围+预分区可只挪一半（分裂而非重洗）——**分片数宁大勿小**是弱命题，真正解法是"逻辑分片多（如 1024）、物理分片少、迁移即映射表变更"。

## 五、分布式主键与分片键的分工

主键（本节任务）管**唯一**：雪花/号段（上一节），配全局唯一索引兜底；分片键（路由依据）管**分布**：user_id/tenant_id 这类业务维度。两者可以不同但要有桥：基因法就是把分片键低位映射进主键，令"给主键必知片"。反例设计：主键雪花+按日期分片+商家查订单——三条路由线都没锚住，查询全靠广播，拆了比分片前更慢。

## 六、常见线上问题

- **广播查询混进核心链路**：客服后台一个"按订单号查用户"无分片键，大促期间把 16 片 CPU 打满——治理：异构索引表+网关拦截无分片键 SQL（ShardingSphere 可配强制路由检查）。
- **全局唯一约束幻想**：分片后"手机号唯一"无法单靠库内唯一索引——需独立注册中心表（不分片按手机号哈希）先占坑再写业务片。
- **跨片事务**：按 user_id 分片后买家自身操作天然单片事务；商家确认+扣库存跨片→降级最终一致（消息）或 Seata XA/AT，禁止想当然的"本地事务包住两片"。
- **DDL 只改了 15 个分片**：手工逐片 ALTER 漏一片，新列查询随机报错——必须用 SchemaHistories/在线 DDL 工具（gh-ost 类）全片执行并校验版本一致。
- **数据倾斜**：大租户占 40% 数据——热点租户单独拆库（列表分片+特判路由），别指望哈希"抹平"业务分布。

## 七、选型对比

| 方案 | 形态 | 侵入 | 能力 |
| --- | --- | --- | --- |
| ShardingSphere-JDBC | 客户端代理 | 引依赖 | 分片+加密+影子库，性能最好 |
| ShardingSphere-Proxy | 独立进程 | 零改造 | 异构语言接入，多一跳网络 |
| MyCat 类 | 独立代理 | 零改造 | 老牌，社区式微 |
| 原生分片数据库（TiDB/Vitess/OceanBase） | 存储层自带 | SQL 基本无改 | 把"分片运维"变成"扩节点"，代价是新存储引擎学习/成本 |

**迁移叙事**：很多团队的分库分表终点是"迁到分布式数据库"——分片中间件解决 MySQL 时代的容量，原生分片解决运维复杂度；选型时按团队 MySQL 熟度与规模拐点决定"自己拆"还是"换引擎"。

## 十、本节小结

水平拆分片是容量问题，垂直与读写分离是可用性/负载问题，先冷归档再拆片是成本次序。分片键是查询模式的一次性投票，解药是异构索引而非换键；跨片代价全在"广播×归并"的结构里，深分页游标化、JOIN 绑定表化、全局唯一独立建模。扩容的正解是逻辑分片映射而非物理重洗——把"迁移"降维成"改映射表"，这条退路要在第一天就铺好。
