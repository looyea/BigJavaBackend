# 数据一致性的校验与修复 · 面试题

## 题 1：怎么证明你的系统"最终一致"真的收敛了？

- 靠校验闭环：定期对账/比对发现差异 + 幂等修复收敛 + 指标观测证明差异归零。
- 只说"会最终一致"不够，要能量化不一致率与修复时延。
- 加分：把关键字段用业务不变量校验（余额=充值−消费−提现），异常直接暴露上游 bug。

## 题 2：比对两份数据，为什么不能只比行数？

- 内容被改但行数不变时，count(*) 完全漏检。
- 应按主键分片比对行内容哈希/版本，命中差异再逐行定位。
- 加分：分片哈希把"全表暴力比对"降到"差异分片才细查"，控制爆炸半径与开销。

## 题 3：对账任务怎么设计才不拖垮线上？

- 错峰、限流、走只读/独立副本，可重入 + 断点续跑。
- 绝不实时全表扫描压主库；把对账做成旁路而非第二套主链路。
- 加分：对账脚本自身纳入监控，防止"脚本挂了以为一切正常"。

## 题 4：发现缓存和 DB 不一致，怎么修？

- 以 DB 为真值源、带版本号回源重建，而不是盲目删缓存造成穿透。
- 修复要幂等：按版本"只向前"，重复执行不把新值覆盖回旧值。
- 加分：能靠不变量安全裁决的自动修；涉资金无法判真值的挂账人工，避免越修越错。

## 题 5：修复逻辑为什么必须幂等？

- 修复常被重试/并发重复触发，非幂等会把正确的较新值覆盖回较旧值，制造二次不一致。
- 用主键 + 版本/CAS 比较保证"只向前"。
- 加分：幂等修复 + 死信/人工兜底 + 可观测，才算完整闭环。

## 题 6：多活架构下 A 地和 B 地数据冲突怎么办？

- 先靠就近写单元化减少跨地同 key 冲突；冲突出现时以业务不变量 + 时间戳/版本裁决前滚或回滚。
- 无法自动裁决的（尤其资金）挂账走人工，别把错的一方当权威。
- 加分：把"脑裂期间产生的差异"纳入专门对账窗口，事后集中收敛。
