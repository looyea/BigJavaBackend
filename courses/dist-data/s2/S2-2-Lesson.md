# 异地多活与容灾架构

> 本节难度：★★★★★
> 本节重要性：★★★★★
> 学习产出：能给系统定出 RTO/RPO 并反推容灾等级（冷备/温备/同城双活/异地多活）的成本曲线；讲清异地多活的三大拦路虎——延迟、数据同步、写冲突——各自的标准解法；设计"按用户分片、单元闭环"的路由体系（路由键、接入层三跳、MQ/缓存单元化配套）；写出一次可执行的切流预案与演练计划，理解"没演练过的多活等于没有多活"。

```flow
例子目的：一次"按用户归属路由"的单元化请求全程——同一用户的读写在同一单元内闭环，只有归档数据跨城同步
用户U(归属杭州单元) -> 接入层(HTTPDNS/LVS): 解析到杭州入口
接入层 -> 杭州单元应用: 携带路由键 uid 转发
杭州单元 -> 杭州DB: 本地读写(毫秒级, 不出城)
杭州DB -> DTS同步 -> 张北单元DB: 异步复制(容灾副本, RPO=秒级)
对照反例: 归属错了的用户流量 -> 路由层校验uid%unitCount不符 -> 纠正转发并告警(防止双单元同时写同一行)
```

## 一、容灾等级先于技术：RTO/RPO 推导

先问业务两个数字，再谈架构：

- **RTO（恢复时间目标）**：故障后多久必须恢复服务——决定切换自动化程度与预案复杂度；
- **RPO（恢复点目标）**：最多能丢多久的数据——决定同步还是异步复制、是否需双写。

| 等级 | 典型形态 | RTO | RPO | 成本 |
|---|---|---|---|---|
| 冷备 | 备份+停机重建 | 小时~天 | 小时 | 最低 |
| 温备 | 从库待命，切换需人工 | 分钟~小时 | 秒~分钟 | 低 |
| 同城双活 | 低延迟同步复制/两中心互备 | 分钟 | ≈0 | 中 |
| 异地多活 | 多单元同时承载流量 | 秒~分钟（自动切流） | 秒（异步） | 高（全栈冗余+流量调度） |

30km 内同城光延 ~1ms，可以谈"同步"；1000km 异地 RTT 30ms+，同步复制会把每个写事务拖慢 30ms——**所以异地多活的数据层几乎必然是异步复制 + 单元化写路由**，用"同一行只在一个单元写"绕开同步窗口内的双写冲突，而不是硬抗延迟。

## 二、异地多活三大拦路虎与解法

1. **延迟**：任何"跨城调用"都要显式标价。原则：单元内闭环，禁止链路中出现同步 RPC 出单元。
   ```java
   // 目的：展示多活单元内服务调用的正确姿势——只调本单元实例
   @FeignClient(name = "order-service")            // 逻辑名解析, 由注册中心按本单元过滤实例
   public interface OrderClient { ... }
   // 结果: 调用不出城, P99 保持同城毫秒级
   // 错误用法: 配置写死跨城实例地址或开启"全局负载均衡优先就近", 下单链路跨城 RPC 往返 30ms×N 跳,
   // 高峰期整条链路超时雪崩——多活单元一旦互相依赖就退化成"更贵的单点"
   ```
2. **数据同步**：DTS/Canal 类增量订阅做单元间复制，链路本身要监控延迟并设熔断阈值（延迟 >30s 禁止把流量切到该单元，否则用户读到"穿越"数据）。
3. **写冲突**：终极手段是分片——每个数据行有唯一"归属单元"，天然消灭冲突；对无法分片的低频全局配置，用"中心单元写 + 其他单元只读"收缩写面。

## 三、单元化路由的落地细节

```java
// 目的：路由键选择与归属计算——选业务"最常一起读写"的维度做分片键
static final int UNIT_COUNT = 3;                        // 单元总数, 扩容需配合数据迁移, 一步到位留余量
int unit = (int) (userId % UNIT_COUNT);                 // 结果: 用户U恒等于同一单元, 其订单/余额同行同单元
// 错误用法: 按"登录地/机房就近"路由——同一用户今天杭州明天张北写余额, 归属漂移=双单元同时写=资损事故
// 说明: 未登录请求(注册/游客浏览)走"无状态单元", 不产生跨单元写
```

- 三跳路径：HTTPDNS/客户端 → 公共接入层（GSLB + 路由规则）→ 单元内网关；每跳都携带并校验路由键，不匹配即纠正 + 告警；
- 中间件配套：MQ Topic 单元内闭环（跨单元只同步"归档事件流"）、Redis 每单元独立集群（禁止跨城读写，缓存击穿域不扩散）、注册中心按单元隔离实例列表；
- 少数"全局单点数据"（库存秒杀总量、优惠券总量）：要么收敛到中心单元串行写，要么预分配额度到各单元（总量 = Σ 单元额度，牺牲全局精确换多活）。

## 四、切流：多活的价值全在切换能力上

```bash
# 目的：模拟故障后把杭州单元 30% 流量迁到张北的标准动作序列
curl -s -XPUT "http://router-admin/api/rules/hz/weight" -d '{"weight":0.7}'  # 结果: 路由层按新权重灰度放量, 观察5分钟
etcdctl get /unit/hz/lag --print                                            # 检查: 目标单元数据同步延迟须 < 切换SLO(如10s)
mysql -h zhangbei-readonly -e "SELECT MAX(update_time) FROM t_order"        # 抽样: 目标单元数据新鲜度达标才扩大切流
# 错误用法: 直接 DNS 全局 TTL 一改了之——客户端缓存 DNS 数小时, 流量一半打不进来一半打错单元, 双写冲突爆发
# 说明: 回滚预案与切换同等重要, 一键回切脚本必须和切流脚本同一次演练里验证
```

RPO>0 的异步复制决定了切换瞬间必然丢尾数据：对资金类表要设计**对账修复流**（切换后按两地 binlog/审计表 diff 出"杭州写了张北没有"的请求，逐笔冲正或人工工单），这是异地多活方案里最不被重视、出事时最救命的模块。

## 五、常见线上问题

- **演练缺失**：预案只在文档里"切换成功"过。季度性故障注入（拔光纤/杀单元）是唯一可信的证明方式；
- **数据同步链路单点**：DTS 任务挂了自己不知道，延迟监控必须独立于被监控链路（旁路心跳表比对）；
- **定时任务多活重复跑**：三个单元各跑一遍扣款任务=三倍资损。任务要么按单元分片只处理本单元数据，要么全局抢占锁收敛到单单元；
- **归属数据倾斜**：大商家 80% 流量集中在同几个 uid 段，单元水位不均——路由键哈希要加盐打散段分布；
- **会话与登录态跨单元**：切流后用户 session 在目标单元不存在引发重登录风暴，登录态需多单元同步或无状态化（JWT）。

## 六、选型对比

| 方案 | 一致性 | RTO/RPO | 改造成本 | 适用 |
|---|---|---|---|---|
| 主备（一城写全城读） | 异步复制秒级旧读 | 分钟 / 秒 | 低 | 中小系统容灾起步 |
| 同城双活同步复制 | 强（组复制/半同步） | 分钟 / 0 | 中 | 金融合规 RPO=0 |
| 异地多活单元化 | 单元内强、单元间最终 | 秒~分 / 秒 | 高（全栈） | 大流量互联网核心链路 |
| 读写按库分活（读多活写单活） | 读旧窗口=复制延迟 | 读秒/写分钟 | 中 | 内容/ feed 类业务折中 |

## 七、小结与过关要点

异地多活不是"多建一个机房"，而是**用分片消灭跨城写、用闭环消灭跨城读、用切流与对账兜住故障瞬间**。过关自测：能否对自己的系统说出——路由键选什么、哪些数据必须收敛中心单元、切流时尾数据丢哪去了、上一次演练是什么时候。四个问题有一个答不上，多活就还是 PPT 架构。
