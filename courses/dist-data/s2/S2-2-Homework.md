# 异地多活与容灾架构 · 作业题

> 本节作业 3 题：一个单元化路由小实验、一份切流预案与对账流设计、一次容灾等级答辩。

## 作业 1：三单元路由模拟与小故障演练（动手）

用 docker-compose 在本机模拟"三单元"：3 套应用+MySQL（`unit-hz/unit-zb/unit-sz`），前置一个路由层（Nginx/OpenResty 或自写网关，按 `userId % 3` 决定转发目标，不匹配返回 307 纠正）。

1. 灌入 3000 用户数据，脚本随机带 uid 发请求，统计"归属正确率"应为 100%；
2. 故意把路由规则改成按来源 IP 路由，重跑并统计同一用户的写入落在几个单元（观察归属漂移）；
3. 停掉 `unit-zb` 的 MySQL，验证：zb 归属用户请求失败，但 hz/sz 用户完全无感（爆炸半径=1/3）；
4. 把 zb 权重切 0、流量改道 hz，恢复 zb 后按延迟追平再切回。

**验收标准**：给出第 3 步的爆炸半径证据（各单元成功率曲线），第 4 步"何时才允许切回"的判定命令与阈值。

## 作业 2：切流预案 + 尾数据对账流（设计+动手）

针对作业 1 的环境写一份可执行切流预案（runbook）：

1. 触发条件（哪些监控指标到什么阈值启动切流）、决策人、步骤序列、回滚步骤；
2. 实现一个最小对账流：两单元各建 `t_order_audit(order_id, unit, version, update_time)`，单元 DB 触发器写审计行，DTS 类同步模拟"丢最后 5 秒"（手工延迟一方应用），切流后跑 diff 脚本找出"hz 有 zb 无"的订单，生成冲正清单；
3. 演练记录：本次切流各步骤耗时，对照你定的 RTO 算达标与否。

**验收标准**：diff 脚本能准确找出人造的丢失写入；预案里每项操作都有"验证点"（怎么确认这步成功了）。

## 作业 3：给真实系统定容灾等级（分析）

挑你熟悉（或仓库里任一）系统：

- 列出业务清单，逐项询问/推定停机 1 小时与丢 1 分钟数据的损失，反推每域的 RTO/RPO；
- 对照冷备/温备/同城双活/异地多活四档，给出每域的最低达标档位与改造清单（哪些必须先单元化、哪些只需加从库）；
- 标出"当前架构宣称的等级"与"实际能到达的等级"的差距（例：宣称多活但注册中心全城共享=假多活）。

**交付物**：一页容灾分级表 + 三行以内的"最优先改造项"结论。

**提示**：判定假多活的三个灵魂拷问——跨城同步 RPC 有几条？全局单点数据谁写？上次演练是什么时候？
