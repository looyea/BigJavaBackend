# 缓存一致性与双写方案 · 实际面试题

## 题 1：更新数据库时，缓存是删还是改？先删还是后删？

**考察点**：是否理解 Cache Aside 每个顺序选择背后的并发窗口，而不是站队口诀。

**参考答案**：优先"更新库提交后删缓存"。删除而非更新：缓存值以"下次读重建"为准，避免并发写导致的乱序覆盖，也避免写扩散（改了但没人读白花一次写）。不先删：删到写库提交前的窗口里并发读会把旧库值回填，错误一直活到 TTL。残余窗口（提交后到删除前）毫秒级，用重试队列保删除必达 + 兜底 TTL 自愈。

**追问**：
- 那"先更库再更缓存"呢？——两个并发写的缓存更新顺序无保证，可能出现旧值后到覆盖新值，除非加版本号；删除没有"写入内容"所以没有乱序覆盖问题。
- 删除失败怎么办？——重试队列（本地消息表/事务消息）+ TTL 兜底 + 可选 binlog 旁路补偿，三层。

**加分点**：主动区分"一致性的定义"——缓存与库的瞬时不一致可接受，收敛速度与错误内容才是关键；能说出"缓存不是事实源，是可重建副本"的立场。

## 题 2：什么是延迟双删？什么时候真的需要它？

**考察点**：会不会把延迟双删当口头禅乱用。

**参考答案**：写完库删一次缓存，延迟 N 毫秒再删一次。第二次删针对的是窗口期里那笔"读到旧值、慢吞吞回填"的迟到写回——第一次删时它还没落进缓存。N 的取值 ≥ 一次"读库+回填"的耗时（压测定，不是拍脑袋 500ms）。适用前提：读路径有回填且读写并发密集；如果删除本身走的是可靠重试 + 短 TTL 兜底，多数场景延迟双删可以不做——它是缓解手段不是银弹。

**追问**：
- 为什么不用分布式锁把读写串行化？——读路径加锁的吞吐代价远超毫秒级不一致窗口的业务损失，过度设计。
- 有比延迟双删更干净的方案吗？——版本号/时间戳守卫（旧值写不回）、Canal 订阅 binlog 把失效从业务代码剥离。

**加分点**：能讲出"延迟双删在 Redis 主从架构下还有个坑：两次删可能落到不同副本，从库未及时同步导致漏删"，并给出"删主 + 短 TTL"的对策。

## 题 3：用 Canal 订阅 binlog 做缓存失效，工程上要注意什么？

**考察点**：是否真搭过旁路失效管道。

**参考答案**：四个要点：① 顺序性——同一行的事件必须按序消费，按主键哈希进同一队列/分区；② 幂等与重放——At-least-once 语义下重放旧事件可能"删掉新值之后的缓存"，靠版本号比对或接受"多删一次"（删除幂等但删除时机不幂等）；③ 只订阅需要的表与列，避免大事务 binlog 打爆下游；④ 兜底——管道本身挂了要告警，且缓存保留 TTL，失效退化为"最多旧 TTL 时长"而不是永久脏。

**追问**：
- binlog 事件里行数据是变更前还是变更后？——ROW 格式含 before/image，UPDATE 要取 after image 判断是否还需要失效（如只更新了无关列可跳过）。
- 和业务代码里删缓存比，Canal 方案的缺点？——链路长、延迟不可控（回放时积压）、DDL 兼容、多一套组件运维；中小规模直接"提交后删+重试"更划算。

**加分点**：说出 Canal 位点（position/GTID）与消费 ACK 的关系，位点提交过早会在消费者崩溃时丢事件。

## 题 4：MySQL 和 Redis 双写，怎么保证两边一致？

**考察点**：对跨存储原子性的边界认知——这题的正确回答往往是"不保证"。

**参考答案**：先反问业务是否真的需要 Redis 作为"写入目标"而不是"读取副本"。若只是缓存：不双写，写只进 MySQL，缓存走失效/重建，一致性目标是"有界陈旧 + 最终收敛"。若确实是双存储架构（如 Redis 承担计数/队列真相）：可选①本地消息表/事务消息把第二跳写入变成可靠投递 + 幂等消费；②TCC/Seata 把两侧纳入柔性事务，接受吞吐损失；③对账闭环兜底——跨存储没有原子提交时的最后防线一定是比对修复任务。

**追问**：
- XA/2PC 能不能把 Redis 拉进来？——Redis 无 prepare 语义，做不到真两阶段；中间件"伪 XA"只是把失败面缩小。
- 对账多久跑一次？——按业务资损窗口定：分钟级增量对账 + T+1 全量。

**加分点**：引用"单存储内 ACID、跨存储 BASE"的原则，能画出你们系统里"事实源只有一个"的架构图。

## 题 5：出过一次"缓存读到旧数据"的线上问题，你怎么排查和根治的？

**考察点**：真实故障处置能力（高频行为题，必须有细节）。

**参考答案**（示范框架，细节要换成自己的）：定位三步——① 用 trace/时间戳确认读到的旧值写回缓存的时间点；② 对齐 DB 的 binlog 时间线，找到"读回填发生在写提交之前"的赛跑证据；③ 检查失效代码是否把删除写在了事务内/删除失败只打日志。根治组合：删除移到提交后 + 失败进重试 + value 带 update_time 守卫回填 + 该对象 TTL 从 30 分钟压到 5 分钟。最后补监控：缓存与 DB 抽样比对任务，把"不一致"从客诉发现变成告警发现。

**追问**：
- 为什么不直接"该 key 永远读主库"？——可以把回答引到分级：资金字段读主或强守卫，普通展示容忍秒级旧值，全量读主是放弃缓存收益的懒惰解。

**加分点**：给出修复前后的量化对比（旧值存活时长 P99 从 30min 降到 200ms），以及一条"我们据此制定了写路径规范"的制度化收尾。
