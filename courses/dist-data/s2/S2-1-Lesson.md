# 缓存一致性与双写方案

> 本节难度：★★★★★
> 重要程度：★★★★★
> 学习产出：能证明"先删缓存后写库"为什么错、"先写库后删缓存"的残余窗口有多大；写出带并发保护的 Cache Aside 变体（版本号/延迟双检）；给出延迟双删的真实适用前提而不是口头禅；设计 Canal binlog 驱动的失效管道（顺序性、幂等、乱序兜底）；对"双写两个存储"给出一致性的判定标准与对账闭环。

```flow
例子目的：Cache Aside 标准形态下，两个并发请求如何制造"缓存里躺着旧值直到过期"的经典不一致
请求A(改价100->120): 更新DB提交完成
请求B(读): 查缓存miss -> 读DB拿到旧主从延迟值100
请求A(改价后续): 删除缓存(此时缓存本来就没有)
请求B(读后续): 把旧值100写回缓存 -> 之后所有读命中100直到TTL到期(错误持续= TTL时长!)
```

## 一、把"一致"定义清楚：三种写法的窗口对比

设操作序列 W=写库、D=删缓存、R=读回填。目标是**缓存值 ∈ [最近一次已提交库值的某个邻域]**。四种组合的失败模式：

| 顺序 | 并发危害 | 窗口量级 | 结论 |
| --- | --- | --- | --- |
| 先 D 后 W | 上图 B 的旧值回填——不一致持续到 TTL | TTL 级（分钟~小时） | 禁止 |
| 先 W 后 D（Cache Aside） | 读回填夹在 W 与 D 之间的极窄窗口（读到的库值需旧于 W 且回填发生在 D 后） | 毫秒级×低概率 | 默认首选 |
| 先 W 后更新缓存（写穿透） | 两写并发时缓存终值可能取先提交者（谁后到不确定）；序列化成本高 | 不定 | 慎用，值需可纯函数计算才行 |
| 双删 D→W→延迟 D' | 针对"读回填旧值"的补救：D' 清掉窗口期回填的旧值 | 收敛时间=延迟量 | 有前提可用（见下） |

**Cache Aside 残余窗口的诚实描述**：读请求在 W 前读了库（拿到旧值）、在 D 后回填——需要"读库早于写提交 + 回填晚于删除"的交错，概率≈(读事务耗时×写频率)，且不一致时长=回填后的 TTL。治理不是消灭窗口而是把窗口变成可接受：**短 TTL 兜底 + 关键数据带版本号校验**。

```java
// 例子目的：带版本号的 Cache Aside 写回保护——旧值回填在版本比较下失效
class VersionedCacheAside {
    Item loadWithGuard(long id) {
        Item c = cache.get(key(id));                          // 例子：先查缓存
        if (c != null) return c;
        Item db = dao.read(id);                                // 说明：miss 才回源（读库返回带 row_version）
        cache.setIfNewer(key(id), db, ttl + jitter());         // 目的：写回时比较版本——错误用法对照：直接 set——结果：并发下把更早版本覆盖进缓存
        return db;
    }
    void updateAndInvalidate(long id, Item delta) {
        long newVer = dao.updateWithVersion(id, delta);        // 例子：UPDATE ... , row_version=row_version+1 返回新版本
        cache.delete(key(id));                                 // 目的：先提交后删除（Cache Aside 正道）
        scheduler.schedule(() -> cache.evictIfOlder(key(id), newVer), 500); // 输出：延迟二检——仅当缓存现值版本 < newVer 才再删，兜住"删后被旧读回填"
    }
}
```

## 二、延迟双删：说清它的前提，别当咒语

`D → W → sleep(t) → D'` 的逻辑：睡过"并发读回填旧值"的窗口再补删。三个常被忽略的前提：

1. **t 的取值是赌博**：应 > 读事务+回填延迟 P99；主从延迟一大，t 就失效——所以延迟双删必须配**从库不服务回源读**（回源走主或 GTID 判定）；
2. **D' 丢失的兜底**：应用崩溃 D' 没执行——不一致持续到 TTL，故 D' 要落重试队列（消息驱动）而不是进程内 sleep；
3. 它治的是"回填旧值"，**不治**"删失败"——W 成功 D 失败时缓存根本还是旧值，与双删无关，那是失效通道的可靠性问题（见第四节）。

结论：延迟双删是 Cache Aside + 版本号方案的低配版；面试说出"前提是回源读不经过未追平的从库、二次删要持久化重试"即与背题者拉开差距。

## 三、binlog 驱动失效：把"谁记得删缓存"变成订阅制

应用内删缓存的死穴：**写入口不止一个**（运营后台直改 DB、数据订正脚本、其他服务同库写）。Canal 类方案把失效从"写方自觉"改为"变更日志订阅"：

```flow
例子目的：binlog 失效管道的数据流与每段的可靠性设计
MySQL主库 -> Canal(伪装从库读binlog): 行变更事件(表,主键,前后镜像)
Canal -> MQ(按主键hash分队列): 同键事件保序(目的: 防同一行先删后写乱序)
MQ -> 失效服务(幂等消费): 删缓存+可选新值预热(结果: 所有写入口统一被覆盖)
失效服务 -> 对账Job(T+5min): 抽样比对DB与缓存版本(兜底: 管道断流也能被发现)
```

三个设计要点：

- **顺序**：同一行的事件必须进同一队列（按主键 hash），否则"改价→下架"乱序执行留下复活缓存；跨行无需全局序；
- **幂等**：删除天然幂等；"更新缓存为新值"则要求事件带版本且比较写（`setIfNewer`）；
- **滞后监控**：Canal 位点 vs 主库当前位点的差值就是失效延迟 SLA，断流告警必须配（管道挂了=全量回到 TTL 兜底世界）。

**删 vs 更新的终局选择**：删（lazy 重建）简单安全；更新（直接写新值）省一次回源但有乱序覆盖风险——高频热点大对象才值得，且必须版本比较。

## 四、双写两个存储：什么时候"删缓存"不够

场景升级：写要同时进 MySQL 与 ES/Redis 集群（搜索/多模）。**双写没有分布式事务撑腰时，一切顺序都有窗口**，工程答案收敛为两种：

1. **主从式（推荐）**：一个存储是唯一真相（MySQL），另一个是**派生副本**（ES/缓存），派生侧只接受 binlog/CDC 单向喂养——把"双写一致"退化成"复制延迟"问题（回到上一节 GTID/位点治理）；
2. **真双主**：两存储都可独立写——必须业务层协调（分布式事务或 TCC），复杂度陡增，除非产品形态强制，否则否决。

**判定标准**：当有人问"缓存和数据库不一致怎么办"，先反问"谁有资格定义真相"。数据库是真相 → 缓存永远只做"可丢弃+可重建+带 TTL"的加速副本，不一致的后果被限制在 TTL 与回源策略里；这句话能解开 80% 的缓存一致性争论。

## 五、常见线上问题

- **缓存雪崩式集中回填旧主从值**：批量失效后回源全打延迟从库——回源读走主或 GTID 守卫。
- **删除失败静默**：Redis 抖动 catch 掉异常——失效失败要进重试队列+计入 SLO，否则不一致无感知。
- **Canal 全量同步打挂缓存**：位点重置触发全表事件风暴——失效服务限流+按表熔断。
- **热点 key 删除瞬时穿透**：先"逻辑过期"异步重建（Caffeine+refreshAfterWrite），物理删除留给冷数据。
- **两套 TTL 互相打架**：多级缓存（本地+Redis）只失效远端、本地靠短 TTL/广播失效——见 Caffeine 包多级缓存。

## 六、动手题

1. 复现开头时序：用两个线程交错"W/D/R 回填"，统计旧值在缓存的存活时长；再实现 `setIfNewer` 版本守卫复测归零。
2. 搭 Canal→RocketMQ→失效服务最小管道：注入同主键两事件乱序与队列重投，验证顺序哈希与幂等删除的表现。

## 七、常见选型对比

| 方案 | 一致性 | 复杂度 | 适用 |
| --- | --- | --- | --- |
| Cache Aside+TTL | 弱（毫秒窗口+TTL 兜底） | 低 | 默认选择 |
| +版本号 setIfNewer | 防回填旧值 | 低 | 并发读写混合 |
| 延迟双删（持久化版） | 收敛更快 | 中 | 无版本列的存量改造 |
| binlog/CDC 失效 | 覆盖全部写入口 | 中（管道运维） | 多写入口/多消费方 |
| 写穿透+逻辑过期 | 强（读侧永不旧） | 高 | 热点大对象 |

## 八、关联技术栈

上一节读写分离（回源读的位点判定直接复用）、Redis 包 s2-2（缓存三大问题与一致性基础）、Caffeine 包 s1-2（多级缓存与失效广播）、Canal/GTID、下一节异地多活把"派生副本"思想放大到机房粒度。

## 九、本节小结

缓存一致性的正确提问是"真相源是谁、不一致的代价谁付"：数据库为真相时，缓存只是可丢弃副本，方案空间收敛到 Cache Aside+TTL+版本守卫；并发回填用 `setIfNewer` 与延迟二检兜住；多写入口交给 binlog 订阅管道并守住主键顺序与幂等；双写两存储的终解是把一个降级为派生副本。延迟双删不是咒语——说出它的前提和失效条件，才算真的会用。
