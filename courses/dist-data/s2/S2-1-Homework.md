# 缓存一致性与双写方案 · 作业题

> 本节作业 3 题：一场赛跑复现实验、一条失效管道搭建、一份一致性分级评审。

## 作业 1：复现"缓存里躺着旧值直到 TTL"（动手）

环境：MySQL + Redis + 任意商品服务（可用本课示例代码改造）。

1. 故意写一个"先删缓存、再更新库"的改价方法，把写库耗时人为垫到 500ms（`Thread.sleep` 模拟慢事务）；
2. 用 50 并发循环读该商品，统计改价一次后缓存中出现的旧值回灌次数与持续时长；
3. 改成"先写库后删缓存"复测，记录残余窗口内的旧读次数；
4. 再加上延迟 1s 的二次删除复测，验证旧值存活时间被压到接近 0。

**验收标准**：三组对照数据成表，能指着数据说出每一步治理各自消灭了哪个窗口；写出"延迟双删的延迟量应该怎么定"的一句话结论。

## 作业 2：搭一条 Canal → MQ → 失效消费者管道（动手）

1. docker 起 MySQL（ROW 格式 binlog）+ Canal + RocketMQ/Kafka + 一个失效消费者；
2. 消费者按主键哈希进同一分区，保证同行事件按序，执行"删缓存 + 500ms 后二删"；
3. 故障演练三件套：kill 消费者再恢复验证不丢事件；人为把 Redis 关停 10s 验证删除失败进重试；重放一段旧 binlog 观察是否把新值删没了，据此给版本号守卫补一层（缓存 value 带 `update_time`，删除前比对）；
4. 记录每次演练的告警/日志证据。

**验收标准**：给出"事件乱序/丢失/重复"三种故障各自的现象、根因与最终采用的防护组合；管道端到端失效延迟 P99。

## 作业 3：给现有系统做缓存一致性分级评审（分析）

挑仓库或你熟悉系统里全部"写 DB 又动缓存"的路径（含定时任务、MQ 消费者里的隐式写），每处标注：

- 采用的模式（Cache Aside / 更新缓存 / binlog 旁路 / 双写）；
- 不一致窗口的理论与实测上界、业务能否容忍（用"读错会不会赔钱"判定）；
- 缺失的兜底（重试？TTL？对账？）。

**交付物**：一张分级表 + 至少两处"实现与声明不符"的结论（例如声明 Cache Aside 实际把删除写进了事务内）。

**提示**：重点盯"删除失败只打日志不回滚也不重试"的路径——那是生产事故报告里最常见的沉默地雷。
