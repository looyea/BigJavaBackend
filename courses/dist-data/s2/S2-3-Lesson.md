# 数据一致性的校验与修复

> 本节难度：★★★★☆
> 本节重要性：★★★★☆
> 学习产出：能把"最终一致"从口号落成**可验证、可修复、可观测**的闭环——校验层用**对账**（全量/增量、T+1 或准实时）、**逐行比对**（主键分片 + 行内容哈希/版本/时间戳水位）、**binlog/CDC 订阅比对**发现缓存与 DB、主与从、A 地与 B 地之间的差异；修复层用**幂等重放 / 以真值源为准回填 / 前滚或回滚**收敛差异，并区分"能自动修"与"必须人工介入"的资金类差异；观测层把**不一致率、修复延迟、积压对账差**做成指标与告警。核心取舍：校验要**可重入、可断点续跑、错峰不影响主链路**；修复必须**幂等**，避免把一次抖动放大成二次不一致。识破"只比对数量不比对内容""对账风暴打满从库""修复逻辑非幂等重复覆盖真值""缓存不一致只靠删除、没有回源校验"等坑。

## 一、校验：怎么发现不一致

```text
图目的：先定位"谁和谁"之间可能不一致, 再选校验手段
缓存 vs DB：比对 key 是否存在 + 值指纹; 增量按写水位扫描
主 vs 从 / 异地 A vs B：分片取主键区间 → 行内容哈希(MD5/xxHash)聚合比对 → 命中差异再逐行定位
强信号：金额/库存等关键字段用业务不变量校验(如 余额 = 充值 − 消费 − 提现)
```

```java
// 目的：分片哈希快速定位差异, 避免全表逐行暴力比对
for (Shard s : shardsByTime(window)) {                 // 说明：按时间水位切成可对账的分片
    String hA = digest(s.rowsInDb());                  // 结果：DB 侧行集指纹
    String hB = digest(cacheClient.get(s));             // 缓存/从库侧同区间指纹
    if (!hA.equals(hB)) repair.queue(s);                // 只把指纹不一致的分片送入逐行修复, 缩小爆炸半径
}
// 反例：只 count(*) 比行数 ❌ 内容被改但行数不变时完全漏检
// 反例：对账全表扫描压满从库 ❌ 拖垮线上读, 必须错峰/走独立副本/限流
```

## 二、修复：把差异收敛回真值

```text
图目的：修复的准绳是"谁是真值源", 且操作必须幂等
缓存不一致：以 DB 为准回源重建(带版本号), 而非盲目删除造成穿透
主从/异地：前滚缺失写 or 回滚脏写, 依据业务不变量与时间戳裁决
资金差异：不可自动覆盖, 生成挂账工单人工裁决, 防把错的一方当权威
```

- **幂等是底线**：修复动作可能重复执行（重试、并发任务），必须按主键 + 版本比较"只向前"，绝不把新值覆盖回旧值。

## 三、可观测与闭环

```text
图目的：不一致要能被量化、被告警、被追踪到修完
指标：不一致率、发现→修复时延、对账积压差、自动修复成功率
告警：关键字段(金额/库存)差异突增即刻升级; 差异长期不归零说明上游有 bug
闭环：对账任务本身也纳入监控, 防止"对账脚本挂了以为一切正常"
```

## 四、坑与底线

- **别把校验做成第二套主链路**：对账/比对要错峰、限流、走只读副本，不能把生产库拖慢。
- **自动修复的边界**：能靠不变量安全裁决的才自动修；涉资金、无法判定真值的必须挂起人工，避免"越修越错"。
