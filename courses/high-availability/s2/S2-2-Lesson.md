# 超时、重试、幂等与退避

> 本节难度：★★★★☆
> 本节重要性：★★★★★
> 学习产出：能把"一次调用失败后系统该怎么办"讲成一套自洽、不打架的工程纪律——这四件事必须**成套设计**，缺一个都会把小故障放大成大事故。**超时**是所有远程调用的第一道防线：没有超时就是"无限等待 = 线程被占满 = 雪崩"；关键是**超时预算沿调用链逐级传导收敛**——入口给了 1s，链路 A→B→C 就不能各层都设 1s（否则末端总耗时远超入口、上游早已放弃下游还在跑），每层预算要**小于剩余预算**并预留。**重试**能快速消化瞬时故障（网络抖动、单实例重启），但**必须配退避与上限**：固定间隔会在故障恢复瞬间形成"重试风暴"（惊群/踩踏）压垮刚爬起来的下游，所以用**指数退避 + 随机抖动（jitter）**打散重试时刻、限制最大次数、并区分**可重试错误**（超时/503/连接失败）与**不可重试错误**（400/业务失败/余额不足——重试也没用还可能重复扣款）。**幂等是重试的前置条件**：非幂等操作（扣款、下单、加库存）一旦重试就可能重复执行，所以重试只安全作用于**幂等**或已做幂等保护的接口（幂等键/去重/唯一约束，与幂等专题强耦合）。四者联动还需**熔断**兜底：连续失败到阈值即快速失败、不再重试、给恢复窗口，防"重试把熔断打穿"或"雪崩时全链路疯狂重试放大流量"。识破"不设超时""每层超时各设一样导致总耗时爆炸""无退避固定重试造成恢复踩踏""对写操作盲目重试又不幂等 → 重复扣款""重试次数 × 服务实例数放大成数倍流量（retry amplification）""重试与熔断互相打架"等坑。

## 一、超时预算要沿链路收敛

```text
图目的：超时不是各层随意设, 而是自上而下递减的预算
入口总预算 1s → A 用 900ms → B 用 700ms → C 用 500ms (每层 < 上游剩余, 留网络/序列化余量)
反例: 入口 1s 但 A/B/C 各设 1s ❌ 末端串行总耗时可远超 1s, 上游已超时返回, 下游仍在白跑 ❌
无超时 = 线程无限阻塞占满连接池/线程池 → 局部故障升级为全站雪崩
```

## 二、重试 + 退避 + 只重试可重试错误

```java
// 目的：瞬时故障用"指数退避 + 抖动 + 上限"重试, 且只针对可重试错误
for (int attempt = 0; attempt < MAX_RETRY; attempt++) {
    try { return call(req, budget()); }               // 说明：每次重试仍受剩余超时预算约束
    catch (TimeoutException | ServiceUnavailable e) { // 结果：仅超时/503 这类"可能自愈"的才重试
        long backoff = BASE * (1L << attempt);        // 指数: 100,200,400...
        Thread.sleep(backoff + rnd.nextInt((int) backoff / 2)); // 说明:+ 随机抖动打散重试时刻防惊群踩踏
    } catch (BusinessException e) { throw e; }        // 反例：对"余额不足"这类重试 ❌ 无意义且可能重复扣款 ❌
}
throw new giveUp();                                    // 反例：无限重试、退避不带抖动 ❌ 恢复瞬间踩踏打垮下游 ❌
```

## 三、幂等是重试的前提 + 放大效应

```text
图目的：能不能重试, 取决于幂等; 且要防重试被链路逐级放大
写操作(扣款/下单)必须幂等才能安全重试: 幂等键/去重存储/DB 唯一约束兜底(见幂等专题)
retry amplification: 入口重试3次 × 每实例又重试3次 × N 实例 → 真实打到下游的流量成倍放大
熔断协同: 连续失败到阈值快速失败、暂停重试给恢复窗口, 别让重试把熔断打穿或雪崩时放大流量
```

## 四、坑与底线

- **不幂等就别自动重试写操作**：否则网络"假失败"（其实已成功）+ 重试 = 重复扣款/重复下单，这是资金事故高发点。
- **警惕重试放大**：多层各自重试会相乘放大流量压垮下游；应只在**靠近故障源的一层**重试、其余层靠熔断快速失败，全局设重试预算。
