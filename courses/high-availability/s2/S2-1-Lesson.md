# 冗余、健康检查与故障自动转移

> 本节难度：★★★★☆
> 重要程度：★★★★★
> 学习产出：能把"消除单点 + 判活 + 自动切换"这条故障自愈主干讲清楚并落地。**冗余**是可用性的物理前提：任何单点（一台应用、一个 LB、一个 DB 主、一个 DNS）挂了就全站不可用，所以要**同层多副本 + 跨故障域分布**（多实例、多可用区/机房），且冗余要"活"——热备随时可接管，冷备演练过才敢切。**健康检查（判活）**分**主动探测**（探活端点 `/health`、Liveness/Readiness 分离、TCP/HTTP/gRPC 探针、依赖就绪性检查）与**被动观测**（真实流量的错误率/超时率滑动窗口）；关键设计：探针要区分**进程活着 ≠ 能服务**（Liveness 判是否重启、Readiness 判是否接流量），避免"半死不活却被导流"；探测要有**阈值 + 防抖**（连续 N 次失败才判死、恢复 M 次才判活）防止抖动误杀。**故障自动转移（failover）**：主从/leader 架构靠仲裁（quorum/多数派）选新主、虚拟 IP/DNS/服务注册摘除旧主、连接与流量重定向；**脑裂（split-brain）**是最大风险——网络分区让两个节点都自认主、双写破坏一致性，防御靠**多数派仲裁 + fencing token/STONITH（隔离旧主）+ 合理超时**。要认清**自动化的边界**：探测误判、抖动、多数派不可达时应倾向"保守不切/降级"而非盲目切换（错误切换比不切更致命，尤其有状态服务）；无状态服务可激进、有状态服务需谨慎。识破"只有一个主库且无自动切换""Liveness 探测太重导致 GC 暂停就被杀全站雪崩""探针无防抖被瞬时抖动反复切换""两节点集群网络分区双主脑裂""failover 后旧主未 fencing 回来双写"等坑。

## 一、冗余布局与"活的"备份

```text
图目的：可用性的物理前提——去单点 + 跨故障域 + 备份可接管
同层多副本: 应用无状态多实例、LB 双活、DB 主从、DNS 多解析
跨故障域: 实例分散到不同可用区/机房, 避免"一个机柜断电=全挂"(与故障域划分呼应)
冗余要"活": 热备随时可接管; 冷备必须演练过, 否则真故障时切不过去
```

## 二、健康检查：主动 + 被动，区分活与可服务

```java
// 目的：探针分离 Liveness(要不要重启) 与 Readiness(要不要导流), 别用一把尺子
// GET /actuator/health/liveness  -> 进程死锁/OOM 卡死才 fail, 触发重启
// GET /actuator/health/readiness -> 依赖(DB/缓存/MQ)未就绪/过载则 false, 只摘流量不重启
Readiness: if (dbPool.exhausted() || !downstream.ok()) return DOWN;  // 说明：慢或未就绪应"摘流量"而非"杀进程"
// 结果：判活/判就绪解耦, 避免一次下游抖动导致大面积误重启雪崩
// 反例：把 readiness 塞进 liveness 且无防抖 ❌ 依赖瞬时不可用就重启全部实例 ❌ 雪崩式误杀 ❌
```

## 三、自动转移与脑裂防护

```text
图目的：failover 的正确机制与"宁保守勿乱切"的边界
选主: 多数派仲裁(quorum)选新 leader; 奇数节点(3/5)才能形成多数派
摘旧: 服务注册/DNS/虚拟 IP 摘除旧主 + fencing token(旧主带过期 token 写被拒)/STONITH 隔离
脑裂: 网络分区双主双写 → 靠多数派 + fencing 防; 2 节点集群最易踩
边界: 探测抖动/多数派不可达时保守不切或降级, 错误切换比不切更致命(有状态尤甚)
```

## 四、坑与底线

- **无状态可激进、有状态要保守**：无状态实例切换风险低可快切；有状态（DB/锁/主从）错切会损坏数据，务必以一致性为先、宁降级不乱切。
- **failover 必配 fencing**：切了新主却不隔离旧主，旧主"复活"回写就是双主脑裂事故；fencing token 是兜底。
