# 开关、灰度与预案演练闭环

> 本节难度：★★★★☆
> 本节重要性：★★★★☆
> 学习产出：能把"上线不靠运气、故障靠排练"落成一套可运营的机制。**功能开关（Feature Flag）**把"部署"与"发布"解耦——代码先上线但开关关着，需要时秒级打开/关闭，无需回滚部署即可控制功能可见性，也是**降级预案的执行抓手**（下游挂了？一键关非核心功能保核心）。**灰度发布**按小流量→逐步放量（按用户/地域/百分比/白名单）验证新版本，每步观测核心指标（错误率、延迟、业务转化），异常即**快速回滚**（切开关/切流量），把"变更引发故障"的爆炸半径限制在最小比例；发布与灰度常依托网关路由/服务网格权重/多版本并行。**降级预案**是预先设计好的"出事先砍谁"：核心链路与非核心分层、每层备兜底（默认值/缓存快照/简化逻辑/静态页），降级要**可分级、可开关触发、演练验证过**。**混沌工程与预案演练闭环**：不演练的预案等于没有——定期做故障注入（杀实例/断网/加延迟，ChaosBlade/Chaos Monkey）与**预案演练、红蓝对抗、故障复盘**，把"纸面预案"逼成"真能执行且有效"；复盘用**无指责（blameless）**文化沉淀成检查项、新预案与门禁，形成"设计→演练→发现→改进→再演练"的闭环。识破"开关只增不理、留一大坟场""灰度不放量也不回滚、灰度变常态""预案从没演练过、真出事切不动/切错""降级把核心也降了""回滚粒度太粗只能全量""复盘追责不沉淀"等坑。

## 一、开关与灰度：变更风险的爆炸半径控制

```text
图目的：把"改坏了"的代价限制在最小可控范围
功能开关: 部署≠发布, 关着先上、需要时秒级开关, 也是降级的执行抓手(关非核心保核心)
灰度放量: 新版本按 1%→5%→20%→全量 递增, 每步观测错误率/延迟/转化, 异常即切回(可回滚)
回滚粒度: 切开关/切流量权重应能做到分钟级、局部, 而非只能全量重启部署
```

## 二、降级预案与演练闭环

```java
// 目的：预案要"可开关触发 + 演练验证过", 否则真出事切不动/切错
if (flags.isOn("recommendation.downgrade"))           // 说明：一键降级——推荐服务异常时关闭个性化推荐
    return fallbackCache.getOrDefault(userId, HOT_LIST); // 结果：返回兜底(热门榜/默认), 不拖垮主链路下单
return recommendationClient.get(userId, budget);       // 正常路径
// 反例：预案写了从没演练 ❌ 真故障时开关找不到/兜底数据是空的/把核心也降了 ❌
// 反例：功能开关只增不理 ❌ 半年后满屏僵尸 flag, 无人敢动 → 开关坟场 ❌
```

## 三、混沌工程与无指责复盘

```text
图目的：不演练的预案等于没有——把"纸面预案"逼成"真能执行"
故障注入: 杀实例/断网/加延迟/打满 CPU(ChaosBlade/Chaos Monkey), 主动暴露脆弱点
演练闭环: 设计预案 → 定期演练/红蓝对抗 → 发现缺口 → 改进(新开关/门禁) → 再演练
复盘文化: blameless 无指责, 聚焦系统与流程而非人, 沉淀成检查项防同类复发
```

## 四、坑与底线

- **预案必须演练**：从未验证的降级/切换预案，真故障时大概率切不动或切错，演练是给可用性上保险。
- **开关要治理、灰度要闭环**：开关要有生命周期与定期清理、避免坟场；灰度要有"放量 + 观测 + 回滚"闭环，否则灰度变无人认领的常态。
