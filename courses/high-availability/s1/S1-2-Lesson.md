# 跨技术联动：降级与熔断体系

> 本节难度：★★★★★
> 本节重要性：★★★★★
> 学习产出：能把**限流、熔断、降级、隔离、兜底、开关**这些分散的组件，组装成一套协同的"高可用防护体系"：以 Sentinel 做流量整形与熔断（慢调用/异常比触发熔断开闸），以线程池/信号量做**资源隔离**防止一个慢依赖拖垮全局，以**多级缓存/静态化**做降级兜底数据，以**开关平台（配置中心）**在故障时一键关停非核心链路。讲清熔断器三态（关闭→打开→半开）的语义与降级分层（读降级/写降级/业务降级），并能设计"预案 + 自动触发 + 手动开关"的组合；识破"没有超时的熔断等于没熔断""降级把核心写也降没了""隔离线程池参数与容量不匹配仍被拖垮""开关平台自身成为新单点"等联动坑。

## 一、一张全景图：请求穿过层层防护

```text
图目的：把散落组件按"请求路径"串成体系
入口限流(Sentinel流控) → 资源隔离(线程池/信号量) → 调用下游(超时+熔断器)
   → 熔断打开时走降级(兜底缓存/静态页/默认值) → 全局异常时开关平台关停非核心
每一层职责单一、可独立触发，也能被一个总预案统一编排
```

## 二、熔断：让失败快速失败，给下游喘息

```java
// 目的：用熔断器把"雪崩式等待"转成"快速失败+降级"
@SentinelResource(value = "queryItem", blockHandler = "onBlock", fallback = "degrade")
public Item queryItem(String id) { return rpc.call(id); }   // 说明：慢调用比例/异常比例超阈值即开闸
public Item degrade(String id, Throwable ex) {               // 结果：熔断打开走兜底——命中缓存/返回静态数据
    return cacheSnapshot(id);                                // 半开窗口放探测流量，成功则闭合，失败再打开
}
// 反例：远程调用不设超时，熔断器永远等不到"失败"信号 ❌ 线程被慢调用耗尽，熔断形同虚设
// 反例：把下单主流程也配成"失败即降级返回成功" ❌ 数据没写却说成功，降级把正确性也降没了
```

## 三、隔离：一个慢依赖不能拖垮整台机器

```text
图目的：舱壁思想，把不同依赖关进各自的池
线程池隔离：每个下游独占线程池，池满只拒该类请求，其他链路照常（Hystrix 式）
信号量隔离：轻量计数限并发，无额外线程切换，适合快速返回的调用
Sentinel 并发线程数限流：按资源统计并发，超阈值走流控效果（快速失败/预热/排队）
关键：隔离池大小要按压测匹配下游 RT 与并发，配错仍会被拖垮或浪费
```

## 四、降级分层与开关平台

- 降级分层：**读降级**（走缓存/静态/默认值，代价低）→ **业务降级**（关闭推荐、简化风控）→ **写降级**（转异步/暂存待补，风险最高须谨慎）。
- 开关平台：用配置中心（Nacos/Apollo）维护降级开关，故障时**一键关停**非核心链路，把容量与依赖让给核心交易；预案平时演练、开关可灰度可回滚。
- 组合拳：自动（熔断器按阈值自开自闭）+ 手动（开关应对预期外大故障）+ 预案（书面化的降级顺序与责任人）。

## 五、联动要点与坑

- 熔断依赖超时：没有合理的调用超时，异常/慢调用比例统计不出来，熔断永不触发。
- 降级要保正确性：可对"读"降级，但对"核心写/资金"绝不能假装成功，宁可明确失败或排队补偿。
- 开关平台自身要 HA：它若挂在同一故障域，故障时想关开关却发现它也宕机，反成新单点。
