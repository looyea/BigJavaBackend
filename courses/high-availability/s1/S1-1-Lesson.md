# SLA 拆解与故障域划分

> 本节难度：★★★★☆
> 重要程度：★★★★★
> 学习产出：能把一句"我们要做到 99.99%"落成可执行的工程预算——讲清 **SLA/SLI/SLO 与错误预算**的数学（四个 9 = 每月约 26 分钟不可用），会用**串联相乘、并联取冗**把整体可用性目标拆到每一层（接入/网关/服务/缓存/DB），识别并消除**单点**；能划分**故障域**（进程→单机→机架→可用区→地域）并据此设计多可用区部署，理解"故障域越大、爆炸半径越大、发生概率越低但影响越广"的取舍；识破"只在同机房做主备却号称高可用""冗余副本同生共死于一个故障域（同源故障）""SLA 目标定了却没往下拆到预算与演练"等伪高可用。

## 一、把"99.99%"变成预算：SLA / SLI / SLO

```text
图目的：可用性不是一个口号，是一笔可花的 downtime 预算
SLI：实际度量指标（如成功请求数/总请求数、P99 延迟达标率）
SLO：内部目标（如 30 天内 99.99% 请求成功）；SLA：对外承诺，违约有赔偿
错误预算(Burn Rate)：1-99.99%=0.01% → 30天×24h×60min×0.01% ≈ 4.3 分钟/月可宕
几个 9 的数量级：99.9%≈43min/月，99.99%≈4.3min/月，99.999%≈26s/月
```

- 预算思维的价值：当错误预算快烧完，就该**冻结高风险变更**；预算是发布节奏与稳定性的调节阀，而不是事后甩锅指标。

## 二、把目标拆到每层：串联相乘、并联取冗

```text
图目的：整体可用性由链路各层共同决定，拆解才知道钱花在哪
串联（依赖叠加）：A→B→C 全成才算成功，可用性≈各层相乘 0.999×0.999×0.999≈0.997
并联（冗余备份）：主+备任一存活即可用，可用性≈1-(1-p)² 远高于单层
推论：链越长相乘越低 → 要么砍依赖、要么给关键依赖加冗余/降级
预算分配：给每层定 SLO（接入99.99/服务99.95/DB99.99），逐层兜底而非笼统承诺
```

```java
// 目的：识别链路上的"单点"并决定是否值得为它加冗余或降级
Result r = call(downstream);                 // 说明：若 downstream 是串联单点，它的宕机=整条链宕机
if (r.failed()) {
    return fallbackFromCache();              // 结果：把强依赖降级为弱依赖，用冗余(缓存/兜底)抬升该层可用率
}
// 反例：核心交易链强依赖一个非核心推荐服务，推荐挂则下单挂 ❌ 长串联未斩断
// 反例：只做同机房主备却称高可用，一次机柜断电主备同灭 ❌ 主备在同一故障域=伪冗余
```

## 三、故障域划分：控制爆炸半径

```text
图目的：故障域=一次故障能波及的最大范围
进程/容器 → 单机 → 机架(共享供电/接入交换) → 可用区(AZ,独立电力网络) → 地域(Region)
规律：域越大 发生概率越低 但爆炸半径越大；高可用=把副本/主备撒进不同故障域
同源故障(Common Mode)：多副本看似冗余，却共享同一开关/同一版本 Bug/同一配置推送 → 一起挂
```

- 多可用区部署：应用无状态多副本跨 AZ + 负载均衡；有状态做跨 AZ 主从/多数派（如 DB 三节点分布三个 AZ，任一 AZ 挂仍有法定多数）。
- 反例警戒：主从都在一个 AZ、备份与生产同存储、所有实例同一镜像版本缺陷——都是"冗余但同故障域/同源"的伪高可用。

## 四、落地清单

- 先测后设：用 SLI 真实度量当前可用性，再定能兑现的 SLO/SLA，别拍脑袋承诺四个 9。
- 画依赖图找单点：串联越长越危险，砍非核心依赖、强依赖降级为弱依赖。
- 副本跨故障域 + 防同源：跨 AZ 部署，且隔离版本/配置/发布，避免一次变更全灭。
