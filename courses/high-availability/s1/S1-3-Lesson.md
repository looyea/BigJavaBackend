# 单元化与异地多活、容量与演练

> 本节难度：★★★★★
> 重要程度：★★★★★
> 学习产出：能把高可用从"单机房冗余"推进到"地理级容灾 + 常态化验证"：讲清**单元化**（Unit-Based / 分而治之，按用户维度把"接入+应用+数据"封装成自包含的**单元**，单元内闭环、跨单元尽量少调用，用**单元路由/标**分流）与它如何支撑**异地多活**（多地域同时承接流量，故障时把某单元流量快速切到其它单元）；理解同城双活→两地三中心→异地多活的演进与其**数据一致性与冲突**代价（分片维度选用户ID、跨地域复制延迟、双向同步防循环）；能用**容量规划 + 全链路压测**把"能不能扛"变成数字，用**混沌工程/故障演练**（宕机、网络分区、依赖劣化、切流演练）持续验证预案不是纸面文章。识破"单元不封闭导致跨单元风暴""多活把简单问题复杂化、为 0.01% 可用性过度设计""压测用生产数据污染真实库""预案从没演练过真出事切不动"等坑。

## 一、单元化：把系统切成自包含的"块"

```text
图目的：单元化是异地多活的地基，先能拆才能手切流量
单元(Unit)：按路由标(如用户ID取模/分段)划分的自包含闭环，含接入+应用+存储
封闭性：一个用户的请求尽量只在本单元内完成，跨单元调用要少且可控
单元路由标：入口按 userId 打标签 → 路由层据此把请求送到该用户所属单元
收益：单元即故障隔离边界，一个单元坏了只影响其用户段，切流=改路由权重
```

- 关键取舍：**分片维度**要选得让业务尽量在单元内闭环（多用 userId），避免订单/库存这类需要全局协调的走跨单元；全局数据（如商品详情）另设只读的全局单元/缓存广播。

## 二、异地多活：地理级容灾与它的代价

```text
图目的：多活不是复制粘贴机房，而是直面数据一致性
演进阶梯：单机 → 同城主备 → 同城双活 → 两地三中心 → 异地多活(单元化)
核心难点：跨地域复制延迟(ms级 RTT) → 就近读写要接受最终一致/冲突合并
数据分片：按单元维度分片各写各的；全局/低频数据用单向同步；双向同步需防循环与冲突
切流：故障时把某单元流量路由到健康单元，RTO/RPO 由复制方式与预案决定
```

- 冷静判断：异地多活成本极高（改造、一致性、运维复杂度），是为**业务连续性 + 超大流量地理分摊**服务的；多数系统"同城双活 + 异地冷备/两地三中心"已足够，别为用不上的 99.999% 过度设计。

## 三、容量规划与全链路压测：把"能不能扛"变成数字

```java
// 目的：用压测建立"容量水位线"，让限流阈值和扩缩容有据可依
// 说明：全链路压测用影子库/影子表 + 流量打标，隔离压测数据与真实数据
LoadTest.markTrafficShadow(req);            // 结果：打上压测标，落影子表，避免污染生产订单/账务
int capacity = stressTest.maxTpsAt(p99Sla); // 说明：在满足 P99 SLA 前提下的最大吞吐=容量水位
gateway.setRateLimit(capacity * 8 / 10);    // 说明：限流阈值设在容量的 80%，留缓冲给突发与抖动
// 反例：压测不打标、不隔离，直接写生产库 ❌ 制造海量脏数据甚至真实扣款
// 反例：只压单接口不做全链路 ❌ 高并发下瓶颈常在被忽略的下游/DB，单点压测结论失真
```

## 四、混沌工程与演练：让预案"平时就灵"

- 常态化演练：主动注入故障（杀节点、断网络、加延迟、依赖劣化），验证**熔断/降级/切流**真能兜住，而不是等真出事才发现开关失灵。
- 切流演练：定期把单元流量整体切换并回切，把"改路由权重"变成肌肉记忆，量化 RTO。
- 闭环：演练 → 暴露问题 → 修预案/加监控 → 再演练；故障复盘产出可验证的改进项而非检讨书。
