# 反序列化、越权与业务逻辑漏洞 · 作业

## 作业 1：给一段原生反序列化上白名单

- **目标**：用 ObjectInputFilter 把危险的 readObject 入口收敛。
- **任务**：写一个从字节流反序列化 Order 的方法，先用无限制版本演示可被构造流触发（用无害 gadget 说明原理即可，勿引入真实 exploit），再加 `ObjectInputFilter` 白名单（只放行 `com.acme.dto.*;!*`），断言非白名单类被拒。
- **验收标准**：白名单版本对合法 Order 正常、对可疑类抛 `InvalidClassException`；说明为何"默认拒绝 !*"是过滤生效的前提。
- **参考解法要点**：优先建议换 JSON（见 [课文](S1-3-Lesson.md) 第一节正解一）；对照 [MyBatis 结果映射](../../mybatis/s1/S1-1-Lesson.md) 为何不用 Java 原生序列化。

## 作业 2：水平越权统一拦截

- **目标**：把"归属校验"从散落 if 收敛为数据层强制条件。
- **任务**：用 MyBatis 拦截器给带 `@DataScope` 的查询自动追加 `owner_id = 当前用户`（或 `tenant_id IN (...)`）；写越权用例：用户 A 用自己的会话请求 `GET /orders/{B的订单id}`，断言返回空/404 而非 B 的数据。
- **验收标准**：不加注解的接口不受影响；加注解后越权查询命中 0 行；全局搜 `findById(` 无裸查（或已补归属）。
- **参考解法要点**：数据权限下推与 [认证授权模型与权限设计](../../spring-security/s1/S1-2-Lesson.md) 同源；返回 404 避免存在性泄漏。

## 作业 3：优惠券并发双花修复（编码）

- **目标**：消灭"查了再改"的 TOCTOU 竞态。
- **任务**：复现"同券并发核销两次成功"（线程池打两台并发请求 + select 判断 update 的旧写法），改为带条件原子 UPDATE（`... WHERE id=? AND status='UNUSED'`）后用 affected rows 判定；用唯一流水表兜底幂等。
- **验收标准**：并发 50 次仅 1 次成功、其余得"券已核销"；重复请求命中幂等键不二次扣；贴出压测结果。
- **参考解法要点**：库存超卖同法（条件扣减），延伸见 [下单链路与库存扣减](../../ecommerce/s1/S1-1-Lesson.md) 与 [重复请求的四类解法](../../idempotent/s1/S1-1-Lesson.md)。
