# 注入原理与预处理防御 · 面试题

## 题 1：SQL 注入的原理是什么？为什么转义单引号不够？

- 原理：拼接让外部输入在 SQL 解析阶段被当成语法，改变了语句结构（数据当代码）。
- 转义单引号是黑名单思路：大小写、注释符、编码、宽字节、二阶注入等绕过无穷。
- 根治是参数化：编译与取值分离，参数永远只作值不作语法。
- 加分：点明"危险不在特殊字符本身，而在参与了解析"，能举 `admin' --` 绕过登录说明结构被改。

## 题 2：MyBatis 的 `#{}` 和 `${}` 有什么区别？什么时候不得不用 `${}`？

- `#{}` 生成 JDBC `?` 占位符走参数通道，防注入；`${}` 是字符串直插 SQL 文本，有注入面。
- 不得不用 `${}`：动态表名/列名/ORDER BY 方向——这些结构位置 `?` 无法替换（会语法错）。
- 关键：`${}` 出现处必须自己上白名单，绝不能把前端原始输入直插。
- 加分：`<if>`/`<foreach>` 里的 `LIKE`、`IN` 也常被 `${}` 误用，正解是 `CONCAT(#{},'%')`、foreach 逐个 `#{}`。

## 题 3：动态 ORDER BY 列名怎么防注入？

- 白名单枚举：后端定义"可排序列集合"，不在其中直接拒绝，绝不用用户输入拼列名。
- 方向同样枚举 asc/desc，非法回默认。
- 反面：`replace("--","")`、过滤 union 等黑名单，编码/嵌套即破。
- 加分：能写"列名→真实列"的 Map 映射，既防注入又能屏蔽物理列名暴露。

## 题 4：除了 SQL 注入，还有哪些"同类"注入？

- 命令注入：拼进 shell/`Runtime.exec` → 参数数组传参不拼串。
- NoSQL 注入：查询对象直吃前端 JSON（`$ne`/`$where`）→ 校验类型只取白名单字段。
- 路径穿越：`base + userPath` 未规范化 → canonical 后校验仍在 base 下。
- LDAP / 模板 / 反序列化注入：本质都是"输入进了会解析语法的引擎"。
- 加分：提出"二阶注入"——入库安全但取出后再拼接发作，防御要覆盖每次使用，不止入口。

## 题 5："前端已经做了校验"能防注入吗？

- 不能。前端校验是体验，攻击者可绕过后端直发请求（改包、关 JS）。
- 服务端是唯一信任边界，必须重复校验：类型、长度、格式、白名单。
- 加分：能顺势讲"藏按钮≠鉴权、参数化≠不校验业务范围"，安全分层，越权防线见 [反序列化、越权与业务逻辑漏洞](S1-3-Lesson.md)。

## 题 6：ORM 都参数化了，是不是就没有注入风险了？

- 大幅降低但非归零：原生 SQL 片段、`${}`/`$` 拼接、JPQL/HQL 字符串拼接、nativeQuery 仍可注入。
- 动态结构（表名、排序、模糊匹配）常绕过参数化通道。
- NoSQL/搜索（ES query_string）等"非关系型"入口不在 ORM 保护范围。
- 加分：给出 CI 防线——静态扫描搜字符串拼 SQL 模式 + 危险 API（`Statement`、`createNativeQuery` 拼接）告警，把防注入固化进流水线。
