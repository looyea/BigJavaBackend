# 反序列化、越权与业务逻辑漏洞 · 面试题

## 题 1：为什么 Java 反序列化容易出 RCE？怎么防？

- 原因：`readObject` 按流中类元数据重建对象并执行其方法链，classpath 上存在 gadget（如 commons-collections）时可被串成任意代码执行。
- 信任边界：只要反序列化的字节流来自不可信来源（网络/Cookie/MQ/RMI），就等同把"对象重建指令"交给攻击者。
- 防：优先换 JSON/Protobuf 等数据格式；必须用原生序列化时设 `ObjectInputFilter` 白名单且默认拒绝、移除有 gadget 依赖、隔离 RMI/JNDI 入口。
- 加分：点出 JNDI/log4j 注入是"不可信输入触发远程类加载"的同源问题。

## 题 2：水平越权和垂直越权分别怎么测、怎么防？

- 水平：同权限跨用户数据（改 id 看别人单），测法是换/改资源标识；防在归属校验（owner/tenant）下推为数据访问层统一条件。
- 垂直：低权限调用高权限功能（普通用户打管理员接口），测法是直接调被"藏起来"的入口；防在链上鉴权 + 方法注解双层。
- 关键：前端隐藏入口不是安全，任何入口都要能回答"直接调会怎样"。
- 加分：查不到时返回 404 而非 403，避免泄漏"该资源存在"的存在性信息。

## 题 3：为什么说"给每个接口写个 if 判断归属"不够好？

- 依赖每个人每次都记得写，一处遗漏即破防，不可审计、不可回归。
- 收敛方案：AOP/MyBatis 拦截器统一注入归属条件，或查询方法强制带 ownerId，让"忘记"在编译/框架层就发生不了。
- 加分：与数据权限下推同源——把横切的安全约束交给框架，不交给个体自觉，参见 [认证授权模型与权限设计](../../spring-security/s1/S1-2-Lesson.md)。

## 题 4：优惠券/库存这类"并发被薅"漏洞的根因与解法？

- 根因：check-then-act（TOCTOU）——先查后改，两请求都通过校验。
- 解法：把判断下推进带条件的原子 UPDATE（`WHERE status='UNUSED'`/`stock>=n`），用 affected rows 判成败；加唯一流水/幂等键防重放。
- 集群下更稳：DB 条件更新或分布式锁/Redis 原子扣减，单机 synchronized 不管用。
- 加分：库存超卖与券双花是同一模式的两个业务面，能统一成"不变式 + 原子 + 幂等"三件套。

## 题 5：业务逻辑漏洞为什么扫不出来？该靠什么防？

- 扫描器靠特征码/异常响应，而逻辑漏洞用的是"合法请求、合法参数类型"，只是滥用了业务流程。
- 防在设计期威胁建模：对每条流程问"攻击者会怎么绕/复用/并发/改值薅"，把规则写成服务端不变式。
- 关键约束：金额/数量服务端重算不信前端、状态机原子流转、幂等防重放、频控防脚本。
- 加分：配合越权用例回归 + 资损对账兜底，即便被薅也能事后发现，形成闭环。

## 题 6：如何系统性地对一个老 Java Web 项目做"这三类漏洞"体检？

- 反序列化：全局搜 `readObject`、`ObjectInputStream`、MQ/Redis 序列化配置、有 gadget 依赖版本。
- 越权：枚举所有"按 id 读改"接口，核对归属校验；用低权账号重放高权接口验垂直越权。
- 逻辑：拉出支付/库存/优惠券/验证码流程做滥用清单，检查是否服务端裁决、是否原子、是否幂等。
- 加分：把三类做成 CI 静态规则 + 越权自动化用例（不同身份互打），一次体检长期防回归。
