# 安全开发生命周期与依赖漏洞治理

> 本节难度：★★★☆☆
> 本节重要性：★★★★☆
> 学习产出：能把"安全"从上线前的一次性扫描，变成贯穿研发全流程的工程能力（SDL/DevSecOps），并对第三方依赖漏洞建立可运转的治理与应急机制。**SDL（安全开发生命周期）**把安全活动嵌入每个阶段：需求期定安全基线/合规要求，设计期做**威胁建模（STRIDE：欺骗/篡改/抵赖/信息泄露/拒绝服务/提权）**枚举资产、入口、信任边界与滥用路径，编码期靠**安全编码规范 + Code Review + SAST**，测试期上 **DAST/IAST + 模糊测试**，发布期做安全门禁与渗透，运行期持续监控与应急响应。**扫描工具分工**：**SAST**（静态，扫源码找注入/硬编码密钥等，左移到 IDE/CI）、**DAST**（动态，跑起来对运行态黑盒打）、**SCA**（软件成分分析，扫依赖树比对 CVE 库、看许可证合规、传递依赖）。**依赖漏洞治理**是本项目最现实的痛：现代 Java 应用几百个 jar，一个 `log4shell`（Log4j2 JNDI 注入，CVE-2021-44228）级漏洞波及全生态。治理闭环：用 SCA（OWASP dependency-check、`versions-maven-plugin`、黑鸭/Snyko）在 CI 生成 **SBOM（软件物料清单）** → 命中高危 CVE 阻断流水线 → 升级修复或**缓解（如删 `JndiLookup` 类、设 `formatMsgNoLookups=true`）** → 内部漏洞库/情报订阅。**应急响应流程**：发现→影响面盘点（哪些服务用了该组件哪个版本）→分级→缓解优先→修复排期→验证→复盘沉淀。识破"只在上线前扫一次""依赖树不看传递依赖""等官方补丁期间没有缓解预案""SBOM 缺失导致应急响应时连影响面都盘不清""把工具报警当结论不复核"等坑。

## 一、SDL 各阶段的安全活动

```text
图目的：安全左移——每个阶段都有动作, 不是上线前一把梭
需求: 安全/合规基线(等保/GDPR)、数据分级
设计: 威胁建模 STRIDE(资产→入口→信任边界→滥用路径), 早识别高危设计
编码: 安全编码规范 + Code Review + SAST(IDE/CI 即时反馈)
测试: DAST/IAST 动态黑盒 + 模糊测试 + 渗透
发布/运行: 安全门禁 + 持续监控 + 应急响应 + 复盘
```

## 二、SAST / DAST / SCA 各司其职

```text
图目的：三类扫描覆盖不同层面, 互补不可替代
SAST: 扫源码——注入/硬编码密钥/危险 API, 左移到提交前
DAST: 打运行态——黑盒, 不看代码, 抓配置与逻辑问题
SCA : 扫依赖——比对 CVE 库、许可证合规、含传递依赖, 出 SBOM
```

## 三、依赖漏洞治理与 Log4Shell 应急

```bash
# 目的：把依赖漏洞扫描做成 CI 门禁, 命中高危即阻断发布
mvn org.owasp:dependency-check-maven:check \
    --failBuildOnCVSS 7                          # 说明：CVSS≥7 的高危直接让流水线红, 阻断带毒上线
# 结果：生成 SBOM(软件物料清单)——应急时才能秒级盘出"谁用了 log4j2 哪个版本"
# 反例：只在发版前手扫一次 ❌ 新 CVE 是持续爆出的, 快照当天就过期 ❌ 必须每次构建常态化扫
# 缓解示例(Log4Shell): 升级 2.17+; 临时: 删 JndiLookup 类 或 设 -Dlog4j2.formatMsgNoLookups=true
```

## 四、坑与底线

- **SBOM 是应急响应的前提**：没有物料清单，出事时连"影响面有多大、哪些服务在用"都盘不清，只能盲猜。
- **缓解优先于等待**：高危 0day 时先上临时缓解（关特性/删类/WAF 规则/网络隔离）争取时间，再排期彻底升级，别干等官方补丁。
