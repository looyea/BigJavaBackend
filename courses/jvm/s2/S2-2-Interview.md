# 实际面试题 · G1 / ZGC / Shenandoah

> 收录 2024—2026 国内中大厂 Java 后端真实面试，含追问链。答题要展示"你知道机制的边界与取舍"，而不是背收集器名字。

## 题 1：线上服务让你选 GC，你怎么选？

**期望时长**：2 分钟

**答题要点**：

- 先问业务要**吞吐**还是要**低停顿**，再看**堆规模**与**JDK 版本/发行版**。
- 通用在线微服务（几 G~几十 G 堆、要可预测停顿）→ **G1**（JDK 9+ 默认，多数 Spring Boot 的正确答案）。
- 大堆 + 延迟极敏感（撮合、实时风控、内存级缓存，TB 级）→ **ZGC**（亚毫秒、与堆大小无关）。
- 追吞吐的离线批处理 / 小堆 → **Parallel**。

**追问链**：

1. 为什么不无脑上 ZGC？→ 读屏障降吞吐、着色指针 + 多重映射更吃内存和 CPU，小堆/成本敏感场景反而不如 G1/Parallel。
2. Shenandoah 呢？→ 也是并发整理低延迟，但只在 OpenJDK 构建，Oracle JDK 不含，选型先看发行版。

## 题 2：G1 是怎么做到"可预测停顿"的？

**答题要点**：

- 堆切成 Region，逻辑分 Eden/Survivor/Old/Humongous。
- 维护每个 Region 的回收价值（垃圾多少、回收成本），按 `-XX:MaxGCPauseMillis` 软目标挑选一轮回收的 Region 集合，优先收垃圾最多的（Garbage-First）。
- 跨 Region 引用靠 **RSet + 写屏障**，避免全堆扫描。

**追问链**：

1. `MaxGCPauseMillis` 设越小越好吗？→ 不是，太小→只敢收极少 Region→回收跟不上分配→GC 更密甚至退化 Full GC。
2. G1 什么时候退化 Full GC？→ **to-space exhausted**（没有空 Region 承接晋升的存活对象），常因 IHOP 太高、堆偏小、Mixed 回收不及时。

## 题 3：CMS 为什么被移除？G1 比它强在哪？

**答题要点**：

- CMS 并发标记但用**标记-清除不整理**→碎片→大对象/晋升触发 **concurrent mode failure** 退化串行 Full GC，停顿爆炸；还浮动垃圾、CPU 敏感。JDK 9 废弃、14 移除。
- G1：Region 化 + 可预测停顿 + **复制式整理**（晋升即搬到空 Region，天然无碎片）+ 优先回收。

**追问链**：G1 也做并发标记，用什么保证并发正确性？→ **SATB 快照法**（开始标记时拍快照，标记期间删除的引用仍当存活，宁可残留），与 CMS/增量更新的"处理新增引用"思路互补。

## 题 4：ZGC 的"停顿与堆大小无关"是怎么实现的？

**答题要点**：

- **着色指针**：把标记/remapped 状态编进对象指针 spare 高位，读指针即知 GC 状态。
- **读屏障**：应用每次从堆读引用时做一小段检查，指针颜色过期就**顺手 self-healing 修正/转发**，于是标记、搬移、重映射都能与业务**并发**，STW 只剩极短根扫描。

**追问链**：

1. 代价是什么？→ 读屏障降吞吐、着色指针 + 多重映射增内存与 CPU、更吃核。
2. JDK 21 的分代 ZGC 解决什么？→ 补上"新生代高回收率"的效率短板（`-XX:+ZGenerational`；JDK 23 起分代默认）。

## 题 5：`Unrecognized VM option` 启动失败，可能踩了什么坑？

**答题要点**：

- 用了当前 JDK/发行版**不支持或已移除**的参数：如 JDK 14+ 的 CMS 参数、Oracle JDK 上的 `-XX:+UseShenandoahGC`、老 JDK 上的 `-XX:+ZGenerational`。
- 或参数拼写/未解锁（实验性参数缺 `-XX:+UnlockExperimentalVMOptions`）。

**追问链**：升级 JDK 后 GC 行为大变怎么排查？→ 默认收集器可能变（8 Parallel→9+ G1）、CMS 被移除、分代 ZGC 引入；用 `-Xlog:gc*` 重新压测对比停顿与吞吐，别沿用旧参数模板。
