# 小测验 · 堆转储分析与内存泄漏定位

> 本卷共 6 题，混合单选 / 多选 / 判断 / 填空 / 简答，满分 100 分折算百分制，≥ 60 分过关。

### 1. 定位内存泄漏时，MAT 里更该看哪个指标？（15分）

- A. Shallow Heap，因为它统计对象自身大小最准
- B. Retained Heap，因为它代表"回收该对象能一并释放的总内存"
- C. 对象地址
- D. 类加载器编号

> 答案：B
> 解析：泄漏的本质是"某持有者拽着一大片对象不放"。Retained Heap 衡量"删掉它能释放多少"，支配树按它排序能直接揪出真凶；Shallow 只是对象自身字节，一个几十字节的静态 Map 可能 Retained 好几 G。

### 2. 追踪泄漏对象"为什么还活着"时，Path to GC Roots 要排除弱/软/虚引用，原因是？（15分）

- A. 弱/软引用会拖慢 MAT 解析
- B. 弱/软/虚引用不是让对象"必须存活"的原因，排除后剩下的强引用链才是真凶路径
- C. MAT 不支持显示弱引用
- D. GC Roots 只认软引用

> 答案：B
> 解析：让对象"不可回收"的是强引用链。弱/软/虚不构成存活理由（呼应 s2-1），排除它们才能把根因锁定到真正的强引用持有者（如静态字段、集合元素）。

### 3. 【多选】下列哪些是 Java 高频内存泄漏现场？（20分）

- A. 静态 `Map/List` 无界增长、只 put 不 evict
- B. ThreadLocal 用完不 `remove()`，线程池核心线程长期存活
- C. 监听器/回调注册后不注销，拽着大对象不放
- D. 用 try-with-resources 正确关闭流

> 答案：ABC
> 解析：A/B/C 分别是"无界缓存/静态集合、不 remove 的 ThreadLocal、不注销的监听器"三大泄漏现场，本质都是对象仍挂在通向 GC Root 的强引用链上。D 是**正确做法**（资源被规范关闭），不泄漏。

### 4. 判断：想分析"包括尚未回收的临时对象在内"的完整现场，就应使用 `jmap -dump:live`。（10分）

- A. 正确
- B. 错误

> 答案：B
> 解析：`:live` 会**先触发一次 Full GC**、只导出存活对象，既扰动现场又丢掉临时对象信息。要分析含临时的完整现场应**不加 live**；且任何 dump 都会 STW，大堆要摘流量。

### 5. 填空题：MAT 里按类聚合实例数与大小、适合先看"类型分布"的视图是 ______；自动给出"Top 可疑占内存对象 + 占比"的启发式报告是 ______。（20分）

> 答案：Histogram（类直方图） / Leak Suspects（泄漏疑犯报告）

### 6. 只有一张堆 dump 时难以确认某业务对象是否泄漏，说出更可靠的判定手法与完整 MAT 分析主线。（20分）

> 参考答案：
> - 手法：间隔一段时间、负载相似时抓两张 dump，做 Histogram 差分，按实例数/Retained 增量 Δ 排序，Δ 持续为正的类即嫌疑
> - 主线四步：Leak Suspects 报告 → Dominator Tree 按 Retained 找"自身小、Retained 巨大"的持有者 → Histogram 看类型分布 → 对可疑对象 Path to GC Roots（排除弱/软）定位到代码行
> - 结论落地：确认是无界缓存/静态集合/ThreadLocal/监听器等哪一类，再按"上限+过期、remove、成对注销、try-with-resources"修复
