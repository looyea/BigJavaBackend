# 实际面试题 · 锁优化与无锁并发

> 收录 2024—2026 国内中大厂 Java 后端真实面试，含追问链。答题要展示"你知道机制的边界"，而不是背名词。

## 题 1：一个高并发接口 P99 很高，怀疑是锁问题，你怎么优化？

**期望时长**：2 分钟

**答题要点**：

- 先定位是不是真锁竞争（火焰图 / `jstack` 看 BLOCKED、`-XX:+UnlockDiagnosticVMOptions` 看争用）。
- 四条路按优先级：**无锁 > 缩小临界区 > 分段降粒度 > 读写分离**。
- 先做"缩小临界区"（把 IO/new/日志移出同步块），往往一把梭解决。

**追问链**：

1. 什么是"分段"，举个 JDK 例子？→ `ConcurrentHashMap` 的 Segment（7）/ 桶级锁（8）、`LongAdder` 的 Cell[]，本质都是把单点竞争摊到多把锁/多地址上。
2. 分段会不会有代价？→ 内存更多、聚合（sum）有最终一致延迟、锁对象管理复杂；段数要按并发度调，太多反而缓存不友好。

## 题 2：LongAdder 为什么比 AtomicLong 快？什么时候反而该用 AtomicLong？

**答题要点**：

- `AtomicLong` 所有线程 CAS 同一 value，高竞争失败自旋 + 缓存行核间来回失效。
- `LongAdder` 分散到 Cell[]，各线程 CAS 不同地址，`sum = base + ΣCell`。
- 需要"读取即时精确值 + 基于当前值做原子比较更新（CAS 循环改余额）"时用 `AtomicLong`，因为 `LongAdder.sum()` 只是近似快照。

**追问链**：`LongAdder` 的 Cell 为什么标 `@Contended`？→ 避免相邻 Cell 伪共享同一缓存行，让"分散"真正生效。

## 题 3：什么是伪共享？怎么解决？有什么注意事项？

**答题要点**：

- 逻辑独立变量落在同一缓存行（约 64B），一核写使另一核同行副本失效，互相拖慢。
- 解决：`@Contended` 填充隔离，或手动 padding。
- 注意：只在**确证的热点竞争字段**上用，滥用导致内存膨胀；对外部类需 `-XX:-RestrictContended`。

**追问链**：为什么 `AtomicLong[]` 手工分段有时更慢？→ 数组元素紧挨着、落同一行，伪共享抵消了分段收益，正该 padding/`@Contended`。

## 题 4：读写锁和 StampedLock 怎么选？写饥饿怎么回事？

**答题要点**：

- `ReentrantReadWriteLock`：读读并行、读写/写写互斥，可重入，支持锁降级。
- 写饥饿：读者源源不断，等待的写者长期拿不到写锁（读优先调度下）。
- `StampedLock`：多一种**乐观读**（不加锁，读完 `validate` 校验），读更密集时吞吐更高；但**不可重入、中断处理要小心**、API 是 stamp 需正确 unlock。

**追问链**：乐观读能省锁为什么不默认全用它？→ 它只保证"校验通过才可信"，读后要 validate 且可能退化重读；写频繁时乐观读常失败，收益不明显还增复杂度。

## 题 5：讲讲无锁队列/栈的思想，ABA 怎么处理？lock-free 等于不会饿死吗？

**答题要点**：

- 无锁靠 CAS 循环 + 数据结构：Treiber 栈（CAS 换 head）、Michael-Scott 队列（head/tail 原子引用 + helping）。
- ABA：CAS 只看值相等，中间被改回原值会误判成功 → 用 `AtomicStampedReference`（版本随值一起比）或 `AtomicMarkableReference`。
- lock-free 只保证"系统整体有进展"，单线程可能反复失败饿死；保证每操作有限步的是 wait-free。

**追问链**：激烈竞争下无锁一定快吗？→ 不一定，CAS 失败率飙升时空转重试可能比一把分段锁还慢——无锁把"阻塞代价"换成"重试代价"，竞争太集中时后者失控。
