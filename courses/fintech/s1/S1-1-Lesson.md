# 核心账务与复式记账模型

> 本节难度：★★★★★
> 本节重要性：★★★★★
> 学习产出：能设计金融级**账务核心**：用**会计科目体系**（资产/负债/权益/收入/费用，树状科目 + 内部户/备付金/手续费等）刻画资金状态，用**复式记账**（"有借必有贷、借贷必相等"）把每一笔业务拆成**至少两条平衡的分录**，从而让"钱从哪来、到哪去"全程可追溯、可自证平；理解**账户余额 = 流水累计**、**明细账↔总账**双轨核对、**日切**（营业日切换、批量记账与结转）的时序；掌握账务与业务解耦（交易触发**会计事件**→生成**分录**落账）的分层，以及**热点账户**（平台备付金/商户收入户被高频记账）的合并/异步入账优化。识破"单式记账只改余额无法对账""借贷不平却强行入账""用浮点存金额导致分位差错""余额直接 UPDATE 不留流水无法审计""热点账户单行 update 排队压垮吞吐"等坑。

## 一、复式记账：让每笔交易自证平衡

```text
图目的：不记"结果"，记"资金的来与去"两条腿
不变式：任一分录集 Σ借 = Σ贷；账户余额只是流水的物化视图
例：用户充值 100 元进备付金 → 借:用户可用余额100 贷:平台备付金(银行)100
好处：任何一笔都能双向追溯、可轧差、可自证平，天然支撑对账与审计
```

```java
// 目的：一次业务生成一组"借贷必相等"的分录，不平则拒绝入账
void post(AccountingEvent ev) {
    List<Entry> entries = ruleEngine.buildEntries(ev);        // 说明：按科目规则把业务翻译成借/贷分录
    long debit  = entries.stream().filter(Entry::isDebit).mapToLong(Entry::amtInCents).sum(); // 结果：金额用整数分
    long credit = entries.stream().filter(Entry::isCredit).mapToLong(Entry::amtInCents).sum();
    if (debit != credit) throw new UnbalancedException();     // 异常：借贷不平拒绝，绝不强行入账
    ledger.insertAll(entries);                                // 说明：分录只增不改(append-only)，余额靠流水累计/物化
    accounts.applyDelta(entries);                             // 结果：更新受影响账户余额，与流水同事务
}
// 反例：只 UPDATE 余额不减来源 ❌ 无流水可追溯，对账/审计两眼一抹黑
// 反例：金额用 double 累加手续费 ❌ 精度漂移，长期对不平，必须整数分/Decimal
```

## 二、账户体系与余额的真相

```text
图目的：余额不是一个孤立字段，是流水的累计
科目树：资产/负债/权益/收入/费用，内部户挂在其下(备付金、待清算、手续费收入)
余额 = 期初 + Σ借 − Σ贷(按科目方向)：可全量重算校验，也可增量物化
明细账↔总账：逐笔明细汇总必须等于总账发生额，双轨核对定位差错
```

- 账务与业务解耦：业务侧只发**会计事件**(充值/消费/退款/分账)，账务侧按**记账规则**生成分录；新业务尽量靠"配置记账规则"而非改账本内核。

## 三、日切与热点账户

```text
图目的：账务有"营业日"概念，还要顶住高频记账热点
日切：到切换点停止当日记账→结转/试算平衡(全账 Σ借=Σ贷)→开启新营业日；跨切点交易归属要明确
热点账户：平台备付金/头部商户收入户被海量分录高频 update 同一行 → 行锁排队成吞吐瓶颈
优化：热点户"明细先落、余额增量累加 + 定期合并快照"，或按子账户打散汇总（承高并发写热点治理）
```

## 四、坑与底线

- **append-only**：分录只追加、冲正用反向分录，绝不物理改历史，保证可审计与可重放。
- **同事务原子**：一组借贷分录 + 余额更新必须原子，防止"借方落了贷方没落"造成不平。
- **幂等**：同一会计事件重复投递只能入账一次（业务事件 ID 做幂等键），与账务对账联动。
