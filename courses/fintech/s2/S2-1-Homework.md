# 支付路由、风控与反欺诈 · 作业

### 作业 1：多维打分 + 故障切换的支付路由

- 目标：让渠道劣化时路由能秒级避开、恢复后灰度回流。
- 任务：实现 `route(req)`：先按限额/币种/签约过滤，剔除健康探测判为不可用的渠道，对剩余渠道按 `wSucc·近5分钟成功率 − wCost·费率 + wPrefer·偏好` 打分选最优；模拟主渠道连续失败，观察自动切到备用渠道。
- 验收标准：无可用渠道时快速失败告警而非硬扣款；主渠道被打标降级后流量自动转移；恢复后先灰度小流量回流再全量。
- 参考解法要点：健康态用滑动窗口统计失败率/超时率；切换与回流都要防抖(避免全量抖动)；严禁把渠道号写死。

### 作业 2：几十毫秒出决策的规则引擎 + 超时降级

- 目标：搭建事前/事中/事后三段闸门，且风控抖动不拖垮支付。
- 任务：给定特征(设备指纹、是否异地、短时高频计数、画像标签)，写评分卡/决策树输出风险分 → 映射放行|二次验证|拦截|转人工；对风控调用设超时(如 50ms)，超时按分档：低危放行、高危挂起转人工。构造一批正常/欺诈样本验证。
- 验收标准：正常样本低误杀、欺诈样本高拦截；风控超时时主链路不阻塞、按策略降级；决策耗时可控在几十毫秒内。
- 参考解法要点：分级处置优于"一刀切拦/放"；高频可疑走限流熔断；事后用对账数据回流调阈值。

### 作业 3：可持久化的名单库

- 目标：让名单命中 O(1) 且重启/扩容不失效。
- 任务：用 Redis Set/Bitmap 存黑/白/灰名单做命中判定，灰名单默认走验证或降额、不直接放行；名单同时落库并支持多实例同步、可重建缓存。模拟进程重启后名单仍生效。
- 验收标准：命中判定为常数级；灰名单不被当白名单放行；重启或扩容后名单从持久层重建、无失效空窗。
- 参考解法要点：Redis 作高速读、DB 作真值源；注意穿透(不存在的名单)防护；更新走版本化推送保证一致性。
