# 支付路由、风控与反欺诈

> 本节难度：★★★★★
> 本节重要性：★★★★☆
> 学习产出：能设计支付链路的**智能路由**与**实时风控**体系：路由侧按**成功率/费率/限额/渠道可用性/权重**多维打分动态选路，配**渠道健康探测**与失败自动切换、成本与成率的可调权衡；风控侧建立**事前**(准入 + 黑白灰名单 + 限额限次)、**事中**(毫秒级同步**规则引擎 + 特征**：设备指纹/地理位置/行为序列/用户画像，评分卡或决策树出放行/二次验证/拦截/人工决策)、**事后**(监控 + 对账 + 追损)三段闸门；理解**名单库**(黑/白/灰，Redis Set/Bitmap 高速命中)与**关系图谱/ML 评分**的互补；坚持风控决策**超时必须降级**(不可让风控拖垮支付主链路)、可疑高频走**限流熔断**。识破"路由硬编码、渠道故障不切换""风控误杀率过高""决策同步阻塞主链路""名单只在内存不落盘、重启即失效""灰名单直接放行"等坑。

## 一、支付路由：多维打分 + 健康探测 + 自动切换

```text
图目的：不写死渠道，按"成率×成本×可用性"动态选路
打分维度：近 N 分钟成功率、费率成本、单笔/单日限额、渠道健康态、商户指定
健康探测：定时/实时统计各渠道失败率超时率，劣化即打标"降级"，路由自动避开
故障切换：主渠道连续失败 → 熔断切备用渠道；恢复再灰度回流，避免全量抖动
```

```java
// 目的：一次支付请求选出最优可用渠道，劣化渠道自动出局
Channel route(PayRequest req) {
    List<Channel> cs = registry.eligible(req);            // 说明：先按限额/币种/商户签约过滤可选渠道
    cs.removeIf(c -> health.isDown(c));                   // 结果：健康探测判为不可用的渠道直接剔除
    if (cs.isEmpty()) throw new NoChannelException();     // 异常：无可用渠道，快速失败并告警而非硬扣款
    return cs.stream().max(Comparator.comparingDouble(c ->
        wSucc*health.succRate(c, MIN5) - wCost*c.feeRate() + wPrefer=c.preferScore())).orElseThrow(); // 成率高/成本低/偏好加权
}
// 反例：把渠道号写死进代码 ❌ 渠道故障无法秒级切换，全量支付挂死
// 反例：只按费率最低选路 ❌ 忽视成功率，钱扣了没到账，成本再低也是资损
```

## 二、实时风控：事前 / 事中 / 事后三段闸门

```text
图目的：拦截欺诈要分层，事中最难——必须在几十毫秒内出决策
事前：准入 + 黑白灰名单命中 + 限额限次(单笔/单日/月累计)
事中：特征(设备指纹/地理位置/行为序列/画像)→ 规则引擎评分卡/决策树 → 放行|二次验证|拦截|转人工
事后：交易监控 + 与账务对账 + 疑似欺诈冻结/追损
```

- **决策超时必降级**：风控服务抖动时，主支付链路不能同步死等——按风险分档"超时可放行"或"高危交易超时则挂起转人工"，绝不能让风控拖垮整条支付。

## 三、名单库与特征存储

```text
图目的：命中要 O(1)，名单既要快又要能持久恢复
黑/白/灰名单：Redis Set/Bitmap 高速判定；灰名单默认不直接放行，走验证或降额
特征：设备指纹、常用地点、行为序列(短时高频/异地突发)、画像标签，实时拼装喂规则引擎
持久化：名单与规则版本落库、多实例同步，重启/扩容不丢，避免"只在内存"
```

## 四、坑与底线

- **误杀 vs 漏放的权衡**：规则过严误伤正常用户(投诉/流失)，过松漏放欺诈(资损)——用灰度 + 分级处置(验证而非直接拦)找平衡，并持续用事后对账回流调参。
- **可疑高频限流熔断**：对短时爆发的高频请求走 Sentinel 流控与熔断，既防刷也保护下游渠道。
