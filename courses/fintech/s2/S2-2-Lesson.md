# 两地三中心、监管合规与信创

> 本节难度：★★★★★
> 本节重要性：★★★★☆
> 学习产出：能设计银行级**容灾架构**并理解其**监管与国产化约束**：讲清**两地三中心**(同城生产 + 同城灾备双中心 + 异地灾备中心)的定位与 **RPO/RTO** 取舍——同城走**同步复制**保零数据丢失、异地走**异步复制**容忍地理延迟；用**单元化(分片)**把用户/商户按单元路由、流量在单元内闭环、控制爆炸半径并支撑异地多活而非纯冷备；理解数据跨中心复制一致性与切换(故障转移、脑裂防护、回切)的工程难点。掌握**监管合规**：审计留痕不可篡改、数据本地化/不出境、等级保护、监管报送、灾备演练与应急预案的强制要求。理解**信创**(国产化替代)约束：芯片/OS/数据库/中间件替换为国产栈带来的兼容性、性能与生态落差，以及灰度双跑、平滑迁移、回退预案的落地策略。识破"把异地当同城同步、切换丢数据""单元间大量跨单元调用把多活做成大泥球""信创一刀切换、无回退""审计日志可被改"等坑。

## 一、两地三中心与 RPO/RTO 取舍

```text
图目的：三个机房各司其职，复制方式随地理距离降级
同城 A(生产) ↔ 同城 B(灾备)：同步复制，RPO≈0，距离近延迟可承受
       ↘ 异地 C(灾备)：异步复制，容忍网络延迟，RPO>0(有秒级数据窗口)
RPO=能容忍丢多少数据；RTO=能容忍停多久恢复——监管对核心系统要求极低 RPO/RTO
```

```java
// 目的：按数据重要性与地理距离选择复制策略，别把异地当同城同步
ReplicationMode pick(Site from, Site to, DataClass dc) {
    if (from.sameCity(to) && dc == CRITICAL) return SYNC;     // 说明：同城核心走同步，保 RPO≈0
    if (!from.sameCity(to)) return ASYNC;                     // 结果：跨城强制异步，同步会因地理延迟拖垮主库写入
    return SEMI_SYNC;                                         // 异常：误配"异地同步"→ 每次提交等跨千公里 RTT，主库 TPS 崩塌
}
// 反例：异地也上同步复制 ❌ 网络抖动即阻塞主链路，可用性反被"强一致"拖死
// 反例：切换脚本无脑裂防护 ❌ 双主同时写造成数据分叉，比宕机更难收拾
```

## 二、单元化：把容灾做成"多活"而非"冷备"

```text
图目的：按单元切分流量与数据，故障只影响一个单元
单元化：用户/商户按分片键路由到某单元(某中心的一组服务+数据)，请求尽量单元内闭环
跨单元：尽量少且显式(如全局唯一 ID、跨单元转账走协调)，否则多活退化成大泥球
价值：任一中心故障只损失其承载单元，其余单元照常服务——比"整站冷备"恢复快、资源不闲置
```

- 切换/回切是难点：要有**流量调度**(DNS/网关按单元切)、**数据一致性核对**与**脑裂防护**(仲裁/围栏)，回切前必须追平增量。

## 三、监管合规与信创双约束

```text
图目的：银行系统"能跑"之外还必须"合规 + 自主可控"
合规：审计留痕 append-only 不可篡改、数据本地化/不出境、等级保护、定期灾备演练与报送
信创：芯片/OS/数据库/中间件替换国产栈 → 兼容性/性能/生态落差，SQL 方言与驱动差异需适配
策略：灰度双跑(新旧并行比对) + 平滑迁移 + 随时回退，绝不一刀切全量切换
```

## 四、坑与底线

- **演练常态化**：灾备从不做切换演练=纸面容灾；真故障时才暴露数据不同步、切换脚本失效。
- **审计不可改**：合规留痕用 append-only + 存证，能自证"谁在何时做了什么"，与账务可追溯同源。
