# 能力边界与 Istio 选型（关联） · 面试题

## 题 1：Linkerd 和 Istio 的本质区别一句话？

**能力模型与复杂度预算的取舍**：Istio 是"Envoy 全量 L7 能力 + CRD 表达一切"的重平台；Linkerd 是"连接级代理 + 控制面决策 + 极简配置面"的轻平台，用放弃可扩展性换取资源与运维成本的数量级下降。

## 题 2：只用了 10% 的 Istio 功能，为什么不继续用？

三个成本在持续支付：① 每 Pod 数十 MB sidecar 的资源账单；② CRD 语义复杂带来的排障/培训成本；③ 控制面升级的高风险窗口。用不到的能力不是"免费放在那"，而是每次故障排查都要多看的嫌疑人清单。

## 题 3：Linkerd 怎么做蓝绿/金丝雀？和 Istio 的差别？

Linkerd 只有权重切分（TrafficSplit，L4 连接级），推进/回滚要配 Flagger 或 Argo Rollouts 读指标决策。Istio 可在 VS 内做按 Header 分流给开发验证、镜像流量给影子服务、多 destination 细权重（请求级）。差别本质：**请求级路由 vs 连接级切分**——gRPC/长连接场景 Linkerd 的权重迁移还滞后于连接重建。

## 题 4：mTLS 开了就等于安全了吗？

不等于。mTLS 解决"加密 + 对端身份"，默认网格内仍是**全部互通**；零信任还需要 deny-all + 显式授权（Istio AuthorizationPolicy / Linkerd 网络策略），且授权粒度两产品差异明显（principal/method 级 vs 服务可达级）。这是面试里区分"装过网格"与"懂网格"的高频题。

## 题 5：给一个电商场景的选型实答？

大促核心链路（多集群、按用户标签灰度、单元化路由）→ Istio：需要 Header 分流与镜像回放真实流量做验证。后台支撑服务（对账、报表、内部 CRUD 数百个 Pod）→ Linkerd：诉求是全量加密 + 基本遥测，sidecar 内存账单在千 Pod 规模下差出几十 GB。同一公司可以两线并行——**按命名空间分域选型**，但绝不让一个 Pod 同时挂两种代理。
