# Redisson 在 Cluster/Sentinel 下的可靠性 · 作业

### 作业 1：hash tag 让跨 key 原子操作可用

- 目标：复现 Cluster 下跨 slot 报错并用 hash tag 修复。
- 任务：对同一商品分别用无共同 tag 的 `lock:sku` 与 `stock:sku` 执行一次多 key Lua 扣减，观察 CROSS_SLOT；再改用 `seckill:{sku1}:lock` 与 `seckill:{sku1}:stock` 复测；比较 tag 过粗（全站同一个 tag）导致的 slot 倾斜。
- 验收标准：相同 tag 后 Lua 原子执行成功；能说明 tag 粒度对热点分布的影响。
- 参考解法要点：slot 由 `{}` 内子串决定；tag 让相关 key 同 slot，但过粗集中热点。

### 作业 2：模拟主从切换验证丢锁窗口

- 目标：直观感受"单点锁不保证跨故障仍唯一"。
- 任务：持有 `RLock` 期间 kill 掉 master 触发哨兵提升 slave（未同步该锁），观察新 master 上锁不存在、另一客户端可立刻获得同一把锁。
- 验收标准：能复现"旧持锁者以为仍持锁、实际新主已无锁"的双持窗口；给出幂等/唯一约束兜底方案。
- 参考解法要点：异步复制就有丢锁窗口；关键正确性不能只押在 Redis 锁上。

### 作业 3：为秒杀选一套可靠锁兜底方案

- 目标：在性能与安全之间做出可论证的选型。
- 任务：为"扣库存不超卖"设计默认方案（单点锁 + 合理 TTL + 幂等消费 + DB 库存非负/唯一约束），并针对更高安全要求分别评估 RedLock 与 ZooKeeper/etcd fencing 的成本与收益。
- 验收标准：给出"够用优先、按需升级"的分层结论，说明每层的失败模式与兜底。
- 参考解法要点：多数场景幂等 + 约束即可防超卖；RedLock 有争议、成本高；fencing token 能拒绝旧持有者写入。
