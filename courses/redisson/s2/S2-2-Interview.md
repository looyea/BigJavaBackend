# Redisson 在 Cluster/Sentinel 下的可靠性 · 面试题

## 题 1：Cluster 下用 Redisson 做跨 key 原子操作要注意什么？

- Cluster 按 key 分 16384 slot，多 key 命令/MULTI/Lua 要求所有 key 同 slot，否则 CROSS_SLOT。
- 用 hash tag `{...}` 把逻辑相关的 key 钉到同一 slot，如 `order:{user1001}:lock` 与 `:stock`。
- 加分：tag 过粗会让热点集中到少数节点，粒度要兼顾原子性与均衡。

## 题 2：主从切换会让 Redisson 的单点锁失效吗？

- 存在丢锁窗口：Sentinel/Cluster 异步复制，master 挂、slave 提升时未同步的锁可能丢失，另一客户端可重新获得。
- 单点 RLock 不是为"跨故障切换仍唯一"设计的。
- 加分：这正是 RedLock 想缓解、但要看清其代价与争议的场景。

## 题 3：看门狗能保证锁绝对安全吗？

- 不能。它只在持锁线程存活时续期，防"业务没做完锁先过期"。
- 网络分区/脑裂时旧持有者与新持有者可能并存，续期救不了"不丢"。
- 加分：锁的唯一性最终靠架构（幂等、约束、fencing），不是靠客户端续期。

## 题 4：RedLock 值不值得上？

- 它用 N 个独立 master 多数派加锁，提升切换期安全，但受时钟漂移/GC 停顿质疑，且成本、延迟更高。
- 一般互斥用单点锁 + TTL + 幂等/唯一约束兜底即可；强一致/正确性关键才考虑。
- 加分：真要防旧持有者写入，ZooKeeper/etcd 的 fencing token 往往更可靠。

## 题 5：连接层重连和"锁可靠"是一回事吗？

- 不是。连接层会感知拓扑、自动重连、命令重试，这只保证"通信恢复"。
- 锁数据是否还在取决于复制是否把那次写同步到了新主。
- 加分：把"连接自愈"与"数据/语义可靠性"分层理解，别误以为重连成功锁就一定没丢。

## 题 6：秒杀防超卖，你只靠 Redis 分布式锁放心吗？

- 不放心。锁可能因切换丢失，且 Redis 是内存态。
- 最终防超卖要靠 DB 库存非负约束 / 唯一幂等键 / 原子扣减（如 Lua 预扣 + DB 落库校验）兜底。
- 加分：锁是提效与降冲突的手段，正确性底线交给带约束的持久层——分层兜底才是稳态架构。
