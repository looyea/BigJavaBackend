# Redisson 在 Cluster/Sentinel 下的可靠性 · 小测

> 本卷满分 100 分：单选 7×6=42，多选 2×9=18，简答 1×40=40。

### 1. Cluster 下多 Key 命令/MULTI/Lua 的约束是（6分）

- A. 无约束
- B. 所有涉及的 key 必须落在同一 slot，通常用 hash tag 保证
- C. 必须跨节点
- D. 只能两个 key

> 答案：B
> 解析：Cluster 按 key 分 16384 slot，跨 slot 的多 key 原子操作会报 CROSS_SLOT；用 `{...}` hash tag 把相关 key 钉到同一 slot。

### 2. 让 "lock:user1001" 与 "stock:user1001" 能同事务执行的正确写法是（6分）

- A. 保持原样
- B. 用相同 hash tag，如 order:{user1001}:lock 与 order:{user1001}:stock
- C. 放到不同库
- D. 加随机后缀

> 答案：B
> 解析：slot 由 `{}` 内子串决定，相同 tag → 同 slot；原写法两 key 大概率落不同 slot。

### 3. Sentinel/Cluster 主从切换时，单节点 RLock 的风险是（6分）

- A. 绝无风险
- B. 异步复制下 master 挂、slave 提升时，尚未同步的锁可能丢失
- C. 锁会变成永久
- D. 会自动 RedLock

> 答案：B
> 解析：单点锁依赖数据不丢，而主从是异步复制，存在丢锁窗口——这正是 RedLock 想缓解的场景。

### 4. 关于看门狗在网络分区/脑裂时的说法正确的是（6分）

- A. 能保证全网只有一位持锁者
- B. 旧 master 与客户端失联未释放时，可能与新持锁者并存，续期解决不了"不丢"
- C. 会自动仲裁
- D. 能防时钟漂移

> 答案：B
> 解析：看门狗只解决"业务未完成锁先过期"，不能保证跨故障/分区下的唯一持有；锁安全性最终靠架构。

### 5. RedLock 的定位与争议是（6分）

- A. 完全无争议且免费
- B. 用 N 个独立 master 多数派提升切换期安全，但受时钟漂移/GC 停顿质疑、成本高
- C. 就是单点锁
- D. 一定比 ZooKeeper 强一致

> 答案：B
> 解析：RedLock 提升安全性但非无懈可击；要 fencing/强一致应评估 CP 协调服务。

### 6. Cluster 下连接层对故障的处理是（6分）

- A. 直接抛异常不管
- B. 感知拓扑变更、自动重连，并做命令级重试（timeout/retryDelay/retryAttempts）
- C. 需要手工重启客户端
- D. 完全不重试

> 答案：B
> 解析：连接层会自愈（重连/重试/跟随 slot 迁移），但这只救"连接"，不等于"锁数据不丢"。

### 7. 绝大多数业务的互斥，推荐的默认方案是（6分）

- A. 一律上 RedLock
- B. 单节点锁 + 合理 TTL + 业务幂等/唯一约束兜底
- C. 不加锁
- D. 用本地 synchronized

> 答案：B
> 解析：单点锁性能最好且够用，正确性靠幂等/唯一约束兜底；强一致才升级到 RedLock/CP 方案。

### 8.（多选）hash tag 使用要注意的有（9分）

- A. 让逻辑相关、需原子操作的 key 同 tag
- B. tag 选得太粗会把热点集中到少数节点
- C. tag 随便乱加不影响性能
- D. `{}` 内的子串决定 slot 归属

> 答案：A、B、D
> 解析：C 错——粗粒度/不当 tag 会造成 slot 倾斜、热点集中；A/B/D 是正确用法与代价认知。

### 9.（多选）要提升"锁在故障切换下仍可靠"的可行手段有（9分）

- A. 关键处叠加幂等与 DB 唯一约束兜底
- B. 用带 fencing token 的 CP 协调服务(ZooKeeper/etcd)拒绝旧持有者
- C. 完全依赖看门狗续期
- D. 视业务安全要求评估 RedLock

> 答案：A、B、D
> 解析：C 错——续期不解决切换丢锁/脑裂双持；幂等兜底、fencing、按需 RedLock 才是可靠取向。

### 10. 在一个 Redis Cluster + 哨兵混合部署的秒杀系统里用 Redisson 加锁扣减库存，请从 slot/hash tag、主从切换丢锁、看门狗局限、可靠性选型四方面给出方案与兜底。（40分）

> 参考答案：
- 要点1：hash tag 归位——把同一商品的锁与库存 key 用相同 tag 钉到同 slot，让 Lua 原子扣减不因 CROSS_SLOT 失败，同时避免 tag 过粗致热点倾斜（10分）
- 要点2：正视丢锁窗口——主从异步复制下 master 切换可能丢失未同步的锁，不能假设单点锁跨故障仍唯一（10分）
- 要点3：看门狗局限——它只防"业务未完锁先过期"，网络分区/脑裂时仍可能双持，需外部兜底（10分）
- 要点4：分层兜底——默认单点锁 + 合理 TTL + 幂等消费 + DB 库存唯一/非负约束防超卖；安全要求高再评估 RedLock 或走 ZooKeeper/etcd 带 fencing（10分）
