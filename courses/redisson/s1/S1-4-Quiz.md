# 小测验 · 与 Lettuce 协同及分布式锁落地边界（关联）

> 本卷共 6 题，混合单选 / 多选 / 判断 / 填空 / 简答，满分 100 分折算百分制，≥ 60 分过关。

### 1. Redisson 与 RedisTemplate 读写同一个 key 出现乱码，首先应统一什么？（15分）

- A. Redis 版本
- B. 编解码器 Codec（如都用 StringCodec / JSON）
- C. 连接池大小
- D. key 的命名

> 答案：B
> 解析：Redisson 默认二进制/Jackson 编码，与 RedisTemplate 的 String/JSON 序列化字节不兼容，跨客户端共读的 key 必须对齐 codec；纯 Redisson 内部结构（锁）无此约束。

### 2. 以下哪种情况最不该用 Redis 分布式锁？（15分）

- A. 多实例抢跑同一个定时任务（纯互斥、秒级）
- B. 账户余额扣减要求终值绝对正确、不能重复
- C. 同一订单同一时刻只能被一个人改
- D. 保护一段短暂的临界区读改写

> 答案：B
> 解析：涉及"钱/终值正确性"必须靠 DB 唯一约束/乐观锁/事务，Redis 锁只给高概率互斥（主从切换丢锁、无 fencing），最多作前置降压，不能当正确性保证。

### 3. 【多选】关于分布式锁粒度与健壮性，正确的有？（20分）

- A. 锁 key 越具体越好：`lock:order:{id}` 优于全局 `lock:order`
- B. 用 `tryLock(waitTime, ...)` 有界等待，避免无限阻塞堆积
- C. unlock 前应判 `isHeldByCurrentThread()`，只解自己持有的锁
- D. 只要加了 Redis 锁，就不用再考虑幂等和 DB 约束了

> 答案：ABC
> 解析：D 错——锁挡不住绕过它的旁路/其它服务，也不保证绝对互斥，正确性仍需幂等 + DB 约束兜底。ABC 是锁落地的三条基本功。

### 4. 判断：热点 key 上加分布式锁能提升该 key 的并发吞吐。（10分）

- A. 正确
- B. 错误

> 答案：B
> 解析：锁本质是串行化，热点上加锁等于把并发打回单线程，越抢越慢；热 key 应走"打散/本地缓存/无锁结构"（redis s2-3）而非加锁。

### 5. 填空题：Redis 不可用时基于它的分布式锁会 ______，因此核心写路径要预留 ______（如降级到 DB 乐观锁 / 放行后对账），不能因拿不到锁就全线不可用。（20分）

> 答案：全部失效（无法加锁） / 降级路径

### 6. 用决策链回答："要不要上分布式锁"你问自己哪几个问题？（20分）

> 参考答案：
> - 是不是只有一个实例会执行？是 → JVM 锁即可，别引入 Redis 网络与故障面
> - 保护的是互斥还是数据终值正确？终值正确（钱/库存）→ DB 约束/乐观锁/原子 SQL，锁只降压
> - 纯互斥且临界区短（秒级）？→ Redisson RLock 合适
> - 临界区长/含跨系统副作用？→ 别长持锁，拆成 幂等 + 状态机 + 分布式任务调度
> - 收口：能不加锁就不加锁，锁是"高概率互斥的降压工具"，不是正确性与性能的银弹
