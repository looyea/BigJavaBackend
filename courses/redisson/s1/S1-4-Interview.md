# 实际面试题 · 与 Lettuce 协同及分布式锁落地边界（关联）

> 收录 2024—2026 国内中大厂 Java 后端真实面试，含追问链。考"锁的边界、什么时候不该用锁、锁挂了怎么办"。

## 题 1：什么时候不该用 Redis 分布式锁？

**期望时长**：90 秒

**答题要点**：

- 单实例/已按分片隔离 → JVM 锁足够，别引入 Redis 网络往返与故障面；
- 要求数据终值绝对正确（钱、库存）→ 靠 DB 唯一约束/乐观锁/原子 SQL，锁只能作前置降压；
- 热点 key → 加锁是串行化反而更慢，应打散/本地缓存；
- 长事务/跨系统副作用 → 用幂等 + 状态机 + 任务调度，不要长持锁。

**追问链**：为什么热点上加锁更慢？→ 锁把并发变串行，抢锁线程排队 + 每次加解锁都是 Redis RTT + Lua，QPS 反而低于无锁原子操作（DECRBY/乐观更新）。

## 题 2：Redisson 锁能替代数据库乐观锁保证不超卖吗？

**答题要点**：

- 不能当唯一保证：主从切换丢锁、GC 停顿过期、旁路直写 DB 都会让"以为持锁"的写穿过；
- 正确组合：Redisson 锁挡掉大部分无效并发（降压）+ DB 层 `stock>=?` 条件更新/唯一约束（保正确性）；
- 锁失效时最坏是并发上升，DB 条件更新仍兜住不超卖。

**追问链**：那还要 Redis 锁干嘛？→ 性能：DB 乐观锁高冲突下大量失败重试很贵，前置一把 Redis 锁把同一资源的并发压成低并发，减少 DB 无效竞争——是"优化"不是"正确性来源"。

## 题 3：Redis 挂了，你们的分布式锁和业务怎么办？

**答题要点**：

- 锁全部不可用（连不上就加不了锁）→ 必须预先设计降级：拿不到锁走 DB 乐观锁兜底 / 有限放行 + 事后对账；
- 不能"拿不到锁=业务全线 500"；
- 可用性取舍：Redis 锁天然 AP 倾向，接受极端情况的小概率失效，用幂等消化。

**追问链**：能避免吗？→ 用 RedLock 多节点降低单点（仍有争议，见 s1-2）；对强一致场景改 CP 系统；但工程上"锁 + 降级 + 幂等 + 对账"的组合远比追求"绝对不丢锁"更现实。

## 题 4：Redisson 和 Lettuce/Spring Data 能共存吗？要注意什么？

**答题要点**：

- 能，且是推荐分工：缓存读写 Spring Data(RedisTemplate/Lettuce)，协调 Redisson；
- 两条注意：① 跨客户端共读的 key 必须统一 codec（否则乱码/WRONGTYPE）；② 两套 Netty 连接各自独立，纳入总连接数核算。

**追问链**：同一 key 一个用 RMap 一个用 HGET 为什么读不出？→ RMap 默认二进制编码 field/value，与 HGET 的裸串字节不兼容；共读就统一 StringCodec，或干脆约定一类数据只由一个框架管。

## 题 5：设计"防重复提交"，用分布式锁是最优解吗？

**答题要点**：

- 防重本质是"同一请求只处理一次"→ 首选**幂等**（唯一请求号 + DB 唯一索引 / Redis SETNX 令牌一次性消费），而非"锁住一段时间"；
- 锁防重有窗口问题（leaseTime 内放行、过期后重复）；幂等键天然精确到"这一次"；
- 锁适合"防并发"，幂等适合"防重复"，二者语义不同。

**追问链**：SETNX 令牌防重和锁区别？→ 防重令牌是"用完即焚、不释放、只认这一枚"（一次性）；锁要释放、保护一段临界区。防重更轻、无续期问题，是幂等专区（idempotent）的核心手段。
