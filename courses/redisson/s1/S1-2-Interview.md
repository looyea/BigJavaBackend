# 实际面试题 · RedLock 争议与读写锁/信号量/闭锁

> 收录 2024—2026 国内中大厂 Java 后端真实面试，含追问链。考"RedLock 原理与争议、Redisson 其它同步器、分布式锁选型"。

## 题 1：讲讲 RedLock 的算法，它解决了什么？

**期望时长**：90 秒

**答题要点**：

- 解决单主锁"主从异步复制 → 切主丢锁"问题；
- 算法：向 N 个（常取 5）**完全独立**的 Redis 实例依次加锁（带 TTL），统计成功数；
- 成功条件：**过半加锁成功** 且 **总耗时 < 锁的 leaseTime**，否则全部释放、退避重试；
- 效果：要破防需多数节点同时宕机/丢数据，可用性远高于单主。

**追问链**：为什么强调"独立实例"而不是主从？→ 主从是一个数据副本，主挂从没同步到就一起丢锁，等于没加固；独立性是红锁容错的前提。

## 题 2：RedLock 的争议你怎么看？该不该用？

**答题要点**：

- Kleppmann 质疑：锁靠超时判持有，**GC 停顿/时钟漂移/NTP 跳变**会让持锁者醒来时锁已过期却以为仍持有 → 无 fencing token → 互斥被破；红锁不能免于此。
- antirez 回应：属误读，且任何系统在极端故障模型下都不绝对安全，红锁假设时钟/进程大致正常。
- 工程判断：红锁显著**降低概率**但不是绝对互斥；效率锁场景单主 RLock+幂等即可，正确性锁上 CP 系统/fencing。

**追问链**：什么是 fencing token？→ 每次加锁发一个单调递增号，写操作带上它，资源侧只接受号不小于当前已见的最大值的请求 → 旧持锁者 GC 醒来用旧号写被拒。Redis 原生锁难提供可靠单调号，是它做不到的关键。

## 题 3：Redisson 读写锁和可重入锁有什么结构差异？

**答题要点**：

- `RReadWriteLock`：读锁用 Hash 记录**每个读者的重入数**（读读共享），写锁独占一个 field；有写锁持有时读者等待。
- 与纯 `RLock` 区别：后者无论谁都要独占互斥；读写锁提升"读多写少"并发。
- 均可重入、均受看门狗管理。

**追问链**：写锁会饿死吗？→ 持续有读者进入可能推迟写者；Redisson 提供公平读写锁（FIFO 队列）缓解，或用 `RFairLock`。

## 题 4：分布式信号量比单机 Semaphore 强在哪？怎么防止许可泄漏？

**答题要点**：

- 许可计数存在 Redis，**跨所有 JVM/节点**共享 → 真正限制"整个集群"的并发数（单机 Semaphore 只限本进程）。
- 防泄漏：`tryAcquire(timeout)` + `finally release()`；持许可进程崩溃时靠 Redisson 的租期/看门狗机制回收。

**追问链**：拿 `RSemaphore` 做限流和 `RRateLimiter` 有何不同？→ 信号量限"同时在跑的并发数"，RRateLimiter 限"单位时间通过速率（令牌桶）"——一个控并发、一个控频率（见 s1-3）。

## 题 5：金钱/账户扣减这类强正确性场景，你的分布式锁方案是？

**答题要点**：

- 不选纯 Redis 锁（含红锁）当唯一保证；
- 用 **CP 协调服务（ZooKeeper/etcd）+ fencing token**，或直接落到**数据库层**（唯一约束、`SELECT FOR UPDATE`、串行化事务、余额字段乐观锁 version）；
- Redis 锁至多作为"前置效率锁"减少无效并发，最终一致靠 DB + 幂等 + 对账。

**追问链**：只用一张订单表唯一索引能当锁吗？→ 对"同一笔只能成功一次"的幂等场景可以（插入冲突即失败），这正是"用存储层约束替代分布式锁"的典型——简单且强一致，比 Redis 锁更可靠。
