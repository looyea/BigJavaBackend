# 实际面试题 · RLock 可重入锁与看门狗续期

> 收录 2024—2026 国内中大厂 Java 后端真实面试，含追问链。考"Redisson 分布式锁原理、看门狗、和手写锁的差异"。

## 题 1：Redisson 分布式锁的底层实现原理？

**期望时长**：90 秒

**答题要点**：

- 锁在 Redis 里是一个 **Hash**：field=`uuid:threadId`（标识持有者）、value=重入次数；
- 加锁/重入/释放/设过期全部用 **Lua 脚本**在服务端原子执行（一次 RTT 完成判断+写入，杜绝竞态）；
- 等锁不轮询：拿不到时订阅解锁通知（**Pub/Sub**），被唤醒再抢；
- 释放靠 `unlock` 计数减到 0 删 key + 发布通知；异常路径用 finally 保证解锁。

**追问链**：为什么用 Hash 不用 String？→ 要同时表达"谁持有 + 重入几层"，String 只能存一个值；Hash 的 field 精确到线程才能既支持同线程重入又阻止跨线程冒领。

## 题 2：什么是看门狗？解决什么问题？

**答题要点**：

- `lock()` 不传 leaseTime 时启用：锁默认 30s，后台定时任务每 **10s（TTL/3）** 检查线程是否仍持有，是则 `PEXPIRE` 续回 30s；
- 解决两难：① 业务没跑完锁就过期（失锁并发）；② 持锁进程宕机锁永不释放（死锁）——看门狗续期依赖进程存活，进程一挂自然到期。

**追问链**：`lock(10, SECONDS)` 还有看门狗吗？→ 没有。显式 leaseTime 表示你自担超时，到点无条件释放；若业务超过 10s 就会锁提前失效，这是常见事故。

## 题 3：Redisson 锁能可重入是怎么做到的？

**答题要点**：

- 同一线程再次 `lock()` → Lua 判断 `hexists field` 命中自己 → `hincrby +1`，不阻塞；
- `unlock()` → -1，>0 不删、==0 才 `del` 发通知；
- field 里的 `uuid`（RedissonClient 实例标识）+ `threadId` 共同定位"哪个进程的哪个线程"。

**追问链**：为什么 field 还要带 uuid 不只 threadId？→ 不同 JVM 里 threadId 可能相同，加实例 uuid 保证全局唯一，避免跨进程误判为同一持有者可"重入"别人的锁。

## 题 4：持锁线程所在服务被重启，锁会怎样？

**答题要点**：

- 进程死 → 看门狗停 → 锁不再续期 → 最多 30s（无 leaseTime 默认）后 TTL 到期自动释放；
- 若是显式 leaseTime，则按其剩余时间到期释放；
- 结论：不会永久死锁，但**重启期间临界区可能只执行了一半**——业务侧要靠幂等/事务补偿，不能假设锁保一切。

**追问链**：能缩短这个空窗吗？→ 调小 `lockWatchdogTimeout`，或改用带 leaseTime 的 lock（但要覆盖最坏耗时）；根本解法是缩短临界区 + 操作幂等。

## 题 5：Redisson 单点 RLock 在高可用场景有什么隐患？怎么缓解？

**答题要点**：

- 主从架构下，锁在 master 加成功、还没同步到 replica 时 master 宕机 → 新主上没有这把锁 → 另一客户端能重复加锁（**异步复制丢锁**）；
- 缓解：① RedLock 多独立节点过半加锁（s1-2，但有争议）；② failover 容忍期 + 业务幂等；③ 对正确性极端要求的可改用基于一致性协议的方案（ZooKeeper/etcd）或数据库唯一约束。
- 认知：Redis 锁是"尽力互斥"，不是强一致保证。

**追问链**：那到底该不该上 RedLock？→ 视 Martin Kleppmann 的批评（GC 停顿/时钟漂移仍可能失锁），多数业务用"单主 Redisson 锁 + 幂等 + fence token"更实际；RedLock 增运维成本且非银弹，别把它当正确性兜底。
