# 网格的延迟/资源成本与何时不用（关联） · 作业

## 作业 1：网格开销实测

**目标**：拿到自己环境的第一手增量数据，而非引用网传数字。

1. kind/minikube 部署一对 httpbin 服务，先基线压测（hey/wrk 直连 Service），再注入 istio sidecar 复测，记录 RPS、P50/P99 对照表（输出：两组数据）。
2. `kubectl top pod` 采集 sidecar 容器自身 CPU/内存稳态值，×500 Pod 折算集群底租（说明：给出计算过程）。
3. 把 sidecar limits 调成 50m 重压一次，观察 P99 突变——记录 CFS 节流证据（错误用例体验：`kubectl exec ... cat /sys/fs/cgroup/cpu.stat` 的 nr_throttled）。

## 作业 2：协议适配性 PoC

**目标**：验证"主力协议在网格下还剩多少收益"。

1. 部署一个 Dubbo（或自定义 TCP 协议）服务对入网格，检查 Envoy 指标里的分类：是 tcp 还是 dubbo 维度（验收：截图证明 L7 统计缺失）。
2. 对照同流量的 HTTP gRPC 服务，列一张"L7 能力可得性矩阵"（路由/重试/熔断/mTLS/黄金指标 × 协议）。
3. 结论段：如果你的技术栈以该协议为主，网格还值不值，写出取舍。

## 作业 3：不用网格的替代架构设计

**目标**：为"5 人团队 + 30 个 Java 服务 + 全 K8s"设计无网格方案。

1. 画出东西向治理责任分配：重试/熔断/超时（resilience4j）、TLS（cert-manager+库内配置）、追踪（OTel javaagent）、指标（micrometer），每项一句话说明落地物（结果：一页 ADR）。
2. 与网格方案对比成本：机器钱、人力钱、演进灵活性三栏打分表。
3. 写出"何时反悔"条款：出现哪三个信号（如多语言接入>3 种、合规要求统一 mTLS、灰度需求爆发）时应重启网格评估。
