# 网格的延迟/资源成本与何时不用（关联） · 面试题

## 题 1：服务网格的代价是什么？怎么量化？

- 延迟：每跳经 sidecar 进出（socket+iptables 重定向+转发决策+TLS），均值约 0.5~2ms，但连接 churn、CPU 节流、证书轮转在 P99 放大（异常表现：均值没变、尾延迟恶化）。
- 资源：每 Pod 一个 proxy 底租（0.1~0.5 核/几十~150Mi），乘以规模就是几十核账单；控制面 istiod 本身也要常驻冗余。
- 复杂度：故障面新增（注入时序、sidecar CrashLoop、xDS 推送）、团队学习成本。
- 量化方法论：自己环境 PoC 压测对照（协议要选生产主力协议）、`kubectl top` 折成本、故障演练爆炸半径——引用他人基准只能当量级参考。

## 题 2：你们用了 istio，延迟增加多少？怎么优化？

- 报数姿势：HTTP 东西向 P50 +0.3~0.5ms、P99 +1~3ms（含灰度期调优前后对比），并说明测试协议与机型量级，避免"绝对值背书"。
- 优化组合拳：①按需注入（批处理/心跳类关闭，缩小面）；②sidecar 资源给足并压测验证防节流；③长连接服务开 L7 感知或调连接池；④裁剪不用的策略/遥测（accessLog 采样、指标 tag 精简——错误做法：全量访问日志打满 stdout 拖慢节点）。
- 终局选项：Ambient 模式把常驻 sidecar 换成节点级 ztunnel+按需 waypoint，底租明显下降（说明：演进方向要报得出）。

## 题 3：Istio 和 Linkerd 怎么选？

- 功能广度：istio 全家桶（L7 路由、东西向网关、策略即代码、多协议），Linkerd 克制（透明代理+mTLS+黄金指标）。
- 成本：linkerd Rust 代理底租与尾延迟普遍更低、装完即用；istio 需要平台团队消化复杂度。
- 决策线：多语言大平台/需要精细流量工程→istio；纯 K8s、Java/Go 为主、人少求稳→linkerd；都不用网格的条件见下一题（结果：答案没有标准件，只有约束匹配）。

## 题 4：什么情况下你会明确建议"不要上网格"？

1. 延迟敏感核心链路（撮合、支付授权）——每跳毫秒比治理能力更值钱。
2. 团队无平台工程承接——网格是新分布式系统，出了故障没人能看懂 Envoy debug 端口。
3. 协议栈以私有 TCP 为主——L7 收益拿不到，只剩 mTLS+TCP 指标，用更轻手段可得。
4. 非 K8s/虚机存量、或规模太小（几十个服务）——边际收益覆盖不了底租与心智成本。
- 加分：说得出替代架构（网关+SDK 容错+库内 TLS+OTel），证明"不上"是选择而非逃避。

## 题 5：已经上了网格想退，怎么安全下车？

- 盘点耦合：哪些能力被网格承担（mTLS、重试、灰度），退网格后谁接——先建替代再拆（错误做法：直接关注入，mTLS STRICT 的对端立刻连不上）。
- 路径：按 ns 反向摘除（先无状态边缘服务，后核心），每步观察错误率/延迟回归；证书与流量策略回迁到应用配置需一轮发布窗口。
- 兜底：保留 ControlPlane 与 istiod 一段时间只做观察不接管（PERIODIC mTLS 过渡），全量验证后删 CRD（结果：下车也要演练，比上车更考验纪律）。

## 题 6：Ambient Mesh 解决了什么，没解决什么？

- 解决：每 Pod sidecar 的底租与注入侵入性——节点级 ztunnel 做 L4 mTLS+路由，内核 eBPF 引导流量，无 CNI 特例（说明：数据面从 N 个代理变每节点 1 个）。
- 部分解决：L7 能力改为按需 waypoint（要 HTTP 路由/可观测的服务再拉一层代理）——不用 L7 的确实省了，用了的延迟只是换了位置。
- 没解决：istio 生态复杂度（CRD/版本演进）、策略即代码的学习成本、以及"网格值不值"这个根本问题（异常预期：把它当纯性能补丁上，收益却按全功能算——决策要分开）。
