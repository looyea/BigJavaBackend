# 五种 IO 模型与同步/异步、阻塞/非阻塞 · 面试题

> 这是 Netty/高并发的开场必答题。区分层次：能背五模型只是及格；把"两阶段、两维度"讲清、说透 select→epoll 的必然、解释"Linux 为什么不用网络 AIO"才是进阶。

## 考点 1：阻塞/非阻塞 vs 同步/异步（最容易答混）

**起手**：阻塞 IO 和同步 IO 是一回事吗？

**期望**：
- 不是一回事，是两个维度。以"一次 `read`"为例，内核视角分**两阶段**：① 等数据就绪（wait for data）② 内核把数据从内核态拷贝到用户态缓冲区（copy）。
- **阻塞/非阻塞**看**阶段①**：阻塞线程傻等到数据就绪才返回；非阻塞没数据立刻返回 `EAGAIN`/0。
- **同步/异步**看**阶段② + 完成通知**：同步 = 拷贝由调用线程自己完成（`read` 返回时数据才就绪）；异步 = 拷贝由内核做，做完再回调/通知（如 AIO `Future`）。

**追问链**：
1. 那 IO 多路复用（select/epoll）算哪种？→ **同步非阻塞**：`epoll_wait` 本身可阻塞，但对"就绪 fd 之后的 read"是非阻塞的；数据拷贝仍由你同步做，所以是同步。
2. 信号驱动（SIGIO）呢？→ 也**同步**：内核信号通知"可读了"，但拷贝还是要你自己 `read`。

## 考点 2：五种模型串讲 + 各自代价

**起手**：按演进顺序讲五种 IO 模型。

**期望**：
1. **BIO（同步阻塞）**：一连接一线程，简单但连接数=线程数，上下文切换与栈内存打爆。
2. **非阻塞轮询**：`read` 返回 `EAGAIN` 就重试，纯浪费 CPU。
3. **IO 多路复用（同步非阻塞）**：一个线程用 `select/poll/epoll` 同时监听很多 fd，就绪才处理 —— 后端高并发主流。
4. **信号驱动**：SIGIO 通知就绪，仍要自己读，用得少。
5. **AIO（真异步）**：内核完成拷贝后回调，理论最省线程。

**追问链**：
1. 多路复用一个线程为什么能扛上万连接？→ 连接与线程解耦，空闲连接只占内核 fd + interest 记录，不占线程。
2. 那既然多路复用够用，还要 AIO 干嘛？→ 见考点 4，网络 AIO 在 Linux 上不成熟。

## 考点 3：select / poll / epoll 三兄弟差异

**起手**：为什么说 select 有性能问题，epoll 改了什么？

**期望（select 三痛 → epoll 三改）**：
- 痛 1：`FD_SETSIZE` 默认 1024 上限 → epoll 用 `epoll_create` 建内核事件表，上限只受 fd 总数限制。
- 痛 2：每次调用把整个 fd 集合**用户态→内核态全量拷贝** → epoll 用 `epoll_ctl` **注册一次**、常驻内核红黑树。
- 痛 3：返回后要 **O(n) 遍历**才知道谁就绪 → epoll 用就绪链表，`epoll_wait` **只返回就绪的 fd**，成本 O(活跃)。
- poll 只解决了"1024 上限"（用链表），没解决全量拷贝与 O(n) 扫描。

**追问链**：
1. 连接很多但活跃很少，谁优势最大？→ epoll（O(活跃) vs O(总)）。
2. epoll 一定比 select 快吗？→ 连接少且都活跃时差距很小，epoll 还多了 `epoll_ctl` 维护成本；差距在规模化时显现。

## 考点 4：LT vs ET + AIO 的真相（送分/送命题）

**起手**：水平触发和边缘触发区别？Netty 用哪个？

**期望**：
- LT（水平）：只要缓冲区"非空/可写"就一直通知 → 好写、不怕漏读。ET（边缘）：只在状态**跳变**时通知一次 → 必须一次性读到 `EAGAIN`，否则剩余数据要等下次跳变，可能永久卡住；省唤醒次数。
- **Netty = LT**（健壮、跨平台一致，Windows JDK 只有 select 语义）；**Nginx = ET**（极致性能、愿意手写复杂逻辑）。

**起手 2**：既然 AIO 是真异步，为什么 Netty 主推 epoll 而不是 AIO？

**期望**：
- **Linux 的网络 AIO 名不副实**：早期 JDK `AsynchronousSocketChannel` 在 Linux 上其实**用 epoll 线程池模拟**；POSIX `aio_read`/`io_submit` 对**普通磁盘文件**较成熟，对**socket** 支持很差（很多退化为阻塞）。所以 Netty 长期主推 **native epoll transport**，`AioSocketChannel` 已标记废弃。
- 磁盘才是真异步（AIO/io_uring）的主场。新变量 **io_uring**（网络+磁盘统一异步）Netty 已有 transport，但生产主流仍是成熟的 epoll。
- 加分：能说出"异步听起来更快，但对 CPU 密集的短任务，多路复用的同步模型反而更快（省队列/回调/线程切换开销）"。

## 考点 5：落到选型（架构视野收尾）

**期望**：
- 事实标准 = **IO 多路复用（epoll）+ Reactor 线程模型**，Netty 就是这条路。
- 选型直觉得说得出：海量空闲长连接 → 必须多路复用；连接少、任务重、图省事 → 线程池 + BIO 也未必不行；对**磁盘大吞吐**才考虑 io_uring/AIO。
- 别用"同步=慢、异步=快"这种一句话结论糊弄 —— 讲清两阶段两维度才是理解的正确打开方式。
