# 分布式主键、读写分离与弹性迁移 · 面试题

## 题 1：Snowflake 的位结构？为什么"趋势递增"重要？

1 符号位 + 41 位毫秒时间戳（约 69 年）+ 10 位 worker-id + 12 位同毫秒序列（单毫秒 4096 个）。趋势递增让 InnoDB 主键 B+ 树永远在最右页追加，页分裂率接近零；随机主键（UUID）让每次插入都可能在树中间分裂，实测写放大 2~3 倍且二级索引跟着膨胀。

## 题 2：worker-id 在容器化环境怎么保证唯一？

不可变原则：StatefulSet 序号、Downward API + 配置中心登记租约、或号段中心统一分配。反例：Deployment 随机取/用 Pod IP 哈希——重启换 IP、哈希可撞，两个实例同 id 同毫秒就撞号，且冲突发生在生产低峰期最难排查。追问"回拨"必答：等待追平 + 超阈值停发告警。

## 题 3：有了读写分离规则，为什么还要 HintManager？

规则的粒度是"全局/事务级"，而业务需要**点状**的强一致：下单成功后立刻跳订单详情，这条读不在事务里、又不该读从库。HintManager 在代码里对该查询强制主库路由，作用域最小；比"为个别场景把全局改成读主"（吞吐坍塌）精确得多。反过来滥用 Hint 把大量查询钉在主库，等于把读写分离白装了——两者要配审计。

## 题 4：在线扩容为什么强调"双写+校验"而不是停机迁移？

停机窗口业务不可接受，且大表 COPY 的时间估算常失真（10 倍误差）。双写把"新旧一致"变成可持续维护的状态：每次写都落到两边，校验闭环保证差异可见可修；切读切写按流量灰度推进，每步可回退。风险点要主动讲：双写期间新库写失败必须进补偿队列+告警，漏写比不一致更致命。

## 题 5：分库分表 + 读写分离叠加后，一个 SELECT 的路由决策顺序？

先看 Hint（强制）→ 事务中？→ 读写分离规则（主/从）→ 分片算法（库/表）→ 改写执行。追问"从库上还有分片吗"：每一片都有自己的主从组，两个维度是正交的矩阵（4 分片 × 每组一主两从 = 12 个连接目标），面试画图说清即加分。
