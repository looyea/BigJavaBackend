# 实际面试题 · 原生镜像原理与限制

## 题 1：GraalVM 原生镜像为什么启动那么快、内存那么省？

**考察层次**：初级只会说"AOT"；中级能讲可达性分析与死代码消除；高级能说出代价（峰值、构建、metadata）与选型边界。

**参考答法**：

1. **AOT**：构建期就把字节码静态编译成本机机器码，运行不再需要解释器 + JIT 编译器预热，上来就是机器码 → 冷启动毫秒级。
2. **可达性分析 + 死代码消除**：从 root 做封闭世界静态分析，只把可达的类/方法/字段编进镜像，产物紧凑。
3. **精简运行时 SubstrateVM**：只带最小 GC/线程等，没有完整 JVM 的解释器、C1/C2、元空间等 → 常驻内存显著下降（常 3~10×）。

**追问**：那它一定比 JVM 快吗？→ 不一定。**启动/内存**占优，但**峰值吞吐**常不如 JIT，因为 AOT 拿不到运行期真实 profile、不能动态去优化。

## 题 2：什么是封闭世界假设？它带来哪些坑？

**答题要点**：AOT 要求"构建期能确定运行期所有会执行的目标"，故做静态可达性分析并丢弃不可达代码。坑在于 Java 的动态特性破坏它：反射（`Class.forName` 目标分析看不到）、JDK 动态代理、`getResourceAsStream`、序列化、注解扫描、JNI、动态类加载——运行期需要"被丢弃的东西"就抛 `ClassNotFoundException`/NPE/找不到资源。

## 题 3：这些坑怎么解？Spring 又做了什么？

**结构化回答**：

1. 根解：**reachability metadata** —— `reflect-config.json`/`proxy-config.json`/`resource-config.json`/`serialization-config.json`，告诉分析器"这些必须保留"。
2. 手写易漏难维护。**Spring AOT 引擎**在构建期（`process-aot`）扫描已知 Bean、`@Configuration`、序列化/反射用法，**自动生成** metadata。
3. 开发者用 **`RuntimeHints`/`RuntimeHintsRegistrar`** 为第三方反射/资源点手动补充。
4. 心智：Boot 的 native 支持不是语法糖，本质是"给封闭世界补可达性"（打包实践见 spring-boot s3-2，原理在本节）。

## 题 4：什么服务该上原生镜像，什么别上？

**答题要点**：该上——Serverless/函数计算、CLI、需要秒级弹性扩容、按量计费或内存密度敏感的短生命周期容器，核心 KPI 是冷启动与内存。别上/慎上——长驻、高吞吐、JIT 预热后跑很久的核心服务（丢峰值性能、收益不明显），以及重度反射/动态代理/字节码增强且无原生支持的库（metadata 维护成本高于收益）。还要权衡构建慢、版本强绑定、可观测工具受限。

## 题 5：原生镜像和虚拟线程是同一类优化吗？

**答题要点**：不是，方向正交。**原生镜像**优化的是**启动时间与内存占用**（AOT/封闭世界路线）；**虚拟线程**优化的是**高并发吞吐**（便宜的大量阻塞任务挂起/恢复，呼应 spring-boot s3-1）。二者可叠加使用。选型的正确姿势是先问"瓶颈是冷启动/内存，还是并发吞吐"，再决定上哪条或两条都上。

## 高频追问速答

1. 原生镜像就没有 JIT 了吗？→ 运行期没有 JIT 层；但有 PGO（profile-guided AOT，基于采样 profile 再编译）弥补部分优化。
2. GC 能选吗？→ 有限，主要 Serial 与 G1，选项比完整 JVM 少。
3. 构建为什么慢？→ 可达性分析（points-to）+ AOT 编译 + 单线程分析阶段，吃内存 CPU。
4. Windows 构建需要什么？→ Visual Studio C++ Build Tools（链接原生代码）。
5. 调试怎么办？→ `-g` 保留调试信息 + GDB/IDE 远程调试；JFR/部分 profiler 支持有限。
