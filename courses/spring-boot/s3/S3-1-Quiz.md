# 小测验 · 虚拟线程与高并发改造

> 共 5 题，合计 100 分，≥ 60 分过关。

### 1. 虚拟线程主要解决的核心问题是？（20分）

- A. 让 CPU 计算变快
- B. 让"一个请求一个线程"的阻塞模型在高并发 IO 等待下不再受限于稀缺的 OS 线程
- C. 完全取代 GC
- D. 消除所有锁竞争

> 答案：B
> 解析：虚拟线程是用户态轻量线程，阻塞时从承载线程卸载，用同步写法拿到接近异步的吞吐。

### 2. Boot 3.2+ 设 `spring.threads.virtual.enabled=true` 后，最直接的变化是？（20分）

- A. 自动把所有 SQL 改写成异步
- B. Web 容器请求处理与默认 `@Async` 执行器切换到虚拟线程模型
- C. JVM 堆大小自动翻倍
- D. 关闭了 Tomcat

> 答案：B
> 解析：它切换的是平台默认线程模型（容器请求线程、SimpleAsyncTaskExecutor 等），不改写业务逻辑。

### 3.（多选）下面哪些是开启虚拟线程后需要警惕的坑？（25分）

- A. 海量虚拟线程冲垮固定大小的数据库连接池
- B. `synchronized` 块内阻塞会钉住（pin）承载线程
- C. 大量使用 ThreadLocal 导致内存被放大
- D. 虚拟线程无法调用任何 HTTP 接口

> 答案：ABC
> 解析：D 错，虚拟线程能正常调用；ABC 是三类真实边界（有限资源、pinning、ThreadLocal 放大）。

### 4. 一个服务以序列化与矩阵计算为主（CPU 密集），开虚拟线程的预期收益是？（15分）

- A. 吞吐大幅提升
- B. 基本无收益，甚至因调度开销略降
- C. 内存骤降
- D. 延迟归零

> 答案：B
> 解析：虚拟线程的收益在 IO 等待密集场景；CPU 密集没有阻塞可让出，帮不上。

### 5. 存量阻塞式高并发服务想提升吞吐，在"虚拟线程 vs WebFlux"之间一般怎么选？（20分）

- A. 一律重写为 WebFlux
- B. 优先用虚拟线程（低成本、保留阻塞写法）；本就是响应式或需精细背压才用 WebFlux，且二者不混用
- C. 两个都开
- D. 都不开，加机器

> 答案：B
> 解析：虚拟线程迁移成本极低、代码不变；WebFlux 需全链非阻塞、改造重。别混用。
