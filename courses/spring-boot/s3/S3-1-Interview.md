# 实际面试题 · 虚拟线程与高并发改造

## 题 1：虚拟线程和平台线程、和线程池，本质区别是什么？

**考察层次**：初级答"更省内存"；中级能说 unmount/mount 与调度；高级能讲清它改变的是并发模型哲学。

**参考答法**：

1. 平台线程 1:1 映射 OS 线程，昂贵、数量有限；线程池是为了复用稀缺线程而做的妥协。
2. 虚拟线程是 JVM 调度的用户态线程，挂在少量承载线程（ForkJoinPool）上；阻塞时 unmount 让出承载线程，就绪后再 mount。
3. 因此你不再需要"用池限制并发来省线程"——可以大胆一个任务一个虚拟线程，回到"每请求一线程"的直观模型。
4. 但**池的第二个作用——限制对有限资源的并发——不会消失**，那是信号量/连接池的活儿，不能靠"少开线程"来实现。

**追问**：那虚拟线程时代还要线程池吗？→ 作为"并发限流器"的语义仍需要（换成信号量/Bulkhead），作为"线程复用"的语义基本不需要了。

## 题 2：Boot 里开虚拟线程怎么开？开了就万事大吉？

**答题要点**：

- `spring.threads.virtual.enabled=true`（Boot 3.2+），切换 Web 容器请求线程、`@Async` 执行器等默认线程模型。
- 不是万事大吉：要看服务是不是 IO 密集；要看连接池/下游能否扛住被放开的并发；要查 `synchronized` pinning 与 ThreadLocal 滥用。
- 需要配套：资源处并发上限、观测承载线程与 pinning 指标、灰度验证。

## 题 3：上了虚拟线程后数据库被打挂了，怎么回事？

**结构化回答**：

1. 现象归因：以前并发被平台线程数"隐式限流"，现在虚拟线程可海量并发，瞬间把连接池/DB 连接数打满，排队超时甚至压垮 DB。
2. 定位：看连接池等待时间、活跃连接、DB 侧连接数与慢查询。
3. 修复：在访问 DB 的路径加并发闸门（信号量/Bulkhead），把该资源并发限到连接池能承受的值；必要时扩池但要评估 DB 上限。
4. 观念纠正：并发控制的职责从"线程池大小"迁移到"资源级限流"，这是架构师必须传达给团队的认知转变。

## 题 4：什么场景不该用虚拟线程？pinning 是什么？

**答题要点**：

- CPU 密集型（计算、编码、压缩为主）没多少阻塞可让出，收益低甚至为负。
- 需要极强、精细背压控制的流式管道，WebFlux 更合适。
- pinning：虚拟线程在 `synchronized` 块内（或某些本地调用中）阻塞会把承载线程钉住，退化为占用 OS 线程，削弱扩展性；热点路径用 `ReentrantLock`，JDK 持续在改进。

## 高频追问速答

1. 虚拟线程会取代 WebFlux 吗？→ 大部分"为提并发而被迫写响应式"的场景可以被虚拟线程替代；但既有响应式资产与背压需求仍成立。
2. `@Async` 上虚拟线程要注意什么？→ Boot 开关系后默认执行器变为每任务虚拟线程，不再池化；如需限并发要显式配执行器/信号量。
3. 虚拟线程会影响 GC/内存吗？→ 数量巨大时其栈与关联对象增多，配合 ThreadLocal 更易内存膨胀，需审计。
4. 怎么确认真的用上了虚拟线程？→ 线程名/`Thread.currentThread()` 判断、`jcmd Thread.print` 看承载线程数是否远低于并发数、压测吞吐变化。
5. 生产现在就上吗？→ JDK 21+ 且 Boot 3.2+，IO 密集、有灰度与限流配套时上；先小流量验证收益与副作用。
