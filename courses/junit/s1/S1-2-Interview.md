# 参数化、动态与重复测试 · 面试题

## 题 1：参数化测试比把循环写进 @Test 好在哪？

- 每组数据是独立用例：失败定位到具体数据行、单组失败不阻断其余组、报告天然形成需求矩阵可评审；
- for 循环版本首个失败即抛出，后面的数据根本没跑，且 CI 报告只有一个方法名，排查靠加日志；
- 加分：能提 name 模板（`[{index}] {0}`）让报告可读、参数化与 @Nested 组合还能表达"维度 × 场景"的矩阵结构。

## 题 2：@CsvSource 和 @MethodSource 怎么选？CSV 有哪些坑？

- 简单标量、少量列用 @CsvSource 内联快；需要复杂对象、null 语义、类型安全时升级 @MethodSource（返回 Stream\<Arguments\>，编译期检查）；
- CSV 坑：逗号/引号转义、默认空串即 null 造成歧义（用 nullValues 显式声明占位符）、超长表可读性差（挪 @CsvFileSource 外置）；
- 加分：指出 @MethodSource 方法必须静态（除非 PER_CLASS），且按方法名字符串关联——重构改名时 IDE 不会帮你改注解里的字符串，是常见 CI 炸点。

## 题 3：@RepeatedTest 和参数化测试的本质区别？什么时候用重复？

- 参数化=不同输入验证数据覆盖面；重复=同一输入跑 N 轮验证稳定性——抓幂等破坏、随机分支漏测、并发时序类偶发 bug；
- 典型场景：带随机路由的策略类每轮走不同分支、缓存刷新在重复调用下是否始终一致；
- 加分：能区分"重复测试"与"多线程并发压"——重复默认串行同实例语义验证，并发安全要靠 Executor 显式构造。

## 题 4：什么样的需求必须用 @DynamicTest / @TestFactory？它有什么代价？

- 用例的名称与条数在运行期才能确定：扫描目录、查询数据库、解析外部配置清单；
- 代价：动态用例没有独立生命周期（@BeforeEach 只跑一次）、不能被 @Disabled/@Tag 单独过滤、静态发现工具（IDE 树/某些 CI）看不到用例列表；
- 加分：给出折中——需要逐条可控时把"取数"提前到固定枚举或用参数化 + 外部文件；TestFactory 返回 Stream 时记得惰性求值可控制内存。

## 题 5：参数化测试怎么和并行执行协作？有什么注意点？

- JUnit 5.3+ 可开模块级并行（junit.jupiter.execution.parallel.enabled=true），参数化产生的每条用例是独立可执行单元，天然可并行；
- 注意：PER_CLASS 或共享可变数据源（如同一个 List 提供参数）会引入竞争；数据集本身要保证无副作用、只读；
- 加分：提到 `@Execution(CONCURRENT)`/`NOT_CONCURRENT` 方法级控制，以及参数工厂方法在并发下可能被多次调用——昂贵资源应放 @BeforeAll 或单例容器而非每条参数构造。

## 题 6：面试官追问"你们团队参数化测试的数据表怎么维护？"怎么答出工程化水平？

- 分层：逻辑边界值进 @MethodSource（与代码同源评审）、业务规则矩阵外置 @CsvFileSource/资源文件（BA 可改），命名规范要求失败信息可追溯到规则编号；
- 防退化：把"新增状态必须补迁移表"写进 PR 检查清单，或再加一条动态测试校验矩阵完备性（枚举数与表行数一致）；
- 加分：用聚合报告看参数化用例的通过率分布，识别"某列数据长期全过"的死用例并定期清理——测试资产也需要债务管理。
